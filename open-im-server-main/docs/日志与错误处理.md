# 日志与错误处理规范

本文说明本项目 Go 代码中的日志（`Logger` 接口）与错误处理（`CodeError` 接口）约定：各自的作用、关键方法以及在什么场景下使用。

> 说明：本文档由上游 OpenIM 英文文档译出，并结合本项目的实际使用方式做了整理。脚本类日志规范不属于本文范围。

## 一、日志（`Logger` 接口）

### 作用

`Logger` 接口为项目提供统一、灵活的日志机制，支持结构化日志，便于日志的集中管理与分析。

### 关键方法

- **Debug / Info / Warn / Error**
  按不同级别输出日志，适配不同场景。方法签名接受一个上下文（`context.Context`）、一条消息（`string`）以及若干键值对（`...interface{}`），因此日志可以携带丰富的上下文信息。
- **WithValues**
  为日志追加键值对，返回一个新的 `Logger` 实例，适合把固定的上下文信息（如用户 ID、请求 ID）挂在 logger 上反复使用。
- **WithName**
  设置 logger 名称，便于区分日志来源（例如哪个服务、哪个模块）。
- **WithCallDepth**
  调整调用栈深度，用于准确定位日志的实际输出位置（封装了日志方法时需要）。

### 使用建议

- 根据信息重要程度选择级别：调试细节用 `Debug`，正常流程用 `Info`，异常但可恢复用 `Warn`，真正的错误用 `Error`。
- 用 `WithValues`、`WithName` 补充上下文，方便后续排查。

## 二、错误处理（`CodeError` 接口）

### 作用

`CodeError` 接口提供统一的错误定义与包装机制，让错误信息更完整、更易管理，并能携带业务错误码返回给客户端。

### 关键方法

- **Code**：返回错误码，用于区分不同错误类型。
- **Msg**：返回错误描述，可直接展示给用户。
- **Detail**：返回详细错误信息，供开发者排查。
- **WithDetail**：为错误附加详细信息，返回新的 `CodeError` 实例。
- **Is**：判断当前错误是否与指定错误匹配，支持灵活的错误比较。
- **Wrap**：包装另一个错误并附加描述，便于追溯错误来源。

### 使用建议

- 定义带错误码和描述的错误时，使用实现了 `CodeError` 接口的错误类型。
- 用 `WithDetail` 追加上下文，便于定位问题。
- 用 `Is` 做错误类型判断，从而走不同的分支逻辑。
- 用 `Wrap` 包装底层错误，同时补充上一层的信息。

## 三、日志接口与示例

项目统一使用日志包 `github.com/openimsdk/tools/log`。

```go
type Logger interface {
    Debug(ctx context.Context, msg string, keysAndValues ...interface{})
    Info(ctx context.Context, msg string, keysAndValues ...interface{})
    Warn(ctx context.Context, msg string, err error, keysAndValues ...interface{})
    Error(ctx context.Context, msg string, err error, keysAndValues ...interface{})
    WithValues(keysAndValues ...interface{}) Logger
    WithName(name string) Logger
    WithCallDepth(depth int) Logger
}
```

以 info 级别打印日志：

```go
func main() {
	logger := log.NewLogger().WithName("MyService")
	ctx := context.Background()
	logger.Info(ctx, "服务已启动", "port", "8080")
}
```

## 四、错误处理接口与示例

统一使用 `github.com/openimsdk/tools/errs` 包。

```go
type CodeError interface {
    Code() int
    Msg() string
    Detail() string
    WithDetail(detail string) CodeError
    Is(err error, loose ...bool) bool
    Wrap(msg ...string) error
    error
}
```

创建并使用 `CodeError`：

```go
package main

import (
	"fmt"
	"github.com/openimsdk/tools/errs"
)

func main() {
	err := errs.New(404, "资源不存在")
	err = err.WithDetail("更多细节")
	if e, ok := err.(errs.CodeError); ok {
		fmt.Println(e.Code(), e.Msg(), e.Detail())
	}
}
```

## 五、日志的具体约定

1. **启动时打印关键信息**
   程序启动时要打印入参与关键流程信息，便于确认启动状态和实际生效的配置。

   ```go
   package main

   import (
       "fmt"
       "os"
   )

   func main() {
       fmt.Println("程序启动，版本：1.0.0")
       fmt.Printf("正在连接数据库：%s\n", os.Getenv("DATABASE_URL"))
   }
   ```

2. **使用 `tools/log` 与 `fmt` 输出日志**
   日志应通过专门的日志库输出，便于统一管理和格式化。

   ```go
   package main

   import (
       "context"
       "github.com/openimsdk/tools/log"
   )

   func main() {
       ctx := context.Background()
       log.Info(ctx, "应用启动成功")
   }
   ```

3. **启动失败或关键信息走标准错误输出**
   关键错误、启动失败需要让用户明确感知，应输出到标准错误。

   ```go
   package main

   import (
       "fmt"
       "os"
   )

   func checkEnvironment() bool {
       return os.Getenv("REQUIRED_ENV") != ""
   }

   func main() {
       if !checkEnvironment() {
           fmt.Fprintln(os.Stderr, "缺少必需的环境变量")
           os.Exit(1)
       }
   }
   ```

   项目已封装成工具函数，可直接通过 `tools/log` 输出错误信息：

   ```go
   package main

   import (
       util "github.com/openimsdk/open-im-server/v3/pkg/util/genutil"
   )

   func main() {
       if err := apiCmd.Execute(); err != nil {
           util.ExitWithError(err)
       }
   }
   ```

4. **运行时日志统一使用 `tools/log`**
   保证日志风格一致、可控。若 `tools/log` 尚未初始化（例如极早期启动阶段），可暂时用 `fmt` 输出。

5. **错误日志由最外层调用方打印**
   避免同一个错误被重复打印。错误应在最外层捕获并记录一次，中间层只负责向上返回。

   ```go
   package main

   import (
       "github.com/openimsdk/tools/log"
       "context"
   )

   func doSomething() error {
       // 此处发生错误
       return errs.Wrap(errors.New("发生了一个错误"))
   }

   func controller() error {
       err := doSomething()
       if err != nil {
           return err
       }
       return nil
   }

   func main() {
       err := controller()
       if err != nil {
           log.Error(context.Background(), "操作失败", err)
       }
   }
   ```

6. **API RPC 调用与非 RPC 应用的日志差别**

   对基于 gRPC 的 RPC 调用，info 级别的日志由 gRPC 服务端中间件统一打印，无需在每个 RPC 方法里手写。对非 RPC 应用，则建议在关键执行路径上手动打日志，形成执行轨迹。

   **gRPC 服务端日志中间件：**

   `UnaryInterceptor` 与 `StreamInterceptor` 分别拦截 Unary 与 Stream 类型的 RPC 调用。下面是一个简单的 Unary 日志中间件：

   ```go
   package main

   import (
       "context"
       "google.golang.org/grpc"
       "google.golang.org/grpc/codes"
       "google.golang.org/grpc/status"
       "log"
       "time"
   )

   // unaryServerInterceptor 返回一个记录每次请求的 Unary 服务端拦截器。
   func unaryServerInterceptor() grpc.UnaryServerInterceptor {
       return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
           // 记录请求开始时间
           start := time.Now()
           // 调用真正的 RPC 方法
           resp, err = handler(ctx, req)
           // 请求结束后打印耗时等信息
           log.Printf("请求方法：%s，耗时：%s，错误状态：%v", info.FullMethod, time.Since(start), status.Code(err))
           return resp, err
       }
   }

   func main() {
       // 创建 gRPC server 并挂载中间件
       s := grpc.NewServer(grpc.UnaryInterceptor(unaryServerInterceptor()))
       // 注册你的服务

       // 启动 gRPC server
       log.Println("正在启动 gRPC server...")
       // ...
   }
   ```

   **非 RPC 应用的日志：**

   关键是在合适的位置打日志，保持执行轨迹可追溯：

   ```go
   package main

   import (
       "log"
   )

   func processTask(taskID string) {
       // 记录任务处理开始
       log.Printf("开始处理任务：%s", taskID)
       // 这里是任务的实际处理逻辑

       // 记录任务处理完成
       log.Printf("任务处理完成：%s", taskID)
   }

   func main() {
       taskID := "task123"
       processTask(taskID)
   }
   ```

   两种场景下，恰当的日志都能帮助研发与运维监控系统状态、追溯问题来源、快速定位并解决故障。gRPC 场景用中间件可以集中管理日志；非 RPC 应用则要在关键执行点打点，以便理解运行流程与状态变化。

## 六、什么时候需要包装错误？

1. **包装函数内部产生的错误**
   函数内部出错时，用 `errs.Wrap` 为原始错误补充上下文。

   ```go
   func doSomething() error {
       // 假设此处发生错误
       err, _ := someFunc()
       if err != nil {
         return errs.WrapMsg(err, "doSomething 执行失败")
       }
   }
   ```

   若不需要自定义描述，直接包装即可：

   ```go
   func doSomething() error {
       // 假设此处发生错误
       err, _ := someFunc()
       if err != nil {
         return errs.Wrap(err)
       }
   }
   ```

2. **包装系统调用或其他包返回的错误**
   调用外部库、系统函数出错时，同样要补充上下文后再包装。

   ```go
   func readConfig(file string) error {
       _, err := os.ReadFile(file)
       if err != nil {
           return errs.Wrap(err, "读取配置文件失败")
       }
       return nil
   }
   ```

3. **模块内部调用不需要重复包装**

   如果错误在下层已经带上了足够的上下文，上层直接返回即可，不要重复包装（否则堆栈和描述会层层叠加，反而难读）。

   ```go
   func doSomething() error {
       err := doAnotherThing()
       if err != nil {
           return err
       }
       return nil
   }
   ```

4. **包装时要给出足够详细的信息**
   补充足够的上下文，让错误可读、可排查。

   ```go
   func connectDatabase() error {
       err := db.Connect(config.DatabaseURL)
       if err != nil {
           return errs.Wrap(err, fmt.Sprintf("连接数据库失败，URL：%s", config.DatabaseURL))
       }
       return nil
   }
   ```

## 七、关于 `WrapMsg`

```go
// "github.com/openimsdk/tools/errs"
func WrapMsg(err error, msg string, kv ...any) error {
	if len(kv) == 0 {
		if len(msg) == 0 {
			return errors.WithStack(err)
		} else {
			return errors.WithMessage(err, msg)
		}
	}
	var buf bytes.Buffer
	if len(msg) > 0 {
		buf.WriteString(msg)
		buf.WriteString(" ")
	}
	for i := 0; i < len(kv); i += 2 {
		if i > 0 {
			buf.WriteString(", ")
		}
		buf.WriteString(toString(kv[i]))
		buf.WriteString("=")
		buf.WriteString(toString(kv[i+1]))
	}
	return errors.WithMessage(err, buf.String())
}
```

1. **函数签名**
   - `err error`：原始错误对象。
   - `msg string`：追加到错误上的描述文本。
   - `kv ...any`：可变参数，用于传入键值对。`any` 是 Go 1.18 引入的别名，等价于 `interface{}`，表示任意类型。

2. **逻辑**
   - 若没有键值对（`kv` 为空）：
     - 若 `msg` 也为空，使用 `errors.WithStack(err)`，返回附带调用栈的原始错误。
     - 若 `msg` 不为空，使用 `errors.WithMessage(err, msg)`，把描述追加到原始错误上。
   - 若有键值对，则先拼描述、再拼所有键值对，格式为 `key=value`，用逗号分隔；有描述时描述在前，后跟一个空格。

3. **键值对的拼接**
   - 循环两两遍历键值对。
   - 用 `toString` 把 key 与 value 都转成字符串，按 `key=value` 写入 `bytes.Buffer`。

4. **返回结果**
   - 用 `errors.WithMessage(err, buf.String())` 把拼好的文本追加到原始错误上并返回。

### 用法示例

**示例 1：不附加任何信息**

```go
// "github.com/openimsdk/tools/errs"
err := errors.New("原始错误")
wrappedErr := errs.WrapMsg(err, "")
// wrappedErr 包含原始错误及其调用栈
```

**示例 2：只加描述**

```go
// "github.com/openimsdk/tools/errs"
err := errors.New("原始错误")
wrappedErr := errs.WrapMsg(err, "补充的错误信息")
// wrappedErr 包含原始错误、调用栈以及「补充的错误信息」
```

**示例 3：描述 + 键值对**

```go
// "github.com/openimsdk/tools/errs"
err := errors.New("原始错误")
wrappedErr := errs.WrapMsg(err, "出现问题", "code", 404, "url", "http://example.com")
// wrappedErr 包含原始错误、调用栈以及「出现问题 code=404, url=http://example.com」
```

**示例 4：只有键值对**

```go
// "github.com/openimsdk/tools/errs"
err := errors.New("原始错误")
wrappedErr := errs.WrapMsg(err, "", "user", "john_doe", "action", "login")
// wrappedErr 包含原始错误、调用栈以及「user=john_doe, action=login」
```

**示例 5：键值对来自运行时上下文**

实际业务中，键值对往往是运行时的变量，例如用户 ID、操作类型、错误码、请求地址。把这些信息带进错误里，能显著降低排查成本。

```go
// 定义一些上下文变量
userID := "user123"
operation := "update profile"
errorCode := 500
requestURL := "http://example.com/updateProfile"

// 创建错误
err := errors.New("原始错误")

// 包装错误，把上下文中的动态键值对一并带上
wrappedErr := errs.WrapMsg(err, "操作失败", "user", userID, "action", operation, "code", errorCode, "url", requestURL)
// wrappedErr 包含原始错误、调用栈以及「操作失败 user=user123, action=update profile, code=500, url=http://example.com/updateProfile」
```

> 提示：`WrapMsg` 不仅能拼接静态描述，还能把执行上下文中的动态信息一并写进错误，这是本项目排查线上问题的主要手段之一。
