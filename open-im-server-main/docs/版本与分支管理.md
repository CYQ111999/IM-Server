# 版本与分支管理

本项目遵循 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/)，版本号格式为 `MAJOR.MINOR.PATCH`。

- `MAJOR`：不兼容的 API 变更。
- `MINOR`：向后兼容的功能新增。
- `PATCH`：向后兼容的问题修复。

功能新增时 `MINOR` 加 1、`PATCH` 归零；重大重构时 `MAJOR` 加 1；`PATCH` 只用于修 bug，不引入新功能，且保证向后兼容。

## 分支约定

| 分支 | 用途 |
| --- | --- |
| `main` | 主干，保持可运行、可编译。日常开发与学习改造都在这里推进 |
| `feature/xxx` | 单个功能的开发分支，完成后合回 `main` |
| `release-x.y` | 发布分支，只接受该版本的 bug 修复，保证稳定 |

## 提交与合并

- 提交信息写清「改了什么、为什么改」，一个提交只做一件事。
- 合并前必须通过 `go build ./...` 与 `go test ./...`。
- 修 bug 时，除了在当前分支修，必要时也要把修复同步回仍在维护的 `release` 分支。

## 版本号与标签

打标签用 `vX.Y.Z`，标签不可变，用于精确回溯某一版本的代码。

版本修饰符常用于标记开发阶段：

| 修饰符 | 含义 |
| --- | --- |
| `alpha` | 内部测试版，问题较多，仅供开发者之间联调 |
| `beta` | 公测版，供愿意尝鲜的用户试用并反馈 |
| `rc` | 候选发布版，正式版前的最后一轮测试 |
| `ga` | 首个正式稳定版 |
| 无修饰符 | 正式发布版，面向所有用户 |

## 微服务的版本偏差策略

本项目是微服务架构（`openim-api`、`openim-rpc-*`、`openim-msggateway`、`openim-msgtransfer`、`openim-push`），多实例部署时存在「新旧版本共存」的窗口期，因此要约定版本偏差上限：

- **`openim-api`**：高可用集群中，最新与最旧的实例之间最多相差一个次版本。例如最新为 v3.3，其余实例可以是 v3.3、v3.2，但不能是 v3.1。
- **`openim-rpc-*`**：所有 RPC 服务同理，滚动升级过程中新旧实例最多相差一个次版本。
- **其他服务**（`openim-msggateway`、`openim-msgtransfer`、`openim-push`）：同样遵循「最多差一个次版本」的原则。

这条约束的实际意义是：**升级时按批次滚动，不要一次跨多个次版本跳跃**，否则新老实例之间的 gRPC 协议、消息结构可能不兼容。

### 推荐的升级顺序

1. 先升级下游消费方（`openim-msgtransfer`、`openim-push`），让它们能兼容新旧两种消息格式；
2. 再升级 `openim-rpc-*` 各服务；
3. 最后升级 `openim-api` 与 `openim-msggateway`（对外入口）。

这样在任意时刻，链路上都不会出现「新格式无人能解析」的窗口。
