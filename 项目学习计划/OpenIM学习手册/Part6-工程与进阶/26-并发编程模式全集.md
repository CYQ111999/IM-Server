## 第一部分 纯理论：并发到底在解决什么

### 1.1 并发 ≠ 并行

这两个词天天被混用，但含义完全不同：

| | 并发（concurrency） | 并行（parallelism） |
|---|---|---|
| 定义 | **同时处理**多件事（结构） | **同时执行**多件事（物理） |
| 前提 | 单核也能并发（时间片轮转） | 必须多核 |
| 目的 | 让等待不浪费 CPU | 缩短总耗时 |
| 类比 | 一个人交替做三件事 | 三个人各做一件事 |

**为什么这个区分重要**：因为后端服务的绝大多数时间在**等**，不是**算**。

一个 IM 服务的典型耗时分布：

```
查一次 Redis：      0.3ms（其中 0.25ms 在等网络）
写一次 Mongo：      2~5ms（其中 4.9ms 在等磁盘）
调一次 gRPC：       1~3ms（几乎全在等网络）
真正 CPU 计算：     几微秒
```

所以「一个请求一个 goroutine」这种写法能撑几十万并发，**不是因为 CPU 强，是因为大家都在等**。如果有 20 万个连接，任何时刻真正在跑 CPU 的可能只有几十个 goroutine。

这也是为什么 Go 的 `netpoller` 这么关键：它把「等网络」从「阻塞一个线程」变成「挂起一个 goroutine」，线程可以去跑别的。

### 1.2 一个 goroutine 到底有多便宜

| | OS 线程 | goroutine |
|---|---|---|
| 初始栈 | 1~8 MB（固定） | **2 KB**（可增长） |
| 创建成本 | ~10μs（系统调用） | ~0.2μs（用户态分配） |
| 切换成本 | ~1~2μs（内核态切换、TLB 刷新） | ~0.1μs（用户态，寄存器保存） |
| 数量上限 | 几千（内存限制） | 几十万~百万 |
| 调度者 | 内核 | Go runtime（GMP） |

具体到 OpenIM：**29 个进程，网关每个连接至少 2 个 goroutine**（读循环 + 写循环）。单网关 10 万连接 = 20 万 goroutine = 20 万 × 2KB = **400MB 栈内存**（实际因为栈会增长，会更多，但量级是这样）。

如果用 OS 线程：20 万 × 1MB = **200GB**，直接不可能。

**这就是「Go 适合写网关」的物理基础**，不是语言偏好问题。

### 1.3 共享内存 vs 消息传递

Go 的官方口号是：

> Do not communicate by sharing memory; instead, share memory by communicating.
> 不要通过共享内存来通信，而要通过通信来共享内存。

这句话到底在说什么？

**共享内存**（传统做法）：

```go
var mu sync.Mutex
var m = map[string]int{}

func inc(k string) {
    mu.Lock()
    m[k]++
    mu.Unlock()
}
```

问题：
- 锁的范围靠人保证。漏一处 `Unlock` → 死锁；锁的范围太大 → 性能差
- 锁和数据的**归属关系是隐式的**：看到 `m` 不知道它归哪个锁保护
- 组合使用时容易死锁（A 锁 B，B 锁 A）

**消息传递**：

```go
ch := make(chan op)
go func() {
    m := map[string]int{}
    for op := range ch {
        m[op.key] += op.delta      // 只有这个 goroutine 碰 m
    }
}()
```

数据**只被一个 goroutine 拥有**，外部想改只能发消息。锁消失了，因为不存在共享。

**但 Go 并没有强制你这么做。** 现实是两者混用，判断标准是：

| 场景 | 选什么 | 为什么 |
|---|---|---|
| 数据被高频读、极少写（如连接表） | **读写锁**（RWMutex） | channel 每次读都要发消息，开销远大于 RLock |
| 数据要跨 goroutine 传递所有权（如任务分发） | **channel** | 天然的所有权转移 |
| 只有一个计数器/标志位 | **atomic** | 锁是杀鸡用牛刀 |
| 需要「等一组 goroutine 全部完成」 | **WaitGroup / errgroup** | 专用工具 |
| 需要「限流并发数」 | **带缓冲 channel 作信号量 / errgroup.SetLimit** | 专用工具 |
| 状态机/事件循环（连接增删） | **单 goroutine + channel** | 消灭锁，逻辑串行化 |

**OpenIM 的实际选择**：连接表用 `RWMutex`（读多写少），连接事件用 `channel`（所有权转移），在线计数用 `atomic`，批量任务用 `WaitGroup`，扇出用 `errgroup`。**每种场景都用了对应的工具，没有「全都用锁」或「全都用 channel」的教条**。

### 1.4 并发安全的四个层次（从好到坏）

理解这四个层次，比记住十种锁的用法有用得多。

**层次 1：不共享**

最安全。每个 goroutine 有自己的数据，从不交叉。

```go
// 每个连接自己的读缓冲
func (c *Client) readLoop() {
    buf := make([]byte, 4096)    // 栈上分配，别的 goroutine 碰不到
    ...
}
```

代价：只能处理「天然可分割」的数据。

**层次 2：共享但不可变**

数据创建后不再修改，所有 goroutine 只读。

```go
// 配置在启动时加载完，运行时只读
type Config struct { ... }        // 加载后不再 Set
```

代价：更新配置要重建整个结构 + 原子替换指针（`atomic.Pointer[Config]`）。

**层次 3：加锁保护**

```go
mu.RLock()
v, ok := m[k]
mu.RUnlock()
```

代价：锁竞争、死锁风险、性能损耗。

**层次 4：靠「约定」不加锁**

```go
// 注释写「这个字段只在 eventLoop 里改」，然后就没加锁
```

代价：**这是 bug 的温床**。约定不会被执行，新同事加一行代码就破防。

⚠️ **易错**：OpenIM 里有不少「层次 4」的代码，靠注释或隐式约定。比如 `userMap.data` 在 `GetAllUserStatus` 里被 `RLock` 保护着**写入**（下面 2.8 会讲），属于「以为加了锁其实加错了」。

### 1.5 锁的粒度：全局锁 → 分段锁 → 无锁

假设要保护 10 万个用户的连接，三种做法：

**① 一把全局锁**

```go
var mu sync.RWMutex
var data = map[string]*Client{}
```

- 优点：简单，绝对正确
- 缺点：所有读写串行。10 万连接、每秒 10 万次操作 → 锁成为瓶颈，CPU 大量时间在自旋/阻塞

**② 分段锁（sharding）**

```go
var shards [16]struct {
    mu sync.RWMutex
    m  map[string]*Client
}

func shardOf(key string) int {
    return int(hash(key)) % 16
}
```

- 优点：锁竞争降到 1/16
- 缺点：跨分片操作变复杂（比如「遍历所有用户」要锁 16 次）

**③ 单 goroutine 拥有 + 消息传递**

```go
for {
    select {
    case c := <-register:    // 增
    case c := <-unregister:  // 删
    case q := <-query:       // 查
    }
}
```

- 优点：完全无锁，逻辑天然串行，不会有「A 看一眼 B 改一下」的时序问题
- 缺点：**吞吐上限 = 单 goroutine 的处理速度**。如果查询量极大，这个 goroutine 会成为瓶颈

**OpenIM 的选择**：

| 数据结构 | 方案 | 码点 | 理由 |
|---|---|---|---|
| 网关连接表 `userMap.data` | **一把 RWMutex** | `user_map.go:58` | 单网关连接数最多几万，一把锁够用；且读多写少，RWMutex 让读并发 |
| 连接增删事件 | **单 goroutine 事件循环** | `ws_server.go:175-190` | 增删必须串行，否则「注册」和「踢人」会打架 |
| 消息批处理分片 | **哈希分片到 50 个 worker** | `batcher.go:250-253` | 保序需要同 key 同 worker，分片是「保序 + 并行」的唯一解法 |
| 在线状态批量上报 | **按 md5 分到 N 个 channel** | `online.go:53-56` | 避免单个 channel 被塞爆 |

**为什么网关连接表不上分段锁？** 因为还有第二层保护——**每个网关节点只管自己的连接**（连接表是进程本地的）。10 万连接分布在 N 个网关节点上，单节点只有几万，一把 RWMutex 的读并发已经够（RWMutex 的读锁之间不互斥）。

📌 **这是「架构上分摊」代替「代码上优化」的例子**：与其把一个 map 拆成 16 个锁，不如把连接分散到多个进程。前者复杂度高、收益有限；后者零代码成本。

### 1.6 背压：三种态度

「背压（backpressure）」是指：**下游处理不过来时，上游怎么办**。

三种态度，没有绝对对错，取决于业务：

**① 阻塞（等）**

```go
select {
case ch <- msg:      // 满了就等
}
```

- 效果：压力向上游传导。上游是 Kafka 消费者 → 停止拉取 → 压力落到 Kafka 磁盘
- 优点：**不丢数据**
- 缺点：一个慢下游会拖慢整条链路（响应时间不可控）
- OpenIM 用在哪：`memamq` 的 `PushCtx`（推送队列）、`batcher` 的分片 channel（消费主链路）

**② 丢弃（丢最新的）**

```go
select {
case ch <- msg:
default:
    // 满了就丢，返回错误或计数
}
```

- 效果：过载时降级，保护自己
- 优点：响应时间可控
- 缺点：**丢数据**
- OpenIM 用在哪：`user_map.push`（在线状态变更通知，丢一次下次还会发）、`websocket writeMessage`（**这里选择的是断开，见下**）

**③ 断开（踢掉消费者）**

```go
select {
case c.writer <- msg:
    return nil
default:
    return c.closeBy(ErrWriteFull)     // 满了直接关连接
}
```

- 效果：判断「这个客户端跟不上了」，主动断开，让它重连后按 seq 补齐
- 优点：**不拖累其他客户端**，且客户端重连后能自愈（因为有 seq 机制）
- 缺点：对用户是「突然掉线」
- OpenIM 用在哪：`client_conn.go:76-88`，写缓冲 256 满 → `ErrWriteFull`

⚠️ **易错**：这三种态度**必须在同一个系统里保持一致**，否则会出现「上游阻塞、下游丢弃」的错配。比如 batcher 用阻塞，但 redis 写入失败只打日志继续（`online_history_msg_handler.go:385`），就变成「假背压」——表面阻塞，实际丢数据。

### 1.7 worker pool vs semaphore

这两个经常被混为一谈，但解决的问题不同。

**worker pool（工作池）**：固定 N 个 goroutine，从队列里取任务。

```go
for i := 0; i < N; i++ {
    go func() {
        for job := range jobs {
            process(job)
        }
    }()
}
```

特点：
- goroutine 数量**恒定**，任务无限排队
- 适合「任务量不可预测、单个任务开销大」
- 队列满时需要背压策略

**semaphore（信号量 / 限流并发）**：每个任务自己起 goroutine，但用信号量限制同时运行的数量。

```go
sem := make(chan struct{}, N)
for _, item := range items {
    sem <- struct{}{}          // 获取
    go func(item Item) {
        defer func() { <-sem }()  // 释放
        process(item)
    }(item)
}
```

特点：
- goroutine 数量 = 任务数（可能很多），但**同时运行**的只有 N 个
- 适合「任务数已知、需要并发但不要太多」
- 不用预先建池

⚠️ **易错**：上面这段代码有个经典陷阱——`sem <- struct{}{}` 放在 `go` 之前是**对的**（限制创建速度），如果放在 goroutine 内部，会瞬间创建 N 万个 goroutine 然后大部分阻塞在 sem 上，**内存炸掉**。

**errgroup 的 `SetLimit`** 就是 semaphore 的语法糖：

```go
var g errgroup.Group
g.SetLimit(3)
for _, item := range items {
    g.Go(func() error { return process(item) })
}
g.Wait()
```

OpenIM 用的是这个（`ws_server.go:236`）。

### 1.8 errgroup 到底是什么

`golang.org/x/sync/errgroup` 是 `sync.WaitGroup` 的增强版，解决了 WaitGroup 的三个痛点：

| WaitGroup 的问题 | errgroup 的解法 |
|---|---|
| 不知道怎么收集子任务错误 | `g.Wait()` 返回第一个错误 |
| 一个失败后其他还在跑 | 配合 `context.WithCancel` 可以取消其他 |
| 不能限制并发数 | `g.SetLimit(n)` |

```go
g, ctx := errgroup.WithContext(ctx)     // ctx 在任一任务失败时取消
g.SetLimit(10)
for _, u := range users {
    u := u
    g.Go(func() error {
        return pushTo(u)
    })
}
if err := g.Wait(); err != nil { ... }
```

⚠️ **易错（Go 1.22 之前）**：`u := u` 这行不能省。因为循环变量在所有迭代间共享，goroutine 里用的 `u` 可能在启动时就变成了最后一个值。Go 1.22 改了这个语义（每次迭代新变量），但老代码还得写。

📌 **OpenIM 里的写法**：`ws_server.go:243` 有 `v := v`，说明写的时候考虑了这个问题。但 `onlinepusher.go` 里有些地方没写，需要逐个看是否真的传参进闭包了。

### 1.9 context：取消的传播

`context` 在并发里的作用只有一个：**把一个「取消信号」广播给一棵 goroutine 树**。

```
main ctx
  ├── 服务 A
  │     ├── 子任务 1  ── 收到取消 → 退出
  │     └── 子任务 2  ── 收到取消 → 退出
  └── 服务 B
        └── ...
```

三个关键 API：

| API | 用途 | 什么时候用 |
|---|---|---|
| `WithCancel` | 手动取消 | 需要主动停止的场景 |
| `WithTimeout` | 超时取消 | 所有外部调用（RPC/DB/HTTP）都该有 |
| `WithCancelCause` | 带原因取消 | 排障：知道为什么退出的 |
| `WithoutCancel` | **剥离**取消 | 退出清理、异步任务 |

`WithoutCancel` 最反直觉，但非常重要。场景：

```go
// 服务要退出了，但我想异步把最后一批数据刷到磁盘
func shutdown(ctx context.Context) {
    ctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)
    defer cancel()
    flush(ctx)      // 如果直接用原 ctx，这里会立刻 context canceled
}
```

OpenIM 里用在两处：
- `cmd/main.go:495`：退出时注销网关地址
- `webhook/http_client.go` 的 `AsyncPost`：异步回调不跟着请求 ctx 取消（否则请求一结束回调就废了）

📌 **这是个很值钱的细节**：`context.WithoutCancel` 是 Go 1.21 才加的。在此之前大家要么 `context.Background()` 丢光所有 value（丢失 operationID），要么自己写个 wrapper。**知道这个 API 说明你跟进语言演进**。

### 1.10 原子操作与 CAS

`sync/atomic` 提供无锁的读-改-写。常用：

| 类型 | 用途 |
|---|---|
| `atomic.Int64/Int32/Bool` | 计数器、标志位（Go 1.19+ 类型化版本） |
| `atomic.Pointer[T]` | 原子替换指针（做不可变配置热更新） |
| `atomic.CompareAndSwap*` | CAS，实现「只执行一次」 |

**CAS 的本质**：「如果当前值还是 A，就改成 B，否则失败」。它是所有无锁算法的基础。

OpenIM 里有个漂亮的用法（`client_conn.go:63-69`）：

```go
type websocketClientConn struct {
    ...
    err atomic.Pointer[error]
}

func (c *websocketClientConn) closeBy(err error) error {
    if !c.err.CompareAndSwap(nil, &err) {
        return *c.err.Load()      // 已经被别人关过了，返回第一次的错误
    }
    close(c.done)                  // 只有第一个关的人会执行
    ...
}
```

这一行 CAS 解决了一个很麻烦的问题：**多个 goroutine 可能同时发现连接坏了**（读循环 EOF、写循环失败、心跳超时），如果都去 `close(c.done)`，第二次 close 会 panic（`close of closed channel`）。

CAS 保证：
- 只有第一个调用者能 `close(c.done)`
- 后续调用者拿到的是**第一次的错误原因**（保留最原始的信息，而不是被覆盖）

**这比 `sync.Once` 好在哪**：`Once` 只能保证执行一次，但拿不到「为什么关」；CAS + `atomic.Pointer[error]` 同时完成了「幂等关闭」和「保留首个错误」。

### 1.11 sync.Pool：什么时候有用，什么时候是负担

`sync.Pool` 是对象复用池。作用是**减少 GC 压力**，不是「减少分配耗时」。

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

b := bufPool.Get().(*bytes.Buffer)
defer func() { b.Reset(); bufPool.Put(b) }()
```

**它有用的三个条件**（缺一不可）：

1. 对象**大**（分配成本高，比如几 KB 的 buffer）
2. 对象**创建频繁**（每秒几千次以上）
3. 对象**用完能完全重置**（有状态残留会导致 bug）

**它没用的场景**：小对象（`[]byte{4}`）、低频创建、对象里有需要额外清理的引用。

⚠️ **易错**：`Put` 之前一定要 `Reset`。否则下一个使用者拿到带脏数据的对象。OpenIM 的 `compressor.go:13-14` 处理得对：

```go
gzipWriterPool = sync.Pool{New: func() any { return gzip.NewWriter(nil) }}
```

但 `gzip.Writer` 的复用必须调 `Reset(io.Writer)` 绑定新输出，否则写到旧的 writer 上。📌 需要看 `compressor.go` 的 `Get/Put` 逻辑确认（下面 2.6 会讲）。

**Go 1.13 之后 sync.Pool 的一个重要变化**：池里的对象会在**每次 GC 时被清空**（除了每个 P 的私有缓存）。所以它**不能当缓存用**——`Put` 进去的对象可能在下次 `Get` 时就没了。这一点很多人不知道。

### 1.12 数据竞争：race detector 能抓什么、抓不到什么

**能抓**：两个 goroutine 同时访问同一内存地址，至少一个是写，且没有同步。

```bash
go test -race ./...
go run -race ./cmd
go build -race -o /tmp/app ./cmd && /tmp/app
```

**抓不到**：
- 依赖特定时序才出现的逻辑错误（比如「先 Set 后 Get」的顺序问题）
- 死锁（race detector 不检测锁顺序）
- goroutine 泄漏
- 加锁了但**锁错了对象**（比如用 A 的锁保护 B 的数据）

⚠️ **Race detector 有 5~10 倍性能开销**，只能用于测试，不能上生产。

**OpenIM 里有一处 race detector 一定会报的地方**（下面 2.8 细讲）：`user_map.go` 的 `GetAllUserStatus` 在 `RLock` 保护下**写** `userPlatform.Time`。两个 goroutine 同时调用它，就是对同一字段的并发写。

### 1.13 并发原语选择决策表（贴墙版）

```
需要做什么？
├─ 只是计数器 / 开关标志
│    → atomic.Int64 / atomic.Bool
├─ 只是「读多写少的 map」
│    → sync.RWMutex
├─ 要在多个 goroutine 间传递数据所有权
│    → channel
├─ 要等 N 个任务全部完成
│    → sync.WaitGroup
├─ 要等 N 个任务、还要收集错误、限制并发
│    → errgroup + SetLimit
├─ 任务量不可预测、要固定 goroutine 数
│    → worker pool（N 个 goroutine + 任务 channel）
├─ 增删改必须严格串行、且逻辑复杂
│    → 单 goroutine 事件循环 + channel
├─ 同一个 key 的操作必须保序、不同 key 要并行
│    → 哈希分片（key → worker）
├─ 只需要初始化一次
│    → sync.Once（或 atomic CAS）
├─ 对象创建频繁且大
│    → sync.Pool（记得 Reset）
└─ 跨进程互斥
     → Redis SETNX + Lua / etcd lease
```

## 第二部分 源码实现：7 个模式 + 5 个反面教材

### 2.1 模式一：读循环 + 写队列（每连接两个 goroutine）

**问题**：WebSocket 是**全双工**的——同一时刻可能在读，也可能在写。而 `gorilla/websocket` 的实现**不允许并发写**：

> Connections support one concurrent reader and one concurrent writer.
> The Close and WriteControl methods can be called concurrently with all other methods.

所以必须：**一个 goroutine 只读，一个 goroutine 只写**。

**结构**（`internal/msggateway/client_conn.go`）：

```
┌───────────── websocketClientConn ─────────────┐
│                                                │
│  ReadMessage() ──── 调用方 goroutine（读循环） │
│                                                │
│  writer chan (256) ──→ loopSend goroutine ──→ conn.WriteMessage
│                                                │
│  doPing goroutine ──→ writer chan（发 ping）   │
│                                                │
│  done chan ──→ 通知所有 goroutine 退出          │
└────────────────────────────────────────────────┘
```

**代码**（`client_conn.go:31-50`）：

```go
func NewWebSocketClientConn(conn *websocket.Conn, readLimit int64, readTimeout time.Duration, pingInterval time.Duration) ClientConn {
    c := &websocketClientConn{
        readTimeout: readTimeout,
        conn:        conn,
        writer:      make(chan *websocketMessage, 256),   // ← 写队列，容量 256
        done:        make(chan struct{}),
    }
    if readLimit > 0 { c.conn.SetReadLimit(readLimit) }
    c.conn.SetPingHandler(c.pingHandler)
    c.conn.SetPongHandler(c.pongHandler)

    go c.loopSend()                                        // ← 唯一写 goroutine
    if pingInterval > 0 { go c.doPing(pingInterval) }       // ← 心跳 goroutine
    return c
}
```

**写入口**（`client_conn.go:76-88`）：

```go
func (c *websocketClientConn) writeMessage(messageType int, data []byte) error {
    if errPtr := c.err.Load(); errPtr != nil {
        return *errPtr                       // 已关闭，直接返回错误
    }
    select {
    case c.writer <- &websocketMessage{MessageType: messageType, Data: data}:
        return nil
    default:
        return c.closeBy(ErrWriteFull)       // ← 关键：满了就断开，不阻塞
    }
}
```

**这是本模式最重要的设计决策**：`default` 分支选择「断开」而不是「阻塞」。

为什么？推演一下如果阻塞会发生什么：

```
客户端 A 网络很慢（比如手机信号差）
  → A 的 writer chan 满了
  → 推送 goroutine 往 A 的 chan 写，阻塞
  → 这个推送 goroutine 是共享的（hub_server 的队列 worker）
  → 它卡住了，无法处理其他用户的消息
  → 千人群里其他 999 人收不到消息
```

**一个慢客户端拖垮整个群**。这就是「阻塞式背压」在推场景下的致命问题——**扇出场景下不能用阻塞**。

所以选择断开，配合 seq 机制：客户端重连后报自己的 maxSeq，服务端从 Redis 补发。**断开不是丢消息，是换一种方式交付**。

📌 这个决策的前提是「有 seq 补偿机制」。如果系统没有离线消息补拉，断开就等于丢消息，那就必须阻塞或扩容。

**心跳的实现**（`client_conn.go:186-200`）：

```go
func (c *websocketClientConn) doPing(d time.Duration) {
    ticker := time.NewTicker(d)
    defer ticker.Stop()
    for {
        select {
        case <-c.done: return
        case <-ticker.C:
            if err := c.writeMessage(websocket.PingMessage, nil); err != nil {
                _ = c.closeBy(fmt.Errorf("send ping %w", err))
                return
            }
        }
    }
}
```

注意 ping 也是走 `writeMessage`（即走 channel），而不是直接 `conn.WriteControl`。**这保证了所有写操作都串行在 `loopSend` 一个 goroutine 里**，彻底避免并发写。

⚠️ 但 `pingHandler` 里有个例外（`client_conn.go:167-180`）：

```go
func (c *websocketClientConn) pingHandler(appData string) error {
    ...
    err := c.conn.WriteControl(websocket.PongMessage, []byte(appData), time.Now().Add(time.Second*1))
```

`WriteControl` **直接写 conn，绕过 channel**。这在 gorilla/websocket 的文档里是允许的（"Close and WriteControl can be called concurrently"），但有个隐患：`WriteControl` 和 `loopSend` 里的 `WriteMessage` 可能**同时写 TCP 缓冲**，导致帧交错？实际上 gorilla 内部有 mutex 保护写，所以不会交错，但会有**锁竞争**。这是「文档允许但不推荐频繁调用」的用法，ping 频率低（45 秒一次），可以接受。

**退出清理**（`client_conn.go:90-130` 的 `loopSend`）：

```go
func (c *websocketClientConn) loopSend() {
    defer func() { _ = c.conn.Close() }()
    for {
        select {
        case <-c.done:
            // 关闭时把队列里剩下的消息尽力写完（drain）
            for {
                select {
                case msg := <-c.writer:
                    writeIt(msg)
                    if err != nil { c.closeBy(err); return }
                default:
                    return      // 队列空了，退出
                }
            }
        case msg := <-c.writer:
            writeIt(msg)
            if err != nil { c.closeBy(err); return }
        }
    }
}
```

**这个 drain 循环值得学**：关闭时不是立刻丢，而是把已入队的消息**尽力写完**（非阻塞，写不完就走）。这是「优雅关闭」在连接级别的对应——已经承诺给客户端的消息，尽量送出去。

### 2.2 模式二：中心事件循环（消灭锁）

**问题**：网关的连接表需要支持三种操作——注册、注销、踢人（多端互踢）。如果每个操作各自加锁，会遇到「注册和踢人同时发生」的时序问题：

```
时间  连接 A（新）              连接 B（旧）
 t1   Set(user1, A)
 t2                            Set(user1, B)
 t3   checkMultiLogin(user1)    ← 此时表里是 [A, B]
 t4                             checkMultiLogin(user1)
```

两个 goroutine 都看到「有两个连接」，都去踢对方，结果把自己踢了。

**解法**：把这三种操作排队，**由一个 goroutine 串行处理**。

**代码**（`ws_server.go:53-55`）：

```go
type WsServer struct {
    ...
    registerChan    chan *Client
    unregisterChan  chan *Client
    kickHandlerChan chan *kickHandler
}
```

初始化（`ws_server.go:160-162`）：

```go
registerChan:    make(chan *Client, 1000),
unregisterChan:  make(chan *Client, 1000),
kickHandlerChan: make(chan *kickHandler, 1000),
```

**为什么是 1000 的缓冲**？因为高峰期连接抖动很厉害（网络切换、APP 切前台），瞬时可能有几百个注册/注销。缓冲太小会阻塞上游（HTTP handler 卡在 `registerChan <- client`），缓冲太大会积压。1000 是个经验值。

**事件循环**（`ws_server.go:175-190`）：

```go
go func() {
    for {
        select {
        case client = <-ws.registerChan:
            ws.registerClient(client)
        case client = <-ws.unregisterChan:
            ws.unregisterClient(client)
        case onlineInfo := <-ws.kickHandlerChan:
            ws.multiTerminalLoginChecker(onlineInfo.clientOK, onlineInfo.oldClients, onlineInfo.newClient)
        }
    }
}()
```

注意这个 `for` 里**没有 `default` 分支**——它是阻塞等待，有事件才处理。这比「轮询 + sleep」好得多（轮询要么浪费 CPU，要么有延迟）。

🟡 **难点**：这个模式的最大代价是**吞吐上限 = 单 goroutine**。如果每秒有 10 万个连接事件，这个循环处理不过来，channel 会积压，最终阻塞 HTTP handler。

**怎么评估够不够用**？粗算：单次 `registerClient` 就是 map 插入 + 一次 push，耗时 ~1μs。每秒 100 万个事件才需要 1 秒。而实际上一个网关节点的连接事件是「每秒几百到几万」，**远远够用**。

**这就是「知道什么时候不该优化」**：单 goroutine 事件循环在 99% 的场景下够用，只有真的到了百万级 QPS 才需要分片。

**注销时的「批量踢人」也用同一套**。`SetKickHandlerInfo`（`ws_server.go:254-256`）：

```go
func (ws *WsServer) SetKickHandlerInfo(i *kickHandler) {
    ws.kickHandlerChan <- i
}
```

📌 **这里有个隐患**：这是**阻塞发送**（没 select/default）。如果事件循环卡住（比如 `multiTerminalLoginChecker` 里同步调了 RPC），`kickHandlerChan` 会积压到 1000 然后**阻塞调用方**。调用方是 `client.go` 的登录流程，最终会阻塞 HTTP handler。

**设计上应该**：要么用 `select + default`（丢了下次还会踢），要么给 `multiTerminalLoginChecker` 加超时。这属于「模式对了但边界没考虑」。

### 2.3 模式三：分片（保序 + 并行）

**问题**：消息处理要满足两个矛盾的要求——

1. **同会话的消息必须保序**（先发的不能后到）
2. **不同会话要并行**（否则吞吐上不去）

**解法**：哈希分片。同一个 key 永远落到同一个 worker。

**代码**（`batcher.go:105-110`）：

```go
b.data = make(chan *T, DefaultDataChanSize)          // 主输入通道，1000
b.chArrays = make([]chan *Msg[T], b.config.worker)   // 50 个 worker channel
for i := 0; i < b.config.worker; i++ {
    b.chArrays[i] = make(chan *Msg[T], b.config.buffer)   // 每个 50 缓冲
}
```

分片函数（`online_history_msg_handler.go:95-98`）：

```go
b.Sharding = func(key string) int {
    hashCode := stringutil.GetHashCode(key)
    return int(hashCode) % och.redisMessageBatches.Worker()
}
```

key 是**会话 ID**（`b.Key` 返回 `GenConversationUniqueKey...`）。

**分发**（`batcher.go:250-253`）：

```go
b.counter.Add(1)                                   // 先 +1，再发
channelID := b.Sharding(key)
b.chArrays[channelID] <- &Msg[T]{key: key, triggerID: triggerID, val: data}
```

⚠️ **注意 `counter.Add(1)` 在发送之前**。如果顺序反了（先发后 Add），worker 可能已经把任务处理完并 `Done()` 了，`counter` 变成负数，`Wait()` 提前返回。这是 WaitGroup 的经典陷阱。

**为什么分片能保序**：同一个会话 ID 哈希到同一个 worker，该 worker 是**单 goroutine 串行处理**，所以顺序天然保持。

**为什么分片数必须是「真的并行」**：50 个 worker，但 Kafka 只有 N 个分区。如果分区数 < 50，某些 worker 会空闲。📌 配置上 Kafka 分区数需要和 worker 数匹配（本仓库 docker-compose 的 Kafka 配置需要核实）。

**对比：`user_map` 为什么不分片**

`user_map` 用的是**一把 RWMutex + 一个大 map**（`user_map.go:58-62`）：

```go
type userMap struct {
    lock sync.RWMutex
    data map[string]*UserPlatform
    ch   chan UserState
}
```

原因：
- 连接表是**读多写少**（每次推消息都查一次 `Get`，连接只在登录/登出时改）
- `RWMutex` 的读锁之间**不互斥**，所以读并发是够的
- 分片会让「遍历所有用户」变复杂（要锁 16 次）
- **最重要**：连接表是进程本地的，多网关节点已经分摊了压力（见 1.5）

⚠️ **但要小心**：`user_map` 的 `push` 是**非阻塞**的（`user_map.go:86-93`）：

```go
func (u *userMap) push(userID string, userPlatform *UserPlatform, offline []int32) bool {
    select {
    case u.ch <- UserState{...}:
        userPlatform.Time = time.Now()
        return true
    default:
        return false          // ← 通道满就丢
    }
}
```

**这个 `default` 意味着在线状态变更通知会丢**。丢了的后果：其他用户看到你的在线状态是旧的。但因为「在线状态」本身有租约续期机制（15 篇讲的 ZSET + score），下次续期会纠正。**这是「可容忍最终一致」的典型判断**——状态类数据丢了会自愈，消息类数据丢了就完了。

而 `ch` 的容量是 **10000**（`user_map.go:49`），已经很大了，说明设计者认为「极少丢」。

📌 **但注意 `push` 在 `RLock` 下被调用**（`RecvSubChange`、`Set` 里），而 `push` 里写 `userPlatform.Time = time.Now()`——**在 RLock 下写共享字段**。这又是一个 race（2.8 会讲）。

### 2.4 模式四：worker pool（固定 goroutine，无限任务）

三个不同规模的实例：

**① batcher：50 worker / 每 worker 50 缓冲**

```go
const (
    size           = 500     // 单批最多 500 条
    mainDataBuffer = 500     // 主通道缓冲
    subChanBuffer  = 50      // 每 worker 通道缓冲
    worker         = 50      // 50 个并行协程
    interval       = 100 * time.Millisecond   // 100ms 强制刷
)
```

（`online_history_msg_handler.go:35-41`）

**容量计算**：50 worker × 50 缓冲 + 500 主通道 = **3000 条消息的缓冲**。超过这个量，`b.data <- data` 会阻塞，压力传回 Kafka 消费者，最终 Kafka 停止拉取。

**这就是完整的背压链**：

```
Mongo 慢
 → worker 处理慢
 → chArrays[i] 满（50）
 → 分发协程阻塞在 b.chArrays[channelID] <-
 → b.data 满（1000/500）
 → Data() 阻塞
 → Kafka 消费者停止拉取
 → Kafka broker 堆积（磁盘）
```

**最终缓冲在 Kafka 磁盘上，不是内存**。这是「用磁盘换内存」的经典设计。

**② memamq：512 worker / 16384 缓冲（网关推送队列）**

```go
queue: memamq.NewMemoryQueue(512, 1024*16)     // hub_server.go:81
```

512 个 worker 同时推送，缓冲 16384 条。为什么这么大？

- 推送是**纯 I/O 等待**（写 WebSocket 帧），单个请求耗时 1~10ms
- 512 并发 × 1000/秒 = 理论 51 万条/秒的推送能力
- 缓冲 16384 是为了吸收突发（比如群里发一条公告，瞬间 5000 人收到）

⚠️ **这里的背压是阻塞的**（`PushCtx` 满时阻塞）。如果 512 个 worker 全卡在慢客户端上（虽然有 `ErrWriteFull` 断开保护），队列会满，然后阻塞 `Push` 调用方——即 `push_handler.go` 的消息处理协程。这条链路会传导到 Kafka。

**③ onlinepusher：errgroup.SetLimit(maxWorkers)**

```go
maxWorkers = d.config.RpcConfig.MaxConcurrentWorkers
if maxWorkers < 3 { maxWorkers = 3 }
wg.SetLimit(maxWorkers)
```

（`onlinepusher.go:84-91`）

这个是 **semaphore 模式**（不完全算 worker pool）——每个网关节点一个 goroutine，用 `SetLimit` 限制同时进行数。因为节点数不多（几十个），不需要池。

### 2.5 模式五：errgroup 扇出（带限流的广播）

**问题**：网关收到「用户 X 上线了」，要通知**所有其他网关节点**（这样其他节点才知道 X 在线，才能把消息路由过去）。节点可能有几十个，串行太慢，全并发可能打爆。

**代码**（`ws_server.go:230-252`）：

```go
func (ws *WsServer) sendUserOnlineInfoToOtherNode(ctx context.Context, client *Client) error {
    conns, err := ws.disCov.GetConns(ctx, ws.msgGatewayConfig.Discovery.RpcService.MessageGateway)
    if err != nil { return err }
    if len(conns) == 0 || (len(conns) == 1 && ws.disCov.IsSelfNode(conns[0])) {
        return nil                                     // 只有一个节点（就是自己），不用广播
    }

    wg := errgroup.Group{}
    wg.SetLimit(concurrentRequest)                     // 3

    for _, v := range conns {
        v := v                                          // ← 闭包捕获，必须！
        if ws.disCov.IsSelfNode(v) {
            continue                                    // 不给自己发
        }
        wg.Go(func() error {
            msgClient := msggateway.NewMsgGatewayClient(v)
            _, err := msgClient.MultiTerminalLoginCheck(ctx, &msggateway.MultiTerminalLoginCheckReq{...})
            if err != nil {
                log.ZWarn(ctx, "MultiTerminalLoginCheck err", err)   // ← 记日志但不返回错误
            }
            return nil
        })
    }
    _ = wg.Wait()                                      // ← 忽略了错误
    return nil
}
```

**四个细节都值得说**：

1. **`SetLimit(3)` 为什么是 3**？`const concurrentRequest = 3`（`ws_server.go:229`）。节点数少的时候无所谓，节点多的时候 3 太小——100 个节点要 33 轮。这个值应该跟节点数挂钩（比如 `min(len(conns), 32)`）。

2. **`v := v`**：Go 1.22 之前必须写，否则所有 goroutine 共享同一个 `v`。

3. **错误被吞掉**：`log.ZWarn` 后 `return nil`。为什么？因为「通知其他节点失败」不影响本机登录成功。但**后果是**：其他节点不知道这个用户在线，消息路由可能走错（把消息发到没有该连接的节点）。📌 这是一个**最终一致性漏洞**，靠「其他节点收到消息后发现本地没连接，再转发」兜底（如果有这个机制的话）。

4. **`_ = wg.Wait()`**：既然错误都被吞了，`Wait` 的返回值必然是 nil，忽略是自洽的。

**对比另一处 errgroup**（`rpccache/conversation.go`）：用于**缓存预热**——并发拉取多个会话的数据。那里的错误处理更严格（有错误要上报）。

### 2.6 模式六：原子操作 + 对象池

**原子的三个用法**：

**① 幂等关闭（`client_conn.go:63-72`）**：已在 1.10 讲。

**② 在线状态上报的随机因子（`online.go:47`）**：

```go
rNum := rand.Uint64()
pushUserState := func(us ...UserState) {
    for _, u := range us {
        sum := md5.Sum([]byte(u.UserID))
        i := (binary.BigEndian.Uint64(sum[:]) + rNum) % uint64(concurrent)
        changeStatus[i] = append(changeStatus[i], u)
        ...
    }
}
```

用 `md5(userID) + 随机数` 取模来分配 channel。**加随机数是为了「同一批用户的分布也均匀」**——如果只用 md5，每次运行的分片结果一样，可能导致某些 channel 永远更忙。加个进程启动时的随机偏移，可以让负载在多次运行间打散。

📌 这是「一致性哈希」和「均匀分布」的折中：纯哈希保证稳定，加随机保证均匀。这里选了均匀（因为不需要稳定性）。

**③ 计数器**：`hub_server.go`、`ws_server.go` 里用 `atomic.Int64` 统计连接数等。

**对象池的三处用法**：

**① gzip 复用（`compressor.go:13-14`）**：

```go
gzipWriterPool = sync.Pool{New: func() any { return gzip.NewWriter(nil) }}
gzipReaderPool = sync.Pool{New: func() any { return new(gzip.Reader) }}
```

`gzip.Writer` 内部有 32KB 的字典缓冲，创建成本高（要初始化哈希表）。压消息时每条都新建会很浪费。

⚠️ **复用 gzip.Writer 必须调 `Reset(w io.Writer)`**，否则它会继续往旧 writer 写。📌 需要确认 `compressor.go` 的 `Put` 前有没有 `Reset`。

**② 请求对象复用（`message_handler.go:48`）**：

```go
var reqPool = sync.Pool{ ... }
```

复用 WS 请求的解析结构体，避免每条消息都分配。

**③ 连接对象复用（`ws_server.go:59`、`:155`）—— 这个是坏的**：

```go
clientPool sync.Pool
...
clientPool: sync.Pool{
    New: func() any { return &Client{} },
}
```

但全项目搜索 `clientPool.Get`，**一处都没有**。只有 `Put`。也就是说：**池子一直在被塞，从来没被取**。

⚠️ 后果：
- 每次 `Put` 的对象在下次 GC 时被清空（sync.Pool 的语义），所以不会内存泄漏
- 但**完全没起作用**：`Put` 的成本（加锁、写 per-P 缓存）白花了
- 更糟的是**误导读者**：看到 `clientPool` 会以为「连接对象是复用的」，实际上每次 `&Client{}` 都是新分配

📌 这是一个典型的「写了但没接上」的代码。面试时可以讲：「我看到它定义了 clientPool，但全项目只有 Put 没有 Get，对象池被当垃圾桶用了。」

### 2.7 模式七：跨进程并发控制

单机内的锁解决不了「多个进程同时干同一件事」。OpenIM 有三层跨进程控制：

**① 分布式锁（定时任务）**

`internal/tools/cron/redis_locker.go:36-68`：

```go
func (e *RedisLocker) lock(ctx context.Context, name string, owner string) (bool, error) {
    ctx, cancel := context.WithTimeout(ctx, time.Second)
    defer cancel()
    return e.client.SetNX(ctx, e.getKey(name), owner, lockLeaseTTL).Result()
}

func (e *RedisLocker) unlock(ctx context.Context, name string, owner string) error {
    return e.script.Run(ctx, e.client, []string{e.getKey(name)}, owner).Err()
}
```

解锁的 Lua：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**为什么解锁必须用 Lua**？因为「GET 判断是自己的锁」和「DEL」之间如果有间隙，可能出现：

```
t1  进程 A: GET lock → "owner-A"，是我的
t2  （A 的锁 TTL 到期，自动删除）
t3  进程 B: SETNX lock "owner-B" → 成功
t4  进程 A: DEL lock → 把 B 的锁删了！
```

Lua 保证「判断 + 删除」原子执行，消灭这个窗口。**这是分布式锁的必修课**，面试常考。

`lockLeaseTTL` 是锁的租约——如果持锁进程崩了，TTL 到期自动释放，不会永久死锁。代价是「任务执行时间必须 < TTL」，否则锁提前释放，两个进程同时跑。

**② etcd lease（服务注册）**

etcd 的 lease 已在 25 篇 1.8 讲过，本质是「带 TTL 的 key + 客户端续约」。

**③ 进程级限流与熔断**

`pkg/common/startrpc/ratelimit.go` 和 `circuitbreaker.go`：

```go
// 限流：BBR
bbr.NewBBRLimiter(
    bbr.WithWindow(config.Window),           // 20s
    bbr.WithBucket(config.Bucket),           // 500 个桶
    bbr.WithCPUThreshold(config.CPUThreshold), // 850 (=85%)
)

// 熔断：SRE（滑动窗口成功率）
sre.NewSREBraker(
    sre.WithWindow(config.Window),
    sre.WithBucket(config.Bucket),
    sre.WithSuccess(config.Success),         // 成功率阈值
    sre.WithRequest(config.Request),         // 最小请求数
)
```

**BBR 限流的原理**（和 TCP BBR 拥塞控制同源）：不看 QPS 绝对值，看**延迟和 CPU**。

- 如果 CPU < 阈值，认为「还有余力」，放行
- 如果 CPU 接近阈值，开始限制
- 核心思想：**用系统的真实负载（CPU/延迟）决定限流，而不是拍一个 QPS 数字**

好处：不用压测就能找到容量上限，自动适应机器配置。

**SRE 熔断的原理**：滑动窗口（10 个桶）统计成功率和请求数，低于阈值就「打开」（拒绝所有请求），过一段时间「半开」（放少量请求试探）。

⚠️ **熔断的一个精妙细节**（`circuitbreaker.go:60-75`）：

```go
if err != nil {
    if st, ok := status.FromError(err); ok {
        switch st.Code() {
        case codes.OK:
            breaker.MarkSuccess()
        case codes.InvalidArgument, codes.NotFound, codes.AlreadyExists, codes.PermissionDenied:
            breaker.MarkSuccess()      // ← 业务错误不算失败！
        default:
            breaker.MarkFailed()
        }
    } else {
        breaker.MarkFailed()
    }
}
```

**「参数错、找不到、已存在、没权限」被标记为成功**。为什么？因为这些是**业务语义上的正常结果**，不是服务故障。如果把它们算失败，用户疯狂试错就会触发熔断，把正常用户也挡住。

**这是熔断器最容易做错的地方**——区分「服务不可用」和「请求不合理」。

### 2.8 五个反面教材（写错了但没崩）

这些是读代码时挖出来的，**面试时讲这些比背架构图有说服力**。

**反面 1：`RLock` 下写共享字段（`user_map.go:185-205`）**

```go
func (u *userMap) GetAllUserStatus(deadline time.Time, nowtime time.Time) (result []UserState) {
    u.lock.RLock()
    defer u.lock.RUnlock()
    result = make([]UserState, 0, len(u.data))
    for userID, userPlatform := range u.data {
        if deadline.Before(userPlatform.Time) {
            continue
        }
        userPlatform.Time = nowtime          // ← 写！在 RLock 下
        ...
    }
    return result
}
```

**问题**：`RLock` 允许多个 goroutine 同时进入，它们都在写 `userPlatform.Time` → **数据竞争**。两个 goroutine 同时写同一个 `time.Time`（24 字节结构），可能写出撕裂的值（前 8 字节是 A 的，后 16 字节是 B 的）。

**实际后果**：`Time` 只用于「判断是否需要上报在线状态」，撕裂的值最多导致一次多余或遗漏的上报，不会崩。所以**跑了很久没出事**。

**但 race detector 一定会报**。修法：要么改成 `Lock()`（代价是失去并发读），要么把 `Time` 的更新移到另一个只写的地方（比如上报完成后统一更新）。

**反面 2：`GetAll` 返回内部切片（`user_map.go:97-105`）**

```go
func (u *userMap) GetAll(userID string) ([]*Client, bool) {
    u.lock.RLock()
    defer u.lock.RUnlock()
    result, ok := u.data[userID]
    if !ok { return nil, false }
    return result.Clients, true          // ← 直接返回内部切片
}
```

**问题**：调用方拿到 `Clients` 后，如果遍历时另一个 goroutine 调了 `DeleteClients`（`result.Clients = result.Clients[:0]` + 重新 append），会发生**切片底层数组被改写**，遍历到脏数据。

**为什么没出事**：`DeleteClients` 用的是 `result.Clients[:0]` 复用底层数组，但遍历方通常是「读一份副本后立刻用」，窗口很小。**属于「概率性正确」**。

**修法**：`GetAll` 返回拷贝（`make` + `copy`）。代价是每次分配，但连接数不多，值得。

**反面 3：`RecvSubChange` 里的 `push` 也在 RLock 下（`user_map.go:67-82`）**

```go
func (u *userMap) RecvSubChange(userID string, platformIDs []int32) bool {
    u.lock.RLock()
    defer u.lock.RUnlock()
    ...
    u.push(userID, result, nil)          // push 里写 result.Time
    return true
}
```

同上。

**反面 4：`clientPool` 只 Put 不 Get（`ws_server.go:59,155`）**

已在 2.6 讲。

**反面 5：`SetKickHandlerInfo` 阻塞发送（`ws_server.go:254-256`）**

```go
func (ws *WsServer) SetKickHandlerInfo(i *kickHandler) {
    ws.kickHandlerChan <- i        // 没有 select/default，没有超时
}
```

**问题**：`kickHandlerChan` 缓冲 1000，满了就阻塞调用方。调用方是登录流程（HTTP handler），阻塞会影响登录。

**为什么没出事**：正常情况踢人事件很少，1000 的缓冲几乎不可能满。**但只要事件循环因为某个 RPC 卡住（比如 `multiTerminalLoginChecker` 里同步调用超时），就会积压**。

**这是一个「正常运行完全没问题，故障时雪崩」的模式**——最危险的一类。

📌 **面试时怎么讲这五个**：

> 我在读网关代码时注意到几个并发细节。比如 `user_map.GetAllUserStatus` 在 `RLock` 保护下修改了 `userPlatform.Time`，这是读写锁误用，`-race` 能抓出来，只是影响面小（最坏是一次在线状态上报错乱）所以没暴露。还有 `clientPool` 定义了 `sync.Pool` 但全项目只有 `Put` 没有 `Get`，对象池完全没起作用。这类问题不影响功能，但说明代码在演进中缺少 review。

2. 一个 goroutine 初始占多少内存？为什么 20 万 goroutine 可行，20 万线程不可行？

6. worker pool 和 semaphore 的区别是什么？`errgroup.SetLimit` 属于哪个？
7. `counter.Add(1)` 为什么必须在「发送到 channel」之前？

9. `sync.Pool` 里的对象会不会在 GC 时被清空？这导致它不能当什么用？
10. 熔断器为什么要把 `InvalidArgument`、`NotFound` 算作「成功」？
11. `user_map.GetAllUserStatus` 的并发问题是什么？race detector 能抓到吗？
12. 分布式锁的解锁为什么必须用 Lua？

<details>
<summary>参考答案</summary>

1. 并发是「同时处理」（结构），并行是「同时执行」（物理）。后端服务大部分时间在等 I/O 而非算 CPU，所以「一个请求一个 goroutine」能用很小的成本撑起海量并发。
2. 2KB。线程初始栈 1~8MB 且固定，20 万线程 = 200GB+；goroutine 栈可增长，20 万 × 2KB = 400MB 量级。
3. 让数据只被一个 goroutine 拥有，其他 goroutine 通过发消息来改它。反例：高频读、极少写的数据（如连接表）用 channel 每次读都要发消息，开销远大于 RWMutex。
4. 全局锁 / 分段锁 / 单 goroutine 拥有。连接表用全局 RWMutex，因为读多写少、读锁之间不互斥，且多网关节点已在架构上分摊了压力，分段锁收益有限而复杂度高。
5. 阻塞、丢弃、断开。网关用断开（`ErrWriteFull`）。因为扇出场景下一个慢客户端会阻塞共享的推送 goroutine，拖垮整个群；断开的代价由 seq 补偿机制兜住。
6. worker pool 是固定 N 个 goroutine 从队列取任务（任务数不可预测）；semaphore 是每个任务一个 goroutine，但限制同时运行数（任务数已知）。`SetLimit` 是 semaphore。
7. 如果先发再 Add，worker 可能在 Add 之前就处理完并 `Done()`，导致计数器变负，`Wait()` 提前返回，批次没处理完就提交位点 → 丢消息。
8. 解决「多个 goroutine 同时发现连接坏了，都去 close(done) 导致 panic」。CAS 保证只有一个执行 close，且后续调用者能拿到第一次的错误原因；`sync.Once` 拿不到原因。
9. 会（每次 GC 清空 per-P 缓存以外的对象）。所以不能当缓存用——Put 进去的对象可能在下次 Get 时消失。
10. 因为它们是「请求本身不合理」，不是「服务故障」。如果算失败，用户反复试错就会触发熔断，把正常用户也挡住。
11. 在 `RLock` 保护下写 `userPlatform.Time`，多个读者并发写同一字段。race detector 能抓到；实际影响小（最坏是一次在线状态上报错乱）所以没暴露。
12. 因为「GET 判断是自己的锁」和「DEL」之间有窗口：锁可能在判断后、删除前过期并被别人抢到，此时 DEL 会删掉别人的锁。Lua 保证原子。

</details>

## 面试话术

**问：Go 的并发模型你怎么理解？**

> Go 的并发模型是 CSP 思想的实现，核心是「goroutine + channel」。但我实际用下来，判断标准不是「尽量用 channel」，而是看数据特征：读多写少的共享状态用 RWMutex，所有权需要转移的用 channel，单纯计数器用 atomic。比如 OpenIM 网关的连接表是读多写少（每次推消息都查，只在登录登出时改），用一把 RWMutex；而连接的增删必须严格串行否则「注册」和「踢人」会打架，所以用单 goroutine 事件循环 + channel。两种都用，是因为场景不同。

**问：你的项目里并发最高到多少？怎么控制的？**

> 分三层。连接层：每个 WebSocket 至少 2 个 goroutine（读循环 + 写循环），单网关 10 万连接就是 20 万 goroutine，靠 Go 的 2KB 初始栈才撑得住。消息层：50 个 worker 按会话 ID 哈希分片，保证同会话保序、不同会话并行，缓冲 3000 条。推送层：512 个 worker + 16384 缓冲的内存队列。三层的背压策略不一样——连接层是「满了断开」，消息层是「满了阻塞传导到 Kafka」，推送层是「阻塞 + 边界处断开慢客户端」。选哪种取决于「丢了能不能自愈」：有 seq 补偿的可以丢，没有的必须阻塞。

**问：怎么避免并发 bug？**

> 四个层次。最优先是「不共享」——每个 goroutine 自己持有数据；其次是「共享但不可变」——配置加载后只读；再次是「加锁」；最差是「靠约定」。OpenIM 里三种都有，比如 `client_conn` 用 `atomic.Pointer[error]` + CAS 做幂等关闭，比 `sync.Once` 好在能保留第一次的错误原因；而 `user_map` 里有一处 `RLock` 下写字段的误用，`-race` 能抓出来，只是因为影响面小（在线状态上报错乱会自愈）才没暴露。所以我的习惯是 CI 里一定跑 `go test -race`。

**问：分布式锁怎么实现？有什么坑？**

> Redis 用 `SETNX key owner TTL` 加锁，解锁必须用 Lua：`if get(key)==owner then del(key) end`。因为「判断是不是自己的锁」和「删除」之间如果锁过期被别人抢到，直接 DEL 会删掉别人的锁。所以判断+删除必须原子。还有一个坑是 TTL 和任务耗时的关系：TTL 太短任务没跑完锁就释放了，两个实例会同时执行；TTL 太长实例崩了要等很久才释放。OpenIM 的定时任务用 Redis 锁，服务注册用 etcd lease，都是这个思路。

**问：你读过的最有价值的代码是什么？**

> 有一个我印象很深：网关的 WebSocket 写缓冲满了之后不是阻塞，而是直接 `close` 连接并返回 `ErrWriteFull`。我一开始觉得这不是丢消息吗？后来想通了——推送是扇出场景，一个慢客户端阻塞的是共享的推送 goroutine，会拖垮整个群；而断开之后客户端重连会报自己的 maxSeq，服务端从 Redis 补发，所以「断开不是丢消息，是换一种方式交付」。这个决策的前提是系统有 seq 补偿机制——如果换成没有离线补拉的系统，就必须阻塞或者扩容。这让我理解了「设计决策必须放在具体约束里看」。
