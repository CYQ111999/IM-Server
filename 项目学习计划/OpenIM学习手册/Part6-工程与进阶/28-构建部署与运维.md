## 第一部分 纯理论：从源码到能跑的服务

### 1.1 构建到底在做什么

`go build ./cmd/openim-api` 做四件事：

```
1. 解析依赖（go.mod / go.sum）→ 下载模块到 GOMODCACHE
2. 编译（每个 package → .a 归档文件）→ 缓存在 GOCACHE
3. 链接（所有 .a + runtime → 一个可执行文件）
4. 嵌入调试信息（符号表、文件路径、行号）
```

**关键认知：Go 编译产出的是「静态链接的单个二进制」**（默认不带 CGO 时）。

这意味着：
- 不依赖 libc（除了 DNS 解析某些情况）
- 拷到任何同架构的 Linux 上都能跑
- 这正是「alpine 镜像 + 静态二进制」能成立的前提

**为什么需要 mage 这种构建工具？**

因为真实项目不是「编译一个包」，而是：

```
12 个服务二进制 + 7 个工具二进制
每个都要：指定输出目录、可能交叉编译、可能压缩、可能注入版本号
还要：启动、停止、检查状态
```

手写 shell 脚本能实现，但跨平台差（Windows 的 bash 很难搞）。**mage 的思路是「用 Go 写构建脚本」**——`magefile.go` 就是一个普通 Go 文件，用 `//go:build mage` 标签隔离，`mage build` 时被编译执行。

好处：
- 跨平台（Go 本身就是跨平台的）
- 能用 Go 的类型和库（不用折腾 shell 引号）
- IDE 支持（能跳转、能补全）

### 1.2 交叉编译与 CGO

```bash
# 编译 Linux amd64 的二进制（在 macOS/Windows 上也能做）
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o app ./cmd
```

两个变量：

| 变量 | 作用 | 影响 |
|---|---|---|
| `GOOS` / `GOARCH` | 目标平台 | 决定二进制能在哪跑 |
| `CGO_ENABLED` | 是否启用 C 互操作 | `0` = 纯静态；`1` = 依赖 libc |

**为什么 `CGO_ENABLED=0` 很重要**：

- 开了 CGO，二进制会**动态链接** libc。放到 `alpine`（用 musl libc）里会报 `not found` 或 `version GLIBC_2.xx not found`
- 关了 CGO，二进制是**完全静态**的，能跑在任何 Linux 上（包括 alpine、scratch）

**代价**：关掉 CGO 后，DNS 解析用 Go 自己实现的解析器（不走 glibc 的 nsswitch），某些特殊配置（如 `/etc/nsswitch.conf` 里的 LDAP 用户解析）会失效。**IM 服务不需要这些，所以关掉是纯赚**。

📌 本仓库的 Dockerfile **没有显式设 `CGO_ENABLED=0`**（`Dockerfile:12` 只有 `RUN RELEASE=${RELEASE} COMPRESS=${COMPRESS} mage build`）。但 `mageutil.ResolveBuildOptions` 会读 `CGO_ENABLED` 环境变量（`build.go:170`），默认值取决于基础镜像。`golang:alpine` 默认 `CGO_ENABLED=0`（因为没有 gcc），所以实际是静态编译。**这是一个隐式依赖，依赖了基础镜像的默认值**。

### 1.3 多阶段构建：为什么 Dockerfile 要写两个 FROM

```dockerfile
FROM golang:alpine AS builder     # 阶段 1：编译
...编译...
FROM alpine:latest                 # 阶段 2：运行
COPY --from=builder /openim-server/_output ./_output
```

**如果不分阶段会怎样**：

```dockerfile
FROM golang:alpine
COPY . .
RUN mage build
ENTRYPOINT ["./mage", "start"]
```

镜像大小：`golang:alpine` ≈ **300MB**（含 Go 工具链、gcc、git）。而运行时真正需要的只有：
- 编译好的二进制（约 100MB）
- 配置文件（几十 KB）
- 一个能跑二进制的 shell

多阶段构建的价值：**最终镜像只含运行所需**，把编译工具链丢在 builder 阶段。

| 方案 | 镜像大小 |
|---|---|
| 单阶段（golang:alpine） | ~400MB |
| 多阶段（alpine + 二进制） | ~180MB |
| scratch + 静态二进制 | ~110MB |

**为什么选 `alpine` 而不是 `scratch`**：
- `scratch` 是空镜像，没有 shell、没有 `ca-certificates`、没有时区文件
- IM 服务要发 HTTPS 请求（webhook）、要读 `Asia/Shanghai` 时区 → 需要 `ca-certificates` 和 `tzdata`
- `alpine` 自带这些，且只有 5MB

⚠️ **`alpine` 的坑**：它用 musl libc 而不是 glibc。任何 CGO 编译的二进制放进去都会挂。所以「`CGO_ENABLED=0` + alpine」是**绑定关系**，缺一不可。

### 1.4 容器的 PID 1 问题（这篇最重要的坑）

**现象**：容器里的 Go 服务收到 `SIGTERM` 后**不退出**，等 10 秒被 `SIGKILL` 强杀。

**原因**：Linux 内核有个特殊规则——**PID 1 进程会忽略没有注册 handler 的信号**。这是为了保护 init 进程不被误杀。

在容器里，`ENTRYPOINT` 指定的进程就是 PID 1：

```dockerfile
ENTRYPOINT ["sh", "-c", "./mage start && sleep infinity"]
```

这里 PID 1 是 **`sh`**，不是你的 Go 服务。所以：
- `docker stop` 发 `SIGTERM` → 发给 `sh`
- `sh` 默认不转发信号给子进程
- Go 服务收不到 `SIGTERM`，不会优雅退出
- 10 秒后 `SIGKILL` 全杀

**看 OpenIM 的写法**（`Dockerfile:27`）：

```dockerfile
ENTRYPOINT ["sh", "-c", "./mage start && sleep infinity"]
```

**问题更大**：`mage start` 是**启动完就返回**的（它 `exec.Command(...).Start()` 后不 wait），所以：
1. `mage start` 拉起 29 个进程（都是 `sh` 的孙子进程）
2. `mage start` 返回 0
3. 执行 `sleep infinity` —— **PID 1 变成 `sleep`**
4. `docker stop` 发 SIGTERM 给 `sleep`，`sleep` 直接死了
5. **29 个 Go 进程变成孤儿进程**，被 PID 1 收养……但 PID 1 已经死了，容器直接退出，所有进程被 SIGKILL

**结论：这个 ENTRYPOINT 会导致「完全无法优雅停止」**。

正确写法有三种：

**① 用 `exec` 让主进程变成 PID 1**

```dockerfile
ENTRYPOINT ["./openim-api"]      # 直接跑一个服务
```

但 OpenIM 一个容器要跑 29 个进程，不适合。

**② 用 tini / dumb-init 做 init**

```dockerfile
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--", "sh", "-c", "./mage start && sleep infinity"]
```

`tini` 会转发信号给子进程组，并回收僵尸进程。

**③ 用 supervisor / s6-overlay 管理多进程**

生产级方案，能处理「某个子进程挂了自动重启」。

📌 **这是一个可以在面试里讲的真实问题**：「它的 Dockerfile 用 `sh -c "./mage start && sleep infinity"` 做 ENTRYPOINT，PID 1 是 `sleep`，收不到信号，29 个子进程全变孤儿。正确做法是加 tini 或者用 supervisor。」

### 1.5 文件描述符上限：网关的生死线

**一个 TCP 连接占一个 fd（文件描述符）**。WebSocket 长连接更是如此。

Linux 默认 `ulimit -n` 是 **1024**（软限制）。这意味着：**一个进程最多 1024 个连接**。

网关要支撑 10 万连接，必须把这个限制提到 10 万以上。

**两个层面都要改**：

**① 系统层面**（宿主机 / 容器）

```bash
# 临时
ulimit -n 100000
# 永久：/etc/security/limits.conf
* soft nofile 100000
* hard nofile 100000
```

**② 进程层面**（`mage start` 做的事）

`magefile.go:62-68`：

```go
func Start() {
    mageutil.InitForSSC()
    err := setMaxOpenFiles()          // ← 提 fd 上限
    if err != nil { ... }
    ...
}
```

`magefile_unix.go`：

```go
func setMaxOpenFiles() error {
    var rLimit syscall.Rlimit
    if err := syscall.Getrlimit(syscall.RLIMIT_NOFILE, &rLimit); err != nil {
        return err
    }
    rLimit.Max = uint64(mageutil.MaxFileDescriptors)    // 10000
    rLimit.Cur = uint64(mageutil.MaxFileDescriptors)
    return syscall.Setrlimit(syscall.RLIMIT_NOFILE, &rLimit)
}
```

值来自 `start-config.yml`（`maxFileDescriptors: 10000`）。

⚠️ **这里有个问题**：`syscall.Setrlimit` 只影响**当前进程及其子进程**。`mage start` 在启动子进程之前调这个，子进程会继承 → **是对的**。

但 **10000 远远不够**。一个网关 10 万连接需要 **20 万+ fd**（每个连接 1 个 socket + 日志文件 + 各种连接池）。10000 只够 **5000 个连接**左右。

📌 **这是一个「配置值与目标场景不匹配」的例子**：文档说支持海量连接，但配置文件里是 10000。生产部署必须调大。

**另外**：Windows 没有 `RLIMIT_NOFILE`，所以有 `magefile_windows.go`（8 行，大概是空实现）。这是「跨平台构建脚本」的必要妥协。

### 1.6 GOMAXPROCS 与容器 CPU limit：一个隐蔽的性能陷阱

**问题**：Go 1.25 之前（以及很多老项目），`runtime.GOMAXPROCS(0)` 默认返回**宿主机 CPU 核数**，而不是容器的 CPU limit。

场景：
- 宿主机 64 核
- 容器 limit 2 核
- Go 看到 64，启动 64 个 P（逻辑处理器）
- 64 个 P 争抢 2 核的 CPU 时间 → **上下文切换爆炸**、GC 线程抢不到 CPU、延迟抖动

**解法：automaxprocs**

```go
import "go.uber.org/automaxprocs/maxprocs"

func main() {
    maxprocs.Set()      // 读 cgroup 的 CPU quota，自动设 GOMAXPROCS
}
```

**OpenIM 里的证据**：`tools/ncpu/main.go` 就是干这个的：

```go
import (
    "go.uber.org/automaxprocs/maxprocs"
)

func main() {
    maxprocs.Set(maxprocs.Logger(func(string, ...interface{}) {}))   // 静默
    fmt.Println(runtime.GOMAXPROCS(0))                                // 打印实际值
}
```

📌 **但这个工具只是个「打印器」**，服务进程自己有没有调 `maxprocs.Set()` 需要核实。搜索结果里 `cmd/main.go` 没有 import automaxprocs。所以：

- **如果服务没调 automaxprocs**：容器里 GOMAXPROCS = 宿主机核数，有 1.6 说的性能问题
- **`ncpu` 工具的作用**：让你手动查「如果调了 automaxprocs，GOMAXPROCS 会是多少」，用来验证 cgroup 配置对不对

**Go 1.25 的改进**：Go 1.25 起，runtime **默认感知 cgroup CPU limit**，不再需要 automaxprocs。📌 本项目 go.mod 的 Go 版本需要核实，如果是 <1.25，就需要显式调。

### 1.7 中间件编排：compose 的三件事

`docker-compose.yml` 负责起 11 个容器：

| 服务 | 镜像 | 端口映射 | 用途 |
|---|---|---|---|
| `mongodb` | `${MONGO_IMAGE}` | 37017:27017 | 主数据库 |
| `redis` | redis | 16379:6379 | 缓存/seq/token |
| `etcd` | etcd | 12379:2379 | 服务注册 |
| `kafka` | kafka | 19094:9092 | 消息队列 |
| `minio` | minio | 10005:9000 | 对象存储 |
| `openim-web-front` | — | — | 演示前端 |
| `prometheus` | prom/prometheus | 19090 | 指标 |
| `alertmanager` | prom/alertmanager | 19093 | 告警 |
| `grafana` | grafana | 13000 | 面板 |
| `node-exporter` | prom/node-exporter | 19100 | 主机指标 |

**三件编排的事**：

**① 网络**

```yaml
networks:
  openim:
    driver: bridge

services:
  mongodb:
    networks:
      - openim
```

所有容器在同一个 bridge 网络里，**可以用服务名互相访问**（`mongodb:27017` 而不是 `127.0.0.1:37017`）。

⚠️ **这是新手最容易混的地方**：
- 容器之间通信用 **服务名 + 容器内端口**（`mongodb:27017`）
- 宿主机访问用 **127.0.0.1 + 映射端口**（`127.0.0.1:37017`）
- 本机跑的 Go 服务（`mage start`）属于「宿主机」，所以 `config/mongodb.yml` 里要写 `127.0.0.1:37017`

**这就是为什么 OpenIM 的端口映射都很怪**（37017、16379、19094…）：**为了避免和宿主机上已有的同名服务冲突**。用户的机器上可能有原生 Redis(6379)，所以把它映射到 16379。

**② 数据卷**

```yaml
volumes:
  - ./components/mongodb/data/db:/data/db
```

把容器内的数据目录挂到宿主机。**这是「容器删了数据还在」的唯一保证**。

⚠️ **绝对不要删 `components/`**：里面有 Mongo 的 305MB 数据、Kafka 的 1.7GB 日志、etcd 的数据。删了等于删库。

**③ 初始化脚本**

MongoDB 的 `command` 里有一大段 bash：启动 mongod → 轮询 ping → 创建业务库和用户。这是「**容器自举**」——容器第一次启动时自动完成初始化，不需要人工执行 SQL。

```yaml
command: >
  bash -c '
  docker-entrypoint.sh mongod --wiredTigerCacheSizeGB $$wiredTigerCacheSizeGB --auth &
  until mongosh ... --eval "db.runCommand({ ping: 1 })" &>/dev/null; do
    echo "Waiting for MongoDB to start..."
    sleep 1
  done &&
  mongosh ... --eval "db = db.getSiblingDB(\"$$MONGO_INITDB_DATABASE\"); ..."
  '
```

注意 `$$` 是 compose 的转义（避免被 compose 自己解析成变量），实际传给容器的是 `$wiredTigerCacheSizeGB`。

### 1.8 自检：为什么需要重试 180 次

`tools/check-component` 做的事：连一下五个中间件，能连上就退出 0，连不上就退出 1。

**为什么需要它**：

- 中间件容器 `docker compose up -d` 之后，**进程起来了不等于服务可用**。Mongo 要建索引、Kafka 要选 leader、etcd 要选主，都需要几秒到几十秒
- 如果服务先起来，连不上中间件会**直接退出**（fail fast），然后 Docker 的重启策略会一直重启，形成「重启风暴」
- 所以标准流程是：**先自检通过，再启动服务**

**为什么重试 180 次**（`check-component/main.go:23`）：

```go
const maxRetry = 180
```

180 次 × 1 秒 = **3 分钟**。这是「最坏情况下 Kafka 集群恢复」的时间量级。

📌 这是一个**经验值**：太小（比如 10 次）会在慢机器上误报失败；太大（比如 1 小时）会让启动卡很久才发现问题。3 分钟是个合理折中。

**五样检查**（`main.go:38-68`）：

| 函数 | 检查什么 | 用的库 |
|---|---|---|
| `CheckMongo` | 连接 + ping | `mongoutil.Check` |
| `CheckRedis` | 连接 + ping | `redisutil.Check` |
| `CheckKafka` | `CheckHealth`（建 topic + 元数据） | `kafka.CheckHealth` |
| `CheckMinIO` | 连接 + bucket 是否存在 | `minio.Check` |
| `CheckEtcd` | 连接 + 写一个 key | `etcd.Check` |

**为什么 Kafka 的检查是 `CheckHealth` 而不是简单 ping**：Kafka 的「客户端能连上 broker」不等于「能正常生产和消费」。`CheckHealth` 会尝试获取元数据、检查 topic 是否存在，更接近真实可用性。

### 1.9 K8s 部署：StatefulSet 与 Deployment 的区别

`deployments/deploy/` 下有 20+ 个 k8s 清单，分两类：

| 类型 | 用于 | 特点 |
|---|---|---|
| **StatefulSet** | mongo、kafka、minio、etcd | 有状态：固定网络标识、按序启动、独立 PVC |
| **Deployment** | openim-api、rpc-*、msggateway、push、msgtransfer | 无状态：Pod 可随意替换、滚动更新 |

**为什么有状态服务必须用 StatefulSet**：

- Kafka 的 broker.id 和存储绑定，重启后必须是「同一个 Pod」才能找到自己的数据
- Mongo 的副本集成员靠主机名识别，Pod 名变了就认不出来
- StatefulSet 给每个 Pod 固定的名字（`kafka-0`、`kafka-1`）+ 固定的 PVC

**为什么无状态服务用 Deployment**：

- Pod 名随机（`openim-api-7d8f9-abc12`），挂了直接换新的
- 可以任意副本数、滚动更新
- 服务注册靠 etcd，不依赖 Pod 身份

📌 **这也解释了为什么 OpenIM 的服务能拆成 29 个进程**：因为它们**都是无状态的**（连接状态在网关，但网关自己也是「每个节点管自己的连接」，节点挂了客户端重连即可）。

**K8s 里的配置差异**：`start-config.yml` 的 `maxFileDescriptors` 在 K8s 里不起作用（容器有独立的 limit），所以 `mageutil` 有 `DeploymentType == KUBERNETES` 的分支（`process_controller.go:44-47`），切到 `Paths.K8sConfig`。

### 1.10 代码质量门禁：golangci-lint

`.golangci.yml` 是 golangci-lint 的配置（700+ 行）。关键配置：

```yaml
run:
  concurrency: 4
  timeout: 5m
  tests: true

linters:
  disable-all: true       # 不用 enable-all（已废弃）
  enable:
    - typecheck           # 基础类型检查
    - gofmt               # 格式
    - ...（还有几十个）
```

**`disable-all: true` + 显式 enable 的意义**：**锁定规则集**。如果不禁用，golangci-lint 升级会带来新规则，CI 突然红一片。

**几个值得注意的规则**（`revive` 段）：

```yaml
- name: line-length-limit
  severity: error
  arguments: [200]        # 单行不超过 200 字符
- name: unhandled-error
  arguments: ["fmt.Printf", "myFunction"]    # 忽略这些函数的错误
- name: atomic
- name: exported
```

**`line-length-limit: 200`**：Go 社区通常建议 120，但 Go 的 `if err != nil {` 嵌套很容易超。200 是「宽松但有用」的设定。

**`unhandled-error` 忽略 `fmt.Printf`**：因为 `fmt.Printf` 返回值基本没人检查。这是「规则要贴合实际」的例子。

📌 **注意 `.golangci.yml` 里 `build-tags: [mytag]`**（第 19 行）——这是一个**奇怪的配置**，项目里没有 `mytag` 标签的代码。可能是从模板复制来的残留。这会导致 lint 时按「有 mytag」编译，可能漏掉一些文件。

## 第二部分 源码实现

### 2.1 magefile：5 个命令（`magefile.go`）

```go
var Default = Build          // mage 不带参数时默认执行 Build

var Aliases = map[string]any{
    "buildcc": BuildWithCustomConfig,
    "startcc": StartWithCustomConfig,
}
```

| 命令 | 做什么 | 关键点 |
|---|---|---|
| `mage build` | 编译所有服务 + 工具 | 默认命令 |
| `mage build <bin...>` | 只编译指定的 | `mage build openim-api seq` |
| `mage start` | 提升 fd 上限 → 自检工具 → 杀旧进程 → 启动 29 个 | |
| `mage stop` | 停所有进程 | |
| `mage check` | 检查二进制状态 | |
| `mage export` | 打包成压缩包 | 发版用 |

**`Build` 的实现**（`magefile.go:34-41`）：

```go
func Build() {
    flag.Parse()
    bin := flag.Args()
    if len(bin) != 0 {
        bin = bin[1:]         // ← 去掉 mage 自己的子命令名
    }
    mageutil.WithSpinner("Building binaries...", func() { mageutil.Build(bin, nil, nil) })

```

### 2.2 `mageutil.Build`：怎么知道要编译哪些

`getBinaries`（`build.go:298-327`）：

```go
sources := []binarySource{
    {baseDir: filepath.Join(Paths.Root, Paths.SrcDir),   prefix: "cmd"},     // cmd/
    {baseDir: filepath.Join(Paths.Root, Paths.ToolsDir), prefix: "tools"},   // tools/
}

for _, source := range sources {
    dirs, err := getSubDirectoriesBFS(source.baseDir)     // 广度优先扫子目录
    for _, dir := range dirs {
        allBinaries = append(allBinaries, withSourcePrefix(source.prefix, dir))
    }
}
```

**它是「扫目录」而不是「读配置」**：

- `cmd/` 下每个子目录 → 一个二进制
- `tools/` 下每个子目录 → 一个二进制

所以 `cmd/openim-rpc/openim-rpc-auth/` 会被扫到（BFS 递归），产出 `openim-rpc-auth`。

⚠️ **这意味着「加一个服务 = 加一个目录」**，不需要改 `magefile.go`。但**也意味着「临时目录也会被编译」**——如果你在 `cmd/` 下建了个 `cmd/scratch/` 放试验代码，`mage build` 会试图编译它。

**编译产物**：`_output/bin/`（服务）和 `_output/bin/tools/`（工具）。

**`Build` 的环境变量**（`build.go:170-175`）：


|---|---|
| `CGO_ENABLED` | 是否静态编译 |

### 2.3 `mage start` 的进程编排（`process_controller.go`）

**① 先起工具**（`StartToolsAndServices`）：

```go
if err := StartTools(); err != nil {   // check-free-memory → check-component → seq
    PrintRed("Some tools failed to start...")
    return
}
```

⚠️ **工具是同步执行的**（`cmd.Wait()`，`process_controller.go:103`）：

```go
if err := cmd.Start(); err != nil { ... }
if err := cmd.Wait(); err != nil { return fmt.Errorf(...) }
```

**这意味着**：`check-component` 要跑完（最多 3 分钟重试）才会继续。如果中间件没起来，`mage start` 会**卡住 3 分钟然后失败**——这正是你看到的「`mage start` 卡住不动」的原因之一。

**② 杀旧进程**（`KillExistBinaries` + `attemptCheckBinaries`）：

```go
func attemptCheckBinaries() error {
    const maxAttempts = 15
    for i := 0; i < maxAttempts; i++ {
        err := CheckBinariesStop()
        if err == nil { return nil }
        PrintYellow("Some services have not been stopped...")
        time.Sleep(1 * time.Second)
    }
    return fmt.Errorf("already waited for %d seconds...", maxAttempts)
}
```

**为什么要等**：`kill` 是**异步**的。发完 `SIGTERM` 进程不会立刻消失，端口可能还被占用。如果立刻启动新进程，会报 `address already in use`。

15 次 × 1 秒 = 15 秒等待。**这个值和 `cmd/main.go` 的 10 秒超时是配套的**（先让进程自己优雅退出 10 秒，再检查）。

**③ 起服务**（`StartBinaries`）：

```go
for binary, count := range binariesToStart {
    binFullPath := filepath.Join(Paths.OutputHostBin, binary)
    if _, err := os.Stat(binFullPath); err != nil {
        PrintRed(fmt.Sprintf("Binary not found: %s. Please build first.", binFullPath))
        continue          // ← 只是 continue，不中断！
    }
    for i := 0; i < count; i++ {
        args := []string{"-i", strconv.Itoa(i), "-c", configPath}
        cmd := exec.Command(binFullPath, args...)
        cmd.Dir = Paths.OutputHostBin          // ← 工作目录 = _output/bin
        cmd.Stdout = os.Stdout
        cmd.Stderr = os.Stderr
        if err := cmd.Start(); err != nil {    // ← 只 Start，不 Wait
            return fmt.Errorf(...)
        }
    }
}
```

**四个关键点**：

1. **`-i <index>`**：实例序号。8 个 push 实例分别是 `-i 0` 到 `-i 7`，用这个下标从 `ports` 数组取端口（`autoSetPorts: false` 时）。
2. **`-c <configPath>`**：配置目录。
3. **`cmd.Dir = OutputHostBin`**：工作目录是 `_output/bin`。所以 `config/log.yml` 里的 `storageLocation: ../../../../logs/` 是相对这个目录算的 → `open-im-server-main/logs/`。
4. **`cmd.Start()` 不 `Wait()`**：**这是关键**。如果 `Wait()`，`mage start` 会一直阻塞到第一个服务退出。不 wait 意味着「启动后立刻返回」，29 个进程成为**孤儿进程**（父进程 mage 退出了）。

⚠️ **「孤儿进程」在这里是有意为之**：`mage start` 完成使命就退出，服务在后台跑。但这也带来 1.4 说的问题：**没有父进程管理，信号无法传递**。

**`Binary not found` 只 `continue` 不中断**——所以如果你没 `mage build`，会看到 **一堆** `Binary not found ... Please build first`，而不是一行。这就是用户笔记里「`mage start` 报一堆 Binary not found」的原因。

### 2.4 `setMaxOpenFiles`：跨平台差异

**Unix/Linux**（`magefile_unix.go`）：用 `syscall.Setrlimit`，真正生效。

**Windows**（`magefile_windows.go`，8 行）：📌 大概是空实现返回 nil。因为 Windows 没有 `RLIMIT_NOFILE` 这个概念（它的句柄上限是另一个机制）。

⚠️ **这意味着 Windows 上跑 29 个进程时，fd/句柄上限没被调整**。在 Windows 上做压力测试会提前遇到瓶颈。

### 2.5 Dockerfile 逐行（`Dockerfile`）

```dockerfile
FROM golang:alpine AS builder              # ① 编译阶段

ARG RELEASE=false
ARG COMPRESS=false
WORKDIR /openim-server

RUN apk add --no-cache upx                 # ② 装 upx（压缩二进制）
RUN go install github.com/magefile/mage@latest   # ③ 装 mage

COPY . .                                   # ④ 拷源码
RUN go mod download                        # ⑤ 下依赖（单独一层，利用缓存）
RUN RELEASE=${RELEASE} COMPRESS=${COMPRESS} mage build   # ⑥ 编译
RUN mage -compile ./mage -ldflags "-s -w"  # ⑦ 把 magefile 编译成二进制

FROM alpine:latest                         # ⑧ 运行阶段

WORKDIR /openim-server

COPY --from=builder /openim-server/_output ./_output     # ⑨ 只拷产物
COPY --from=builder /openim-server/config ./config
COPY --from=builder /openim-server/start-config.yml ./start-config.yml
COPY --from=builder /openim-server/mage ./mage

ENTRYPOINT ["sh", "-c", "./mage start && sleep infinity"]  # ⑩
```

**逐条点评**：

**② `upx`**：一个可执行文件压缩器。`COMPRESS=true` 时会把二进制压小 50%~70%。代价是启动时要在内存里解压（慢几十毫秒）。**对 29 个进程意味着 29 次解压**，冷启动会明显变慢。

**⑤ `go mod download` 单独一层**：这是 Docker 层缓存的经典技巧。只要 `go.mod`/`go.sum` 没变，这一层就命中缓存，不用重新下依赖（可能几百 MB）。

⚠️ 但 `COPY . .` 在 `go mod download` **之前**（第 15 行）——**这破坏了缓存**！因为任何源码改动都会让 `COPY . .` 这一层失效，后面所有层（包括 `go mod download`）都要重跑。

**正确顺序应该是**：

```dockerfile
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN mage build
```

📌 **这是一个真实的 Dockerfile 优化点**，面试可以讲：「它把 `COPY . .` 放在 `go mod download` 前面，导致依赖缓存完全失效，每次改一行代码都要重下几百 MB 依赖。正确做法是先 COPY go.mod/go.sum 再 download。」

**⑦ `mage -compile ./mage`**：把 magefile 编译成一个可执行文件。为什么不直接用 `mage` 命令？因为运行阶段（alpine）**没有装 mage**，也没有 Go 工具链。所以必须在编译阶段把 magefile 编译好带过去。

**⑩ ENTRYPOINT**：1.4 详细分析过，这是最大的问题。

### 2.6 docker-compose 的角色：只起中间件

⚠️ **一个常见误解**：以为 `docker compose up -d` 会把 OpenIM 服务也起起来。

**不会**。看 `docker-compose.yml` 的 `services:` 列表——只有 mongodb、redis、etcd、kafka、minio、前端、prometheus、alertmanager、grafana、node-exporter，**没有 openim-api、openim-rpc-* 这些**。

所以完整部署是**两段式**：

```
① docker compose up -d      → 起 11 个中间件容器
② mage build && mage start  → 在宿主机起 29 个服务进程
```

**为什么这么设计**：
- 开发调试方便（改代码只要重启进程，不用重建镜像）
- 不用为每次代码改动重新 build 镜像
- 日志直接写宿主机文件，方便 `tail -f`

**如果要全容器化**：Dockerfile 就是为这个准备的——构建一个包含所有服务的镜像，`ENTRYPOINT` 里 `mage start`。但这样调试就麻烦了。

### 2.9 K8s 清单：`deployments/`

```
deployments/deploy/
├── clusterRole.yml                  # RBAC
├── ingress.yml                      # 入口
├── kafka-{secret,service,statefulset}.yml
├── mongo-{secret,service,statefulset}.yml
├── minio-{secret,service,statefulset}.yml
├── openim-api-{deployment,service}.yml
├── openim-config.yml                # ConfigMap（所有配置）

├── openim-msgtransfer-{deployment,service}.yml
```

**三个值得注意的设计**：

**① 配置用 ConfigMap**（`openim-config.yml`）：所有 yml 塞进一个 ConfigMap，挂载到容器的 `/config`。**改配置 = 改 ConfigMap + 滚动重启**。

**② 密码用 Secret**（`*-secret.yml`）：Mongo/Kafka/MinIO 的密码单独放 Secret。⚠️ 但 Secret 默认只是 base64（不是加密），**提交到 git 仍然会泄露**。生产应该用 SealedSecrets / External Secrets。

**③ msggateway 和 api 有 Service**（外部访问），rpc 服务**没有 Service**（只走 etcd 服务发现，不需要 k8s Service 的负载均衡）。

📌 **这是一个重要的架构认知**：**内部 RPC 不需要 k8s Service**，因为服务发现已经由 etcd 承担了。再套一层 k8s Service 反而多一跳。

### 2.10 设计评价

**做得好的：**

1. **构建脚本用 Go 写（mage）**：跨平台，不用维护 bash/PowerShell 两套。
2. **`getBinaries` 扫目录**：加服务零配置。
3. **`start-config.yml` 集中管理实例数**：29 个进程的来源一目了然。
4. **`check-component` 有 180 次重试**：解决「容器起来了但服务没就绪」。
5. **多阶段 Dockerfile**：镜像里不含 Go 工具链。
6. **`attemptCheckBinaries` 等 15 秒**：解决 kill 异步导致的端口占用。
7. **K8s 清单区分 StatefulSet/Deployment**：有状态/无状态分得清。

**可改进的（10 条）：**

| # | 位置 | 问题 | 后果 | 建议 |
|---|---|---|---|---|
| 1 | `Dockerfile:27` | `ENTRYPOINT sh -c "./mage start && sleep infinity"`，PID 1 是 `sleep` | **无法优雅停止**，29 进程变孤儿 | 加 tini，或用 supervisor |
| 2 | `Dockerfile:15-17` | `COPY . .` 在 `go mod download` 之前 | 依赖缓存失效，每次改代码重下几百 MB | 先 COPY go.mod/go.sum |
| 3 | `start-config.yml` | `maxFileDescriptors: 10000` | 只够 ~5000 连接，远不够网关场景 | 调到 100 万或按场景配置 |
| 4 | `process_controller.go` | 起服务不 `Wait`，`mage` 退出后进程变孤儿 | 无父进程管理、无法统一收信号 | 用 supervisor/tini |
| 5 | `StartBinaries` | `Binary not found` 只 `continue` 不汇总 | 输出一堆重复错误 | 收集缺失列表一次性报 |
| 6 | 全项目 | 服务进程**未见 `maxprocs.Set()`** | 容器 CPU limit < 宿主机核数时性能劣化 | 在 `main` 里加 |
| 7 | `.golangci.yml:19` | `build-tags: [mytag]`，项目里无此 tag | 可能漏检部分文件 | 删除该配置 |
| 8 | `tools/imctl` | 空壳，只打印一行 | 误导使用者 | 删除或实现 |
| 9 | `tools/yamlfmt` | 为 prow 准备，与业务无关 | 上游残留 | 删除 |
| 10 | `deployments/*-secret.yml` | 密码明文 base64 进 git | 泄露风险 | SealedSecrets / 外部密钥管理 |

**第 1、2、3 条是最值得在面试里讲的**——它们都是「不影响功能但影响可用性/效率」的问题，而且有明确的修法。

## 自测题

1. `go build` 默认产物是静态链接还是动态链接？`CGO_ENABLED=0` 改变了什么？
2. 为什么 `golang:alpine` 基础镜像下编译出的二进制要配 alpine 运行镜像，不能配 ubuntu？
3. 多阶段构建省了什么？为什么不用 `scratch`？
4. 容器的 PID 1 有什么特殊？OpenIM 的 ENTRYPOINT 会导致什么问题？
5. 一个 WebSocket 连接占几个 fd？`maxFileDescriptors: 10000` 够支撑多少连接？
6. `GOMAXPROCS` 在容器里为什么可能设错？automaxprocs 解决什么？
7. `mage start` 的完整流程是什么？为什么它起服务时用 `Start()` 而不是 `Run()`？
8. `attemptCheckBinaries` 为什么要等 15 秒？
9. `check-component` 为什么要重试 180 次？
10. `docker-compose.yml` 里为什么没有 openim 服务本体？
11. StatefulSet 和 Deployment 的区别是什么？为什么 Kafka 必须用 StatefulSet？
12. OpenIM 的 Dockerfile 里哪一行破坏了层缓存？正确写法是什么？

<details>
<summary>参考答案</summary>

1. 默认（`CGO_ENABLED=0`）是静态链接，不依赖 libc。`CGO_ENABLED=1` 会动态链接 libc，产出的二进制只能在 glibc 环境跑。
2. alpine 用 musl libc，ubuntu 用 glibc。CGO 编译的二进制在 musl 环境会报 `GLIBC_2.xx not found`。静态二进制（CGO=0）两边都能跑。
3. 省掉了 Go 工具链、gcc、git（约 300MB）。不用 scratch 是因为需要 `ca-certificates`（HTTPS 请求）和 `tzdata`（时区）。
4. PID 1 会忽略没有注册 handler 的信号。OpenIM 的 `sh -c "./mage start && sleep infinity"` 让 PID 1 变成 `sleep`，`docker stop` 的 SIGTERM 打不到 Go 进程，29 个进程变孤儿然后被 SIGKILL。
5. 1 个（每个 TCP 连接一个 socket fd）。10000 大概够 5000~9000 个连接（还要留 fd 给日志、连接池、epoll 等）。
6. 因为它读的是宿主机 /proc/cpuinfo 而不是 cgroup 的 CPU quota。容器 limit 2 核但宿主机 64 核时，Go 会起 64 个 P，上下文切换爆炸。automaxprocs 读 cgroup 的 quota 自动设对。
7. `InitForSSC`（读 start-config.yml）→ `setMaxOpenFiles` → `StartToolsAndServices`（先同步跑工具自检 → 杀旧进程 → 等 15 秒 → 按实例数启动 29 个进程）。用 `Start()` 不用 `Run()` 是因为要让 mage 启动完就退出，服务在后台跑。
8. 因为 kill 是异步的，发完 SIGTERM 进程不会立刻消失，端口还被占用。立刻启动新进程会 `address already in use`。
9. 因为中间件容器「进程起来了」不等于「服务可用」（Mongo 要建索引、Kafka 要选 leader）。180 次 × 1 秒 = 3 分钟，覆盖最坏情况的恢复时间。
10. 因为设计成两段式：compose 只起中间件，服务用 `mage start` 在宿主机跑。这样改代码不用重建镜像，日志直接落宿主机。
11. StatefulSet 给 Pod 固定名字和固定 PVC、按序启停；Deployment 的 Pod 是随机名字、可随意替换。Kafka 的 broker.id 和存储绑定，Pod 名变了就找不到自己的数据。
12. `COPY . .`（第 15 行）放在 `go mod download`（第 17 行）之前。应该先 `COPY go.mod go.sum ./`，再 `RUN go mod download`，最后 `COPY . .`。

</details>

## 面试话术

**问：你们项目怎么部署的？**

> 两段式。`docker compose up -d` 起 11 个中间件容器（Mongo、Redis、etcd、Kafka、MinIO 加监控栈），然后 `mage build` + `mage start` 在宿主机起 29 个服务进程。之所以不用 compose 把服务也容器化，是因为开发期改代码只要重启进程，不用重建镜像。生产有 Dockerfile 和 k8s 清单两套，部署形态和开发期分开。

**问：29 个进程是怎么来的？**

> `start-config.yml` 里按服务配实例数：api 1、crontask 4、8 个 rpc 各 1、push 8、msgtransfer 8，加起来正好 29。push 和 msgtransfer 多开是因为推送是 I/O 密集、落库是写瓶颈；crontask 多开是因为每个任务执行前抢分布式锁，多开只是提高准时率，不会重复执行。这个「按瓶颈分配实例数」的前提是服务无状态。

**问：容器化踩过什么坑？**

> 三个。一是 PID 1：`ENTRYPOINT sh -c "./mage start && sleep infinity"` 会让 PID 1 变成 sleep，`docker stop` 的 SIGTERM 打不到 Go 进程，29 个子进程变孤儿然后被 SIGKILL，等于完全没法优雅停止——正确做法是加 tini 做 init。二是文件描述符：默认 `ulimit -n` 是 1024，网关一个连接一个 fd，不改根本撑不住，`mage start` 里用 `Setrlimit` 调到配置里的值，但那个值只有 10000，对 10 万连接远远不够。三是 GOMAXPROCS：Go 读的是宿主机核数而不是 cgroup limit，容器限 2 核但宿主机 64 核时会起 64 个 P，上下文切换爆炸，要用 automaxprocs 修。

**问：Dockerfile 有什么可以优化的？**

> 它的分层顺序错了：`COPY . .` 在 `go mod download` 之前，导致任何源码改动都会让依赖下载那一层失效，每次改一行代码都要重下几百 MB 依赖。正确顺序是先 `COPY go.mod go.sum` 再 download，最后 `COPY . .`。另外多阶段构建用得对，运行阶段只有 alpine 加二进制，把 300MB 的 Go 工具链丢在 builder 里了。

**问：怎么保证服务启动时中间件可用？**

> `mage start` 会先同步跑 `check-component`，检查 Mongo、Redis、Kafka、MinIO、etcd 五项，每项失败重试，总共 180 次约 3 分钟。这个数字是覆盖「Kafka 集群最坏恢复时间」的经验值。工具是同步执行的，所以中间件没起来时 `mage start` 会卡住然后失败，而不是启动一堆连不上依赖的进程形成重启风暴。
