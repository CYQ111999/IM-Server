## 第一部分 纯理论：出问题时你靠什么定位

### 1.1 可观测性的三根支柱

线上出了个问题：「用户说消息发不出去」。

你手上有什么工具？

| 工具 | 回答的问题 | 数据形态 | 成本 |
|---|---|---|---|
| **日志（Logs）** | 这一条请求**具体发生了什么**？ | 文本/JSON，离散事件 | 存储贵（量大） |
| **指标（Metrics）** | 系统**整体健康度**如何？趋势怎样？ | 数值时间序列，聚合 | 便宜（预聚合） |
| **链路（Traces）** | 一次请求**经过了哪些服务、每段多久**？ | 树状 span，带耗时 | 采样后可控 |

**关键区别在于「能不能聚合」**：

- 日志：**不能**。你不能 `SELECT count(*) FROM logs WHERE error` 然后画趋势图（能，但很贵）
- 指标：**天生就是聚合的**。`rate(http_requests_total[5m])` 一行就能算出 QPS
- 链路：**部分聚合**。可以算 P99 延迟，但看不了「所有请求的完整路径」

所以正确的使用顺序是：

```
1. 看指标 → 发现「哪个服务、哪类请求出问题了」（秒级）
2. 看链路 → 定位「卡在哪个环节」（分钟级）
3. 看日志 → 找出「具体是什么错误」（十分钟级）
```

**反例**：很多人一上来就 `grep error app.log`，在几个 G 的日志里翻——这是最慢的路径。

**OpenIM 的三支柱现状**：

| 支柱 | 实现 | 成熟度 |
|---|---|---|
| 日志 | zap + 文件轮转 + operationID 注入 | ✅ 完整 |
| 指标 | Prometheus + 4 类业务指标 + Go runtime 指标 | ✅ 完整 |
| 链路 | **只有 operationID，没有真正的分布式追踪（无 span）** | ⚠️ 半成品 |

📌 **这是一个重要的认知**：OpenIM 有 `operationID` 能把日志串起来，但**没有 OpenTelemetry/Jaeger 那种 span 树**。所以你能知道「一次请求打了哪些日志」，但不知道「每一段耗时多少」。这是它跟现代云原生项目的差距，也是你可以提的改进点。

### 1.2 日志：级别、结构化、成本

**级别（Level）**

日志级别的作用是「按重要性过滤」。但级别的**数值方向**是个大坑：

| 框架 | 数值方向 | 例子 |
|---|---|---|
| zap / logrus / slog | **数值越大越严重**（Debug=-1, Info=0, Warn=1, Error=2） | `level: -1` 表示 Debug |
| syslog | 数值越小越严重（0=emerg, 7=debug） | — |
| **OpenIM** | **数值越大越详细**（0=Fatal, 3=Warn, 6=DebugWithSQL） | `remainLogLevel: 6` = 全开 |

⚠️ **这是本篇最重要的易错点**。看源码（`tools/log/zap.go:39-47`）：

```go
const (
    LevelFatal = iota          // 0
    LevelPanic                 // 1
    LevelError                 // 2
    LevelWarn                  // 3
    LevelInfo                  // 4
    LevelDebug                 // 5
    LevelDebugWithSQL          // 6
)
```

`iota` 从 0 递增，所以 **`3` 是 Warn，不是 Info**。

于是 `config/log.yml:8` 的注释：

```yaml
# remainLogLevel: 日志级别，生产环境用 3；调试环境用 6 输出更详细日志
remainLogLevel: 6
```

**注释是对的**：3 = 只输出 Warn/Error/Fatal（生产），6 = 全部（调试）。

但如果你按「3 = Info」的直觉去理解，会得出「生产环境输出 Info」的错误结论，然后在排查时发现「怎么没有 Debug 日志」——因为 3 根本不含 Debug。

📌 **这个 iota 顺序是反的**（正常应该 Fatal 最大）。这是「设计时没想清楚」的遗留，但它已经写在配置注释里了，改的成本高于收益。

**结构化日志**

```go
// 非结构化（拼接字符串）—— 无法被机器解析
log.Printf("user %s send msg to %s failed: %v", userID, recvID, err)

// 结构化（key-value）—— 可以被 jq / ES / Loki 查询
log.ZError(ctx, "send msg failed", err, "sendID", userID, "recvID", recvID)
```

结构化日志的价值：**能被机器查询**。

```bash
# 找出所有 recvID=user123 的失败
cat app.log | jq 'select(.recvID=="user123" and .level=="error")'
```

如果是拼接字符串，你只能 `grep "user123"`，然后人工看。

**成本**

日志是最贵的一环。粗算：

```
单条日志 200 字节
单进程 1000 条/秒
29 个进程
→ 5.8 MB/秒 = 500 GB/天（未压缩）
```

所以生产环境必须：降级（3）、轮转（`rotationTime: 24` 小时）、限量（`remainRotationCount: 2` 份）、必要时采样。

OpenIM 的 `log.yml`：

```yaml
storageLocation: ../../../../logs/
rotationTime: 24            # 24 小时轮转一次
remainRotationCount: 2      # 只保留 2 份（= 2 天）
remainLogLevel: 6           # 调试全开
isStdout: false             # 不输出到控制台
isJson: false               # console 格式（不是 JSON）
isSimplify: true            # 长字段精简
```

⚠️ **这份配置是「开发配置」不是「生产配置」**：`remainLogLevel: 6` + 只留 2 天，意味着「日志量巨大但只存 2 天」。生产应该改成 `3` + 留 7 天。

**`isSimplify` 是什么**（`config/config.go:53`）：

```go
IsSimplify bool `yaml:"isSimplify"`
```

对应 `zap.go:594-605`：

```go
if l.isSimplify {
    if len(keysAndValues)%2 == 0 {
        for i := 1; i < len(keysAndValues); i += 2 {
            if val, ok := keysAndValues[i].(LogFormatter); ok && val != nil {
                keysAndValues[i] = val.Format()     // 调用自定义精简
            }
        }
    } else {
        ZError(ctx, "keysAndValues length is not even", errs.ErrInternalServer.Wrap())
    }
}
```

`LogFormatter` 接口（`logger.go:36-38`）：

```go
type LogFormatter interface {
    Format() any
}
```

任何实现了 `Format()` 的类型，在日志里会被替换成 `Format()` 的返回值。典型用法：消息体（`sdkws.MsgData`）可能有几十个字段，日志里打全量会长得没法看，实现一个 `Format()` 只输出关键字段。

📌 **这也是一个可讲的细节**：「日志里打大对象会拖垮性能 + 刷屏，OpenIM 用 `LogFormatter` 接口做摘要」。

### 1.3 operationID：一次请求的身份证

**问题**：一次「发消息」在服务端经过：

```
API 进程（或 WS 网关）
  → msg RPC（校验）
    → Kafka
      → msgtransfer（落库）
        → Redis / Mongo
          → push → 网关 → 客户端
```

**七个环节、五个进程**。如果某个环节报错，你怎么知道「这条错误日志对应的是哪个用户的哪次请求」？

靠 `operationID`：**入口生成一个唯一 ID，全程透传，所有日志都带上它**。

```
18:00:01.123 [API]     opID=abc123 user=u1 send msg
18:00:01.130 [msg]     opID=abc123 validate ok
18:00:01.135 [transfer] opID=abc123 assign seq=100
18:00:01.140 [transfer] opID=abc123 write mongo failed: timeout
```

排查：`grep abc123 app.log` → 一次拿全。

**关键设计问题：怎么透传？**

四个环节，四种机制：

| 环节 | 机制 | 码点 |
|---|---|---|
| HTTP 入口 | **请求头** `operationID` | `api/router.go` 的 `GinParseOperationID` |
| HTTP → gRPC | **gRPC metadata**（本质也是 header） | `GrpcClientContext()` 拦截器 |
| gRPC → gRPC | 同上 | `GrpcServerMetadataContext()` 拦截器 |
| 进程内 RPC（standalone） | **ctx 直接传**（不序列化） | `inprocess` 的 localConn |
| 异步（Kafka） | **消息体里带**（context 不能序列化） | `ConsumerMessage.Ctx` |
| WebSocket | **请求体字段 `Req.operationID`** | `msggateway/context.go` |

⚠️ **最容易漏的是异步**：context 是内存对象，**不能塞进 Kafka 消息**。所以异步链路必须把 operationID 显式写进消息体，消费时再 `mcontext.SetOperationID` 恢复。

📌 这是一条通用规律：**同步链路靠 ctx 透传，异步链路靠消息体携带**。任何 MQ / 定时任务 / 协程池都要显式处理，否则「链路在这一段断了」。

**OpenIM 的 `mcontext` 只有四个字段**（`tools/mcontext/ctx.go`）：

```go
var mapper = []string{constant.OperationID, constant.OpUserID, constant.OpUserPlatform, constant.ConnID}
```

| 字段 | 用途 |
|---|---|
| `operationID` | 唯一请求 ID |
| `opUserID` | 操作者（谁发起的） |
| `opUserPlatform` | 平台（iOS/Android/Web/PC） |
| `connID` | 连接 ID（网关用，定位具体连接） |

**这四个字段就是「日志能串起来」的全部信息量**。它们会被注入到**每一条**日志（见 2.2）。

### 1.4 指标：四种类型与「标签基数」陷阱

Prometheus 有四种指标类型，选错会导致查询困难或性能问题：

| 类型 | 语义 | 例子 | 常用函数 |
|---|---|---|---|
| **Counter** | 只增不减的累计值 | 请求总数、错误总数 | `rate()`、`increase()` |
| **Gauge** | 可增可减的瞬时值 | 当前连接数、内存占用 | 直接读，或 `avg_over_time()` |
| **Histogram** | 分桶统计（客户端算分位） | 请求耗时 | `histogram_quantile()` |
| **Summary** | 分位统计（客户端算好） | 请求耗时 | 直接读 quantile |

**Histogram vs Summary 的关键区别**：

- Histogram：客户端记「落进哪个桶」，服务端用 `histogram_quantile()` 算任意分位，**桶边界固定**，可跨实例聚合
- Summary：客户端直接算 P99，**不可跨实例聚合**（每个实例的 P99 加权平均 ≠ 全局 P99）

所以**分布式系统几乎都该用 Histogram**。OpenIM 里 `gp.ServerMetrics.EnableHandlingTimeHistogram()`（`prommetrics/rpc.go:44`）就是开了 gRPC 的耗时直方图。

**标签基数是最大的坑**

指标名 + 标签 = 一条时间序列。标签的**每个不同取值组合**都是一条独立序列。

```go
// 危险：用 userID 做标签
requestCounter.WithLabelValues(userID).Inc()
```

如果有 100 万用户 → **100 万条时间序列** → Prometheus 内存爆掉、查询卡死。这叫「**基数爆炸（cardinality explosion）**」。

**安全标签的判定标准**：取值数量**有上界且不大**（< 100 左右）。

OpenIM 的标签选择（`prommetrics/api.go:12-24`）：

```go
apiCounter = prometheus.NewCounterVec(..., []string{"path", "method", "code"})
httpCounter = prometheus.NewCounterVec(..., []string{"path", "method", "status"})
```

| 标签 | 取值数 | 安全吗 |
|---|---|---|
| `path` | 153 条路由 | ⚠️ 偏多但可控 |
| `method` | 6 种 | ✅ |
| `code` | 几十种错误码 | ⚠️ 可控 |
| `status` | 5 种 | ✅ |

**153 × 6 × 50 ≈ 4.6 万条序列**——偏多但能接受。如果加上 `userID` 标签，立刻变成几百万，直接崩。

📌 **面试可以讲**：「我们给 API 指标打了 path/method/code 三个标签，粗算 4.6 万条序列。这个人数的决定因素是标签基数，绝不能把 userID、msgID 这类高基数字段做标签，否则 Prometheus 会 OOM。」

### 1.5 Prometheus 的拉模型

Prometheus 是**拉（pull）**模型：Prometheus 主动去各个实例的 `/metrics` 抓数据。

对比推（push）模型（如 StatsD、InfluxDB）：

| | 拉模型 | 推模型 |
|---|---|---|
| 谁发起 | Prometheus | 被监控方 |
| 服务要做什么 | 暴露一个 HTTP 端点 | 主动发数据到收集器 |
| 优点 | 目标存活状态天然可知（抓不到就是 down）；配置集中在 Prometheus | 适合短生命周期任务（batch job）；能穿透 NAT |
| 缺点 | 需要 Prometheus 能访问到目标；目标要暴露端口 | 收集器要处理「谁还活着」；服务要配置收集器地址 |

**「抓不到就是 down」这一点特别重要**：Prometheus 自带 `up` 指标（每次抓取成功=1，失败=0）。所以最基础的告警只需要一行：

```yaml
- alert: InstanceDown
  expr: up == 0
  for: 1m
```

这就是 OpenIM 的第一条告警规则（`config/instance-down-rules.yml:5-13`）。

### 1.6 动态服务发现：为什么不能写死 target

单机部署，target 写死就行：

```yaml
scrape_configs:
  - job_name: openim-api
    static_configs:
      - targets: [127.0.0.1:12002]
```

但 OpenIM 的部署是：

- `openim-push` **8 个实例**
- `openim-msgtransfer` **8 个实例**
- `autoSetPorts: true` → **端口是随机的**
- 实例随时可能重启、扩缩容

所以 target 列表**不能写死**。必须让 Prometheus 动态问「现在有哪些实例」。

Prometheus 支持多种服务发现机制（`http_sd_configs` 就是其中一种）：

```yaml
- job_name: openimserver-openim-push
  http_sd_configs:
    - url: "http://127.0.0.1:10002/prometheus_discovery/push"
```

Prometheus 定期请求这个 URL，期望拿到：

```json
[{ "targets": ["10.0.0.5:12020", "10.0.0.5:12021"], "labels": {"namespace": "default"} }]
```

于是 OpenIM 需要**自己实现这个「服务发现 API」**——把注册在 etcd 里的实例地址，转成 Prometheus 能读的格式。

**闭环是这样**：

```
每个实例启动时
  → 把自己的 prometheus 抓取地址写进 etcd（startrpc/start.go:170-180）
      key = prometheus_discovery/<服务名>/<index>
      value = {"target":"ip:port","labels":{"namespace":"default"}}

Prometheus 定期请求 /prometheus_discovery/<服务名>
  → API 去 etcd 读所有 key（prometheus_discovery.go:29）
  → 拼成 targets 数组返回
  → Prometheus 开始抓这些地址
```

⚠️ **这里有个循环依赖的风险**：Prometheus 通过 API 找实例，而 API 自己也可能是被监控对象。如果 API 挂了，所有实例的发现都失败 → 所有指标都断。这是一个**单点**。生产上应该多个 Prometheus 或者给 API 做高可用。

### 1.7 告警：怎么写才不「天天响」

告警设计的三个原则：

**① 告警必须可行动（actionable）**

「CPU 80%」不是告警，因为**你不知道该做什么**。
「CPU 持续 5 分钟 > 95% 且影响 P99 延迟」才是告警，因为**你知道要扩容**。

**② 用 `for` 过滤抖动**

```yaml
- alert: InstanceDown
  expr: up == 0
  for: 1m        # 持续 1 分钟才告警
```

一次抓取失败（网络抖动）不告警，持续 1 分钟才告警。**没有 `for` 的告警 90% 是噪音**。

**③ 分级（severity）**

| 级别 | 含义 | 通知方式 |
|---|---|---|
| `critical` | 用户受影响，必须立刻处理 | 电话/短信 |
| `warning` | 可能出问题 | 邮件/群消息 |
| `info` | 趋势异常，观察即可 | 日报 |

OpenIM 的四条规则（`config/instance-down-rules.yml`）：

| 告警 | 表达式 | 级别 | 含义 |
|---|---|---|---|
| `InstanceDown` | `up == 0` | critical | 实例挂了 |
| `DatabaseInsertFailed` | `increase(msg_insert_redis_failed_total[5m]) > 0` | critical | 消息写入 Redis/Mongo 失败 |
| `RegistrationsFew` | `increase(user_login_total[1h]) == 0` | info | 1 小时零登录（可能有问题，也可能凌晨没人用） |
| `MessagesFew` | `increase(single_chat_msg_process_success_total[1h]) + increase(group_chat_msg_process_success_total[1h]) == 0` | info | 1 小时零消息 |

**第 2 条是最有价值的**：它直接对应业务损失（消息没落库）。而且用的是 `increase(...) > 0`——**只要有过失败就告警**，非常敏感。配合 `for: 1m` 过滤偶发。

**第 3、4 条值得吐槽**：`== 0` 在凌晨必然成立（没人用），会产生大量无意义告警。这是典型的「**没有考虑业务周期**」。正确写法应该用「同比」：`increase(...) < 0.1 * 昨天的同时段`。

📌 **面试可以讲**：「我发现它的 `RegistrationsFew` 用 `== 0` 判断，凌晨必然触发，属于告警设计没考虑业务周期。更好的写法是和上周同时段做同比。」

### 1.8 Webhook：before 与 after 的语义差异

「Webhook」在 OpenIM 里指的是**业务回调**：服务端在关键时刻调用你的 HTTP 接口，让你介入。

分两类，语义完全不同：

| 类型 | 时机 | 你的返回值有没有用 | 阻塞主流程吗 |
|---|---|---|---|
| **Before**（`SyncPost`） | 操作**执行前** | **有用**，可以改请求 / 拒绝 | 阻塞（有超时） |
| **After**（`AsyncPost`） | 操作**执行后** | 无用（只记日志） | 不阻塞（进队列） |

**Before 的典型用途**：
- 消息发送前，把内容送审（敏感词、涉黄涉政），不通过就拒绝
- 发送前，改写消息（加签名、替换内容）
- 建群前，校验配额

**After 的典型用途**：
- 消息落库后，同步到你的消息归档系统
- 用户注册后，初始化你的业务数据（钱包、积分）
- 群解散后，清理关联业务

**代码**（`pkg/common/webhook/http_client.go:49-57`）：

```go
func (c *Client) SyncPost(ctx context.Context, command string, req callbackstruct.CallbackReq, resp callbackstruct.CallbackResp, before *config.BeforeConfig) error {
    return c.post(ctx, command, req, resp, before.Timeout)
}

func (c *Client) AsyncPost(ctx context.Context, command string, req callbackstruct.CallbackReq, resp callbackstruct.CallbackResp, after *config.AfterConfig) {
    if after.Enable {
        c.queue.Push(func() { c.post(ctx, command, req, resp, after.Timeout) })
    }
}
```

**注意 `AsyncPost` 的 `if after.Enable`**：关闭时**直接丢弃**，不进队列。这是「配置驱动」——不开就不产生任何开销。

⚠️ **一个很有意思的细节**：`AsyncPost` 把 `ctx` 直接捕获进闭包：

```go
c.queue.Push(func() { c.post(ctx, command, req, resp, after.Timeout) })
```

但 HTTP 请求结束后 `ctx` 会被 cancel！所以闭包里用 `ctx` 发请求会立刻失败。

它怎么解决的？看 `post` 的第一行（`http_client.go:66`）：

```go
func (c *Client) post(ctx context.Context, command string, input interface{}, output callbackstruct.CallbackResp, timeout int) error {
    ctx = mcontext.WithMustInfoCtx([]string{mcontext.GetOperationID(ctx), mcontext.GetOpUserID(ctx), mcontext.GetOpUserPlatform(ctx), mcontext.GetConnID(ctx)})
    ...
}
```

**它用 `WithMustInfoCtx` 重新建了一个 `context.Background()`**，只把四个字段搬过来。这样既保留了 trace 信息，又不受原 ctx 取消影响。

🟡 **这是本篇最值得学的技巧之一**：异步任务不能直接用请求的 ctx（会被取消），但也不能用裸 `Background()`（会丢 trace）。正确做法是「搬字段」。

**但这里还有坑**：`WithMustInfoCtx` 的实现（`mcontext/ctx.go:104-110`）：

```go
func WithMustInfoCtx(values []string) context.Context {
    ctx := context.Background()
    for i, v := range values {
        ctx = context.WithValue(ctx, mapper[i], v)
    }
    return ctx
}
```

它用 `mapper[i]` 按下标对应——**values 的顺序必须严格是「operationID, opUserID, platform, connID」**。传错顺序不会报错，会把 opUserID 写成 operationID。

📌 这是一个**隐式的顺序契约**，非常脆。更好的设计是 `WithInfoCtx(operationID, opUserID, platform, connID string)` 用显式参数。

### 1.9 定时任务的可观测性

定时任务有三个特殊要求：

**① 不能重复执行**（多实例）→ 分布式锁
**② 执行结果要能查**（成功/失败/耗时）→ 日志 + 指标
**③ 漏执行要比执行失败更严重**（清理任务没跑，磁盘会满）

OpenIM 的 cron（`internal/tools/cron/cron_task.go`）三个任务：

| 任务 | 注册条件 | 做什么 |
|---|---|---|
| `clearS3` | `FileExpireTime > 0 && len(DeleteObjectType) > 0` | 清理过期对象存储文件 |
| `deleteMsg` | `RetainChatRecords > 0` | 清理超过保留期的聊天记录 |
| `clearUserMsg` | 无条件 | 清理用户已删除的消息 |

**每个都套了锁**：

```go
c.locker.ExecuteWithLock(c.ctx, "clearS3", c.clearS3)
```

锁的实现在 Redis（`SetNX` + UUID owner + Lua 释放）或 etcd（lease）。

⚠️ **一个设计缺陷**：`ExecuteWithLock` 拿到锁后直接 `task()`，**没有超时控制**。如果 `clearS3` 执行 2 小时，锁的 TTL（`lockLeaseTTL`）可能早就过了，第二个实例会拿到锁**同时执行**。

正确做法是：持锁期间**定期续约**，或者把任务拆成小批（每次处理 N 个，处理完释放锁，下一轮继续）。

📌 **这是「分布式锁 + 长任务」的经典陷阱**，面试常考。

### 2.1 日志初始化：13 个参数（`cmd/main.go:237-256`）

```go
func (x *cmds) initLog() error {
    conf := x.config.Log
    return log.InitLoggerFromConfig(
        "openim-service-log",              // loggerPrefixName：日志文件名前缀
        program.GetProcessName(),          // moduleName：进程名（openim-api / openim-rpc-user...）
        "", "",                            // sdkType, platformName（服务端用不到）
        conf.RemainLogLevel,               // 级别（注意是 iota 反序！）
        conf.IsStdout,                     // 是否输出到控制台
        conf.IsJson,                       // 是否 JSON 格式
        conf.StorageLocation,              // 日志目录
        conf.RemainRotationCount,          // 保留几份
        conf.RotationTime,                 // 几小时轮转
        strings.TrimSpace(version.Version),// 版本（写进日志，方便对齐发布）
        conf.IsSimplify,                   // 长字段精简
    )
}
```

**几个值得注意的点**：

**① 第二个参数是进程名**：`program.GetProcessName()` 返回二进制名（`openim-api`）。所以 29 个进程的日志文件各不相同，能从文件名直接区分。

**② 版本号写进日志**：`version.Version`。线上排查时第一件事就是「这个实例是什么版本」，如果没有这个字段，你得去翻部署记录。

**③ 为什么 `initLog` 在 `initAllConfig` 之后、其他一切之前**：因为后面所有初始化（连 Mongo、连 Redis）都可能失败，**失败时要能打日志**。如果日志没就绪，错误信息只能打到 stderr，而 `isStdout: false` 时 stderr 可能没人看。

**④ 参数是位置参数不是 option 模式**：13 个位置参数，调用时必须严格按顺序。加一个参数就要改所有调用方。📌 这是一个**不好的 API 设计**（应该用 `WithXxx` option），但它是外部库的接口，改不了。

### 2.2 ctx 注入日志字段：6 个字段自动带上（`zap.go:583-610`）

```go
func (l *ZapLogger) kvAppend(ctx context.Context, keysAndValues []any) []any {
    if ctx == nil {
        return keysAndValues
    }
    operationID := mcontext.GetOperationID(ctx)
    opUserID := mcontext.GetOpUserID(ctx)
    connID := mcontext.GetConnID(ctx)
    triggerID := mcontext.GetTriggerID(ctx)
    opUserPlatform := mcontext.GetOpUserPlatform(ctx)
    remoteAddr := mcontext.GetRemoteAddr(ctx)
    ...
    // 后面把这些字段 append 到 keysAndValues
}
```

**这是「日志能串起来」的实现核心**：任何 `log.ZInfo(ctx, ...)` / `log.ZError(ctx, ...)` 调用，都会自动从 ctx 取出 6 个字段附加到日志。

所以业务代码**不需要手动写 operationID**：

```go
// 不用这样
log.ZError(ctx, "send msg failed", err, "operationID", mcontext.GetOperationID(ctx))

// 直接这样，框架自动带
log.ZError(ctx, "send msg failed", err, "sendID", userID)
```

⚠️ **代价**：每次打日志都要做 6 次 `ctx.Value()` 查找。`ctx.Value` 是**链表遍历**（`context.valueCtx` 嵌套），深度可能有 5~10 层。高 QPS 下这是可观测的开销。

📌 优化手段：在入口把 6 个字段一次性取出来，用 `logger.With(...)` 建一个带字段的子 logger。OpenIM 没这么做，属于「可优化但不急」。

### 2.3 operationID 的全链路

把一条消息的 operationID 传递路径完整走一遍：

**① HTTP 入口生成**（`internal/api/router.go` 的 `GinParseOperationID` 中间件）

```go
operationID := c.GetHeader(constant.OperationID)
if operationID == "" {
    operationID = idutil.OperationIDGenerator()   // 生成
}
ctx = mcontext.SetOperationID(ctx, operationID)
c.Request = c.Request.WithContext(ctx)
```

**② API → gRPC：写进 metadata**（`GrpcClientContext()` 拦截器，外部库）

```go
// 伪代码
md := metadata.Pairs(
    constant.OperationID, mcontext.GetOperationID(ctx),
    constant.OpUserID, mcontext.GetOpUserID(ctx),
    ...
)
ctx = metadata.NewOutgoingContext(ctx, md)
```

**③ gRPC 服务端 → ctx**（`GrpcServerMetadataContext()`，`startrpc/start.go:49`）

```go
// 伪代码
md, _ := metadata.FromIncomingContext(ctx)
ctx = mcontext.SetOperationID(ctx, md.Get(constant.OperationID)[0])
ctx = mcontext.SetOpUserID(ctx, md.Get(constant.OpUserID)[0])
```

**④ Kafk 异步：写进消息体**

```go
// msg 服务投 Kafka 时，把 ctx 的信息放进消息
type ConsumerMessage struct {
    Ctx   context.Context    // ← 注意：这不是真的序列化 ctx
    Key   string
    Value []byte
    Raw   mq.Message
}
```

⚠️ **`ConsumerMessage.Ctx` 是进程内对象，不进 Kafka**。所以跨进程时，operationID 必须在 `Value`（消息体）里。📌 具体在哪个字段需要看 `MsgData` 的 proto 定义（`//operationID` 之类）。这一点我标为待验证，因为 protocol 模块不在本仓库。

**⑤ WebSocket 入口**

`msggateway/context.go` 的 `UserConnContext` 从握手 URL 参数取 `operationID`，以及每条 `Req` 里带 `operationID`：

```go
type Req struct {
    ReqIdentifier int32  `json:"reqIdentifier"`
    Token         string `json:"token"`
    SendID        string `json:"sendID"`
    OperationID   string `json:"operationID"`   // ← 每条消息自带
    MsgIncr       string `json:"msgIncr"`
    Data          []byte `json:"data"`
}
```

**为什么 WS 要每条消息都带 operationID**：因为长连接没有「请求」的概念，一条连接上跑几百条消息，必须是消息级的 ID。

**⑥ 网关 → RPC：走 gRPC metadata**

网关调 `msg.SendMsg` 时，把 ctx 里的 operationID 通过拦截器写进 metadata。

**完整链路图**：

```
客户端
  │ HTTP header: operationID（或由 API 生成）
  ▼
[API 进程] GinParseOperationID → ctx
  │ gRPC metadata
  ▼
[rpc-msg 进程] GrpcServerMetadataContext → ctx
  │ Kafka 消息体（必须是消息体，不能是 ctx）
  ▼
[msgtransfer 进程] 消费时 SetOperationID → ctx
  │ 同一个 ctx 用于日志
  ▼
[Redis/Mongo 日志] opID 一致
```

### 2.4 指标全集：4 类 + 业务计数

`pkg/common/prommetrics` 一共 444 行，10 个文件，定义的指标分四类：

**① HTTP/API 层（`api.go`）**

```go
apiCounter  = CounterVec("api_count",  []string{"path", "method", "code"})
httpCounter = CounterVec("http_count", []string{"path", "method", "status"})
```

`APICall(path, method, apiCode)` 和 `HttpCall(path, method, status)` 分别在业务 handler 和 HTTP 中间件里调用。

**② RPC 层（`rpc.go`）**

```go
rpcCounter = CounterVec("rpc_count", []string{"name", "path", "code"})
```

在拦截器里调用（`start.go:270-282`）：

```go
return grpc.ChainUnaryInterceptor(func(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    resp, err := handler(ctx, req)
    prommetrics.RPCCall(rpcRegisterName, info.FullMethod, getCode(err))
    return resp, err
})
```

`getCode` 把 error 转成 gRPC status code：

```go
getCode := func(err error) int {
    if err == nil { return 0 }
    rpcErr, ok := err.(interface{ GRPCStatus() *status.Status })
    if !ok { return -1 }
    return int(rpcErr.GRPCStatus().Code())
}
```

**③ 消息处理业务指标（`grpc_msg.go`）**

```go
SingleChatMsgProcessSuccessCounter = Counter("single_chat_msg_process_success_total")
SingleChatMsgProcessFailedCounter  = Counter("single_chat_msg_process_failed_total")
GroupChatMsgProcessSuccessCounter  = Counter("group_chat_msg_process_success_total")
GroupChatMsgProcessFailedCounter   = Counter("group_chat_msg_process_failed_total")
```

**这四个是业务健康的直接体现**：告警规则里的 `MessagesFew` 就是用前两个算的。

**④ 中转链路指标（`transfer.go`）**

```go
MsgInsertRedisSuccessCounter / MsgInsertRedisFailedCounter
MsgInsertMongoSuccessCounter / MsgInsertMongoFailedCounter
SeqSetFailedCounter
```

**这五个对应消息链路的每一步**：写 Redis 成功/失败、写 Mongo 成功/失败、seq 设置失败。

告警 `DatabaseInsertFailed` 就是 `increase(msg_insert_redis_failed_total[5m]) > 0 or increase(msg_insert_mongo_failed_total[5m]) > 0`。

**⑤ 登录指标（`grpc_auth.go`）**

```go
UserLoginCounter = Counter("user_login_total")
```

告警 `RegistrationsFew` 用的就是它。

**设计点评**：

✅ 好的地方：**指标命名统一带 `_total` 后缀**（Counter 的惯例），语义清晰。
⚠️ 不足：**没有耗时指标**（除了 gRPC 自带的 histogram）。业务侧「分配 seq 耗时」「写 Mongo 耗时」都没有。排查性能问题只能靠日志时间戳。

### 2.5 指标暴露：三套入口，三种用法

指标定义好了，怎么让 Prometheus 抓到？OpenIM 有**三套不同的暴露方式**：

**① API 进程：全局 registry**（`prommetrics/prommetrics.go:65-69`）

```go
func Start(listener net.Listener) error {
    srv := http.NewServeMux()
    srv.Handle(commonPath, promhttp.HandlerFor(registry, promhttp.HandlerOpts{}))
    return http.Serve(listener, srv)
}
```

用的是**全局 `registry`**（`prommetrics.go:16`），所有 `RegistryXxx()` 注册的指标都在里面。启动在 `cmd/main.go:276-300`。

**② msgtransfer：独立 registry**（`transfer.go:38-58`）

```go
func TransferInit(listener net.Listener) error {
    reg := prometheus.NewRegistry()          // ← 独立 registry
    cs := append(baseCollector, MsgInsertRedisSuccessCounter, ...)
    return Init(reg, listener, commonPath, promhttp.HandlerFor(reg, promhttp.HandlerOpts{Registry: reg}), cs...)
}
```

**为什么要独立**？因为 msgtransfer 是单独进程（拆分布署），只需要暴露自己那 5 个指标 + Go runtime，不需要 API 的指标。

**③ RPC 服务：拦截器 + 独立 registry**（`rpc.go:27-35`）

```go
func RpcInit(cs []prometheus.Collector, listener net.Listener) error {
    reg := prometheus.NewRegistry()
    cs = append(append(baseCollector, rpcCounter), cs...)
    return Init(reg, listener, rpcPath, promhttp.HandlerFor(reg, promhttp.HandlerOpts{Registry: reg}), cs...)
}
```

**注意 `cs` 是参数传进来的**——因为每个 RPC 服务要暴露不同的指标集合（user 服务有登录指标，msg 服务有消息指标）。

**三套入口的对比**：

| 进程 | registry | 指标集合 | 暴露方式 |
|---|---|---|---|
| API | 全局 | 全部 | `prommetrics.Start` |
| msgtransfer | 独立 | 5 个中转指标 + runtime | `TransferInit` |
| RPC | 独立 | rpcCount + 本服务指标 + runtime | `RpcInit` + `cs` 参数 |

**`baseCollector` 是三套共有的**（`prommetrics.go:40-45`）：

```go
baseCollector = []prometheus.Collector{
    collectors.NewProcessCollector(...),   // CPU、内存、文件描述符
    collectors.NewGoCollector(),           // goroutine 数、GC、堆
}
```

**`GoCollector` 提供的最有用的指标**：

| 指标 | 用途 |
|---|---|
| `go_goroutines` | goroutine 泄漏的直接指标（持续增长 = 泄漏） |
| `go_memstats_heap_inuse_bytes` | 堆内存 |
| `go_gc_duration_seconds` | GC 停顿 |
| `process_open_fds` | 文件描述符（网关最需要关注） |

📌 **面试可以讲**：「排查 goroutine 泄漏第一件事就是看 `go_goroutines` 曲线，如果它锯齿状上升不回落，基本就是泄漏。OpenIM 的 `GoCollector` 提供了这个指标，但没有针对它的告警规则——这是一个可以补的点。」

### 2.6 动态服务发现：`prometheus_discovery.go`

**写入端**（`startrpc/start.go:166-180`）：

```go
target, err := jsonutil.JsonMarshal(prommetrics.BuildDefaultTarget(registerIP, prometheusPort))
if autoSetPorts {
    if err = client.SetWithLease(ctx, prommetrics.BuildDiscoveryKey(rpcRegisterName, index), target, prommetrics.TTL); err != nil {
        if !errors.Is(err, discovery.ErrNotSupported) {
            return err
        }
    }
}
```

- key：`prometheus_discovery/<服务名>/<index>`
- value：`{"target":"10.0.0.5:12020","labels":{"namespace":"default"}}`
- TTL：300 秒（`prommetrics.go:75`）

**只有 `autoSetPorts: true` 时才写**。为什么？因为 `autoSetPorts: false` 时端口是配置里写死的，Prometheus 可以直接用 static_configs 配。**这是「按需付出复杂度」**。

**读取端**（`api/prometheus_discovery.go:28-55`）：

```go
func (p *PrometheusDiscoveryApi) discovery(c *gin.Context, key string) {
    value, err := p.kv.GetKeyWithPrefix(c, prommetrics.BuildDiscoveryKeyPrefix(key))
    if err != nil {
        if errors.Is(err, discovery.ErrNotSupported) {
            c.JSON(http.StatusOK, []struct{}{})      // ← 不支持就返回空数组，不报错
            return
        }
        apiresp.GinError(c, errs.WrapMsg(err, "get key value"))
        return
    }
    if len(value) == 0 {
        c.JSON(http.StatusOK, []*prommetrics.RespTarget{})
        return
    }
    var resp prommetrics.RespTarget
    for i := range value {
        var tmp prommetrics.Target
        json.Unmarshal(value[i], &tmp)
        resp.Targets = append(resp.Targets, tmp.Target)
        resp.Labels = tmp.Labels
    }
    c.JSON(http.StatusOK, []*prommetrics.RespTarget{&resp})
}
```

**三个设计细节**：

**① `ErrNotSupported` 返回空数组而不是报错**

如果服务发现是 `standalone` 模式（内存 KV），根本没有 etcd，`GetKeyWithPrefix` 会返回 `ErrNotSupported`。此时返回 `[]`（空 targets）是正确行为——Prometheus 会认为「这个 job 现在没有目标」，而不是「发现接口坏了」。

**这是一个很好的「优雅降级」示例**：不支持的场景返回空，而不是 500。

**② 所有实例合并成一个 `RespTarget`**

注意它把 N 个实例的 target 合并到**一个** `resp` 里返回：

```go
c.JSON(http.StatusOK, []*prommetrics.RespTarget{&resp})
```

而不是 N 个 `RespTarget`。为什么？因为 `RespTarget.Labels` 是 `map[string]string`，如果每个实例一个 `RespTarget`，Prometheus 会认为它们是不同的 target group。合并成一个，等于「这一组实例共享同样的 labels」。

⚠️ 但这有个隐患：**`resp.Labels` 是循环里最后一次赋值**（`resp.Labels = tmp.Labels`）。如果某些实例的 labels 不同（比如跨 namespace），会被最后一个覆盖。📌 当前所有实例的 labels 都是 `{"namespace":"default"}`，所以没问题，但这是**脆弱的假设**。

**③ 返回格式必须严格符合 Prometheus 的 HTTP SD 协议**

```json
[
  {
    "targets": ["host1:port", "host2:port"],
    "labels": {"namespace": "default"}
  }
]
```

`_` 前缀的 label 会被 Prometheus 忽略，其他 label 会被附加到所有抓取到的指标上。

### 2.7 告警规则与 Alertmanager

**规则文件**（`config/instance-down-rules.yml`）已在上文列出。**加载方式**（`config/prometheus.yml:12-13`）：

```yaml
rule_files:
  - instance-down-rules.yml
```

**Alertmanager 接到告警后的处理**（`config/alertmanager.yml`）：

```yaml
route:
  group_by: ['alertname']      # 同名告警合并
  group_wait: 5s               # 首批延迟 5 秒（等一等，可能还有同类）
  group_interval: 5s           # 同组两次通知间隔
  repeat_interval: 5m          # 持续未恢复时，每 5 分钟提醒
  receiver: email

receivers:
  - name: email
    email_configs:
      - to: 'alert@example.com'
        html: '{{ template "email.to.html" . }}'
        send_resolved: true     # 恢复时也发（很重要！）
```

**三个参数的作用**：

| 参数 | 作用 | 调大/调小的后果 |
|---|---|---|
| `group_wait` | 新告警组首次发送前的等待 | 太小 → 同类告警刷屏；太大 → 告警延迟 |
| `group_interval` | 同组两次通知的最小间隔 | 太小 → 刷屏；太大 → 状态更新延迟 |
| `repeat_interval` | 持续未恢复时的提醒间隔 | 太小 → 烦；太大 → 忘了这事 |

**`send_resolved: true` 非常重要**：告警恢复时也发一封「已恢复」的邮件。否则你收到「服务挂了」，然后一直不知道它什么时候好的。

**`templates` 里的 `email.tmpl`** 是自定义 HTML 模板（`config/email.tmpl`）。这是**刻意保留的文件**——删了它 Alertmanager 启动会报「模板文件不存在」。

### 2.8 Webhook 的完整调用点

OpenIM 里 webhook 的调用点分布在各个业务服务：

| 场景 | Before（可拦截） | After（通知） |
|---|---|---|
| 发消息 | `msg/send.go` 的 `webhookClient.SyncPost(... "callbackWordFilter" ...)` | `msgtransfer` 落库后 |
| 建群 | `group/group.go` | 同 |
| 加好友 | `relation/friend.go` | 同 |
| 用户注册 | `user/user.go` | 同 |

**Before 的返回值可以被修改**，这是「业务扩展」的核心机制。具体实现（📌 需看 `callbackstruct` 包）：

```go
type CallbackResp interface {
    Parse() error      // 解析响应
}
```

`Parse()` 里如果服务端返回「拒绝」，`SyncPost` 会返回 error，业务层直接中断。

📌 **这是一个很好的「扩展点设计」范例**：主流程只依赖 `CallbackResp` 接口，具体能改什么由具体类型决定。

### 2.9 设计评价

**做得好的：**

1. **operationID 贯穿同步链路**：HTTP header → gRPC metadata → ctx → 日志，一套机制全覆盖。
2. **异步链路显式重建 ctx**：`WithMustInfoCtx` 解决了「异步任务不能复用请求 ctx」的问题。
3. **`ErrNotSupported` 优雅降级**：服务发现不支持时返回空数组而非 500。
4. **指标命名规范**：统一 `_total` 后缀，标签基数可控。
5. **告警覆盖「基础设施 + 业务」两层**：既看 `up`，也看「消息是否在流动」。
6. **`send_resolved: true`**：告警恢复也通知，这是运维友好的细节。

**可改进的（8 条）：**

| # | 位置 | 问题 | 后果 | 建议 |
|---|---|---|---|---|
| 1 | `instance-down-rules.yml` `RegistrationsFew` / `MessagesFew` | 用 `== 0` 判断，凌晨必然触发 | 告警疲劳，真问题被淹没 | 改成与昨日同时段同比 |
| 2 | 全项目 | **没有真正的分布式追踪**（无 span） | 只知道「打了哪些日志」，不知道「每段耗时」 | 接入 OpenTelemetry |
| 3 | `prommetrics/*` | 只有 Counter，**没有业务耗时 Histogram** | 排查性能问题只能靠日志时间戳 | 给 seq 分配、Mongo 写入加 Histogram |
| 4 | `prometheus_discovery.go:51` | `resp.Labels` 在循环里被覆盖 | 跨 namespace 部署时 labels 丢失 | 按 labels 分组返回多个 RespTarget |
| 5 | `instance-down-rules.yml` | 没有 `go_goroutines` 泄漏告警 | goroutine 泄漏只能靠人肉看 | 加 `rate(go_goroutines[10m]) > 0` 类规则 |
| 6 | `cron_task.go:120` | `ExecuteWithLock` 无任务超时/续约 | 长任务超过锁 TTL 会双实例并发 | 续约或分批 |
| 7 | `zap.go:583-592` | 每条日志 6 次 `ctx.Value` 查找 | 高 QPS 下有不小开销 | 入口处建子 logger |
| 8 | `log.yml` | `remainLogLevel: 6` + 只留 2 份 | 生产会「日志巨大但只存 2 天」 | 生产改 3 + 留 7 天 |

**第 2 条（没有分布式追踪）是最值得在面试里讲的改进点**——因为它体现了你知道「现代可观测性」的标准形态。

## 自测题

1. 可观测性三支柱分别回答什么问题？为什么排查顺序是「指标 → 链路 → 日志」？
2. `log.yml` 里 `remainLogLevel: 3` 是什么级别？为什么这个方向是反的？
3. operationID 在「同步链路」和「异步链路」分别怎么传？为什么异步不能用 ctx？
4. 一个指标加了 `userID` 标签会发生什么？怎么判断一个标签安不安全？
5. Histogram 和 Summary 的关键区别是什么？为什么分布式系统要用 Histogram？
6. Prometheus 为什么用拉模型？「拉」带来了什么免费的好处？
7. OpenIM 为什么要自己实现 `/prometheus_discovery/*` 接口？不实现会怎样？
8. `AsyncPost` 里为什么要把 ctx 换成 `WithMustInfoCtx`？直接用原 ctx 会怎样？
9. `GetAllUserStatus`... 不对，是 `discovery()` 里 `resp.Labels = tmp.Labels` 有什么隐患？
10. 「没有分布式追踪」具体缺的是什么能力？加 OpenTelemetry 能补上什么？

<details>
<summary>参考答案</summary>

1. 日志=具体发生了什么；指标=整体健康度；链路=经过哪些环节、各段多久。先看指标因为它是聚合的、秒级能发现「哪里不对」，再去链路定位环节，最后用日志看具体错误。反过来在几 G 日志里 grep 是最慢的。
2. Warn（`LevelWarn = 3`）。因为常量用 `iota` 从 0 开始，`LevelFatal=0` 递增到 `LevelDebugWithSQL=6`，数值越大越详细，与 zap/logrus 的惯例相反。
3. 同步链路靠 ctx（HTTP header → gRPC metadata → ctx）；异步靠消息体显式携带，消费时 `SetOperationID` 恢复。因为 ctx 是内存对象，不能序列化进 Kafka。
4. 每个不同的 userID 都是一条独立时间序列，100 万用户 = 100 万条序列，Prometheus 内存爆掉（基数爆炸）。安全标准：取值数量有上界且不大（< 100 左右）。
5. Histogram 客户端记分桶、服务端算分位，桶边界固定因此可跨实例聚合；Summary 客户端算好分位，各实例的 P99 加权平均不等于全局 P99，不可聚合。分布式系统必须用 Histogram。
6. 配置集中在 Prometheus 侧；且「抓不到就是 down」是免费的健康检查（`up` 指标），一条 `up == 0` 就是最基础的可用性告警。
7. 因为 push 有 8 个实例、msgtransfer 有 8 个实例、`autoSetPorts: true` 时端口随机，target 不能写死。需要把 etcd 里注册的实例地址转成 Prometheus 的 HTTP SD 格式。
8. 因为 HTTP 请求结束后原 ctx 会被 cancel，异步闭包里用它发请求会立刻 `context canceled`。`WithMustInfoCtx` 重建一个 Background 并搬入 4 个 trace 字段，既不受取消影响又不丢链路信息。
9. 循环里 `resp.Labels = tmp.Labels` 是覆盖赋值，所有实例的 labels 会被最后一个覆盖。当前 labels 都相同所以没问题，但跨 namespace 部署就会丢标签。
10. 缺的是「span 树」——每段调用的开始/结束时间、父子关系、耗时占比。有了它才能直接看出「这次请求 300ms 里，250ms 花在写 Mongo 上」。现在只能靠日志时间戳人工拼。

</details>

## 面试话术

**问：线上出问题你怎么定位？**

> 三步。先看指标，因为它天生聚合，`rate(api_count{code!="0"}[5m])` 一眼能看出「错误率什么时候起来的、是哪个 path」。然后看日志——OpenIM 的 operationID 从 HTTP header 进来到 gRPC metadata、再到 Kafka 消息体，全程透传，`grep <opID>` 就能拿到一次请求在五个进程里的所有日志。如果要做耗时归因，就得靠链路，但 OpenIM 这块是半成品，只有 operationID 没有 span，所以耗时只能靠日志时间戳推。这也是我会提的改进点：接 OpenTelemetry。

**问：日志级别怎么设计的？**

> OpenIM 用的是 zap，但级别常量是 `iota` 从 Fatal=0 递增到 DebugWithSQL=6，所以**数值越大越详细**，跟常见框架相反。配置里 `remainLogLevel: 3` 是 Warn 及以上，`6` 是全开。这个反直觉的设计容易踩坑——我一开始按「3=Info」理解，结果以为生产在输出 Info。另外它用 `kvAppend` 在每条日志里自动注入 operationID、opUserID、platform、connID 六个字段，所以业务代码不用手写这些。

**问：Prometheus 的指标类型怎么选？**

> Counter 用于只增的累计值，配 `rate()` 用；Gauge 用于瞬时值（连接数、内存）；Histogram 用于耗时，客户端记分桶、服务端算分位，能跨实例聚合；Summary 是客户端算好分位，不能跨实例聚合，所以分布式系统基本都用 Histogram。选类型之外更要小心标签基数——OpenIM 的 `api_count` 打了 path/method/code 三个标签，粗算 4.6 万条序列，这个量级能接受；但绝对不能把 userID 这种高基数字段做标签，会直接把 Prometheus 打 OOM。

**问：告警怎么设计才不会天天响？**

> 三个原则。一是可行动——「CPU 80%」不是告警，因为不知道该干什么；「CPU 持续 5 分钟 > 95% 且 P99 恶化」才是。二是必须带 `for`，过滤网络抖动，没有 `for` 的告警九成是噪音。三是分级，critical 走电话、info 走日报。OpenIM 有一处反面例子：`RegistrationsFew` 用 `increase(user_login_total[1h]) == 0` 判断，凌晨必然成立，会天天响，应该改成跟昨日同时段同比。

**问：webhook 的 before 和 after 有什么区别？**

> before 是同步的，在操作执行前调用，返回值有意义——可以改请求内容或者直接拒绝（比如消息送审不通过就拦掉）。after 是异步的，操作执行完投进内存队列慢慢发，返回值只记日志。实现上有个细节：after 的异步任务不能直接用请求的 ctx，因为请求结束 ctx 就取消了；也不能用裸 Background，会丢 trace。它用 `WithMustInfoCtx` 把 operationID 等四个字段搬到一个新的 Background 里，这个技巧很实用。
