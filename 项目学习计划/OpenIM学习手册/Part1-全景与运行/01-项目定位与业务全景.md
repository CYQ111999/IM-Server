# 第一部分　理论：IM 到底是什么

## 1.1 从「聊天」这件小事说起

假设你只会写 CRUD 后端，现在老板让你做一个「给 App 加聊天功能」的需求。你的第一反应大概率是这样：

```sql
create table message (
  id bigint primary key auto_increment,
  from_user varchar(64),
  to_user   varchar(64),
  content   text,
  create_time datetime
);
```

发消息 = `INSERT`；看消息 = `SELECT ... WHERE to_user = ? ORDER BY create_time`。跑通了，看起来完全没问题。

**然后需求开始加码**：

1. 群聊，500 人的群 —— 一条消息只插一行，还是插 500 行？
2. A 在群里发了消息，B 此刻离线，明天上线要看得到 —— 从哪条开始拉？
3. B 有两个手机 + 一个网页，三个端都要收到，而且顺序一致 —— 谁负责扇出？
4. B 说「我明明看到红点有 3 条未读，点进去是空的」—— 未读数怎么算才不会错？
5. A 发送时网络抖了一下，客户端重试了一次 —— 会不会出现两条一样的消息？
6. 有人把手机时间调到了 2030 年 —— 按 `create_time` 排序会怎样？

**这六个问题，就是 IM 服务端 90% 的复杂度来源。** 它们的共同点是：**都不是「增删改查」的问题，而是「分发、顺序、状态同步」的问题。**

> 🔴 **一句话结论**：普通后端处理的是「**一条请求 → 改一份数据 → 返回**」；IM 后端处理的是「**一条消息 → 分发给 N 个人 × M 个设备 → 保证顺序、不丢、不重、状态可追**」。这是两个不同量级的问题。

## 1.2 IM 与普通 CRUD 后端的四个本质差异

这一节是全篇最重要的。四个差异，每一个都能直接推出后面某个具体设计。

### 差异一：写一次、读多次，而且「读者是谁」在写的时候不知道

普通后端：用户发一条微博，读者是「所有关注他的人」，但你不需要在发的时候把内容复制给每个粉丝——粉丝打开首页时按关注关系去查一次就够了。这叫**读时扇出（fan-out on read）**。

IM 不行。原因很硬：**聊天必须是「推送」而不是「拉取」**。

- 拉取（轮询）：客户端每秒问一次「有新消息吗」。延迟至少一个轮询间隔，90% 的请求是空转，服务端 QPS 被无意义放大 10 倍以上。
- 推送：服务端主动把消息塞给客户端。需要一条**一直开着的连接**，也就是长连接（WebSocket）。

一旦要推送，就必须在**写的时刻**知道「这条消息该给谁」，也就是要在写路径上完成**群成员展开**：

```
一条群消息 → 群有 500 人 → 500 个接收者 → 每人平均 1.5 个在线设备
           = 750 个在线推送目标 + 500 份未读状态 + 1 份历史
```

这个动作叫**扇出（fan-out）**。写一次要扇出几百次，这是 IM 和 CRUD 的第一个分水岭。

> ⚠️ **易错**：初学者常以为「群消息存一行，大家来查」。在 OpenIM 里确实只有**一份**消息本体（Mongo 的 `msg` 集合按会话存，不按人存），但**未读状态、已读水位、会话列表**是每人一份的。所以「一份消息 + N 份状态」，不是「一份消息」也不是「N 份消息」。第 13、19 篇会把这条讲透。

### 差异二：必须有一个「所有人都认可的顺序」

普通后端不太在乎顺序，`order by create_time desc` 凑合着能用。IM 不行，因为：

- **客户端时钟不可信**。用户可以把手机时间改成 2030 年，也可以因为时区/夏令时漂移几分钟。用发送方时间排序 = 把排序权交给用户。
- **服务端多实例的时钟也不同步**。NTP 同步误差在毫秒级，而热门群一秒可能几十条消息。
- **同一毫秒可能有 N 条消息**，时间戳精度不够，无法定序。
- **分页会漏**。用时间做游标，`>` 和 `>=` 都可能漏掉或多拿同一毫秒的数据。

所以 IM 必须引入一个服务端分配的、**单调递增**的整数序号。OpenIM 里它叫 **seq（sequence，序列号）**。

```
会话 A：消息 seq = 1, 2, 3, 4, 5 ...
会话 B：消息 seq = 1, 2, 3 ...        ← 独立计数，互不相干
```

有了 seq，很多问题瞬间变成「整数比较」：

| 问题 | 没有 seq | 有 seq |
|---|---|---|
| 拉增量 | 时间比较，边界模糊 | `seq > 本地最大seq`，精确 |
| 判断漏收 | 无法判断 | 收到 5 又收到 7，缺 6 |
| 算未读 | 需要 count 一张表 | `maxSeq - hasReadSeq`，一次减法 |
| 幂等 | 靠 messageID 去重表 | seq 已存在就跳过 |

> 🔴 **面试锚点**：seq 是**会话级**（per-conversation）的，不是全局的。会话 A 的 seq=100 和会话 B 的 seq=100 毫无关系。这个细节很多人答错。

### 差异三：投递语义必须是「不丢、不重、不重复」

分布式系统里有个经典三选二（其实是三选一）：

| 语义 | 含义 | 代价 |
|---|---|---|
| **at-most-once**（最多一次） | 可能丢，绝不重 | 简单、快 |
| **at-least-once**（至少一次） | 绝不丢，可能重 | 需要去重 |
| **exactly-once**（恰好一次） | 不丢不重 | 极难，通常靠「至少一次 + 幂等」模拟 |

IM 的选择是：**写入端至少一次 + 读取端幂等**。

具体到 OpenIM：
- 投 Kafka 失败会重试 → 可能重复投递
- 消费端用 `seq` 做主键写入 → 重复写入变成覆盖，天然幂等
- 客户端拉消息按 seq 区间拉 → 重复拉到同一条，客户端按 seq 去重

> ⚠️ **易错**：「exactly-once」在工程上几乎不存在。任何跟你说「我们实现了严格 exactly-once」的方案，往下追一层，基本都是「at-least-once + 幂等」。面试时说这句话比硬吹 exactly-once 加分。

### 差异四：一个用户 = N 个设备 = N 份状态

普通后端的 user 是一行记录。IM 的 user 是：

```
user1
 ├── iOS 设备（在线，前台）
 ├── Android 设备（在线，后台）
 └── Web 端（离线）
```

于是产生一堆「状态」问题：

- **在线状态**：user1 算在线还是离线？三个端有一个在线就算在线。
- **多端同步**：手机发的消息，网页要不要显示？要。
- **多端互踢**：同一个端类型重复登录，旧连接踢不踢？OpenIM 默认踢。
- **推送策略**：三个端都在线，推给哪个？还是都推？如果在后台，要不要走厂商离线推送？

这些状态**不能存在业务进程的内存里**（因为有多个网关实例），必须放到 Redis 之类的共享存储。这是第 15、22 篇的主题。

## 1.3 十二个必懂名词（先建立词典）

后面所有篇章都会反复用这些词。**这一节建议反复看，比记代码重要。**

| 名词 | 英文/代码名 | 是什么 | 解决什么问题 |
|---|---|---|---|
| **会话** | conversation | 一个「聊天窗口」。单聊、群聊、系统通知各是一种 | 把消息归到一个可枚举的容器里，客户端才能列会话列表 |
| **会话 ID** | conversationID | 会话的唯一标识。单聊 `si_小ID_大ID`，群聊 `sg_群ID`，通知 `sn_A_B` | 全局唯一定位一个会话 |
| **消息** | message / MsgData | 一条聊天内容，是**多态结构**（文本/图片/文件/自定义） | 承载用户内容 |
| **seq** | sequence | 会话内**单调递增**的整数，服务端分配 | 定序 + 增量同步 + 算未读 |
| **maxSeq** | maxSeq | 某会话当前最大 seq | 客户端判断「我拉全了没」 |
| **hasReadSeq** | hasReadSeq | 某用户在某会话「已读到」的 seq（**水位**，不是列表） | 算未读、显示已读回执 |
| **未读数** | unread | `maxSeq - hasReadSeq`（**减法，不是统计**） | 红点 |
| **长连接** | WebSocket | 一次握手后双方可以持续双向发数据的 TCP 连接 | 让服务端能主动推送 |
| **网关** | msggateway | 专门持有长连接的进程 | 连接管理与业务逻辑解耦 |
| **推送** | push | 把消息塞给在线设备（在线推送）/ 交给厂商通道（离线推送） | 让对端「立刻」看到 |
| **回执** | receipt / hasRead | 已读回执：告诉发送方「对方读到这里了」 | 业务功能，且是「水位」不是「条数」 |
| **webhook** | callback | 业务方提供的 HTTP 接口，服务端在关键节点回调 | 让接入方在不改代码的情况下干预（如内容审核、发消息前拦截） |

> 🟡 **难点：为什么「未读」是减法而不是 count？**
> 如果每条消息给每个成员插一条「未读记录」，500 人群 × 每天 1000 条 = 50 万行/天，还要在已读时逐条 UPDATE。而用「水位」表达：每人每会话只存一个 `hasReadSeq` 整数，来新消息只改会话的 `maxSeq`。**存储从 O(消息数 × 人数) 降到 O(会话数 × 人数)**，这是数量级的差异。第 19 篇会讲这个设计的副作用（水位不能表达「跳着读」）。

## 1.4 业务域是怎么划出来的

拿到「做 IM」这个需求，怎么拆模块？不是拍脑袋，有几个明确的切分依据：

**依据一：按「聚合根（Aggregate Root）」切**

聚合根是 DDD（领域驱动设计）里的概念，通俗说就是「**有独立生命周期的、一改就要整体一致的那个对象**」。

IM 里的聚合根很清楚：

```
User（用户）—— 有独立生命周期，改昵称不影响别人
Friend（好友关系）—— 一对用户之间的关系，独立
Group（群）—— 独立生命周期，解散是整体动作
Conversation（会话）—— 每人一份，独立
Message（消息）—— 追加型，一旦写入不再改（撤回是标记）
```

于是业务域就出来了：**用户域、好友域、群组域、会话域、消息域**。这不是 OpenIM 特有，微信、Telegram、Slack 的模块划分本质一样。

**依据二：按「访问模式」切**

| 数据 | 访问模式 | 适合的存储/模块 |
|---|---|---|
| 用户资料 | 读多写少 | 缓存友好，强一致 |
| 好友/群成员 | 读多写少，但读极频繁（每条消息都要校验） | 需要本地缓存 |
| 会话 | **高频 UPDATE 同一行** | 不适合关系库，见 21 篇 |
| 消息 | **无限追加** | 只追加不改，适合分桶 |

**依据三：按「谁能独立扩容」切**

如果一个功能的热度和其他功能差 10 倍，就该拆开，否则只能一起扩。消息是 IM 里最热的，所以它有独立的 RPC 服务、独立的异步中转进程（msgtransfer）、独立的推送进程（push）。

> 📌 **落到 OpenIM 上**：七个 RPC 服务 = 七个业务域，一一对应：
> `auth / user / relation / group / msg / conversation / third`

## 1.5 消息不是字符串：多态与「开关位图」

普通后端的「内容」字段就是个 `text`。IM 的消息必须是**多态结构**，因为一条消息可能要装：

- 一段文本
- 一张图片（URL + 宽高 + 缩略图）
- 一个文件（URL + 文件名 + 大小）
- 「撤回」这个动作
- 「正在输入」这个状态
- 「建群通知」这种系统事件

**为什么不能用一个 union 结构（所有字段都塞进去）？**
因为消息是**持久化**的，每加一种消息类型都改表结构，历史上几亿条消息的字段全空着，浪费且难维护。

所以主流做法是：**公共头（sender/recv/seq/time）+ 一个 `contentType` 枚举 + 一个 `content` 二进制字段**，`content` 里再按 `contentType` 反序列化成不同的结构体。

这就是**多态消息**。

更关键的是第二个设计：**消息的「行为开关」**。

同一条消息在系统里的行为差异很大：

```
「大家好」        → 要存历史、要算未读、要推送、要进会话
「正在输入」      → 不存历史、不算未读、不推送、不进会话
「已读回执」      → 不存历史、不算未读、要推送（对端要看到"已读"）
「撤回」          → 不改历史（标记原消息）、不算未读、要推送
「系统通知」      → 存历史、算未读、要推送、但会话是 sn_ 开头的通知会话
```

如果每种类型都写 `if type == Typing { ... } else if type == ReadReceipt { ... }`，代码会烂掉。所以 OpenIM 用了一个 **11 位的开关组**（`options` 位图）：

| 开关 | 含义 |
|---|---|
| `IsHistory` | 存不存历史 |
| `IsPersistent` | 落不落库（Redis/Mongo） |
| `IsUnreadCount` | 算不算未读 |
| `IsOfflinePush` | 要不要离线推送 |
| `IsOnlinePush` | 要不要在线推送 |
| `IsConversationUpdate` | 要不要更新会话 |
| `IsSenderSync` | 发送方其他端要不要同步 |
| `IsSendMsg` | 是否为真实发送（vs 内部消息） |
| `IsUpdateConvUnread` | 是否更新会话未读数 |
| `IsSyncSelf` | 是否同步给自己 |
| `IsNotify` | 是否作为通知 |

**好处**：链路里每一处只要问「这个开关开了吗」，不用关心具体消息类型。加一种新消息类型，只要配好开关，链路代码一行不用改。这叫**用数据驱动行为，代替分支判断**。

> 🔴 这是本项目最值得学的设计之一。第 10 篇会逐位拆开。

## 1.6 为什么会有「开源 IM 服务端」这个品类

自研 IM 的坑有多深？列一下你必须要做的事：

| 必需能力 | 难点 |
|---|---|
| 长连接网关 | 连接保活、心跳、多实例、连接迁移、内存 |
| 消息可靠性 | 不丢、不重、顺序、补洞 |
| 多端同步 | 已读同步、漫游、拉增量 |
| 群组体系 | 成员管理、禁言、角色、@、已读统计 |
| 关系链 | 好友申请、黑名单、备注 |
| 离线推送 | iOS APNs / 各安卓厂商 / 海外 FCM |
| 内容安全 | 敏感词、审核、撤回 |
| 运维 | 扩容、监控、灰度、数据迁移 |

一个 3 人小组从零做到「能上生产」，业内经验值 6 人月以上，而且坑会在上线后半年陆续爆。

于是有三条路：

1. **自研**：大厂，有团队，要极致定制。
2. **买云 IM**（融云 / 环信 / 腾讯云 IM）：开箱即用，按量付费，但数据在别人家，深度定制受限。
3. **开源私有化**（OpenIM / Matrix）：数据自主，可改源码，但要自己运维。

**OpenIM 就是第 3 条路的产品。** 它的价值主张是：我不做 App，我只做服务端；你用 SDK 接进来，剩下的通信复杂度我扛。

> 📌 **面试话术**：被问「为什么不用云 IM」时，答案不是「云 IM 不好」，而是「业务要求数据不出内网 / 要按自己业务改消息模型 / 长期成本」。技术选型永远是场景决定的。

## 1.7 预算题：一次群聊发送，要写几份数据？

这是本篇的理论收尾，也是理解「为什么必须有消息队列」的钥匙。

张三给 500 人的群发一句「大家好」：

| 要写的东西 | 数量 | 能不能不写 |
|---|---|---|
| 消息本体（历史） | 1 份 | 不能，离线的人要能拉到 |
| 消息缓存（近期） | 1 份 | 可省，但省了拉历史会打 Mongo |
| 会话的 maxSeq | **500 份**（每人一份会话） | 不能，这是未读的基础 |
| 每人的未读状态 | 500 份 | 不能 |
| 发送者已读水位 | 1 份 | 不能，否则自己显示未读 |
| 在线推送 | 最多 750 次网络写 | 部分可省 |
| 离线推送任务 | 离线人数份 | 可异步 |
| 操作日志 / 指标 | 若干 | 可批量 |

**总写入次数在 1500 次量级。** 如果全部同步做，一次发送的 P99 会到几百毫秒甚至秒级，客户端就会「转圈」。

所以工业界的统一解法是：**同步只做「校验 + 投递」，其余全部异步**。

```
同步（必须快，10ms 内）：校验权限 → 投消息队列 → 返回成功
异步（可以慢，100ms 内）：展开、分配 seq、写缓存、落库、推送
```

这就是 **消息队列（Kafka）在 IM 里的第一性作用**：把「一次请求内的 N 次写」变成「请求外的流水线」。

> ⚠️ **代价**：异步意味着「发送成功」不等于「已落库」。如果进程在投递后、落库前崩溃，消息可能丢。所以必须有可靠性机制（Kafka 位点 + 幂等写入 + 客户端按 seq 补洞）。这是第 11、23 篇的全部内容。

## 2.1 一句话定位与三个关键事实

**OpenIM Server 是一个开源的即时通讯（IM）服务端。** 它不直接面向终端用户，而是给「想给自己的 App 加聊天功能」的团队提供一套可私有化部署的通信底座。

| 事实 | 意味着什么 |
|---|---|
| 它是**服务端**，不是完整产品 | 没有用户界面，靠 SDK 接入（iOS/Android/Web/Flutter/小程序…） |
| 它**私有化部署** | 数据在自己服务器上，不是用别人的云 IM |
| 它**只做通信** | 不做音视频（那是 RTC 的事）、不做支付、不做内容审核 |

⚠️ **易错**：很多人以为 OpenIM 是「聊天 App 的后端」，实际上它连「用户注册」都不对普通用户开放——注册接口只有管理员能调（`internal/rpc/user/user.go:287` 的 `authverify.CheckAdmin`）。业务用户体系由接入方自己的系统管理，OpenIM 只负责「这个 userID 存在、能发消息」。

这条设计和 1.4 讲的「按聚合根切域」是一致的：用户域只管「用户档案 + 状态」，**不管注册登录流程**（那是接入方账号系统的事）。

## 2.2 理论落地：五大业务域 = 七条路由前缀

从路由表就能反推业务边界（`internal/api/router.go`，共 153 条 HTTP 路由）：

| 业务域 | 路由前缀 | 路由数 | 核心能力 | 代码位置 |
|---|---|---|---|---|
| **鉴权** | `/auth` | 4 | 管理员 token、用户 token、token 校验 | `internal/rpc/auth/` |
| **用户** | `/user` | 25 | 资料、状态、在线平台、全局消息接收选项 | `internal/rpc/user/` |
| **好友** | `/friend` | 22 | 申请、同意、删除、黑名单、增量同步 | `internal/rpc/relation/` |
| **群组** | `/group` | 32 | 建群、解散、成员管理、禁言、角色 | `internal/rpc/group/` |
| **消息** | `/msg` | 19 | 发消息、撤回、删除、已读、搜索 | `internal/rpc/msg/` |
| **会话** | `/conversation` | 12 | 会话列表、置顶、免打扰、未读 | `internal/rpc/conversation/` |
| **第三方** | `/third`、`/object` | 15 | 对象存储签名、日志、推送 token | `internal/rpc/third/` |
| **统计** | `/statistics` | 4 | 消息量统计（管理端） | 复用 msg/group/user |
| **运维** | `/config`、`/restart`、`/prometheus_discovery` | 18 | 配置中心、重启、监控发现 | `internal/api/` |
| **小程序** | `/jssdk` | 2 | 微信小程序签名 | `internal/api/jssdk/` |

注意最后三行：**统计、运维、小程序没有独立的 RPC 服务**。

- `statistics` 是「读别人的数据做聚合」，它复用 msg/group/user 的 RPC，自己只是查询编排。
- `config` / `restart` / `prometheus_discovery` 是**纯粹的进程级操作**（读配置、重启自己、暴露抓取目标），不需要跨进程，直接写在 `internal/api/` 里。
- `jssdk` 是签名计算，无状态、无存储。

> 📌 **洞察**：业务域划分不是「一个前缀一个服务」。判据是「**是否需要独立部署 + 独立存储 + 独立扩容**」。运维操作三个都不满足，所以它不进 RPC 层。

## 2.3 消息多态在代码里的落点

1.5 讲了多态 + 开关位图。对应代码：

| 理论概念 | 代码位置 | 说明 |
|---|---|---|
| `contentType` 枚举 | `github.com/openimsdk/protocol/sdkws`（外部模块） | 消息类型定义在协议库里，不在本仓库 |
| `options` 位图 | `pkg/msgprocessor/options.go` | 11 个开关的位运算定义 |
| 按类型配开关 | `internal/rpc/msg/verify.go:146-153` | `encapsulateMsgData` 里根据 contentType 设置 options |
| 链路里问开关 | 全链路（msgtransfer / push） | `msgprocessor.IsUnreadCount(o)` 这类判断 |

⚠️ **重要细节**：`Typing`（正在输入）消息**也走完整发送链路**（进 Kafka、进 msgtransfer），只是在 `encapsulateMsgData` 阶段被关掉了「存历史/持久化/未读/推送」四个开关（`internal/rpc/msg/verify.go:146-153`）。

所以它**会占 seq 吗？不会**——`IsHistory=false` 的消息会被分到 `notStorageMsgList`，不参与 seq 分配（第 12 篇）。

> 🔴 这个细节是「是否真读懂链路」的试金石。能答出来的人，说明他看过分类逻辑而不是只看过架构图。

## 2.4 一次群聊产生的九类数据（对 1.7 的源码级展开）

理论部分说「1500 次写入」。落到代码里，是这样：

| 数据 | 存哪 | 谁写 | 同步/异步 | 对应代码 |
|---|---|---|---|---|
| 消息本体 | Mongo `msg` 集合（100 条/文档） | msgtransfer | 异步 | `online_msg_to_mongo_handler.go` |
| 消息 seq | Redis Hash + Mongo `seq` 集合 | msgtransfer（Malloc） | 异步 | `cache/redis/seq_conversation.go` |
| 消息缓存 | Redis | msgtransfer | 异步 | `controller/msg.go` |
| 群会话 | Mongo `conversation` 集合 | msgtransfer（首次）或 conversation 服务 | 异步/同步 | `controller/conversation.go` |
| 群成员未读 | Redis（`seq_user`） | msgtransfer / conversation | 异步 | `cache/redis/seq_user.go` |
| 发送者已读 | Redis | msgtransfer（`userSeqMap`） | 异步 | 同上 |
| 在线推送 | 不落盘 | push + gateway | 实时 | `push/onlinepusher.go` |
| 离线推送任务 | Kafka `toOfflinePush` | push | 异步 | `push/offlinepush_handler.go` |
| 操作日志 / 指标 | 文件 / Mongo `log` 集合 / Prometheus | 全局 | 实时 | `pkg/common/prommetrics/` |

**「同步」只有一行**：`internal/rpc/msg/send.go:67-70` 投 Kafka 就返回。

```go
// internal/rpc/msg/send.go:67-70（群聊分支）
err = m.MsgDatabase.MsgToMQ(ctx, conversationutil.GenConversationUniqueKeyForGroup(req.MsgData.GroupID), req.MsgData)
if err != nil {
    return nil, err
}
// ← 到这里就返回了，不等落库、不等推送
```

这张表就是「为什么需要 Kafka」的答案：一次发送要写 9 个地方，同步做必然超时。

> ⚠️ **易错：单聊 conversationID 为什么「顺序敏感」？**
> `GenConversationIDForSingle` 会把两个 userID **排序**后拼接（小 ID 在前）。如果不排序，A→B 是 `si_A_B`，B→A 是 `si_B_A`，就变成两个会话了。这是「单聊必须只有一个会话」的直接推论。第 10 篇有完整代码。

## 3.3 面试话术（30 秒版）

> 「OpenIM 是一个 Go 写的开源 IM 服务端，定位是私有化部署的通信底座。它把业务拆成七个域：鉴权、用户、好友、群组、消息、会话、第三方。
>
> 它的核心难点不是 CRUD，而是消息的分发与一致性——一条群消息要扇出给 N 个成员的 M 个设备，还要保证有序、不丢、多端同步。所以架构上是 WS 网关 + gRPC 微服务 + Kafka 异步流水线 + Mongo/Redis 分层存储。
>
> 我觉得最能体现 IM 特殊性的是两个设计：一是用服务端分配的会话级 seq 代替时间戳做定序和增量同步；二是用『已读水位』代替『未读记录表』，把未读的存储从 O(消息数×人数) 降到 O(会话数×人数)。」

**追问预案**

| 追问 | 答法 |
|---|---|
| 「seq 为什么不能用 Redis 的 INCR 全局自增？」 | 因为 seq 是会话级的，全局自增会让每个会话的 seq 出现巨大空洞，客户端无法用「连续区间」判断漏收。而且会形成全局单点热点。 |
| 「不用 Kafka 行不行？」 | 可以（Redis Stream 也行，项目里 `pkg/mqbuild` 就有双实现），但 Kafka 的持久化 + 分区有序 + 消费组语义最匹配这个场景。 |
| 「消息丢了怎么办？」 | 三道防线：Kafka 位点先 Mark 后 Commit；Mongo 写入用 seq 做幂等；客户端重连上报本地 maxSeq 拉增量补洞。 |
