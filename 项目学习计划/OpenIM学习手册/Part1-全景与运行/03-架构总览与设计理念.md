# 第一部分　理论：架构设计的基本盘

## 3.1 单体 vs 微服务：不是「新的一定好」

### 3.1.1 单体架构是什么

**单体（Monolith）**：所有功能打成一个可执行程序，部署一份。

```
┌──────────────────────────────────────┐
│           一个进程 / 一份代码          │
│  ┌──────┬──────┬──────┬──────┐       │
│  │ 用户  │ 订单  │ 支付  │ 通知  │       │
│  └──────┴──────┴──────┴──────┘       │
│           一个数据库                    │
└──────────────────────────────────────┘
```

你写过的 bluebell 就是单体。它**没有任何问题**，而且在一个团队 < 10 人、QPS < 几千的时候，单体是**更优解**：

| 优点 | 说明 |
|---|---|
| 开发简单 | 一个仓库，一次构建，一次部署 |
| 调试简单 | 一个进程，断点能一路跟到底 |
| 无网络开销 | 函数调用是纳秒级，不是毫秒级 |
| 事务简单 | 一个本地事务搞定，不需要分布式事务 |

**那为什么业务量一大就要拆？** 因为单体会遇到四个「墙」：

| 墙 | 现象 |
|---|---|
| **扩容墙** | 只有「读接口」热，但整个单体一起扩容，浪费 10 倍机器 |
| **发版墙** | 改一行通知文案，也要重启整个应用，聊天服务跟着中断 |
| **故障墙** | 支付模块内存泄漏，整个应用 OOM，聊天也用不了 |
| **组织墙** | 50 个人改同一个仓库，天天冲突 |

### 3.1.2 微服务是什么

**微服务（Microservices）**：按业务边界拆成多个独立部署的服务，服务间通过网络（通常是 RPC 或 HTTP）通信。

```
   ┌──────┐   ┌──────┐   ┌──────┐
   │ 用户  │   │ 订单  │   │ 支付  │     ← 各自独立进程、独立库
   └──┬───┘   └──┬───┘   └──┬───┘
      └──────────┼──────────┘
            网络调用（gRPC / HTTP）
```

它解掉了上面四堵墙，但**引入了新的复杂度**，这是新手最容易忽略的：

| 新问题 | 说明 |
|---|---|
| **网络不可靠** | 函数调用不会失败，网络调用会超时、会重试、会重放 |
| **分布式事务** | 跨服务的一致性没法和本地事务一样做 |
| **链路难追踪** | 一个请求过 6 个服务，出问题定位难（所以要 `trace_id`） |
| **部署运维复杂** | 20 个服务、20 套配置、20 份日志 |
| **开发环境重** | 想跑一个服务，得把依赖的 6 个服务都起来 |

> 🔴 **面试要点**：被问「微服务有什么好处」时，只说好处是背答案。**能说出代价、并说出「什么规模不该用微服务」，才是真懂。**
>
> 一句话总结：**微服务是组织问题和技术问题一起解，不是性能优化手段。** 10 个人的团队上微服务，大概率是负收益。

### 3.1.3 第三条路：模块化单体 / 双模式

很多项目走的是中间路线：**代码按模块严格分好（逻辑上是微服务），但部署时可以合成一个进程（物理上是单体）**。

这就是所谓 **modular monolith（模块化单体）**，或者叫「**同一份代码，两种跑法**」。

OpenIM 走的就是这条路（第二部分 3.5 会讲它怎么做到的）。

> 📌 这种设计的价值在**开发体验**：新人 clone 下来，一个二进制就能跑全链路；上生产时再拆成 12 个服务独立扩容。**不用维护两套代码。**

## 3.2 分层架构与依赖方向

### 3.2.1 为什么要分层

不分层的代码长这样：

```go
func SendMessage(c *gin.Context) {
    // 校验 token
    // 查群成员（直接连 Mongo）
    // 检查禁言（直接查 Redis）
    // 写 Mongo
    // 发 Kafka
    // 拼响应
}
```

问题：**这段代码同时知道了 HTTP、鉴权、Mongo、Redis、Kafka**。改任何一个都来动它，测任何一个都要把所有依赖 mock 掉。

分层就是把「知道的事」分开：

| 层 | 只知道 | 不知道 |
|---|---|---|
| 接入层（Handler） | HTTP / WS 协议、参数校验 | 业务规则、数据库 |
| 逻辑层（Service） | 业务规则 | 协议、具体存储实现 |
| 数据层（Repository） | 怎么读写存储 | 业务规则 |

**收益**：换存储不用改业务；加一个 HTTP 接口不用碰业务；业务逻辑可以脱离 HTTP 单测。

### 3.2.2 依赖方向：只能单向

```
接入层 → 逻辑层 → 数据层
```

**绝对不能反向。** 如果数据层反过来 import 接入层，就形成循环依赖，Go 编译器会直接报错（Go **不允许包级循环依赖**，这是它比 C++ 严格的地方）。

> 🔴 **依赖倒置（DIP）**：更严格的做法是「逻辑层定义接口，数据层实现接口」。这样**依赖方向指向接口**，而不是指向实现。
>
> ```go
> // 逻辑层定义（它只知道自己要什么）
> type MsgRepository interface {
>     Create(ctx context.Context, msg *Msg) error
> }
> // 数据层实现（它知道怎么做）
> type mongoMsgRepo struct { ... }
> ```
>
> 好处：测试时可以塞一个内存实现，不用起 Mongo。OpenIM 的 `pkg/common/storage/controller` 就是这一层（第 04 篇详讲）。

### 3.2.3 三层在 IM 里的具体切法

IM 的三层不是「Controller-Service-Dao」那种教科书切法，而是按**部署边界**切：

| 层 | 特征 | 为什么单独一层 |
|---|---|---|
| **接入层** | 只做协议转换 + 鉴权 + 连接管理 | 协议会变（HTTP/WS/小程序），业务不变 |
| **逻辑层** | 全部业务规则 | 需要水平扩容，且要能独立发版 |
| **数据层** | MongoDB / Redis / Kafka | 有状态，扩容方式完全不同 |

注意：**「接入层」和「逻辑层」之间是网络调用（gRPC），不是函数调用**。这是微服务和普通分层最大的差别。

## 3.3 有状态 vs 无状态：架构里最重要的一条分界线

### 3.3.1 定义

| 类型 | 含义 | 例子 |
|---|---|---|
| **无状态（Stateless）** | 处理请求不依赖「本进程之前存了什么」，任何实例都能处理任何请求 | 普通 HTTP API |
| **有状态（Stateful）** | 请求的正确处理依赖「这个进程持有的数据」 | 持有长连接的网关、有内存缓存的进程 |

### 3.3.2 为什么这条线这么重要

因为**它决定了「能不能随便扩容」**：

```
无状态服务：
   来 100 个请求 → 随便加一台机器 → 立刻分担 50 个 ✅

有状态服务：
   A 用户的连接在机器 1 上，B 用户在机器 2 上
   你要给 A 推消息 → 必须找到机器 1 → 不能随便加机器 ❌
```

**具体到 IM**：WebSocket 网关是**有状态**的——它内存里存着「这个连接属于哪个 userID」。所以：

- 扩容后，新连接落在新机器上，老连接还在老机器上 → **连接分布不均**
- 要给某个用户推消息，得先知道他在哪台机器上 → 需要「**路由表**」（OpenIM 存在 Redis 的 `online` 里）
- 机器挂了，上面的连接全断，必须重连 → 需要「**重连 + 增量拉取**」机制

> 🔴 **一句话结论**：**所有有状态的组件，都是架构里最难的部分。** 数据库有状态 → 所以有主从/分片；网关有状态 → 所以有路由表和广播；Kafka 有状态 → 所以有分区和副本。
>
> 反过来，架构优化的一个通用思路就是：**尽量把状态从业务进程里挪出去**（挪到 Redis / DB），让业务进程尽量无状态。

### 3.3.3 「无状态」不等于「没有状态」

⚠️ **易错**：无状态服务不是「不存任何数据」，而是「**不在进程内存里存跨请求依赖的数据**」。

- 把 session 放 Redis → 服务仍然是无状态的（状态在外部）
- 把 session 放进程 map → 服务变成了有状态的

判断标准一句话：**「这个请求的结果，是否依赖『恰好是这台机器』？」** 依赖 = 有状态。

## 3.4 同步 vs 异步：消息队列到底在解决什么

### 3.4.1 三个动机

引入消息队列（MQ）通常有三个动机，**要分清你的场景是哪个**：

| 动机 | 说明 | 例子 |
|---|---|---|
| **解耦（Decoupling）** | 生产者不需要知道消费者是谁 | 发消息的服务不关心有几个下游要处理 |
| **异步（Async）** | 把耗时操作从请求路径里挪走，缩短响应时间 | 发消息不等落库就返回 |
| **削峰（Peak Shaving）** | 突发流量先堆在队列里，消费者按自己能力处理 | 秒杀、群发 |

IM 的动机是**前两个**（异步 + 解耦），几乎不涉及削峰。

### 3.4.2 同步 vs 异步的取舍

```
同步：客户端 → 服务端 → 写库(30ms) → 推送(50ms) → 返回
      总耗时 = 80ms+，且任何一步慢都拖累整个请求，任何一步挂都导致请求失败

异步：客户端 → 服务端 → 投队列(2ms) → 返回  ✅
                         ↓（消费者慢慢处理）
                    写库 / 推送
      总耗时 = 2ms，但「返回成功」≠「已落库」
```

**异步的代价，必须背下来**（面试常问）：

| 代价 | 表现 | 补偿手段 |
|---|---|---|
| 不保证已持久化 | 返回成功但消息可能还在队列里 | 客户端按 seq 拉增量补洞 |
| 不保证顺序被业务感知 | 客户端可能先收到后发的 | 用 seq 排序，不用到达顺序 |
| 失败要重试 → 可能重复 | 同一条消息处理两次 | 幂等写入 |
| 排查难 | 链路变长 | 全链路 `operationID` |

### 3.4.3 消息队列的两个核心机制

要理解 Kafka 在 IM 里的作用，必须懂两个机制：

**机制一：分区（Partition）—— 决定并行度和顺序**

一个 topic 分成多个分区，每个分区是一个**有序的、只能追加的日志**：

```
topic: toRedis
 ├── partition 0: [msg1, msg4, msg7, ...]   ← 分区内严格有序
 ├── partition 1: [msg2, msg5, msg8, ...]
 └── partition 2: [msg3, msg6, msg9, ...]
```

- **分区内有序，分区间无序**
- 生产者在发消息时指定一个 **key**，同一个 key 永远进同一个分区
- 消费者组里，**一个分区只能被一个消费者消费**（保证不重复消费）

> 🔴 **这就是 IM 保证「同一会话消息有序」的原理**：把 `conversationID` 当 key，同一会话的消息必然进同一分区，同一分区只被一个消费者处理，天然有序。
>
> 反过来说：**如果 key 选错了（比如用空的 RecvID），同一会话的消息会散落到不同分区，顺序就乱了**。本项目 `push_handler.go:276` 就踩了这个坑（第 15 篇）。

**机制二：位点（Offset）—— 决定「不丢」**

消费者处理完一条消息，要「提交位点」告诉 Kafka「我处理到哪了」。

```
先处理 → 后提交：可能重复（处理完但没来得及提交就崩了）→ 至少一次
先提交 → 后处理：可能丢失（提交了但处理失败）→ 至多一次
```

**工业界的标准做法是「至少一次 + 幂等」**：先处理成功，再提交位点。重复了靠幂等去重。

> 📌 本项目用的是 `counter.Wait() → Mark() → Commit()` 三段式（第 23 篇），本质就是「等这一批都处理完再提交」。

## 3.5 一致性问题：CAP 与最终一致

### 3.5.1 CAP 是什么

**CAP** = Consistency（一致性）+ Availability（可用性）+ Partition tolerance（分区容忍性），**分布式系统最多同时满足两个**。

先解释三个词：

| 词 | 含义 |
|---|---|
| **一致性 C** | 任何时刻，所有节点读到的数据都一样（线性一致） |
| **可用性 A** | 每个请求都能在有限时间内得到非错误响应 |
| **分区容忍 P** | 网络断了、节点失联了，系统还能继续工作 |

**关键结论**：只要是分布式系统（多台机器通过网络通信），**P 必然要满足**（网络一定会出问题）。所以真正的选择是：

```
网络分区发生时，你选 C 还是 A？
  选 C → 拒绝服务（宁可报错，也不给可能错的数据）→ CP（如 etcd、ZooKeeper）
  选 A → 继续服务（可能返回旧数据）→ AP（如 Cassandra、大多数缓存）
```

> ⚠️ **易错**：CAP 不是「三选二」的自由选择题，而是「P 必选，在 C 和 A 之间权衡」。面试时说「我们选 CA」会被扣分——那等于说「我们没有网络分区」，不成立。

### 3.5.2 BASE 与最终一致

完全的强一致代价太大，所以互联网系统普遍采用 **BASE**：

| 词 | 含义 |
|---|---|
| **B**asically **A**vailable（基本可用） | 允许降级：慢一点、少一点功能，但不整体挂 |
| **S**oft state（软状态） | 允许中间态（数据正在同步中） |
| **E**ventually consistent（最终一致） | 不保证立刻一致，但保证「过一段时间」一致 |

**IM 就是典型的最终一致系统**：

```
T+0ms    发送方收到「发送成功」
T+50ms   消息落库、对端收到
T+200ms  会话列表更新
```

在 T+0 到 T+50 之间，数据是「不一致」的（库里还没有这条消息）。用户能接受，因为**延迟在 100ms 量级，人感知不到**。

> 🔴 **面试话术**：「IM 用的是最终一致，不是强一致。理由是：强一致要求写要等所有副本确认，延迟会从几十毫秒涨到几百毫秒，而聊天场景对延迟极敏感、对『200ms 后才真正落库』不敏感。代价是要有一套补洞机制——客户端按 seq 拉增量，保证最终能看到全部消息。」

### 3.5.3 「最终一致」的前提：可收敛

最终一致不是「什么都不做，等着它自己好」。它必须有**确定性的收敛路径**：

| 场景 | 收敛机制 |
|---|---|
| 消息可能漏收 | 客户端重连时上报本地 `maxSeq`，服务端返回 `seq > maxSeq` 的所有消息 |
| 未读数可能不准 | 未读是 `maxSeq - hasReadSeq` 的**计算值**，源数据对了就自动对 |
| 缓存与 DB 不一致 | 缓存过期后回源 DB |

> 📌 **关键设计思想**：**能用「计算」表达的，就不要用「存储」维护。** 未读数是算的，不是存的——所以它天然不会「算错累积」。

## 3.6 幂等、顺序、投递语义

### 3.6.1 幂等（Idempotency）

**定义**：同一个操作执行一次和执行 N 次，结果相同。

为什么需要？因为分布式系统里**重试是必然的**：网络超时你不知道是「没收到」还是「收到了但响应丢了」，只能重试。重试就可能重复执行。

三种常见实现：

| 做法 | 例子 | 适用 |
|---|---|---|
| **唯一键约束** | 用 `seq` 当唯一索引，重复插入报错/覆盖 | 最可靠 |
| **状态机** | 「已支付」状态不能再次支付 | 状态流转类 |
| **去重表 / 幂等 token** | 客户端带 `clientMsgID`，服务端查表 | 无天然唯一键时 |

**OpenIM 的选择**：消息用 `(conversationID, seq)` 天然唯一，重复写入 Mongo 就是覆盖同一位置（用 `$set` + 位置寻址），天然幂等。

### 3.6.2 顺序性

| 级别 | 含义 | 代价 |
|---|---|---|
| **全局有序** | 所有消息一个顺序 | 只能单线程消费，吞吐极低 |
| **分区有序** | 同一分区内有序 | 需要正确的 key |
| **无序** | 不保证 | 最快 |

IM 需要的是**会话内有序**，也就是「分区有序」，key = `conversationID`。这是吞吐和正确性的最佳平衡点。

⚠️ **易错**：很多人以为「Kafka 保证顺序」。**Kafka 只保证分区内顺序**，跨分区不保证。所以「用 Kafka 实现有序」的真正含义是「**用正确的 key 把需要有序的消息路由到同一分区**」。

### 3.6.3 三种投递语义（再强调一次）

| 语义 | 做法 | 风险 |
|---|---|---|
| at-most-once | 先提交位点，后处理 | 处理失败就丢了 |
| at-least-once | 先处理，后提交位点 | 可能重复 |
| exactly-once | 事务 + 幂等 + 位点原子提交 | 实现极复杂，通常只在流处理框架里 |

IM 选 at-least-once + 幂等。**所有「我们做到了 exactly-once」的说法，往下追一层都是这个。**

## 3.7 服务发现：服务之间怎么找到对方

微服务拆开后，「用户服务」要调「群组服务」，它怎么知道群组服务在哪台机器、哪个端口？

三种方式：

| 方式 | 做法 | 问题 |
|---|---|---|
| **硬编码** | 配置里写 `127.0.0.1:8001` | 扩容/迁移就要改配置 |
| **DNS / 负载均衡器** | 访问 `group-svc` 域名，LB 转发 | 多一跳，且更新有延迟 |
| **服务注册中心** | 服务启动时注册自己，调用方查询 | 需要额外组件，但最灵活 |

**注册中心的工作方式**：

```
群组服务启动 → 往 etcd 写入 /openim/group/1 = "10.0.0.5:8003"（带 TTL，定期续约）
用户服务要调 → 从 etcd 读 /openim/group/ → 拿到地址列表 → 选一个 → gRPC 调用
群组服务挂了 → TTL 过期 → etcd 自动删除这个节点
```

常见实现：**etcd**（K8s 用的就是它）、Consul、ZooKeeper、Nacos。

> 🔴 **关键抽象**：好的设计会把「服务发现」抽象成接口，这样**etcd 实现**和**进程内实现（直接返回内存里的服务对象）**可以互换。OpenIM 的 `inprocess` 就是这么做的（第二部分 3.5）。

## 3.8 RPC 是什么，gRPC 又是什么

### 3.8.1 RPC（Remote Procedure Call，远程过程调用）

目标：**让调用远程服务像调用本地函数一样**。

```go
// 本地调用
user, err := GetUser(ctx, "user1")

// RPC 调用（看起来一样）
user, err := userClient.GetUser(ctx, &pb.GetUserReq{UserID: "user1"})
```

底层做的事：把参数**序列化** → 通过网络发送 → 对方**反序列化** → 执行 → 把结果序列化回来。

### 3.8.2 gRPC 的特点

gRPC = Google 的 RPC 框架，基于 **HTTP/2 + Protocol Buffers**。

| 特性 | 说明 |
|---|---|
| **protobuf 序列化** | 二进制，比 JSON 小 3~10 倍，快 5~10 倍 |
| **IDL 契约** | 用 `.proto` 文件定义接口，自动生成客户端和服务端代码 |
| **HTTP/2 多路复用** | 一条 TCP 连接上并发多个请求，不像 HTTP/1.1 要多个连接 |
| **支持流式** | 客户端流、服务端流、双向流 |
| **强制 schema** | 字段有编号，前后兼容（加字段不破坏老客户端） |

**为什么微服务内部用 gRPC 而不是 HTTP+JSON？**
1. 性能：protobuf 编解码快、体积小
2. 契约：proto 就是接口文档，且编译期检查
3. 代码生成：不用手写 client
4. 流式：推送、订阅场景需要

**为什么客户端接入（App/Web）不用 gRPC？**
浏览器不支持 gRPC 的底层帧（gRPC-Web 需要代理），移动端 SDK 生态也不如 WebSocket 成熟。所以**对外用 WS/HTTP，对内用 gRPC**，这是行业惯例。

> 📌 这个「对内 gRPC、对外 WS/HTTP」的分界，就是 OpenIM 三个入口的由来（第二部分 3.3 理念 6）。

## 3.9 缓存分层：LRU、Cache-Aside、三级缓存

### 3.9.1 为什么要缓存

因为**存储介质的访问速度差了 4~6 个数量级**：

| 介质 | 典型延迟 |
|---|---|
| CPU L1 缓存 | ~1 ns |
| 内存 | ~100 ns |
| 本机 SSD | ~100 μs |
| 同机房网络（Redis） | ~500 μs |
| 同机房数据库（Mongo） | ~1~10 ms |

一次 Mongo 查询 = 一万次内存访问。所以「能在内存里拿到的，绝不查库」。

### 3.9.2 LRU 是什么

**LRU（Least Recently Used，最近最少使用）**：缓存满了就淘汰「最久没被访问」的那个。

实现方式：哈希表 + 双向链表。

```
访问 A → 把 A 移到链表头
插入新元素 → 满了 → 删链表尾
```

Go 里常用 `hashicorp/golang-lru` 或自己写。**为什么不用 map + 定时清理？** 因为 LRU 的淘汰是有依据的（时间局部性原理：刚被访问的数据，很快还会被访问），命中率远高于随机淘汰。

### 3.9.3 三级缓存的分工

```
本地 LRU（进程内）  →  Redis（跨进程共享）  →  DB（真相）
    ~1 μs               ~500 μs                ~5 ms
    会丢（进程挂）        可能丢（重启）           不丢
    每实例一份            全局一份               全局一份
```

**为什么需要本地缓存？** 因为 Redis 虽快，但一次网络往返也要几百微秒。对于「每条消息都要查一次群成员」这种超高频读，本地缓存能把 500μs 降到 1μs。

**本地缓存的问题：数据不一致。** A 机器上的缓存说「张三在群里」，B 机器上的缓存说「张三已被踢」——因为 B 更新了，A 没收到通知。

**解法**：本地缓存设短 TTL（几秒），接受短暂不一致；或者用「失效广播」（复杂）。

### 3.9.4 Cache-Aside 模式

最常用的缓存模式，读的时候这么写：

```
读：先查缓存 → 命中就返回
              → 未命中 → 查 DB → 写回缓存 → 返回
写：先写 DB → 再删缓存（不是更新缓存）
```

**为什么是「删缓存」而不是「更新缓存」？**
因为并发下「更新缓存」会导致旧值覆盖新值：

```
线程1: 写 DB = 100
线程2: 写 DB = 200
线程2: 更新缓存 = 200
线程1: 更新缓存 = 100   ← 错了！缓存是 100，DB 是 200
```

删缓存的话，两个线程都删，下次读自然回源拿到最新的 200。

> 🔴 **面试高频**：「缓存穿透/击穿/雪崩」分别是什么？
> - **穿透**：查一个不存在的 key，缓存永远不命中，每次都打 DB → 解法：缓存空值 / 布隆过滤器
> - **击穿**：热点 key 过期的瞬间，大量请求同时打 DB → 解法：互斥锁 / 逻辑过期
> - **雪崩**：大量 key 同时过期 / Redis 挂了 → 解法：TTL 加随机 / 熔断降级 / 多级缓存

## 3.10 增量同步：为什么用「游标」而不是「页码」

### 3.10.1 分页的两种方式

| 方式 | SQL | 问题 |
|---|---|---|
| **offset 分页** | `LIMIT 20 OFFSET 10000` | 深分页要扫 10000 行，越翻越慢；且数据在变会导致**重复/遗漏** |
| **游标分页（cursor）** | `WHERE seq > 10000 LIMIT 20` | 只扫 20 行，快且稳定 |

IM 的消息拉取**必须**用游标，因为：

- 消息是**不断追加**的，offset 会漂移
- 用户翻到第 50 页时，新消息进来，`OFFSET` 会错位
- 深分页性能不可接受（一个群几十万条消息）

### 3.10.2 seq 就是天然的游标

```
客户端本地记：localMaxSeq = 5000
重连时请求：  给我 seq > 5000 的消息
服务端返回：  seq 5001...5100（100 条）
客户端更新：  localMaxSeq = 5100
```

**这个设计的精妙之处**：

- 拉取是**幂等**的（重复请求同一个 seq 区间，结果一样）
- 拉取是**可续**的（断在哪就从哪继续）
- **能检测漏收**（收到 5001、5003，说明缺 5002）
- 不需要「会话快照」之类的额外机制

> 📌 这就是第 14 篇「同步与已读」的全部基础。**理解了 seq，就理解了整个同步体系。**

## 3.2 三层架构与「硬边界」

| 层 | 组件 | 有状态? | 职责 | 扩容方式 |
|---|---|---|---|---|
| **接入层** | `internal/api`（HTTP）、`internal/msggateway`（WS） | API 无状态；网关**有状态**（持连接） | 协议转换、鉴权、连接管理 | API 直接扩；网关扩需广播 |
| **逻辑层** | `internal/rpc/*`、`msgtransfer`、`push` | 无状态 | 全部业务逻辑 | 直接水平扩 |
| **数据层** | Mongo / Redis / Kafka / MinIO | 有状态 | 持久化、缓存、异步 | 分片/集群 |

**为什么必须这么分？**（对应 3.2.1 的分层动机）

反例：如果网关直接写 Mongo——

- 网关要持有 DB 连接池，连接数 × 实例数 = DB 被打爆
- 业务规则（群成员校验、禁言）要在网关里重复实现
- 网关重启会丢正在处理的消息

所以：**网关只做「连接 + 编解码 + 转发」，业务一律下沉到 RPC**。这是一条硬边界。

> 📌 **这条硬边界怎么验证？** 用依赖实测：`internal/msggateway/init.go:38` 是
> `dbb := dbbuild.NewBuilder(nil, &conf.RedisConfig)` —— **Mongo 参数传的是 `nil`**，只建 Redis 客户端。
> 这就是「网关只用 Redis 存在线状态、完全不碰 Mongo」的硬证据，比看架构图可靠。
> 网关对 `pkg` 的依赖也确实只有 `rpcli`（RPC 客户端）、`rpccache`、`cachekey`、`authverify`、`webhook` 这些，**没有 `storage/database`、没有 `storage/controller`**。

⚠️ **易错**：`msggateway` 里面也有一个 gRPC 服务端（`msggateway.RegisterMsgGatewayServer`，`hub_server.go:32`），那是给 **push 服务回调推消息**用的，不是业务 RPC。别把它当成第七个业务服务。

## 3.3 六条设计理念（每条都配反例）

### 理念 1：接入与逻辑分离 🔴

**理论对应**：3.3「有状态 vs 无状态」。

**做法**：网关只管连接，RPC 只管业务，两者通过 gRPC 双向调用。

- 网关 → msg 服务：`message_handler.go:137` `SendMessage` → `msgClient.MsgClient.SendMsg`
- msg/push → 网关：`hub_server.go:157` `SuperGroupOnlineBatchPushOneMsg`

**为什么不合并**：长连接是**有状态且长生命周期**的，业务逻辑是**无状态短请求**。混在一起，任何一次业务代码发版都要断开所有连接。

**面试追问**：「为什么不用网关直接连 Kafka 发消息，省掉 gRPC 一跳？」

答：可以，但会失去三样东西——① 统一的鉴权与限流入口 ② 业务规则（群成员/禁言/黑名单）复用 ③ RPC 层的可观测性。这一跳换来的是「业务变更不动网关」。

---

### 理念 2：写路径异步化 🔴

**理论对应**：3.4「同步 vs 异步」+ 3.5「最终一致」。

**做法**：`SendMsg` 只做「校验 + 补字段 + 投 Kafka」，投递成功即返回。

```go
// internal/rpc/msg/send.go:67-70（群聊分支）
err = m.MsgDatabase.MsgToMQ(ctx, conversationutil.GenConversationUniqueKeyForGroup(req.MsgData.GroupID), req.MsgData)
if err != nil {
    return nil, err
}
// ← 到这里就返回了，不等落库、不等推送
```

```go
// pkg/common/storage/controller/msg.go:112-118
func (db *commonMsgDatabase) MsgToMQ(ctx context.Context, key string, msg2mq *sdkws.MsgData) error {
    data, err := proto.Marshal(msg2mq)
    if err != nil {
        return err
    }
    return db.producer.SendMessage(ctx, key, data)   // 就这一行
}
```

注意 `key` 这个参数：它就是 Kafka 的分区 key（3.4.3）。**用 conversationID 做 key，保证同一会话进同一分区，从而保证会话内有序。**

**同步做的代价（反例）**：一次发送要写 Mongo（10~50ms）+ 更新会话（10ms）+ 推送给 N 个成员。群有 500 人时，同步扇出必然超时。

**代价与补偿**（严格对应 3.4.2 的表格）：

| 代价 | 补偿机制 |
|---|---|
| 发送成功 ≠ 已落库 | 客户端按 seq 拉取补洞（第 14 篇） |
| 短暂不一致 | 正常 100ms 内完成落库 |
| 需要保证不丢 | Kafka 位点 + 幂等写入（第 23 篇） |

---

### 理念 3：seq 驱动的一致性模型 🔴

**理论对应**：3.6.2「顺序性」+ 3.10「游标增量同步」。

**做法**：不依赖时间戳，每条消息在落库时分配会话内自增 `seq`。

```go
// pkg/common/storage/controller/msg_transfer.go:214
currentMaxSeq, err := db.seqConversation.Malloc(ctx, conversationID, int64(len(msgs)))
// 然后逐条赋值
for _, m := range msgs {
    currentMaxSeq++
    m.Seq = currentMaxSeq          // :224-225
}
```

**为什么不用时间戳**（对应 3.10.1 的三条理由，加上 IM 特有的两条）：

- 客户端时钟不可信（可篡改、可漂移）
- 服务端多实例时钟也不同步
- 同一毫秒可能有 N 条消息，无法排序
- 时间做游标会漏（`>` 和 `>=` 都有问题）

**seq 带来的整个同步体系**：

```
客户端本地：每个会话记一个 maxSeq
重连时：    GET /msg/pull_msg_by_seq?seq=localMaxSeq
服务端：    SELECT 所有 seq > localMaxSeq 的消息
```

这就把「消息同步」从「按时间翻页」变成了「按序号的整数区间查询」——**可索引、可计算、可比较**。

📌 **重点**：`seq` 是**会话级**的，不是全局的。会话 A 的 seq=100 和会话 B 的 seq=100 毫无关系。

> 🟡 **难点：为什么不做全局 seq？**
> 三个原因：① 全局自增要一个全局锁/单点，成为性能瓶颈 ② 每个会话的 seq 会出现巨大空洞，客户端无法用「连续区间」判断漏收 ③ 按会话分片存储时，全局 seq 没有分片意义。**「谁需要有序，就在谁的粒度上编号」** —— 这是分布式 ID 设计的一条通则。

---

### 理念 4：三层存储，各管一段

**理论对应**：3.9「缓存分层」。

```
本地 LRU（进程内）  →  Redis（跨进程共享）  →  MongoDB（真相）
   微秒级              毫秒级                    十毫秒级
   会丢                 可能丢                    不丢
```

| 层 | 存什么 | 典型代码 |
|---|---|---|
| 本地 LRU | 用户信息、群成员、会话接收选项 | `pkg/rpccache/user.go`、`pkg/localcache/` |
| Redis | seq 分配器、近期消息、token、在线状态、已读 seq | `pkg/common/storage/cache/redis/` |
| Mongo | 消息文档、seq 表、用户/群/好友/会话 | `pkg/common/storage/database/mgo/` |

**关键设计**：**Redis 不是主存储**。证据：读消息时缓存未命中会返回「已删除」占位（`controller/msg.go:808-810`），说明系统假设「Mongo 才有真相，Redis 只是加速」（对应 3.9.4 的 Cache-Aside）。

⚠️ **易错**：seq 分配器是「Redis 为主 + Mongo 兜底」（第 12 篇），这是**唯一**一个 Redis 承担写主责的地方，其他都是缓存。

> 🟡 **为什么 seq 必须让 Redis 当主？** 因为 seq 分配是「读-改-写」，必须原子。Redis 单线程 + Lua 脚本能保证原子性，Mongo 单文档也能，但 Redis 快一个数量级。代价是「Redis 挂了不能发消息」，所以用 Mongo 的 `$inc` 做兜底降级。

---

### 理念 5：配置驱动 + 单进程合并

**理论对应**：3.1.3「模块化单体/双模式」。

**做法**：每个服务一个 yml，`AllConfig` 聚合 22 个子配置（`pkg/common/config/config.go:734-757`），standalone 模式下反射注入给每个服务。

```go
// cmd/main.go:194-231  parseConf 的核心：按类型匹配字段，反射赋值
pkt := x.getTypePath(field.Type())   // 用"包路径+类型名"做 key
val, ok := x.conf[pkt]
field.Set(val)
```

**收益**：服务代码完全不知道自己的配置从哪来——单进程是反射注入，微服务是各自读文件，**同一份业务代码两种跑法**。

**代价**：反射难调试、IDE 跳转失效、配置缺字段只能在运行时发现（`main.go:224` 的 `config field %s %s not found`）。

🟡 **难点**：`FileConfig` 接口（`config.go:20-22`）只有 `GetConfigFileName()` 一个方法，作用是**让结构体自报「我来自哪个文件」**，从而让反射能自动加载（`main.go:150-161`）。这是「用接口做元数据标记」的典型用法——接口不定义行为，只定义**身份**。

> 📌 这个设计对应 3.7 的「服务发现抽象成接口」。**同一份代码两种跑法的关键，就是把「环境相关的东西」抽成接口**：服务发现（etcd vs 内存 map）、配置来源（文件 vs 反射注入）、RPC 传输（网络 vs 进程内）。第 09、25 篇会逐个展开。

---

### 理念 6：三个入口，一套协议

**理论对应**：3.8「RPC / gRPC」。

| 入口 | 协议 | 谁用 | 典型接口 |
|---|---|---|---|
| HTTP | JSON over HTTP | 管理端、服务端集成 | `/auth/get_admin_token`、`/msg/send_msg` |
| WebSocket | 二进制帧 + protobuf | 客户端（App/Web） | 发消息、拉消息、已读 |
| gRPC | protobuf | 服务间 | `Msg.SendMsg`、`User.GetUsersInfo` |

三者共用同一套 protobuf 定义（外部模块 `github.com/openimsdk/protocol`）。

**为什么客户端不用 HTTP 轮询**（对应 3.3.2 的「服务端主动推送」）：
- 轮询有延迟（间隔多久？）
- 轮询浪费（90% 是空请求）
- 无法服务端主动推送

**为什么 WebSocket 不做成 gRPC-stream**（对应 3.8.2 最后一段）：
- 浏览器/移动端 SDK 对 WS 支持最好
- gRPC-web 生态不成熟（尤其小程序）

## 3.4 消息链路 8 步（本篇只需记住骨架，细节在第 10~15 篇）

```
① 客户端 WS 握手（鉴权）
      ↓
② 网关解码分发（Gob/JSON → Req）
      ↓
③ msg RPC：校验 → 补 ServerMsgID → 投 Kafka(toRedis) → 返回 ✅ 发送成功
      ↓ ─────────── 以下是异步 ───────────
④ msgtransfer 消费：batcher 聚合 → 按会话分片保序
      ↓
⑤ 分配 seq → 写 Redis 缓存 → 建会话（首次）→ 分两路投递
      ↓                                    ↓
⑥ toMongo → 批量落 Mongo(100条/文档)     toPush → push 服务
                                             ↓
                                    ⑦ 在线推送（gRPC 回调网关）
                                       或 离线推送（dummy）
                                             ↓
                                    ⑧ 对端客户端
```

**一句话记忆**：`WS → 校验 → Kafka → seq → Redis → Mongo + Push`。

> 🔴 **用理论解释这条链路**：
> - ③ 到 ④ 之间是 **异步解耦**（3.4.1）——用 Kafka 把「接收」和「处理」分开
> - ④ 的「按会话分片保序」是 **分区有序**（3.6.2）——key = conversationID
> - ⑤ 的 seq 分配是**串行化的临界区**（第 12 篇的 Lua 脚本）
> - ⑥ 到 ⑦ 是**最终一致**（3.5.2）——落库和推送各自异步，最终都完成
>
> **能把 8 步每一步映射到一个架构概念，就是真正理解了，而不是背图。**

## 3.5 架构的演进视角（面试加分）

这个项目经历了三个阶段，理解演进比记住现状更有价值：

| 阶段 | 形态 | 问题 | 解法 |
|---|---|---|---|
| v1 | 单体：一个进程干所有事 | 无法扩容、发版全停 | 拆服务 |
| v2 | 微服务：7 个 RPC + 2 个接入 + etcd | 部署复杂、开发环境重 | 加 standalone 模式 |
| v3（当前） | 双模式并存：微服务 + standalone | —— | `inprocess` 抽象让同一份代码两种跑法 |

📌 **重点**：`inprocess`（进程内服务发现）是关键设计——它让 `discovery.Conn` 这个抽象在同一份业务代码里，既可以是 etcd，也可以是内存 map（`pkg/common/discovery/discoveryregister.go:22-24`）。

> ⚠️ **一个容易误解的细节**：inprocess 模式下**仍然做编解码**，不是直接函数调用。它把请求序列化后再反序列化，强制深拷贝隔离。为什么？因为如果不做，跨服务传递的指针会被共享，A 服务改了对象会影响 B 服务——这在从 standalone 切到微服务时会变成极难查的 bug。**用一点性能换行为一致性**，这是正确的取舍（第 09 篇）。

**面试话术**：「它的架构演进很典型：从单体到微服务解决扩容，再从微服务补一个 standalone 模式解决开发体验。关键是它没有写两套代码，而是把服务发现抽象成接口，etcd 和进程内注册表是同一个接口的两个实现。」

## 3.6 数据流全景（一次群聊发送产生的所有写入）

| 时刻 | 数据 | 位置 | 写者 |
|---|---|---|---|
| 同步 | 消息投递 | Kafka `toRedis` | msg RPC |
| 异步 1 | seq | Redis Hash + Mongo `seq` | msgtransfer |
| 异步 1 | 消息缓存 | Redis | msgtransfer |
| 异步 1 | 会话（首次） | Mongo `conversation` | msgtransfer → conversation RPC |
| 异步 1 | 已读 seq | Redis `seq_user` | msgtransfer |
| 异步 2 | 消息文档 | Mongo `msg` | msgtransfer（第二个消费者） |
| 异步 3 | 在线推送 | 内存（不落盘） | push → gateway |
| 异步 3 | 未读计数 | Redis | push/conversation |
| 异步 3 | 离线推送任务 | Kafka `toOfflinePush` | push |

**这张表回答了一个高频追问**：「你说异步，那到底异步了几层？」

答：**三层**。第一层 msgtransfer 落缓存+分配 seq，第二层落 Mongo，第三层推送。三层之间用 Kafka topic 解耦，各自可以独立扩缩容。

## 3.7 架构的「不完美」之处（主动指出，面试加分）

| 问题 | 现象 | 为什么这样 |
|---|---|---|
| standalone 单点 | 进程挂了全挂 | 为了开发体验的取舍 |
| 网关有状态 | 扩缩容需广播、连接迁移无解 | 长连接的本质约束（3.3.2） |
| 消息最终一致 | 发送成功到对方收到有延迟 | 换吞吐和延迟（3.5.2） |
| Redis 承担 seq 写 | Redis 挂了无法发消息 | 用 Mongo 兜底降级 |
| 离线推送是 dummy | 真实厂商推送未实现 | 瘦身时移除，保留接口 |
| API 层几乎无逻辑 | 大量 `a2r.Call` 一行式 | 薄接入层，逻辑归 RPC |

> 🔴 **这段话的价值**：「它不是一个『完美架构』，而是一堆取舍。比如为了开发体验牺牲了 standalone 的单点问题，为了吞吐牺牲了强一致性。我觉得能说清『为什么这么取舍』比说『这个架构很好』更有价值。」
>
> 面试官最烦的是「我们项目架构非常先进、高可用、高并发」这种空话。**能指出缺点并解释为什么接受这个缺点，才是工程判断力。**

## 3.4 面试话术（3 分钟版，背下来）

> 「OpenIM 是三层架构：接入层是 HTTP API 和 WS 网关，逻辑层是七个 gRPC 服务加 msgtransfer、push，数据层是 Mongo、Redis、Kafka、MinIO。
>
> 它最关键的设计是**写路径异步化**。客户端发消息，网关解码后调 msg 服务，msg 只做校验然后投 Kafka 就返回，不等待落库。后面 msgtransfer 消费，按会话分片聚合，分配 seq、写 Redis、再投 toMongo 和 toPush 两个主题，分别落库和推送。这里用 conversationID 当 Kafka 的 key，保证同一会话的消息落在同一分区，从而保证会话内有序。
>
> 第二个关键设计是**seq 驱动的一致性**。因为客户端时钟不可信，它用服务端分配的会话内自增 seq 来做消息排序和同步，客户端重连只需要上报本地 maxSeq 就能拉到增量。seq 是会话级的而不是全局的，因为全局自增会形成单点瓶颈，而且每个会话的 seq 会出现巨大空洞，没法用连续区间判断漏收。
>
> 存储是三层：本地 LRU、Redis、Mongo，Mongo 是唯一真相。整套设计都是围绕『消息要扇出给很多人、要保证有序不丢』这个核心矛盾展开的。
>
> 它也不是完美架构：standalone 模式是单点、网关有状态所以扩容需要广播、消息是最终一致。但每一处取舍都能说清理由，我觉得这比说架构先进更有价值。」
