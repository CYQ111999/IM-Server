# 第一部分　理论：跑起来之前，你得先懂这些

## 2.1 为什么会有「容器」这个东西

先说一个你肯定经历过的场景：

> 你在自己电脑上装了 MySQL 5.7、Redis 6、MongoDB 5，跑得好好的。同事 clone 你的代码，装不上，或者装上了版本不一样，跑不起来。你远程帮他搞了两小时，最后发现是他本机 3306 端口被另一个 MySQL 8 占了。

这类问题的根源只有一个：**软件运行依赖「环境」，而环境是隐式的、不可复现的。**

一个程序要跑起来，依赖：

| 依赖类型 | 例子 |
|---|---|
| 运行时 | Go / Node / JDK 版本 |
| 系统库 | glibc、libssl 版本 |
| 系统配置 | 时区、locale、文件描述符上限 |
| 端口 | 3306 有没有被占 |
| 数据目录 | 数据存在哪个路径、权限对不对 |
| 环境变量 | `MALLOC_ARENA_MAX`、`TZ` |

只要有一项不匹配，就是「在我机器上是好的」。

**容器（Container）就是把这套隐式环境变成显式、可复制、可分发的东西。**

> 🔴 **一句话定义**：容器 = **一个被隔离的进程** + **一份打包好的文件系统**。它不是虚拟机，没有自己的内核，只是借 Linux 的 Namespace（隔离视图）和 Cgroups（限制资源）让进程「以为自己独占一台机器」。

## 2.2 镜像 / 容器 / 仓库：三个必须分清的概念

初学者最容易把这三个混在一起。

| 概念 | 英文 | 类比 | 说明 |
|---|---|---|---|
| **镜像** | Image | 装系统的 ISO / 一张光盘 | **只读**的模板，包含文件系统 + 启动命令 + 元数据 |
| **容器** | Container | 用光盘装出来的一台机器 | 镜像的**运行实例**，可读可写（写在上层可写层） |
| **仓库** | Registry | 软件下载站 | 存放镜像的地方，如 Docker Hub、腾讯云 TCR |

关系是：

```
Registry（远程仓库）
   │ docker pull
   ▼
Image（本地只读镜像）  ── docker run ──→  Container（运行中的实例）
                                              │
                                         可写层（容器删了就没）
```

**关键理解：镜像不可变。** 你在容器里 `apt install` 装了个东西，重启容器就没了——因为改动只在可写层，而 `docker run` 每次都会新建一个可写层。想让改动持久，要么 `docker commit` 成新镜像（不推荐），要么挂**数据卷**（下面讲）。

## 2.3 容器 vs 虚拟机：别再搞混了

| 维度 | 虚拟机（VM） | 容器（Container） |
|---|---|---|
| 隔离级别 | 硬件虚拟化，每台有独立内核 | 进程级隔离，**共享宿主内核** |
| 启动时间 | 几十秒到几分钟 | 毫秒到秒 |
| 体积 | GB 级 | MB 级 |
| 资源开销 | 每台预留内存/CPU | 用多少占多少 |
| 隔离强度 | 强（安全边界清晰） | 弱（内核共享，逃逸风险） |
| 能不能跑不同内核 | 能（Linux 上跑 Windows） | 不能（Linux 上只能跑 Linux 容器） |

> 🟡 **难点理解**：容器「共享内核」意味着你在容器里 `uname -r` 看到的是宿主机内核版本。所以 OpenIM 的 Mongo 容器在 Windows 上跑，其实是跑在 **WSL2 的 Linux 内核** 上的——这也是为什么 Windows 上必须装 Docker Desktop（它内置了 WSL2 或 Hyper-V 后端）。

**面试追问**：「容器为什么不安全？」
答：因为共享内核，内核漏洞可以直接逃逸；而且默认以 root 运行。所以生产上要做：非 root 用户、seccomp/AppArmor、只读根文件系统、独立的用户命名空间。这是 K8s 安全基线的一部分。

## 2.4 镜像分层与数据卷（这一节直接决定你敢不敢删目录）

### 2.4.1 镜像分层

镜像不是一个整体，而是**一层层叠出来的**。看一个典型 Dockerfile：

```dockerfile
FROM ubuntu:22.04                 # 第 1 层：基础系统
RUN apt-get install -y curl       # 第 2 层：装 curl
COPY app /app                     # 第 3 层：拷程序
CMD ["/app"]                      # 只是元数据，不占层
```

每一条 `RUN` / `COPY` / `ADD` 都会产生一个新层，层与层**只读、可复用**。

**好处**：你本地已经有 `ubuntu:22.04` 这层了，再拉一个基于它的镜像，只需要拉新增的层。这叫**层缓存**，是 Docker 快的原因。

**副作用（重要的工程实践）**：层是累积的，你在第 2 层 `apt install` 装了个 500MB 的包，第 3 层又删掉它，**镜像体积不会变小**——因为第 2 层还在。所以 Dockerfile 里要用「`&&` 串联 + 最后清理」的写法。

> 📌 这条知识在本项目里有直接体现：`Dockerfile` 里 `COPY` 和 `RUN download` 的顺序会影响构建缓存命中率（第 28 篇会讲这个 Dockerfile 的实际问题）。

### 2.4.2 数据卷：容器的「硬盘」

容器删了，可写层就没了。但数据库的数据不能没。所以要把**宿主机的某个目录**映射到容器里，这就是**挂载（Mount）**。

Docker 有两种主要挂载方式：

| 方式 | 写法 | 存在哪 | 谁管理 | 适合 |
|---|---|---|---|---|
| **bind mount**（绑定挂载） | `./components/mongodb/data/db:/data/db` | **你指定的宿主机路径** | 你 | 配置文件、需要自己备份的数据 |
| **named volume**（命名卷） | `mongo_data:/data/db` | Docker 自己管理的目录（Linux 在 `/var/lib/docker/volumes/`） | Docker | 生产环境数据 |

**核心区别一句话**：

- bind mount = 「我把我的目录借给你用」→ **你能直接看到、能直接改、删了就真没了**
- named volume = 「你给我开个保险箱」→ 你看不到路径，用 `docker volume ls` 管

> ⚠️ **这就是 `components/` 不能删的根本原因。**
> `docker-compose.yml` 里写的是 `./components/mongodb/data/db:/data/db`——这是 **bind mount**，`components/mongodb/data/db` 就是 Mongo 的 `dbpath`，里面的每个文件都是真实的数据库文件。
>
> 删掉这个目录：容器**还在**（`docker ps` 看得到），但 Mongo 起来会**创建一个全新的空库**。你的 `im_v3` 库里所有用户、群、消息**全部消失**，而且**无法恢复**（没有备份的话）。

### 2.4.3 怎么验证一个目录真的是数据卷（不是猜，是证明）

看 compose 文件是「声明」，`docker inspect` 是「事实」。两者可能不一致（比如你起了别处的 compose）。

```bash
docker inspect openim-mongodb --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
```

输出里应该出现 `.../open-im-server-main/components/mongodb/data/db -> /data/db`。

**如果指向别处，说明你起的根本不是这个仓库的 compose**——这是排查「我改了配置为什么不生效」的第一手段。

> 🧪 这个实验在 2.9 节会真的做一遍。

## 2.5 端口映射：为什么是 `37017:27017`

容器有自己的网络命名空间，里面的端口外部访问不到。所以要**端口映射**：

```
宿主机:容器   37017:27017
        │      └─ 容器内部监听的端口（Mongo 默认 27017）
        └──────── 你在宿主机上访问的端口
```

于是：

- 容器内部的进程认为自己监听 `27017`（不受影响，镜像不用改）
- 你在 Windows 上用 `127.0.0.1:37017` 访问
- 其他容器之间用「容器名:27017」访问（Docker 内建 DNS）

**为什么全改成 3xxxx / 1xxxx？** 只有一个原因：**宿主机上可能已经有同端口的原生服务**。

比如你的机器上 `D:/Redis` 有个原生 Redis 跑在 6379。如果容器也映射 6379，`docker compose up` 会直接报 `port is already allocated`。改成 16379 就绕开了。

> 📌 **这是一个真实的工程习惯**：开发机上给容器统一分配一个端口段（比如 3xxxx），和生产默认端口错开。好处是「看到 37017 就知道是容器里的 Mongo，看到 27017 就是本机的」。

> ⚠️ **易错**：改了宿主端口，**配置文件里的地址也要跟着改**。`config/*.yml` 里写的是 `127.0.0.1:37017`，不是 27017。这就是为什么 2.7 节的 `check-component` 工具这么重要——它专门验证「配置里的地址」和「实际能连的地址」是否一致。

## 2.6 Docker Compose：把「一堆 docker run」写成文件

一个中间件栈有 5 个容器，每个都要写一长串 `docker run -p ... -v ... -e ...`，还要保证启动顺序、网络互通。手敲是灾难。

**Compose 就是声明式的容器编排**：把「我要哪些容器、怎么配」写进一个 YAML，然后 `docker compose up -d` 一条命令拉起。

```yaml
services:
  mongodb:
    image: mongo:6.0.4
    ports: ["37017:27017"]
    volumes: ["./components/mongodb/data/db:/data/db"]
```

几个必须知道的概念：

| 概念 | 说明 |
|---|---|
| `service` | 一个容器的定义（不是「服务」的意思，是「一组相同配置的容器」） |
| `-d` | detached，后台运行。不加会占住终端 |
| `docker compose ps` | 看当前项目的容器状态 |
| `docker compose logs -f <svc>` | 跟日志 |
| `docker compose down` | **停止并删除容器**（bind mount 的数据不会删，named volume 默认保留） |
| `docker compose down -v` | **连 named volume 一起删**（⚠️ 危险） |

**关键设计：Compose 项目（project）**。同一个目录下 `docker compose up` 会创建一个「项目」，名字默认是目录名（本项目是 `open-im-server-main`）。容器名会带项目前缀，**所以两个不同目录的同名 compose 可以共存不冲突**（但端口会冲突）。

> ⚠️ **易错**：`docker compose down` 和 `docker compose stop` 不一样。`down` 会删容器（下次 `up` 重建），`stop` 只是停。日常开发用 `stop`，改 compose 文件后要 `down` 再 `up` 才会生效。

## 2.7 编译型语言：为什么 `mage build` 必须在 `mage start` 之前

这是 Go 和 PHP/Python 最大的使用差异之一，很多人第一次接触会懵。

| 语言类型 | 执行方式 | 部署产物 | 改代码后 |
|---|---|---|---|
| 解释型（PHP/Python） | 源码直接交给解释器执行 | 源码文件 | 重启进程即可 |
| 编译型（Go/C++/Rust） | 先编译成**机器码二进制** | 一个可执行文件 | **必须重新编译** |

Go 的流程是：

```
.go 源码  ──go build──→  二进制文件（如 openim-api）──→  运行
```

**关键点：`openim-api` 这个命令不存在于 `go run` 之外。** 你必须先编译出可执行文件，才能执行它。

所以本项目的启动脚本 `start-config.yml` 里列的是**二进制名**：

```yaml
serviceBinaries:
  openim-api: 1
  openim-msggateway: 1
  ...
```

`mage start` 做的事就是「按这个清单，去 `_output/` 目录里找这些二进制，逐个拉起来」。

**如果 `_output/` 是空的**，它就会报：

```
Binary not found ... Please build first
```

> 🔴 **这不是 bug，是编译型语言的基本约束**。`mage start` 只负责「拉起」，不负责「编译」——这两件事被刻意分开了（`magefile.go` 里 `Build()` 和 `Start()` 是两个独立函数）。

**为什么这样设计？** 因为开发时的节奏是：改代码 → build（2 分钟）→ start（1 秒）。如果 start 里包含 build，你每次调一个参数都要等 2 分钟编译。

## 2.8 Mage 是什么

Go 生态里的构建工具，定位类似 `make`，但**任务用 Go 代码写**，而不是 Makefile 那种 tab 缩进的 DSL。

```go
// magefile.go 的形态
func Build() {
    mageutil.WithSpinner("Building...", func() {
        mageutil.Build(bin, config, nil)
    })
}

func Start() {
    mageutil.StartToolsAndServices(bin, nil)
}
```

好处：

| Makefile | Mage |
|---|---|
| tab 缩进，错一个空格报奇怪的错 | 就是 Go 代码，IDE 有补全 |
| 平台差异要自己处理（Windows 没 bash） | 跨平台，本身就是 Go 程序 |
| 复杂逻辑只能调 shell | 可以直接写 Go 逻辑 |

> 📌 `mage` 本身是个二进制的 Go 程序，它读 `magefile.go`（带 `//go:build mage` 标签），编译执行里面的函数。所以 `mage build` 本质是「编译并运行 `magefile.go` 的 `Build()` 函数」。

**本项目的 magefile 做了什么**（`magefile.go`）：

| 函数 | 作用 |
|---|---|
| `Build()` | 编译 `cmd/openim-*` 下所有入口 → 输出到 `_output/` |
| `Start()` | 读 `start-config.yml` → 按 `serviceBinaries` 拉起进程 |
| `Stop()` | 按进程名杀掉 |
| `Clean()` | 删 `_output/` |
| `BuildTools()` | 编译 `tools/` 下的运维工具 |

> ⚠️ **易错**：`mage build` 编译的是 **`cmd/` 下的入口**，不是 `internal/` 下的包。`internal` 是库，不能单独运行。这是 Go 的组织约束：**只有 `package main` 才能编译成可执行文件**。

## 2.9 进程模型：29 个进程从哪来

很多人第一次 `mage start` 后 `tasklist | findstr openim` 看到 29 个进程会愣住。

答案在 `start-config.yml`：

```yaml
serviceBinaries:
  openim-api: 1                 # API 服务
  openim-crontask: 4            # 定时任务，4 个实例
  openim-rpc-user: 1
  openim-msggateway: 1          # WS 网关
  openim-push: 8                # 推送，8 个实例
  openim-msgtransfer: 8         # 消息中转，8 个实例
  openim-rpc-conversation: 1
  openim-rpc-auth: 1
  openim-rpc-group: 1
  openim-rpc-friend: 1
  openim-rpc-msg: 1
  openim-rpc-third: 1
```

加一下：`1+4+1+1+8+8+1+1+1+1+1+1 = 29`。

**为什么 push 和 msgtransfer 要 8 个？**
因为它们是**吞吐瓶颈**：msgtransfer 要处理所有消息的中转和落库，push 要处理所有在线/离线推送。多实例并行 + Kafka 消费组分区，是最直接的扩容方式。而 rpc-* 是纯计算，1 个实例足够演示。

**为什么 crontask 要 4 个？**
定时任务通常按「周期 + 分片」跑。4 个实例意味着有 4 个不同的定时任务在跑（或者同一个任务的不同分片）。具体见 `internal/tools/cron/`。

> 📌 **注意**：这 29 个进程**都在宿主机上**，不在 Docker 里。Docker 里只有 5 个中间件。所以 `docker stats` 看不到业务进程，这是正常的。

## 2.10 JWT 是什么，`operationID` 又是什么

### 2.10.1 JWT（JSON Web Token）

传统 session 方案：登录后服务端存一个 session，返回 sessionId 给客户端；每次请求带上 sessionId，服务端去查存储。**问题**：多实例要共享 session（得放 Redis），有状态。

JWT 方案：**把「用户是谁」这件事签名后直接交给客户端**，服务端不存。

一个 JWT 长这样（三段，用 `.` 分隔）：

```
eyJhbGciOiJIUzI1NiJ9 . eyJ1c2VySUQiOiJ1c2VyMSIsImV4cCI6MTcwMDAwMDAwMH0 . 签名
        ↑ header              ↑ payload（base64 的 JSON）              ↑ signature
```

| 部分 | 内容 |
|---|---|
| header | 算法（HS256）+ 类型 |
| payload | 业务声明（claims），如 `userID`、`platformID`、`exp` 过期时间 |
| signature | `HMAC-SHA256(header.payload, 密钥)` |

**验证方式**：服务端用同一个密钥重算签名，一致就说明**没被篡改**。

**关键认知：JWT 不是加密，只是签名。** payload 是 base64，**任何人都能解开看**。所以里面**不能放密码、手机号等敏感信息**。

**JWT 的天然缺陷**：无法主动失效。签出去 7 天有效，用户注销了也只能等它过期。所以工程上要配合「黑名单 / 强制下线标记」——OpenIM 就是这么做的（token 存 Redis，支持 `KickToken`）。

> 🔴 这是面试高频题：「JWT 怎么实现登出？」标准答法：JWT 本身做不到，要么维护黑名单（Redis 存被注销的 jti），要么用短期 access token + 长期 refresh token。

### 2.10.2 `operationID`：一条请求的身份证

一个请求会经过：客户端 → API → gRPC → Kafka → msgtransfer → Mongo → 推送。

出问题时你要回答：「**这条消息在哪个环节丢了？**」如果每层日志都是独立的、没有关联字段，你只能靠时间戳猜。

**解法**：请求进来时生成一个唯一 ID，一路透传，所有日志都带上它。

- 在微服务里这个字段常叫 `trace_id` / `request_id`
- **OpenIM 里叫 `operationID`**（`mw.GinParseOperationID`）

它有两个作用：
1. **全链路日志串联**：`grep operationID _output/logs/*.log` 能看到这个请求经过的每一步。
2. **客户端请求去重/关联**：客户端把 `operationID` 带上去，服务端响应带上同一个，客户端能对上「这个响应是哪个请求的」。

> ⚠️ **易错**：`operationID` 是**必填的 HTTP Header**。不传会直接报 1001。这是新手最常踩的坑之一——很多人第一次调 `/auth/get_admin_token` 就是被这个拦住的。

## 2.11 WebSocket 握手：一句话版

详细在 06 篇，这里只建立概念。

普通 HTTP 是「**请求-响应**」：客户端问，服务端答，答完连接就断了。服务端**没法主动**给客户端发东西。

WebSocket 解决这个问题：客户端发一个带特殊 Header 的 HTTP 请求（`Upgrade: websocket`），服务端同意后，**这条 TCP 连接就不关了**，双方可以随时互发数据帧。

```
客户端                                 服务端
  │  GET /?token=xxx  (Upgrade: websocket)  │
  │ ──────────────────────────────────────→ │  ← 握手（复用了 HTTP 的格式）
  │  101 Switching Protocols                │
  │ ←────────────────────────────────────── │
  │                                         │
  │  ←── binary frame（新消息）────────────  │  ← 从此双向
  │  ──── binary frame（发消息）──────────→  │
```

**为什么握手要带 `token`？** 因为 WS 一旦建立就是长连接，后续不再有 HTTP Header 可以带认证信息。所以认证必须在**握手这一次**完成。

> 📌 这就是 06 篇要讲的「握手鉴权」。OpenIM 把 `token` 放在 **URL query** 里（不是 Header），这是 WS 的常见做法（浏览器 WS API 不支持自定义 Header）。

# 第二部分　源码：把这个环境跑起来并证明它真的在跑

## 2.1 运行架构：我们要起哪些东西

这个项目的运行环境分两层：

```
┌───────────────────── 业务进程层（Go 二进制，宿主机） ─────────────┐
│  mage start 拉起：api / msggateway / msgtransfer / push /         │
│                   rpc×7 / crontask（共 29 个进程）                 │
└───────────────────────────────┬───────────────────────────────────┘
                                │ 通过 127.0.0.1:3xxxx 访问
┌───────────────────── 中间件层（Docker 容器） ─────────────────────┐
│  mongodb · redis · etcd · kafka · minio                          │
│  （+ 可选监控栈：prometheus · alertmanager · grafana · node-exp）  │
│  （+ 可选前端：openim-web-front）                                  │
└───────────────────────────────────────────────────────────────────┘
```

**关键认知**（呼应 2.9）：中间件在 Docker 里，业务进程**在宿主机上**。所以必须区分「容器起没起」和「进程起没起」两件独立的事。

**为什么这么设计？** 开发时改 Go 代码要重新编译，如果业务进程也在容器里，就得「改代码 → 重建镜像 → 重启容器」，一次几分钟。放在宿主机上，`mage build && mage start` 就完事。

## 2.2 中间件清单（`docker-compose.yml`）

|---|---|---|---|---|---|
| mongodb | openim-mongodb | **37017** | 27017 | 主存储（消息/用户/群/会话） | `components/mongodb/data/db` |
| redis | openim-redis | **16379** | 6379 | 缓存 + seq + token | `components/redis` |
| etcd | openim-etcd | **12379** | 2379 | 服务注册发现 | `components/etcd` |
| kafka | openim-kafka | **19094** | 9094（外部） | 消息队列 | `components/kafka` |
| minio | openim-minio | **10005** / 10006 | 9000/9001 | 对象存储（图片/文件） | `components/mnt` |
| openim-web-front | — | 11001 | 80 | 管理后台前端（可选） | — |
| prometheus | — | 19090 | 9090 | 指标采集（可选） | — |
| grafana | — | 13000 | 3000 | 监控面板（可选） | — |

📌 **重点**：端口全部避开了默认端口。原因见 2.5——你机器上可能已有原生 Redis/Mongo，用默认端口必然冲突。

⚠️ **绝对不要删 `components/`**（原因见 2.4.2）：

```
components/mongodb/data/db   ← Mongo 的 dbpath（305M，含 im_v3 库）
components/kafka             ← Kafka 的 log.dirs（1.7G）
components/etcd              ← etcd 的 data-dir（139M）
```

🧪 **验证挂载是否真的指向这里**（这是 2.4.3 讲的「声明 vs 事实」）：

```bash
docker inspect openim-mongodb --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
```

**如果指向别处，说明你起的不是这个仓库的 compose。**

## 2.3 五步启动流程（顺序不能乱）

```bash
cd /d/IM-Server/open-im-server-main
```

### 第 1 步：起中间件

```bash
docker compose up -d
docker compose ps          # 五个都是 running 才算好
```

⚠️ 首次启动 Kafka 需要 30~60 秒初始化（它要格式化 log 目录、创建元数据），不要立刻做第 2 步。

### 第 2 步：自检五项中间件

```bash
go run ./tools/check-component -c ./config
```

期望输出：五项（Mongo / Redis / etcd / Kafka / MinIO）全部 `succeeded`。

这个工具在 `tools/check-component/main.go`，做的事就是**按 `config/*.yml` 里的地址逐个尝试连接**。它挂了说明「配置里的地址」和「实际能连的地址」不一致——呼应 2.5 的警告。最常见的三种原因：

- 容器没起（`docker compose ps` 看不到）
- 端口被本机其他服务占了（比如你机器上 `D:/Redis` 的原生 6379）
- 配置文件被改过

### 第 3 步：构建（**最容易漏的一步**）

```bash
mage build
```

约 2 分钟，产出 `_output/` 目录（8 个工具 + 12 个服务二进制）。

⚠️ **`mage start` 不会自动构建**（原因见 2.7）。`_output/` 不存在时直接 `mage start`，会报一堆：

```
Binary not found ... Please build first
```

### 第 4 步：启动

```bash
mage start
```

期望：29 个进程起来（清单见 2.9）。观察方式：

```bash
# Windows
tasklist | findstr openim
```

核心端口起来后可以立刻验证：
- API `10002`
- WS 网关（看 `config/openim-msggateway.yml` 的端口配置）

### 第 5 步：停止

```bash
mage stop
```

中间件不停（`docker compose down` 才停容器）。**日常开发不需要停中间件**——它们占的内存不多，重启一次要等 Kafka 初始化。

## 2.4 端到端验证（做完这三条才算真跑通）

### 验证 1：拿到管理员 token（验证 JWT 签发链路）

```bash
curl -s -X POST "http://127.0.0.1:10002/auth/get_admin_token" \
  -H "Content-Type: application/json" -H "operationID: t1" \
  -d '{"secret":"<见凭据文件>","userID":"imAdmin"}'
```

期望：`errCode: 0`，`data.token` 是一段 JWT。

**这一步验证了什么**（比表面多）：

1. API 进程活着（HTTP 端口通）
2. `operationID` 中间件工作正常（缺了会报 1001）
3. API 能通过 gRPC 调通 auth RPC 服务
4. auth 服务能读 Redis（token 要写缓存，用于后续 KickToken）
5. 配置里的 `share.secret` 生效

⚠️ **易错**：`get_admin_token` 在**鉴权白名单**里（`router.go:434-439`），不需要 `token` 头。但 `operationID` 头**必须有**——这是 `mw.GinParseOperationID` 强制要求的（见 2.10.2）。

### 验证 2：用 token 调一个业务接口（验证 token 透传链路）

```bash
TOKEN="<上一步的 token>"
curl -s -X POST "http://127.0.0.1:10002/user/get_users_info" \
  -H "Content-Type: application/json" \
  -H "token: $TOKEN" -H "operationID: t2" \
  -d '{"userIDs":["imAdmin"]}'
```

期望：返回管理员用户信息。

**这一步验证了什么**：token 解析链路 —— `HTTP header → auth RPC ParseToken → 写 ctx → gRPC 透传 → user 服务`。

> 📌 注意这两步的差别：验证 1 走的是「白名单 + secret」，验证 2 走的是「token + 中间件解析」。两条路要都通，才算真的通了。

### 验证 3：WS 网关连通

WS 是这个项目的主通道，必须单独验证。**四个坑连环**，缺一个都连不上（理论背景见 2.11）：

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | 握手 URL 缺参数 | `ParseBool "" invalid syntax` | 必带 `token`、`sendID`、`platformID`、`operationID`、`isBackground` |
| 2 | 发 text 帧 | `not support text message type` | 必须发 **binary** 帧 |
| 3 | 请求体当 JSON 发 | 解码失败/字段全空 | 体是 `Req{reqIdentifier,token,sendID,operationID,msgIncr,data}`，`data` 是 **base64(protobuf)** |
| 4 | 没加 `sdkType=js` | 服务端按 Gob 解码，乱码/失败 | URL 加 `sdkType=js` 走 JSON 编码器 |

**四个坑的源码根因**（这才是本篇的价值）：

| # | 源码位置 | 原因 |
|---|---|---|
| 1 | `internal/msggateway/context.go:126` | `strconv.ParseBool(query.Get(BackgroundStatus))` 对空字符串直接返回 error，不忽略 |
| 2 | `internal/msggateway/client_conn.go`（读循环）| 只处理 `websocket.BinaryMessage`，其他类型返回错误 |
| 3 | `internal/msggateway/message_handler.go:29-36` | `Req.Data []byte`，protobuf 序列化后 base64 传输 |
| 4 | `internal/msggateway/client.go:88-92` | `if c.SDKType == GoSDK { GobEncoder } else { JsonEncoder }`，默认 SDKType 是 `GoSDK`（`context.go:159-161`） |

> 🟡 **坑 4 特别值得讲**：为什么默认是 Gob？
> Gob 是 Go 标准库的二进制序列化格式（`encoding/gob`），比 JSON 小、比 JSON 快，但**只有 Go 能解**。所以 Go SDK 用 Gob，Web/小程序/其他语言 SDK 必须显式声明 `sdkType=js` 走 JSON。这是「性能优先 + 显式降级」的设计，不是 bug。

🧪 **最小 WS 验证脚本思路**（Go 或 Node 都行）：

```
1. 先拿 token（get_admin_token）
2. 连 ws://127.0.0.1:<gw端口>/?token=...&sendID=imAdmin&platformID=5&operationID=ws1&isBackground=false&sdkType=js
3. 发一个 binary 帧，内容是 JSON 序列化的 Req，reqIdentifier 取 WSGetNewestSeq，data 是 base64(protobuf GetMaxSeqReq)
4. 收到 Resp，errCode=0 即通
```

📌 这一步不跑也能学下去，但跑通了后面讲链路会非常踏实。建议至少把验证 1 和 2 跑通。

## 2.5 日志在哪（以及为什么你可能看不到）

配置在 `config/log.yml`：

| 配置 | 值 | 含义 |
|---|---|---|
| `storageLocation` | `../../../../logs/` | 相对**二进制所在目录**，即 `_output/logs/` |
| `remainLogLevel` | `6` | 6 = debug（生产建议 3 = info） |
| `isStdout` | `false` | 不打印到终端 |
| `rotationTime` | `24` | 24 小时轮转 |
| `remainRotationCount` | `2` | 保留 2 份 |

> 🟡 **难点：为什么日志级别 6 是 debug，3 是 info？**
> 大多数框架是「数值越大越严重」，这里反过来。因为 OpenIM 用 iota 定义了级别枚举：
> `LevelFatal=0 → LevelError → LevelWarn → LevelInfo → LevelDebug → LevelDebugWithSQL=6`
> **数值越小越严重**。所以 `remainLogLevel: 6` 意思是「保留到 debug 及以上」，即全打。这个反直觉的设计在第 27 篇会展开。

⚠️ **易错**：`isStdout: false` 时，`mage start` 的终端看起来「什么都没发生」——其实日志全在 `_output/logs/` 下按服务名分文件。排查问题时先改 `isStdout: true` 或直接 `tail -f`。

🧪 看某个服务的实时日志：

```bash
tail -f _output/logs/openim-msggateway*.log
```

**日志格式值得注意**：每条日志会自动带 `operationID`（通过 `mcontext`，见 2.10.2），这是全链路追踪的关键。

## 2.6 常见故障排查表

| 现象 | 原因 | 解决 |
|---|---|---|
| `check-component` 某项失败 | 容器没起/端口冲突 | `docker compose ps` + `netstat -ano \| findstr 37017` |
| `mage start` 报 `Binary not found` | 没构建 | `mage build` |
| API 起不来，日志报 `address already in use` | 10002 被占 | 改 `config/openim-api.yml` 的 `ports` |
| WS 握手 400 | URL 缺参数 | 补齐 5 个参数 |
| WS 连上立刻断 | 发的是 text 帧 | 改 binary |
| WS 收不到消息 | `sdkType` 没设 | 加 `sdkType=js` |
| 发消息报 1001 | 缺 `operationID` 头 | 加上 |
| 发消息报 1002 | 不是管理员 | `/msg/send_msg` 只有 admin 能调（见 2.7） |
| Mongo 连不上但容器正常 | 连到了原生 Mongo | 检查配置端口是不是 37017 |
| 消息发出去了但库里没有 | msgtransfer 没起/kafka 没消费 | 看 `_output/logs/openim-msgtransfer*.log` |
| 改了 compose 配置不生效 | 没有 `down` 再 `up` | `docker compose down && up -d`（见 2.6） |

## 2.7 一个必须知道的边界：`/msg/send_msg` 不是普通发消息接口

`internal/api/msg.go:266` 的 `SendMessage` 里有：

```go
if !authverify.IsAdmin(c) {
    apiresp.GinError(c, errs.ErrNoPermission.WrapMsg("only app manager can send message"))
    return
}
```

（`internal/api/msg.go:278`）

所以：**普通用户发消息只能走 WebSocket**。这个 HTTP 接口是给管理端/服务端用的（比如客服系统代发、系统公告）。

⚠️ **易错**：很多教程拿 `/msg/send_msg` 演示发消息，然后困惑「为什么普通用户 token 报 1002」。原因就在这里。

> 📌 这条设计的合理性：**IM 的写路径必须走长连接**。因为消息要立刻扇出给对端，走 HTTP 一遍还要回头推，等于绕了一圈。HTTP 发消息只是给「服务端代发」这种场景留的口子，天然应该是管理员权限。

## 2.8 环境相关的三条铁律

1. **只用本仓库的 `docker-compose.yml`**。不要另外 clone 上游的 `openim-docker`——端口（etcd 12379 / MinIO 10005）会撞，两个一起开必炸。
2. **`components/` 是活数据**（2.4.2）。要备份就整体备份，不要单独动某个子目录。
3. **`_output/` 可随时重建**。删了不心疼，`mage build` 两分钟回来。

## 3.2 面试话术

**版本 A：讲部署形态（30 秒）**

> 「这个项目是中间件容器化、业务进程宿主机直跑的部署方式。五个中间件都改了默认端口避免冲突——37017、16379 这些——数据目录以 bind mount 方式挂在仓库的 `components/` 下，所以那个目录就是真实的数据卷，不能当普通文件夹删。
>
> 启动顺序是 compose 起中间件、check-component 自检、mage build、mage start。之所以 build 和 start 必须分开，是因为 Go 是编译型语言，start 脚本拉的是 `_output/` 里的二进制，不负责编译。」

**版本 B：讲验证方法（面试加分，体现工程素养）**

> 「验证一套分布式环境我不用『看起来没报错』当标准，而是分层验证：先用 check-component 验证中间件连通性，再用管理员 token 打一个 auth 接口——这一步能同时验证 API 进程、operationID 中间件、gRPC 调用、Redis 写入四层；然后用这个 token 打一个业务接口，验证 token 的解析和 ctx 透传；最后单独验 WS 握手，因为长连接是另一个通道。
>
> 另外我习惯用 `docker inspect` 看实际的挂载点，而不是只看 compose 文件——因为『声明』和『事实』经常不一致，这是排查配置不生效最快的手段。」
