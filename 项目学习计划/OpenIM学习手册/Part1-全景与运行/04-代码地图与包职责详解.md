# 第一部分　理论：Go 项目的组织方式

## 4.1 为什么 Go 项目都长成 `cmd/ internal/ pkg/`

### 4.1.1 从「所有代码堆在一个目录」说起

如果你写小工具，代码是这样的：

```
myapp/
├── main.go
├── handler.go
└── db.go
```

所有文件都是 `package main`，互相直接调函数。**这在 500 行以内是最优解**。

一旦超过几千行，问题就来了：

| 问题 | 现象 |
|---|---|
| 命名冲突 | 两个文件都想叫 `Config` |
| 无法复用 | 想把 `db.go` 用到另一个项目，但它依赖 `main.go` 里的全局变量 |
| 无法测试 | 测 `handler` 必须启动整个 main |
| 循环依赖 | A 调 B，B 又调 A，在同一个包里编译器不报错，但逻辑已经乱了 |

解法就是**拆包**。而拆包需要一套**约定**——因为 Go 官方没有强制布局，社区就形成了事实标准。

### 4.1.2 事实标准：`cmd` / `internal` / `pkg`

这个布局来自 [golang-standards/project-layout](https://github.com/golang-standards/project-layout)（注意：**它不是官方标准**，但被绝大多数项目采用）。

| 目录 | 放什么 | 规矩 |
|---|---|---|
| `cmd/` | **可执行入口**，每个子目录一个 `main` 包 | 只做装配，不写业务 |
| `internal/` | **私有代码**，外部项目不能 import | Go 编译器强制（见 4.3） |
| `pkg/` | **可被外部复用的库** | 理论上外部项目可以 import |
| `api/` | 对外 API 定义（proto/openapi） | 本次项目在外部模块里 |
| `config/` | 配置文件 | — |
| `docs/` | 文档 | — |
| `tools/` | 构建/运维脚本工具 | — |

**为什么入口要单独放 `cmd/`？**

因为 Go 的约束：**只有 `package main` 且包含 `func main()` 的包才能编译成可执行文件**。

一个项目可能有很多入口：

```
cmd/
├── server/main.go        → 编译出 server
├── worker/main.go        → 编译出 worker
└── cli/main.go           → 编译出 cli
```

如果入口和业务混在一起，就会出现「业务包里有一堆 `func main()`」的混乱，而且**业务包无法被其他入口复用**（`main` 包不能被 import）。

> 🔴 **一句话原则**：`cmd/` 只负责「组装」（读配置、建连接、拉起服务），**一行业务逻辑都不写**。业务全在 `internal/`。

### 4.1.3 `pkg/` 的争议

`pkg/` 这个目录名其实**有争议**。Go 社区的另一种观点是：**不需要 `pkg/`，直接放根目录**（如 `myapp/storage`、`myapp/cache`）。理由是 `pkg` 只是一层无意义的嵌套。

两种写法都存在，看到时不用纠结。**关键不是目录名，而是「能不能被外部 import」这个语义**。

## 4.2 Go 模块（Module）与 import 路径

### 4.2.1 module 是什么

Go 1.11 引入 module，取代了 `GOPATH`。一个 module 由 `go.mod` 定义：

```
module github.com/openimsdk/open-im-server/v3

go 1.25.0
```

- `module` 后面那串 = **模块路径（module path）**，也是所有包的 import 前缀
- 最后一个 `/v3` = **主版本号后缀**（Go modules 的语义化版本规则：v2 以上必须带 `/vN`）

所以这个项目里，`internal/rpc/msg` 包的完整 import 路径是：

```go
import "github.com/openimsdk/open-im-server/v3/internal/rpc/msg"
```

> ⚠️ **易错**：全局搜代码时，搜 `open-im-server/v3/internal` 能命中，搜 `internal/rpc/msg` 也能命中，但**搜 `openim-server/internal` 什么都搜不到**（少了 `open-im` 里的连字符和 `v3`）。很多人第一次用 grep 找依赖时就被这个卡住。

### 4.2.2 `go.mod` / `go.sum` 分别是什么

| 文件 | 作用 |
|---|---|
| `go.mod` | 声明模块路径 + 依赖的模块和版本 |
| `go.sum` | 每个依赖的**内容哈希**，防止被篡改（供应链安全） |

`go.sum` 不能手改，也不能随便删——删了下次 `go mod download` 会重新生成，但如果依赖被投毒，你就失去校验能力了。

### 4.2.3 依赖版本管理的关键命令

| 命令 | 作用 |
|---|---|
| `go mod tidy` | 补全缺失依赖、删除未使用依赖 |
| `go mod download` | 下载依赖到本地缓存 |
| `go list -m all` | 列出所有依赖及版本 |
| `go mod why <pkg>` | 为什么这个包被引入（排查依赖来源神器） |

> 🧪 **实战技巧**：想知道某个可疑依赖是谁引入的，用 `go mod why -m <module>`。这比翻几十个 go.mod 快得多。

## 4.3 `internal/` 是编译器强制的（这是 Go 最独特的设计之一）

**这一节是本篇最重要的理论点。**

### 4.3.1 `internal` 的规则

Go 有一条硬规则：

> 路径中**包含 `internal` 目录**的包，**只能被 `internal` 的父目录（及其子树）内的代码 import**。

举例，假设模块是 `example.com/proj`：

```
proj/
├── internal/
│   └── db/            import 路径：example.com/proj/internal/db
├── pkg/
│   └── util/
└── cmd/
    └── app/
```

| 谁想 import `internal/db` | 允许吗 | 原因 |
|---|---|---|
| `example.com/proj/cmd/app` | ✅ | 在 `proj` 子树内 |
| `example.com/proj/pkg/util` | ✅ | 在 `proj` 子树内 |
| `example.com/other` | ❌ **编译报错** | 不在 `proj` 子树内 |

**这是编译器级别的隔离，不是靠约定。**

编译错误长这样：

```
use of internal package example.com/proj/internal/db not allowed
```

### 4.3.2 为什么这个设计很妙

对比一下其他语言：

| 语言 | 「私有包」怎么实现 |
|---|---|
| Java | `package-private` 只在包内可见，但**跨 jar 仍可通过反射/同名包绕过**，且没有「模块内私有」这个粒度 |
| Python | 靠 `_` 前缀约定，**完全没有强制力** |
| Node.js | 靠 `exports` 字段，比较新，且是运行时检查 |
| **Go** | **编译器强制，零成本** |

`internal/` 提供了第三个粒度：

```
公开（pkg/）  →  模块内可见（internal/）  →  包内可见（小写标识符）
```

这三层刚好对应工程上真实需要的三种边界。

### 4.3.3 落到本项目

```
github.com/openimsdk/open-im-server/v3/
├── internal/     ← 业务实现，外部项目 import 会编译失败
│   ├── api/
│   ├── msggateway/
│   ├── msgtransfer/
│   ├── push/
│   ├── rpc/
│   └── tools/
└── pkg/          ← 公共库，理论上可被外部 import
    ├── common/
    ├── localcache/
    ├── rpccache/
    └── ...
```

> 📌 **这解释了 03 篇的一条硬边界**：为什么 OpenIM 把业务放 `internal`、把存储和工具放 `pkg`？
> 因为 `pkg/common/storage` 是「**通用的存储能力**」（可以被别的项目复用），而 `internal/rpc/msg` 是「**这个产品的业务**」（不该被复用）。
>
> **判断标准**：「这段代码换一个项目还能用吗？」能 → `pkg`；不能 → `internal`。

> ⚠️ **注意**：`pkg` 只是约定，不是强制。Go 编译器不会阻止别人 import 你的 `pkg` 目录。真要做到「绝对不可外部引用」，只能靠 `internal`。

## 4.4 导出规则：大写公开，小写私有

Go 没有 `public`/`private` 关键字，靠**首字母大小写**：

| 写法 | 可见性 |
|---|---|
| `func SendMsg()` | 包外可见（exported） |
| `func sendMsg()` | 仅包内可见 |
| `type Client struct` / `client` | 同上 |
| `var ErrNotFound` / `errNotFound` | 同上 |

**这条规则不只是语法，它决定了你的 API 面积。**

好的设计原则：**默认小写，只在确实需要对外时才大写**。因为一旦导出，就有人依赖它，你就不敢改了（这叫「公开 API 是负债」）。

> 🟡 **难点：结构体字段的导出**
> ```go
> type Client struct {
>     UserID string   // 包外能读写
>     token  string   // 包外完全看不到（连反射都要特殊处理）
> }
> ```
> 这就带来一个问题：包外怎么构造带私有字段的对象？答案是**构造函数**：
> ```go
> func NewClient(userID, token string) *Client
> ```
> 这是 Go 的惯用法（没有构造函数语法，就用 `NewXxx` 函数）。OpenIM 里大量 `NewXXX()` 都是这个作用。

## 4.5 依赖倒置：接口定义在「使用者」侧

### 4.5.1 常规依赖 vs 依赖倒置

**常规依赖**（业务直接依赖实现）：

```
rpc/msg/send.go  ──import──→  storage/database/mgo   （具体的 Mongo 实现）
```

问题：想给 `send.go` 写单测，必须起一个 Mongo。想换存储，要改 `send.go`。

**依赖倒置**（业务依赖接口，实现依赖接口）：

```
rpc/msg/send.go  ──import──→  storage/controller   （接口）
                                      ↑
                              mgo 实现它
```

现在 `send.go` 只知道「有个东西能存消息」，不知道是 Mongo 还是 MySQL。

### 4.5.2 Go 的接口是「隐式实现」的（关键差异）

Java 要显式 `implements`，Go 不用——**只要方法签名对了，就自动实现了接口**。

```go
// 定义方（使用者）
type MsgRepository interface {
    Create(ctx context.Context, msg *Msg) error
}

// 实现方（谁都不需要声明 implements）
type mongoMsgRepo struct{}
func (r *mongoMsgRepo) Create(ctx context.Context, msg *Msg) error { ... }
// 编译器自动认为 mongoMsgRepo 实现了 MsgRepository
```

**这个设计带来一个重要后果：接口应该定义在「使用方」包里，而不是「实现方」包里。**

为什么？因为「实现方」不该知道自己被谁需要。如果接口定义在实现方，那接口就是为了实现方设计的，容易长出一堆用不上的方法。

> 📌 本项目其实**部分违反**了这条（Go 项目普遍如此）：接口定义在 `database/msg.go` 里，实现在 `database/mgo/msg.go`。这是「先有实现，后抽接口」的常见形态，不算错，但不如「接口在使用方定义」纯粹。面试时如果被问到设计能力，这点可以主动讲，显示你懂原理而不是只懂抄。

### 4.5.3 为什么需要「门面层（Facade）」

一个业务操作往往要碰多个组件：

```go
// 理想中业务代码长这样
func (m *msgServer) SendMsg(...) {
    m.mongo.Create(msg)
    m.redis.Set(msg)
    m.kafka.Send(msg)
}
```

问题：

- 事务边界在业务层，每个业务方法都要考虑「先写哪个、失败怎么补偿」
- 换存储要改所有业务方法
- 单测要 mock 三个组件

**门面层把「一次完整的数据操作」封装成一个方法**：

```go
// controller 层
func (db *commonMsgDatabase) MsgToMQ(ctx, key, msg) error {
    data, _ := proto.Marshal(msg)
    return db.producer.SendMessage(ctx, key, data)   // 内部细节被藏起来
}

// 业务层只调一个方法
func (m *msgServer) SendMsg(...) {
    m.MsgDatabase.MsgToMQ(ctx, key, msg)
}
```

这就是 `pkg/common/storage/controller/` 存在的理由（第二部分 4.4.2 详讲）。

## 4.6 分层命名的行业约定

不同框架的命名不一样，但语义基本一致：

| 本项目的叫法 | 常见叫法 | 职责 |
|---|---|---|
| `model` | entity / domain model / PO | 数据结构定义（Mongo 文档结构、DB 表结构） |
| `database` | repository / dao / mapper | 存储访问**接口** |
| `database/mgo` | repository impl / dao impl | 存储访问**实现** |
| `cache` | cache repository | 缓存访问 |
| `controller` | service / facade / biz | **编排**多个存储组件，对外暴露一个方法 |
| `internal/api/*.go` | handler / controller | 协议层：解析请求、调 service、返回响应 |
| `internal/rpc/*/xxx.go` | service impl | gRPC 服务实现，真正的业务逻辑 |

> ⚠️ **易错：`controller` 这个词在不同项目里意思完全相反。**
> 在 Spring MVC / Gin 教程里，`controller` 是**HTTP 层**（接收请求）。
> 在 OpenIM 里，`internal/api/` 才是 HTTP 层，而 `pkg/common/storage/controller/` 是**存储编排层**。
>
> **看代码时不要靠目录名猜，要看它 import 了什么。** 这是读陌生项目的通用心法。

## 4.7 怎么读一个陌生的 Go 项目（方法论，本节最值钱）

拿到一个 4 万行的项目，从哪开始？**不要从第一个文件开始读**——那是浪费时间。

### 4.7.1 五步定位法

```
第 1 步：读 go.mod（1 分钟）
   → 知道模块名、Go 版本、关键依赖（有这个项目的技术栈全貌）

第 2 步：看目录树（3 分钟）
   → ls 顶层 + ls internal + ls pkg，建立空间感

第 3 步：找入口（5 分钟）
   → 读 cmd/*/main.go，看它装配了哪些组件
   → 这一步决定「这个项目有哪些进程」

第 4 步：找「主动脉」（30 分钟）
   → 找最核心的一条链路（本例：发消息），顺着它走一遍
   → 不要横向铺开读所有模块，要纵向打穿一条

第 5 步：按需展开（长期）
   → 遇到具体问题再回到对应目录
```

### 4.7.2 「顺藤摸瓜」四连问

读任何一段代码，反复问这四个问题：

| 问题 | 手段 |
|---|---|
| 谁调我？（caller） | 搜函数名 / 用 IDE 的 Find Usages |
| 我调谁？（callee） | 读函数体里的调用 |
| 我的数据从哪来？ | 看参数和上游 |
| 我的结果去哪了？ | 看返回值和下游 |

**这四个问题串起来，就是一条完整的数据流。** 走通一条，胜过读十个孤立文件。

### 4.7.3 三个反模式（新手最常犯）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| **从第一个目录开始顺序读** | `pkg/` 有 24,245 行样板代码，读完就放弃了 | 从入口和核心链路开始 |
| **试图读懂每一行** | 大量代码是错误处理、日志、类型转换，不影响理解主线 | 第一遍跳过错误处理，只看 happy path |
| **只看不跑** | 静态阅读会漏掉运行时行为（配置注入、反射、goroutine） | 至少跑通一条链路，加日志验证 |

> 🔴 **一句话**：**读代码的目标不是「读完」，而是「能回答具体问题」。** 有目标地读，效率是盲目阅读的 10 倍。

### 4.7.4 代码量 ≠ 重要性

这是本项目的实测数据（第二部分 4.7）：

| 模块 | 行数 | 重要性 |
|---|---|---|
| `pkg/common/storage` | ~9,000 行 | ⭐⭐⭐（数据是核心） |
| `internal/msgtransfer` | ~1,200 行 | ⭐⭐⭐⭐⭐（**消息可靠性设计的全部核心**） |

`msgtransfer` 只占 3% 的代码量，但它决定了「消息会不会丢」。**为什么？**

因为**代码量和「决策密度」不成正比**：

- 存储层 9,000 行里，8,000 行是「一个集合一个文件，5 个方法」的样板
- msgtransfer 1,200 行里，每一行都在做一个可靠性决策（先 Mark 还是先 Commit、批多大、怎么分片）

> 📌 **这是面试可以讲的洞察**：「我读这个项目最大的收获是学会判断代码的『决策密度』。msgtransfer 只有 1200 行，但它是整个消息可靠性设计的核心；存储层 9000 行，大部分是样板。这让我明白读代码要按『这段代码做了多少决策』分配精力，而不是按行数。」

## 4.1 顶层结构

```
open-im-server-main/
├── cmd/          7 个目录，13 文件，655 行      → 进程入口，只做装配
├── internal/     100 文件，18,747 行            → 业务实现（读码主战场）
├── pkg/          271 文件，24,245 行            → 公共库（按需读）
├── tools/        12 文件，1,153 行              → 运维小工具
├── config/       24 个 yml + 监控配置            → 全部服务的配置
├── components/   容器数据（Mongo/Kafka/etcd）   → 活数据，不能删
├── docs/         9 份中文文档                    → 工程规范
├── deployments/  部署相关                        → K8s/镜像
├── start-config.yml                             → mage start 的进程清单
└── docker-compose.yml                           → 中间件编排
```

**模块路径**：`github.com/openimsdk/open-im-server/v3`（`go.mod` 第 1 行），Go 1.25.0。

**读码顺序建议**（对应 4.7.1 的五步法）：

```
cmd/main.go → internal/msggateway → internal/rpc/msg → internal/msgtransfer → pkg/common/storage
```

这条路径就是消息的流动方向。**先纵向打穿一条，再横向铺开。**

## 4.2 `cmd/`：七个入口，只做装配

| 路径 | 作用 | 代码量 |
|---|---|---|
| `cmd/main.go` | **standalone 一体模式**，反射注入配置 + 拉起 12 个服务 | **510 行** |
| `cmd/openim-api/` | HTTP API 进程 | ~10 行 |
| `cmd/openim-msggateway/` | WS 网关进程 | ~10 行 |
| `cmd/openim-msgtransfer/` | 消息中转进程 | ~10 行 |
| `cmd/openim-push/` | 推送进程 | ~10 行 |
| `cmd/openim-rpc/` | 7 个 RPC 服务的独立入口（每个一个 main） | ~85 行 |
| `cmd/openim-crontask/` | 定时任务进程 | ~10 行 |
| **合计** | | **13 文件 / 655 行** |

> 📌 510 行占 `cmd/` 的 78%。**剩下的 12 个入口加起来只有约 145 行**——平均一个入口 12 行。这个分布本身就是证据：入口层「几乎不写代码」是设计出来的，不是偶然。

📌 **重点**（对应 4.1.2 的原则）：除了 `main.go`，其他入口都只有不到 10 行——`cmd.NewXxxCmd().Exec()`。真正的装配在 `pkg/common/cmd/`。

```go
// cmd/openim-api/main.go 的全部内容
package main

import (
	"github.com/openimsdk/open-im-server/v3/pkg/common/cmd"
	"github.com/openimsdk/tools/system/program"
	_ "net/http/pprof"
)

func main() {
	if err := cmd.NewApiCmd().Exec(); err != nil {
		program.ExitWithError(err)
	}
}
```

**为什么这么薄？** 因为 `main` 包不能被 import，所以「能复用的装配逻辑」必须挪出去。`pkg/common/cmd/` 里是 Cobra 命令 + 配置加载，这样 standalone 和微服务可以共用。

⚠️ **易错**：`cmd/openim-rpc/` 下不是一个 main，是 7 个（auth/user/group/msg/...）。第一次读很容易以为只有 1 个。

> 这正是 4.7 方法论的应用：**别靠目录名判断，靠代码事实判断。**

|---|---|
| auth | user |

| relation | user, msg |

### 4.4.2 `pkg/common/storage/` 展开（第二重要）

```
storage/
├── model/       数据模型（Mongo 文档结构、Seq、版本日志）  ← 先读
├── database/    数据库访问接口 + mgo 实现
├── cache/       缓存接口 + redis 实现
├── controller/  【门面】组合 database + cache + MQ 的对外接口  ← 最常被业务调用
├── kafka/       点击量统计的 Kafka 消费（独立于通用 MQ）
└── versionctx/  版本上下文
```

📌 **重点：`controller` 是门面层**（对应 4.5.3）。业务代码（如 `rpc/msg/send.go`）只依赖 `controller.CommonMsgDatabase` 接口，不直接碰 Mongo/Redis。这是「接口隔离 + 可测试」的经典做法。

三层的关系：

```
rpc/msg/send.go
    ↓ 只依赖接口
controller.CommonMsgDatabase（接口，msg.go:38-90）
    ↓ 实现
commonMsgDatabase（结构体，msg.go:102-109）
    ├─ database.Msg       （Mongo 文档操作）
    ├─ cache.MsgCache     （Redis 消息缓存）
    ├─ cache.SeqUser      （用户已读 seq）
    ├─ cache.SeqConversation（会话 seq 分配）
    └─ mq.Producer        （投 Kafka）
```

🟡 **难点：为什么要有 controller 这一层？**
因为一个业务操作往往要「写 Redis + 写 Mongo + 投 MQ」，如果业务层直接调三个组件：

- 事务边界散落在每个业务方法里
- 错误处理重复 N 遍
- 换存储要改所有业务方法
- 单测要 mock 三个组件

controller 把「一次完整的数据操作」封装成一个方法，业务层只看到 `MsgToMQ` / `GetMsgBySeq` 这样的语义化接口。

> ⚠️ **这是「门面模式（Facade）」的典型应用**。注意它和「Service 层」的区别：Service 层含业务规则（能不能发、谁能发），Facade 只做技术编排（先写哪、失败了怎么办）。**业务规则在 `internal/rpc`，技术编排在 `controller`。** 这条边界守住了，代码就不会烂。

## 4.5 依赖方向（谁能 import 谁）

```
         cmd/
          ↓
      internal/  ──────→ pkg/
          ↓                ↓
    （不反向依赖）      pkg/common/storage
                            ↓
                      model / database / cache
```

**规则**：

| 规则 | 说明 |
|---|---|
| ✅ `internal` 可以 import `pkg` | 单向 |
| ⚠️ `pkg` **原则上不** import `internal` | **约定，不是编译器强制**！见下方重要更正 |
| ✅ `rpc/*` 可以 import `pkg/rpcli`、`pkg/rpccache` | 客户端与缓存 |
| ❌ `rpc/msg` 不能 import `rpc/group` | 服务间只能走 gRPC，不能直接调函数 |
| ✅ `pkg/common/storage/controller` 可以 import `database` + `cache` | 门面 |
| ❌ `database` 不能 import `controller` | 反向 |

> 🔴 **重要更正（我在本仓库实测发现的，很多资料写错）**：
>
> 常说「`pkg` 不能 import `internal`，这是编译器强制的」——**这句话是错的，至少在本仓库不成立**。
>
> 为什么？因为 4.3 讲的规则是「`internal` 只能被**其父目录子树**内的代码 import」。`pkg/` 和 `internal/` 都在模块根目录下，**`pkg` 完全在允许范围内**。编译器不会拦。
>
> 真正被编译器拦住的是**模块外部**（比如 `example.com/other`）import 这个项目的 `internal/xxx`。
>
> **本仓库的实际事实**（实测）：`pkg/` 下**确实有 12 个文件** import 了 `internal/`，全部在 `pkg/common/cmd/`：
>
> ```bash
> grep -rln "open-im-server/v3/internal" pkg/ --include="*.go"
> # pkg/common/cmd/api.go
> # pkg/common/cmd/auth.go
> # pkg/common/cmd/conversation.go
> # pkg/common/cmd/cron_task.go
> # pkg/common/cmd/friend.go
> # pkg/common/cmd/group.go
> # pkg/common/cmd/msg.go
> # pkg/common/cmd/msg_gateway.go
> # pkg/common/cmd/msg_transfer.go
> # pkg/common/cmd/push.go
> # pkg/common/cmd/third.go
> # pkg/common/cmd/user.go
> ```
>
> **这 12 个文件是「装配层」**：它们定义 Cobra 命令，把「配置 + 服务实现」组装起来。装配层**必须**知道具体服务在哪，否则没法装配。
>
> 🟡 **这是一个非常典型的例外，且是合理的**：
> - 装配层（composition root）天然依赖一切，这是依赖注入的入口
> - 如果连装配层都不能 import 业务，那 `cmd/openim-api/main.go` 里就没法写 `api.Start` 了
>
> **所以正确的表述是**：`pkg` 里**除装配层 `pkg/common/cmd/` 以外**，不能 import `internal`。这是一条**架构约定**，靠 code review 守，不靠编译器。
>
> 📌 这也是一条方法论：**看到「某规则是编译器强制的」这种说法，一定要去试一下。** 我刚才就是靠 `grep` 才发现这条流传很广的说法在本仓库不成立。

> 🔴 **注意：这一条不是编译器强制的**（很多资料写错了，详见下方 4.5 的更正）。`pkg` 里除装配层 `pkg/common/cmd/` 外不 import `internal`，靠的是架构约定。

🧪 **验证依赖方向**：

```bash

# 2. 排除装配层后，应该为空

## 4.6 找代码方法论（本篇最实用）

### 场景 1：想找某个 HTTP 接口的实现

```
1. 打开 internal/api/router.go
2. 搜索路由路径字符串（如 "/user_register"）
3. 看它绑定的 handler（如 u.UserRegister）
4. 如果 handler 是 a2r.Call 一行 → 直接跳到 RPC 层同名方法
   （如 internal/rpc/user/user.go 的 UserRegister）
```

### 场景 2：想找某个 gRPC 方法的实现

```
1. 确认服务名（proto 里的 service，如 openim.msg.msg）
2. 去 internal/rpc/<服务>/ 找同名函数
3. 如果找不到 → 可能在 sync.go / group_member.go 等拆分文件里
```

### 场景 3：想找某个数据表/集合的操作

```
1. 表名 → pkg/common/storage/model/<xxx>.go（结构体定义）
2. 操作 → pkg/common/storage/database/<xxx>.go（接口）
3. 实现 → pkg/common/storage/database/mgo/<xxx>.go
4. 门面 → pkg/common/storage/controller/<xxx>.go（业务实际调用的）
```

**例：消息表**

```
model/msg.go            → MsgDocModel（docID + 100 条数组）
database/msg.go         → Msg 接口（Create/UpdateMsg/GetMsgBySeqIndexIn1Doc）
database/mgo/msg.go     → 实现
controller/msg.go       → CommonMsgDatabase（业务调用入口）
```

### 场景 4：想找某个 Redis key 的含义

```
1. pkg/common/storage/cache/cachekey/  ← 所有 key 的前缀定义都在这
2. pkg/common/storage/cache/redis/<xxx>.go  ← 具体读写
```

### 场景 5：想找某个配置项

```
1. 先看 config/<服务>.yml（实际值）
2. 再看 pkg/common/config/config.go（结构体 + 默认值 + tag）
3. 用字段名全局搜，看谁在用
```

### 场景 6：想知道「这个函数被谁调用」

用 Grep 工具搜函数名。⚠️ 注意同名方法可能有多个 receiver，要看清是 `(s *msgServer)` 还是 `(db *commonMsgDatabase)`。

### 场景 7：想知道某个包能不能外部引用

看它在 `internal/` 还是 `pkg/`（4.3）。**`internal/` 下的，外部项目 import 必编译失败。**

## 4.7 代码规模分布（决定读码投入）

| 模块 | 行数 | 占 internal+pkg | 建议投入 |
|---|---|---|---|
| `pkg/common/storage` | ~9,000 | 21% | 30% 时间（数据是核心） |
| `internal/rpc/*` | ~9,000 | 21% | 30% 时间（业务逻辑） |
| `internal/msggateway` | ~4,500 | 10% | 15% 时间（并发设计） |
| `internal/msgtransfer` | ~1,200 | 3% | 10% 时间（可靠性核心） |
| `internal/api` | ~3,000 | 7% | 5% 时间（薄层，看懂模式即可） |
| `pkg/rpccache` + `localcache` | ~2,100 | 5% | 5% 时间 |
| 其他 | ~14,000 | 33% | 5% 时间（用到再看） |

📌 **重点**（对应 4.7.4）：`msgtransfer` 只有 1,200 行（3%），但承载了消息可靠性设计的全部核心。**代码量和重要性不成正比**——这也是面试可以讲的洞察。

## 3.1 🧪 实验一：验证 `internal` 是编译器强制的

在项目外建一个临时模块，试着 import 本项目的 `internal` 包：

```bash
mkdir -p /tmp/probe && cd /tmp/probe
cat > go.mod <<'EOF'
module example.com/probe
go 1.25.0
require github.com/openimsdk/open-im-server/v3 v3.0.0
replace github.com/openimsdk/open-im-server/v3 => /d/IM-Server/open-im-server-main
EOF
cat > main.go <<'EOF'
package main
import _ "github.com/openimsdk/open-im-server/v3/internal/api"
func main() {}
EOF
go build ./... 2>&1 | head -3
```

期望看到：`use of internal package ... not allowed`。

再把它改成 `pkg/util`，就能编译通过。**这个实验一次性把 4.3 的理论变成肌肉记忆。**

## 3.2 🧪 实验二：验证「API 层是薄翻译层」

```bash
cd /d/IM-Server/open-im-server-main

# 每个 api 文件里 a2r.Call 出现的次数
grep -c "a2r.Call" internal/api/*.go

# 对照文件总行数
wc -l internal/api/*.go
```

如果某个文件里 `a2r.Call` 次数接近它的 handler 数量，说明它几乎没有业务逻辑。**这就是「薄接入层」的量化证据。**

## 3.3 🧪 实验三：顺藤摸瓜走一条链路

按 4.7.2 的四连问，走通「用户注册」这一条：

```bash
# 1. 找路由
grep -n "user_register" internal/api/router.go

# 2. 找 handler
grep -n "func.*UserRegister" internal/api/user.go

# 3. 找 RPC 实现
grep -rn "func.*UserRegister" internal/rpc/user/

# 4. 找存储
grep -rn "UserRegister\|CreateUser" pkg/common/storage/controller/user.go
```

走完这四步，你就把「HTTP → gRPC → 存储」打穿了一次。**后面所有接口都是同一个套路。**

## 3.6 面试话术

> 「读这个项目我用的是『先打穿一条，再横向铺开』的方法。先读 `cmd/main.go` 看它装配了哪些组件，然后顺着发消息这条链路走：网关解码 → msg RPC 校验投 Kafka → msgtransfer 消费分配 seq → 落 Mongo + 推送。走通一条之后，其他接口都是同一个套路。
>
> 项目布局上它用的是社区事实标准：`cmd` 放入口、`internal` 放业务、`pkg` 放通用库。这里有个 Go 特有的点——`internal` 是**编译器强制**的私有，外部项目 import 会直接编译报错，不是靠约定。所以它把『这个产品独有的业务』放 `internal`，把『换个项目还能用的存储和工具』放 `pkg`。
>
> 存储层是 model / database / cache / controller 四层，其中 controller 是门面，把『写 Redis + 写 Mongo + 投 MQ』这种一次完整的数据操作封装成一个方法，业务层只依赖接口。
>
> 我最大的收获是学会判断代码的『决策密度』：`msgtransfer` 只有 1200 行，但它是整个消息可靠性设计的核心；存储层 9000 行，大部分是『一个集合一个文件五个方法』的样板。读代码要按『这段代码做了多少决策』分配精力，而不是按行数。」
