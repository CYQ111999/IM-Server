# 第一部分 · 纯理论

## 1.1 群成员是 M:N 关系，存哪儿

一个群有 N 个成员，一个人有 M 个群。这是典型的**多对多**关系。

### 方案一：群文档里存成员数组

```json
{
  "group_id": "123",
  "group_name": "技术群",
  "members": [
    {"user_id": "a", "role": 1},
    {"user_id": "b", "role": 3},
    ...  // 500 人
  ]
}
```

优点：查「群的所有成员」是一次查询，快。
缺点，而且是致命的：

**（1）文档大小限制**。MongoDB 单个文档上限 16MB。每条成员记录算 200 字节，16MB 能存 8 万人。听起来够用，但：
- 每次读群信息（比如判断群是否解散）都会把整个 members 数组拉回来，浪费带宽
- 更新单个成员的禁言状态要重写整个数组

**（2）无法按成员查询**。「我加入了哪些群」需要遍历所有群文档，扫 members 数组。O(群总数)。

**（3）并发更新冲突**。两个人同时改不同成员的信息，都会重写整个数组，后写的覆盖前写的。

### 方案二：独立的成员表（OpenIM 的选择）

```
group_member 集合：
{ group_id: "123", user_id: "a", role_level: 1, join_time: ..., mute_end_time: ... }
{ group_id: "123", user_id: "b", role_level: 3, ... }
{ group_id: "456", user_id: "a", role_level: 1, ... }
```

一条记录 = 一个「用户在某群里的身份」。

索引：
- `(group_id, user_id)` 唯一索引 → 查单个成员、防重复
- `group_id` 普通索引 → 查群的所有成员
- `user_id` 普通索引 → 查某人加入的所有群

优点：
- 单条记录小，可以精确更新某个字段
- 两个方向的查询都有索引
- 并发更新不同成员不冲突

缺点：
- 「群有多少人」需要 `count`，不是读一个字段
- 「拉群成员列表」+「拉这些人的昵称头像」是两次查询（OpenIM 用 `PopulateGroupMember` 解决）

> 📌 记忆点：**M:N 关系用中间表，不要塞进数组。** 数组只适合「数量有上限、总是整体读写」的场景（比如一条消息的 @ 列表）。

`pkg/common/storage/model/group_member.go` 的 `GroupMember` 结构：

```go
type GroupMember struct {
	GroupID        string    `bson:"group_id"`
	UserID         string    `bson:"user_id"`
	Nickname       string    `bson:"nickname"`        // 群昵称（可以和个人昵称不同）
	FaceURL        string    `bson:"face_url"`
	RoleLevel      int32     `bson:"role_level"`      // 1=owner 2=admin 3=ordinary
	JoinTime       time.Time `bson:"join_time"`
	JoinSource     int32     `bson:"join_source"`     // 怎么进来的
	InviterUserID  string    `bson:"inviter_user_id"` // 谁邀请的
	OperatorUserID string    `bson:"operator_user_id"`// 谁操作的
	MuteEndTime    time.Time `bson:"mute_end_time"`   // 禁言到什么时候
	Ex             string    `bson:"ex"`
}
```

三个字段值得注意：

**`Nickname` 是冗余的**。它和 `user.Nickname` 可能不同（群昵称）。为什么要存一份而不是每次查用户表？

因为「群成员列表」是高频查询，如果每个人的昵称都要去用户表查，就是 N+1 查询（500 人的群 = 501 次查询）。存一份冗余，读的时候直接用。代价是用户改了昵称，要同步更新所有群的成员记录——这就是 `PopulateGroupMember` 的用途（发现空了就补），以及 `NotificationUserInfoUpdate` 的存在（用户资料变更时通知所有群）。

**`MuteEndTime` 用「结束时间」而不是「剩余秒数」**。因为剩余秒数会随时间变化，存下来就过期了。存结束时间，判断禁言就是 `MuteEndTime.After(time.Now())`。**这是「存绝对时间而不是相对时间」的通用原则**。

**`JoinSource` 记录了入群方式**（邀请/扫码/搜索/导入）。用于统计和风控。

## 1.2 三级角色：一个极简的 RBAC

RBAC（Role-Based Access Control）是权限模型的通称。完整的 RBAC 有「角色、权限、角色-权限映射、用户-角色映射」四张表。

OpenIM 用了一个**极简版**：角色是写死的三级，权限是写死在代码里的 `switch`。

```
RoleLevel: 1 = GroupOwner   群主
           2 = GroupAdmin   管理员
           3 = GroupOrdinaryUsers  普通成员
```

没有「权限表」，权限判断全在代码里：

```go
switch opMember.RoleLevel {
case constant.GroupOwner:
	// 什么都能干
case constant.GroupAdmin:
	// 不能动群主和其他管理员
case constant.GroupOrdinaryUsers:
	return nil, errs.ErrNoPermission.WrapMsg("opUserID no permission")
}
```

**为什么不设计成可配置的权限表？**

因为 IM 的群权限是**行业标准化的**——几乎所有 IM 产品都是「群主 > 管理员 > 成员」，权限边界也大同小异。做成可配置会带来：
- 配置复杂度（每个群一套权限配置）
- 前端渲染复杂度（按钮的显示取决于权限矩阵）
- 一致性问题（同一个操作在不同群的行为不同）

代价是**灵活性差**：如果产品需要「自定义角色」（比如「只读成员」「审计员」），得改代码。

> 📌 **这是一个很好的架构取舍案例**：不是所有东西都值得做成可配置。**稳定的领域模型应该硬编码，变化频繁的部分才配置化。** 群角色属于前者，`needVerification`（入群验证策略）属于后者。

### 权限矩阵

把代码里的判断汇总成表（这是读源码时最该做的事）：

| 操作 | 群主 | 管理员 | 普通成员 | 系统管理员 |
|---|---|---|---|---|
| 修改群信息 | ✅ | ✅ | ❌ | ✅ |
| 修改群公告 | ✅ | ✅ | ❌ | ✅ |
| 邀请成员 | ✅ | ✅ | ✅（视验证策略） | ✅ |
| 踢人 | ✅ | ✅（不能踢群主/管理员） | ❌ | ✅ |
| 设置管理员 | ✅ | ❌ | ❌ | ✅ |
| 禁言成员 | ✅ | ✅（不能禁言群主/管理员） | ❌ | ✅ |
| 群禁言（全员） | ✅ | ✅ | ❌ | ✅ |
| 转让群主 | ✅（只能转给自己名下的） | ❌ | ❌ | ✅ |
| 解散群 | ✅ | ❌ | ❌ | ✅ |
| 退群 | ❌（群主不能退） | ✅ | ✅ | ✅ |

注意「群主不能退群」（`group.go:1007`）：

```go
if member.RoleLevel == constant.GroupOwner {
	return nil, errs.ErrNoPermission.WrapMsg("group owner can't quit")
}
```

因为群主一退，群就没有主了。要么先转让，要么解散。这是**业务不变量的代码体现**。

## 1.3 禁言的两层设计

「禁言」在 IM 里有两种完全不同的粒度：

| | 群禁言 | 成员禁言 |
|---|---|---|
| 范围 | 整个群（所有人不能发言） | 某个成员 |
| 存在哪 | `group.status = GroupStatusMuted` | `group_member.mute_end_time` |
| 谁能设 | 群主/管理员 | 群主/管理员（有层级限制） |
| 解除 | 手动 `CancelMuteGroup` | 到期自动解除，或手动 |

**为什么必须分开存？**

因为它们的语义不同：

- **群禁言**是「群的状态」。整个群进入静默，只有管理员能发言（用于紧急情况，比如群里在吵架）。它改变的是**群的属性**。
- **成员禁言**是「成员的状态」。某个人被禁言，其他人正常说话。它改变的是**成员关系的属性**。

如果只用一套机制表达，会遇到问题：
- 用群状态表达成员禁言 → 无法表达「500 人里禁言 3 个人」
- 用成员字段表达群禁言 → 要给 500 人逐个设禁言时间，且新增成员会漏掉

### 实现细节

**群禁言**（`group.go:1563-1583`）：

```go
func (g *groupServer) MuteGroup(ctx context.Context, req *pbgroup.MuteGroupReq) (*pbgroup.MuteGroupResp, error) {
	if err := g.CheckGroupAdmin(ctx, req.GroupID); err != nil {
		return nil, err
	}
	if err := g.db.UpdateGroup(ctx, req.GroupID, UpdateGroupStatusMap(constant.GroupStatusMuted)); err != nil {
		return nil, err
	}
	g.notification.GroupMutedNotification(ctx, req.GroupID)
	return &pbgroup.MuteGroupResp{}, nil
}
```

就是一个状态字段的更新。**没有时间**——群禁言是「一直禁到手动解除」，不自动过期。

**成员禁言**（`group.go:1489-1521`）：

```go
func (g *groupServer) MuteGroupMember(ctx context.Context, req *pbgroup.MuteGroupMemberReq) (*pbgroup.MuteGroupMemberResp, error) {
	member, err := g.db.TakeGroupMember(ctx, req.GroupID, req.UserID)
	// ...
	if !authverify.IsAdmin(ctx) {
		opMember, err := g.db.TakeGroupMember(ctx, req.GroupID, mcontext.GetOpUserID(ctx))
		switch member.RoleLevel {
		case constant.GroupOwner:
			return nil, errs.ErrNoPermission.WrapMsg("set group owner mute")
		case constant.GroupAdmin:
			if opMember.RoleLevel != constant.GroupOwner {          // ← 只有群主能禁言管理员
				return nil, errs.ErrNoPermission.WrapMsg("set group admin mute")
			}
		case constant.GroupOrdinaryUsers:
			if !(opMember.RoleLevel == constant.GroupAdmin || opMember.RoleLevel == constant.GroupOwner) {
				return nil, errs.ErrNoPermission.WrapMsg("set group ordinary users mute")
			}
		}
	}
	data := UpdateGroupMemberMutedTimeMap(time.Now().Add(time.Second * time.Duration(req.MutedSeconds)))
	if err := g.db.UpdateGroupMember(ctx, member.GroupID, member.UserID, data); err != nil {
		return nil, err
	}
	g.notification.GroupMemberMutedNotification(ctx, req.GroupID, req.UserID, req.MutedSeconds)
}
```

**权限矩阵在这里是显式的三级判断**：

| 操作者 → 目标 | 群主 | 管理员 | 普通成员 |
|---|---|---|---|
| 群主 | ❌（不能禁言自己） | ❌ | ❌ |
| 管理员 | ✅（只有群主能） | ❌ | ❌ |
| 普通成员 | ✅ | ✅（管理员能禁言） | ❌ |

注意「不能禁言群主」是**无条件的**——连系统管理员都要绕过这一段（`if !authverify.IsAdmin(ctx)` 之外）。这意味着**系统管理员可以禁言群主**（因为跳过了整个检查块）。

**用 `MutedSeconds`（时长）而不是 `MuteEndTime`（结束时间）入参**，是个 API 设计选择：
- 传时长：客户端不用管时间同步，服务端算 `now + duration`
- 传结束时间：客户端时钟不准会导致错误

OpenIM 选了前者。但注意 `TransferGroupOwner` 里有个反向操作（`group.go:1291-1297`）：

```go
if newOwner.MuteEndTime.After(time.Now()) {
	if _, err := g.CancelMuteGroupMember(ctx, &pbgroup.CancelMuteGroupMemberReq{
		GroupID: group.GroupID,
		UserID:  req.NewOwnerUserID}); err != nil {
		return nil, err
	}
}
```

**转让群主前先解除新群主的禁言**。如果不做，会出现「群主被禁言」的荒谬状态——一个不能说话的群主。

这是个**业务不变量**：群主不该被禁言。代码在转让这个「入口」处保证它，而不是在发消息时检查「如果是群主就忽略禁言」。前者的成本更低（一次检查 vs 每条消息都检查）。

## 1.4 入群的四条路径与四种验证策略

入群方式（`JoinSource`）：

| 值 | 含义 | 入口函数 |
|---|---|---|
| 邀请 | 管理员/成员拉进来 | `InviteUserToGroup` |
| 申请 | 自己申请，等审批 | `JoinGroup` |
| 直接进 | 谁都行，无需审批 | `JoinGroup`（当 `needVerification = Directly`） |
| 导入 | 管理端批量导入 | `CreateGroup` / CMS 接口 |

验证策略（`group.need_verification`）：

| 值 | 常量 | 语义 |
|---|---|---|
| 0 | `Directly` | 直接进，无需审批 |
| 1 | `AllNeedVerification` | 所有人都需要审批（包括管理员邀请） |
| 2 | `InviteNeedVerification` | 只有被邀请的需要审批 |
| 3 | `NotNeedVerification` | 不需要（可能和 0 等价，📌 待验证） |

### 邀请路径的分叉

`group.go:397-425` 是关键：

```go
if group.NeedVerification == constant.AllNeedVerification {
	if !authverify.IsAdmin(ctx) {
		if !(groupMember.RoleLevel == constant.GroupOwner || groupMember.RoleLevel == constant.GroupAdmin) {
			// 普通成员邀请人 → 转成"申请"，需要审批
			var requests []*model.GroupRequest
			for _, userID := range req.InvitedUserIDs {
				requests = append(requests, &model.GroupRequest{
					UserID:        userID,
					GroupID:       req.GroupID,
					JoinSource:    constant.JoinByInvitation,
					InviterUserID: opUserID,
					ReqTime:       time.Now(),
				})
			}
			if err := g.db.CreateGroupRequest(ctx, requests); err != nil {
				return nil, err
			}
			for _, request := range requests {
				g.notification.JoinGroupApplicationNotification(ctx, &pbgroup.JoinGroupReq{...}, request)
			}
			return &pbgroup.InviteUserToGroupResp{}, nil   // ← 注意：直接返回，没有真的拉人
		}
	}
}
```

**逻辑是：在「所有人需要审批」的群里，普通成员邀请人 = 发起申请，不是直接拉人。**

三个判断的优先级：
1. `NeedVerification == AllNeedVerification`（群策略）
2. `!IsAdmin`（不是系统管理员）
3. `RoleLevel 不是 owner/admin`（不是群主/管理员）

三者都满足才转成申请。所以：
- 系统管理员邀请 → 直接进（跳过 2）
- 群主/管理员邀请 → 直接进（跳过 3）
- 普通成员邀请 → 变成申请，等审批

**这个设计的意义**：防止普通成员随便拉人进群（尤其在「需要审批」的群里）。

### 申请路径

`JoinGroup`（`group.go:917-993`）：

```go
func (g *groupServer) JoinGroup(ctx context.Context, req *pbgroup.JoinGroupReq) (*pbgroup.JoinGroupResp, error) {
	user, err := g.userClient.GetUserInfo(ctx, req.InviterUserID)   // ① 申请人必须存在
	group, err := g.db.TakeGroup(ctx, req.GroupID)
	if group.Status == constant.GroupStatusDismissed {
		return nil, servererrs.ErrDismissedAlready.Wrap()            // ② 群已解散
	}
	// webhook before...
	_, err = g.db.TakeGroupMember(ctx, req.GroupID, req.InviterUserID)
	if err == nil {
		return nil, errs.ErrArgs.Wrap()                              // ③ 已经在群里
	} else if !g.IsNotFound(err) && errs.Unwrap(err) != errs.ErrRecordNotFound {
		return nil, err
	}

	if group.NeedVerification == constant.Directly {
		// ④ 直接进
		groupMember := &model.GroupMember{...}
		g.db.CreateGroup(ctx, nil, []*model.GroupMember{groupMember})
		g.notification.MemberEnterNotification(ctx, req.GroupID, req.InviterUserID)
		g.setMemberJoinSeq(ctx, req.GroupID, []string{req.InviterUserID})   // ← 关键
		return &pbgroup.JoinGroupResp{}, nil
	}

	// ⑤ 走申请
	groupRequest := model.GroupRequest{...}
	g.db.CreateGroupRequest(ctx, []*model.GroupRequest{&groupRequest})
	g.notification.JoinGroupApplicationNotification(ctx, req, &groupRequest)
	return &pbgroup.JoinGroupResp{}, nil
}
```

**第 ③ 步的判断写法很别扭**：

```go
_, err = g.db.TakeGroupMember(ctx, req.GroupID, req.InviterUserID)
if err == nil {
	return nil, errs.ErrArgs.Wrap()          // 在群里 → 报错
} else if !g.IsNotFound(err) && errs.Unwrap(err) != errs.ErrRecordNotFound {
	return nil, err
}
```

为什么既检查 `IsNotFound` 又检查 `errs.ErrRecordNotFound`？

因为错误可能来自两个不同的层：
- `IsNotFound(err)`（`:161-163`）：包装了 `errs.ErrRecordNotFound.Is(specialerror.ErrCode(errs.Unwrap(err)))`，判断的是「错误码是不是 RecordNotFound」
- `errs.Unwrap(err) != errs.ErrRecordNotFound`：直接比较解包后的错误

**这两个检查其实是同一件事的两种写法，用 `&&` 连起来是冗余的**。正确写法应该是其一。这是「防御性编程写过头」的典型——两个都对，但没必要都写。

📌 **`errs.ErrArgs.Wrap()` 没带消息**，返回给客户端的错误信息是空的。调试时会很难受。这类「Wrap 不带参数」在全项目里有不少，是个可改进点。

### `setMemberJoinSeq`：`0` 是「解除限制」不是「禁止查看」

先说结论，这条结论已经过源码逐行验证（2026-10-22 修正，此前版本理解反了）：

> **`userMaxSeq` 是「这个用户在此会话可见消息的上界」；而 `0` 被特殊处理为「不限制」。**
> 所以 `setMemberJoinSeq` 写 0 的效果是**恢复全部可见**，不是「看不到历史」。

先看两个调用点。

**① 入群 / 被拉入群：写 0**（`internal/rpc/group/group.go:1035-1038`）

```go
func (g *groupServer) setMemberJoinSeq(ctx context.Context, groupID string, userIDs []string) error {
	conversationID := msgprocessor.GetConversationIDBySessionType(constant.ReadGroupChatType, groupID)
	return g.conversationClient.SetConversationMaxSeq(ctx, conversationID, userIDs, 0)
}
```

**② 退群 / 被踢：写当前 max**（`group.go:1026-1033`，push 侧还有一份同样的 `push_handler.go:402-409`）

```go
func (g *groupServer) deleteMemberAndSetConversationSeq(ctx context.Context, groupID string, userIDs []string) error {
	conversationID := msgprocessor.GetConversationIDBySessionType(constant.ReadGroupChatType, groupID)
	maxSeq, err := g.msgClient.GetConversationMaxSeq(ctx, conversationID)   // 取当前群 max
	if err != nil {
		return err
	}
	return g.conversationClient.SetConversationMaxSeq(ctx, conversationID, userIDs, maxSeq)
}
```

**③ 真正决定语义的那一行**（`pkg/common/storage/controller/msg.go:390-395`）

```go
log.ZDebug(ctx, "GetMsgBySeqsRange", "userMinSeq", userMinSeq, "conMinSeq", minSeq, "conMaxSeq", maxSeq, "userMaxSeq", userMaxSeq)
if userMaxSeq != 0 {                 // ← 关键：0 视为「没有上界限制」
    if userMaxSeq < maxSeq {
        maxSeq = userMaxSeq          // ← 只有非 0 才收紧上界
    }
}
// "maxSeq" 表示该用户可拉取的结束序号
```

`GetMsgBySeqs`（`controller/msg.go:443-446`）里是同一套判断：

```go
if userMaxSeq > 0 && userMaxSeq < maxSeq {
    maxSeq = userMaxSeq
}
```

**④ 这个值从哪来**：`PullMessageBySeqs`（`internal/rpc/msg/sync_msg.go:34-35`）把**用户自己的会话记录**里的 `MaxSeq` 传进来：

```go
minSeq, maxSeq, msgs, err := m.MsgDatabase.GetMsgBySeqsRange(ctx, req.UserID, seq.ConversationID,
    seq.Begin, seq.End, seq.Num, conversation.MaxSeq)   // ← conversation 是该用户自己的会话行
```

于是完整语义就清楚了：

| 场景 | 写入的 `max_seq` | 拉取时的效果 | 业务含义 |
|---|---|---|---|
| 从未设置（默认） | 0 | 不收紧上界 → 能拉到群的最新消息 | 正常成员 |
| 新人入群 / 被重新拉回 | 0 | 不收紧上界 → **能看到入群前的历史** | 与 Telegram 等产品一致：新成员可翻历史 |
| 退群 / 被踢 | 当前群 max | 上界冻结 → 历史还在，之后的新消息拉不到 | 离开后不能再获取新消息 |

**所以「0」在这里的正确读法是「清空限制」，而不是「上界为 0」。**

这也解释了为什么入群时要**显式写一次 0**：因为一个人可能曾经被踢过（`max_seq` 已被冻结成某个值），再次被拉进群时如果不重置，他会一直拉不到新消息。`setMemberJoinSeq(0)` 本质是一次 **reset**（幂等），而不是「设置成不可见」。

> ⚠️ **易错点（我本人踩过）**：如果只看到「入群设 0、踢人设 max」两个调用点，很容易脑补成「0 = 看不到历史、max = 能看到历史」，正好反了。必须去看**读取侧**有没有对 0 做特殊判断——这里 `userMaxSeq != 0` 就是那个分水岭。
>
> 这条也顺带说明一个通用经验：**判断一个字段的语义，永远以「读它的地方」为准，不要从「写它的地方」猜。** 写入点只告诉你「谁在改」，读取点才告诉你「改成这个值意味着什么」。

**产品层面的取舍**：OpenIM 默认让新成员可见历史。如果业务要求「新人只能看入群后的消息」，实现方式是在入群时把 `max_seq` 写成**当时的群 max**（也就是复用踢人那套冻结逻辑），而不是写 0。也就是说：**这套机制本身是中性的，「可见性策略」由调用方决定**——这正是把策略从机制里剥离出来的好处。

## 1.5 群成员数的缓存问题

「这个群有多少人？」看似简单，实际很麻烦。

**方案一：实时 count**

```go
db.group_member.countDocuments({group_id: "123"})
```

问题：群成员列表是高频查询（每个群会话都要显示人数），每次 count 都是全索引扫描。500 人的群，count 一次要扫 500 条。

**方案二：群文档里存 member_count 字段**

每次成员变更时 `$inc: {member_count: 1}` 或 `-1`。

问题：**容易算错**。批量踢 100 人时，如果循环 100 次 `$inc -1`，中间失败就错了。而且历史数据可能已经不准（没有从零校准的机制）。

**方案三：缓存 + 定期校准（OpenIM 的做法）**

`controller/group.go` 里有 `DelGroupsMemberNum` 这样的缓存操作（见 `:290`），说明成员数走缓存。

具体实现需要看 `cache/redis/group.go` 的 `GetGroupMemberNum`。大致是：
- 缓存里有 → 直接返回
- 没有 → 查 Mongo 的聚合 count → 回填缓存
- 成员变更 → 删缓存（下次读时重新 count）

**这是「缓存 + Cache-Aside」的标准做法**：不维护精确计数（容易错），而是缓存查询结果（错了下次就纠正）。

代价：成员变更后第一次查询会慢一点（回源）。但成员变更是低频的，可接受。

## 1.6 群成员变更通知的扇出成本

「A 加入了群」这件事，要让谁在群里看到一条「A 加入了群聊」的系统消息？

答案是**全群所有人**。这就是一次**扇出**：1 个事件 → N 个接收者。

在 11 篇讲过，群消息的扇出在**推送层**做（`internal/push`），不是在存储层。存储层只写一份（群会话的消息），推送层根据「谁在线」逐个推。

但这里有个成本问题：**每次成员变更都发一条群消息，会污染群聊记录**。

想象一个 500 人的群，一天有 20 个人进出，就是 20 条系统消息。用户翻聊天记录时会看到大量「xxx 加入了群聊」。

OpenIM 给的开关是 `SendMessage` 参数（`group.go:282` 的 `g.notification.GroupCreatedNotification(ctx, tips, req.SendMessage)`）。调用方可以决定「要不要发这条通知消息」。

而且通知行为本身也是配置化的（`config/notification.yml` 的 `memberEnter` 等），运维可以关掉。

**三层控制**：
1. 调用方传 `sendMessage: false` → 这次不发
2. 配置 `notification.memberEnter.enable: false` → 这类通知全局不发
3. 客户端渲染时可以折叠（连续多条「xx 加入」合并显示）

这是「默认行为可关闭」的设计——基础设施不该强制业务接受某种用户体验。

## 1.7 群主转让的原子性

转让群主要改两个成员记录：
- 旧群主：`role_level` 从 1 → 3（变成普通成员）
- 新群主：`role_level` 从 3（或 2）→ 1

如果第二个更新失败，会出现「没有群主」的群（旧群主降级了，新群主没升上去）。

`controller/group.go` 的 `TransferGroupOwner` 应该在一个事务里做（`g.ctxTx.Transaction`）。同时要处理：
- 新群主原来的角色（如果是管理员，要记下来）
- 旧群主降级成什么（普通成员 or 管理员）

看调用处 `group.go:1299`：

```go
if err := g.db.TransferGroupOwner(ctx, req.GroupID, req.OldOwnerUserID, req.NewOwnerUserID, newOwner.RoleLevel); err != nil {
```

**传了 `newOwner.RoleLevel`**——新群主原来的角色。这个参数大概是用来决定「旧群主降级成什么」：

## 1.8 解散群的两种模式

`group.go:1455` 的 `DismissGroup(ctx, req.GroupID, req.DeleteMember)`，`deleteMember` 决定两种模式：

**模式一：`deleteMember = false`（仅解散）**

- 群状态改为 `GroupStatusDismissed`
- **成员记录保留**
- 发一条「群已解散」通知

适用场景：软删除，允许恢复。或者保留成员关系用于数据分析。

**模式二：`deleteMember = true`（解散并删除成员）**

- 群状态改为 dismissed
- **删除所有成员记录**
- 给每个成员写一条「我退出了这个群」的版本日志

适用场景：彻底删除，释放空间。

看 `controller/group.go:273-310` 的实现：

```go
func (g *groupDatabase) DismissGroup(ctx context.Context, groupID string, deleteMember bool) error {
	return g.ctxTx.Transaction(ctx, func(ctx context.Context) error {
		c := g.cache.CloneGroupCache()
		if err := g.groupDB.UpdateStatus(ctx, groupID, constant.GroupStatusDismissed); err != nil {
			return err
		}
		if deleteMember {
			userIDs, err := g.cache.GetGroupMemberIDs(ctx, groupID)
			if err := g.groupMemberDB.Delete(ctx, groupID, nil); err != nil {   // nil = 删全部
				return err
			}
			c = c.DelJoinedGroupID(userIDs...).      // 每个人的"我加入的群"缓存
				DelGroupMemberIDs(groupID).           // 群的成员ID列表缓存
				DelGroupsMemberNum(groupID).          // 群成员数缓存
				DelGroupMembersHash(groupID).         // 成员hash
				DelGroupAllRoleLevel(groupID).        // 角色映射
				DelGroupMembersInfo(groupID, userIDs...).  // 每个成员详情
				DelMaxGroupMemberVersion(groupID).    // 群成员版本
				DelMaxJoinGroupVersion(userIDs...)    // 每个人的加入群版本
			for _, userID := range userIDs {
				g.groupMemberDB.JoinGroupIncrVersion(ctx, userID, []string{groupID}, model.VersionStateDelete)
			}
		}
		return c.DelGroupsInfo(groupID).ChainExecDel(ctx)
	})
}
```

**缓存要删 8 类**。这个列表本身就是理解「群模块有哪些缓存」的最好材料：

| 缓存 | key 维度 | 内容 |
|---|---|---|
| `JoinedGroupID` | userID | 我加入了哪些群 |
| `GroupMemberIDs` | groupID | 群有哪些成员 |
| `GroupsMemberNum` | groupID | 群有多少人 |
| `GroupMembersHash` | groupID | 成员列表的 hash（增量同步用） |
| `GroupAllRoleLevel` | groupID | 群内所有成员的角色 |
| `GroupMembersInfo` | groupID + userID | 成员详情 |
| `MaxGroupMemberVersion` | groupID | 群成员的版本号 |
| `MaxJoinGroupVersion` | userID | 我的「加入的群」版本号 |

**为什么要这么多维度的缓存？**

因为查询模式多：
- 「我加入了哪些群」（按用户）
- 「群有哪些人」（按群）
- 「这个群有多少人」（按群，但可以单独缓存）
- 「我和这个群的关系」（按群+用户）

每个查询模式一个 key 维度。这是**多维度缓存**的必然结果，代价是**失效要删一大堆**。

> ⚠️ **易错点**：这里漏了任何一个缓存，就会出现「群解散了但我的列表里还有」或者「成员数显示 500 但实际 0 人」。`ChainExecDel` 把所有删除攒到最后一次性执行，是为了减少往返，但**不能保证原子性**——如果执行到一半失败，缓存就处于部分失效的状态。

**模式二里的版本日志**：给每个成员写一条 `JoinGroupIncrVersion(userID, [groupID], VersionStateDelete)`。这样客户端下次增量同步时，会收到「你退出了 groupID」的变更。

而模式一（不删成员）写的是 `MemberGroupIncrVersion(groupID, []string{""}, VersionStateUpdate)`：

```go
if err := g.groupMemberDB.MemberGroupIncrVersion(ctx, groupID, []string{""}, model.VersionStateUpdate); err != nil {
```

注意 `[]string{""}`——一个空字符串。这是**哨兵**，表达「群本身变了（状态改为解散），但没有具体哪个成员变了」。客户端收到这个变更后，会重新拉群信息，发现 `status = dismissed`。

这和 17 篇的 `VersionSortChangeID = "____S_O_R_T_I_D____"` 是同一个套路：**用特殊 ID 表达「非成员维度的变更」**。

## 1.9 群 ID 的生成

`group.go:165-192`：

```go
func (g *groupServer) GenGroupID(ctx context.Context, groupID *string) error {
	if *groupID != "" {
		// 调用方指定了 ID：检查是否已存在
		_, err := g.db.TakeGroup(ctx, *groupID)
		if err == nil {
			return servererrs.ErrGroupIDExisted.WrapMsg("group id existed " + *groupID)
		} else if g.IsNotFound(err) {
			return nil
		}
		return err
	}
	for i := 0; i < 10; i++ {
		id := encrypt.Md5(strings.Join([]string{
			mcontext.GetOperationID(ctx),
			strconv.FormatInt(time.Now().UnixNano(), 10),
			strconv.Itoa(rand.Int()),
		}, ",;,"))
		bi := big.NewInt(0)
		bi.SetString(id[0:8], 16)        // 取 MD5 前 8 个十六进制字符
		id = bi.String()                  // 转成十进制字符串
		_, err := g.db.TakeGroup(ctx, id)
		if err == nil {
			continue                       // 撞了，重试
		} else if g.IsNotFound(err) {
			*groupID = id
			return nil
		}
		return err
	}
	return servererrs.ErrData.WrapMsg("group id gen error")
}
```

**ID 生成的三要素**：`operationID + 纳秒时间 + 随机数`，MD5 后取前 8 个 hex 字符（32 位），转十进制。

为什么是这三样？
- `operationID`：同一次请求内的不同群不会撞
- 纳秒时间：跨请求不撞
- `rand.Int()`：同一纳秒（几乎不可能）也不撞

**32 位 hex = 2^32 ≈ 43 亿**种可能。取前 8 个字符，碰撞概率符合生日悖论：**约 7.7 万个群时，碰撞概率到 50%**。

所以它加了「最多重试 10 次」——撞了就换一个。10 次都撞的概率极低（除非 ID 空间真的用尽了）。

**为什么不用 UUID 或者 Snowflake？**

- UUID：128 位，太长了。群 ID 要显示在 UI 上、要拼进会话 ID（`sg_{groupID}`），太长会影响存储和传输
- Snowflake：也可以用，但需要 worker ID 分配机制。OpenIM 的 standalone 模式是多进程，worker ID 不好管

用「哈希 + 截断 + 重试」，是**最简单且够用**的方案。代价是 ID 不可读、不有序（不能用来排序）。

**调用方可以指定 ID**（`*groupID != ""` 的分支）——这是给「业务系统已经有一套群 ID」的场景准备的。比如你的业务里群就是「项目」，用项目 ID 当群 ID。

### 2.2.1 前置校验与成员集合


**第 ① 步的 `WorkingGroup`**：OpenIM 只支持工作群（`constant.WorkingGroup`）。`constant` 里可能还有 `SuperGroup`（超大群）的定义，但代码不支持。

> 📌 **这是个重要的现状**：你可能在网上看到 OpenIM 宣传「支持十万人大群」，但这个版本的 `CreateGroup` 只接受 `WorkingGroup`。大群能力可能需要用其他方式（比如直接操作数据库、或者读群消息时分页优化）实现。文章不替它吹牛。

**第 ② 步的 `append(append(...))`**：`append(req.MemberUserIDs, req.AdminUserIDs...)` 会**修改 `req.MemberUserIDs` 的底层数组**（如果容量够）。这是个隐蔽的副作用——如果调用方还持有 `req.MemberUserIDs`，会发现它变了。

Go 里 `append` 的语义陷阱：`append(s, x...)` 在 `cap(s) > len(s)` 时会原地修改，否则才分配新数组。**这个代码没有先复制，直接 append 到 `req` 的字段上**。虽然这里 `req` 是一次性的请求对象，没有别处引用，不影响功能，但属于「不安全的写法」。

正确写法：

```go
userIDs := make([]string, 0, len(req.MemberUserIDs)+len(req.AdminUserIDs)+1)
userIDs = append(userIDs, req.MemberUserIDs...)
userIDs = append(userIDs, req.AdminUserIDs...)
userIDs = append(userIDs, req.OwnerUserID)
```

**第 ③ 步的 `len(userMap) != len(userIDs)`**：用「查出来的数量」和「请求的数量」比较。这是批量校验「是否都存在」的常用技巧——比逐个检查快，且能容忍部分不存在（只是结果是「有不存在」而不是「哪个不存在」）。

**`MuteEndTime: time.UnixMilli(0)`**：1970-01-01，表示「从未被禁言」。为什么用 0 而不是 `time.Time{}`（零值 = 公元 1 年）？

```go
	GroupOwnerUser: g.groupMemberDB2PB(groupMembers[0], userMap[groupMembers[0].UserID].AppMangerLevel),
}
for _, member := range groupMembers {
	member.Nickname = userMap[member.UserID].Nickname      // ← 就地改成员对象
	tips.MemberList = append(tips.MemberList, g.groupMemberDB2PB(member, ...))
	if member.UserID == opUserID {
		tips.OpUser = g.groupMemberDB2PB(member, ...)
		break
	}
}
g.notification.GroupCreatedNotification(ctx, tips, req.SendMessage)
```

**`groupMembers[0]` 一定是群主吗？** 是的，因为 `joinGroupFunc(req.OwnerUserID, GroupOwner)` 是第一个被调用的。这是**隐式的位置约定**——代码依赖了「第一个元素是群主」，如果哪天调整了调用顺序，这里就错了。

这是个**典型的脆弱点**：应该显式记录 owner 的索引，或者用 `member.RoleLevel == GroupOwner` 来找。

**`member.Nickname = userMap[...].Nickname` 就地改**：把这些成员对象的昵称补上，然后转成 PB 给客户端。注意这**修改了传入 `CreateGroup` 的对象**——如果 `CreateGroup` 内部对 `groupMembers` 做了引用保存（比如放进缓存），就会受影响。目前看是写完库就不用了，没有副作用。

**`tips.Group.MemberCount = uint32(len(userIDs))`**（`:268`）：直接用请求里的成员数，而不是查库。因为刚创建，肯定准确。这省了一次 count 查询。

## 2.3 邀请入群：分批写入

`group.go:447-463`：

```go
const singleQuantity = 50
for start := 0; start < len(groupMembers); start += singleQuantity {
	end := min(start+singleQuantity, len(groupMembers))
	currentMembers := groupMembers[start:end]

	if err := g.db.CreateGroup(ctx, nil, currentMembers); err != nil {
		return nil, err
	}

	userIDs := datautil.Slice(currentMembers, func(e *model.GroupMember) string { return e.UserID })
	if len(userIDs) != 0 {
		g.notification.GroupApplicationAgreeMemberEnterNotification(ctx, req.GroupID, req.SendMessage, opUserID, userIDs...)
	}
}
if err := g.setMemberJoinSeq(ctx, req.GroupID, req.InvitedUserIDs); err != nil {
	return nil, err
}
```

**为什么要分批（50 个一批）？**

因为：
1. **Mongo 单次插入的文档数上限**。批量 `InsertMany` 一次几千条会超时或者超过 16MB 的请求限制
2. **锁的持有时间**。如果 `CreateGroup` 内部有事务/锁，一次插 1000 条会让锁持有很久
3. **失败的影响范围**。分批后某批失败，只影响这一批（虽然前面的已经成功，需要人工处理）

**但这里有个问题**：分批写入**不是原子的**。如果第 3 批失败，前 2 批（100 人）已经进群了，后 300 人没进。而函数返回错误，调用方以为全失败了。

**这是一个真实的「部分成功」问题**。处理方式有几种：
- 全部回滚（需要事务，且 1000 条事务性能差）
- 记录「已完成的部分」，支持断点续传
- 返回「部分成功」的明细

OpenIM 选了「直接返回错误」，没有回滚也没有明细。**这是基础设施的常见取舍**：批量操作要么全成功要么部分成功，使用方要能接受。

**`setMemberJoinSeq` 在循环外调用**，且传的是 `req.InvitedUserIDs`（原始请求的列表，不是分批后的）。这是对的——不管分几批写，所有人的 seq 都要设。

**注意它不在循环内调用**：如果放在循环内，每次都要调一次会话服务，N/50 次 RPC。放外面只调一次（内部是批量设置）。

## 2.4 踢人：三层校验

`group.go:542-650`。这是群里权限最复杂的操作。

```go
func (g *groupServer) KickGroupMember(ctx context.Context, req *pbgroup.KickGroupMemberReq) (*pbgroup.KickGroupMemberResp, error) {
	group, err := g.db.TakeGroup(ctx, req.GroupID)
	if err != nil {
		return nil, err
	}
	if len(req.KickedUserIDs) == 0 { ... }
	if datautil.Duplicate(req.KickedUserIDs) { ... }

	opUserID := mcontext.GetOpUserID(ctx)
	if datautil.Contain(opUserID, req.KickedUserIDs...) {
		return nil, errs.ErrArgs.WrapMsg("opUserID in KickedUserIDs")    // ① 不能踢自己
	}
	owner, err := g.db.TakeGroupOwner(ctx, req.GroupID)
	if datautil.Contain(owner.UserID, req.KickedUserIDs...) {
		return nil, errs.ErrArgs.WrapMsg("ownerUID can not Kick")        // ② 不能踢群主
	}

	members, err := g.db.FindGroupMembers(ctx, req.GroupID, append(req.KickedUserIDs, opUserID))
	g.PopulateGroupMember(ctx, members...)
	memberMap := ...   // userID → *GroupMember

	isAppManagerUid := authverify.IsAdmin(ctx)
	opMember := memberMap[opUserID]
	for _, userID := range req.KickedUserIDs {                            // ③ 逐人校验角色
		member, ok := memberMap[userID]
		if !ok {
			return nil, servererrs.ErrUserIDNotFound.WrapMsg(userID)
		}
		if !isAppManagerUid {
			if opMember == nil {
				return nil, errs.ErrNoPermission.WrapMsg("opUserID no in group")
			}
			switch opMember.RoleLevel {
			case constant.GroupOwner:
				// 群主：什么都能踢（除了群主自己，第 ② 步已挡）
			case constant.GroupAdmin:
				if member.RoleLevel == constant.GroupOwner || member.RoleLevel == constant.GroupAdmin {
					return nil, errs.ErrNoPermission.WrapMsg("group admins cannot remove the group owner and other admins")
				}
			case constant.GroupOrdinaryUsers:
				return nil, errs.ErrNoPermission.WrapMsg("opUserID no permission")
			default:
				return nil, errs.ErrNoPermission.WrapMsg("opUserID roleLevel unknown")
			}
		}
	}
	// ... 删除 + 通知 + setConversationMaxSeq
}
```

三道校验：

**① 不能踢自己**：`Contain(opUserID, KickedUserIDs)`。为什么？因为「踢自己」应该用「退群」接口，语义不同（退群有群主不能退的检查，踢自己有别的副作用）。

**② 不能踢群主**：`Contain(owner.UserID, KickedUserIDs)`。这是**绝对的**——连系统管理员都不能踢群主（第 ② 步在 `isAppManagerUid` 判断之外）。

**③ 按操作者角色判断**：
- 群主：可以踢任何人（除了自己，第 ① 步挡了；除了群主，第 ② 步挡了）→ 实际能踢管理员和普通成员
- 管理员：不能踢群主和其他管理员
- 普通成员：什么都不能踢

**注意第 ③ 步的 `switch opMember.RoleLevel` 里 `case constant.GroupOwner:` 是空的**——没有 `break` 也没有代码，直接落到下一个 case？不，Go 的 `switch` 不会 fallthrough，空的 case 就是「什么都不做」，然后跳出 switch。所以群主通过校验。

这是 Go 里一个容易误读的写法：**空 case = 什么都不做 + 不 fallthrough**。对比 C 语言，空 case 会继续往下执行。

**`opMember == nil` 的判断在 `switch` 外面**：如果操作者不在群里（`memberMap` 里没有），直接拒绝。这是**必要的防御**——不然 `opMember.RoleLevel` 会 panic。

### `deleteMemberAndSetConversationSeq`

```go
if err := g.db.DeleteGroupMember(ctx, group.GroupID, req.KickedUserIDs); err != nil {
	return nil, err
}
num, err := g.db.FindGroupMemberNum(ctx, req.GroupID)     // 重新查人数
// ... 构造 tips
g.notification.MemberKickedNotification(ctx, tips, req.SendMessage)
if err := g.deleteMemberAndSetConversationSeq(ctx, req.GroupID, req.KickedUserIDs); err != nil {
	return nil, err
}
```

**顺序很关键**：
1. 先删成员
2. 再查人数（拿到新的人数放进通知）
3. 发通知
4. 最后设 `userMaxSeq`

为什么「设 seq」在最后？因为它是**防止被踢者继续收消息**的。如果先设 seq 再发通知，被踢的人可能收不到这条「你被踢了」的通知（因为 seq 已经冻结）。

这个顺序保证：**被踢的人能收到最后一条通知，之后的消息看不到**。

## 2.5 退群：为什么群主不能退

`group.go:995-1024`：

```go
func (g *groupServer) QuitGroup(ctx context.Context, req *pbgroup.QuitGroupReq) (*pbgroup.QuitGroupResp, error) {
	if req.UserID == "" {
		req.UserID = mcontext.GetOpUserID(ctx)      // 不传就是自己
	} else {
		if err := authverify.CheckAccess(ctx, req.UserID); err != nil {
			return nil, err
		}
	}
	member, err := g.db.TakeGroupMember(ctx, req.GroupID, req.UserID)
	if err != nil {
		return nil, err
	}
	if member.RoleLevel == constant.GroupOwner {
		return nil, errs.ErrNoPermission.WrapMsg("group owner can't quit")   // ← 关键
	}
	g.PopulateGroupMember(ctx, member)
	if err := g.db.DeleteGroupMember(ctx, req.GroupID, []string{req.UserID}); err != nil {
		return nil, err
	}
	g.notification.MemberQuitNotification(ctx, g.groupMemberDB2PB(member, 0))
	if err := g.deleteMemberAndSetConversationSeq(ctx, req.GroupID, []string{req.UserID}); err != nil {
		return nil, err
	}
}
```

`req.UserID == ""` 时取 `opUserID`，**这让同一个接口支持两种用法**：
- 普通成员退群：不传 `userID`
- 管理员把人踢出群（用退群的语义）：传 `userID`

但第二种用法有权限问题：`CheckAccess(ctx, req.UserID)` 要求「操作者 == userID 或者是管理员」。所以**群管理员不能用这个接口踢普通成员**（群管理员不是系统管理员，`CheckAccess` 会失败）。

要踢人必须用 `KickGroupMember`。这个接口的 `userID` 参数实际只对**系统管理员**有用。

> 📌 这是一个「接口设计有历史包袱」的例子：一个接口承担了两种语义，但权限模型只覆盖了一种。

## 2.6 群主转让与解散

### 转让的五个步骤

`group.go:1247-1308`：


**第 ② 步的 `datautil.Single`** 是个「差集」函数：找出 `[old, new]` 里不在 `memberMap` 的 key 中的元素。用来报错时明确指出「谁不在群里」（`strings.Join(ids, ",")`）。

**第 ④ 步的「先解禁」**（前文 1.3 讲过）保证「群主不被禁言」这个不变量。

**第 ④ 步和第 ⑤ 步不在同一个事务里**：如果解禁成功但转让失败，新群主就被白解禁了。这是个**无害的不一致**（解禁本身是对的，只是转让没成）。

### 解散的两种模式

前文 1.8 讲过。补充一个细节：`group.go:1452`：

```go

	return nil, servererrs.ErrDismissedAlready.WrapMsg("group status is dismissed")
}
```

**只有「仅解散」模式才检查「是否已解散」**。如果 `deleteMember = true`（彻底删除），不检查——因为这是幂等操作，多删一次也无害。

**`DismissGroup` 为什么不调 `deleteMemberAndSetConversationSeq`？**

因为群解散后，整个群会话就不该再有了。成员的 `userMaxSeq` 不需要单独冻结——`verify.go:83` 的检查会拒绝所有发往已解散群的消息。

但**成员的历史消息还在**（如果 `deleteMember = false`）。用户还能翻到解散前的聊天记录，只是不能再发。

## 2.7 群信息的填充：`PopulateGroupMember`

`notification.go:72-105`：

```go
func (g *NotificationSender) PopulateGroupMember(ctx context.Context, members ...*model.GroupMember) error {
	if len(members) == 0 {
		return nil
	}
	emptyUserIDs := make(map[string]struct{})
	for _, member := range members {
		if member.Nickname == "" || member.FaceURL == "" {
			emptyUserIDs[member.UserID] = struct{}{}
		}
	}
	if len(emptyUserIDs) > 0 {
		users, err := g.getUsersInfo(ctx, datautil.Keys(emptyUserIDs))
		userMap := ...
		for i, member := range members {
			user, ok := userMap[member.UserID]
			if !ok { continue }
			if member.Nickname == "" {
				members[i].Nickname = user.GetNickname()
			}
			if member.FaceURL == "" {
				members[i].FaceURL = user.GetFaceURL()
			}
		}
	}
	return nil
}
```

**核心思路**：成员记录里的昵称头像可能是空的（历史数据、或者用户后来才设置），这时去用户表补。

**为什么只查「空的」？** 因为大部分成员的昵称已经存了，全部重查就是 N+1 查询。先收集空的那批，一次批量查，然后回填。

**这是一个「懒填充」设计**：不在写成员记录时就要求昵称非空，而是读的时候发现空了再补。好处是写入路径简单（不依赖用户服务），坏处是每次读都要检查一次（虽然大部分时候是空 map，开销很小）。

**注意它改的是 `members[i]` 而不是 `member`**：`for i, member := range members` 里，`member` 是副本，改它不会影响 `members[i]`。所以必须用下标赋值。**这是 Go 里 range 的经典陷阱**。

## 2.9 群成员缓存的多维度

前面 1.8 节列了 8 类缓存。这里补充它们的用途和失效策略：

| 缓存 | 读多写少？ | TTL | 失效时机 |
|---|---|---|---|
| `JoinedGroupID`（我加入的群） | 读多 | 长 | 成员变更、群解散 |
| `GroupMemberIDs`（群成员 ID 列表） | 读多 | 长 | 成员变更 |
| `GroupsMemberNum`（成员数） | 读极多 | 短/长 | 成员变更 |
| `GroupMembersHash`（成员 hash） | 读多 | 长 | 成员变更 |
| `GroupAllRoleLevel`（角色映射） | 读多 | 长 | 角色变更 |
| `GroupMembersInfo`（成员详情） | 读多 | 长 | 成员信息变更 |
| `MaxGroupMemberVersion`（群成员版本） | 读多 | 长 | 成员变更 |
| `MaxJoinGroupVersion`（我的加群版本） | 读多 | 长 | 加群/退群 |

**注意 `GroupMemberIDs` 和 `GroupsMemberNum` 是分开的**。前者是 ID 列表（用于推送扇出），后者是数量（用于展示）。

为什么数量要单独缓存？因为 `GroupMemberIDs` 返回的是完整列表，计算 `len()` 也要把列表拉回来。如果只需要数量（比如群列表页显示「500 人」），单独缓存一个整数更省。

## 2.11 群通知的发送路径

`internal/rpc/group/notification.go` 有 1034 行——比 `group.go` 的一半还多。全是通知函数。

看一个典型的（`GroupMemberMutedNotification` 之类），结构都是：

**为什么通知函数要单独一个文件？** 因为：

# 第四部分 · 自测题

**Q1** 群成员关系为什么不用「群文档里存 members 数组」？

<details>
<summary>答案</summary>

三个原因：
1. 文档大小限制（16MB），且读群信息时会把整个数组拉回来
2. 无法按成员查询「我加入了哪些群」——要遍历所有群文档
3. 并发更新不同成员会冲突（都重写整个数组）

独立成员表：一条记录 = 一个「用户在某群的身份」，索引 `(group_id, user_id)` 唯一、`group_id`、`user_id` 各有索引，两个方向都能高效查询。

代价是「群有多少人」要 count（OpenIM 用缓存解决），以及「成员列表 + 用户信息」要两次查询（用 `PopulateGroupMember` 补昵称）。
</details>

**Q2** 群禁言和成员禁言为什么要分开存？

<details>
<summary>答案</summary>

语义不同：群禁言是「群的状态」（`group.status = GroupStatusMuted`），成员禁言是「成员关系的状态」（`group_member.mute_end_time`）。

合一的方案会遇到问题：
- 用群状态表达成员禁言 → 无法表达「500 人里禁言 3 个人」
- 用成员字段表达群禁言 → 要给所有人逐个设时间，新增成员会漏

另外群禁言没有过期时间（手动解除），成员禁言有（到期自动解除），语义也不同。
</details>

**Q3** 三级角色的权限边界在哪几个函数里体现？举三个容易搞错的点。

<details>
<summary>答案</summary>

主要在 `CheckGroupAdmin`（`group.go:144`）、`KickGroupMember`（`:578-599`）、`MuteGroupMember`（`:1497-1514`）、`SetGroupMemberInfo`（`:1593`）、`DismissGroup`（`:1440`）、`TransferGroupOwner`（`:1285`）。

三个易错点：
1. **管理员不能踢其他管理员**（`:590`），也不能禁言管理员（群主才能）
2. **群主不能退群**（`:1007`），必须先转让或解散
3. **系统管理员可以绕过所有群内角色检查**（靠 `if !authverify.IsAdmin(ctx)` 跳过整个块），包括禁言群主——但**不能踢群主**（`:561` 在 IsAdmin 判断之外）
</details>

**Q4** 踢人之后为什么要调 `SetConversationMaxSeq`？新人入群为什么也调它（但值不同）？

<details>
<summary>答案</summary>

踢人后把被踢者的 `max_seq` 设成**当前群的最大 seq**，让他拉不到之后的新消息（历史保留）。这靠的是读取侧的 `if userMaxSeq != 0 && userMaxSeq < maxSeq { maxSeq = userMaxSeq }`，把「可见上界」收紧。

新人入群写 **0**，效果是**解除**这个上界（`userMaxSeq != 0` 不成立，不收紧），所以能看到入群前的历史。这一步的作用是 **reset**：一个人可能曾被踢过、上界被冻结，重新拉进群时必须清掉，否则他永远拉不到新消息。

> ⚠️ 这里有个反直觉点，面试时正好可以展示严谨性：**`0` 不是「上界为 0」，而是「没有上界」。** 判断依据不在写入点，在读取点（`controller/msg.go:393-395`）。如果业务要求「新人不可见历史」，正确做法是把入群时的值改成当时的群 maxSeq，而不是保留 0。
</details>

**Q5** 邀请入群时，什么情况下会变成「申请」？

<details>
<summary>答案</summary>

三个条件同时满足（`group.go:397-425`）：
1. `group.NeedVerification == AllNeedVerification`（群策略：所有人都需要审批）
2. 操作者不是系统管理员（`!authverify.IsAdmin(ctx)`）
3. 操作者在群里的角色不是 owner/admin

此时 `InviteUserToGroup` 不会真的拉人，而是创建 `GroupRequest` 并通知审批人。函数提前 `return`。

意义：防止普通成员在「需要审批」的群里随便拉人。
</details>

**Q6** 批量邀请 1000 人，代码分 50 一批写入。如果第 3 批失败会怎样？

<details>
<summary>答案</summary>

前 2 批（100 人）已经进群，后 900 人没进，函数返回错误。**没有回滚，也没有返回「部分成功」的明细**。

这是「批量操作要么全成功要么部分成功」的取舍。使用方要能接受这种中间状态，或者自己在业务层做补偿（比如重新调一次，已进群的人会被 `Duplicate` 检查挡掉——但 `InviteUserToGroup` 没有检查「已在群里」，可能会重复插入）。

改进方向：事务（性能差）、断点续传（记录进度）、或返回部分成功明细。
</details>

**Q7** 群主转让前为什么要先解除新群主的禁言？

<details>
<summary>答案</summary>

保证「群主不被禁言」这个业务不变量（`group.go:1291-1297`）。

如果不做，会出现「群主不能发言」的荒谬状态。代码选择在「转让」这个入口处修，而不是在「发消息」时检查「如果是群主就忽略禁言」——前者的成本更低（一次检查 vs 每条消息都检查）。
</details>

**Q8** 解散群的 `deleteMember` 参数两种模式的区别？分别写什么版本日志？

<details>
<summary>答案</summary>

- `false`（仅解散）：群状态改为 dismissed，**成员记录保留**，写 `MemberGroupIncrVersion(groupID, [""], VersionStateUpdate)`——用空字符串作哨兵，表示「群本身变了但没有具体成员变化」
- `true`（解散并删除成员）：删除所有成员记录，给每个成员写 `JoinGroupIncrVersion(userID, [groupID], VersionStateDelete)`

两种模式都删 8 类缓存（见 `controller/group.go:288-295`）。
</details>

**Q9** 群成员缓存有哪几个维度？为什么数量要单独缓存？

<details>
<summary>答案</summary>

8 个维度：`JoinedGroupID`（按用户）、`GroupMemberIDs`（按群）、`GroupsMemberNum`（按群）、`GroupMembersHash`（按群）、`GroupAllRoleLevel`（按群）、`GroupMembersInfo`（群+用户）、`MaxGroupMemberVersion`（按群）、`MaxJoinGroupVersion`（按用户）。

数量单独缓存是因为「群列表页显示人数」只需要一个整数，不需要拉回完整 ID 列表再 `len()`。省传输、省内存。

代价是失效时要删一大堆——漏一个就会出现「群解散了但我的列表里还有」这类不一致。
</details>

**Q10** `GenGroupID` 取 MD5 前 8 个十六进制字符（32 位）。这个 ID 空间够吗？为什么不用 UUID？

<details>
<summary>答案</summary>

32 位 = 2^32 ≈ 43 亿。按生日悖论，**约 7.7 万个群时碰撞概率到 50%**。代码加了「最多重试 10 次」，撞了就换——10 次都撞的概率极低。

不用 UUID 因为 128 位太长：群 ID 要显示在 UI、要拼进会话 ID（`sg_{groupID}`），会影响存储和传输。

不用 Snowflake 因为需要 worker ID 分配机制，standalone 模式下多进程不好管。

代价：ID 不可读、不有序（不能用来排序）。
</details>

# 第五部分 · 面试话术

## 5.1 30 秒版本

> OpenIM 的群模块用「群表 + 成员表 + 申请表」三张表。成员表是 M:N 的中间表，索引 `(group_id, user_id)` 唯一，两个方向都能查。没有把成员塞进群文档的数组，因为文档有 16MB 上限、无法按成员反查、并发更新会冲突。
>
> 角色是三级硬编码（群主/管理员/成员），权限判断散在几个函数里用 `switch RoleLevel`。没有做成可配置的权限表，因为 IM 的群权限是行业标准化的，配置化只会增加复杂度和不一致。
>
> 禁言分两层：群禁言改 `group.status`，成员禁言改 `group_member.mute_end_time`。必须分开，因为一个是群属性、一个是关系属性。
>
> 最精妙的设计是踢人/退群后调 `SetConversationMaxSeq`——用 `max_seq` 作为「可见上界」冻结被踢者的消息范围，历史保留但看不到新消息。同一套机制写 0 就变成「解除限制」，用于重新入群时 reset。**机制只有一个：一个上界值；策略（新人是否可见历史）交给调用方决定。**

## 5.2 3 分钟版本

**开场**：讲数据建模（三张表、为什么不用数组），强调三个理由。

**中间**：讲权限矩阵。用一个具体场景串起来——「管理员想踢另一个管理员会怎样」（被拒），「群主想退群会怎样」（被拒，必须先转让），「系统管理员能踢群主吗」（不能，`group.go:561` 的检查在 `IsAdmin` 之外）。

**然后**：讲禁言的两层设计，以及「转让群主前先解禁」这个细节（体现「业务不变量在入口处保证」的思想）。

**收尾**：讲 `userMaxSeq` 的复用——一套机制、两个值、两种效果。这是最值得讲的设计。

**预判追问**：

| 追问 | 回答要点 |
|---|---|
| 「大群（10 万人）怎么支持？」 | 当前版本的 `CreateGroup` 只接受 `WorkingGroup`，不支持超大群。要支持需要：成员表分片、推送扇出限流、成员列表分页、群消息不落每人的收件箱。📌 这是个诚实的回答——不要吹 |
| 「群成员缓存有 8 个维度，怎么保证一致性？」 | `CloneGroupCache` 累积删除操作，最后 `ChainExecDel` 一次性执行。但不保证原子性，部分失败会导致部分缓存脏。兜底靠 TTL 和下次写操作再删 |
| 「批量邀请 1000 人为什么分 50 一批？」 | Mongo 单次插入的文档数/请求大小限制；锁持有时间；失败影响范围。代价是非原子，第 3 批失败前 2 批已写入 |
| 「群主转让是原子的吗？」 | 转让本身在事务里（`controller/group.go` 的 `TransferGroupOwner`），但「先解禁新群主」在事务外。如果解禁成功转让失败，是「无害的不一致」 |
| 「解散群为什么不冻结成员的 seq？」 | 因为群解散后 `verify.go` 会拒绝所有发往这个群的消息，不需要靠 seq 冻结。成员的历史消息还在（`deleteMember=false` 时） |
| 「群 ID 会重复吗？」 | 32 位空间，7.7 万群时碰撞率 50%。代码重试 10 次。实际部署中建议监控碰撞率 |
| 「成员数是怎么算的？」 | 缓存 + 定期回源 count，不维护精确计数字段（容易算错）。成员变更时删缓存，下次读时重新 count |

## 5.3 可以主动抛出的问题

1. **`CreateGroup:204` 的 `append(append(req.MemberUserIDs, ...))`** 会修改 `req.MemberUserIDs` 的底层数组（容量够时），是隐蔽的副作用。应该先 `make` 新切片。

2. **`JoinGroup:942-947` 的错误判断冗余**：`!g.IsNotFound(err) && errs.Unwrap(err) != errs.ErrRecordNotFound` 两个检查是同一件事，用 `&&` 连起来没意义。

3. **`JoinGroup:944` 的 `errs.ErrArgs.Wrap()` 不带消息**，返回给客户端的错误信息是空的，调试困难。

4. **`CreateGroup:272` 依赖 `groupMembers[0]` 是群主**，这是隐式的位置约定。应该用 `RoleLevel == GroupOwner` 显式查找。

5. **`InviteUserToGroup` 分批写入非原子**，第 N 批失败时前面已写入，没有回滚也没有部分成功明细。而且没有检查「已在群里」，重复邀请可能产生重复记录（取决于 `CreateGroup` 是否用 upsert）。
