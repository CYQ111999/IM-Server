# 第一部分 · 纯理论

## 1.1 IM 为什么必须用对象存储

聊天里发一张图片，数据流向是：

```
手机相册 → 上传到某处 → 得到一个 URL → 把 URL 放进消息体 → 对方收到消息 → 点开 URL 下载
```

**关键点：消息体里存的是 URL，不是文件本身。**

如果把文件塞进消息体会怎样？

**MongoDB 单文档上限 16MB**（13 篇讲的 100 条消息一个文档，那一个文档里每条消息平均只剩 160KB）。一张手机照片就有 3~5MB，**三条消息就把一个文档撑爆了**。

所以文件必须存在别的地方。选项：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 存本地磁盘 | 简单 | 多节点无法共享、无法扩容、备份麻烦、单点故障 |
| 存 MongoDB GridFS | 不用引入新组件 | 性能差、占数据库资源、运维复杂 |
| 存对象存储（S3 协议） | 无限扩容、多副本、CDN 友好、按量付费 | 需要额外部署一个组件 |
| 存云厂商对象存储（COS/OSS） | 免运维 | 花钱、数据在别人机房 |

OpenIM 支持全部选项（`third.go:74-90`）：

```go
switch enable := config.RpcConfig.Object.Enable; enable {
case "minio":   // 自建 MinIO（本项目 Docker 里跑的就是它）
case "cos":     // 腾讯云
case "oss":     // 阿里云
case "kodo":    // 七牛
case "aws":     // AWS S3
case "":        // 禁用（o = disable.NewDisable()）
default:        // 配置错误
}
```

**`case "":` 这个分支很重要**：如果不配置对象存储，用的是 `disable.NewDisable()`——一个「所有方法都返回错误」的空实现。这意味着**上传功能不可用，但服务能正常启动**。

> 📌 这解释了你环境里「MinIO 必须存在」的原因：不是代码依赖 MinIO，是**功能依赖**。禁用 MinIO 后聊天还能发文字，但发不了图片和文件。这也是我记忆里「坚决不同意禁用 MinIO」的技术根源。

### 对象存储的核心抽象

S3 协议把存储抽象成三个概念：

```
Bucket（桶）        ← 类似「一个磁盘分区」，有名字、有权限
  └─ Key（键）      ← 类似「文件路径」，如 avatar/20261021/abc.jpg
       └─ Object    ← 实际数据（字节流）+ 元数据（Content-Type、大小）
```

**没有目录**。`avatar/20261021/abc.jpg` 里的 `/` 只是 Key 的一部分，不是真实的目录层级（虽然控制台会按 `/` 分组显示）。

这个设计带来一个好处：**Key 可以随便起，不需要先创建目录**。也带来一个麻烦：**无法「重命名目录」**，只能逐个复制。

## 1.2 三种上传方式

### 方式一：服务端中转

```
客户端 → POST 文件到 IM 服务 → IM 服务转存到对象存储 → 返回 URL
```

优点：客户端简单，不用知道对象存储的存在。
缺点，也是致命的：

- **带宽翻倍**。文件流经 IM 服务，服务要接收一遍再发一遍
- **内存压力**。服务端要缓冲整个文件（或者用流式处理，但实现复杂）
- **IM 服务成为瓶颈**。上传 1GB 视频时，IM 服务的连接被占满

**IM 服务是「消息路由器」，不该承担文件传输。** 这是架构上的分工。

### 方式二：客户端直传（预签名 URL）

```
① 客户端 → IM 服务：我要上传 avatar/xxx.jpg
② IM 服务 → 客户端：给你一个 URL，带签名，10 分钟内有效
③ 客户端 → 对象存储：PUT 文件到那个 URL（不经过 IM 服务）
④ 客户端 → IM 服务：我传完了
⑤ IM 服务：记录这个文件属于谁
```

**核心是第 ② 步的「预签名 URL」。**

对象存储的权限模型是「私有桶」——默认谁都不能访问。要访问必须带签名。签名的生成需要**密钥**（AccessKey + SecretKey）。

客户端不能持有密钥（会泄露）。所以由服务端生成一个**带时效的签名 URL**，客户端拿着它去操作。

**预签名 URL 的本质**：服务端用密钥把「操作类型 + Key + 过期时间」算一个 HMAC 签名，拼在 URL 里。对象存储收到请求后，用同样的密钥重算签名，比对一致就放行。

```
https://minio.example.com/bucket/avatar/xxx.jpg
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256
  &X-Amz-Credential=...
  &X-Amz-Date=20261021T120000Z
  &X-Amz-Expires=600
  &X-Amz-Signature=abc123...
```

**关键：签名覆盖了「过期时间」**。所以客户端无法篡改 URL 让它永久有效——改了 `X-Amz-Expires`，签名就对不上。

**这也意味着服务端无法「提前作废」一个已签发的 URL**（和 JWT 一样的困境，见 16 篇）。只能等它过期。

### 方式三：分片上传

大文件（比如 500MB 的视频）一次性 PUT 有几个问题：
- 网络中断就要从头再来
- 无法并行（单连接带宽有限）
- 服务端要缓冲整个文件

分片上传把它拆成 N 块：

```
① 客户端 → IM 服务：我要传 500MB，算出来要 10 片
② IM 服务 → 对象存储：初始化一个 multipart upload，拿到 uploadID
③ IM 服务 → 客户端：uploadID + 每片的预签名 URL + 片大小
④ 客户端：并行上传 10 片（每片 50MB）
⑤ 客户端 → IM 服务：传完了，这是每片的 ETag
⑥ IM 服务 → 对象存储：complete upload（把 10 片合成一个对象）
```

优点：
- **断点续传**：中断后只需重传失败的那几片
- **并行**：10 个连接同时传，速度提升
- **内存友好**：每片单独处理

`MinIO` 和所有 S3 兼容存储都支持这个模式（`CreateMultipartUpload` / `UploadPart` / `CompleteMultipartUpload` / `AbortMultipartUpload`）。

### 秒传：hash 去重

如果用户要传的文件，**服务器上已经有了**（比如一张流传很广的表情包），还要再传一遍吗？

不需要。做法是：

```
① 客户端算出文件的 hash（比如 SHA256）
② 客户端 → IM 服务：我要传这个 hash 的文件
③ IM 服务：查一下这个 hash 有没有对应的对象
   - 有 → 直接返回可访问的 URL（秒传完成，没传任何字节）
   - 没有 → 走正常的上传流程
```

OpenIM 的实现就在 `InitiateMultipartUpload` 里（`s3.go:46-98`）：

```go
result, err := t.s3dataBase.InitiateMultipartUpload(ctx, req.Hash, req.Size, t.defaultExpire, int(req.MaxParts), req.ContentType)
if err != nil {
	if haErr, ok := errs.Unwrap(err).(*cont.HashAlreadyExistsError); ok {   // ← 秒传
		obj := &model.Object{
			Name:   req.Name,
			UserID: mcontext.GetOpUserID(ctx),
			Hash:   req.Hash,
			Key:    haErr.Object.Key,        // 复用已存在的 Key！
			Size:   haErr.Object.Size,
			...
		}
		if err := t.s3dataBase.SetObject(ctx, obj); err != nil {
			return nil, err
		}
		return &third.InitiateMultipartUploadResp{
			Url: t.apiAddress(req.UrlPrefix, obj.Name),   // 直接返回 URL
		}, nil
	}
	return nil, err
}
```

**注意：秒传时创建了一条新的 Object 记录，但 `Key` 指向同一个对象。**

于是数据库里可能出现：

```
Object 表：
{ name: "alice/avatar.jpg",  user_id: "alice", hash: "abc...", key: "obj/20261021/xyz.jpg" }
{ name: "bob/表情包.png",    user_id: "bob",   hash: "abc...", key: "obj/20261021/xyz.jpg" }  ← 同一个 key！
```

**两个不同的 `name`（用户可见路径）指向同一个 `key`（实际存储路径）。**

这就是「引用计数」的由来：删除 `alice/avatar.jpg` 时，不能直接删 `obj/20261021/xyz.jpg`——bob 还在用。

看 `DeleteOutdatedData`（`s3.go:294-304`）：

```go
count, err := t.s3dataBase.GetKeyCount(ctx, engine, obj.Key)   // 这个 key 还被几个 Object 引用？
if count == 0 {
	if err := t.s3.DeleteObject(ctx, obj.Key); err != nil {       // 没人引用了，真删
		return nil, err
	}
}
```

`GetKeyCount` 就是数「Object 表里有多少条记录的 key 是这个值」。

> 📌 **这是一个「逻辑删除 + 引用计数回收」的经典模式**。类似的还有：Git 的 object（多个分支可以指向同一个 blob）、Docker 的 layer（多个镜像共享同一层）。

## 1.3 安全：`name` 为什么必须以 `userID/` 开头

对象存储的 Key 是全局的（一个桶内）。如果不管，Alice 可以上传一个叫 `bob/avatar.jpg` 的对象，**覆盖 Bob 的头像**。

`s3.go` 的 `checkUploadName`（`tool.go:29-49`）：

```go
func (t *thirdServer) checkUploadName(ctx context.Context, name string) error {
	if name == "" {
		return errs.ErrArgs.WrapMsg("name is empty")
	}
	if name[0] == '/' {
		return errs.ErrArgs.WrapMsg("name cannot start with `/`")     // ① 不能绝对路径
	}
	if err := checkValidObjectName(name); err != nil {                 // ② 长度 ≤ 1024、必须 UTF-8
		return errs.ErrArgs.WrapMsg(err.Error())
	}
	opUserID := mcontext.GetOpUserID(ctx)
	if opUserID == "" {
		return errs.ErrNoPermission.WrapMsg("opUserID is empty")
	}
	if !authverify.CheckUserIsAdmin(ctx, opUserID) {                   // ③ 普通用户强制隔离
		if !strings.HasPrefix(name, opUserID+"/") {
			return errs.ErrNoPermission.WrapMsg(fmt.Sprintf("name must start with `%s/`", opUserID))
		}
	}
	return nil
}
```

**第 ③ 条是核心**：普通用户的 `name` 必须以 `<自己的userID>/` 开头。

于是：
- Alice 上传只能写 `alice/xxx.jpg`
- 她想写 `bob/xxx.jpg` → 被拒（前缀不匹配）

**这是一种「用命名空间做权限隔离」的做法**——简单粗暴但有效。不需要在对象存储层配 ACL，靠这个字符串前缀就够了。

**代价**：用户无法共享一个「公共目录」（比如 `public/表情包/`）。管理员可以（`CheckUserIsAdmin` 跳过前缀检查），普通用户不行。

**第 ① 条「不能以 `/` 开头」** 防的是什么？

如果 name 是 `/bob/xxx`，经过某些路径拼接（比如 `path.Join(bucket, name)`）后可能变成 `bucket/bob/xxx`，绕过前缀检查（因为 `strings.HasPrefix("/bob/xxx", "alice/")` 是 false，其实已经被第 ③ 条挡了）。

更危险的是**路径穿越**：`alice/../../bob/xxx`。这种 name 通过了前缀检查（以 `alice/` 开头），但实际指向 `bob/xxx`。

`checkValidObjectName` 只检查了长度和 UTF-8，**没有检查 `..`**。这是个**潜在漏洞**：

📌 **需要验证**：S3 协议里 Key 是扁平字符串，`..` 不会被解析成上跳目录（不是文件系统语义）。所以实际上传时 `alice/../../bob/xxx` 会作为一个字面 Key 存储，不会覆盖 `bob/xxx`。

但如果代码里用 `path.Join` 或 `filepath.Clean` 处理过 name，就会出问题。需要看 `InitiateFormData` 里的 `path.Join(cont.DirectPath, date, opUserID, ...)` —— 这个 Join 只处理内部生成的 key，不处理用户传的 name。

**结论**：当前实现看起来安全，但**依赖「S3 是扁平的」这个前提**。如果哪天换成本地文件系统存储，这个假设就崩了。这是「隐式依赖」的典型风险。

## 1.4 为什么 `/object/*name` 是 GET 且不走 token

`internal/api/router.go:245-253`：

```go
objectGroup.POST("/part_limit", t.PartLimit)
objectGroup.POST("/part_size", t.PartSize)
objectGroup.POST("/initiate_multipart_upload", t.InitiateMultipartUpload)
objectGroup.POST("/auth_sign", t.AuthSign)
objectGroup.POST("/complete_multipart_upload", t.CompleteMultipartUpload)
objectGroup.POST("/access_url", t.AccessURL)
objectGroup.POST("/initiate_form_data", t.InitiateFormData)
objectGroup.POST("/complete_form_data", t.CompleteFormData)
objectGroup.GET("/*name", t.ObjectRedirect)      // ← 注意这个 GET
```

**除了最后一个，全是 POST**。

05 篇讲过：`GinParseToken` 中间件的 `switch` 只有 `case POST`，没有 default，所以 **13 个 GET 路由完全绕过 token 校验**。`/object/*name` 就是其中之一。

**它靠什么保证安全？**

`ObjectRedirect`（`internal/api/third.go:108-143`）：

```go
func (o *ThirdApi) ObjectRedirect(c *gin.Context) {
	name := c.Param("name")
	// ... 去掉开头的 /
	// ... 设置 operationID
	query := ...  // 收集所有 URL 参数
	resp, err := o.Client.AccessURL(ctx, &third.AccessURLReq{Name: name, Query: query})
	// ...
	c.Redirect(http.StatusFound, resp.Url)      // ← 302 重定向到预签名 URL
}
```

它的逻辑是：**收到 `GET /object/alice/xxx.jpg`，查出这个对象的 key，生成一个预签名 URL，302 重定向过去**。

**这就是「短链」模式**：

```
客户端：<img src="http://im-server:10002/object/alice/xxx.jpg">
   ↓ 302
客户端：<img src="https://minio:10005/bucket/obj/20261021/xyz.jpg?signature=...">
```

**安全性分析**：

| 攻击方式 | 是否可行 | 原因 |
|---|---|---|
| 遍历别人的文件 | **可行** | 只要知道 `name`（`bob/xxx.jpg`），就能拿到 URL |
| 猜 name | 难 | name 里通常有随机 UUID（见下方 `InitiateFormData` 的 key 生成） |
| 无限刷接口 | 有限 | 每次请求都产生一次签名，消耗 CPU。但可以通过 CDN 缓存 302 响应缓解 |
| 拿到永久 URL | **不可行** | 重定向到的 URL 有 `defaultExpire`（7 天）的时效 |

**关键问题：`name` 可猜吗？**

看 `InitiateFormData`（`s3.go:199-206`）：

```go
uid, err := uuid.NewRandom()
key := path.Join(cont.DirectPath, date, opUserID, hex.EncodeToString(uid[:])+path.Ext(req.Name))
```

内部 key 是 `direct/20261021/alice/<随机16字节>.jpg`——**58 个十六进制字符，不可猜**。

但**用户可见的 `name` 是客户端自己定的**。如果客户端用 `alice/avatar.jpg`，那就是可猜的。

**这是一个「客户端自律」的安全模型**：服务端不保证 name 不可猜，客户端应该用随机名字。

> 📌 **实际风险**：如果有人把私密照片存在 `alice/photo1.jpg` 这种可猜的名字下，别人遍历 `photo1~photo100` 就能拿到。这是**真实存在的安全隐患**，也是为什么微信的图片 URL 都是长串随机字符。

**改进方向**：
1. 强制 name 里包含随机部分（比如 UUID）
2. 用「签名 URL 短期有效 + 服务端校验访问者是否有权」的方式（但 302 到 S3 后就无法校验了）
3. 用 CDN 的「防盗链」（Referer 校验）——但 App 里没有 Referer

## 1.5 日志上报：为什么要自己生成 log_id

`internal/rpc/third/log.go:18-31`：

```go
func genLogID() string {
	const dataLen = 10
	data := make([]byte, dataLen)
	rand.Read(data)
	chars := []byte("0123456789")
	for i := 0; i < len(data); i++ {
		if i == 0 {
			data[i] = chars[1:][data[i]%9]     // ← 第一位不能是 0
		} else {
			data[i] = chars[data[i]%10]
		}
	}
	return string(data)
}
```

生成 10 位数字串，**第一位非 0**（避免被当成八进制或者被去掉前导零）。

为什么要自己生成，不用 UUID 或者数据库自增？

- UUID：太长（36 字符），日志 ID 要用户报给客服，越短越好
- 自增：需要中心化，且能推算「系统一共有多少条日志」（信息泄露）
- 时间戳：可预测，且同一毫秒会撞

**10 位数字** = 90 亿种可能（第一位 1-9，其余 0-9）。够用，且**用户好念**。

**生成后要检查是否重复**（`log.go:48-61`）：

```go
for i := 0; i < 20; i++ {
	id := genLogID()
	logs, err := t.thirdDatabase.GetLogs(ctx, []string{id}, "")
	if len(logs) == 0 {
		log.LogID = id
		break
	}
}
if log.LogID == "" {
	return nil, servererrs.ErrData.WrapMsg("Log id gen error")
}
```

**「生成 → 查重 → 重试 20 次」**。这是 18 篇 `GenGroupID` 的同款模式。

> ⚠️ **这里的实现有个性能问题**：批量上报 N 个日志文件，就要做 N 次「生成 + 查重」= N 次 Mongo 查询。如果用户一次上报 10 个日志文件，就是 10 次查询。
>
> 更好的是批量查重（一次查 10 个 ID），或者用更长的 ID 降低碰撞概率、干脆不查重（接受极低概率的重复）。

### 日志上报的完整流程

```
客户端写日志到本地文件 → 用户点「反馈问题」 → 客户端调 /object/initiate_form_data 上传日志文件 → 
拿到 URL → 调 /third/upload_logs 把「URL + 设备信息」写进 log 表 → 客服按 userID 搜日志
```

**注意上传日志文件本身也走对象存储**，不是直接 POST 给 IM 服务。`UploadLogs` 只是登记元数据：

```go
type Log struct {
	LogID        string    // 10 位数字，用户报给客服
	Platform     string    // ios/android/web
	UserID       string    // 谁上报的
	CreateTime   time.Time
	Url          string    // 日志文件的 URL（对象存储）
	FileName     string
	AppFramework string    // 客户端框架（react-native/flutter/原生）
	Version      string    // 客户端版本
	Ex           string
}
```

**`AppFramework` 和 `Version` 的作用**：排查问题时，先按版本分组看是不是某个版本的 bug。

## 1.6 推送 token：命名留下的坑

`third.go:110-116`：

```go
func (t *thirdServer) FcmUpdateToken(ctx context.Context, req *third.FcmUpdateTokenReq) (resp *third.FcmUpdateTokenResp, err error) {
	err = t.thirdDatabase.FcmUpdateToken(ctx, req.Account, int(req.PlatformID), req.FcmToken, req.ExpireTime)
	...
}
```

接口叫 `FcmUpdateToken`，参数叫 `FcmToken`。

**但 FCM（Firebase Cloud Messaging）的代码已经被删了**（你瘦身时删除的 `offlinepush/fcm`）。现在只保留 `dummy` 实现。

这个接口**还在，还在工作**，但它的语义已经不是「更新 FCM token」，而是「**更新任意厂商的推送 token**」：
- iOS：APNs 的 device token
- Android：小米/华为/OPPO/vivo 的 token
- 或者任何推送服务商的 token

**为什么改名这么难？**

因为它是**对外协议的一部分**。改名字要改：
1. protobuf 定义（`protocol/third` 包）
2. 所有 SDK（Go/JS/Java/iOS/Android）
3. 所有已部署的客户端

这叫**协议兼容性包袱**。一旦发布就不能随便改名。

> 📌 **这是一个很好的「技术债」案例**：删实现容易（删代码就行），改 API 名字难（破坏了所有客户端）。所以现实中你会看到大量「名字和实际不符」的接口。

**`expire_time` 参数**：告诉服务端「这个 token 多久后失效」。因为推送 token 会过期（比如用户重装 App），客户端知道自己的 token 什么时候过期，提前报给服务端。

**`SetAppBadge`**（`third.go:118-127`）：设置 App 图标的角标数字。

**为什么服务端要存「角标数」？**

因为 iOS 的角标是**由推送服务设置的**（APNs 的 `badge` 字段），不是客户端自己画的。服务端发推送时要带上正确的角标数，否则角标会不准。

所以服务端需要知道「这个用户当前的总未读数」。客户端算出来上报，服务端存着，发推送时用。

**`CheckAccess` 保证只能设自己的角标**。

## 1.7 对象清理：定时任务的逻辑

`DeleteOutdatedData`（`s3.go:277-307`）是定时任务调的清理接口：

```go
func (t *thirdServer) DeleteOutdatedData(ctx context.Context, req *third.DeleteOutdatedDataReq) (*third.DeleteOutdatedDataResp, error) {
	if err := authverify.CheckAdmin(ctx); err != nil {          // ① 只有管理员
		return nil, err
	}
	engine := t.config.RpcConfig.Object.Enable
	expireTime := time.UnixMilli(req.ExpireTime)
	// ② 查所有过期的 Object 记录
	models, err := t.s3dataBase.FindExpirationObject(ctx, engine, expireTime, req.ObjectGroup, int64(req.Limit))
	for i, obj := range models {
		// ③ 删除 Object 记录
		if err := t.s3dataBase.DeleteSpecifiedData(ctx, engine, []string{obj.Name}); err != nil {
			return nil, errs.Wrap(err)
		}
		if err := t.s3dataBase.DelS3Key(ctx, engine, obj.Name); err != nil {
			return nil, errs.Wrap(err)
		}
		// ④ 引用计数：还有别人用这个 key 吗？
		count, err := t.s3dataBase.GetKeyCount(ctx, engine, obj.Key)
		if count == 0 {
			// ⑤ 没人用了，删实际文件
			if err := t.s3.DeleteObject(ctx, obj.Key); err != nil {
				return nil, err
			}
		}
	}
	return &third.DeleteOutdatedDataResp{Count: int32(len(models))}, nil
}
```

**「过期」的判定标准**：`CreateTime < expireTime`。也就是说，**对象不会因为「没人访问」而过期，只会因为「创建太久」而过期**。

这是**「定期清理」而不是「LRU 淘汰」**。区别：
- 定期清理：不管有没有人用，到时间就删（适合「聊天记录里的媒体文件保留 90 天」这种策略）
- LRU 淘汰：按访问时间删（适合「缓存」）

IM 的媒体文件通常用前者（产品策略：只保留 N 天）。

**注意第 ③ 步先删 Object 记录再查引用计数**。顺序是对的——先把自己这条引用去掉，再数剩下的。

**遍历方式有个问题**：`for i, obj := range models` 里逐个 `DeleteSpecifiedData`（每个一次 Mongo 删除），而不是批量删。如果有 1000 个过期对象，就是 1000 次删除。

📌 **可改进点**：批量删除（`DeleteMany`），或者至少批量删 Object 记录后再逐个处理实际文件。

**`req.Limit` 的用途**：每次只处理 N 个，避免一次处理太多导致超时。调用方（定时任务）循环调用直到返回 0。

**两个存储层**：
- `thirdDatabase`：日志 + 推送 token + 角标（走 Mongo + Redis 缓存）
- `s3dataBase`：对象存储操作（走 s3.Interface + Object 表）

**`defaultExpire = 7 * 24 小时`**：预签名 URL 的有效期。这个值偏长——7 天内任何人拿到 URL 都能访问。

**为什么这么长？** 因为消息里的 URL 要长期可用（用户翻历史消息时还能看到图片）。如果只有 10 分钟，历史消息里的图片就全挂了。

**但这也意味着「URL 泄露 = 7 天可访问」**。真正的安全做法是「短效 URL + 客户端每次请求时重新换」，但那要多一次往返。

**MinIO 的 `minioCache`**：MinIO 的实现把「分片上传的中间状态」存在 Redis 里（`redis.NewMinioCache(rdb)`）。

为什么？因为分片上传是有状态的（记住 uploadID、已上传的片），如果状态只在内存，服务重启就丢了。存 Redis 可以跨实例、跨重启。

## 2.2 分片大小怎么算

`third/s3.go:38-44`：

```go

	if err != nil {
		return nil, err
	}

```

委托给 `s3.Interface.PartSize(size)`。这个实现（在 `github.com/openimsdk/tools/s3/cont` 里）的逻辑大致是：

```
① 如果文件 <= minPartSize（通常 5MB），直接单次 PUT，不分片
② 否则：partSize = max(minPartSize, fileSize / maxParts)
③ 但 partSize 不能超过 maxPartSize（通常 5GB）
④ 最后一片可能小于 partSize（余数）
```

**`PartLimit` 返回三个值**（`s3.go:26-36`）：

```go
return &third.PartLimitResp{
	MinPartSize: limit.MinPartSize,   // 每片最小值
	MaxPartSize: limit.MaxPartSize,   // 每片最大值
	MaxNumSize:  int32(limit.MaxNumSize),  // 最多多少片
}, nil
```

**为什么要给客户端算好？**

因为不同存储引擎的限制不同：
- S3/MinIO：最小 5MB（除最后一片）、最多 10000 片
- 阿里云 OSS：最小 100KB、最多 10000 片
- 腾讯云 COS：最小 1MB、最多 10000 片

如果客户端自己写死 5MB，换成 OSS 就会失败。**服务端告诉客户端「当前引擎的限制」，客户端据此算分片**。

**这是个「能力协商」的设计**：客户端先调 `/object/part_limit` 拿到限制，自己算 size，再调 `/object/part_size` 验证（或者直接算完就传）。

### ① `InitiateMultipartUpload`（`s3.go:46-98`）

```go
func (t *thirdServer) InitiateMultipartUpload(ctx context.Context, req *third.InitiateMultipartUploadReq) (*third.InitiateMultipartUploadResp, error) {
	// ① 校验 name（必须以 userID/ 开头）
	if err := t.checkUploadName(ctx, req.Name); err != nil {
		return nil, err
	}
	expireTime := time.Now().Add(t.defaultExpire)

	// ② 初始化（内部会先查 hash 是否存在）
	result, err := t.s3dataBase.InitiateMultipartUpload(ctx, req.Hash, req.Size, t.defaultExpire, int(req.MaxParts), req.ContentType)
	if err != nil {
		// ③ 秒传分支
		if haErr, ok := errs.Unwrap(err).(*cont.HashAlreadyExistsError); ok {
			obj := &model.Object{
				Name:        req.Name,
				UserID:      mcontext.GetOpUserID(ctx),
				Hash:        req.Hash,
				Key:         haErr.Object.Key,      // ← 复用已有对象的 key
				Size:        haErr.Object.Size,
				ContentType: req.ContentType,
				Group:       req.Cause,
				CreateTime:  time.Now(),
			}
			if err := t.s3dataBase.SetObject(ctx, obj); err != nil {
				return nil, err
			}
			return &third.InitiateMultipartUploadResp{
				Url: t.apiAddress(req.UrlPrefix, obj.Name),    // ← 直接返回可访问 URL
			}, nil
		}
		return nil, err
	}

	// ④ 正常分片流程：返回 uploadID + 每片的预签名 URL
	var sign *third.AuthSignParts
	if result.Sign != nil && len(result.Sign.Parts) > 0 {
		sign = &third.AuthSignParts{
			Url:    result.Sign.URL,
			Query:  toPbMapArray(result.Sign.Query),
			Header: toPbMapArray(result.Sign.Header),
			Parts:  make([]*third.SignPart, len(result.Sign.Parts)),
		}
		for i, part := range result.Sign.Parts {
			sign.Parts[i] = &third.SignPart{
				PartNumber: int32(part.PartNumber),
				Url:        part.URL,
				Query:      toPbMapArray(part.Query),
				Header:     toPbMapArray(part.Header),
			}
		}
	}
	return &third.InitiateMultipartUploadResp{
		Upload: &third.UploadInfo{
			UploadID:   result.UploadID,
			PartSize:   result.PartSize,
			Sign:       sign,
			ExpireTime: expireTime.UnixMilli(),
		},
	}, nil
}
```

**响应的两种形态**：
- 秒传：`{ url: "..." }`——客户端直接用，不用传文件
- 正常：`{ upload: { uploadID, partSize, sign: { url, parts: [...] }, expireTime } }`——客户端按 parts 逐个 PUT

**「秒传用 error 表达」的设计**：`HashAlreadyExistsError` 是一个 error 类型，但它表达的是「成功」的语义。

这是个**有争议的设计**：
- 好处：不用在返回值里加一个 `Exists bool` 字段，调用方用 `errors.As` 判断
- 坏处：error 通常是「失败」的意思，用它表达「秒传成功」违反直觉

Go 社区对这类做法有争议。更常见的做法是返回值里带状态（`result.Exists = true`）。

**`Group` 字段**（`req.Cause`）：文件的分组。用来区分「头像」「消息附件」「日志」等，清理时可按组批量删（`DeleteOutdatedData` 的 `req.ObjectGroup`）。

**`req.Parts`** 是每片的 ETag 列表。对象存储据此校验「这些片都传上来了、顺序对、内容没变」。

**注意这里又调了一次 `checkUploadName`**。为什么？

因为 `req.Name` 是客户端传的，第二次传可能是不同的值（第一次传 `alice/a.jpg`，第二次传 `bob/b.jpg`）。**每次用到 name 都要校验**，不能信任「第一次校验过了」。

这是**「不信任客户端状态」的原则**：每个请求独立校验，不依赖前一个请求的结果。

**`Id` 字段的设计很妙**：它把「name/size/contentType/group/key」这些元信息用 JSON 序列化后 base64 编码，直接返回给客户端。

`CompleteFormData`（`s3.go:235-271`）再解码回来：

```go
data, err := base64.RawStdEncoding.DecodeString(req.Id)

**为什么要把元信息编码进 `Id` 而不是存在服务端？**

因为**服务端无状态**。如果存在 Redis，就是一次额外的写入 + 一次读取 + TTL 管理。编码进 Id，服务端不用存任何东西。

**代价是 `Id` 可伪造**。客户端可以自己构造一个 base64(JSON) 当 Id 传进来。

**但伪造能干什么？** `CompleteFormData` 会：
1. `checkUploadName(mate.Name)` —— 要求 name 以 userID/ 开头
2. `StatObject(mate.Key)` —— 要求这个 key 真实存在于对象存储

所以伪造者只能：
- 用自己的 userID 前缀（合法）
- 指向一个**真实存在的 key**

如果他能猜到一个别人上传的 key（`direct/20261021/bob/<随机>.jpg`），他可以把那个文件「登记」到自己名下。

**这算不算漏洞？** 算**信息泄露的辅助**——它不直接给人访问权限（`AccessURL` 只看 name 和 key 的映射），但可以让攻击者在自己的 Object 记录里指向别人的文件。

实际影响有限（还是要先猜到 key），但设计上不够严谨。

**改进**：`Id` 里加签名（`base64(json + hmac(json))`），或者服务端存一份临时记录。

**`Absolute` 参数**（`:193-195`）：管理员可以直接用 `name` 当 `key`（不生成随机路径）。用途：预置一些固定路径的资源（比如内置表情包 `public/sticker/1.png`）。

**普通用户的 `duration` 固定 10 分钟**（`:197`）：表单上传的 URL 有效期短，因为表单上传是「一次性」的。

### 表单上传 vs 分片上传

| | 表单直传 | 分片上传 |
|---|---|---|
| 适用大小 | 小文件（< 100MB） | 大文件 |
| 断点续传 | ❌ | ✅ |
| 并行 | ❌（单次 POST） | ✅ |
| 客户端复杂度 | 低 | 高 |
| 服务端状态 | 无（`Id` 自包含） | 有（uploadID 存 Redis） |

**OpenIM 两种都支持**，客户端按文件大小选。

		return time.Time{}, "", err
	}
	if opt.ContentType == "" {
		opt.ContentType = obj.ContentType
	}
	if opt.Filename == "" {
		opt.Filename = filepath.Base(obj.Name)                // ← 下载时的文件名
	}
	expireTime := time.Now().Add(expire)
	rawURL, err := s.s3.AccessURL(ctx, obj.Key, expire, opt)  // ← 用 key 签名，不是 name
	...
}
```

**关键：签名用的是 `obj.Key`（内部路径），不是 `name`（用户可见路径）。**

这解释了为什么有「两层路径」：
- `name`：`alice/photo.jpg`（用户可见，可重复）
- `key`：`direct/20261021/alice/a1b2c3...jpg`（内部唯一）

**为什么要两层？**

因为**秒传**。多个 name 可以指向同一个 key。如果直接用 name 当 key，秒传就无法实现（同一个文件要存多份）。

`Filename` 参数：设置 `Content-Disposition` 头，让浏览器下载时用这个文件名。`filepath.Base(obj.Name)` 取 name 的最后一段（`alice/photo.jpg` → `photo.jpg`）。

**`cache.GetName(engine, name)`**：name → Object 的映射缓存。因为每次访问文件都要查这个映射，缓存是必须的。

## 2.6 `SetObject` 与缓存

`controller/s3.go:70-76`：

```go
func (s *s3Database) SetObject(ctx context.Context, info *model.Object) error {
	info.Engine = s.s3.Engine()                   // ← 记录用了哪个引擎
	if err := s.db.SetObject(ctx, info); err != nil {
		return err
	}

```

**`info.Engine = s.s3.Engine()`**：每个 Object 记录都标注「存在哪个引擎里」（minio/cos/oss）。

- 老文件在 MinIO
- 新文件在 COS
- 读的时候要根据 Engine 决定去哪读

这是个**前瞻性设计**（也叫「多后端支持」）。当前实现里 `AccessURL` 用的是 `s.s3.Engine()`（当前配置的引擎），没有按 Object 的 Engine 分发——所以这个字段目前**只写不读**。

📌 **待验证**：`FindExpirationObject(engine, ...)` 是带 engine 参数查询的，说明清理时会按引擎过滤。所以字段有用，只是「读文件」时没用上。

# 第四部分 · 自测题

**Q1** 为什么 IM 服务端不能自己存文件，必须用对象存储？

<details>
<summary>答案</summary>

因为消息体里存的是 URL，不是文件本身。MongoDB 单文档上限 16MB，而 100 条消息一个文档，平均每条只剩 160KB——一张手机照片就撑爆了。

不用本地磁盘因为多节点无法共享、无法扩容、单点故障。不用 GridFS 因为性能差、占数据库资源。

对象存储（S3 协议）无限扩容、多副本、CDN 友好。
</details>

**Q2** 预签名 URL 的原理是什么？为什么它能安全地把上传权限交给客户端？

<details>
<summary>答案</summary>

服务端用密钥（AccessKey/SecretKey）对「操作类型 + Key + 过期时间」算 HMAC 签名，拼在 URL 里。对象存储收到请求后用同样的密钥重算签名，比对一致就放行。

安全因为：
1. 客户端不持有密钥，无法自己生成签名
2. 签名覆盖了过期时间，客户端篡改 `X-Amz-Expires` 会导致签名不匹配
3. 签名覆盖了具体的 Key 和操作类型，只能操作指定的对象

局限：服务端无法提前作废已签发的 URL（和 JWT 一样），只能等过期。OpenIM 的有效期是 7 天，偏长。
</details>

**Q3** 秒传是怎么实现的？为什么必须要有引用计数？

<details>
<summary>答案</summary>

`InitiateMultipartUpload` 时先按 hash 查对象是否已存在。存在则返回 `HashAlreadyExistsError`，代码捕获后创建一条新的 Object 记录，但 `Key` 指向已存在的对象，直接返回 URL——没传任何字节。

必须引用计数因为多个 name 可以指向同一个 key。删除 `alice/photo.jpg` 时不能直接删 `obj/xxx`（bob 还在用）。`DeleteOutdatedData` 里 `GetKeyCount(key) == 0` 才真删。
</details>

**Q4** `checkUploadName` 的三个检查分别防什么？

<details>
<summary>答案</summary>

1. `name[0] == '/'`：防绝对路径。如果路径被 `path.Join` 处理，`/bob/xxx` 可能变成 `bob/xxx`，绕过前缀检查
2. `checkValidObjectName`：长度 ≤ 1024、必须 UTF-8。防超长 key 和编码问题
3. **前缀必须是 `<自己的userID>/`**：防越权覆盖。没有这条，Alice 可以传 `bob/avatar.jpg` 覆盖 Bob 的头像

第三条是核心，本质是「用命名空间做权限隔离」，简单有效。管理员跳过这条（可以写任意路径）。
</details>

**Q5** `/object/*name` 是 GET 路由，绕过 token 校验，靠什么保证安全？

<details>
<summary>答案</summary>

它的逻辑是「查 name → 生成预签名 URL → 302 重定向」。安全性依赖：

1. **name 不可猜**：内部 key 里有 UUID（58 个十六进制字符）。但用户可见的 name 是客户端定的，如果用 `alice/photo1.jpg` 就可猜
2. **URL 有时效**：重定向到的 URL 有 7 天有效期

**真实风险**：如果客户端用可猜的 name，别人遍历就能拿到文件。这是「客户端自律」的安全模型，不是服务端强制的。

改进方向：强制 name 含随机部分、用短效 URL + 重新换、或加 Referer 防盗链（但 App 没有 Referer）。
</details>

**Q6** 分片上传的 `partSize` 为什么要服务端算，不能客户端写死？

<details>
<summary>答案</summary>

因为不同存储引擎的限制不同：
- S3/MinIO：最小 5MB（除最后一片）、最多 10000 片
- 阿里云 OSS：最小 100KB
- 腾讯云 COS：最小 1MB

客户端写死 5MB，换成 OSS 就浪费（本可以更小），换成一个限制更大的引擎就失败。

所以提供 `/object/part_limit` 让客户端拿到当前引擎的限制，自己算。这是「能力协商」的设计。
</details>

**Q7** 为什么 `InitiateFormData` 返回的 `Id` 里编码了元信息，而不存在服务端？

<details>
<summary>答案</summary>

因为服务端无状态。存 Redis 要多一次写入 + 一次读取 + TTL 管理。编码进 `Id`（base64(JSON)），服务端不用存任何东西。

代价：`Id` 可伪造。但伪造者受限于：
1. `checkUploadName` 要求 name 以自己 userID 开头
2. `StatObject` 要求 key 真实存在

所以伪造只能「把别人的文件登记到自己名下」（还要先猜到 key）。实际影响有限但设计不够严谨。改进：`Id` 里加 HMAC 签名。
</details>

**Q8** 客户端日志上报的 `log_id` 为什么要自己生成，不用 UUID？

<details>
<summary>答案</summary>

因为 log_id 要用户念给客服听（10 位数字 vs 36 字符的 UUID），越短越好。

自增 ID 不行：需要中心化、且能推算出系统总日志数（信息泄露）。时间戳不行：可预测、同毫秒会撞。

10 位数字（第一位非 0）= 90 亿种可能。生成后「查重 + 重试 20 次」，和 `GenGroupID` 同款模式。

**性能问题**：批量上报 N 个文件就要 N 次查重查询。应该批量查重或干脆不查（接受极低概率重复）。
</details>

**Q9** 为什么推送 token 的接口还叫 `FcmUpdateToken`？

<details>
<summary>答案</summary>

因为它是**对外协议的一部分**，改名要改 protobuf 定义 + 所有 SDK（Go/JS/Java/iOS/Android）+ 所有已部署客户端。

删实现容易（删代码），改 API 名字难（破坏兼容性）。所以现实中大量接口「名字和实际不符」。

现在这个接口的语义是「更新任意厂商的推送 token」，不只是 FCM。
</details>

**Q10** 对象清理为什么用「创建时间过期」而不是「LRU 淘汰」？

<details>
<summary>答案</summary>

因为产品策略是「媒体文件只保留 N 天」，不是「按访问频率淘汰」。

- 定期清理（创建时间）：适合「保留 90 天」这种明确的产品策略
- LRU 淘汰：适合缓存（热数据留、冷数据删）

IM 的媒体文件通常用前者——不管有没有人看，到时间就删（节省成本）。

`DeleteOutdatedData` 里 `CreateTime < expireTime` 就是「创建太久」。它遍历删 Object 记录 → 查引用计数 → 为 0 才删实际文件。
</details>

# 第五部分 · 面试话术

## 5.1 30 秒版本

> IM 的文件走对象存储，消息体里只存 URL。这是必须的——MongoDB 单文档 16MB，100 条消息一个文档，一条照片就撑爆。
>
> 上传有三种方式：服务端中转（不推荐，带宽翻倍）、预签名直传（客户端直接 PUT 到对象存储，不经过 IM 服务）、分片上传（大文件、断点续传、并行）。
>
> 预签名 URL 的核心是「服务端用密钥算 HMAC 签名，客户端拿着有时效的 URL 去操作」。客户端不持有密钥，所以安全；签名覆盖过期时间，所以不能篡改。
>
> 还有秒传：先按 hash 查有没有，有就直接返回 URL。这带来「多个 name 指向同一个 key」的情况，所以删除时必须做引用计数——`GetKeyCount(key) == 0` 才真删。

## 5.2 3 分钟版本

**开场**：讲「为什么不能用服务端中转」——带宽翻倍、内存压力、IM 服务变成瓶颈。IM 是消息路由器，不该承担文件传输。

**中间**：讲预签名 URL 的原理（HMAC 覆盖「操作 + Key + 过期时间」），以及它的局限（无法提前作废）。再讲分片上传的三个好处（断点续传、并行、内存友好）。

**然后**：讲秒传和引用计数。举实验里的例子——两个 name 指向同一个 key，删一个不能删文件。

**收尾**：讲安全设计的坑——`name` 必须以 `userID/` 开头（防越权覆盖），但 `/object/*name` 是 GET 路由不走 token，靠「name 不可猜 + URL 有时效」保证安全。指出风险：「如果客户端用可猜的 name，别人遍历就能拿到文件」。

**预判追问**：

| 追问 | 回答要点 |
|---|---|
| 「为什么不直接给客户端密钥？」 | 密钥能签发任意 URL，泄露后整个桶可被任意读写。预签名只给「这一个对象、这一种操作、这段时间」的权限 |
| 「7 天有效期是不是太长？」 | 是。但短了会导致历史消息里的图片挂掉。折中是「URL 里带长期有效的 name，每次访问时重新签名」（就是 `/object/*name` 这个 302 的设计） |
| 「引用计数并发安全吗？」 | 不安全。`GetKeyCount` 和 `DeleteObject` 之间可能有新引用进来。需要分布式锁或者「先标记删除、延迟真删」 |
| 「分片上传中断了怎么办？」 | 客户端保留 uploadID 和已传片的 ETag，断线后调 `/object/auth_sign` 重签失败的片，再 complete。未完成的 uploadID 会一直占空间，需要定时 abort（OpenIM 有 `DeleteOutdatedData`，但那是删 Object 记录，不是 abort 上传） |
| 「图片缩略图怎么做的？」 | `AccessURL` 支持 `type=image&width=&height=&format=`，依赖对象存储/云厂商的实时处理能力。MinIO 不支持，参数会被忽略 |
| 「为什么日志上传也要走对象存储？」 | 日志文件可能几十 MB，走 IM 服务一样有带宽和内存问题。上传拿 URL，再调 `/third/upload_logs` 登记元数据 |

## 5.3 可以主动抛出的问题

1. **`/object/*name` 是 GET 路由，绕过 token 校验**（05 篇的问题，这里的具体体现）。安全性完全依赖「name 不可猜」，但 name 是客户端定的，服务端不强制随机。建议强制 name 含 UUID。

2. **`FormDataMate` 编码进 `Id` 但没有签名**，可伪造。虽然受限于 `checkUploadName` 和 `StatObject`，但攻击者可以「把别人的文件登记到自己名下」（需先猜 key）。

3. **引用计数不是原子的**：`GetKeyCount` 后 `DeleteObject`，中间可能有新引用进来，导致删掉了还在用的文件。需要分布式锁或「延迟删除」。

4. **`UploadLogs` 批量上报时，每个文件都做一次「生成 + 查重」查询**（`log.go:48-61`），N 个文件 = N 次 Mongo 查询。应该批量查重。

5. **`DeleteOutdatedData` 逐个删除 Object 记录**（`s3.go:288-294`），1000 个过期对象 = 1000 次删除。应该批量。

6. **`checkValidObjectName` 不检查 `..`**，安全性依赖「S3 的 Key 是扁平字符串，不解析 `..`」这个隐式前提。如果换成文件系统存储就会出问题。

# Part4 小结

五篇讲完了 OpenIM 的四个业务域 + 一个基础设施模块：

```
16 用户与鉴权  →  谁在用（JWT + Redis 白名单、多端策略、两条鉴权范式）
17 好友关系链  →  人和人能聊天（双向边表、申请状态机、单向拉黑、版本日志增量）
18 群组与成员  →  一群人能聊天（M:N 中间表、三级角色、两层禁言、seq 冻结）
19 会话与未读  →  怎么看到聊天（视图而非容器、n_ 通知会话、减法未读、排序）
20 第三方服务  →  聊天里能发文件（预签名直传、分片、秒传、引用计数）
```

**这四个业务域共享同一套骨架**：

| 共性 | 体现 |
|---|---|
| 认证在 API、授权在 RPC | 每个函数开头都是 `CheckAccess`/`CheckAdmin` |
| 缓存包在数据库外面 | `NewXxxDatabase(db, cache, tx)` |
| 变更写版本日志 | relation/group/conversation 都有 `IncrVersion` |
| 通知走消息通道 | 都调 `msgClient.SendMsg` 发 `SysMsgType` 消息 |
| 软删除 + 状态位 | 申请不删改状态、群解散改 status、消息用 del_list |
| 批量操作分批 | 群成员 50/批、消息 100/文档 |

**这不是巧合，是「基础设施的一致性」**。一个项目里如果每个模块都有自己的套路，读代码的成本会指数上升。
