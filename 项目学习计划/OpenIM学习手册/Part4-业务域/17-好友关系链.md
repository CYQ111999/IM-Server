# 第一部分 · 纯理论

> 这一部分先讲清楚「社交关系」这类数据在存储上的三条路线，以及「增量同步」这个通用问题的解法。第二部分再落到 OpenIM 的具体实现。

## 1.1 社交关系怎么存：三种建模方式

假设有 4 个用户：A、B、C、D。关系是 A-B 好友、A-C 好友、B-C 好友。

### 方式一：邻接表（每人一行，好友 ID 列表）

```
┌────────┬──────────────────┐
│ userID │ friendIDs        │
├────────┼──────────────────┤
│ A      │ [B, C]           │
│ B      │ [A, C]           │
│ C      │ [A, B]           │
│ D      │ []               │
└────────┴──────────────────┘
```

优点：查「我的好友列表」是一次查询，最常用的场景最快。
缺点：**无法存关系属性**。你给 B 的备注是「老王」，B 给你的备注是「小张」，这两个备注属于「边」而不属于「点」，邻接表塞不下（塞进去就变成「每条边一个元素」的复杂结构）。

### 方式二：邻接矩阵（N×N 的表）

```
    A  B  C  D
A   -  1  1  0
B   1  -  1  0
C   1  1  -  0
D   0  0  0  -
```

优点：查「A 和 B 是不是好友」是 O(1)。
缺点：**N² 的存储**。100 万用户就是 1 万亿个格子，完全不可行。只适合「用户数很少且关系密集」的场景（比如小团队权限表）。

### 方式三：边表（一条关系一行）

```
┌───────────────┬─────────────┬────────┬─────────┐
│ owner_user_id │ friend_user_id │ remark │ add_source │
├───────────────┼─────────────┼────────┼─────────┤
│ A             │ B           │ 老王    │ 1       │
│ B             │ A           │ 小张    │ 1       │
│ A             │ C           │        │ 2       │
│ C             │ A           │        │ 2       │
└───────────────┴─────────────┴────────┴─────────┘
```

这是 OpenIM 的选择（`pkg/common/storage/model/friend.go:11` 的 `Friend` 结构）。关键特征是：

**一对好友存两行，方向相反。** A→B 一行，B→A 一行。

### 为什么必须存两份？

理论上存一份 + 查询时用 `OR` 就够了：

```sql
SELECT * FROM friend WHERE (owner='A' AND friend='B') OR (owner='B' AND friend='A')
```

但这样有两个问题：

**问题一：关系是「有向」的，属性也是「有向」的。**

备注是「我给对方的备注」，不是「双方共同的备注」。A 给 B 备注「老王」，B 那边看到的应该还是 A 的昵称，不是「老王」。

同样的还有：
- `is_pinned`（是否置顶）：A 把 B 置顶了，不影响 B 的列表
- `add_source`（添加来源）：A 是从群聊加的 B，B 是扫码加的 A，来源不同
- `ex`（扩展字段）：各自存各自的业务数据

**一份记录无法同时表达两个方向的不同属性**。所以要么存两份，要么存一份 + 一张「方向属性表」——后者更复杂。

**问题二：查询路径要短。**

IM 最高频的查询是「拉我的好友列表」和「判断这两人是不是好友」。

- 存两份：`WHERE owner_user_id = 'A'` 走单字段索引，一次范围扫描
- 存一份 + OR：`WHERE (owner='A' AND friend='B') OR (owner='B' AND friend='A')` 是**两个不同条件的并集**，优化器可能走 index merge，也可能全表扫。在 Mongo 里 `$or` 的性能明显差于单条件。

> 📌 记忆点：**双向存两份 = 用空间换「方向属性」和「单索引查询」。代价是写入放大 2 倍、一致性要自己保证（两条要么都写成功，要么都不写）。**

一致性怎么保证？`BecomeFriends` 里用**事务**（`controller/friend.go:148` 的 `f.tx.Transaction`）把两行包在一起。

## 1.2 申请的三种状态与「不删除」原则

好友申请是一张独立的表（`model/friend_request.go:8` 的 `FriendRequest`），核心字段：

```
from_user_id     谁发起
to_user_id       发给谁
handle_result    0=未处理 1=同意 -1=拒绝
req_msg          申请附言
handle_msg       处理附言
handle_time      处理时间
handler_user_id  谁处理的（可能是管理员代处理）
```

**为什么申请记录不删除，而是改 `handle_result`？**

三个原因：

1. **客户端要展示历史**。「我发出的申请」列表里，被拒绝的申请也要能看到（用户可能想再试一次）
2. **幂等与防重**。同一个方向重复申请，如果删了记录就无法判断「是不是刚申请过」
3. **审计**。谁在什么时候拒绝了谁，是运营和风控的数据

代价是：表会一直增长，需要定期归档。OpenIM 没有做归档（这是它作为基础设施的取舍——留给使用方决定保留策略）。

**重复申请怎么处理？** `controller/friend.go:121-144` 的 `AddFriendRequest`：

```go
_, err := f.friendRequest.Take(ctx, fromUserID, toUserID)
switch {
case err == nil:
	// 已存在申请：重置处理状态并更新内容
	m["handle_result"] = 0        // ← 关键：重置为未处理
	m["handle_msg"] = ""
	m["req_msg"] = reqMsg
	m["create_time"] = time.Now()
	return f.friendRequest.UpdateByMap(...)
case mgo.IsNotFound(err):
	// 不存在：创建新的
	return f.friendRequest.Create(...)
}
```

注意它把 `handle_result` **重置为 0**。这意味着：如果你被拒绝了，再申请一次，之前的拒绝记录会被覆盖成「未处理」。

这是个**设计选择**：它放弃了「申请历史」，换来「同一对用户只有一条申请记录」的简单模型。

> ⚠️ **可讨论点**：如果 A 申请 B 被拒，A 再申请，原来的拒绝记录就消失了。用户视角看「我的申请历史」，那条「被拒绝」变成了「待处理」。这可能导致体验上的困惑。更严谨的做法是保留历史（每次申请一条新记录），但那样就要处理「同一对用户多条未处理申请」的合并问题。

## 1.3 双方互发申请：一次同意处理两条

一个常见场景：A 申请加 B，B 也申请加 A（两人都在对方的好友申请列表里，都没处理）。

此时 B 点「同意」，会发生什么？

朴素实现：只把「A→B」这条标记为同意，然后建立好友关系。但「B→A」那条还挂在 A 的待处理列表里——A 登录后会看到「B 申请加你好友」，但他们已经是好友了。

OpenIM 的处理（`controller/friend.go:257-269`）：

```go
// 若对方也给我方发过申请，一并标记为同意
fr2, err := f.friendRequest.Take(ctx, friendRequest.ToUserID, friendRequest.FromUserID)
if err == nil && fr2.HandleResult == constant.FriendResponseNotHandle {
	fr2.HandlerUserID = mcontext.GetOpUserID(ctx)
	fr2.HandleResult = constant.FriendResponseAgree    // ← 反向申请也标记同意
	fr2.HandleTime = now
	err = f.friendRequest.Update(ctx, fr2)
} else if err != nil && (!mgo.IsNotFound(err)) {
	return err
}
```

三个细节：
- `Take(ToUserID, FromUserID)` 查的是**反方向**的申请
- 只在 `HandleResult == 0`（未处理）时才改。如果对方那条已经被拒绝过，不动它
- `mgo.IsNotFound(err)` 要显式排除——「反向申请不存在」是正常情况，不该报错

> 📌 这是「双向关系要用一次操作收敛」的典型案例。如果不处理，系统会进入一个**不一致状态**：数据库说他们是好友，但申请列表说有未处理申请。这类状态最终会以「客户端显示错乱」的形式暴露出来。

## 1.4 黑名单：独立于好友关系

很多人以为「拉黑 = 删除好友 + 加入黑名单」。OpenIM 不是这样。

看 `internal/rpc/relation/black.go:63-87` 的 `AddBlack`：它只做三件事——校验、写黑名单表、发通知。**完全没有碰好友表**。

所以拉黑后：
- 好友关系还在（`friend` 表里那两行还在）
- 黑名单表多了一行 `{owner: A, block: B}`

这意味着「A 拉黑 B」和「A 删除好友 B」是两个独立操作：
- **删除好友**：双方的好友列表里都看不到对方了（但历史消息还在）
- **拉黑**：好友关系保留，但对方发来的消息被拒

### 单向阻断

关键在发消息的校验上，`internal/rpc/msg/verify.go:60-66`：

```go
black, err := m.FriendLocalCache.IsBlack(ctx, data.MsgData.SendID, data.MsgData.RecvID)
if err != nil {
	return err
}
if black {
	return servererrs.ErrBlockedByPeer.Wrap()
}
```

`rpccache/friend.go:63-64` 的注释说清楚了参数语义：

```go
// IsBlack 判断 possibleBlackUserID 是否为 selfUserID 的黑名单用户。
func (f *FriendLocalCache) IsBlack(ctx context.Context, possibleBlackUserID, userID string) (val bool, err error)
```

调用是 `IsBlack(SendID, RecvID)`，即「**发送者是不是接收者的黑名单用户**」。

于是：
| 操作 | 结果 |
|---|---|
| B 发给 A（A 拉黑了 B） | `IsBlack(B, A)` = true → **拒绝**，`ErrBlockedByPeer` |
| A 发给 B（A 拉黑了 B） | `IsBlack(A, B)` = false → **允许** |

**拉黑是单向的**：被拉黑的人发不进来，拉黑的人还能发出去。

为什么这样设计？因为「拉黑」的产品语义通常是「我不想收到你的消息」，而不是「我要和你断绝联系」。微信也是这样——你拉黑某人后，你还能给他发消息（虽然对方收不到回执）。

> ⚠️ **易错点**：如果你要实现「双向阻断」，需要在发送校验里加一次反向检查 `IsBlack(RecvID, SendID)`。但这会带来一个新问题：拉黑者发消息给对方，对方如果也拉黑了拉黑者，就变成双向都发不了。产品上要定义清楚。

### 黑名单的缓存穿透

`IsBlack` 走的是 `rpccache` + `localcache` 的两级缓存。为什么这里特别需要缓存？

因为**每一条单聊消息都要检查黑名单**。如果每次都查 Mongo，单聊的 QPS 上限就被 Mongo 卡死了。而黑名单是「极少变更、极高频读」的典型数据，完美适合缓存。

## 1.5 增量同步：一个通用难题

客户端本地有一个好友列表。服务器上的好友关系会变（加了新好友、被删了、备注改了）。客户端怎么保持同步？

### 方案一：每次全量拉取

```
客户端启动 → 拉取全部好友 → 覆盖本地
```

优点：简单，永远不会不一致。
缺点：好友 500 人，每人 200 字节，一次 100KB。启动慢、耗流量。而且 99% 的数据没变，纯浪费。

### 方案二：按时间戳拉取

```
客户端记住「上次同步时间 T」→ 请求「更新时间 > T 的所有好友」
```

这看起来很合理，但有个致命问题：**服务器时间与客户端时间不可比，且时间戳不唯一**。

- 客户端时钟可能不准（用户手动改时间、时区问题）
- 同一毫秒内有多条变更，用 `> T` 会漏掉、用 `>= T` 会重复
- **删除操作没有「更新时间」可查**——记录都被删了，怎么查它什么时候被删的？

第三条是根本性的：**物理删除后无法增量**。要么改成软删除（留一堆垃圾），要么另建变更日志。

### 方案三：版本号 + 变更日志（OpenIM 的选择）

核心思想：**每次变更不直接改数据，而是先写一条日志**。

```
version_log 集合（每个用户一条）：
{
  d_id: "userA",                    // 数据 ID（这里是 ownerUserID）
  version: 128,                     // 当前版本号，单调递增
  logs: [                           // 从这个版本之后发生的变更
    { e_id: "userB", state: 1, version: 126 },   // 1=插入
    { e_id: "userC", state: 2, version: 127 },   // 2=删除
    { e_id: "userD", state: 3, version: 128 }    // 3=更新
  ],
  last_update: ...
}
```

客户端同步流程：

```
1. 客户端带着本地记录的 version（比如 125）请求
2. 服务端读 version_log，取出 version > 125 的所有日志
3. 日志里只有 ID 和操作类型，服务端据此去查实际数据：
   - 插入/更新 → 查这些 ID 的最新数据
   - 删除 → 只需要 ID（数据已经没了）
4. 返回 {version: 128, insert: [...], update: [...], delete: [...]}
5. 客户端按这三类操作更新本地
```

这个方案的精妙之处：

| 问题 | 解法 |
|---|---|
| 删除无法增量 | 日志里记「谁被删了」，不依赖数据本身 |
| 时间戳不唯一 | 用单调递增的版本号，严格有序 |
| 数据量大 | 只返回变更部分 |
| 日志无限增长 | 日志可以截断（客户端版本太老就返回全量） |

**「Full」标志**：如果客户端的版本太老（日志已经被截断），服务端返回 `Full: true` + 全量数据，客户端直接覆盖。这是**增量的兜底**。

> 📌 记忆点：**版本日志 = 先记「发生了什么」，再让别人按图索骥。** 这和数据库的 WAL（预写日志）、Kafka 的 commit log 是同一个思想——**日志是真相，数据是日志的物化视图**。

### OpenIM 的实现细节

`model/version_log.go:30-52`：

```go
type VersionLogTable struct {
	ID         primitive.ObjectID `bson:"_id"`
	DID        string             `bson:"d_id"`     // data id，比如 ownerUserID
	Logs       []VersionLogElem   `bson:"logs"`     // 变更日志数组
	Version    uint               `bson:"version"`  // 当前版本号
	Deleted    uint               `bson:"deleted"`  // 已删除的日志数（用于计算「能不能给增量」）
	LastUpdate time.Time          `bson:"last_update"`
}

type VersionLogElem struct {
	EID        string    `bson:"e_id"`     // element id，比如 friendUserID
	State      int32     `bson:"state"`    // 1=insert 2=delete 3=update
	Version    uint      `bson:"version"`  // 这条日志对应的版本
	LastUpdate time.Time `bson:"last_update"`
}
```

`Deleted` 字段值得注意：它记录「已经删掉了多少条旧日志」。如果客户端版本 < `Version - len(Logs)`，说明需要的日志已经被截断了，只能返回全量。

还有一个特殊 ID：`model/version_log.go:15` 的 `VersionSortChangeID = "____S_O_R_T_I_D____"`。这是一个**哨兵 ID**，用来表达「排序变了」。

为什么排序变化要单独记？因为好友列表是按「昵称首字母」排序的。改了昵称后，排序位置会变，但客户端如果只拿到「userB 的数据更新了」，它不知道要重新排序。所以额外写一条 `EID = ____S_O_R_T_I_D____` 的日志，客户端看到它就知道「需要重排」。

`slices.DeleteFunc` 在 `internal/rpc/relation/sync.go:81-88` 把这个哨兵从日志里剔除，同时把它的版本号记到 `sortVersion`，单独返回给客户端。

## 1.6 通知走消息通道

好友申请、同意、删除这些事件，怎么让客户端知道？

方案一：另开一条推送通道（比如 HTTP 回调、单独的 WebSocket 消息类型）。
方案二：**复用现有的消息系统**——把通知包装成一条「系统消息」发出去。

OpenIM 选方案二（`pkg/notification/msg.go`）。原因：

1. **复用可靠性保障**。消息系统已经有 Kafka、有重试、有离线补偿、有多端同步。另开通道要重新实现一遍这些。
2. **复用客户端渲染逻辑**。客户端已经有一套「收到消息 → 判断类型 → 渲染」的逻辑，通知消息只是多一种 content type。
3. **能落库**。通知消息会存进消息表，用户换设备后还能看到「B 同意了你的好友申请」。

代价是：通知消息会占消息存储，且需要仔细设计「哪些通知要存、哪些只推」——`pkg/notification/msg.go:21-67` 的 `newContentTypeConf` 就是这张表：

```go
constant.FriendApplicationNotification:  conf.FriendApplicationAdded,   // ← 从配置读「是否发送」
constant.MsgRevokeNotification:  {IsSendMsg: false, ReliabilityLevel: constant.ReliableNotificationNoMsg},
constant.HasReadReceipt:         {IsSendMsg: false, ReliabilityLevel: constant.ReliableNotificationNoMsg},
constant.DeleteMsgsNotification: {IsSendMsg: false, ReliabilityLevel: constant.ReliableNotificationNoMsg},
```

注意后三条的 `IsSendMsg: false`——撤回、已读回执、删除消息这三种**不发成消息**（只推送）。因为它们本身就是对消息的操作，存成消息会形成「消息的消息」无限套娃。

### 会话类型怎么定

`msg.go:69-113` 的 `newSessionTypeConf` 决定每种通知落在哪个会话里：

```go
constant.JoinGroupApplicationNotification: constant.SingleChatType,   // 入群申请 → 单聊
constant.GroupCreatedNotification:         constant.ReadGroupChatType, // 建群 → 群聊
constant.FriendApplicationNotification:    constant.SingleChatType,    // 好友申请 → 单聊
```

一个规律：**「关于群的事」发到群会话里，「关于人的事」发到单聊里**。

例外是「入群申请」——它发给群主/管理员个人，不是发到群里（不然全群都看到谁在申请），所以是 `SingleChatType`。

## 1.7 缓存的「延迟删除链」

好友关系有一堆缓存：
- `GetFriendIDs(ownerUserID)`：我的好友 ID 列表
- `GetFriend(ownerID, friendID)`：某个好友的详情（含备注）
- `GetMaxFriendVersion(ownerUserID)`：我的版本号
- `DelFriendIDs` / `DelFriends` / `DelMaxFriendVersion`：对应的删除

关系变更时，要删的缓存是**一组**，不是一个。OpenIM 的做法在 `controller/friend.go:194-204`：

```go
err = f.friend.Create(ctx, friends)
if err != nil {
	return err
}
// 写库成功后清理相关缓存
cache = cache.DelFriendIDs(ownerUserID).DelMaxFriendVersion(ownerUserID)
if len(newMyFriendIDs) > 0 {
	cache = cache.DelFriendIDs(newMyFriendIDs...)
	cache = cache.DelFriends(ownerUserID, newMyFriendIDs).DelMaxFriendVersion(newMyFriendIDs...)
}
if len(newMyOwnerIDs) > 0 {
	cache = cache.DelFriendIDs(newMyOwnerIDs...)
	cache = cache.DelOwner(ownerUserID, newMyOwnerIDs).DelMaxFriendVersion(newMyOwnerIDs...)
}
return cache.ChainExecDel(ctx)
```

三个要点：

**（1）`CloneFriendCache` 先克隆**（`:149`）。因为要在一个事务里累积多个删除操作，如果直接改原对象，事务失败时缓存已经被标记删除了。

**（2）链式累积，最后一次性执行**。`DelFriendIDs` 返回的还是 cache 对象，可以继续 `.DelXXX()`。最后 `ChainExecDel(ctx)` 一次性发出所有 DEL 命令（大概率是 pipeline）。

**（3）删除范围要覆盖「双方」**。
- `newMyFriendIDs`：我新加的好友 → 要删**我**的列表缓存，和**他们**的列表缓存
- `newMyOwnerIDs`：把我加为好友的人 → 同样要删双方的

漏掉任何一边，就会出现「A 看到 B 是好友，B 看不到 A」的不一致。

> 📌 **面试点**：为什么不在写库前删缓存？
> 因为「删缓存 → 写库」之间如果有读请求，会把**旧数据**回填进缓存，导致缓存里长期是旧值。正确顺序是「先写库、再删缓存」（Cache-Aside 的标准写法）。OpenIM 就是这么做的——`Create` 成功后才删。

注意三张独立的表：`friend`、`friend_request`、`black`。它们没有合并成一张「关系表 + 类型字段」，因为：

- 生命周期不同（好友长期存在、申请会处理完、黑名单独立）
- 索引不同

**「一个业务概念一张表」比「一张大表加类型字段」更清晰**，这是文档型数据库的常见取舍。

`memamq.NewMemoryQueue(16, 1024*1024)` 是**通知发送的异步队列**：16 个 worker 并发发消息，缓冲 100 万。为什么要异步？

因为发通知需要调 `msg.SendMsg`（一次 gRPC），如果同步做，`ApplyToAddFriend` 的响应时间会翻倍。而通知失败不该影响主流程（申请已经写库成功了）。

> ⚠️ 但这里的缓冲 100 万条是**内存**。如果 worker 堵住（比如 msg 服务挂了），队列会一直涨到 100 万才阻塞。每条通知消息可能有几 KB，100 万条就是几个 GB —— **有内存溢出风险**。对比 `internal/push` 用的 `NewMemoryQueue(512, 1024*16)`（16K 缓冲），这里明显偏大。

## 2.2 一条好友申请的全过程

### 2.2.1 `ApplyToAddFriend`

`internal/rpc/relation/friend.go:123-151`，五步：

```go
func (s *friendServer) ApplyToAddFriend(ctx, req) {
	// ① 授权：只能以自己的名义申请
	if err := authverify.CheckAccess(ctx, req.FromUserID); err != nil {
		return nil, err
	}

	// ② 不能加自己
	if req.ToUserID == req.FromUserID {
		return nil, servererrs.ErrCanNotAddYourself.WrapMsg("req.ToUserID", req.ToUserID)
	}

	// ③ 前置回调（可拒绝，也可返回 ErrCallbackContinue 表示"我拒绝但流程继续"）
	if err = s.webhookBeforeAddFriend(ctx, ...); err != nil && err != servererrs.ErrCallbackContinue {
		return nil, err
	}

	// ④ 两个人必须都存在
	if err := s.userClient.CheckUser(ctx, []string{req.ToUserID, req.FromUserID}); err != nil {
		return nil, err
	}

	// ⑤ 已经是好友就直接拒
	in1, in2, err := s.db.CheckIn(ctx, req.FromUserID, req.ToUserID)
	if in1 && in2 {
		return nil, servererrs.ErrRelationshipAlready.WrapMsg("already friends has f")
	}

	// ⑥ 写申请 + 发通知 + 后置回调
	if err = s.db.AddFriendRequest(ctx, req.FromUserID, req.ToUserID, req.ReqMsg, req.Ex); err != nil {
		return nil, err
	}
	s.notificationSender.FriendApplicationAddNotification(ctx, req)
	s.webhookAfterAddFriend(ctx, ...)
}
```

**第 ⑤ 步的 `in1 && in2` 值得琢磨**。为什么不写成 `in1 || in2`？

因为「好友关系」要求**双向**。如果只有 A→B 的记录，没有 B→A，那他们**不算好友**（这是 `BecomeFriends` 里「补齐另一个方向」的动机）。

现实中出现单向记录的原因：历史数据、或者某个写操作部分失败（没有事务的老代码）。用 `&&` 判断的意思是「只有真正双向才算好友」，单向的会允许继续申请——然后 `BecomeFriends` 会补齐缺失的方向。

**第 ③ 步的 `ErrCallbackContinue`** 是个有意思的约定。webhook 可以返回三种结果：

| 返回 | 含义 |
|---|---|
| `nil` | 通过，继续 |
| `ErrCallbackContinue` | **拒绝但允许流程继续**（比如「我记录一下，但我不阻止」） |
| 其他 error | 拒绝且中断 |

这是「回调方需要区分『否决』和『放行』之外的第三态」的需求。在企业集成里很常见：审计系统想记录每一次申请，但它没有否决权。

### 2.2.3 通知的底层：变成一条消息

`pkg/notification/msg.go:185-240` 的 `send`，是「通知 → 消息」的转换器：

```go
func (s *NotificationSender) send(ctx context.Context, sendID, recvID string, contentType, sessionType int32, m proto.Message, opts ...NotificationOptions) {
	ctx = context.WithoutCancel(ctx)                        // ① 脱离父 context 的取消
	ctx, cancel := context.WithTimeout(ctx, time.Second*5)  // ② 5 秒超时
	defer cancel()

	n := sdkws.NotificationElem{Detail: jsonutil.StructToJsonString(m)}   // ③ 包装成 NotificationElem
	content, _ := json.Marshal(&n)

	msg.SendID = sendID
	msg.RecvID = recvID
	msg.Content = content
	msg.MsgFrom = constant.SysMsgType                       // ④ 标记为系统消息
	msg.ContentType = contentType
	msg.SessionType = sessionType
	if msg.SessionType == constant.ReadGroupChatType {
		msg.GroupID = recvID                                // ⑤ 群聊时 RecvID 就是 GroupID
	}
	msg.Options = config.GetOptionsByNotification(optionsConfig, notificationOpt.SendMessage)  // ⑥ 从配置读「存不存/推不推」
	_, err = s.sendMsg(ctx, &req)                           // ⑦ 走 msg 服务发送
}
```

几个关键点：

**（1）`context.WithoutCancel`（`:186`）**。这个函数是 Go 1.21 才加的。作用是「继承父 context 的所有值，但**不继承取消信号**」。

为什么需要？因为调用方可能是一个 HTTP 请求，用户断连了 context 就被 cancel。但通知是在**队列的 goroutine 里异步执行**的，此时父请求可能已经结束。如果不脱离，所有通知都会因为「context canceled」而失败。

这是个**异步任务必须处理的问题**：异步执行时，原始的请求上下文已经作废了，但 `userID`、`operationID` 这些值还要保留。`WithoutCancel` 正好是这个语义。

**（2）`msg.MsgFrom = constant.SysMsgType`（`:215`）**。系统消息类型，让客户端知道「这不是真人发的」。

**（3）`msg.ClientMsgID = idutil.GetMsgIDByMD5(sendID)`（`:222`）**。用发送者 ID 的 MD5 当 ClientMsgID。

这里有个**潜在问题**：如果同一个发送者在短时间内发多条通知，ClientMsgID 会重复。而 ClientMsgID 是幂等键（见 10 篇），重复会导致后一条被当成重复消息丢掉。

实际影响：`GetMsgIDByMD5` 可能内部加了随机/时间因素。需要看 `idutil` 的实现才能确定。📌 **待验证**。

**（4）`optionsConfig` 从配置读（`:223`）**。每种通知类型的「是否落库、是否推送」都在 `config/notification.yml` 里配。这给了运营极大的灵活性——比如「好友申请不推送但落库」「群公告既推送也落库」。

## 2.3 同意申请：一次事务里做四件事

`internal/rpc/relation/friend.go:189-222` 的 `RespondFriendApply` 是入口，同意时调 `s.db.AgreeFriendRequest`。

`controller/friend.go:239-310`（核心片段）：

```go
func (f *friendDatabase) AgreeFriendRequest(ctx context.Context, friendRequest *model.FriendRequest) (err error) {
	return f.tx.Transaction(ctx, func(ctx context.Context) error {
		now := time.Now()

		// ① 取出申请，检查是否已处理
		fr, err := f.friendRequest.Take(ctx, friendRequest.FromUserID, friendRequest.ToUserID)
		if err != nil {
			return err
		}
		if fr.HandleResult != 0 {
			return errs.ErrArgs.WrapMsg("the friend request has been processed")
		}

		// ② 更新正向申请为「同意」
		friendRequest.HandlerUserID = mcontext.GetOpUserID(ctx)
		friendRequest.HandleResult = constant.FriendResponseAgree
		friendRequest.HandleTime = now
		if err = f.friendRequest.Update(ctx, friendRequest); err != nil {
			return err
		}

		// ③ 反向申请也标记为同意（如果存在且未处理）
		fr2, err := f.friendRequest.Take(ctx, friendRequest.ToUserID, friendRequest.FromUserID)
		if err == nil && fr2.HandleResult == constant.FriendResponseNotHandle {
			fr2.HandlerUserID = mcontext.GetOpUserID(ctx)
			fr2.HandleResult = constant.FriendResponseAgree
			fr2.HandleTime = now
			err = f.friendRequest.Update(ctx, fr2)
			if err != nil {
				return err
			}
		} else if err != nil && (!mgo.IsNotFound(err)) {
			return err
		}

		// ④ 补齐双向好友关系
		exists, err := f.friend.FindUserState(ctx, friendRequest.FromUserID, friendRequest.ToUserID)
		existsMap := datautil.SliceSet(datautil.Slice(exists, func(friend *model.Friend) [2]string {
			return [...]string{friend.OwnerUserID, friend.FriendUserID}
		}))

		var adds []*model.Friend
		// 缺「B→A」就补
		if _, ok := existsMap[[...]string{friendRequest.ToUserID, friendRequest.FromUserID}]; !ok {
			adds = append(adds, &model.Friend{
				OwnerUserID:    friendRequest.ToUserID,     // 同意者
				FriendUserID:   friendRequest.FromUserID,   // 申请者
				AddSource:      int32(constant.BecomeFriendByApply),
				OperatorUserID: friendRequest.FromUserID,
			})
		}
		// 缺「A→B」就补
		if _, ok := existsMap[[...]string{friendRequest.FromUserID, friendRequest.ToUserID}]; !ok {
			adds = append(adds, &model.Friend{...})
		}

		if len(adds) > 0 {
			if err := f.friend.Create(ctx, adds); err != nil {
				return err
			}
		}
		// 后面还有缓存清理
	})
}
```

这段代码有四个设计要点：

**要点一：整个流程在一个事务里。**

「更新申请状态」和「插入好友关系」必须原子。否则可能出现：申请标记为同意，但好友没建成 → 用户看到「已同意」但好友列表里没有。

MongoDB 4.0+ 支持多文档事务（副本集模式）。OpenIM 的 `mgocli.GetTx()` 就是开启事务的封装。**这也意味着 Mongo 必须部署成副本集**，单机模式（standalone）不支持事务。这是个部署上的硬要求，`docker-compose.yml` 里的 mongo 配置应该能看出来。📌 **待验证**：检查 compose 里 mongo 是否有 `--replSet` 参数。

**要点二：用 `FindUserState` 先查再补，而不是直接插入。**

为什么不直接 `Create` 两条？因为可能已经有一条（用户先单向加了好友，或者历史数据）。直接插会撞唯一索引（如果建了）或产生重复记录。

`existsMap` 用 `[2]string` 作为 key 来表达「有向边」——这是个很巧的写法：`[2]string{A, B}` 和 `[2]string{B, A}` 是不同的 key，天然区分方向。Go 的数组是可比较类型，可以直接当 map key。

**要点三：`HandleResult != 0` 就报错。**

这保证了幂等性。「同意」操作重复调用会失败，而不是重复插入好友。这是**乐观并发控制**——不用锁，用状态字段做守卫。

但如果两个请求**同时**进来（都读到 `HandleResult == 0`），都会通过检查，然后都去 `Update` 和 `Create`。`Update` 可能都成功（后写的覆盖），`Create` 就会插入重复记录。

**这是一个真实的并发窗口**。要彻底解决需要用 `FindOneAndUpdate` 的原子操作（`WHERE handle_result = 0`），或者加唯一索引让第二条 `Create` 失败。

**要点四：`AddSource` 记录来源。**

`constant.BecomeFriendByApply` vs `BecomeFriendByImport`（`friend.go:173` 的批量导入）。这个字段用于运营分析（多少好友是通过申请加的、多少是导入的），也可能用于风控（短时间内大量导入 = 可疑）。

## 2.4 批量建好友：`BecomeFriends`

`controller/friend.go:147-206`，这是「导入好友」和「同意申请」共用的底层函数。它的逻辑比 `AgreeFriendRequest` 的 ④ 更完整：

```go
func (f *friendDatabase) BecomeFriends(ctx context.Context, ownerUserID string, friendUserIDs []string, addSource int32) (err error) {
	return f.tx.Transaction(ctx, func(ctx context.Context) error {
		cache := f.cache.CloneFriendCache()                         // ① 克隆缓存对象

		myFriends, _ := f.friend.FindFriends(ctx, ownerUserID, friendUserIDs)       // 我已有的
		addOwners, _ := f.friend.FindReversalFriends(ctx, ownerUserID, friendUserIDs) // 反向已有的

		opUserID := mcontext.GetOpUserID(ctx)
		friends := make([]*model.Friend, 0, len(friendUserIDs)*2)    // ② 预估容量 *2

		myFriendsSet := ...   // set of friendUserID
		addOwnersSet := ...   // set of ownerUserID

		var newMyFriendIDs, newMyOwnerIDs []string
		for _, userID := range friendUserIDs {
			if ownerUserID == userID {
				continue                                             // ③ 跳过自己
			}
			// 补齐「我 → 好友」
			if _, ok := myFriendsSet[userID]; !ok {
				myFriendsSet[userID] = struct{}{}
				newMyFriendIDs = append(newMyFriendIDs, userID)
				friends = append(friends, &model.Friend{OwnerUserID: ownerUserID, FriendUserID: userID, ...})
			}
			// 补齐「好友 → 我」
			if _, ok := addOwnersSet[userID]; !ok {
				addOwnersSet[userID] = struct{}{}
				newMyOwnerIDs = append(newMyOwnerIDs, userID)
				friends = append(friends, &model.Friend{OwnerUserID: userID, FriendUserID: ownerUserID, ...})
			}
		}
		if len(friends) == 0 {
			return nil                                               // ④ 没什么可加，直接返回
		}
		if err = f.friend.Create(ctx, friends); err != nil {
			return err
		}
		// ⑤ 缓存清理（前文 1.7 已讲）
		return cache.ChainExecDel(ctx)
	})
}
```

**要点：`FindFriends` 和 `FindReversalFriends` 是两个不同的查询。**

- `FindFriends(owner, friendIDs)`：查「owner 的好友列表里，哪些在 friendIDs 中」→ 得到 `myFriends`
- `FindReversalFriends(owner, friendIDs)`：查「friendIDs 这些人里，哪些把 owner 当好友」→ 得到 `addOwners`

只有分成两个查询，才能分别判断两个方向是否已存在。如果只查一个 `OR` 条件的查询，无法区分方向。

**`friends` 的容量预估 `len(friendUserIDs)*2`** 是个小优化：最坏情况每人两个方向都要插，正好 2 倍。避免了 slice 扩容时的多次拷贝。

## 2.5 删除好友：为什么是单向的

`internal/rpc/relation/friend.go:225-243`：

```go
func (s *friendServer) DeleteFriend(ctx context.Context, req *relation.DeleteFriendReq) (resp *relation.DeleteFriendResp, err error) {
	if err := authverify.CheckAccess(ctx, req.OwnerUserID); err != nil {
		return nil, err
	}
	_, err = s.db.FindFriendsWithError(ctx, req.OwnerUserID, []string{req.FriendUserID})
	if err != nil {
		return nil, err       // 不是好友就报错
	}
	if err := s.db.Delete(ctx, req.OwnerUserID, []string{req.FriendUserID}); err != nil {
		return nil, err
	}
	s.notificationSender.FriendDeletedNotification(ctx, req)
}
```

而 `controller/friend.go:312` 的 `Delete`：

```go
func (f *friendDatabase) Delete(ctx context.Context, ownerUserID string, friendUserIDs []string) (err error) {
	// 只删 owner_user_id = ownerUserID AND friend_user_id IN (friendUserIDs) 的记录
}
```

**只删一个方向！** A 删除 B 后，B 那边「A 是我的好友」这条记录还在。

这是个**故意的设计**，对应真实产品语义：**单向删除**。A 删了 B，A 的列表里没有 B 了；但 B 不知道，B 的列表里还有 A，B 还能给 A 发消息（如果 A 没拉黑 B）。

等等——那 A 会收到 B 的消息吗？

会。因为发消息的校验只看黑名单（`verify.go:60`），不看好友关系（除非开了 `FriendVerify`）。所以「删除好友」只是「从我的列表里移除」，不阻断通信。

这就是微信的行为：你删了对方，对方还能给你发消息，你也能收到（除非拉黑）。而 QQ 的「删除好友」是双向的——对方列表里也没你了。

OpenIM 选了微信的语义。为什么？

因为**双向删除在分布式下很难做好**。你要保证两条记录都被删，如果第二条失败，关系就处于「一半有一半没有」的状态。而单向删除每次只操作一条记录，天然原子。

> 📌 **面试点**：这是个很好的「业务语义决定技术实现」的例子。如果产品要求双向删除，就必须用事务或最终一致补偿；如果产品接受单向，实现就简单得多。OpenIM 选择了简单。

**那 B 什么时候会发现自己被删了？** 下次 B 试图发消息给 A 时，如果开了 `FriendVerify`（`verify.go:67`），会返回 `ErrNotPeersFriend`。客户端可以据此提示「你们已经不是好友」。

如果没开 `FriendVerify`（默认），B 永远不知道，直到某天主动拉好友列表发现 A 不在了。

## 2.6 黑名单：`AddBlack` 的克制

`internal/rpc/relation/black.go:63-87`，只有 25 行：

```go
func (s *friendServer) AddBlack(ctx context.Context, req *relation.AddBlackReq) (resp *relation.AddBlackResp, err error) {
	if err := authverify.CheckAccess(ctx, req.OwnerUserID); err != nil {
		return nil, err
	}
	if err := s.webhookBeforeAddBlack(ctx, &s.config.WebhooksConfig.BeforeAddBlack, req); err != nil {
		return nil, err     // 注意：这里没有 ErrCallbackContinue 的例外
	}

```

对比 `ApplyToAddFriend`（2.2.1），有两个差异值得注意：

**差异一：没有 `ErrCallbackContinue` 的例外。**
`ApplyToAddFriend:131` 写的是 `if err != nil && err != servererrs.ErrCallbackContinue`，而这里只有 `if err != nil`。意思是：**黑名单的 webhook 没有「记录但放行」的第三态**，只能通过或拒绝。

为什么？可能因为拉黑是敏感操作，不该被外部系统干扰。也可能是遗漏（一致性上的小瑕疵）。

**差异二：没有检查「是否已拉黑」。**
如果 A 重复拉黑 B 两次，会插入两条记录（除非有唯一索引）。`blackDatabase.Create` 内部用的是什么？📌 **待验证**：需要看 `mgo/black.go` 的 `Create` 是否用了 upsert。

如果没有唯一索引也没有 upsert，重复拉黑会产生脏数据，`GetPaginationBlacks` 会返回重复项。

**最关键的是：它没有删好友。**

## 2.7 批量删除的入口：`DeleteOutdatedData`（第三方服务里的）

这个不属于好友，但值得提一句：`internal/rpc/third/s3.go:277` 的 `DeleteOutdatedData` 里有一个「引用计数」的清理：

```go
count, err := t.s3dataBase.GetKeyCount(ctx, engine, obj.Key)
if count == 0 {
	if err := t.s3.DeleteObject(ctx, obj.Key); err != nil { ... }
}
```

`GetKeyCount` 查的是「这个 S3 key 还被多少个 Object 记录引用」。只有引用数为 0 才真删。

这和好友关系里的一个道理：**删除一个「引用」不等于删除「被引用的实体」**。好友表、黑名单表、消息表、object 表，都是不同的「视图」，每个视图独立管理，不互相删除。

## 2.8 增量同步的实现

### 2.8.1 三个入口

`internal/rpc/relation/sync.go`：

| 函数 | 行号 | 用途 |
|---|---|---|
| `NotificationUserInfoUpdate` | 17-40 | 用户资料变了，更新所有好友的版本日志 |
| `GetFullFriendUserIDs` | 42-64 | 全量拉好友 ID（带 hash 快判） |
| `GetIncrementalFriends` | 66-108 | 增量拉取（版本日志） |

### 2.8.2 全量入口的「hash 快判」

`sync.go:46-63`：

```go
vl, _ := s.db.FindMaxFriendVersionCache(ctx, req.UserID)
userIDs, _ := s.db.FindFriendUserIDs(ctx, req.UserID)
idHash := hashutil.IdHash(userIDs)
if req.IdHash == idHash {
	userIDs = nil                  // ← hash 相同，说明客户端已经是最新的
}
return &relation.GetFullFriendUserIDsResp{
	Version:   uint64(vl.Version),
	VersionID: vl.ID.Hex(),
	Equal:     req.IdHash == idHash,
	UserIDs:   userIDs,
}
```

客户端带上「上次拿到的好友 ID 列表的 hash」。服务端算一遍当前的 hash，相同就返回 `Equal: true` + 空的 `UserIDs`。

**为什么要有这个？** 因为客户端启动时经常需要「确认本地数据是不是最新的」。如果每次都传全量 ID 列表，500 个好友就是几十 KB。用 hash 快判，正常情况下响应只有几十字节。

`hashutil.IdHash` 大概率是「排序后拼接再哈希」。**排序是关键**——好友 ID 的顺序在数据库里不保证稳定，不排序的话每次算出来的 hash 都不一样。📌 **待验证**：看 `pkg/util/hashutil` 的实现。

### 2.8.3 增量入口：`incrversion.Option`

`sync.go:70-107`：

```go
opt := incrversion.Option[*sdkws.FriendInfo, relation.GetIncrementalFriendsResp]{
	Ctx:           ctx,
	VersionKey:    req.UserID,           // 谁的版本
	VersionID:     req.VersionID,        // 客户端记录的 version_log 文档 ID
	VersionNumber: req.Version,          // 客户端记录的版本号
	Version: func(ctx, ownerUserID, version, limit) (*model.VersionLog, error) {
		vl, err := s.db.FindFriendIncrVersion(ctx, ownerUserID, version, limit)
		vl.Logs = slices.DeleteFunc(vl.Logs, func(elem model.VersionLogElem) bool {
			if elem.EID == model.VersionSortChangeID {      // 剔除哨兵
				vl.LogLen--
				sortVersion = uint64(elem.Version)
				return true
			}
			return false
		})
		return vl, nil
	},
	CacheMaxVersion: s.db.FindMaxFriendVersionCache,
	Find: func(ctx context.Context, ids []string) ([]*sdkws.FriendInfo, error) {
		return s.getFriend(ctx, req.UserID, ids)            // 按 ID 查实际数据
	},
	Resp: func(version, deleteIds, insertList, updateList, full) *relation.GetIncrementalFriendsResp {
		return &relation.GetIncrementalFriendsResp{
			VersionID:   version.ID.Hex(),
			Version:     uint64(version.Version),
			Full:        full,          // ← 日志被截断时为 true
			Delete:      deleteIds,
			Insert:      insertList,
			Update:      updateList,
			SortVersion: sortVersion,
		}
	},
}
return opt.Build()
```

这是一个**泛型 + 函数式**的设计（`incrversion.Option[A, B]`），把「增量同步」这件通用事抽象出来，realtion / group / conversation 三个服务共用。

`Option` 的四个函数字段各司其职：

| 字段 | 职责 |
|---|---|
| `Version` | 查版本日志（并做业务相关的裁剪，比如剔除哨兵） |
| `CacheMaxVersion` | 查最大版本（用于判断「客户端版本超了」） |
| `Find` | 按 ID 查实际数据（不同服务查不同的表） |
| `Resp` | 组装响应（不同服务的响应结构不同） |

**这是「策略模式 + 泛型」的教科书用法**：算法骨架（怎么读日志、怎么分类、怎么判断 Full）在 `Option.Build()` 里写一遍，可变部分用函数注入。

### 2.8.4 `NotFound` 的语义

`Find` 函数返回的列表可能比 `ids` 少——因为日志里记的 ID 对应的数据可能已经被删了（比如「插入」日志写完，数据还没插入，就被删了）。

这种情况下，`Build()` 应该把「查不到的 ID」当成什么？当成删除，还是当成不存在？

OpenIM 的处理在 `incrversion` 的实现里。这是一个**幂等性**的关键点：如果「查不到」被当成「不存在」，客户端会保留旧数据（因为没收到 delete）；如果当成「删除」，客户端会删掉——两种都有可能出错。

📌 **待验证**：读 `internal/rpc/incrversion/*.go` 看 `Build()` 的具体处理。

## 2.9 好友版本日志是怎么写的

写日志的地方在 `controller/friend.go:396`：

```go
func (f *friendDatabase) OwnerIncrVersion(ctx context.Context, ownerUserID string, friendUserIDs []string, state int32) error
```

而 `sync.go:27` 的调用：

```go
if err := s.db.OwnerIncrVersion(noCancelCtx, userID, friendUserIDs, model.VersionStateUpdate); err != nil {
```

注意这里叫 `OwnerIncrVersion`——**「给 owner 的版本号 +1」**。语义是：`ownerUserID` 的好友列表发生变化，需要记录「哪些 friendUserID 变了、怎么变的」。

实现细节（`pkg/common/storage/database/mgo/version_log.go` 或类似文件）大致是：
1. 用 `$inc` 把 `version` 加 1，拿到新版本号
2. 把 `{e_id, state, version}` push 进 `logs` 数组
3. 如果 `logs` 超过某个长度，删掉最前面的（同时 `deleted` 加 N）

**这里也是「号段」思想**：`$inc` 是原子的，多个并发写入不会拿到相同的 version。和 12 篇讲的 seq 分配是同一个套路，只是简单得多（不需要预分配号段，因为版本号不需要稠密，也不在热点路径上）。

## 2.10 关系变更时谁被通知

把通知链梳理一遍，这是理解「业务事件」的最好材料：

| 操作 | 通知 | 发给谁 | 会话类型 |
|---|---|---|---|
| 申请加好友 | `FriendApplicationNotification` | **接收方**（ToUserID） | 单聊 |
| 同意申请 | `FriendApplicationApprovedNotification` | **申请方**（FromUserID） | 单聊 |
| 拒绝申请 | `FriendApplicationRejectedNotification` | **申请方** | 单聊 |
| 删除好友 | `FriendDeletedNotification` | **被删方**（FriendUserID） | 单聊 |
| 设置备注 | `FriendRemarkSetNotification` | 自己（同步多端） | 单聊 |
| 加黑名单 | `BlackAddedNotification` | 自己（同步多端） | 单聊 |
| 用户资料变更 | `FriendInfoUpdatedNotification` | **每个好友** | 单聊 |

**「发给谁」这一列是最容易搞错的**。看 `notification.go:155`（申请）和 `:176`（同意）：

```go
// 申请：from → to
f.Notification(ctx, req.FromUserID, req.ToUserID, constant.FriendApplicationNotification, &tips)

// 同意：to → from   ← 方向反了
f.Notification(ctx, req.ToUserID, req.FromUserID, constant.FriendApplicationApprovedNotification, &tips)
```

`Notification(ctx, sendID, recvID, ...)` 的第二个参数是**发送者**、第三个是**接收者**。

- 申请时：申请人是「发送者」，被申请人是「接收者」→ 通知落在「申请人和被申请人之间的会话」里，被申请人看到
- 同意时：**同意人变成发送者**，申请人变成接收者 → 通知落在**同一个会话**里，申请人看到

**这保证了两个事件落在同一个单聊会话里**。这是关键——如果方向搞反，申请通知和同意通知会落在两个不同的会话（`si_A_B` 和 `si_B_A` 是同一个会话，因为会话 ID 是排序拼接的；但如果 sendID/recvID 反了，`GetConversationIDBySessionType` 内部排序后还是同一个）。

实际上 `si_` 前缀的会话 ID 是「排序后拼接」，所以 A→B 和 B→A 是同一个会话。但 `MsgData.SendID` / `RecvID` 不同，客户端渲染时会显示不同的「谁发的」。

- 申请通知的发送者是申请人 → 客户端显示「A 申请加你好友」
- 同意通知的发送者是同意人 → 客户端显示「B 同意了你的好友申请」

**方向虽然反了，但语义正好对**。这是设计得好的地方。

## 2.11 一个容易忽略的点：好友关系不参与消息路由

回顾一下 15 篇讲的推送：消息推送的目标是「接收者的所有在线设备」，和「是不是好友」无关。

好友关系只影响两件事：
1. **发送校验**（如果开了 `FriendVerify`）
2. **客户端的联系人列表**

这意味着：即使 A 和 B 不是好友，只要知道对方的 userID，A 就能给 B 发单聊消息（`FriendVerify` 默认关闭）。

**这是 OpenIM 作为「基础设施」的定位决定的**：它不该假设「只能给好友发消息」。有些产品允许「陌生人私信」，有些不允许。OpenIM 用配置项 `friendVerify` 把这个决定权交给使用方。

> ⚠️ **安全提示**：如果直接部署 OpenIM 而不开 `friendVerify`，你的系统就是一个「只要知道 userID 就能给任何人发消息」的系统。这在社交产品里可能是个漏洞（骚扰），在客服系统里却是必须的（用户要能主动联系客服）。

# 第四部分 · 自测题

**Q1** 为什么好友关系要存两份？如果只存一份会有什么问题？

<details>
<summary>答案</summary>

两个原因：

1. **方向属性**：备注、置顶、添加来源都是「我对你的」而不是「我们共同的」。A 给 B 备注「老王」，B 那边不该看到这个备注。一份记录存不下两个方向的不同属性。

2. **查询性能**：最高频的查询是「拉我的好友列表」，存两份可以 `WHERE owner_user_id = 'A'` 走单索引。存一份要用 `WHERE (owner=A AND friend=B) OR (owner=B AND friend=A)`，在 Mongo 里 `$or` 性能明显差。

代价是写入放大 2 倍，需要事务保证两行一致。
</details>

**Q2** 好友申请为什么用「改状态」而不是「删除记录」？重复申请时怎么处理？

<details>
<summary>答案</summary>

不删记录的原因：客户端要展示申请历史；需要判断「是不是刚申请过」；审计需求。

重复申请时（`controller/friend.go:121-144`）会把现有记录的 `handle_result` 重置为 0、更新 `req_msg` 和 `create_time`。这意味着**之前的拒绝记录会被覆盖**——这是一个取舍：放弃了申请历史，换来了「同一对用户只有一条记录」的简单模型。
</details>

**Q3** 双方互发申请，一次同意怎么处理两条？

<details>
<summary>答案</summary>

`AgreeFriendRequest` 在标记正向申请为同意后，会 `Take(ToUserID, FromUserID)` 查反向申请。如果存在且 `HandleResult == 0`（未处理），也标记为同意。`mgo.IsNotFound` 要显式排除，因为「反向申请不存在」是正常情况。

不处理的话会进入不一致状态：数据库说是好友，但反向申请还挂在待处理列表里。
</details>

**Q4** 拉黑为什么不删除好友关系？被拉黑的人发消息会怎样？拉黑的人发消息又会怎样？

<details>
<summary>答案</summary>

不删是因为「拉黑」的产品语义是「我不想收到你的消息」，不是「断绝关系」。用户可以随时取消拉黑，好友关系还在，不用重新加。

发消息校验在 `verify.go:60`：`IsBlack(SendID, RecvID)` 判断的是「发送者是否在接收者的黑名单里」。
- B 发给 A（A 拉黑 B）：`IsBlack(B, A)` = true → 拒绝，`ErrBlockedByPeer`
- A 发给 B：`IsBlack(A, B)` = false → 允许

所以拉黑是**单向阻断**。
</details>

**Q5** 增量同步为什么不能用时间戳？OpenIM 用什么方案？

<details>
<summary>答案</summary>

时间戳的三个问题：
1. 客户端时钟不可信
2. 同一毫秒多条变更，`> T` 会漏、`>= T` 会重
3. **删除操作没有时间戳可查**——记录被物理删了，无法「按更新时间查」

OpenIM 用「版本号 + 变更日志」（`model/version_log.go`）：每次变更先写一条日志（`{e_id, state, version}`），`version` 用 `$inc` 保证单调递增。客户端带本地 version 请求，服务端返回 `version > 本地` 的日志，再按日志里的 ID 去查实际数据。

日志过长会被截断，此时返回 `Full: true` + 全量数据兜底。
</details>

**Q6** `VersionSortChangeID = "____S_O_R_T_I_D____"` 是干什么的？

<details>
<summary>答案</summary>

是一个**哨兵 ID**，用来表达「排序变了」。

好友列表按昵称首字母排序。改了昵称后，如果只告诉客户端「userB 的数据更新了」，客户端不知道要重新排序。所以额外写一条 `EID = ____S_O_R_T_I_D____` 的日志。

`sync.go:81-88` 用 `slices.DeleteFunc` 把它从日志数组里剔除（因为它不是一个真实的好友 ID，不能拿去查数据），同时把它的版本号记到 `sortVersion`，单独返回给客户端。
</details>

**Q7** `BecomeFriends` 里为什么要同时调 `FindFriends` 和 `FindReversalFriends`？

<details>
<summary>答案</summary>

因为要分别判断两个方向是否已存在。

- `FindFriends(owner, ids)`：查「owner 的好友列表里有没有这些人」→ 得到「我→好友」方向已有的
- `FindReversalFriends(owner, ids)`：查「这些人里有没有把 owner 当好友的」→ 得到「好友→我」方向已有的

只查一个 `OR` 条件无法区分方向，也就无法决定「缺哪个方向就补哪个」。分开查之后，用两个 set 分别判断，缺则补。
</details>

**Q8** 为什么删除好友是单向的？如果产品要求双向删除，技术上要怎么做？

<details>
<summary>答案</summary>

单向是产品语义的选择（对齐微信）。技术上，单向删除每次只操作一条记录，天然原子，不需要事务。

双向删除的做法：在一个事务里删两条记录（`A→B` 和 `B→A`）。Mongo 需要副本集支持事务。如果不能用事务，就要用「先删一条、记录补偿任务、异步删另一条」的最终一致方案，或者把两条记录放在同一个文档里（用数组），用单文档原子更新保证。

OpenIM 选单向，本质是「简单优先」。
</details>

**Q9** 好友变更通知为什么复用「发消息」而不是另开通道？

<details>
<summary>答案</summary>

复用消息系统的好处：
1. 白拿可靠性（Kafka、重试、离线补偿、多端同步）
2. 白拿客户端渲染逻辑（已有「收消息→判断类型→渲染」的流程）
3. 能落库，换设备后还能看到

代价：占消息存储，需要设计「哪些通知存、哪些只推」（`newContentTypeConf` 里 `IsSendMsg: false` 的就是只推不存）。

`pkg/notification/msg.go:186` 的 `context.WithoutCancel` 是关键——通知在队列的 goroutine 里异步执行，父请求的 context 可能已经取消，必须脱离取消信号但保留值。
</details>

**Q10** `sender` 和 `receiver` 在「申请」和「同意」两个通知里为什么反了？

<details>
<summary>答案</summary>

`Notification(ctx, sendID, recvID, ...)` 的 sendID 决定「客户端显示谁发的」。

- 申请通知：`FromUserID → ToUserID`，发送者是申请人 → 客户端显示「A 申请加你好友」
- 同意通知：`ToUserID → FromUserID`，发送者是同意人 → 客户端显示「B 同意了你的好友申请」

方向虽然反了，但语义正好对。两个通知落在同一个单聊会话里（`si_` 前缀的会话 ID 是排序拼接的，A→B 和 B→A 是同一个会话）。
</details>

# 第五部分 · 面试话术

## 5.1 30 秒版本

> OpenIM 的好友关系用「边表双向存两份」：A→B 和 B→A 各一行。因为备注、置顶这些属性是「我对你的」而不是双方共享的，一份记录存不下两个方向；同时双向存储让「拉我的好友列表」能走单字段索引。
>
> 申请用一张独立表，状态是 0/1/-1，不删除只改状态。同意时在一个事务里做四件事：标记正向申请、标记反向申请（如果对方也申请过）、补齐两个方向的好友关系、清缓存。
>
> 拉黑是独立操作，不删好友。发消息时检查 `IsBlack(SendID, RecvID)`，所以是单向阻断——被拉黑的人发不进来，拉黑的人还能发出去。
>
> 增量同步用「版本号 + 变更日志」：每次变更写一条 `{e_id, state, version}` 日志，`version` 用 `$inc` 保证单调。客户端带 version 请求，返回比它新的日志。这个方案能解决「删除无法按时间戳增量」的根本问题。

## 5.2 3 分钟版本

**开场**：讲数据建模（三种方式 → 为什么选双向边表），强调「方向属性」和「单索引查询」两个理由。

**中间**：讲申请状态机。重点讲两个细节：
- 重复申请会重置状态（覆盖历史，是取舍）
- 双方互发申请时，一次同意要收敛两条记录（否则进入不一致状态）

**然后**讲拉黑的单向性，以及它和「删除好友」的区别。可以顺带提「删除好友也是单向的」——这是「产品语义决定技术实现」的好例子。

**收尾**：讲增量同步的版本日志，对比时间戳方案，指出「删除无法按时间戳增量」这个根本问题。提一下 `Full` 兜底和哨兵 ID。

**预判追问**：

| 追问 | 回答要点 |
|---|---|
| 「双向存储的一致性问题怎么解决？」 | 用 Mongo 事务包住两次插入。这要求 Mongo 部署为副本集，单机模式不支持事务。 |
| 「同意申请有并发问题吗？」 | 有。`HandleResult != 0` 的检查是「读后判断」，两个并发请求都能通过。彻底解决要用 `FindOneAndUpdate`（`WHERE handle_result=0`）或加唯一索引。 |
| 「版本日志会无限增长吗？」 | 会，但有截断机制。`VersionLogTable.Deleted` 字段记录「已经删了多少条旧日志」。客户端版本太老（早于被截断的部分）时返回 `Full: true` + 全量。 |
| 「为什么用 Mongo 不用 MySQL？」 | 好友关系的查询模式简单（按 owner 查列表、按二元组查单条），没有复杂 join，文档模型够用。而且整个项目已经用 Mongo，不需要为关系单独引入 MySQL。代价是事务能力弱（需要副本集）。 |
| 「缓存一致性怎么保证？」 | Cache-Aside：先写库、再删缓存，且在一个事务内累积删除操作最后一次性执行（`ChainExecDel`）。不在写库前删缓存，因为中间的读请求会回填旧值。 |
| 「删除好友后对方为什么还能发消息？」 | 因为发送校验只看黑名单（和可选的 `FriendVerify`），不看好友关系。这是「基础设施」的定位——不该假设只能给好友发消息。开 `friendVerify` 就会拒绝。 |

## 5.3 可以主动抛出的问题

1. **`friend.go:116` 的 `NewMemoryQueue(16, 1024*1024)` 缓冲 100 万条**，每条通知几 KB，峰值可能占几个 GB 内存。对比 `internal/push` 用的 16K 缓冲，这里明显偏大。

2. **`AddBlack` 没有检查重复拉黑**（`black.go:82`），如果 `blackDatabase.Create` 没有唯一索引或 upsert，重复拉黑会产生重复记录。

3. **`AddBlack` 的 webhook 没有 `ErrCallbackContinue` 例外**（`black.go:68`），和 `ApplyToAddFriend`（`friend.go:131`）不一致——拉黑的 webhook 只能通过或拒绝，没有「记录但放行」的第三态。可能是遗漏。

4. **`AgreeFriendRequest` 的并发窗口**：`HandleResult != 0` 是读后判断，两个并发请求都能通过检查，都会执行 `Create`。需要 `FindOneAndUpdate` 或唯一索引兜底。
