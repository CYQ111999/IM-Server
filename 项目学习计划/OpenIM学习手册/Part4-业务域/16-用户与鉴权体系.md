# 第一部分 · 纯理论

> 这一部分一行 OpenIM 代码都没有。先把名词和机制讲透，第二部分再落源码。

## 1.1 先说清楚两个词：认证与授权

这两个词在中文里经常被混着说，但它们是两件完全不同的事：

| | 认证 Authentication | 授权 Authorization |
|---|---|---|
| 回答的问题 | **你是谁？** | **你能做什么？** |
| 输入 | 凭证（密码、token、证书） | 已知的身份 + 目标资源 |
| 输出 | 一个可信的身份标识 | 允许 / 拒绝 |
| 失败表现 | 401 Unauthorized（其实叫「未认证」更准确） | 403 Forbidden |
| 发生时机 | 请求进来第一件事 | 认证之后、业务逻辑之前 |

一个常见的错误做法是把两者揉在一起：在每个业务函数里写「如果 userID 不等于当前用户就报错」。这样写出来的代码，权限规则散落在几十个文件里，改一条规则要全局搜索。

国际惯例是分成两道关卡：

```
请求 → [认证：你是谁] → [授权：你能不能] → 业务逻辑
```

OpenIM 严格遵守了这个划分，而且分得比大多数项目更彻底：

- **认证在 API 层和网关层做**——HTTP 请求过 `GinParseToken` 中间件，WebSocket 连接在握手时校验 token。认证通过后，把 `userID` 和 `platformID` 塞进 `context`（上下文）里，一路往下传。
- **授权在 RPC 层做**——每个业务函数开头调 `authverify.CheckAccess` 或 `authverify.CheckAdmin`。

为什么不在 API 层一次做完？因为 RPC 服务可以被别的服务直接调用，绕过 HTTP 那一层。如果授权只写在 API 层，任何内部服务都能越权调 RPC。**把授权写进 RPC 层，等于把「门锁」装在了保险柜上而不是大门上**——不管从哪个门进来，都得开这把锁。

> 📌 记忆点：**认证回答「你是谁」，授权回答「你能碰谁」。OpenIM 把认证放门口（API/网关），把授权放保险柜（RPC）。**

## 1.2 会话状态放哪里：Cookie-Session 与 Token 的两条路

HTTP 是**无状态**协议——服务器处理完一个请求就忘了你是谁，下一个请求它完全不认识。这不是缺陷，是设计：无状态才能随便加机器、随便重启。

但业务需要「记住登录状态」，于是有两种解法。

### 路线一：服务端存 Session

```
1. 登录 → 服务器生成一个随机 sessionID，把 {sessionID: userID} 存进服务器内存或 Redis
2. 响应头 Set-Cookie: sessionID=abc123
3. 后续请求浏览器自动带上 Cookie: sessionID=abc123
4. 服务器拿 sessionID 去查表，查出 userID
```

优点：**随时可以踢人**——把 Redis 里那条记录删了，下次请求就查不到，立刻失效。

缺点：**每次请求都要查一次存储**。对普通 Web 站点无所谓，对 IM 这种百万长连接、消息每秒几千条的系统，是实打实的开销。而且多机房部署时，Session 存储成了全局依赖。

### 路线二：把状态放进 Token（JWT）

JWT = JSON Web Token，是一串三段式的字符串：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJ1c2VySUQiOiJpbUFkbWluIn0 . 3f2a9c...
└────────── Header ──────────┘   └────────── Payload ──────────┘   └─ Signature ─┘
```

- **Header**：说明用什么算法签名，这里通常是 `{"alg":"HS256","typ":"JWT"}`
- **Payload**：真正的数据（叫 claims，声明），OpenIM 放的是 `userID`、`platformID`、过期时间
- **Signature**：用密钥对「Header.Payload」算出的 HMAC

前两段只是 **base64url 编码，不是加密**——任何人拿去解码都能看到你的 userID。第三段才是关键：**没有密钥就无法伪造签名**。

服务器验证时不需要查任何存储：

```
1. 拆成三段
2. 用密钥重算 Signature，和第三段比对
3. 比对通过 → 相信 Payload 里的 userID 是真的
4. 检查 exp 有没有过期
```

优点：**零存储查询**，服务器完全无状态，横向扩容随便加机器。

缺点，也是最要命的一点：**签发出去的 token，在过期之前收不回来**。

因为服务器根本不记录「发过哪些 token」，它只验证签名。你想让某个 token 立刻失效，无处下手——除非：

| 补救方案 | 做法 | 代价 |
|---|---|---|
| 黑名单 | 把要作废的 token 写进黑名单，每次校验都查一次 | 又变回「每次查询」，且黑名单会一直长 |
| 白名单 | 把有效的 token 存起来，校验时必须存在 | 等于 Session，JWT 无状态的好处全没了 |
| 短 token + refresh token | access token 只活 5 分钟，靠 refresh 续 | 客户端复杂度上升，仍需吊销 refresh token |

### OpenIM 选了哪条？

**它选了「JWT + 白名单」的混合体**——也就是上表第二行。听起来很讽刺：既然最后还是要查 Redis，为什么还要 JWT？

因为**查的粒度不同**：

- 纯 Session 方案：一个用户的登录状态存一条，查的是「这个 sessionID 对应谁」
- OpenIM 方案：JWT 自己带着 userID 和 platformID，Redis 里只存「这个 token 还有效吗」这个布尔语义

关键差别在**踢人**上。OpenIM 要实现的不是「登出」，而是「**把某个用户在某个端的某个 token 精确踢掉**」——比如同一台手机上重新登录，旧 token 必须立刻失效，但同一账号的 PC 端不能受影响。

要做到这种精度，必须能按 token 定位。所以它存的结构是：

```
key   = UID_PID_TOKEN_STATUS:{userID}:{platformName}   (一个用户的一个端)
field = token 字符串
value = 状态码（1=正常，2=被踢）
```

这是一个 **Redis HASH**。为什么必须是 HASH 而不是 `SET token 1 EX 7d`？

因为**「同端多 token」是常态**：
- 用户在同一台手机上卸载重装 App，旧 token 还在有效期内，新 token 又签发了，此时同一个端有两个 token
- 多端登录策略是「同端不互踢」时，同一端可以并存多个 token

用独立 key 存，要枚举「这个端有哪些 token」就得 `SCAN` 前缀——O(N) 且会阻塞 Redis。用 HASH，`HGETALL` 一次拿到这个端的全部 token，`HDEL` 一次删掉一批。

> 📌 记忆点：**JWT 负责「我是谁」，Redis HASH 负责「这个 token 还活着吗」。OpenIM 用 JWT 换来了免解析存储，又用 HASH 换来了精确踢人。这不是纯 JWT，也不是纯 Session，是「带吊销名单的 JWT」。**

## 1.3 Token 的完整生命周期

把上面两节拼起来，一个 token 从生到死有五个阶段：

```
① 签发     登录接口验证身份 → 生成 JWT → 写入 Redis HASH（状态=正常）→ 返回给客户端
② 携带     HTTP 放 header 的 token 字段；WebSocket 放握手 URL 的 token 参数
③ 校验     验签 → 查 Redis 里这个 token 的状态 → 正常则放行，把 userID/platformID 塞进 context
④ 踢出     状态改成「被踢」→ 下次校验直接拒绝（注意：不是删掉，是改状态）
⑤ 过期     Redis key 的 TTL 到期自动消失；JWT 的 exp 也到期，两边同时失效
```

有两个细节值得停下来想：

**细节一：踢人为什么是「改状态」而不是「删除」？**

因为要区分两种失败原因，好给客户端不同的错误码：

| Redis 里的情况 | 含义 | 客户端该怎么做 |
|---|---|---|
| HASH 里根本没有这个 token | 从没签发过 / 已被清理 | `ErrTokenNotExist`，重新登录 |
| HASH 里有，状态=2（被踢） | 被人顶下线了 | `ErrTokenKicked`，弹「您的账号在另一台设备登录」 |

如果踢人时直接 `HDEL`，这两种情况就分不开了，客户端只能笼统提示「登录失效」，用户体验差一截。

**细节二：Redis key 的 TTL 必须和 JWT 的 exp 对齐**

否则会出现两种错位：
- Redis 先过期 → JWT 还没过期但查不到记录 → 用户明明没过期却被踢
- JWT 先过期 → Redis 里留一堆永远用不到的死 token → 内存泄漏

OpenIM 的做法是：签发 token 时用同一个 `accessExpire` 同时设置 JWT 的 exp 和 Redis 的 `EXPIRE`。这个 `accessExpire` 的单位是**天**，`config/share.yml` 里的 `tokenPolicy.expire`。

## 1.4 多端登录：五种策略背后的产品问题

「一个账号能不能同时在手机和电脑上登录？」这不是技术问题，是产品问题。不同产品答案不同：

- 微信：手机 + 平板 + 电脑可以同时在线，同类型设备互踢
- QQ：多端同时在线，但同类设备只能一个
- 银行 App：新设备登录，旧设备立刻下线
- 企业内部系统：PC 端允许多开（多标签页），移动端只允许一个

OpenIM 把它做成了**配置项**（`config/share.yml` 的 `multiLogin.policy`），共五种：

| 策略 | 常量名 | 语义 |
|---|---|---|
| 0 | `DefalutNotKick` | 默认不互踢，同端超过上限才踢最早的 |
| 1 | `AllLoginButSameTermKick` | 所有端都能登，但同端只留最新一个 |
| 2 | `PCAndOther` | PC 端互不踢，其他端（手机/平板/网页）合起来只留一个，优先保 Android |
| 3 | `AllLoginButSameClassKick` | 同「类别」的端互踢，其他类别各留一个 |
| 4 | `AdminPlatformID` 相关 | 管理端单独处理（新管理端登录，旧管理端 token 全废） |

「端」和「类别」是两个不同粒度的概念：

```
platformID 是具体的端：1=iOS 2=Android 3=Windows 4=OSX 5=Web 6=小程序 7=Linux ...
PlatformIDToClass(platformID) 是类别：PC（Win/Mac/Linux）/ 手机 / 平板 / 网页
```

为什么需要「类别」？因为 PC 上可能同时开着 Windows 客户端和 Mac 客户端（用户两台电脑），它们是不同的 platformID，但都属于「PC 这一类」。`PCAndOther` 策略要表达的是「电脑随便登，手机只留一个」——用 platformID 表达不了，必须用 class。

## 1.5 管理员体系：为什么 IM 不开放注册

打开任何一个 IM 产品的后台，你会发现「加用户」是管理员的操作，不是用户自己点注册。

这是因为 IM 服务端的定位是**基础设施**，不是完整产品。它的用户数据必须和业务系统（你的 App 的账号体系）对齐。如果允许自由注册，会出现：业务系统里没有这个人，但 IM 里有；或者两边 userID 不一致，消息发不过去。

所以 OpenIM 的设计是：

```
你的业务后端（自己写）  ──调 API──▶  OpenIM 的 /user/user_register
     ↑                                      │
     └────── 用户在你的 App 注册 ────────────┘
```

**IM 只负责「已经存在的用户之间怎么聊天」，不负责「用户怎么来」。**

这也解释了为什么 `UserRegister` 要求 `CheckAdmin`——只有拿着管理员 token 的服务端才能创建用户。

那管理员自己是怎么来的？两条路：

1. **配置文件里写死**：`config/share.yml` 的 `imAdminUser.userIDs`，服务启动时自动写进用户表（如果不存在）
2. **通过 secret 换 token**：`/auth/get_admin_token` 传 `secret`（配置文件里的共享密钥）+ 管理员的 userID

这里有一个很重要的设计：**管理员 token 用的是独立的 platformID（`AdminPlatformID`）**。这样它和普通用户的 iOS/Android token 在 Redis 里落在不同的 HASH 里，互不干扰。而且管理端登录时会走一条特殊分支——把这用户之前所有管理端 token 全部删掉，相当于「管理后台只允许一处登录」。

## 1.6 「临时管理员」：一个为多节点设计的补丁

设想一个场景：你开了 3 个 gateway 节点，某个管理员登录后连在节点 A 上。现在他通过节点 A 发一个管理请求。

请求路径是：`客户端 → 节点A 的 API → RPC 服务`。在 RPC 服务看来，操作者（opUserID）是管理员，`IsAdmin` 应该返回 true。

但 `IsAdmin` 是怎么判断的？它检查的是「上下文里的 `CtxAdminUserIDsKey` 里有没有这个 userID」。而这个值是谁塞进去的？是 API 层从配置里读出来塞的（`router.go` 的 `setGinIsAdmin` 中间件）。

问题来了：**如果某个请求不是从 API 层进来的呢？** 比如：
- 网关内部要调 RPC（踢人、查会话）
- 定时任务要调 RPC
- 服务 A 调服务 B

这些路径没有经过 `setGinIsAdmin`，上下文里没有管理员列表，`IsAdmin` 就返回 false，操作被拒。

「临时管理员」就是解决这个的：调用方在发起 RPC 前往上下文里打一个标记，接收方看到标记就认为「这次调用是可信的内部调用，按管理员处理」。

实现上它借用了 gRPC 的 metadata：在 `RpcCustomHeader` 这个 key 里塞一个特殊字符串 `ctxImTempAdminKey`，这个 metadata 会随 gRPC 请求一起传到对端，对端解析后把 `ctxTempAdminKey` 塞进 context。

> ⚠️ **易错点**：临时管理员是**信任内部网络**的假设——只要能调通 gRPC 端口，就能伪造这个 header 拿到管理员权限。所以生产环境必须保证 RPC 端口不对外暴露（Docker 网络内部通信 + 防火墙）。这不是 OpenIM 独有的问题，所有「内网互信」的微服务架构都有这个前提。

## 1.7 两条鉴权范式，覆盖全项目

翻遍 `internal/rpc`，你会发现授权检查只有两个函数被反复调用：

```go
authverify.CheckAdmin(ctx)              // 我是管理员吗？
authverify.CheckAccess(ctx, ownerUserID) // 我是这个人，或者我是管理员吗？
```

它们分别对应两类资源：

| 范式 | 语义 | 典型场景 |
|---|---|---|
| `CheckAdmin` | 只有系统管理员能做 | 创建用户、创建群、导入好友、发系统通知、删除过期文件 |
| `CheckAccess(ctx, userID)` | 我是这个 userID，或者是管理员 | 改自己的资料、读自己的会话、删自己的好友、拉自己的消息 |

为什么 `CheckAccess` 里要允许管理员？因为管理后台要能「代用户操作」——查任意用户的消息、改任意用户的资料。如果只允许本人，后台就没法做客服了。

还有一个变体 `CheckAccessIn(ctx, userIDs...)`：**任意一个匹配即可**。用在「群管理员或群主都能操作」这类场景，避免写两遍判断。

这种「两个函数打天下」的设计有个巨大好处：**权限规则可审计**。你想知道「哪些接口需要管理员」，grep 一下 `CheckAdmin` 就够了。反过来，如果一个项目里权限判断散落成几十种写法，安全审计基本没法做。

## 1.8 用户信息缓存：为什么要用 rockscache

用户信息是**读多写极少**的典型数据：一个用户注册后，昵称头像可能一年都不改，但每发一条消息、每拉一次会话列表，都要查发送者的昵称头像。

朴素做法是「查 Redis，没有就查 Mongo 再回填」。这个模式有个著名的坑叫**缓存击穿**：热点 key 过期的瞬间，几百个请求同时发现缓存没了，同时去查 Mongo，Mongo 被打穿。

解决办法有几种：加互斥锁（只让一个请求去查）、逻辑过期（永不过期，异步刷新）、单飞（singleflight）。OpenIM 用的是 `rockscache` 这个库，它提供的是**「带分布式锁的缓存读取 + 延迟双删」**：

- 读：缓存命中直接返回；未命中则加锁 → 查库 → 回填 → 释放锁，其他请求等锁后直接读缓存
- 写：先更新数据库 → 删除缓存 → 延迟一段时间再删一次（应对「读请求在更新前读到旧值、在删除后回填」的竞态）

> 📌 记忆点：**缓存一致性没有完美解，只有「把不一致窗口压到可接受」。延迟双删压的是「旧值被回填」这个窗口。**

# 第二部分 · 源码实现

> 从这里开始，每一个结论都能落到 `文件:行号`。

## 2.1 全景：一个请求要过几道关

先看 HTTP 请求的完整路径（细节在 05 篇）：

```
POST /user/user_register
  │
  ├─ gzip 压缩
  ├─ BBR 限流                    internal/api/ratelimit.go
  ├─ standalone 注入管理员        internal/api/router.go（setGinIsAdmin）
  ├─ GinLogger / prommetrics / Recovery / Cors
  ├─ ParseOperationID            生成链路追踪 ID
  ├─ GinParseToken               认证：验签 + 查 Redis 状态
  │     └─ 通过后 c.Set("userID", ...) 之类
  │
  └─ handler: a2r.Call(...)  → gRPC → user 服务
                                        │
                                        └─ authverify.CheckAdmin(ctx)  授权
```

注意这里有个**容易被忽略的顺序**：限流在认证之前。这是有意的——如果先认证再限流，被限流的请求已经花掉了一次 Redis 查询（甚至一次 gRPC 调用），白白消耗资源。先限流能把成本挡在更前面。

> 📌 参见 05 篇「中间件顺序」一节，以及 `internal/api/router.go:122` 那行完整的中间件链。

## 2.2 `authverify` 包：107 行的权限中枢

整个包只有两个文件，`doc.go` 是空的包注释，真正的逻辑全在 `token.go`（106 行）。这是全项目「代码量最小、影响面最大」的文件。

### 2.2.1 密钥与验签入口

`pkg/authverify/token.go:14`：

```go
func Secret(secret string) jwt.Keyfunc {
	return func(token *jwt.Token) (any, error) {
		return []byte(secret), nil
	}
}
```

这个函数返回的是 `jwt.Keyfunc` 类型——一个「给我 token，我给你验签密钥」的回调。为什么不直接传 `[]byte`？

因为 JWT 支持多种签名算法（HS256 对称、RS256 非对称），非对称算法需要根据 Header 里的 `kid`（密钥 ID）去找对应的公钥。设计成回调后，调用方可以在回调里做「按 kid 选密钥」的逻辑，而不用改库的接口。

OpenIM 只用 HS256（对称），所以这个回调永远返回同一个密钥。**它不是「最灵活」的写法，但是「接口对齐标准库」的写法**。

> ⚠️ **易错点**：这个函数**不校验算法**。JWT 有一个经典漏洞叫「算法混淆攻击」——攻击者把 Header 的 `alg` 改成 `none`，某些库会跳过验签。`golang-jwt/jwt/v4` 默认会拒绝 `none`，但如果你自己实现了 Keyfunc 且没检查 `token.Method`，仍然可能被降级到弱算法。OpenIM 这里没检查，属于「依赖库的默认防护」，不算漏洞但值得知道。

```go
// :104 —— 看配置里的管理员 ID 列表
```

这是个**容易踩的坑**：在 IM 里，「App 管理员」和「IM 系统管理员」是两个概念。前者是业务角色（用在第三方推送、通知账号等场景），后者是运维角色（能调管理接口）。

**`CheckAccessIn` 为什么需要**（`:66`）：


### 2.2.3 临时管理员的实现细节

`token.go:79-97`：

```go
var tempAdminValue = []string{"1"}
const ctxTempAdminKey = "ctxImTempAdminKey"

func WithTempAdmin(ctx context.Context) context.Context {
	keys, _ := ctx.Value(constant.RpcCustomHeader).([]string)
	if datautil.Contain(ctxTempAdminKey, keys...) {
		return ctx                       // 已经有标记，直接返回
	}
	if len(keys) > 0 {
		temp := make([]string, 0, len(keys)+1)
		temp = append(temp, keys...)
		keys = append(temp, ctxTempAdminKey)   // ⚠️ 见下方分析
	} else {
		keys = []string{ctxTempAdminKey}
	}
	ctx = context.WithValue(ctx, constant.RpcCustomHeader, keys)
	return context.WithValue(ctx, ctxTempAdminKey, tempAdminValue)
}
```

这段代码有几个值得注意的地方：

**（1）它操作的是 `constant.RpcCustomHeader` 这个 key**，不是自定义的 key。这个 key 是 OpenIM 与 SDK 的约定——凡是放在这个 key 下的字符串切片，都会被 gRPC 拦截器序列化进 metadata，跨服务传递。相当于「自定义 header 的通道」。

**（2）`temp = append(temp, keys...)` 之后又 `keys = append(keys, ctxTempAdminKey)`**——这里新建了 `temp` 拷贝了一份，但随后又往**原来的 `keys`** 上 append。

如果 `keys` 的容量还有富余，`append(keys, ...)` 会直接改底层数组，而 `temp` 共享同一个底层数组的前缀——两个切片都指向同一块内存，`temp` 的内容会被覆盖。这是个**潜在的别名 bug**。

不过实际影响很小：`ctx.Value` 取出来的切片是从 gRPC metadata 反序列化来的，容量通常等于长度，`append` 会重新分配。而且 `temp` 赋值后只被用作……等等，`temp` 赋值后**根本没有被使用**。看第 89-91 行：

```go
temp := make([]string, 0, len(keys)+1)
temp = append(temp, keys...)
keys = append(keys, ctxTempAdminKey)
```

`temp` 创建、填充，然后**再也没出现**。这是一段**残留代码**——原本大概想写 `keys = append(temp, ctxTempAdminKey)`，后来改成了直接 append 到 `keys`，但 `temp` 忘了删。

> 📌 **这是个很好的面试素材**：`go vet` 不会报这个（它只报「赋值后从未使用」的局部变量，而 `temp` 被 append 过，算「使用过」）。但它明显是死代码，说明这段逻辑被人改过、没清理干净。

**（3）`IsTempAdmin` 的判断依赖 `constant.RpcCustomHeader` 能被带过去**。所以它只在「同一个 RPC 调用链」内有效，HTTP 请求里的 header 是不会自动变成这个的——必须由代码显式调 `WithTempAdmin`。

### 2.2.4 谁在调 `WithTempAdmin`

grep 一下就知道：`internal/msggateway`、`internal/msgtransfer` 等需要「以系统身份」调 RPC 的地方。比如网关要给用户推通知消息，它调 `msg.SendMsg` 时如果操作者是普通用户，`SendMsg` 内部的权限检查会挡住——加上临时管理员标记后，这个内部调用就被信任了。

## 2.3 Token 的存储结构

### 2.3.1 key 怎么拼

`pkg/common/storage/cache/cachekey/token.go:9-15`：


为什么用 **platformName（字符串）** 而不是 platformID（数字）？

因为可读性。运维用 `redis-cli` 排查问题时，看到 `:ios` 立刻明白，看到 `:1` 要去查表。代价是拼接时多一次映射（`PlatformIDToName`），反向解析时多一次 `strings.Split`（`:29-33`）。

**这个反向解析函数有个脆弱点**：

```go

	platform := splitKey[len(splitKey)-1]
	return constant.PlatformNameToID(platform)
}
```

它假设「最后一段就是平台名」。而 `GetTemporaryTokenKey`（`:17-19`）拼出来的 key 是：

```
UID_PID_TOKEN_STATUS::TEMPORARY:{userID}:{platformName}:{token}
```

最后一段是 **token 本身**，不是平台名。如果哪天有人把临时 token 的 key 传给 `GetPlatformIDByTokenKey`，会得到错误结果（`PlatformNameToID` 查不到就返回 0 或 -1）。

目前没有这种调用路径（临时 token 用 `GET` 单个 key，不参与平台解析），属于「设计上埋了个雷，但暂时踩不到」。

### 2.3.2 HASH 里存什么

`pkg/common/storage/cache/redis/token.go:31-42`：

```go
func (c *tokenCache) SetTokenFlag(ctx context.Context, userID string, platformID int, token string, flag int) error {
	key := cachekey.GetTokenKey(userID, platformID)
	if err := c.rdb.HSet(ctx, key, token, flag).Err(); err != nil {
		return errs.Wrap(err)
	}
	if c.localCache != nil {
		c.removeLocalTokenCache(ctx, key)
	}
	return nil
}
```

结构：

```
key   = UID_PID_TOKEN_STATUS:user001:ios
field = eyJhbGciOi...（完整 token 字符串，200+ 字节）
value = 1（正常）或 2（被踢）
TTL   = tokenPolicy.expire 天
```

把**完整 token 当作 field**看起来浪费空间（一个 field 200 字节），但这是唯一能精确定位的方式——你无法从 token 里提取一个短 ID 来当 field，因为 JWT 的签名部分依赖整个 payload，任何截断都会导致无法验证。

**`SetTokenFlagEx` 与 `SetTokenFlag` 的区别**（`:45-59`）：前者多一句 `Expire`。

```go
func (c *tokenCache) SetTokenFlagEx(ctx context.Context, userID string, platformID int, token string, flag int) error {
	// ...
	if err := c.rdb.Expire(ctx, key, c.accessExpire).Err(); err != nil {
		return errs.Wrap(err)
	}
	// ...
}
```

这个 `Expire` 每次都会**重置整个 HASH 的 TTL**，而不是单个 field 的 TTL。这带来一个副作用：

> 用户在 iOS 端登录两次，第一次的 token 是 7 天有效期，第 3 天又登录一次，`EXPIRE` 重置为 7 天。此时第一个 token 在 Redis 里能活到第 10 天，但它的 JWT 在第 7 天就过期了。
> 结果是：Redis 里留了 3 天的无效数据。这是**空间换简单**的取舍——Redis 里多几个 field 无所谓，比维护每个 field 的独立 TTL（Redis HASH 不支持 field 级 TTL）简单得多。

### 2.3.3 为什么读全平台要分片

`token.go:85-120` 的 `GetAllTokensWithoutError` 要读「这个用户所有平台的 token」，做法是：

```go
keys := cachekey.GetAllPlatformTokenKey(userID)   // 拼出所有平台的 key
if err := ProcessKeysBySlot(ctx, c.rdb, keys, func(ctx context.Context, slot int64, keys []string) error {
	pipe := c.rdb.Pipeline()
	// 对这批 key 批量 HGETALL
})
```

为什么要 `ProcessKeysBySlot`？因为 **Redis Cluster 不允许跨 slot 的 MULTI/EXEC**。

如果直接 `pipeline.HGetAll(k1); pipeline.HGetAll(k2); ...`，而 k1 和 k2 落在不同 slot，pipeline 仍能工作（pipeline 不是事务），但如果有 `MULTI` 就会报 `CROSSSLOT` 错误。

`ProcessKeysBySlot` 的作用是**按 slot 分组，同组内用 pipeline 批量执行**，既避开了跨 slot 问题，又保住了批量性能。这是「代码里看不出为什么，但删了会在集群模式炸」的典型。

> 📌 **面试点**：如果你被问「Redis Cluster 下批量操作怎么做」，答案就是「按 slot 分组 + 组内 pipeline」，OpenIM 的 `ProcessKeysBySlot` 就是这个模式的开源实现。

### 2.3.4 本地缓存怎么失效

`token.go:229-247`：

```go
func (c *tokenCache) removeLocalTokenCache(ctx context.Context, keys ...string) {
	// ...
	topic := c.localCache.Auth.Topic
	data, err := json.Marshal(keys)
	// ...
	c.rdb.Publish(ctx, topic, string(data))
}
```

每次改 token 状态，除了改 Redis，还要**通过 Redis Pub/Sub 广播一条消息**，通知所有节点「这几个 key 的本地缓存作废」。

这是一个**经典的本地缓存一致性问题**：每个服务进程都在内存里缓存了 token 状态（为了避免每次校验都查 Redis），一旦某个节点改了状态，其他节点的缓存就脏了。

三种解法：

| 方案 | 做法 | 缺点 |
|---|---|---|
| 设短 TTL | 本地缓存 1 秒过期 | 最长 1 秒的不一致窗口 |
| Pub/Sub 广播 | 改了就发消息，各节点收到后删本地 | 消息丢失 = 永久不一致（无重试） |
| 版本号 | 每个 key 带版本，读时比对 | 多一次查询，复杂 |

OpenIM 选了 Pub/Sub（第二种）。**它的风险是消息丢失**——如果某个节点在广播时刚好断线，它的本地缓存会一直脏着，直到进程重启。

代码里只 `log.ZWarn` 了发布失败（`:244`），没有重试、没有兜底。这是「可以接受的不完美」：token 校验有 Redis 兜底路径（`rpccache.AuthLocalCache` 应该会在本地缓存 miss 时回源），而且真实环境 Redis Pub/Sub 丢失概率很低。

## 2.4 签发：`CreateToken` 先踢人再发牌

`pkg/common/storage/controller/auth.go:93-139`，这个函数是整个鉴权体系的核心：

```go
func (a *authDatabase) CreateToken(ctx context.Context, userID string, platformID int) (string, error) {
	tokens, err := a.cache.GetAllTokensWithoutError(ctx, userID)   // ① 取该用户所有端的 token
	deleteTokenKey, kickedTokenKey, adminTokens, err := a.checkToken(ctx, tokens, platformID)  // ② 算踢谁
	if len(deleteTokenKey) != 0 {
		a.cache.DeleteTokenByTokenMap(ctx, userID, deleteTokenKey)  // ③ 物理删除无效 token
	}
	if len(kickedTokenKey) != 0 {
		a.cache.SetTokenFlagEx(ctx, userID, plt, k, constant.KickedToken)  // ④ 标记为被踢
	}
	if len(adminTokens) != 0 {
		a.cache.DeleteAndSetTemporary(ctx, userID, constant.AdminPlatformID, adminTokens)  // ⑤ 管理端特殊处理
	}
	claims := tokenverify.BuildClaims(userID, platformID, a.accessExpire)  // ⑥ 构造 claims
	token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
	tokenString, err := token.SignedString([]byte(a.accessSecret))          // ⑦ 签名
	a.cache.SetTokenFlagEx(ctx, userID, platformID, tokenString, constant.NormalToken)  // ⑧ 写入状态
	return tokenString, nil
}
```

**注意执行顺序**：先算踢谁、再踢、最后才签发。为什么不是「先签发再踢」？

因为如果先签发，中间那段时间会出现「新旧 token 都有效」的窗口。虽然只有几毫秒，但对「同端互踢」这种语义来说是不严谨的。**先踢后发，保证任意时刻同端最多一个有效 token。**

### 2.4.1 `checkToken`：五种策略的具体算法

`auth.go:142-266`，这是全项目**逻辑最绕**的 100 行。先看第一轮分类（`:153-166`）：

```go
for plfID, tks := range tokens {          // tokens: map[platformID]map[token]state
	for k, v := range tks {
		_, err := tokenverify.GetClaimFromToken(k, authverify.Secret(a.accessSecret))
		if err != nil || v != constant.NormalToken {
			deleteToken[plfID] = append(deleteToken[plfID], k)   // 无效 or 已被踢 → 待删
		} else {
			if plfID != constant.AdminPlatformID {
				loginTokenMap[plfID] = append(loginTokenMap[plfID], k)  // 有效登录 token
			} else {
				adminToken = append(adminToken, k)               // 管理员 token 单独放
			}
		}
	}
}
```

三类分流：
1. **待删**：JWT 解析失败（密钥换了/格式坏了）或状态不是「正常」
2. **有效登录 token**：普通端的正常 token
3. **管理员 token**：`AdminPlatformID` 的正常 token

分类依据里有个值得注意的点：`v != constant.NormalToken` 就删。这意味着**被踢的 token 会被物理删除**，而不是留着让用户看到「你被踢了」。

等等——前面 1.3 节不是说「踢人是改状态不是删除」吗？这里矛盾了？

不矛盾，只是**时机不同**：
- **踢的瞬间**：改状态为 2（`SetTokenFlagEx`），用户下次请求能收到 `ErrTokenKicked`
- **下次登录时**：把这些状态为 2 的 token 物理删除（`deleteToken`），因为已经不需要再给用户提示了

这是**两阶段清理**：先「标记」保证语义正确，再「删除」回收空间。很聪明的设计。

第二轮按策略计算（`:169-250`），逐条拆：

**策略 0：`DefalutNotKick`（默认不互踢）**（`:170-181`）

```go
case constant.DefalutNotKick:
	for plt, ts := range loginTokenMap {
		l := len(ts)
		if platformID == plt {
			l++                          // 加上即将登录的这个
		}
		limit := a.multiLogin.MaxNumOneEnd
		if l > limit {
			kickToken[plt] = ts[:l-limit]  // 踢掉最早的（切片前部）
		}
	}
```

关键点：`l++` 是因为**当前要签发的 token 还没进 map**，得先算上。踢的是 `ts[:l-limit]`——这个写法依赖「`ts` 是按时间顺序排的」，而 `loginTokenMap` 是遍历 `tks`（一个 Go map）得来的，**顺序是随机的**！

这是一个**真实的 bug 风险**：`map` 遍历无序，`ts` 里的 token 顺序不确定，`ts[:l-limit]` 踢掉的可能是最新的而不是最旧的。

除非……`GetAllTokensWithoutError` 返回的 map 有某种顺序保证？看 `token.go:85-120`，它遍历的是 `keys`（由 `GetAllPlatformTokenKey` 生成的有序切片），但每个 key 对应的 HASH 用 `HGetAll` 读出来是 `map[string]string`，**还是无序**。

所以严格说：**策略 0 在「同端 token 超限」时，踢掉的可能是任意一个，不一定是最旧的**。实际影响有限（因为超限本身就少见，且被踢的 token 用户重新登录即可），但这是「依赖了不存在的顺序保证」的典型缺陷。

**策略 1：`AllLoginButSameTermKick`（同端互踢）**（`:182-190`）

```go
case constant.AllLoginButSameTermKick:
	for plt, ts := range loginTokenMap {
		kickToken[plt] = ts[:len(ts)-1]      // 踢掉除最后一个之外的全部
		if plt == platformID {
			kickToken[plt] = append(kickToken[plt], ts[len(ts)-1])  // 同端连最后一个也踢
		}
	}
```

逻辑是「每个端都保留最后一个；如果这个端就是当前登录的端，那最后一个也要踢」——因为新的马上要顶上来。

这里的 `ts[len(ts)-1]` 同样依赖顺序，同样有这个隐患。

**策略 2：`PCAndOther`**（`:191-228`）

这是最绕的一段。语义：PC 类互不踢，其他端只留一个，优先保 Android。

```go
unkickTerminal = constant.TerminalPC
if constant.PlatformIDToClass(platformID) != unkickTerminal {
	// 当前登录的是「非 PC」→ 把所有非 PC 的端全部踢掉
	for plt, ts := range loginTokenMap {
		if constant.PlatformIDToClass(plt) != unkickTerminal {
			kickToken[plt] = ts
		}
	}
} else {
	// 当前登录的是 PC → 非 PC 端里只留一个
	var preKickToken string
	var preKickPlt int
	var reserveToken = false
	for plt, ts := range loginTokenMap {
		if constant.PlatformIDToClass(plt) != unkickTerminal {
			if !reserveToken {
				reserveToken = true
				kickToken[plt] = ts[:len(ts)-1]     // 保留最后一个
				preKickToken = ts[len(ts)-1]
				preKickPlt = plt
			} else {
				if plt == constant.AndroidPlatformID {
					if preKickToken != "" {
						kickToken[preKickPlt] = append(kickToken[preKickPlt], preKickToken)  // 踢掉之前保留的
					}
					kickToken[plt] = ts[:len(ts)-1]  // 现在保 Android
				} else {
					kickToken[plt] = ts               // 其他全踢
				}
			}
		}
	}
}
```

这段有个**逻辑漏洞**：`reserveToken` 一旦为 true 就不再回到 false，所以「保留的那个非 PC 端」是在 map 遍历中**第一个遇到的**，而 map 遍历顺序随机。

于是「优先保 Android」只在**Android 恰好不是第一个**时才生效——如果 iOS 先被遍历到，它被保留；然后 Android 被遍历到，代码把 iOS 的保留 token 也踢了，改成保 Android。这个逻辑是对的。

但如果**没遍历到 Android**（用户没有 Android 设备），那保留的就是「随机第一个非 PC 端」。这在语义上没问题（反正只留一个）。

真正的 bug 是：如果**遍历到 Android 时，Android 的 `ts` 有多条**，`kickToken[plt] = ts[:len(ts)-1]` 保留最后一条，然后前面保的 iOS token 被 append 进 `kickToken[preKickPlt]`。逻辑正确。

**策略 3：`AllLoginButSameClassKick`（同类互踢）**（`:229-247`）

```go
var reserved = make(map[string]struct{})
for plt, ts := range loginTokenMap {
	if constant.PlatformIDToClass(plt) == constant.PlatformIDToClass(platformID) {
		kickToken[plt] = ts                      // 同类别：全踢
	} else {
		if _, ok := reserved[constant.PlatformIDToClass(plt)]; !ok {
			reserved[constant.PlatformIDToClass(plt)] = struct{}{}
			kickToken[plt] = ts[:len(ts)-1]      // 该类别第一个：留一个
			continue
		} else {
			kickToken[plt] = ts                  // 该类别后续：全踢
		}
	}
}
```

这个用的是 `reserved` map 记录「这个类别已经留过了」，逻辑比策略 2 清晰——**不依赖遍历顺序挑「留谁」，只依赖「第一个遇到的类别留一个」**。同类别内留的是 `ts[len(ts)-1]`（仍然依赖顺序，但只影响「留哪个」不影响「留几个」）。

**策略 4：管理端**（`:260-265`）

```go

	deleteAdminToken = adminToken
```

为什么管理端要「删除 + 设临时」而不是「标记被踢」？看 `token.go:212-227`：

```go

	for _, f := range fields {
		k := cachekey.GetTemporaryTokenKey(userID, platformID, f)
		c.rdb.Set(ctx, k, "", time.Minute*5)     // 保留 5 分钟的临时记录
	}

	c.rdb.HDel(ctx, key, fields...)              // 从主 HASH 删掉

```

它给旧管理端 token 建了一个 **5 分钟有效的临时 key**。作用是：旧 token 的持有者如果在这 5 分钟内发请求，`parseToken` 会先查主 HASH（没有），再查临时 key（有）——但临时 key 的存在意味着什么？

回看 `auth.go:168-176`：

```go
if len(m) == 0 {
	isAdmin := authverify.CheckUserIsAdmin(ctx, claims.UserID)
	if isAdmin {
		if err = s.authDatabase.GetTemporaryTokensWithoutError(ctx, claims.UserID, claims.PlatformID, tokensString); err == nil {
			return claims, nil       // ⚠️ 临时 key 存在 → 放行！
		}
	}
	return nil, servererrs.ErrTokenNotExist.Wrap()
}
```

**临时 key 存在 = 放行**。也就是说，被顶掉的管理端旧 token，在 5 分钟内**仍然有效**。

这看起来反直觉，但想一下场景：管理员在 A 浏览器登录，然后在 B 浏览器登录，A 应该被踢。但 A 可能正在提交一个表单，请求正在路上。5 分钟的宽限期是为了**避免正在进行的操作被硬中断**——体验优先于严格。

> ⚠️ **这是个值得讨论的设计**：从安全角度，管理端 token 的宽限期是风险（5 分钟内旧 token 仍可用）。从可用角度，硬中断会丢操作。OpenIM 选了可用性。如果是我做，可能会把宽限期缩到 30 秒，并在响应里告知「您的账号已在别处登录」。

## 2.5 校验：`parseToken` 的状态机

`internal/rpc/auth/auth.go:157-195`：

```go

	claims, err = tokenverify.GetClaimFromToken(tokensString, authverify.Secret(s.config.Share.Secret))  // ① 验签
	if err != nil {
		return nil, err
	}

	m, err := s.AuthLocalCache.GetExistingToken(ctx, claims.UserID, claims.PlatformID)  // ② 查该端所有 token
	if err != nil {
		return nil, err
	}

		isAdmin := authverify.CheckUserIsAdmin(ctx, claims.UserID)

			if err = s.authDatabase.GetTemporaryTokensWithoutError(...); err == nil {
				return claims, nil
			}
		}
		return nil, servererrs.ErrTokenNotExist.Wrap()
	}
	if v, ok := m[tokensString]; ok {
		// ④ 找到了这个 token
		switch v {
		case constant.NormalToken:
			return claims, nil
		case constant.KickedToken:
			return nil, servererrs.ErrTokenKicked.Wrap()
		default:
			return nil, errs.Wrap(errs.ErrTokenUnknown)
		}
	} else {
		// ⑤ 这个端有别的 token，但没有这一个 —— 同样给管理员一次机会
		isAdmin := authverify.CheckUserIsClientAdmin...  // 实际是 CheckUserIsAdmin
		if isAdmin { ... GetTemporaryTokensWithoutError ... }
	}
	return nil, servererrs.ErrTokenNotExist.Wrap()
}
```

画成状态图：

```
                    ┌─────────────┐
   token 字符串 ──▶ │ ① 验签       │──失败──▶ ErrTokenNotExist
                    └──────┬──────┘
                           │ 成功，拿到 claims(userID, platformID)
                           ▼
                    ┌─────────────┐
                    │ ② 查该端 HASH│
                    └──────┬──────┘
                 ┌─────────┴──────────┐
             空  │                    │ 非空
                 ▼                    ▼
        ┌────────────────┐    ┌──────────────┐
        │是管理员？       │    │这个 token 在？│
        └───┬────────┬───┘    └───┬──────┬───┘
         是 │        │ 否       在 │      │ 不在
            ▼        ▼             ▼      ▼
      ┌──────────┐  ┌────────┐  ┌──────────────┐   ┌──────────┐
      │临时 key 在│  │NotExist│  │状态=1→放行   │   │管理员兜底│
      │→放行     │  │        │  │状态=2→Kicked │   │→放行/拒绝│
      └──────────┘  └────────┘  │其他→Unknown  │   └──────────┘
```

**这张图是面试时的杀手锏**——它把「为什么会有三种 token 错误码」讲清楚了：

| 错误码 | 触发条件 | 客户端处理 |
|---|---|---|
| `ErrTokenNotExist` | 从没签发过 / 已被物理删除 / 用户不存在 | 重新登录 |
| `ErrTokenKicked` | 状态=2，被别的端顶掉 | 提示「账号在其他设备登录」 |
| `ErrTokenUnknown` | 状态是未知值（数据损坏） | 重新登录（可上报） |

## 2.6 三个登录入口

`auth.go` 里暴露了三个「拿 token」的接口，用途完全不同：

### 2.6.1 `GetAdminToken`（`:88-113`）：secret 换 token

```go
func (s *authServer) GetAdminToken(ctx, req) {
	if req.Secret != s.config.Share.Secret {
		return nil, errs.ErrNoPermission.WrapMsg("secret invalid")   // ① 验 secret
	}
```

三道检查，缺一不可：
- **secret**：防止任何人调这个接口就能拿管理员 token。这个 secret 是配置文件里的 `share.secret`，等同于「系统 root 密码」
- **userID 在管理员列表**：即使知道 secret，也不能给任意用户发管理员 token
- **用户存在**：避免给一个不存在的 userID 签发 token

这就是你环境验证时用的那个接口：

```bash

  -H "Content-Type: application/json" -H "operationID: t1" \
  -d '{"secret":"<share.secret>","userID":"imAdmin"}'
```

### 2.6.2 `GetUserToken`（`:115-144`）：管理员替用户签 token

```go
func (s *authServer) GetUserToken(ctx, req) {
	if err := authverify.CheckAdmin(ctx); err != nil {       // ① 必须是管理员在调
		return nil, err
	}
	if req.PlatformID == constant.AdminPlatformID {          // ② 不能伪造管理端
		return nil, errs.ErrNoPermission.WrapMsg("platformID invalid...")
	}
	if authverify.CheckUserIsAdmin(ctx, req.UserID) {        // ③ 不能给管理员发普通 token
		return nil, errs.ErrNoPermission.WrapMsg("don't get Admin token")
	}
	user, err := s.userClient.GetUserInfo(ctx, req.UserID)
	if user.AppMangerLevel >= constant.AppNotificationAdmin { // ④ 通知账号不能登录
		return nil, errs.ErrArgs.WrapMsg("app account can`t get token")
	}
	token, err := s.authDatabase.CreateToken(ctx, req.UserID, int(req.PlatformID))
}
```

这个接口的用途：**你的业务后端在用户登录成功后，替用户向 IM 换一个 token**。这是最常见的集成方式——因为 IM 不认识你的用户密码，只能由你验证完密码后，用管理员身份去换。

四条防线，每一条都堵一个滥用路径：

- ① 防止普通用户自己调这个接口，随便给自己签 token
- ② 防止用 `platformID=AdminPlatformID` 混进管理端 HASH
- ③ 防止「管理员账号」被当成普通用户登录（管理端和用户端是隔离的）
- ④ 防止「通知账号」（系统通知的发送者，如 `notification` 账号）被登录

**第 ④ 条特别值得讲**：OpenIM 里有一类特殊账号叫「通知账号」，它的 `app_manger_level` 是 `AppNotificationAdmin`。这类账号用来给用户发系统通知消息，但它**不是真人**，不该有登录能力。如果允许它登录，任何人都能冒充系统发通知。

### 2.6.3 `ParseToken`（`:197-207`）：给网关和中间件用

```go

	return &pbauth.ParseTokenResp{
		UserID:            claims.UserID,
		PlatformID:        int32(claims.PlatformID),

	}, nil
}
```

这是 API 层 `GinParseToken` 中间件（`router.go:414`）和 WS 握手（`ws_server.go:511`）共同调用的接口。

**为什么要走 gRPC 而不是各服务自己验？**

因为「token 是否有效」这个判断需要查 Redis。如果每个服务都自己实现一遍，就会出现：
- 密钥配置不一致（有的服务用旧密钥）
- 校验逻辑不一致（有的忘了查状态）

统一到一个 RPC，所有调用方共享同一套逻辑。代价是**每个 HTTP 请求多一次 gRPC 调用**——这也是为什么需要 `AuthLocalCache`（把「查 Redis」变成「查本地内存」，把 RPC 的开销压到最低）。

## 2.7 踢人的三条路径

### 2.7.1 `ForceLogout`：管理员强制下线

`auth.go:209-249`：

```go
func (s *authServer) forceKickOff(ctx context.Context, userID string, platformID int32) error {
	conns, err := s.RegisterCenter.GetConns(ctx, s.config.Discovery.RpcService.MessageGateway)  // ① 找到所有网关
	for _, v := range conns {
		client := msggateway.NewMsgGatewayClient(v)
		kickReq := &msggateway.KickUserOfflineReq{KickUserIDList: []string{userID}, PlatformID: platformID}
		_, err := client.KickUserOffline(ctx, kickReq)   // ② 通知每个网关踢连接
	}
	m, err := s.authDatabase.GetTokensWithoutError(ctx, userID, int(platformID))
	for k := range m {
		m[k] = constant.KickedToken                     // ③ 把所有 token 标记为被踢
		s.authDatabase.SetTokenMapByUidPid(ctx, userID, int(platformID), m)
	}
}
```

**两步都要做**：
- 第 ② 步踢的是**连接**（WebSocket 长连接），让用户立刻掉线
- 第 ③ 步改的是 **token 状态**，防止用户拿旧 token 重连

只做第一步，用户会「掉线后立刻重连成功」；只做第二步，用户当前连接还能用（直到下次请求才被拒）。

**第 ③ 步的代码有个小问题**：`SetTokenMapByUidPid` 在循环里被调用了 N 次，而每次传的都是整个 `m`。第一次循环就把所有 token 都设成被踢了，后面 N-1 次是重复写入。

正确的写法是在循环外调用一次。这是**性能上的冗余**，不是功能 bug。

### 2.7.2 `InvalidateToken`：保留一个，踢掉其他

`auth.go:251-274`：语义是「除了 `preservedToken` 之外全踢」。用于「修改密码后，让其他设备下线，但保留当前设备」。

```go
for k := range m {
	if k != req.GetPreservedToken() {
		m[k] = constant.KickedToken
	}
}
```

注意它**只改状态不踢连接**——被踢的设备不会立刻掉线，下次发请求才会被拒。这和 `ForceLogout` 的策略不同：
- `ForceLogout`：管理员操作，要立刻见效（用户能感知）
- `InvalidateToken`：改密码场景，可以「软踢」（下次请求再拒）

### 2.7.3 `KickTokens`：按 token 批量踢

`auth.go:276-281`：接收一批 token 字符串，逐个解析出 userID/platformID，然后分组批量改状态。

这个接口用于「客户端上报一批要作废的 token」（比如 App 卸载时清本地缓存）。实现在 `controller/auth.go:70-90`：


`continue` 而不是 `return err` 是刻意的：**批量操作要容错**。一批 100 个 token 里有 1 个格式坏的，不该让整批失败。

## 2.8 用户注册：为什么必须是管理员

`internal/rpc/user/user.go:278-334`：

```go
func (s *userServer) UserRegister(ctx context.Context, req *pbuser.UserRegisterReq) (*pbuser.UserRegisterResp, error) {
	if len(req.Users) == 0 {
		return nil, errs.ErrArgs.WrapMsg("users is empty")
	}
	if err = authverify.CheckAdmin(ctx); err != nil {     // ① 只有管理员
		return nil, err
	}
	if datautil.DuplicateAny(req.Users, func(e *sdkws.UserInfo) string { return e.UserID }) {
		return nil, errs.ErrArgs.WrapMsg("userID repeated")  // ② 请求内不能重复
	}
	for _, user := range req.Users {
		if user.UserID == "" {
			return nil, errs.ErrArgs.WrapMsg("userID is empty")
		}
		if strings.Contains(user.UserID, ":") {
			return nil, errs.ErrArgs.WrapMsg("userID contains ':' is invalid userID")  // ③ 不能含冒号
		}
	}
	exist, err := s.db.IsExist(ctx, userIDs)
	if exist {
		return nil, servererrs.ErrRegisteredAlready.WrapMsg("userID registered already")  // ④ 已存在
	}
	if err := s.webhookBeforeUserRegister(ctx, ...); err != nil {   // ⑤ 前置回调
		return nil, err
	}
	// 构造 model.User 批量插入
	s.webhookAfterUserRegister(ctx, ...)                            // ⑥ 后置回调（异步）
}
```

**第 ③ 条「userID 不能含冒号」值得深挖**。为什么？

因为冒号是 OpenIM 内部的**分隔符**：
- token key：`UID_PID_TOKEN_STATUS:{userID}:{platform}`
- 会话 ID：`si_{user1}_{user2}`（这里用下划线，但其他 key 用冒号）
- 在线状态 key、seq key 等都用 `:` 拼

如果 userID 里含冒号，拼接出来的 key 会变成 `UID_PID_TOKEN_STATUS:a:b:ios`，反解析时 `strings.Split` 会得到错的段数，「a:b 的 iOS token」被解析成「用户 a 的 b 端 token」。

这是一个**用输入校验来保护内部 key 设计**的做法。很粗暴，但有效。

> 📌 **可讨论点**：更健壮的做法是对 userID 做转义或哈希（比如 `url.QueryEscape`），而不是禁止。禁止会让「用邮箱当 userID」变得麻烦（邮箱里有 `@` 没事，但如果用 `tenant:user` 这种格式就不行）。这是一个「简单优先」的取舍。

**第 ⑤⑥ 步的 webhook**：OpenIM 允许你在注册前后插手。前置回调可以拒绝注册（返回错误），也可以修改请求（比如强制加前缀）。后置回调是异步的，不阻塞注册返回。

**注意没有「校验昵称长度」「校验头像 URL 格式」这类校验**。这些属于业务规则，OpenIM 不管——它假设调用方（你的业务后端）已经验过了。

这是一个**幂等的启动初始化**：每次启动都执行，但只在「缺」或「昵称不一致」时才写库。所以：
- 第一次启动：创建 `imAdmin`
- 之后启动：什么都不做（除非你改了配置里的昵称）

**为什么管理员不从配置文件「读」而是「写进库」？**

因为用户表是唯一真相。如果每次鉴权都去配置文件里查管理员列表，改配置就得重启所有服务。写进库后，`CheckUserIsAdmin` 查的是 context 里的列表（由 API 层从配置读），而「这个用户存不存在」查的是库——两者解耦。

顺带一提：`AppMangerLevel: constant.AppAdmin` 这个字段，在 `CheckSystemAccount`（`token.go:35`）里被用到。所以管理员账号有两个身份标识：
1. 在 `share.imAdminUser.userIDs` 配置里（决定能不能拿管理员 token）
2. 用户表里的 `app_manger_level >= AppAdmin`（决定业务上算不算管理账号）

```go
	// 1. 查 Redis
	// 2. 命中 → 直接返回
	// 3. 未命中 → 加分布式锁 → 查 Mongo → 回填 Redis → 释放锁
	// 4. 其他等锁的请求 → 拿到锁后发现已有缓存，直接读
}
```

rockscache 的几个关键参数（在 `pkg/localcache` 与配置里）：

| 参数 | 作用 | 典型值 |
|---|---|---|
| `Expire` | 缓存 TTL | 12 小时 |
| `LockExpire` | 分布式锁的过期时间 | 3 秒 |
| `LockSleep` | 抢不到锁时的重试间隔 | 100 毫秒 |
| `RandomExpireAdjustment` | TTL 随机抖动比例 | 0.1（防雪崩） |

**为什么要随机抖动？** 如果 1000 个用户的缓存同时写入、TTL 都是 12 小时，那 12 小时后它们会同时过期，同时回源，Mongo 被打穿。加 10% 抖动后，过期时间散落在 10.8~13.2 小时之间，压力被摊平。这叫**防缓存雪崩**。

**写路径的延迟双删**在哪？在 controller 层的 `UpdateByMap` 之后。这里涉及用户信息更新（`user.go:145` 的 `UpdateUserInfo`）：

```go
if err := s.db.UpdateByMap(ctx, req.UserInfo.UserID, data); err != nil { ... }
s.friendNotificationSender.UserInfoUpdatedNotification(ctx, req.UserInfo.UserID)
```

`UpdateByMap` 内部会删缓存；`UserInfoUpdatedNotification` 会通知所有好友「我的资料变了」，让他们刷新。

## 实验 1：看 token 在 Redis 里长什么样

```bash
# 1. 拿管理员 token
TOKEN=$(curl -s -X POST "http://127.0.0.1:10002/auth/get_admin_token" \
  -H "Content-Type: application/json" -H "operationID: t1" \
  -d '{"secret":"<你的share.secret>","userID":"imAdmin"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)

echo $TOKEN

# 2. 进 Redis 看
docker exec -it openim-redis redis-cli -p 6379   # 容器内端口是 6379，宿主机映射 16379
# 如果上面进不去，用宿主机端口：
# redis-cli -p 16379

SELECT 0
KEYS UID_PID_TOKEN_STATUS:*
HGETALL UID_PID_TOKEN_STATUS:imAdmin:admin
TTL UID_PID_TOKEN_STATUS:imAdmin:admin
```

**预测**：
- `KEYS` 应该只有一条（`imAdmin:admin`）
- `HGETALL` 返回 1 个 field（就是你刚拿到的 token），value 是 `1`
- `TTL` 应该接近 `expire * 86400`（默认 7 天 = 604800）

**验证点**：把 token 贴进 jwt.io 解码，看 payload 里的 `platformID` 是不是 `AdminPlatformID`（通常是 10 或类似值），`exp` 和 `TTL` 是否对得上。

## 实验 2：亲手制造一次「被踢」

```bash
# 连续调两次 get_admin_token，拿两个 token
T1=$(curl ... )
T2=$(curl ... )

# 用 T1 调一个需要权限的接口
curl -s -X POST "http://127.0.0.1:10002/user/user_register" \
  -H "Content-Type: application/json" -H "operationID: t2" -H "token: $T1" \
  -d '{"users":[{"userID":"test001","nickname":"测试"}]}'

# 再用 T2 调同一个接口
# 然后回头用 T1 再调一次
```

**预测**：
- T1 第一次调用：成功
- T2 调用：成功
- T1 第二次调用：**失败**，错误码是 `ErrTokenKicked`（不是 `ErrTokenNotExist`）

**为什么**：`CreateToken` 在签发 T2 时，把管理端的所有旧 token 走 `DeleteAndSetTemporary`——从主 HASH 删掉，但设了 5 分钟临时 key。所以在 5 分钟内，T1 会被 `parseToken` 的「管理员兜底」放行！

**等一下**，那 T1 应该还是能用的。你实际会观察到什么？

去 `HGETALL UID_PID_TOKEN_STATUS:imAdmin:admin` 看——只有 T2，没有 T1。
再去 `KEYS *TEMPORARY*` 看——有 T1 的临时 key。

**结论**：T1 在 5 分钟内**仍然可用**（管理员兜底放行），5 分钟后返回 `ErrTokenNotExist`。

这个实验结果会让你对 2.4.1 末尾那段「5 分钟宽限期」有直观感受。

# 第四部分 · 自测题

> 不要翻回去看。先答，再对照。

**Q1** 认证和授权分别发生在 OpenIM 的哪一层？为什么授权不能只在 API 层做？

<details>
<summary>答案</summary>

认证在 API 层（`GinParseToken`）和网关层（WS 握手时 `ParseToken`）；授权在 RPC 层（每个业务函数开头的 `CheckAccess`/`CheckAdmin`）。

授权不能只在 API 层，因为 RPC 服务可以被内部服务直接调用，绕过 HTTP。把授权写进 RPC 层，等于把门锁装在保险柜上——不管从哪个门进来都要开锁。
</details>

**Q2** JWT 为什么「无法吊销」？OpenIM 怎么补上这个洞？补上之后还是「无状态」吗？

<details>
<summary>答案</summary>

JWT 的校验只依赖签名，服务器不记录发过哪些 token，所以无法让某个 token 提前失效。

OpenIM 用 Redis HASH 存「这个 token 还有效吗」：`UID_PID_TOKEN_STATUS:{userID}:{platform}` → `{token: state}`。校验时除了验签还要查这个 HASH。

补上之后**不是纯无状态了**，但仍有价值：JWT 自带 userID/platformID，Redis 只需回答「有效/无效」，且 HASH 结构支持精确踢人（按端、按 token）。本质是「带吊销名单的 JWT」。
</details>

**Q3** 为什么 token 状态用 HASH 而不是每个 token 一个独立 key？

<details>
<summary>答案</summary>

因为「同端多 token」是常态（重装 App、同端不互踢策略）。用独立 key 要枚举「这个端有哪些 token」就得 `SCAN` 前缀，O(N) 且可能阻塞 Redis。

HASH 可以 `HGETALL` 一次拿全部、`HDEL` 一次删一批，且天然按「用户+端」分组。

另一个原因是 TTL 管理：HASH 只能设整体 TTL，这反而简化了实现——所有 token 共用 `accessExpire`，虽然会导致「旧 token 被新登录续命」的空间浪费，但省去了「每个 field 单独 TTL」的复杂逻辑（Redis 本身不支持 field 级 TTL）。
</details>

**Q4** 用户被踢下线后，为什么错误码是 `ErrTokenKicked` 而不是 `ErrTokenNotExist`？如果踢人时直接删 key 会怎样？

<details>
<summary>答案</summary>

因为踢人是「改状态为 2」而不是删除，`parseToken` 能区分「有但被踢」（`ErrTokenKicked`）和「根本没有」（`ErrTokenNotExist`）。

直接删 key 的话，两种情况都会变成 `ErrTokenNotExist`，客户端无法区分「你被顶下线了」和「登录过期了」，只能笼统提示「请重新登录」。用户体验差，且排查问题时无从下手。
</details>

**Q5** 五种多端登录策略里，`PCAndOther` 的「优先保 Android」是怎么实现的？这段代码有什么隐患？

<details>
<summary>答案</summary>

实现在 `controller/auth.go:191-228`。当前登录的是 PC 时，遍历所有非 PC 端：
- 第一个遇到的非 PC 端：保留它最新的 token（`ts[:len(ts)-1]`），记下这个「待踢的保留 token」
- 后续遇到 Android：把之前保留的那个 token 踢掉，改成保 Android
- 后续遇到其他端：全踢

隐患：`reserveToken` 依赖 `loginTokenMap` 的 map 遍历顺序，而 Go map 遍历是随机的。所以「第一个遇到的非 PC 端」是不确定的。如果用户没有 Android 设备，保留哪个端是随机的（语义上可接受，但不可预测）。

更根本的问题是：`ts[:len(ts)-1]` 假设切片按时间排序，但 `HGetAll` 返回的是 map，顺序随机。「保留最新的」这个语义没有被真正保证。
</details>

**Q6** 为什么 IM 不开放用户自助注册？

<details>
<summary>答案</summary>

因为 IM 是基础设施，不是完整产品。它的用户数据必须和业务系统的账号体系对齐。如果允许自由注册，会出现「业务系统没有这个人但 IM 有」或者「两边 userID 不一致导致发不出消息」。

正确流程是：用户在你的 App 注册 → 你的后端调 `/user/user_register` 创建 IM 用户 → 用户登录你的 App → 你的后端调 `/auth/get_user_token` 换 IM token → 客户端拿这个 token 连 IM。

`UserRegister` 里的 `CheckAdmin` 就是这个设计的代码体现。
</details>

**Q7** 「临时管理员」解决什么问题？它有什么安全前提？

<details>
<summary>答案</summary>

解决「非 API 层发起的内部 RPC 调用拿不到管理员身份」的问题。`IsAdmin` 依赖 context 里的 `CtxAdminUserIDsKey`，而这个值是 API 层中间件塞的。网关、定时任务等内部调用没有经过这个中间件，需要显式调 `WithTempAdmin` 打标记。

安全前提是**内网可信**：只要能连上 gRPC 端口，就能伪造 `RpcCustomHeader` 拿到管理员权限。所以生产环境必须保证 RPC 端口不对外暴露（Docker 内部网络 + 防火墙）。

这不是 OpenIM 独有的问题，所有「内网互信」架构都有这个前提。零信任架构会要求每次调用都带 mTLS 证书或 JWT。
</details>

**Q8** `CheckSystemAccount(ctx, level)` 和 `IsSystemAdmin(ctx)` 有什么区别？一个 `app_manger_level = AppAdmin` 的用户调管理接口一定成功吗？

<details>
<summary>答案</summary>

`CheckSystemAccount` 看的是**用户表里的等级字段**（数据驱动）；`IsSystemAdmin` 看的是**配置里的管理员 ID 列表**（配置驱动）。

不一定成功。`CheckAdmin` 走的是 `IsAdmin` → `IsSystemAdmin`，要求 userID 在 `share.imAdminUser.userIDs` 里。如果这个用户只是 `app_manger_level = AppAdmin` 但不在配置列表里，会被拒。

这是「业务角色」和「运维角色」的区别：前者用于第三方推送、通知账号等业务场景，后者才有调管理接口的权限。
</details>

# 第五部分 · 面试话术

## 5.1 30 秒版本

> OpenIM 的用户鉴权是「JWT + Redis 白名单」的混合方案。JWT 负责携带身份（userID、platformID），Redis HASH 负责「这个 token 还有效吗」。选这个方案是因为纯 JWT 无法吊销、纯 Session 每次都要查存储。
>
> 用 HASH 而不是独立 key，是为了支持「同端多 token」的场景——`HGETALL` 一次拿到这个端的全部 token，`HDEL` 一次删一批，还能区分「被踢」和「不存在」两种失败原因。
>
> 认证在 API 层和网关层做，授权在 RPC 层做。因为 RPC 能被内部服务直接调用，授权写在 RPC 层才能保证「不管从哪个门进来都要开锁」。整个项目的授权只有两个函数：`CheckAdmin`（我是管理员吗）和 `CheckAccess`（我是这个人吗，或者是管理员吗）。

## 5.2 3 分钟版本（含追问预判）

**开场**：讲 token 生命周期五阶段（签发→携带→校验→踢出→过期），重点讲「踢出为什么是改状态不是删除」。

**中间**：讲 `CreateToken` 的执行顺序——先踢人再发牌，保证任意时刻同端最多一个有效 token。展开五种多端登录策略，举 `PCAndOther` 的例子（电脑随便登、手机只留一个、优先保 Android）。

**收尾**：讲两条鉴权范式，以及「为什么权限规则要收敛成两个函数」——可审计性。grep `CheckAdmin` 就能列出所有需要管理员的接口。

**预判追问**：

| 追问 | 回答要点 |
|---|---|
| 「Redis 挂了会怎样？」 | 所有 token 校验失败，全站不可用。这是单点。改进方向：本地缓存兜底（OpenIM 有 `AuthLocalCache`，但缓存 miss 仍要查 Redis）、或降级为「只验签不查状态」（安全性下降但可用） |
| 「JWT 放 header 还是 cookie？」 | OpenIM 放 header（`token` 字段）。因为客户端是 App/小程序不是浏览器，没有自动带 cookie 的机制，且能避免 CSRF |
| 「token 泄露了怎么办？」 | 用户改密码后调 `InvalidateToken`（保留当前设备，踢掉其他）；管理员可以 `ForceLogout`。但如果是当前设备的 token 泄露，只能等它过期——这是 JWT 的固有缺陷，需要配合短有效期 + refresh token 来解决 |
| 「为什么 admin 的 platformID 要单独？」 | 因为管理端和用户端是隔离的：管理端 token 存在独立的 HASH 里，登录时清空旧管理端 token（管理后台只允许一处登录），且普通 token 接口不允许签 `AdminPlatformID` |
| 「多节点下踢人怎么保证一致？」 | `ForceLogout` 会遍历所有网关节点调 `KickUserOffline`，同时改 Redis 里的 token 状态。前者让连接立刻断，后者防止用旧 token 重连。网关节点列表来自服务发现 |
| 「临时管理员的 5 分钟宽限期合理吗？」 | 权衡题。合理的一面：避免正在进行的操作被硬中断。风险：旧 token 在 5 分钟内仍可操作。改进：缩短到 30 秒 + 响应里提示「账号已在别处登录」 |

## 5.3 可以主动抛出的「我读代码时发现的问题」

面试时最加分的不是背架构，是**指出问题**。下面三个都是真的：

1. **`token.go:88-91` 的 `temp` 是死代码**：创建、填充，然后从未使用。原意可能是 `keys = append(temp, ctxTempAdminKey)`，后来改成直接 append 到 `keys`，`temp` 忘了删。`go vet` 抓不到（因为被 append 过算「使用」）。

2. **`controller/auth.go:170-181` 策略 0 的 `ts[:l-limit]` 依赖顺序**，但 `ts` 来自 `HGetAll` 返回的 map，顺序随机。所以「踢最早的」这个语义没有保证。同理 `:185`、`:188`、`:197` 的 `ts[len(ts)-1]` 也假设了「最新的在最后」。

3. **`auth.go:238-247` 的 `SetTokenMapByUidPid` 在循环里调用 N 次，每次都传整个 map**。第一次就把所有 token 设成被踢了，后面 N-1 次是重复写入。应该移到循环外。
