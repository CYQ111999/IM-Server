# 第一部分 · 纯理论

## 1.1 会话是什么

打开微信，首页那一列就是「会话列表」：

```
┌──────────────────────────┐
│ 群聊A          3 条新消息 │
│ 张三           昨天       │
│ 群聊B          12:30     │
└──────────────────────────┘
```

每一行就是一个「会话」（conversation）。它包含：
- 对方是谁（单聊的话是用户，群聊的话是群）
- 最后一条消息的摘要
- 未读数
- 时间
- 是否置顶
- 是否免打扰

**关键认知：会话是一个「用户视角的视图」，不是「消息的容器」。**

同一个群，对 A 来说这个会话是「置顶的、免打扰的、有 3 条未读」；对 B 来说可能是「没置顶、不免打扰、全部已读」。

**所以会话是「用户 × 对话对象」的笛卡尔积上的一行数据**，而不是「对话对象」本身。

这就是为什么会话表的主键是 `(owner_user_id, conversation_id)`：
- `conversation_id` 标识「哪个对话」（A 和 B 的对话，或者群 G）
- `owner_user_id` 标识「谁的视角」

一个 500 人的群，会话表里有 500 行（每人一行）。每行的 `max_seq` 相同（都是群的最新 seq），但 `has_read_seq`/`is_pinned`/`recv_msg_opt` 各不相同。

## 1.2 能不能不建会话表

理论上，会话列表可以从消息表算出来：

```sql
-- 伪 SQL
SELECT conversation_id, MAX(seq), COUNT(*)
FROM message
WHERE conversation_id IN (我参与的所有会话) AND seq > 我的已读位置
GROUP BY conversation_id
```

**为什么不行？** 四个原因：

**（1）性能**。用户有 200 个会话，每个会话有几千条消息。`GROUP BY` 要扫大量数据。而会话表是 200 行的直接读取。

**（2）有些信息消息表里没有**。置顶、免打扰、草稿、@ 我的状态——这些是「会话的属性」，和消息无关。

**（3）空会话无法表达**。用户主动创建了一个会话（比如点开某人但没发消息），消息表里没有记录，但会话列表里应该有这一行。

**（4）已删除的会话无法表达**。用户删除了一个会话（清空了消息），消息表里可能还有数据（其他人还能看到），但这个用户的会话列表里不该有。

所以会话表是**必需的冗余**：它是「消息 + 用户偏好」的物化视图，为了读性能而存在。

> 📌 记忆点：**会话表 = 消息的索引 + 用户的偏好。** 它不是消息的容器，是「这个用户怎么看待这个对话」的记录。

## 1.3 会话 ID 的设计

`pkg/msgprocessor/conversation.go:85-101`：

```go
func GetConversationIDBySessionType(sessionType int, ids ...string) string {
	sort.Strings(ids)                          // ← 关键：先排序
	if len(ids) > 2 || len(ids) < 1 {
		return ""
	}
	switch sessionType {
	case constant.SingleChatType:
		return "si_" + strings.Join(ids, "_")
	case constant.WriteGroupChatType:
		return "g_" + ids[0]
	case constant.ReadGroupChatType:
		return "sg_" + ids[0]
	case constant.NotificationChatType:
		return "sn_" + strings.Join(ids, "_")
	}
	return ""
}
```

四种前缀：

| 前缀 | 用途 | 例子 |
|---|---|---|
| `si_` | 单聊（single） | `si_userA_userB` |
| `g_` | 群聊（group） | `g_123456` |
| `sg_` | 超大群（super group） | `sg_123456` |
| `sn_` | 服务端通知会话（server notification） | `sn_userA_userB` |

**`sort.Strings(ids)` 是精髓**。A 发给 B 和 B 发给 A，拼出来的会话 ID 必须相同：

```go
sort.Strings([]string{"userB", "userA"})  // → ["userA", "userB"]
// "si_userA_userB"
```

如果忘了排序，A 看到的是 `si_userA_userB`，B 看到的是 `si_userB_userA`——**两个人会在两个不同的会话里聊天**，消息互相看不见。

这是个「一行代码决定系统能否工作」的例子。

**`g_` 和 `sg_` 的区别**：`WriteGroupChatType`（写扩散群）vs `ReadGroupChatType`（读扩散群）。

- 写扩散：消息写进每个成员的收件箱（每人一份）
- 读扩散：消息只写一份，成员按需拉取

OpenIM 实际用的是 `ReadGroupChatType`（`group.go:431` 生成 `sg_` 前缀），也就是读扩散。`g_` 前缀是历史遗留或未启用的模式。

> ⚠️ **命名陷阱**：`sg_` 里的 `s` 不是「super」，更可能是「session + group」。而 `WriteGroupChatType` 的 `g_` 反而没有 `s`。这套命名是历史积累的产物，不要从字面猜语义。

### 通知会话：`n_` 前缀

`conversation.go:54-83` 的 `GetConversationIDByMsg` 是关键：

```go
func GetConversationIDByMsg(msg *sdkws.MsgData) string {
	options := Options(msg.Options)
	switch msg.SessionType {
	case constant.SingleChatType:
		l := []string{msg.SendID, msg.RecvID}
		sort.Strings(l)
		if !options.IsNotNotification() {
			return "n_" + strings.Join(l, "_")     // ← 通知消息 → n_ 会话
		}
		return "si_" + strings.Join(l, "_")
	// ...
	}
}
```

**同一个单聊，有两种会话 ID**：

| 消息类型 | 会话 ID | 例子 |
|---|---|---|
| 普通消息 | `si_` | `si_userA_userB` |
| 通知消息 | `n_` | `n_userA_userB` |

**通知消息（好友申请、群成员变更、已读回执等）不进入正常会话，而是进入 `n_` 会话。**

为什么要这样？

**（1）通知消息不该影响未读数。** 「B 同意了你的好友申请」这条消息，如果算进未读数，用户的「未读消息」里会混着系统通知。

**（2）通知消息不该改变会话排序。** 如果通知也算「最后一条消息」，会话列表会频繁跳动。

**（3）通知消息不需要落库到正常消息表。** `n_` 会话的消息可以单独处理（或者只推不存）。

**（4）客户端可以单独决定是否显示。** 有些产品把通知单独放在「系统消息」里，有些直接过滤掉。

`IsNotification` 判断的就是这个前缀（`conversation.go:103-105`）：

```go
func IsNotification(conversationID string) bool {
	return strings.HasPrefix(conversationID, "n_")
}
```

三处调用：
- `internal/msggateway/client.go:250`：推送时判断，决定是否发送
- `internal/push/push_handler.go:314`：离线推送时判断
- `internal/rpc/msg/sync_msg.go:25`：拉消息时**跳过**通知会话

第三处最关键——**拉历史消息时，通知会话的消息不会被拉下来**（除非客户端单独请求 `n_` 会话）。

> 📌 **这是理解 OpenIM 消息模型的关键一环**。你在客户端看到「系统消息」和「聊天消息」分开，根源就在这个 `n_` 前缀。

**注意 `GetConversationIDBySessionType` 里也定义了 `sn_` 前缀**（`:97-98`），但 `GetConversationIDByMsg` 只有在「通知会话 + 非通知消息」时才返回 `sn_`——这是一个几乎不会出现的组合（通知会话里放非通知消息）。

`sn_` 更像是一个未完成的设想。实际运行中，会话 ID 只有 `si_`、`sg_`、`n_` 三种。

## 1.4 未读数：减法模型

14 篇讲过，这里从「会话」的角度再讲一遍。

### 朴素做法：数出来

```sql
SELECT COUNT(*) FROM message
WHERE conversation_id = 'xxx' AND seq > 我的已读位置 AND 不是我发的
```

问题：
- 每次打开会话列表，200 个会话要 200 次 count（或者一次复杂的聚合）
- 消息表是分桶存储的（100 条一个文档），count 要遍历多个文档

### OpenIM 的做法：减法

```go
// internal/rpc/conversation/conversation.go:166-170
for conversationID, maxSeq := range maxSeqs {
	unreadCount := maxSeq - hasReadSeqs[conversationID]
	conversation_unreadCount[conversationID] = unreadCount
	unreadTotal += unreadCount
}
```

**未读数 = 会话最大 seq - 我的已读 seq**。

这个公式成立需要四个前提（14 篇详细讲过，这里列结论）：

| 前提 | 保证方式 |
|---|---|
| seq 在会话内**严格连续无空洞** | 12 篇的号段分配，空洞用占位消息填 |
| 每条消息**恰好占一个 seq** | 撤回不删消息，只改状态 |
| **自己发的消息也占 seq** | 所以要在 `hasReadSeq` 里跟上自己发的 |
| `hasReadSeq` 是**单调不减**的 | 已读水位只增不减 |

第三个前提容易被忽略：如果你发了 10 条消息，对方没回，你的未读数应该是 0（你自己发的消息不算未读）。所以发送消息时，**要把自己的 `hasReadSeq` 也推到最新 seq**。

这就是为什么「发消息」这个操作会更新两条会话记录（发送方和接收方）。📌 待验证具体实现：`CreateSingleChatConversations` 只创建不更新，更新可能在 msgtransfer 里。

### 减法的边界情况

如果 `hasReadSeq > maxSeq`（已读位置超过了最新消息），减出来是负数。这在正常情况下不会发生，但如果有并发或者数据损坏，可能出现。

代码里没有做 `max(0, ...)` 的保护——`unreadCount` 可能为负。客户端如果直接显示负数会很难看。

📌 **这是一个潜在的健壮性问题**。实际影响取决于 `hasReadSeq` 怎么维护（如果只会被设成「当前 maxSeq」，就不会超过）。

## 1.5 会话排序

会话列表的排序规则通常是：

```
1. 置顶的排前面
2. 置顶的之间按「最后消息时间」倒序
3. 非置顶的之间按「最后消息时间」倒序
```

`internal/rpc/conversation/conversation.go:172-204`：

```go
conversation_isPinTime := make(map[int64]string)
conversation_notPinTime := make(map[int64]string)

for _, v := range conversations {
	conversationID := v.ConversationID
	var time int64
	if _, ok := conversationMsg[conversationID]; ok {
		time = conversationMsg[conversationID].MsgInfo.LatestMsgRecvTime   // 最后消息时间
	} else {
		conversationMsg[conversationID] = &pbconversation.ConversationElem{...}
		time = v.CreateTime.UnixMilli()                                    // 没有消息就用创建时间
	}

	if v.IsPinned {
		conversation_isPinTime[time] = conversationID      // ← ⚠️ 用时间戳当 map key
		continue
	}
	conversation_notPinTime[time] = conversationID
}
c.conversationSort(conversation_isPinTime, resp, conversation_unreadCount, conversationMsg)
c.conversationSort(conversation_notPinTime, resp, conversation_unreadCount, conversationMsg)
```

**这里有一个真实的 bug**：`map[int64]string` 用**时间戳当 key**。

如果两个会话的 `LatestMsgRecvTime` 相同（同一毫秒收到两条消息，完全可能），后者会**覆盖**前者——**丢了一个会话**。

这在活跃用户身上很容易发生：群 A 和群 B 在同一毫秒各来一条消息，会话列表就少一个。

**正确写法**应该是 `map[int64][]string`（时间戳 → 会话 ID 列表），排序时同时间的按 ID 再排。

或者用切片 + `sort.Slice`：

```go
type convWithTime struct {
	id   string
	t    int64
}
list := make([]convWithTime, 0, len(conversations))
// ...
sort.Slice(list, func(i, j int) bool { return list[i].t > list[j].t })
```

> 📌 **这是本篇最有价值的发现**。面试时讲「我发现会话排序用时间戳做 map key，同一毫秒会覆盖」，比背架构图有说服力得多。

`conversationSort`（`:526-546`）的实现：

```go
func (c *conversationServer) conversationSort(conversations map[int64]string, resp *..., conversation_unreadCount map[string]int64, conversationMsg map[string]*...) {
	keys := []int64{}
	for key := range conversations {
		keys = append(keys, key)
	}
	// 然后大概是 sort.Sort 倒序，再按 key 取 conversationID 追加到 resp
}
```

先收集所有时间戳，排序，再按顺序取会话——因为 map 无序，必须先排序 key。

**为什么排序在服务端做？**

因为客户端的数据可能不全（分页拉取）。如果客户端只拉了前 20 个会话，它无法正确排序全部 200 个。服务端知道全部数据，排序后才分页返回（`:206`）：

```go
resp.ConversationElems = datautil.Paginate(resp.ConversationElems, int(req.Pagination.GetPageNumber()), int(req.Pagination.GetShowNumber()))
```

**代价是每次拉会话列表都要排序全部会话**。200 个会话排序大概是微秒级，可接受。但如果是 2000 个会话（重度用户），就会开始有压力。

优化方向：把排序结果缓存起来，或者按「置顶/非置顶」分开维护有序结构。OpenIM 没做。

### 排序用的时间：`LatestMsgRecvTime` 而不是 `LatestMsgSendTime`

注意用的是 `LatestMsgRecvTime`（接收时间）而不是发送时间。

为什么？因为多端同步时，消息的「发送时间」由发送方决定，可能不准（客户端时钟）。而「接收时间」是服务端在处理消息时打的，可信。

📌 这涉及 `MsgData` 里两个时间字段的区别，具体见 13 篇。

## 1.6 免打扰：三态而不是布尔

`model/conversation.go:17` 的 `RecvMsgOpt` 是个 int32，不是 bool：

| 值 | 含义 | 行为 |
|---|---|---|
| 0 | 正常接收 | 收消息、算未读、推送 |
| 1 | 接收但不通知 | 收消息、算未读、**不推送** |
| 2 | 不接收 | **不收消息**（或者说收但不展示） |

**为什么是三态？**

因为「免打扰」和「不接收」是两件事：
- **免打扰**：消息还是要来的（会话列表里的未读数要涨），只是不弹通知、不响铃
- **不接收**：连未读数都不涨（比如退订的营销群）

如果用 bool，只能表达「打扰/不打扰」，无法表达「完全不收」。

### 免打扰在哪里生效

**（1）离线推送过滤**，`conversation.go:502-524`：

```go
func (c *conversationServer) GetConversationOfflinePushUserIDs(ctx, req) (*pbconversation.GetConversationOfflinePushUserIDsResp, error) {
	// 查出"不接收消息"的用户
	userIDs, err := c.conversationDatabase.GetConversationNotReceiveMessageUserIDs(ctx, req.ConversationID)
	if len(userIDs) == 0 {
		return &pbconversation.GetConversationOfflinePushUserIDsResp{UserIDs: req.UserIDs}, nil
	}
	// 从候选里剔掉
	userIDSet := make(map[string]struct{})
	for _, userID := range req.UserIDs {
		userIDSet[userID] = struct{}{}
	}
	for _, userID := range userIDs {
		delete(userIDSet, userID)
	}
	return &pbconversation.GetConversationOfflinePushUserIDsResp{UserIDs: datautil.Keys(userIDSet)}, nil
}
```

推送服务在群发离线推送前，先问会话服务：「这个群里哪些人不该收到？」然后剔掉。

**注意函数名是 `GetConversationNotReceiveMessageUserIDs`**——只查「不接收」（opt=2），不查「免打扰」（opt=1）。

那 opt=1 的免打扰在哪过滤？

📌 **待验证**：可能在 push 服务里，或者客户端收到推送后自己决定是否展示。iOS/Android 的推送到达客户端后，客户端可以判断「这个会话免打扰」然后静默处理。但那样推送还是消耗了流量和电量。

更好的做法是服务端过滤。需要在 `internal/push` 里找 `RecvMsgOpt` 的使用。

**（2）未读数**：opt=2 时不该涨未读。这个逻辑在 msgtransfer 里（决定是否更新会话的 maxSeq）。

**（3）会话列表的排序**：免打扰的会话通常不参与「新消息上浮」。OpenIM 没做这个，客户端可以自己处理。

## 1.7 会话的 13 个字段

`pkg/common/storage/model/conversation.go:7-27` 的完整结构：

```go
type Conversation struct {
	OwnerUserID           string    `bson:"owner_user_id"`            // 1. 谁的会话
	ConversationID        string    `bson:"conversation_id"`          // 2. 哪个对话
	ConversationType      int32     `bson:"conversation_type"`        // 3. 单聊/群聊/通知
	UserID                string    `bson:"user_id"`                  // 4. 单聊对方
	GroupID               string    `bson:"group_id"`                 // 5. 群聊的群
	RecvMsgOpt            int32     `bson:"recv_msg_opt"`             // 6. 免打扰三态
	IsPinned              bool      `bson:"is_pinned"`                // 7. 是否置顶
	IsPrivateChat         bool      `bson:"is_private_chat"`          // 8. 是否私密聊天
	BurnDuration          int32     `bson:"burn_duration"`            // 9. 阅后即焚时长（秒）
	GroupAtType           int32     `bson:"group_at_type"`            // 10. @ 我的类型
	AttachedInfo          string    `bson:"attached_info"`            // 11. 扩展信息（草稿等）
	Ex                    string    `bson:"ex"`                       // 12. 业务扩展
	MaxSeq                int64     `bson:"max_seq"`                  // 13. 最新消息 seq
	MinSeq                int64     `bson:"min_seq"`                  // 14. 最小可见 seq
	CreateTime            time.Time `bson:"create_time"`              // 15. 创建时间
	IsMsgDestruct         bool      `bson:"is_msg_destruct"`          // 16. 是否开启阅后即焚
	MsgDestructTime       int64     `bson:"msg_destruct_time"`        // 17. 焚毁时间（秒）
	LatestMsgDestructTime time.Time `bson:"latest_msg_destruct_time"` // 18. 最近一次焚毁时间
}
```

（实际是 18 个字段，不是 13 个。我一开始数少了——这也说明「不要凭印象说数字」。）

逐个解释：

**1-2. `OwnerUserID` + `ConversationID`**：复合主键。同一个对话，每个人一行。

**3. `ConversationType`**：冗余字段。可以从 `ConversationID` 的前缀推出来（`si_` → 单聊），但存一份避免每次解析字符串。

**4. `UserID`**：单聊时的对方 userID。群聊时为空。

**5. `GroupID`**：群聊时的 groupID。单聊时为空。

这两个字段是**冗余索引**：想「查我和某人的会话」时，可以用 `UserID` 直接查，不用拼 `si_` 前缀（虽然也能拼）。

**6. `RecvMsgOpt`**：前文 1.6 讲过了。

**7. `IsPinned`**：置顶。排序的第一优先级。

**8. `IsPrivateChat`**：私密聊天（阅后即焚的另一种叫法？）。和 `IsMsgDestruct` 的区别需要看代码。📌 待验证。

**9. `BurnDuration`**：阅后即焚的时长。

**10. `GroupAtType`**：群里的 @ 类型。这是**给会话列表做红点提示用的**：

| 值 | 含义 |
|---|---|
| 0 | 没有 @ |
| 1 | @ 我 |
| 2 | @ 所有人 |
| 3 | @ 我和所有人 |

客户端据此在会话上显示「[有人@我]」的提示。

**11. `AttachedInfo`**：扩展信息。最典型的用途是**草稿**——你在会话里打了个字没发，退出后草稿要保留。存这里。

**12. `Ex`**：业务扩展字段。给使用方自己用的。

**13. `MaxSeq`**：这个会话的最新消息 seq。**注意这与会话实际的最大 seq 可能不同**：
- 群会话的 `max_seq` 是所有消息的最大 seq
- 但如果你被踢出群，你的 `max_seq` 会被冻结（18 篇讲的 `SetConversationMaxSeq`）

**14. `MinSeq`**：最小可见 seq。用于：
- 清空聊天记录（设成当前 maxSeq）
- 阅后即焚（设成焚毁位置）
- 被踢出群后保留历史

**15-18. 阅后即焚相关**：
- `IsMsgDestruct`：是否开启
- `MsgDestructTime`：每条消息活多久（秒）
- `LatestMsgDestructTime`：上次焚毁的时间点（用于批量清理）

**字段数量的启示**：一个「会话」看似简单，实际承载了排序、未读、免打扰、@提示、草稿、阅后即焚六种功能。**这就是为什么它必须单独建表**——消息表存不下这些用户偏好。

## 1.8 会话的懒创建

会话是什么时候创建的？

**不是**「用户注册时给每个可能的关系建一个会话」（那是 N² 的组合爆炸）。

**而是**「第一条消息发出时创建」。

`conversation.go:369-426` 的 `CreateSingleChatConversations` 的注释说得很清楚：

```go
// 为消息 Redis 转存创建会话，不发送通知。
func (c *conversationServer) CreateSingleChatConversations(ctx context.Context, req *pbconversation.CreateSingleChatConversationsReq) ...
```

**「为消息 Redis 转存创建会话」**——它是在 msgtransfer 把消息写进 Redis 时调用的，不是用户主动创建。

**为什么懒创建？**

因为不可能预知谁会给谁发消息。1 万个用户，理论上 5000 万个单向关系，不可能都建会话。

**代价**：第一次查会话列表时，可能某些会话不存在（用户点开某人但没发消息，就没有会话）。这时客户端要自己构造一个「空会话」。

**一个细节**：`CreateSingleChatConversations` 里创建失败只 `log.ZWarn` 不返回错误（`:385-388`）：

```go
err := c.conversationDatabase.CreateConversation(ctx, []*dbModel.Conversation{&conversation})
if err != nil {
	log.ZWarn(ctx, "create conversation failed", err, "conversation", conversation)
}
```

**这是有意的**：会话创建失败不该阻塞消息投递。消息已经写进 Redis 了，会话没有只是「列表里看不到」，用户还能收到消息推送。

但这会留下一个**不一致**：消息存在，会话不存在。修复方式大概是下次发消息时再试一次创建（`CreateConversation` 应该是 upsert）。

📌 待验证：`CreateConversation` 是否用 upsert。

**单聊要创建两条**（`:376-406`）：发送方视角和接收方视角各一条。

```go

conversation.OwnerUserID = req.SendID
conversation.UserID = req.RecvID
c.conversationDatabase.CreateConversation(ctx, []*dbModel.Conversation{&conversation})

// 接收方视角

conversation2.UserID = req.SendID
```

注意 `conversation2 := conversation` 是**值拷贝**（struct 赋值）。如果 `Conversation` 里有指针或 slice 字段，拷贝会共享底层数据——好在它全是值类型（string/int/bool/time.Time），安全。

**群聊只创建一条**（`CreateGroupChatConversations`）——但**给每个成员**：

## 1.9 会话删除与阅后即焚

### 删除会话

`conversation.go:768+` 的 `DeleteConversations`，有两个互斥的参数：

### 阅后即焚

`conversation.go:720-748` 的 `ClearUserConversationMsg`：

```go
func (c *conversationServer) ClearUserConversationMsg(ctx context.Context, req *pbconversation.ClearUserConversationMsgReq) (*pbconversation.ClearUserConversationMsgResp, error) {
	conversations, err := c.conversationDatabase.FindRandConversation(ctx, req.Timestamp, int(req.Limit))
	latestMsgDestructTime := time.UnixMilli(req.Timestamp)

	for i, conversation := range conversations {
		if !conversation.IsMsgDestruct || conversation.MsgDestructTime == 0 {
			continue                                          // 没开启阅后即焚，跳过
		}
		// 找出「应该被焚毁」的消息的 seq
		seq, err := c.msgClient.GetLastMessageSeqByTime(ctx, conversation.ConversationID,
			req.Timestamp-(conversation.MsgDestructTime*1000))    // ← 当前时间 - 存活时长
		if seq <= 0 {
			// 没有需要焚毁的
			c.setConversationMinSeqAndLatestMsgDestructTime(ctx, ..., -1, latestMsgDestructTime)
			continue
		}
		seq++
		c.setConversationMinSeqAndLatestMsgDestructTime(ctx, ..., seq, latestMsgDestructTime)
	}
	return &pbconversation.ClearUserConversationMsgResp{Count: int32(len(conversations))}, nil
}
```

**核心思想**：阅后即焚**不删除消息**，而是**抬高 `min_seq`**。

```
假设 MsgDestructTime = 60 秒（消息活 60 秒）
当前时间 T，那么 T-60 之前的消息都该"焚毁"
GetLastMessageSeqByTime(conv, T-60) → 找到 seq=100（T-60 时刻的最后一条）
min_seq = 101 → 用户只能看到 seq >= 101 的消息
```

**为什么不真删？**

因为群聊的消息是共享的。A 的阅后即焚设置不该影响 B 的可见性。抬高 A 的 `min_seq` 只影响 A 自己。

而且真删是物理操作，不可逆。抬 `min_seq` 是逻辑操作，改一个数字就行。

**`seq++` 的原因**：`GetLastMessageSeqByTime` 返回的是「时间点之前的最后一条」，也就是「最后一条该被删的」。`min_seq` 是「第一条可见的」，所以是 `seq + 1`。

**`FindRandConversation(timestamp, limit)`** 用的是「随机取一批」——因为要处理全站所有会话，一次处理不完，分批轮询。这个函数大概是用 `$sample` 或者按时间分片。

**`latestMsgDestructTime`** 记录「上次处理到哪个时间点」，用于断点续传和监控延迟。

## 1.10 会话变更通知

会话的很多字段变了要让客户端知道（置顶、免打扰、已读）。

`conversationNotificationSender.ConversationChangeNotification(ctx, userID, conversationIDs)`。

它的实现应该是发一条「会话变了」的通知消息，让客户端重新拉这几个会话的最新状态。

**为什么不用「推送新状态」而是「通知变更」？**

因为会话状态有 18 个字段，全推太大，而且容易不一致。发一条「convA 变了」的轻量通知，客户端自己来拉，简单可靠。

这是**「通知 + 拉取」模式**（notify-and-fetch），比「推数据」更常见：
- 通知小，省带宽
- 客户端拉的是权威数据
- 天然支持批量（一次通知多个会话）

代价是多一次往返（收到通知 → 发请求拉 → 拿到数据）。对会话变更这种低频操作，完全可接受。

## 2.2 会话列表：完整流程

`conversation.go:123-208`，六步：

```go
func (c *conversationServer) GetSortedConversationList(ctx context.Context, req *pbconversation.GetSortedConversationListReq) (resp *pbconversation.GetSortedConversationListResp, err error) {
	// ① 授权
	if err := authverify.CheckAccess(ctx, req.UserID); err != nil {
		return nil, err
	}

	// ② 拿到会话 ID 列表（不传就用全部）
	var conversationIDs []string
	if len(req.ConversationIDs) == 0 {
		conversationIDs, err = c.conversationDatabase.GetConversationIDs(ctx, req.UserID)
		if err != nil {
			return nil, err
		}
	} else {
		conversationIDs = req.ConversationIDs
	}

	// ③ 查会话详情
	conversations, err := c.conversationDatabase.FindConversations(ctx, req.UserID, conversationIDs)
	if len(conversations) == 0 {
		return nil, errs.ErrRecordNotFound.Wrap()
	}

	// ④ 查每个会话的最大 seq
	maxSeqs, err := c.msgClient.GetMaxSeqs(ctx, conversationIDs)

	// ⑤ 查每个会话的最后一条消息（用于显示摘要和时间）
	chatLogs, err := c.msgClient.GetMsgByConversationIDs(ctx, conversationIDs, maxSeqs)
	conversationMsg, err := c.getConversationInfo(ctx, chatLogs, req.UserID)

	// ⑥ 查我的已读位置，算未读
	hasReadSeqs, err := c.msgClient.GetHasReadSeqs(ctx, conversationIDs, req.UserID)
	var unreadTotal int64
	conversation_unreadCount := make(map[string]int64)
	for conversationID, maxSeq := range maxSeqs {
		unreadCount := maxSeq - hasReadSeqs[conversationID]
		conversation_unreadCount[conversationID] = unreadCount
		unreadTotal += unreadCount
	}
	// ... 排序 + 分页
}
```

**三次跨服务调用**：`GetMaxSeqs`、`GetMsgByConversationIDs`、`GetHasReadSeqs`。都是批量接口（传一组 conversationID）。

**为什么是三次而不是一次？** 因为它们在 msg 服务里是不同的数据源：
- `GetMaxSeqs`：查 Redis 的 seq 缓存
- `GetMsgByConversationIDs`：查消息表（Mongo）
- `GetHasReadSeqs`：查 Redis 的已读水位

合并成一个 RPC 也行，但会让 msg 服务的接口变复杂。**分开的好处是每个都能独立优化/缓存**。

**代价是三次网络往返**。对「打开 App 看会话列表」这个高频操作，延迟是累积的。

优化方向：在 msg 服务里加一个组合接口（`GetConversationListMeta`），一次返回三者。OpenIM 没做。

## 2.4 会话状态的更新

`conversation.go:633-682` 的 `UpdateConversation` 是**改变会话字段的统一入口**：

```go

	}
	if req.Ex != nil {
		m["ex"] = req.Ex.Value
	}

		m["is_pinned"] = req.IsPinned.Value

	if req.GroupAtType != nil {
		m["group_at_type"] = req.GroupAtType.Value
	}
	if req.MsgDestructTime != nil {
		m["msg_destruct_time"] = req.MsgDestructTime.Value
	}
	if req.IsMsgDestruct != nil {
		m["is_msg_destruct"] = req.IsMsgDestruct.Value
	}
	if req.BurnDuration != nil {
		m["burn_duration"] = req.BurnDuration.Value
	}
	if req.IsPrivateChat != nil {
		m["is_private_chat"] = req.IsPrivateChat.Value
	}
	if req.MinSeq != nil {

	if req.MaxSeq != nil {

			return nil, err
		}
	}

```

**这个模式叫「部分更新」或「PATCH 语义」**：

- 用 `*bool`、`*int32` 之类的指针，null 表示「不更新这个字段」
- 用 `map[string]any` 收集，只写有值的
- Mongo 的 `$set` 天然支持部分更新

**为什么不用 `UpdateConversationReq` 里的完整对象覆盖？**

因为会**丢失未传的字段**。比如只想改置顶，传了一个只设了 `IsPinned` 的对象，其他字段是零值——全量覆盖会把 `recv_msg_opt`、`attached_info` 都清空。

**代价是代码冗长**：17 个 `if`，每个字段三行。这是「部分更新」不可避免的样板代码。

优化方向：用反射或代码生成（protobuf 的 `fieldmask` 就是干这个的）。但 Go 里手写更清晰可控。

**注意 `:653` 的 `time.UnixMilli(req.LatestMsgDestructTime.Value)`**：其他字段直接传值，这个要转成 `time.Time`。因为模型里这个字段是 `time.Time` 类型，其他是 int。

- 遗漏：应该服务端过滤，省流量和电量

📌 **这个问题值得在面试时提出来**：「如果让我改，我会在 `GetConversationOfflinePushUserIDs` 里同时过滤 opt=1，把免打扰的判断收到服务端，而不是依赖客户端的通知渠道。」

## 2.7 会话缓存的失效

会话的缓存维度多（8 个），失效是个麻烦事。

看 `DeleteConversations` 和 `UpdateConversation` 之后要删哪些缓存：

**改置顶**（`IsPinned` 变化）：
- 会话详情缓存
- 置顶列表缓存

**改免打扰**（`RecvMsgOpt` 变化）：
- 会话详情缓存
- 免打扰列表缓存
- 「不接收消息的用户」列表缓存

**改已读**（`hasReadSeq` 变化）：
- 已读水位缓存
- 会话详情缓存（因为未读数变了）

**删会话**：
- 会话详情
- 会话 ID 列表
- 置顶列表
- 免打扰列表
- 已读水位
- 版本号

📌 **具体实现需要读 `controller/conversation.go` 的 `Delete`/`UpdateUsersConversationField`**。从 `DeleteConversations` 的实现看，应该有类似的 `ChainExecDel` 模式。

**这就是「多维缓存」的代价**：8 个维度，任何一个更新都要维护对应的几个。漏一个就出现不一致。

## 2.8 会话与消息的耦合点

会话模块本身不存消息，但它依赖消息模块的三样东西：

| 依赖 | 用途 | 调用频率 |
|---|---|---|
| `GetMaxSeqs` | 算未读、排序 | 每次拉列表 |
| `GetMsgByConversationIDs` | 显示最后一条消息摘要 | 每次拉列表 |
| `GetHasReadSeqs` | 算未读 | 每次拉列表 |
| `GetLastMessageSeqByTime` | 阅后即焚 | 定时任务 |
| `SetUserConversationMaxSeq` | 踢人/入群冻结 | 低频 |

**这个耦合是必要的**：会话是消息的视图，不依赖消息就无法展示。

但**耦合的方式是「RPC 调用 + 缓存」**，不是「直接查消息表」。这样消息表的结构变化（比如分桶策略调整）不会影响会话模块。

**代价是延迟**。一次 `GetSortedConversationList` 要调三次 msg 服务。如果 msg 服务慢，会话列表就慢。

优化方向：
1. 在 msg 服务里加组合接口（一次返回 maxSeqs + lastMsgs + hasReadSeqs）
2. 会话模块自己缓存「最后一条消息摘要」（但会有一致性问题）

OpenIM 选了「不优化」，接受这个延迟。因为三次调用都是批量 + Redis 为主，实际 P99 可能只有几十毫秒。

## 2.9 `getConversationInfo` 的读时改写

`conversation.go:548-624`（76 行）。它的作用是：给定「每个会话的最后一条消息」，生成「会话列表里要显示的摘要」。

要做的事：
1. **填充发送者昵称**：群消息要显示「张三: 你好」，所以要知道发送者的昵称
2. **处理撤回**：撤回的消息不显示内容，显示「[消息已撤回]」
3. **处理 @ 提示**：如果消息 @ 了我，要标记
4. **处理自己的消息**：显示「我: xxx」还是「昵称: xxx」

**这些逻辑都依赖「当前用户是谁」**——同一个消息，A 看和 B 看不一样。这就是「读时改写」的核心：**存储一份，渲染 N 份**。

📌 **性能隐患**：如果每个会话都要查一次发送者昵称，200 个会话就是 200 次查询。正确做法是批量查（收集所有发送者 ID，一次查用户服务）。

从代码结构看，`getConversationInfo` 应该做了批量查询（它接收的是 `map[string]*sdkws.MsgData`，可以一次性收集所有 sender）。

## 2.10 会话的增量同步

`GetUserConversationIDsHash`（`:491-500`）返回「我的会话 ID 列表的 hash」。

和 17 篇好友的 hash 快判是同一个思路：客户端带 hash 请求，相同则返回「没变」，省传输。

但**会话有更强的增量需求**——一个活跃用户的会话列表每天可能变好几次（新会话、删除、置顶变化）。

📌 OpenIM 的会话增量同步是否用 `incrversion`？从 `cache/redis/conversation.go` 的 `getConversationUserMaxVersionKey` 看，应该是有版本机制的。但 `conversation.go` 里没看到 `GetIncrementalConversations` 这样的接口。

可能是客户端用「hash 快判 + 全量拉取」：hash 变了就重拉全部。对 200 个会话来说，全量拉也不算大（每个会话几十字节，总共几十 KB）。

**这是个合理的取舍**：会话数据量小，不值得做复杂的增量。好友列表可能 5000 人，才需要增量。

# 第四部分 · 自测题

**Q1** 会话表为什么不能从消息表算出来？

<details>
<summary>答案</summary>

四个原因：
1. 性能：200 个会话的 `GROUP BY` 要扫大量数据，而会话表是 200 行直接读
2. 有些信息消息表没有：置顶、免打扰、草稿、@ 状态都是「会话属性」
3. 空会话无法表达：用户点开某人但没发消息，会话列表也该有这一行
4. 已删除的会话无法表达：用户清了消息，会话列表里不该有

会话表是「消息 + 用户偏好」的物化视图，为读性能而存在。
</details>

**Q2** `si_` 前缀的会话 ID 为什么要先 `sort.Strings`？

<details>
<summary>答案</summary>

保证 A→B 和 B→A 拼出相同的 ID。

`GetConversationIDBySessionType(SingleChatType, "userB", "userA")` 排序后是 `["userA", "userB"]`，拼成 `si_userA_userB`。反过来调用也得到同样的结果。

如果不排序，A 的会话是 `si_userA_userB`，B 的会话是 `si_userB_userA`——两个人在两个不同的会话里，消息互相看不见。
</details>

**Q3** `n_` 前缀的通知会话是干什么的？为什么通知消息不进入 `si_` 会话？

<details>
<summary>答案</summary>

`n_` 是通知会话（`GetConversationIDByMsg` 里当 `!options.IsNotNotification()` 时返回）。

不让通知进 `si_` 的原因：
1. 通知不该影响未读数（否则「未读消息」里混着系统通知）
2. 通知不该改变会话排序（会话列表不会因通知而跳动）
3. 通知可以不落正常消息表
4. 客户端可以单独处理（放在「系统消息」里或过滤掉）

`sync_msg.go:25` 拉消息时会跳过 `n_` 会话，所以正常拉历史看不到通知。
</details>

**Q4** 未读数的减法公式是什么？需要哪四个前提？

<details>
<summary>答案</summary>

`未读 = maxSeq - hasReadSeq`。

四个前提：
1. seq 在会话内严格连续无空洞（12 篇的号段分配保证）
2. 每条消息恰好占一个 seq（撤回改状态不删消息）
3. 自己发的消息也占 seq（所以要把自己的 hasReadSeq 也推上去）
4. hasReadSeq 单调不减（只增不减）

缺任何一个，减法结果就错了。比如有空洞，`maxSeq - hasReadSeq` 会比实际消息数大。
</details>

**Q5** 会话排序为什么在服务端做？`conversation.go:192` 的 `map[int64]string` 有什么问题？

<details>
<summary>答案</summary>

服务端做因为客户端数据可能不全（分页拉取），无法正确排序全部会话。服务端知道全部数据，排完再分页。

`map[int64]string` 用时间戳当 key 有 bug：两个会话的 `LatestMsgRecvTime` 相同（同一毫秒）时，后者覆盖前者，**丢一个会话**。

正确应该是 `map[int64][]string`（时间戳 → 会话 ID 列表），或者用切片 + `sort.Slice`。
</details>

**Q6** 免打扰为什么是三态而不是 bool？

<details>
<summary>答案</summary>

因为「免打扰」和「不接收」是两件事：
- 0 正常：收消息、算未读、推送
- 1 免打扰：收消息、算未读、**不推送**（但消息还是来的）
- 2 不接收：连未读都不涨（比如退订的营销群）

bool 只能表达「打扰/不打扰」，表达不了「完全不收」。
</details>

**Q7** 会话是什么时候创建的？为什么「懒创建」？

<details>
<summary>答案</summary>

第一条消息发出时创建（`CreateSingleChatConversations` 的注释：「为消息 Redis 转存创建会话」）。

不预创建因为组合爆炸：1 万用户理论上有 5000 万个单向关系，不可能都建。

代价：用户点开某人但没发消息时，会话列表里没有这一行，客户端要自己构造空会话。
</details>

**Q8** 阅后即焚是删除消息吗？

<details>
<summary>答案</summary>

不是。它抬高会话的 `min_seq`（`ClearUserConversationMsg`）。

流程：`GetLastMessageSeqByTime(conv, now - MsgDestructTime)` 找到「该焚毁的最后一条」的 seq，然后 `min_seq = seq + 1`。

不真删的原因：
1. 群聊消息是共享的，A 的阅后即焚不该影响 B
2. 抬 min_seq 是逻辑操作（改一个数字），真删是物理操作（不可逆）
</details>

**Q9** `UpdateConversation` 为什么用 17 个 `if` + map，而不是直接覆盖？

<details>
<summary>答案</summary>

因为要支持「部分更新」（PATCH 语义）。

如果用完整对象覆盖，只传了 `is_pinned` 的请求会把其他字段都覆盖成零值（`recv_msg_opt` 变成 0、`attached_info` 变成空）。

用 `*bool`/`*int32` 指针，nil 表示「不更新」；用 map 收集非 nil 的字段，Mongo 的 `$set` 只更新这些。

代价是代码冗长。protobuf 的 `fieldmask` 是更好的方案，但 OpenIM 手写了。
</details>

**Q10** 一次 `GetSortedConversationList` 要调几次 msg 服务？为什么？

<details>
<summary>答案</summary>

三次：`GetMaxSeqs`（算未读 + 排序）、`GetMsgByConversationIDs`（最后一条消息摘要）、`GetHasReadSeqs`（算未读）。

分开因为它们在 msg 服务里是不同数据源：seq 在 Redis、消息在 Mongo、已读水位在 Redis。

代价是三次往返。优化方向是在 msg 服务加组合接口，一次返回三者。OpenIM 没做。
</details>

# 第五部分 · 面试话术

## 5.1 30 秒版本

> 会话不是「消息的容器」，而是「用户视角的视图」——同一个群，500 个成员有 500 行会话记录，`max_seq` 相同但 `has_read_seq`、`is_pinned`、`recv_msg_opt` 各不相同。
>
> 它必须单独建表，因为置顶、免打扰、草稿、@ 状态这些是「会话属性」，消息表里没有；而且空会话和已删除的会话都无法用消息表表达。
>
> 会话 ID 有四种前缀，最关键的是 `n_`——通知消息走独立的 `n_` 会话，不污染正常会话的未读数和排序。这是 OpenIM 消息模型里很容易被忽略但很重要的一环。
>
> 未读数是减法：`maxSeq - hasReadSeq`，不是数出来的。前提是 seq 严格连续、每条消息占一个 seq、自己的消息也占 seq、已读水位单调不减。

## 5.2 3 分钟版本

**开场**：讲「会话是视图不是容器」，用 500 人群的例子说明为什么一个群有 500 行会话。

**中间**：讲会话 ID 的四种前缀 + `n_` 通知会话。强调 `sort.Strings` 那一行（不排序会导致两人在两个会话里聊天）。

**然后**：讲未读数的减法模型和四个前提。举「如果有空洞会怎样」的反例。

**收尾**：讲排序的实现，并主动指出那个 bug：「`conversation.go:192` 用时间戳当 map key，同一毫秒会覆盖，丢会话。正确应该用 `map[int64][]string`。」

**预判追问**：

| 追问 | 回答要点 |
|---|---|
| 「会话列表慢怎么办？」 | 目前要调三次 msg 服务（maxSeq/lastMsg/hasReadSeq）。优化：组合接口一次返回、或缓存「最后消息摘要」。代价是一致性 |
| 「置顶和免打扰为什么要单独缓存集合？」 | 客户端渲染「置顶区」和判断「要不要响铃」很频繁，从 200 个会话里筛太慢。代价是失效要维护多个集合 |
| 「免打扰在哪些地方生效？」 | ① 决定是否更新会话 maxSeq（影响未读）② 在线推送 ③ 离线推送的接收者过滤。目前 `GetConversationOfflinePushUserIDs` 只过滤 opt=2，不过滤 opt=1，可能依赖客户端通知渠道 |
| 「阅后即焚怎么实现的？」 | 抬 `min_seq`，不删消息。`GetLastMessageSeqByTime(now - MsgDestructTime)` 找到该焚毁的边界，min_seq = seq + 1 |
| 「会话怎么增量同步？」 | 目前是 hash 快判 + 全量拉取。会话数据量小（200 个 × 几十字节），不值得做复杂增量。好友列表才需要（5000 人） |
| 「删除会话后消息还在吗？」 | 在。删除会话只删会话记录（用户的视图），消息表里的消息还在（其他人还能看到） |

## 5.3 可以主动抛出的问题

1. **`conversation.go:192, 195` 用时间戳当 map key**，同一毫秒的多个会话会互相覆盖，导致会话列表丢项。这是确定的 bug，读代码就能确认。

2. **未读数在 `GetSortedConversationList:167` 和 `GetConversation` 两处实现**，如果不一致会出现「列表显示 3 条，点进去 2 条」。应该抽成函数。

3. **`unreadCount := maxSeq - hasReadSeqs[conversationID]` 没有 `max(0, ...)` 保护**，异常情况下可能为负，客户端会显示负数。

4. **`CreateSingleChatConversations:385-388` 创建失败只 log 不返回错误**，会留下「有消息但没会话」的不一致。需要靠下次发消息重试 + upsert 兜底。

5. **`GetConversationOfflinePushUserIDs` 只过滤 opt=2 不过滤 opt=1**，免打扰的会话仍会触发离线推送。更好的做法是服务端过滤，省流量和电量。
