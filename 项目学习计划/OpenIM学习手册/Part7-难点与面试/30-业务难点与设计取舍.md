## 第一部分 · 理论：业务建模到底在做什么

一行代码没有，但这一节决定了你后面能不能讲出「设计感」。

### 1.1 业务难点 ≠ 技术难点

| | 技术难点 | 业务难点 |
|---|---|---|
| 冲突在哪 | 性能 vs 正确性、规模 vs 简单 | 语义 vs 实现成本、灵活 vs 简单 |
| 典型问题 | 「10 万连接怎么扛」 | 「『已读』到底是个什么概念」 |
| 答错的后果 | 系统慢、会崩 | **功能是对的但用户觉得别扭**，或者后期改不动 |
| 面试怎么考 | 「怎么保证不丢」 | 「为什么这么建模」「如果产品要 XX 你怎么改」 |

**关键区别**：技术难点有标准答案（业界共识），业务难点**没有标准答案，只有一致性**。所以业务难点考的不是「你知不知道正确答案」，而是「你有没有想清楚代价」。

### 1.2 建模的四件事

任何一个业务域，翻译成代码时都要回答四个问题：

| # | 问题 | 例子 |
|---|---|---|
| ① **实体** | 有哪些独立存在的东西？ | 用户、群、消息、会话、文件对象 |
| ② **关系** | 实体之间是什么基数？ | 用户↔群 是 M:N；用户↔会话 是 1:N |
| ③ **状态机** | 有哪些状态？怎么迁移？谁有权迁移？ | 好友申请：待处理→已同意/已拒绝；群：正常→禁言→解散 |
| ④ **不变量** | 什么条件永远必须成立？ | 「群主不能被禁言」「会话的 maxSeq ≥ hasReadSeq」 |

**第 ④ 条是最容易被忽略的，也是最值钱的。**

因为不变量决定了「哪些操作必须在同一个事务/同一个函数里完成」。比如「群主转让时必须先解除新群主的禁言」——这不是业务规则，这是**不变量**：群主不能被禁言。如果转让后群主还处于禁言状态，系统就进入了一个非法状态，后续所有「群主可以发消息」的判断都会出错。

面试时如果你能指出「这里有个不变量，代码在入口处保证了它」，说明你不是在描述功能，而是在**维护模型的一致性**。

### 1.3 取舍的判断框架（三问）

遇到「两种建模都行」的时候，问三个问题：

**第一问：谁承受代价？**

- 写的时候多写几行（服务端成本）vs 读的时候多查几次（用户等待）→ 通常选「写时多花，读时少等」，因为读远多于写。
- 但如果是「写一次读一万次」的场景（比如群消息），反过来选「读时多算」，因为写放大的倍数更大。

**第二问：出错时谁负责？**

- 数据冗余（好友存两行）出错时可能不一致 → 需要补偿逻辑
- 数据归一（好友存一行）出错时不可能不一致，但查询要两次 → 性能差

**冗余换性能**是常见选择，但必须配「怎么修不一致」的方案。

**第三问：这个决定以后能改吗？**

- 能改的（比如配置项）→ 先选简单的，以后再说
- 不能改的（比如消息的存储结构、seq 的语义）→ 一次想清楚

**第三问是分水岭**。消息分桶 100 条是编译期常量，上线后改不了；多端登录策略是配置项，随时能改。**面试时能区分这两类，说明你有工程感。**

### 1.4 一个示范：把「已读」拆开

「已读」这个词，产品经理说的是一个功能，但它其实是两个不同的东西：

| | 我想知道「我读到哪了」 | 我想知道「对方读了没」 |
|---|---|---|
| 用户 | 自己 | 对方 |
| 用途 | 算未读数、同步进度 | 社交压力（双蓝勾） |
| 数据形态 | 一个数字 | 每人一个状态 |
| 成本 | O(1) | O(参与人数) |
| 出错影响 | 未读数不准 | 显示错误，但不影响功能 |

拆开之后设计就清楚了：**自己用的用「水位」（一个数字），给别人看的用「回执」（数组）**。

如果不拆，就会陷入「用一张表同时满足两个需求」的泥潭——要么为了支持回执把存储放大 O(N) 倍，要么为了省存储放弃回执功能。

**这个「把一个词拆成两个概念」的能力，是业务建模的核心动作。** 后面的 9 个取舍，有一半都是这类拆分。

### 取舍 1 · 会话：用户视角的视图，不是消息的容器 🔴

**表面问题**

「会话列表」这个功能，数据从哪来？

**两种做法**

| 做法 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **A. 容器模型** | 一个会话一个文档，里面有消息列表、成员列表 | 结构直观，读一次拿全 | 500 人群 = 一台服务器存不下；权限、置顶、免打扰是「每人不同」的，存不进去 |
| **B. 视图模型** | 会话 = 「某个人看到的某个对话」，每人一行 | 每人的个性化状态天然有地方放 | 500 人群 = 500 行；消息不在会话里，要另外查 |

**选了 B**，代码证据：`pkg/common/storage/model/conversation.go` 的第一行字段就是 `OwnerUserID`——**会话是「属于某个人的」**，不是「属于某个群的」。

```go
type Conversation struct {
	OwnerUserID      string  // ← 谁看到的
	ConversationID   string  // ← 看到的是哪个对话
	RecvMsgOpt       int32   // 免打扰（每人不同）
	IsPinned         bool    // 置顶（每人不同）
	BurnDuration     int32   // 阅后即焚（每人不同）
	GroupAtType      int32   // @我的状态（每人不同）
	MaxSeq, MinSeq   int64   // 可见范围（每人不同）
	...
}
```

**为什么必须这样**

看那 18 个字段：除了 `ConversationID`、`GroupID`、`CreateTime`，**其余几乎全是「每人不同」的**。置顶、免打扰、@状态、草稿、阅后即焚……如果会话是「群的一个属性」，这些字段就没地方放。

而消息为什么不在会话里？因为消息是「会话的所有成员共享的」，存一份就够。**会话是「个性化的视图」，消息是「共享的事实」**——这两个东西的生命周期和所有者都不同，必须分开。

**换成 A 会怎样**

1. 500 人群要存 500 份消息副本 → 存储爆炸
2. 或者消息只存一份，但「谁置顶了」无处可放 → 要么再加一张表（绕回 B），要么放弃功能
3. 消息进入会话文档 → 单文档 16MB 上限，一个活跃群一天就爆

**追问：那「会话列表」怎么排序？**

按每个会话的 `latest_msg` 时间 + 置顶标志。因为会话是 per-user 的，排序也是 per-user 的——这正好符合 B 模型。

📌 **这里有个真实 bug**：`internal/rpc/conversation/conversation.go:192-196` 用 `map[int64]string` 存「时间戳 → 会话 ID」：

```go
conversation_isPinTime[time] = conversationID
```

如果两个会话的 `CreateTime` 落在**同一毫秒**（批量创建会话时完全可能），后一个会覆盖前一个 → **会话列表丢项**。正确做法是 `map[int64][]string` 或者用有序切片。这是个很好的「读代码能发现的问题」例子。

### 取舍 2 · 好友关系：为什么存两行 🔴

**表面问题**

A 和 B 是好友，存一条记录还是两条？

**两种做法**

| 做法 | 结构 | 查询 | 个性化字段 |
|---|---|---|---|
| **A. 一条边** | `{user1, user2}`，查询时 `user1=A OR user2=A` | 需要 OR 查询或两次查询 | 无处安放 |
| **B. 双向两行** | `{owner=A, friend=B}` + `{owner=B, friend=A}` | 单索引 `owner=A` 一次搞定 | 每人一份备注、置顶 |

**选了 B**，代码证据：`pkg/common/storage/controller/friend.go` 的 `BecomeFriends` 里**两次写入**，一个正向一个反向。

**为什么**

三个理由，按重要性排序：

1. **关系有方向属性**。A 给 B 的备注是「老王」，B 给 A 的备注是「张经理」。一条记录只能存一个备注，两行才能各存各的。
2. **查询必须走单索引**。`owner_user_id` 上建索引，`find({owner_user_id: A})` 一次索引扫描。如果是 OR 查询，Mongo 要用 `$or` 两个索引再合并，慢一倍不止。
3. **删除是单向的**（这点最容易被忽略）。A 删了 B，B 的好友列表里 A 还在——如果只有一条边，删掉就两边都没了。而「单向删除」是真实产品需求（微信就是这样：你删了我，我还能给你发消息）。

**代价：一致性**

两行必须同时成功。如果第一行写成功、第二行失败，就出现「A 认为 B 是好友，B 不认为」的**半关系**。

OpenIM 的做法：`BecomeFriends` 里两次写入，没有事务（单机 Mongo 不支持事务，见 21 篇的事务降级）。所以**理论上存在半关系**。缓解方式是「所有读路径都以单向为准」——查 A 的好友时只看 `owner=A` 的行，即使 B 那边缺了也不影响 A 的视图；B 那边缺了，他重新加一次会补上。

📌 **这是一个「用读路径的宽容来掩盖写路径的不一致」的典型**。不优雅，但成本极低。

**换成 A 会怎样**

- 备注只能存一份 → 产品功能缺失
- 单向删除无法表达 → 要么改成双向删除（用户会困惑「为什么我删了他，他也看不到我了」），要么再加一张「删除记录表」（比两行还复杂）
- 查询要 OR → 索引效率下降

**追问：那「好友申请」为什么又是单独一张表？**

因为申请有**状态机**（待处理/已同意/已拒绝/已过期），而好友关系没有状态——是好友就是，不是就不是。**有状态的东西单独建表，无状态的关系用边表**，这是通用原则。

### 取舍 3 · 群成员：M:N 中间表 vs 内嵌数组 🔴

**表面问题**

一个群有成员，成员有角色、禁言时间、入群时间。存哪？

**两种做法**

| 做法 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **A. 内嵌** | `group.members = [{userID, role, muteEndTime}]` | 读群信息一次拿全 | 16MB 上限（约几万人）；无法反查「我加了哪些群」；并发加人冲突 |
| **B. 中间表** | `group_member{group_id, user_id, role_level, mute_end_time, join_time}` | 可反查、可索引、无上限 | 读群成员要单独查；群信息要 join |

**选了 B**，代码证据：`pkg/common/storage/model/group_member.go` 是独立集合，主键是 `(group_id, user_id)` 复合索引。

**为什么**

三个硬约束：

1. **反查需求**：「我加入了哪些群」是高频操作（登录时要拉全部会话）。内嵌数组要全表扫描 `members.user_id = X`，中间表一个索引搞定。
2. **16MB 上限**：一个 10 万人的群，光成员列表就超了。而且 Mongo 每次更新数组都是「读整个文档、改、写回」，10 万人的数组每次改一个人要重写几 MB。
3. **并发冲突**：两个管理员同时踢人，内嵌数组会互相覆盖（Mongo 的数组更新是文档级的）。中间表是两行独立文档，互不影响。

**代价**

- **读群信息要两次查询**：`group` + `group_member`。所以有了缓存（`pkg/rpccache`）和「群成员数」的冗余字段。
- **群成员数是冗余的**：`group.member_count` 和实际行数可能不一致（并发踢人时）。OpenIM 的 `FindGroupMemberNum` 是实时 count，不是读冗余字段——**选择了准确而不是快**。
- **角色只有三级且硬编码**（Owner/Admin/Normal）：扩展性差。要加「自定义角色」就得改表结构 + 所有权限判断。这是「简单 vs 灵活」的取舍，选了简单。

**换成 A 会怎样**

小群（<100 人）其实 A 更好——一次查询拿全，没有 join。所以很多轻量 IM 用 A。**分界线是「群规模上限」**：如果你的产品规定群最多 500 人，A 完全够用；OpenIM 要支持 10 万人大群，只能选 B。

**这个「按规模上限选模型」的思路，面试时说出来很有说服力。**

### 取舍 4 · 消息可见性：一个上界值，两种语义 🔴⚠️

**表面问题**

1. 被踢出群的人，不该再收到新消息——怎么实现？
2. 新入群的人，能不能看入群前的历史？

**这两种做法**

| 做法 | 实现 | 成本 |
|---|---|---|
| **A. 读取时校验成员身份** | 每次拉消息都查一次「他还在群里吗」 | 每条消息一次成员查询 |
| **B. 数据边界** | 给每个用户一个「可见上界」，拉取时收敛 | 一次读取，无额外查询 |

**选了 B**：`max_seq`（会话表 per-user 行）作为上界。

**关键机制（这里必须精确，很容易讲反）**

`pkg/common/storage/controller/msg.go:390-395`：

```go
if userMaxSeq != 0 {                 // ← 0 = 不限制
    if userMaxSeq < maxSeq {
        maxSeq = userMaxSeq          // ← 非 0 才收紧上界
    }
}
// "maxSeq" 表示该用户可拉取的结束序号
```

于是两个操作：

| 操作 | 写入值 | 效果 | 码点 |
|---|---|---|---|
| 退群 / 被踢 | 当前群 max | 上界冻结 → 历史留着，新消息拉不到 | `group.go:1026` |
| 入群 / 被拉回 | **0** | 解除限制 → **能看到入群前的历史** | `group.go:1035` |

⚠️ **最反直觉的地方**：`0` 不是「上界为零」，是「没有上界」。入群写 0 是一次 **reset**——清掉之前可能残留的冻结值（一个人可能被踢过又拉回来）。

**我本人在这里读反过一次**，18 篇早期版本写成了「入群设 0 = 看不到历史」。教训是：

> **判断一个字段的语义，看「读它的地方」，不要看「写它的地方」。** 写入点只说明谁在改，读取点才说明值意味着什么。

**为什么选 B**

因为**读取是高频路径**。一条群消息可能被 500 个人拉，如果每次都查成员表，读放大 500 倍。而 B 方案的检查是「一次比较整数」，零成本。

**代价**

- **不精确**：冻结的是「当时的最大 seq」，如果有一条消息正在处理中（seq 已分配未落库），被踢的人可能刚好能看到。这是最终一致的必然。
- **策略硬编码**：OpenIM 默认「新人可见历史」。如果业务要「新人不可见」，得把 `setMemberJoinSeq` 的 0 改成当时的群 max。**机制是中性的，策略在调用方**——这是好的设计，但需要文档说明（📌 现状没有）。
- **两处重复实现**：`group.go:1026` 和 `push_handler.go:402` 各一份冻结逻辑，改一处忘另一处就不一致。

**换成 A 会怎样**

正确性更高（能精确判断「此刻是否在群」），但读路径多一次查询，且群成员表本身就是缓存过的——**你可能查的是一个已经过期的成员列表**，同样不精确。所以 A 付出性能代价却换不来精确性，不划算。

**追问：那「彻底不可见」怎么做？**

只能「按人复制消息」（写扩散），或「读取时逐条校验权限」。前者存储 O(N×消息)，后者性能 O(N)。**都不划算，所以业界（微信、Telegram、Slack）普遍选「历史保留、新消息切断」。**

### 取舍 5 · 已读：拆成两个成本差 4 个数量级的概念 🔴

（1.4 节已经拆过概念，这里讲取舍的推演）

**表面问题**

「显示已读」这个需求，怎么用一张表满足？

**两种做法**

| 做法 | 结构 | 成本 | 能回答什么 |
|---|---|---|---|
| **A. 每人每条一个标记** | `read_record{msg_id, user_id}` | O(消息 × 人数) | 「谁读了这条」+「我读到哪」 |
| **B. 每人一个水位 + 消息里存数组** | `hasReadSeq`（一个数字）+ `msg.is_read[]`（只单聊） | O(人数) + O(1) | 水位能算未读；数组能显示单聊已读 |

**选了 B**，而且是「**分场景用不同方案**」：

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 算未读数 | `hasReadSeq`（一个数字） | O(1) 减法，`maxSeq - hasReadSeq` |
| 单聊显示「已读」 | 消息文档里的 `is_read` 数组 | 只有两个人，O(2) 可接受 |
| 群聊显示「谁读了」 | **不做**（默认不广播） | 500 人 O(N)，一条消息写 500 次 |

**码点**

| 位置 | 作用 |
|---|---|
| `internal/rpc/msg/as_read.go:92` `MarkMsgsAsRead` | 取 `Seqs` 最后一个作为新水位 |
| `internal/rpc/msg/as_read.go:115-116` | `if hasReadSeq > currentHasReadSeq` 才写（只能前进） |
| `pkg/common/storage/database/mgo/msg.go:232` `MarkSingleChatMsgsAsRead` | 只有单聊写 `is_read` |
| `pkg/common/storage/cache/redis/seq_user.go` | 水位存 Redis HASH |

**为什么**

算一下成本就清楚了。500 人群，一天 1 万条消息：

- A 方案：500 × 10000 = **500 万条记录/天**
- B 方案：500 个数字 + 0（群聊不广播）

**差 4 个数量级。** 而且 A 方案的记录绝大部分永远不会被查询——没人会去看「3 天前第 427 条消息都有谁读了」。

**代价**

- **群聊功能缺失**：产品上少一个功能。但这是「技术上不划算」的正确决策——Slack 的「已读」也是有限制的。
- **水位只能前进**：乱序请求不会把水位倒退，但「标记更早的消息已读」不生效。业务上通常不需要，但要注意这个限制。
- **📌 水位只写 Redis**：`readSeqWriteRatio: 100` 声明了但**全文未使用**，意味着批量落库没实现。Redis 30 天过期后，回源 Mongo 拿到旧值 → 未读数虚增。**这是一个「设计了一半」的功能。**

**换成 A 会怎样**

存储成本爆炸，且写入路径变成 O(N)——每读一条消息写 500 次。**这是唯一能真正支持「群已读回执」的方案**，但代价是必须做异步批量写 + 冷热分离。

**判断标准**：如果产品**强需求**群已读（比如企业办公 IM，老板要看谁没读通知），那就必须付这个成本。**技术选型跟着产品定位走**，这句话讲出来很加分。

### 取舍 6 · 删除与撤回：读时改写 vs 写时物化 🔴

**表面问题**

A 删了一条消息，B 还能看到。这条消息在库里怎么处理？

**三种做法**

| 做法 | 实现 | 存储 | 读成本 | 一致性 |
|---|---|---|---|---|
| **A. 每人一份副本** | 每人一条消息记录 | O(N) | 读自己的，快 | 强 |
| **B. 物理删除** | 直接删掉 | O(1) | 别人也看不到了 | **错的** |
| **C. 读时改写** | 存一份 + `del_list` 标记，读时按 userID 过滤 | O(1) | 读时判断 | 最终一致 |

**选了 C**，代码证据：

| 机制 | 字段 | 码点 |
|---|---|---|
| 单人删除 | `del_list` 数组（存 userID） | `pkg/common/storage/controller/msg.go:534` `DeleteUserMsgsBySeqs` |
| 撤回 | `revoke` 结构体 | `pkg/common/storage/controller/msg.go:222` `RevokeMsg` |
| 读时过滤 | `handlerDBMsg` | `pkg/common/storage/controller/msg.go:249` |
| 区间清除 | `min_seq` 水位 | `msg_transfer.go` / `conversation.go` |

**为什么**

因为**消息是「一份事实、多个视角」**：内容只有一份（发送者写的那份），但「这条消息对我可见吗」是每人不同的。跟取舍 1 的会话是同一个道理。

**代价（三条，都能追问）**

1. **读时计算**：每次读都要判断 `del_list` 里有没有我、有没有被撤回、我是不是发送者（撤回对发送者可见）。**读路径变复杂。**
2. **逻辑重复**：📌 读时改写有两份实现（`mgo/msg.go:138-169` 和 `controller/msg.go:734-779`），改一处容易漏另一处。
3. **`del_list` 会膨胀**：500 人群里 400 人都删了这条消息，数组就有 400 个 userID。极端情况下接近文档大小上限。**缓解方式是「超过一定比例就整条物理删」，但 OpenIM 没做**（`IsFull()` 的调用点只有一处，且是防御性的）。

**换成 A 会怎样**

- 存储 O(N)：500 人群一条消息 500 份
- 撤回变成 O(N) 更新：撤回一条消息要改 500 份
- 但如果「每人一份副本」，已读、删除、撤回全都变成「改自己的那份」，读路径极简

**这是「读扩散 vs 写扩散」在存储层的翻版**（和难点 6 的群扇出是同一个思路）。OpenIM 全线选读扩散，一致性靠「读时计算」保证。

**追问：撤回为什么不物理删除？**

因为「撤回」的语义是「这条消息被撤回了，请显示『对方撤回了一条消息』」，不是「从来没存在过」。物理删了客户端就不知道这里曾经有消息，会话会出现空洞。**所以撤回是「内容替换 + 标记」，不是删除。**

这个区分很重要：**「删」是可见性问题，「撤」是内容问题。**

### 取舍 7 · 系统消息：复用消息通道，但开独立会话 🟡

**表面问题**

「你被邀请进群了」「XX 同意了你的好友申请」这类通知，走什么通道？

**两种做法**

| 做法 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| **A. 独立通知系统** | 单独的表 + 单独的推送链路 + 客户端单独的处理逻辑 | 语义清晰，不污染消息表 | 一整套新链路（存储、同步、未读、推送）都要重写 |
| **B. 复用消息通道** | 造一条「通知类型的消息」，走同一条链路 | 零新增链路；离线、同步、多端全部免费获得 | 消息表被污染；客户端要区分 |

**选了 B**，而且加了一个关键设计：**通知消息进独立的 `n_` 会话**。

代码证据：`pkg/msgprocessor/conversation.go`

```go
func GetConversationIDByMsg(msg *sdkws.MsgData) string {
	options := Options(msg.Options)
	switch msg.SessionType {
	case constant.SingleChatType:
		l := []string{msg.SendID, msg.RecvID}
		sort.Strings(l)
		if !options.IsNotNotification() {
			return "n_" + strings.Join(l, "_")   // ← 通知走 n_ 会话
		}
		return "si_" + strings.Join(l, "_")
	...
	case constant.ReadGroupChatType:
		if !options.IsNotNotification() {
			return "n_" + msg.GroupID
		}
		return "sg_" + msg.GroupID
	}
}
```

**为什么这样设计**

1. **复用链路省下的是「可靠性」**：通知也必须不丢、必须多端同步、必须离线推送。如果另起一套，这些都要重做一遍。
2. **`n_` 会话解决「污染」问题**：通知消息如果混进正常会话，用户会看到「群消息」和「你被踢了」交错，而且未读数会混在一起。开一个独立会话，两者彻底分离。
3. **拉消息时跳过 `n_`**：`internal/rpc/msg/sync_msg.go:25` 的 `if !msgprocessor.IsNotification(...)` 分支——通知会话走 `GetMsgBySeqs`（按 seq 列表精确查），普通会话走 `GetMsgBySeqsRange`（区间查）。**两条路径，因为通知消息不需要「连续」语义。**

**代价**

- **消息表混了两类数据**：统计、清理、迁移都要区分。`msg` 集合里既有聊天也有通知。
- **客户端要处理两种会话**：UI 上要区分「系统通知」和「聊天」。
- **📌 `sn_` 前缀几乎不会出现**：`GetConversationIDBySessionType` 定义了 `sn_`，但 `GetConversationIDByMsg` 只在「通知会话 + 非通知消息」时返回它——这个组合几乎不存在。**是一个没完成的设想。**

**换成 A 会怎样**

要新写：通知表、通知同步接口、通知未读、通知推送、通知多端一致。**大约是整个消息链路的一半工作量**，而且每一处都可能出 bug。

**这就是「复用」的价值：不是省代码行数，是省掉了一整条链路的正确性验证成本。**

### 取舍 8 · 文件上传：预签名 + 秒传 + 引用计数 🟡

**表面问题**

客户端要发一张 5MB 的图片，怎么传？

**三种做法**

| 做法 | 流量 | 服务端压力 | 安全性 |
|---|---|---|---|
| **A. 客户端传给服务端，服务端转存** | 5MB 进 + 5MB 出 | 服务端带宽翻倍 | 好控制 |
| **B. 服务端发临时凭证，客户端直传对象存储** | 5MB 直传 | 服务端零流量 | **靠凭证的有效范围** |
| **C. 公开可写桶** | 5MB 直传 | 零 | 灾难 |

**选了 B（预签名 URL）**，代码证据：`internal/rpc/third/s3.go`。

**预签名的本质**

```
签名 = HMAC-SHA256(secret, "PUT\n<key>\n<expires>")
```

服务端用自己的 secret 算一个签名，把「key + 过期时间 + 签名」给客户端。客户端拿这个去请求对象存储，存储侧用同样的 secret 重算一遍签名，一致就放行。

**关键点：客户端从来没有拿到 secret**，只有一个「限定操作、限定 key、限时」的凭证。所以即使凭证泄露，影响范围也被锁死。

**秒传与引用计数**

「秒传」= 客户端先报文件的 hash，如果服务端已经有这个 hash，直接创建一条记录指向已有的 key，不上传。

问题来了：多个用户上传同一个文件，`object` 集合里有多条记录指向**同一个 key**。删一个的时候，能直接删 key 吗？**不能**——其他人还在用。

OpenIM 的做法：**用「行数」当引用计数**（`pkg/common/storage/database/mgo/object.go:98` `GetKeyCount` 就是 `count(key = X)`），只有 `count == 0` 时才真删。

```go
// internal/rpc/third/s3.go 删除时的判断
count, err := s3Database.GetKeyCount(ctx, engine, key)
if count == 0 {
    // 真正删除对象存储里的文件
}
```

**为什么用「计数查询」而不是「计数字段」**

| | 计数字段 | 计数查询 |
|---|---|---|
| 性能 | O(1) | O(1)（走索引 count） |
| 一致性 | 需要原子增减，出错会永久偏移 | 天然准确（数行数） |
| 缺点 | — | 无法表达「同一条记录被引用两次」 |

选了查询，因为**准确比快重要**——删除是低频操作，多一次 count 无所谓；而计数字段一旦偏移，要么永不删除（泄漏），要么误删（数据丢失）。

**代价**

- **非原子**：`count == 0` 判断和真正删除之间有窗口。两个请求同时删同一个 key，可能都看到 `count == 1`，都不删 → 泄漏；或者都看到 0 → 重复删（幂等，无害）。**选了「可能泄漏」而不是「可能误删」**，方向是对的。
- **命名空间靠约定**：`internal/rpc/third/tool.go:29-49` 要求 `name` 必须以 `<userID>/` 开头。这是**应用层校验，不是存储层约束**——绕过 API 直接写 Mongo 就能破坏。📌 而且 `/object/*name` 是 GET 免认证（靠签名 URL 保护），`name` 由客户端定，**这是一个真实的风险面**。
- **存储引擎可切换**：5 种引擎（MinIO/OSS/COS/AWS/七牛），`case ""` 走 `disable.NewDisable()`——能启动但上传不可用。**这就是为什么不能删 MinIO**。

**追问：为什么不让服务端中转？**

5MB 的文件过一遍服务端 = 10MB 流量 + 内存占用 + 超时风险。而 IM 的图片/视频是**流量大头**，中转会让带宽成本翻倍。**直传是必然选择，问题是「怎么安全地直传」，答案就是预签名。**

### 取舍 9 · 多端登录：把产品策略做成配置 🔴

**表面问题**

用户在手机上登录了，又在电脑上登录。踢不踢？

**这不是技术问题，是产品问题**

不同产品答案不同：
- 微信：手机 + 电脑可以同时在线，但两个手机不行
- QQ：多端同时在线，消息同步
- 银行 App：新登录踢掉旧登录

**所以正确的做法是：把策略做成配置，不在代码里写死。**

**四种策略**（`internal/msggateway/ws_server.go:374-430`，配置在 `config/share.yml:19-22` 的 `multiLogin.policy`）

| 值 | 策略 | 行为 |
|---|---|---|
| 1 | `DefalutNotKick` | 都允许，不踢 |
| 2 | `PCAndOther` | PC 端不互踢，移动端互踢 |
| 3 | `AllLoginButSameTermKick` | 同平台踢，不同平台共存 |
| 4 | `AllLoginButSameClassKick` | 同类终端互踢（PC 类 / 移动类） |

**代码里有个值得学的技巧**：`PCAndOther` 用 `fallthrough` 复用 `AllLoginButSameTermKick` 的逻辑：

```go
case constant.PCAndOther:
    if constant.PlatformIDToClass(newClient.PlatformID) == constant.TerminalPC {
        return   // PC 登录，不踢任何人
    }
    // 移动端登录：先收集「非 PC 的旧连接」
    clients, ok := ws.clients.GetAll(newClient.UserID)
    clientOK = ok
    oldClients = filterOutPC(clients)
    fallthrough   // ← 复用下面「踢掉 oldClients」的逻辑
case constant.AllLoginButSameTermKick:
    if !clientOK { return }
    oldClients = checkSameTokenFunc(oldClients)
    ws.clients.DeleteClients(newClient.UserID, oldClients)
    ...  // 踢连接 + 踢 token
```

**`fallthrough` 的用法很关键**：「选哪些人踢」是策略差异，「怎么踢」是共同逻辑。用 `fallthrough` 把两者拼起来，避免复制一遍「踢连接 + 踢 token + 广播」的代码。

**代价**

- **策略之间不能自由组合**：四种硬编码的策略，想加「最多 3 个设备」就得改代码。
- **同 token 不踢是必需的补丁**：`ws_server.go:356` 的 `checkSameTokenFunc`——多网关节点下，客户端从 A 节点断开重连到 B 节点，A 可能还没清理旧连接，此时同 token 有两个连接。**不踢是为了避免误伤自己。** 这个注释在源码里写得很清楚，是个好例子：**分布式环境下「看起来重复」的东西，往往是「正在收敛中」。**

**追问：为什么「踢人」要同时踢连接和踢 token？**

- 只踢连接：客户端会自动重连，重连时用旧 token 又能进来 → **踢不掉**
- 只踢 token：连接还在，消息照样能收 → **踢了但没效果**

所以必须两者都做。而 token 存在 Redis（`UID_PID_TOKEN_STATUS`），连接存在网关内存，**两个地方都要改，这是「有状态 + 无状态混合架构」的必然成本**。

## 第三部分 · 九条建模原则（可以背下来）

从上面 9 个取舍里提炼，这九句话在面试里可以直接用：

| # | 原则 | 来源 |
|---|---|---|
| 1 | **共享的事实存一份，个性化的视角每人一份** | 取舍 1（会话）、取舍 6（删除） |
| 2 | **有状态的东西单独建表，无状态的关系用边表** | 取舍 2（好友 vs 申请） |
| 3 | **按规模上限选数据结构，不是按当前数据量** | 取舍 3（M:N vs 内嵌） |
| 4 | **判断字段语义看读取点，不看写入点** | 取舍 4（`0` 是「不限制」） |
| 5 | **一个词拆成两个概念，成本可能差几个数量级** | 取舍 5（水位 vs 回执） |
| 6 | **「删」是可见性问题，「撤」是内容问题** | 取舍 6 |
| 7 | **复用的价值是省掉正确性验证成本，不是省代码** | 取舍 7（通知复用消息链路） |
| 8 | **准确 > 快，如果操作是低频的** | 取舍 8（引用计数用 count） |
| 9 | **产品策略做成配置，机制才写进代码** | 取舍 9（多端策略） |

**第 1 条和第 5 条是最值钱的**。它们不只适用于 IM——Feedly 的已读、GitHub 的通知、电商的购物车，全是同一个模式。

## 第五部分 · 面试话术

<details>
<summary>🔴 「讲讲你对这个项目业务建模的理解」</summary>

> 「我觉得这个项目最关键的建模决策是**把『共享的事实』和『个性化的视角』分开**。
>
> 最典型的是会话和消息。消息是共享的——一个群一条消息只存一份；但会话是个性化的——置顶、免打扰、@状态、可见范围，每个人都不一样。所以会话表的主键是 `(owner_user_id, conversation_id)`，500 人的群就有 500 行会话，但消息只有一份。
>
> 这个模式在项目里反复出现。好友关系存两行而不是一行，因为备注和置顶是每人不同的；消息删除用 `del_list` 标记而不是删文档，因为「谁能看见」是每人不同的；已读拆成水位和回执，因为「我读到哪」和「谁读了我的消息」是两个成本差 4 个数量级的东西。
>
> **一旦用这个视角看，很多看起来奇怪的设计就都合理了**——它们不是冗余，是「个性化视角」的存储成本。」
</details>

<details>
<summary>追问 1：「那这种设计有什么代价？」</summary>

> 「三个代价。
>
> 第一是**读路径变复杂**。读一条消息要现场判断：我删了没、被撤回了没、我是不是发送者、我的可见范围是什么。这些逻辑有两份实现（mgo 层和 controller 层），改一处容易漏另一处。
>
> 第二是**一致性靠最终一致**。好友关系两行写入没有事务（单机 Mongo 不支持），理论上会出现半关系；踢人冻结 seq 也不精确，正在处理中的消息可能漏出去。都靠读路径的宽容来掩盖。
>
> 第三是**清理困难**。`del_list` 会随删除人数膨胀，极端情况下接近文档上限；消息表混了聊天和通知两类数据，统计和迁移都要区分。
>
> 但这些代价换来的是存储成本从 O(N) 降到 O(1)。在 IM 这个场景里，**写放大是最致命的**，所以这个交换是划算的。」
</details>

<details>
<summary>追问 2：「如果产品要求『新入群的人看不到历史消息』，你怎么改？」</summary>

> 「不用改机制，只改一个参数。
>
> 现在的机制是：每个用户在会话上有一个 `max_seq` 作为可见上界，读取时 `if userMaxSeq != 0` 才收紧，所以写 0 等于『不限制』。入群时写 0 是 reset，目的是清掉可能残留的冻结值（比如这个人被踢过又拉回来）。
>
> 要做到『不可见历史』，就在入群时把 `max_seq` 写成**当时的群最大 seq**，也就是复用踢人那套冻结逻辑（`deleteMemberAndSetConversationSeq`）。这样他的上界停在入群那一刻，之前的拉不到，之后的新消息能拉到。
>
> 这是个很典型的『机制中性、策略外置』的设计——一个上界值同时支持两种产品策略，改的是调用方传的参数，不是底层逻辑。」
</details>

<details>
<summary>追问 3：「文件上传为什么不走服务端中转？」</summary>

> 「带宽成本翻倍，而且 IM 的图片视频是流量大头。
>
> 走预签名 URL：服务端用 secret 算一个签名，覆盖『操作类型 + 对象 key + 过期时间』，客户端拿着签名直传对象存储，存储侧用同样的 secret 重算校验。**客户端从头到尾没有 secret**，凭证泄露的影响范围也被限制在『这一个 key、这一段时间』。
>
> 有一层额外设计是秒传：客户端先报 hash，服务端发现已有同 hash 的对象，就直接建一条记录指向同一个 key。这时候多个 `object` 记录共享一个 key，所以删除时必须先 `count(key)`，只有 0 才真删——**引用计数用的是行数查询而不是计数字段，因为准确比快重要，而删除是低频操作**。」
</details>

<details>
<summary>追问 4：「说一个你觉得产品和技术冲突的地方。」</summary>

> 「群聊的已读回执。
>
> 产品上很自然：500 人的群，发个通知，想知道谁看了。技术上这是 O(消息 × 人数)：500 人一条消息要写 500 个已读状态。一天一万条消息就是 500 万条记录，而且绝大部分永远不会被查询——没人会去查三天前第 427 条消息都有谁读了。
>
> OpenIM 的选择是：水位照常维护（一个数字，用来算未读），但群聊不广播回执。单聊才写 `is_read` 数组，因为只有两个人，O(2) 可接受。
>
> 这个取舍的判断标准是**产品定位**：如果是企业办公 IM（老板要看谁没读通知），那就必须付这个成本，做法是异步批量写 + 冷热分离，把近期消息的已读放 Redis、历史的归档。如果是社交 IM，用户其实不需要这个功能，砍掉是对的。」
</details>

## 本篇小结：必须记住的 8 句话

| # | 一句话 |
|---|---|
| 1 | 业务难点没有标准答案，只有**一致性**和**代价** |
| 2 | 建模四件事：实体、关系、状态机、**不变量** |
| 3 | 会话是**用户视角的视图**，所以主键带 `OwnerUserID` |
| 4 | 好友存两行：方向属性 + 单索引 + 单向删除 |
| 5 | 群成员用中间表，因为**反查 + 16MB + 并发**三个硬约束 |
| 6 | `userMaxSeq = 0` 是「不限制」，入群写 0 是 reset |
| 7 | 已读拆两个概念，成本差 **4 个数量级** |
| 8 | **删是可见性问题，撤是内容问题** |
