## 第一部分 · 理论：面试到底在评什么

### 1.1 面试官在每个问题里采集四种信号

同一个问题，面试官脑子里在打四个勾：

| 信号 | 他在判断 | 你答什么能得分 |
|---|---|---|
| **知识** | 你知道这个概念吗 | 术语准确、不混淆 |
| **经验** | 你真的用过/读过吗 | 具体数字、文件、踩坑 |
| **判断** | 你会不会权衡 | 说得出代价和替代方案 |
| **表达** | 能不能合作 | 结论先行、有结构、不啰嗦 |

**只答知识，最多给到中级**。要往上升，必须给「经验 + 判断」——而这两样恰好是「读过源码」和「想过代价」才能提供的。

所以本篇的题库里，每道题都标了**码点**（证明经验）和**追问**（证明判断）。

### 1.2 答题的四层结构（背下来）

```
① 结论先行（一句话，10 秒内说完）
② 展开机制（2-4 句，讲清「怎么做到的」）
③ 码点（一句「代码里在 xxx.go 的 xxx 函数」，证明真读过）
④ 代价/边界（一句「这样做的代价是……」）
```

示范（问「消息怎么保证不丢」）：

> ①「靠位点提交时机——整批处理完之后才提交。」
> ②「消费侧拉一批，按会话切片分给 worker，等全部完成才标记最后一条并提交位点。这里有个隐含前提：标记最后一条等于标记整批，依赖同步等待。」
> ③「在 `msgtransfer` 的落库回调和 `batcher` 里，`Wait` 之后才 `Mark`，`Do` 返回后才 `Commit`。」
> ④「代价是尾延迟由最慢的 worker 决定。而且这块有个真实缺陷：`Do` 没有返回值，落库失败也会提交位点。」

**这个结构的好处是「随时可停」**：面试官听到 ① 就懂，可以打断问细节；你也可以在 ② 处停，看他反应。

### 1.3 三套脚本的用途

| 长度 | 场景 | 要点 |
|---|---|---|
| **30 秒** | 自我介绍里带一句 / 「简单说说你这个项目」 | 只讲「是什么 + 最难的一点」，不求全 |
| **3 分钟** | 「详细讲讲」/ 「讲讲架构」 | 一条主线：消息链路，八步走 |
| **10 分钟** | 深挖环节 / 白板 | 按因果链展开 + 主动暴露一个问题 |

### 1.4 卡住的时候（三句话，务必背）

1. **「这块我没细读，但按架构推应该是……」** —— 推测 + 说明推理依据
2. **「如果要确认，我会去看 xxx 目录下的 xxx」** —— 给出验证路径
3. **「我不确定，不过我可以讲讲我的理解，您看对不对」** —— 把判断题变成讨论

**绝对不能做的**：编一个具体的函数名/行号。一旦被追问就崩，而且会被判定为「不诚实」——这比「不知道」严重得多。

## 第二部分 · 三套讲解脚本

### 2.1 30 秒版（自我介绍里用）

> 「我最近在深入研究一个开源的 IM 服务端 OpenIM，40 万行 Go，用到了 WebSocket、gRPC、Kafka、MongoDB、Redis、etcd。
>
> 我不是只看架构图，是把消息链路从握手到落库整条读了一遍。印象最深的是它为了保证消息不丢不乱，用了一套**批处理 + 三层保序 + 号段 seq** 的组合：发送只写 Kafka 就返回，消费侧批处理削峰，但批处理会打乱顺序，所以分区键、worker 分片、同 key 成组三层都要对齐；而保序的基础是 seq 要提前确定，所以用号段预分配，代价是产生空洞，读取侧就必须容忍空洞。
>
> 我比较喜欢这种『每个设计都是被上一个选择逼出来的』的感觉。」

**为什么这个版本有效**：它没有罗列功能，而是**展示了一条因果链**。面试官听完会想追问「号段怎么分配」——这正是你想要的。

### 2.2 3 分钟版（「详细讲讲架构」）

按八步走，每步一句：

> 「这个项目的架构可以按一条消息的生命周期来讲。
>
> **第一，接入。** 客户端走 WebSocket 连网关，握手时带 token，网关调 auth 服务校验。网关是唯一有状态的进程——它保存着「谁连在哪个节点」，业务服务全是无状态的。
>
> **第二，发送。** 网关把消息转给 msg 服务，做六维校验：会话存在、成员身份、群状态、禁言、黑名单、好友关系。校验通过后补上 ServerMsgID、设置 Options，**只投 Kafka 就返回**，不等落库。
>
> **第三，中转。** msgtransfer 消费 Kafka，用 batcher 聚合——500 条或 100ms 双触发，按会话切片给 50 个 worker。
>
> **第四，分配 seq。** 这是关键。号段预分配：Redis 一次给 50（单聊）或 100（群聊）个，用完才去 Mongo `$inc` 取下一段。两段式 Lua，因为 Lua 里不能做数据库调用。
>
> **第五，落库。** 消息按 100 条一个文档分桶，`docIndex = (seq-1)/100`。写入是先 update 后 insert，所以重投是幂等的。
>
> **第六，推送。** 投 toPush topic，push 服务消费。群消息在这里扇出——一条消息在 MQ 里只有一份，推给 500 人是 push 服务的事。
>
> **第七，在线推送。** push 服务查在线状态（Redis ZSET，score 是过期时间），然后遍历所有网关节点，用批量接口一次推一批用户。网关内部再用内存队列 + 512 个 worker 摊平到单连接。
>
> **第八，离线兜底。** 在线推失败的、不在线的，走离线推送通道。
>
> 整条链路的核心思想是：**发送只保证『进 Kafka』，落库和推送全异步，用 seq 保证最终有序，用幂等保证重复无害。**」

**关键技巧**：每步都用「动词 + 一个反直觉的细节」。比如「只投 Kafka 就返回」「Lua 里不能做数据库调用」——这些细节让 3 分钟不显得空洞。

### 2.3 10 分钟版（白板 + 深挖）

结构：**画图（3 分钟）→ 讲三个设计决策（5 分钟）→ 主动暴露一个问题（2 分钟）**。

**画图**（按 03 篇的图简化）：

```
客户端 ──WS──→ msggateway ──gRPC──→ msg ──Kafka──→ msgtransfer ──→ Redis(seq) + Mongo
                    ↑                                     │
                    │                                     ├──Kafka──→ push ──→ 各网关节点
                    └─────────────────────────────────────┘
```

**三个设计决策**（挑你能讲最深的三个）：

1. **接入与逻辑分离**：网关有状态、业务无状态。为什么？因为连接不能迁移，但业务要能随便扩。
2. **发送与落库分离**：写放大是 IM 最致命的问题。500 人群一条消息，如果同步做校验 + 落库 + 扇出，延迟随群规模线性增长。
3. **seq 驱动一致性**：不靠时间戳，靠会话内序号。这样客户端同步退化成「比大小」，未读退化成「减法」。

**主动暴露一个问题**（这是加分项，选一个你能讲透的）：

> 「我读的时候发现一个真实的缺陷：`msg_transfer.go:205` 的批次上限是 100，但 batcher 的批大小是 500。热门会话单批超过 100 条时，整批会报 `message count exceeds limit` 直接失败。
>
> 根因是两处用了不同的约束来源：100 是存储分桶常量（一个文档最多 100 条），500 是吞吐调参。但这两个本来不该相等——500 条完全可以拆进 5 个文档。正确做法是按 docIndex 分组后再检查每组的 100，而不是拿总数比 100。」

**为什么要主动暴露**：面试官最怕「什么都好」的候选人，因为那通常意味着「没真读过」。**主动指出一个具体缺陷 + 给出修法**，可信度远高于自夸。

### A 组 · 项目与背景（4 题）

#### A1. 介绍一下这个项目

#### A2. 这个项目有多少代码？你读了哪些部分？

- **码点**：能说出「`internal/rpc/msg/` 下 send/verify/seq/sync_msg/as_read 几个文件的分工」。

#### A3. 为什么要二次开发这个项目？你改了什么？

### B 组 · 架构（5 题）

#### B1. 为什么网关要独立成一个服务？

- **结论**：因为连接是**有状态**的，业务逻辑是**无状态**的，两者扩缩容策略完全不同。
- **展开**：网关保存「userID → 连接」的映射，进程重启连接就断；业务服务只依赖数据库，随时可以加机器。如果混在一起，加业务机器就得断连接。
- **码点**：`internal/msggateway/`（连接表在 `user_map.go`）、`internal/rpc/*`（无状态）。
- **追问**：那网关怎么和业务服务通信？→ gRPC。网关不直接调数据库。

#### B2. 一个消息要推给用户，怎么找到他的连接？

- **结论**：**广播式路由**——push 服务不知道用户在哪个网关，所以问所有网关节点。
- **展开**：从服务发现拿到所有 gateway 的连接，用 `errgroup.SetLimit` 并发调用批量接口，每个节点自己判断「这个人连在我这吗」。没连的返回空结果。
- **码点**：`internal/push/onlinepusher.go:67` `GetConnsAndOnlinePush`，`:91` 的 `wg.SetLimit(maxWorkers)`。
- **追问**：节点多了不会慢吗？→ 会。这是「不知道路由」的代价。要优化就得维护「userID → 节点」的路由表（比如写 Redis），但那张表本身要一致性和清理。OpenIM 选了简单方案：N 个节点 N 次调用，N 一般在个位数。

#### B3. etcd 在这里做什么？

- **结论**：服务注册与发现。
- **展开**：每个 RPC 服务启动时把自己的地址写进 etcd（带 lease 保活），客户端通过 discovery 拿到地址列表。另外还有两种模式：`standalone`（进程内直连）和 `kubernetes`（用 K8s 的 Service）。
- **码点**：`config/discovery.yml`（`etcd` / `kubernetes` / `standalone`）、`pkg/common/config/config.go` 的 `AllConfig`。
- **追问**：服务挂了 etcd 怎么知道？→ lease 到期自动删 key。但「进程卡死但没退出」时 lease 还在续，这就是为什么还需要健康检查和熔断（`pkg/common/startrpc/circuitbreaker.go`）。

#### B4. 一体化模式和拆分模式有什么区别？

- **结论**：一体化是「单进程跑 12 个服务」，用 `inprocess` 做进程内 RPC；拆分是「每个服务一个进程」，用 etcd + gRPC。
- **展开**：两者共用同一份业务代码——`internal/rpc/auth.Start` 只负责「把服务注册到注册器」，真正的 Serve 由外层决定。`inprocess` 的注册器只把方法登记进 map，**但仍然做序列化**（深拷贝，避免共享指针的 bug）。
- **码点**：`cmd/main.go`（一体化）、`pkg/common/startrpc/start.go`（拆分）。
- **追问**：为什么 inprocess 还要序列化？→ 如果直接传指针，调用方和被调方共享同一个对象，被调方改字段调用方看得见——这是最难排查的一类 bug。序列化强制深拷贝，同时保证「一体化能跑，拆分就不会崩」。

#### B5. 「29 个进程」是怎么来的？

- **结论**：`start-config.yml` 里每个服务的实例数加起来。
- **展开**：api 1 + crontask 4 + 8 个 rpc 各 1 + msggateway 1 + push 8 + msgtransfer 8 = 29。push 和 msgtransfer 各 8 是因为一个是 I/O 密集、一个是写瓶颈；crontask 4 是因为每个任务执行前要抢分布式锁，多开不会重复执行。
- **码点**：`start-config.yml`、`internal/tools/cron/redis_locker.go`。
- **追问**：为什么网关只有 1 个？→ 演示配置。生产要按连接数扩，而且网关前面要有负载均衡（因为 WS 需要保持会话，通常用四层 LB）。

### C 组 · 接入层（5 题）

#### C1. WebSocket 握手做了什么？

- **结论**：借用一次 HTTP 请求完成协议升级，之后同一条 TCP 连接上跑 WS 帧。
- **展开**：客户端发 `Upgrade: websocket` + `Sec-WebSocket-Key`；服务端返回 101 + `Sec-WebSocket-Accept`（key 拼上固定 GUID 做 SHA1 再 base64）。这个值不是加密，是**证明服务端真的懂 WS 协议**，防止中间的缓存代理把请求当普通 HTTP 处理。
- **码点**：`internal/msggateway/ws_server.go:143`（Upgrader）、`:479`（Upgrade 调用）、`:491`（wsHandler）。
- **追问**：为什么参数都放在 URL 里？→ 因为浏览器原生的 WebSocket API 不支持自定义 header，token 只能走 query 或子协议。代价是 token 会进日志（安全隐患）。

#### C2. 客户端发来的二进制数据怎么解析？

- **结论**：**双层编码**——外层是 `Req` 结构体（JSON 或 Gob），里层 `data` 字段是 base64(protobuf)。
- **展开**：外层要装 `reqIdentifier`、`token`、`sendID`、`operationID`、`msgIncr` 这些路由信息，用 JSON 是因为要跨语言；内层是业务消息，用 protobuf 是因为体积小、有 schema。
- **码点**：`internal/msggateway/encoder.go`（Gob/JSON 两套编码器）、`internal/msggateway/context.go:94-166`（解码分发）。
- **追问**：为什么要 base64？→ 因为 JSON 不能直接放二进制。代价是体积膨胀 33%。**如果纯 Go 之间通信，用 Gob 就不需要 base64**——这是 `sdkType=js` 要走 JSON 时的一个额外开销。

#### C3. 心跳怎么做的？为什么间隔要小于超时？

- **结论**：服务端定期 ping，客户端回 pong，超时未回就关连接。
- **展开**：`pingPeriod` 必须小于 `pongWait`，一般留 10% 余量（比如 54s vs 60s）。因为 ping 发出去到 pong 回来有网络延迟，如果两者相等，网络抖动一下就会误判。
- **码点**：`internal/msggateway/client.go`（读循环里的 pong handler 重置 deadline）、`internal/msggateway/constant.go`。
- **追问**：为什么需要心跳？TCP 不是有 keepalive 吗？→ TCP keepalive 默认 2 小时，而且中间设备（NAT、负载均衡）的超时更短。应用层心跳是为了**主动发现半开连接**，而不是等 TCP 自己超时。

#### C4. 多端登录怎么处理的？

- **结论**：策略配置化，四种策略；踢人时要同时踢连接和踢 token。
- **展开**：只踢连接，客户端会自动重连又进来；只踢 token，连接还在照样收消息。所以两者都要。另外有个关键补丁：**同 token 不踢**——多节点下重连时，旧节点可能还没清理，会出现同 token 两个连接，不踢是为了避免误伤自己。
- **码点**：`internal/msggateway/ws_server.go:333` `multiTerminalLoginChecker`、`:356` 的 `checkSameTokenFunc`、`:374` 的策略 switch、`config/share.yml:19` 的 `multiLogin.policy`。
- **追问**：`PCAndOther` 怎么实现的？→ 用 `fallthrough`：先过滤出「非 PC 的旧连接」，然后 fallthrough 复用「踢掉这些连接」的公共逻辑。**「选谁踢」是策略差异，「怎么踢」是共同逻辑。**

#### C5. HTTP API 层的鉴权是怎么做的？

- **结论**：认证在 API 层（token → userID），授权在 RPC 层（`CheckAdmin` / `CheckAccess`）。
- **展开**：中间件 `GinParseToken` 解析 token，把 userID 塞进 ctx；到了 RPC 层，凡是「操作别人数据」的接口都调 `CheckAccess(ctx, ownerUserID)` 比对。
- **码点**：`internal/api/router.go:396-425`（GinParseToken）、`pkg/authverify/token.go:56`（CheckAccess）、`:20`（CheckAdmin）。
- **追问**：这里有什么问题？→ **`GinParseToken` 的 switch 只有 `case POST`，没有 default**，而 Gin 里不调 `Abort()` 后续 handler 仍会执行，所以 13 个 GET 路由完全绕过了 token 校验。目前这 13 条都是内部接口（`/object/*name` 靠签名 URL、`/prometheus_discovery/*` 给 Prometheus），没有业务影响，但**新增 GET 业务接口就是越权**。

### D 组 · 消息链路（8 题，最重要）

#### D1. 一条消息从发出到对端收到，完整路径是什么？

见 2.2 的八步版。**核心记忆点**：WS → 网关 → gRPC → msg（校验）→ Kafka(toRedis) → msgtransfer（批处理 + seq）→ Redis + Kafka(toMongo/toPush) → push → 网关 → 客户端。

#### D2. 为什么发送接口不等落库就返回？

- **结论**：写放大扛不住。
- **展开**：500 人群一条消息，如果同步做「校验 + 分配 seq + 落库 + 扇出 500 次推送」，延迟随群规模线性增长。异步化后，发送侧只做「校验 + 投 MQ」，延迟和群规模无关。
- **码点**：`internal/rpc/msg/send.go:23`（SendMsg）、`:67`（群聊投 MQ）、`pkg/common/storage/controller/msg.go:112` `MsgToMQ`。
- **追问**：那客户端什么时候知道成功？→ 发送 API 返回的 `SendMsgResp` 里只有 `serverMsgID` 和 `clientMsgID`，**没有 seq**。seq 是异步分配的，客户端要通过推送或拉取才能拿到。这是「异步化」的直接体现。

#### D3. 消息乱序怎么办？

- **结论**：三层保序，缺一不可。
- **展开**：① Kafka 分区键用会话唯一键（同一会话进同一分区）；② batcher 用同一个 key 的哈希决定 worker；③ 同一批里同 key 的消息归一组串行处理。
- **码点**：`internal/rpc/msg/send.go:67`、`pkg/tools/batcher/batcher.go:245` `distributeMessage`。
- **追问**：为什么第 1、2 层必须用同一个 key？→ 如果用不同的 key（比如 Kafka 用 conversationID，batcher 用 userID），第二层就会打乱第一层排好的顺序。

#### D4. 消息重复怎么办？

- **结论**：靠「按 seq 定位 + 先 update 后 insert」的幂等写。
- **展开**：`docIndex = (seq-1)/100`、`arrayIndex = (seq-1)%100`，位置由 seq 唯一确定，所以重复写只会覆盖同一个位置。
- **码点**：`pkg/common/storage/controller/msg_transfer.go:98` `BatchInsertBlock`、`pkg/common/storage/database/mgo/msg.go:47` `UpdateMsg`。
- **追问**：如果 seq 本身重复了呢？→ 那就没救了，两条不同消息会互相覆盖。所以 seq 的唯一性是整条链的地基（`mgo/seq_conversation.go` 的索引缺 `Unique` 是个真实风险）。

#### D5. seq 是怎么分配的？为什么不用数据库自增？

- **结论**：号段预分配，Redis Lua 原子操作，Mongo `$inc` 兜底。不用自增是因为每条消息一次跨网络往返，高峰期扛不住。
- **展开**：单聊一次批 50，群聊 100。两段式 Lua：第一段判断状态（key 不存在 / 被锁 / 够用 / 用完），第二段校验锁值后写回新号段。**不能合并成一段，因为 Lua 里不能做 Mongo 调用。**
- **码点**：`pkg/common/storage/cache/redis/seq_conversation.go:244`（第一段）、`:325`（第二段）、`:349`（50/100 的选择）、`pkg/common/storage/database/mgo/seq_conversation.go`。
- **追问**：号段用不完怎么办？→ 产生空洞。这不可怕，因为读取侧本来就容忍「某个 seq 查不到消息」。

#### D6. 消息在 MongoDB 里怎么存的？为什么要分桶？

- **结论**：一个会话的 100 条消息存一个文档，`docIndex = (seq-1)/100`。
- **展开**：不分桶（一条一个文档）会导致索引爆炸；一整个会话一个文档会撞 16MB 上限，而且每次更新都要重写整个文档。100 条一桶是折中：单个文档小（几十 KB），索引数量可控，且能通过算术定位。
- **码点**：`pkg/common/storage/model/msg.go:11`（`singleGocMsgNum = 100`）、`pkg/common/storage/database/mgo/msg.go`（`docIndex` 计算）。
- **追问**：为什么是 100 不是 1000？→ 100 是编译期常量，上线后改不了（老数据对不上）。这是一个**架构级硬约束**，也是选型时最该想清楚的地方。

#### D7. 用户离线后再上线，怎么同步消息？

- **结论**：按 seq 区间拉取，四道边界收敛。
- **展开**：`begin = 本地 maxSeq + 1`，`end = min(会话 maxSeq, 用户 maxSeq)`，`num` 截断，方向（升/降）决定 `isEnd` 怎么算。未读数是 `maxSeq - hasReadSeq` 的减法，不是统计。
- **码点**：`internal/rpc/msg/sync_msg.go:17` `PullMessageBySeqs`、`pkg/common/storage/controller/msg.go:370` `GetMsgBySeqsRange`。
- **追问**：为什么不用时间戳？→ 客户端时钟不可信、同一毫秒分不出先后、时钟可能回拨、**而且时间戳稀疏，没法做减法算未读**。

#### D8. 群消息怎么扇出？500 人要推 500 次吗？

- **结论**：不是。一条群消息在 MQ 里只有一份，扇出在 push 服务做，且用「按节点批量」而不是「按人逐个」。
- **展开**：push 消费一条群消息 → 查群成员 → 算出要推的人 → 遍历所有网关节点，每个节点一次批量调用 `SuperGroupOnlineBatchPushOneMsg` → 网关内部再用内存队列（512 worker / 16384 缓冲）摊平到单连接。
- **码点**：`internal/push/push_handler.go:221` `Push2Group`、`:286` `groupMessagesHandler`、`internal/msggateway/hub_server.go:157`。
- **追问**：为什么不在存储层就写 500 份？→ 那是写扩散，写放大 500 倍。IM 选读扩散：存一份，读时按权限过滤。**代价是读的时候要判断「这个人能不能看」。**

### E 组 · seq 与存储（6 题）

#### E1. 为什么 seq 要「稠密」？

- **结论**：只有稠密，才能用「区间」表达状态、用「减法」算未读。
- **展开**：如果 seq 是 1、5、9，客户端说「我到 5 了」，服务端不知道 6、7、8 是不存在还是没收到。稠密之后，「5 之后到最新」就是一个连续的区间。
- **码点**：`pkg/common/storage/controller/msg.go:370`（区间拉取）、未读计算在 conversation 服务。
- **追问**：那号段产生空洞怎么办？→ 接受它。读取侧遇到不存在的 seq 就跳过，未读数因此可能略微偏大，但不会错到用户能感知。**这是「近似稠密」而不是「严格稠密」。**

#### E2. 撤回一条消息，存储上发生了什么？

- **结论**：写一个 `revoke` 标记，**读时改写**，不物理删除。
- **展开**：撤回后，别人读到的内容是「对方撤回了一条消息」，发送者自己还能看到原文（不同视角）。如果消息被别人引用过，还要额外处理「引用的消息已撤回」。
- **码点**：`pkg/common/storage/controller/msg.go:222` `RevokeMsg`、`:734` `handlerDeleteAndRevoked`（读时改写）。
- **追问**：为什么读时改写而不是写时物化？→ 写时物化要给每个成员改一份（O(N)）；读时改写只存一个标记（O(1)）。代价是读路径变复杂，而且逻辑有两份实现（mgo 层和 controller 层），容易漏。

#### E3. 用户删除一条消息，别人还能看到吗？

- **结论**：能。删除是**单人可见性**，写进 `del_list` 数组。
- **展开**：读的时候检查 `del_list` 里有没有当前 userID。清空整个会话用的是另一个机制：抬高 `min_seq` 水位（O(1)，不是逐条删）。
- **码点**：`pkg/common/storage/controller/msg.go:534` `DeleteUserMsgsBySeqs`、`:557` `SetUserConversationsMinSeqs`。
- **追问**：`del_list` 会不会太大？→ 会。500 人群 400 人都删了，数组就有 400 个 ID。极端情况接近文档上限。缓解办法是「超过一定比例就整条物理删」，但 OpenIM 没做。

#### E4. 已读怎么存？为什么群聊不做已读回执？

- **结论**：已读水位一个数字（Redis），回执是消息里的数组（只有单聊）。
- **展开**：水位用来算未读（O(1) 减法）；回执用来显示「已读」（O(人数)）。500 人群一条消息广播回执是 N² 成本，且绝大部分数据永远不会被查询。
- **码点**：`internal/rpc/msg/as_read.go:92` `MarkMsgsAsRead`、`pkg/common/storage/database/mgo/msg.go:232` `MarkSingleChatMsgsAsRead`。
- **追问**：水位会不会丢？→ 会。📌 `readSeqWriteRatio: 100` 声明了但全文未使用，意味着批量落库没实现。Redis 过期后回源 Mongo 拿到旧值，未读数会虚增。

#### E5. 缓存是怎么设计的？有几级？

- **结论**：三级——本地 LRU（~100ns）→ Redis（~0.3ms）→ MongoDB（几 ms）。
- **展开**：本地缓存解决「极热数据不走网络」；Redis 解决跨进程共享；Mongo 是真相。再叠加 rpccache，把「一次 RPC 的结果」缓存起来，并维护依赖图做级联失效。
- **码点**：`pkg/localcache/`、`pkg/rpccache/`、`pkg/common/storage/cache/redis/`。
- **追问**：缓存一致性怎么保证？→ rockscache 模式：`TagAsDeleted` 不是 DELETE，而是把 `lockUntil` 置 0 并设短 TTL，让读请求来抢锁刷新。再叠加「依赖图级联失效」解决 key 之间的依赖（比如删好友要同时失效 `FRIEND_IDS` 和 `IS_FRIEND`）。

#### E6. 群成员关系为什么用中间表？

- **结论**：三个硬约束——要反查「我加了哪些群」、单文档 16MB 上限、并发更新会互相覆盖。
- **展开**：内嵌数组在小群（<100 人）其实更好（一次查询拿全），但 OpenIM 要支持大群，只能选中间表。代价是读群信息要两次查询，所以加了缓存和冗余字段。
- **码点**：`pkg/common/storage/model/group_member.go`。
- **追问**：那成员数是读冗余字段吗？→ 不是，`FindGroupMemberNum` 是实时 count。**选择了准确而不是快**，因为踢人/加人时数量错会让用户困惑。

### F 组 · 业务域（5 题）

#### F1. JWT 不能吊销，怎么实现「踢下线」？

- **结论**：Redis 白名单。JWT 只是载体，真正的有效性靠 Redis 里的状态。
- **展开**：token 状态存在 HASH 里（`UID_PID_TOKEN_STATUS:userID:platform`），区分「被踢出」和「不存在」两种错误。创建新 token 时**先踢旧的再签新的**，保证同端最多一个有效 token。
- **码点**：`internal/rpc/auth/auth.go:157` `parseToken`（状态机）、`:115` `GetUserToken`、`pkg/common/storage/controller/auth.go`。
- **追问**：为什么用 HASH 不用独立 key？→ 要支持同端多 token，并且能精确踢某一端。独立 key 只能是「一端一个」，做不到「同端多个 token 但只踢最早的那个」。

#### F2. 好友关系怎么存的？为什么是两行？

- **结论**：双向两行，因为关系有方向属性（备注、置顶）、查询要走单索引、删除是单向的。
- **展开**：`BecomeFriends` 写两次。没有事务（单机 Mongo 不支持），所以理论上会出现半关系，靠「读路径只看自己那一行」来掩盖。
- **码点**：`pkg/common/storage/controller/friend.go:95` `BecomeFriends`。
- **追问**：拉黑为什么删好友？→ **拉黑不删好友**，只做单向阻断。而且发消息时的校验里**并不检查黑名单**——这是「好友关系」和「能否发消息」两个独立问题。

#### F3. 群禁言和成员禁言有什么区别？

- **结论**：群禁言改 `group.status`，成员禁言改 `group_member.mute_end_time`，两层独立。
- **展开**：群禁言时成员记录不变，成员禁言时群状态不变。校验时两个都要看。
- **码点**：`internal/rpc/msg/verify.go`（双规则校验）、`pkg/common/storage/model/group.go`、`group_member.go`。
- **追问**：群主能被禁言吗？→ 不能。群主转让时**先解除新群主的禁言**——这是「不变量」（群主不能被禁言）在入口处的保证。

#### F4. 撤回和删除的语义区别是什么？

- **结论**：**删是可见性问题，撤是内容问题。**
- **展开**：撤回是「这条消息被撤回了，请显示提示」——内容被替换，但消息还在（否则会话出现空洞）；删除是「我看不到它了」——别人不受影响。
- **码点**：`revoke` 字段 vs `del_list` 字段，都在消息文档里。
- **追问**：被撤回的消息如果被引用了呢？→ 引用方要显示「引用的消息已撤回」。这是读时改写的典型场景。

#### F5. 文件上传为什么走预签名？秒传怎么保证不误删？

- **结论**：预签名让客户端直传对象存储（省带宽），秒传靠引用计数（用 count 查询而不是计数字段）。
- **展开**：签名覆盖「操作 + key + 过期时间」，客户端从不接触 secret。秒传后多个 `object` 记录共享同一个 key，删除时 `count(key) == 0` 才真删。
- **码点**：`internal/rpc/third/s3.go`、`pkg/common/storage/database/mgo/object.go:98` `GetKeyCount`。
- **追问**：`/object/*name` 是 GET 免认证，安全吗？→ 靠签名 URL 保护，且内部 key 含 UUID 不可猜。但 `name` 由客户端定，靠「必须以 `<userID>/` 开头」做命名空间隔离——**这是应用层校验，有风险面**。

### G 组 · 中间件与并发（4 题）

#### H1. Kafka 的 topic 怎么规划的？为什么要分四个？

- **结论**：按「处理阶段」拆——toRedis（分配 seq + 写缓存）、toMongo（落库）、toPush（在线推送）、toOfflinePush（离线推送）。
- **展开**：拆开是为了**独立控制节奏**：落库慢了不该拖累推送，推送慢了不该拖累落库。每个 topic 可以有自己的消费者数量和重试策略。
- **码点**：`pkg/mqbuild/builder.go`。
- **追问**：会不会有消息在两个 topic 之间不一致？→ 会。比如落库成功但推送失败，用户就收不到。靠消费侧重试 + 客户端主动拉取兜底。

#### H2. Kafka 只保证分区内有序，这对设计有什么影响？

- **结论**：分区键必须选「需要保序的维度」——这里是会话 ID。
- **展开**：如果用随机分区或按用户分区，同一会话的消息会散到不同分区，顺序就丢了。用会话 ID 之后，同一会话永远进同一分区，Kafka 的分区内有序就变成了「会话内有序」。
- **码点**：`internal/rpc/msg/send.go:67`（`GenConversationUniqueKeyForGroup`）。
- **追问**：代价是什么？→ 热点会话（10 万人大群）会把一个分区打满，Kafka 的并行度对它完全无效。**保序和吞吐的正面冲突，选了保序。**

#### H3. 批处理怎么保证不丢？背压链是什么样的？

- **结论**：位点在整批完成后才提交；背压从下游一路传到 Kafka broker。
- **展开**：worker 慢 → 分片 channel 满 → scheduler 阻塞 → 停止拉取 → 压力落在 broker 的磁盘上（而不是进程内存）。**最终缓冲位置是 Kafka，这是有意的设计**——放内存会 OOM。
- **码点**：`pkg/tools/batcher/batcher.go:152` `scheduler`、`:263` `run`、`internal/msgtransfer/init.go`。
- **追问**：`Put` 失败怎么办？→ 📌 `online_history_msg_handler.go` 里 `Put` 失败只记日志仍返回 nil，缓冲满时消息会丢。这是一个真实缺陷。

#### H4. 项目里用了哪些并发模式？

- **结论**：七种——读循环+写队列、中心事件循环、哈希分片、worker pool、errgroup 限流扇出、原子+对象池、跨进程锁。
- **展开**：网关用「每连接两个 goroutine」+「中心事件循环串行改连接表」；msgtransfer 用「分片 worker pool」保序；push 用 `errgroup.SetLimit` 扇出到网关；cron 用 Redis 锁防重复执行。
- **码点**：`internal/msggateway/client.go`、`ws_server.go:171` `Run`、`pkg/tools/batcher/`、`internal/push/onlinepusher.go:91`、`internal/tools/cron/redis_locker.go`。
- **追问**：有发现问题吗？→ 有。`user_map.go:173` 在 `RLock` 保护下写 `userPlatform.Time`，是确定的数据竞争，`-race` 一定会报；`ws_server.go:155` 的 `clientPool` 只 `Put` 不 `Get`，对象池完全没用上。

### H 组 · 难点与反思（3 题）

#### I1. 如果让你改进这个项目，你会改什么？

**准备三个，按「影响 × 可验证」排序**：

1. **批次上限和 batcher size 不一致**（`msg_transfer.go:205`）：热门会话单批超 100 条整批失败。改成「按 docIndex 分组后检查每组」。
2. **失败语义缺失**（`batcher.go:272` 的 `Do` 无返回值）：落库失败仍提交位点，消息丢。改成返回 error + 靠幂等兜住重投。
3. **本地缓存命中率不可观测**（`localcache.WithTarget` 零调用）：5 个 rpccache 都用 `EmptyTarget{}`，没法判断本地缓存是否有效。

**说的时候配一句**：「前两个是正确性问题，第三个是可观测性问题。我会先修正确性——虽然丢消息的概率低，但一旦发生就无法追溯。」

#### I2. 这个项目有什么设计得不好的地方？

见 30 篇和 29 篇的「📌 待验证/缺陷」清单。**挑一个你能讲透的**，别念清单。

推荐：`userMaxSeq = 0` 的语义反直觉 + 没有文档说明。这个例子的好处是**你可以讲自己读错的过程**：

> 「我一开始看到『入群写 0、踢人写当前 max』，脑补成『0 = 看不到历史』，正好反了。后来去看读取侧才发现 `if userMaxSeq != 0` 这个判断——0 是『不限制』。这说明一个经验：**判断字段语义要看读它的地方，不要从写它的地方猜。**」

**这种「我犯过错然后搞清楚了」的叙述，比「我全都懂」可信度高得多。**

#### I3. 你从这个项目学到了什么？

**不要答「学到了 Kafka、MongoDB」**（那是工具名，不是能力）。答「方法」：

> 「最大的收获是理解了『每个设计都是被上一个选择逼出来的』。
>
> 比如我看到批处理，第一反应是『为了性能』，但读下去才发现批处理带来了乱序，所以要有三层保序；保序要求 seq 提前确定，所以要有号段；号段产生空洞，所以读取要容错；读取要高效，所以存储要分桶加位置寻址。
>
> **单独看任何一个设计都不合理，连起来才成立。** 这个视角让我读别的项目也能看进去——先找『它在解决什么冲突』，再看『代价是什么』。」

### 白板 1 · 消息链路全景

```
┌────────┐   WS    ┌────────────┐  gRPC   ┌─────────┐
│ Client │ ──────→ │ msggateway │ ──────→ │   msg   │
└────────┘         └────────────┘         └────┬────┘
     ↑                    ↑                    │ 校验 + 补字段
     │ WS push            │ gRPC               ↓
     │                    │              ┌──────────┐

     │            │   push     │         │ key=会话ID│
     │            └───────↑────┘         └────┬─────┘
     │                    │                   ↓
     │                    │            ┌──────────────┐
     │              Kafka toPush       │  msgtransfer │
     │                    ↑            │  batcher 500 │
     │                    │            │  /100ms/50w  │
     │            ┌───────┴────┐       └──┬────────┬──┘
     │            │   Redis    │←─seq──────┘        │
     │            │  seq/在线   │                   ↓
     │            └────────────┘            ┌──────────────┐

     │                                      └──────┬───────┘
```

**画的时候嘴上要说**：每一步「为什么要这样」。光画图不说话是减分的。

### 白板 2 · seq 分配的两段式

```
Malloc(convID, size)
   │
   ├─→ [Lua 第一段]
   │     EXISTS key? ──否──→ HSET LOCK、EXPIRE → 返回 1
   │     HEXISTS LOCK? ─是─→ 返回 2（等）
   │     CURR+size > LAST? ─是─→ HSET LOCK、CURR=LAST → 返回 3
   │     否则 → HSET CURR=CURR+size → 返回 0
   │
   ├─ 状态 0 → 直接用
   ├─ 状态 1/3 → 拿 lockValue → 去 Mongo $inc 取新段
   │              → [Lua 第二段] 校验 HGET LOCK == lockValue
   │                 ├─ 相等 → 写新 CURR/LAST、删 LOCK
   │                 └─ 不等 → 说明锁过期被别人抢了，放弃
   └─ 状态 2 → 重试
```

**关键一句**：「第二段的 `HGET LOCK == lockValue` 是安全阀——锁过期被别人抢走之后，旧请求回来不能覆盖新值。」

### 白板 3 · 多端同步的水位

```
会话 maxSeq = 1200        ← 服务端最新
用户 max_seq = 1100       ← 可见上界（被冻结过）
用户 min_seq = 500        ← 可见下界（清除过）
用户 hasReadSeq = 1050    ← 已读水位

拉取：begin = 本地maxSeq + 1
      end   = min(1200, 1100) = 1100
      未读  = 1100 - 1050 = 50
```

**关键一句**：「未读数是减法，不是 count。前提是 seq 稠密、只有别人的消息计数、非计数类消息关掉 `IsUnreadCount`。」
