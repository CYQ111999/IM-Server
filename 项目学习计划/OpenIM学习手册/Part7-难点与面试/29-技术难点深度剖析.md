## 第一部分 · 理论：什么叫「技术难点」

这一部分一行代码都没有。但它决定了你后面 14 个难点能不能讲出「层次感」。

### 1.1 难点不是「复杂的功能」，是「互相冲突的约束」

初学者容易把「难点」理解成「代码多、逻辑绕」。但真正的技术难点有一个共同特征：

> **两个或多个正确的目标互相冲突，你只能选一个方向妥协，而且必须说清妥协的代价。**

举个最直观的例子。IM 里「消息不能丢」和「发送要快」是冲突的：

- 要绝对不丢 → 发送时必须同步写库、等落盘、再返回 → 延迟从 5ms 变成 50ms
- 要发送快 → 先返回、异步落库 → 中间进程崩了消息就没了

你说「我两个都要」，那就是没理解问题。**面试官问难点，本质是在问：你意识到这个冲突了吗？你选了哪边？为什么？**

所以「难点」可以按冲突类型分成三类，OpenIM 恰好三类都有：

| 类型 | 冲突的两端 | OpenIM 里的例子 |
|---|---|---|
| **正确性 vs 性能** | 严格一致 / 低延迟高吞吐 | 消息落库要不要等、seq 要不要每次查库 |
| **规模 vs 简单** | 单机简单实现 / 十万连接与扇出 | 连接表单机 map、群消息 fanout |
| **实时 vs 最终一致** | 立刻可见 / 可恢复 | 已读水位只写 Redis、缓存与库不同步 |

**记住这张表**。面试时任何一个难点，你都可以先归类，再讲冲突，再讲取舍——这就自然有了结构，不会讲成流水账。

### 1.2 面试官问「你觉得这个项目最难的地方是什么」，他在考什么

这句话是行为面试里最容易被浪费的一题。很多人答成「功能列表」：「我们做了消息、群组、推送、文件上传……」——这等于没答。

面试官真正在筛四层能力，**一层比一层值钱**：

| 层次 | 你的回答长什么样 | 面试官心里的评价 |
|---|---|---|
| L1 知道现象 | 「消息用 Kafka 异步落库」 | 读过代码 |
| L2 知道方案 | 「用批处理 + 位点提交保证不丢」 | 理解了实现 |
| L3 知道为什么 | 「因为这个场景写放大 500 倍，同步写扛不住」 | 有工程判断 |
| L4 知道代价 | 「代价是最终一致，客户端要容忍几百毫秒的延迟，而且要处理重复投递」 | **可以给 offer 了** |

**L3 和 L4 的分界线是「代价」**。任何方案都有代价，能主动说出代价的人，说明他不是在背方案，而是真的权衡过。

所以本篇每个难点我都写了三样东西：**方案、为什么这么选、代价**。第三样是你要重点记的。

### 1.3 讲难点的通用模板（六步，可以直接套）

```
① 场景：什么情况下会出问题（一句话，带数字）
② 约束：为什么不能用最简单的办法（点出冲突）
③ 候选：至少两个方案，各一句优缺点
④ 选择：选了哪个 + 一句话理由
⑤ 代价：这个选择牺牲了什么 + 怎么缓解
⑥ 验证：怎么知道它真的有效（实验/指标/现象）
```

以「seq 分配」为例，套一遍：

> ① 群聊 500 人，一条消息要落库，如果每条消息都去 Mongo 取一次自增 ID，写入路径就多一次跨网络往返。
> ② 但 seq 又不能本地生成——多个 msgtransfer 实例会撞号。
> ③ 候选：Mongo 自增（简单但每次 RTT）、Snowflake（无 RTT 但有序性不满足「会话内连续」）、号段（一次取一批，内存分配）。
> ④ 选了号段：每实例每次取 50/100 个，用 Redis Lua 保证原子。
> ⑤ 代价：会有「已分配但没用完」的空洞，seq 不严格连续；缓解办法是读取侧允许跳过不存在的 seq。
> ⑥ 验证：看 Redis 里 `CURR/LAST` 的差值，和 Mongo 里实际最大 seq 比较，能看到空洞率。

**这个模板能套住本项目的绝大多数难点**。你现在可以试着用它讲「消息不丢」，讲不顺就往下读。

### 1.4 一个反面示范（对比着看）

同样讲「消息不丢」，L1 式回答：

> 「我们用 Kafka 做的，发了消息先进 Kafka，然后消费者落库，这样就不会丢了。」

这句话有 **三个漏洞**，面试官随便挑一个就能问穿：

1. **「进 Kafka 就不会丢？」** —— Kafka 默认 `acks=1`，leader 挂了就可能丢。它的可靠性靠副本，不靠「进了队列」。
2. **「消费者落库成功了吗？」** —— 如果落库失败但位点提交了，消息就永久丢了。这才是真正的难点。
3. **「重复怎么办？」** —— 位点没提交成功会重投，同一条消息可能落两次库。

对照 L4 式回答（本篇 2.1 节会完整展开）：

> 「发送侧只保证『写进 Kafka』，可靠性靠 topic 副本；真正的难点在消费侧——位点必须在整批处理完之后才提交，而且要保证『标记最后一条 = 标记整批』，这依赖同步等待；同时落库要幂等，因为位点回退会重投。」

差别在哪？**L4 回答指出了「哪一段才是真问题」**。

## 第二部分 · 14 个技术难点

按冲突类型分成四组。每个难点固定五段：**难在哪 / 方案 / 码点 / 代价 / 追问**。

### A 组 · 消息正确性（1-4）

这四个是 IM 的地基。任何一个破了，用户直接能感知（丢消息、乱序、重复）。

---

#### 难点 1 · 消息不丢：位点提交时机 🔴

**难在哪**

「不丢」听起来是个存储问题，实际上是**提交时机问题**。Kafka 的消费模型是「拉取—处理—提交位点」，如果处理失败但位点前进了，消息就永久消失，而且没有任何日志会告诉你「这里少了一条」。

更麻烦的是它和吞吐冲突：每处理一条提交一次位点，等于每条消息一次网络往返；攒着批量提交，崩溃时就会重放一批。

**方案**

OpenIM 的做法是「整批处理完，才标记最后一条」：

```
Kafka 拉一批 → batcher 按会话切片 → 分发给 worker → WaitGroup 等全部完成
                                                        ↓
                                            标记批次最后一条 → 提交位点
```

关键在最后两步的顺序。`internal/msgtransfer/online_msg_to_mongo_handler.go` 的落库回调里，是先做实际写入，再 `Mark()`，最后在 `Do` 返回后才 `Commit()`。

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/tools/batcher/batcher.go:245` `distributeMessage` | 按会话把一批切成多组，记录每组最后一条 |
| `pkg/tools/batcher/batcher.go:263` `run` | 每个 worker 处理一个 channel 分组 |
| `pkg/tools/batcher/batcher.go:272` `b.Do` | **业务处理入口，注意它没有返回值** |
| `internal/msgtransfer/online_msg_to_mongo_handler.go` | `MsgToMongoMQ` 落库 + `Mark` |
| `internal/msgtransfer/init.go` | `Subscribe` 的调用方，位点提交发生在这里 |

**代价（必须能说出来）**

1. **延迟换可靠**：整批等最慢的那条完成，尾延迟由最慢的 worker 决定。所以 batcher 的 `size=500`、`interval=100ms` 不能随便调大。
2. **失败语义缺失**：`Do` 没有返回值，业务失败无法向上传递，位点照常前进 —— 这是真实缺陷，📌 见难点 1 的「追问」。

**追问：如果落库失败了呢？**

现状：`HandleChatWs2Mongo` 没有返回值（`internal/msgtransfer/init.go:128-131`），所以 batcher 认为成功，位点照常提交 → **这一批消息就丢了**。

正确做法有两条路：
- 让 `Do` 返回 error，失败的批次不 Mark，触发重投（要配套幂等）
- 或者把失败消息投进死信 topic，异步补偿

这两条 OpenIM 都没做。**面试时主动指出这一点，比假装完美强得多**——但要紧接着说「如果我来改，我会让 `Do` 返回 error 并配合幂等写，因为落库本身就是按 seq 幂等的，重投的代价很低」。这样既承认问题，又展示方案能力。

#### 难点 2 · 消息不重：写入幂等 🟡

**难在哪**

上一条已经说明：位点回退会重投。Kafka 的语义是 **at-least-once**（至少一次），不是 exactly-once。所以**重复是常态，不是异常**。

重复的后果很严重：同一条消息在会话里出现两次，用户立刻能看见；如果 seq 也重复，整条链的假设（seq 唯一、稠密）全崩。

**方案**

靠「按 seq 定位 + 先 update 后 insert」实现幂等：

1. 每条消息的存储位置是确定的：`docIndex = (seq-1)/100`，`arrayIndex = (seq-1)%100`（`pkg/common/storage/database/mgo/msg.go`，分桶常量在 `pkg/common/storage/model/msg.go:11` `singleGocMsgNum=100`）
2. 写入时先尝试 `$set` 更新「已存在的那个位置」，如果更新影响行数为 0（说明位置空着），再 `$setOnInsert` / push 插入
3. 因为位置由 seq 唯一决定，重复写入只会覆盖同一个位置，不会产生第二条

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/common/storage/controller/msg_transfer.go:98` `BatchInsertBlock` | 按 docIndex 分组，逐文档批处理 |
| `pkg/common/storage/controller/msg_transfer.go:120` `batchInsertBlock`（controller 侧同名） | 更新优先、插入兜底的实现 |
| `pkg/common/storage/database/mgo/msg.go:47` `UpdateMsg` | `$set` 指定位置字段 |
| `pkg/common/storage/model/msg.go:11` | `singleGocMsgNum = 100` |

**代价**

- **位置表达式脆弱**：`$map` + `$arrayElemAt` 的更新语句复杂，出错时 Mongo 报的是「更新语法错」而不是「业务错」，排查成本高。
- **100 是编译期常量**：上线后不能改，改了和老数据对不上。这是架构级硬约束（📌 见 13 篇）。
- **幂等只在「seq 确定」时成立**：如果 seq 分配出了问题（重复分配），幂等就退化成「后写覆盖前写」，两条不同消息会互相覆盖。

**追问：为什么不用 Mongo 的 upsert 唯一索引？**

因为消息是**数组里的元素**，不是独立文档。唯一索引只能约束文档级字段，管不到数组下标。要用唯一索引就得「一条消息一个文档」——那就回到了「索引爆炸」的问题（详见 13 篇 1.2 节）。**这是「分桶」这个选择的连带代价**，不是疏忽。

#### 难点 3 · 同一会话有序：三层保序 🔴

**难在哪**

Kafka 只保证**分区内**有序。一条消息从进队到落库，中间要经过：Kafka 分区 → 消费线程 → batcher 分片 → worker。**任何一层打乱了顺序，最终存储就乱了。**

而乱序的后果比丢失更隐蔽：客户端按 seq 排序显示，如果落库时 seq 顺序错乱，读取时很可能出现「seq 5 的文档存在、seq 4 的文档不存在」的空洞。

**方案**

三层防线，缺一不可：

| 层 | 机制 | 码点 |
|---|---|---|
| **① 分区键** | MQ 的 key 用会话唯一键，同一会话进同一分区 | `internal/rpc/msg/send.go:67`（群）、`:178`（单聊）；`conversationutil.GenConversationUniqueKeyForGroup/ForSingle` |
| **② 分片** | batcher 用 `key` 的哈希值决定 worker，同一 key 永远同一 worker | `pkg/tools/batcher/batcher.go:245-262` |
| **③ 成组** | 同一批里相同 key 的消息归到一组，串行处理 | `categorizeMessageLists`，被 `distributeMessage` 调用 |

注意 ① 和 ② 用的是**同一个 key**。如果这两处用了不同的 key（比如 ① 用 conversationID、② 用 userID），保序就只在第一层成立，第二层会打乱。**这是很容易被忽略的一致性要求。**

**代价**

- **热点会话**：一个 10 万人的超级群，所有消息挤在一个分区、一个 worker 上。Kafka 的分区并行度对这个会话完全无效。这就是「保序」和「吞吐」的正面冲突——OpenIM 选择了保序（因为 IM 的业务不允许乱序），代价是超级群成为瓶颈。
- **worker 数固定为 50**：`pkg/tools/batcher/batcher.go` 的默认值。worker 多了会增加分片竞争，少了会拖慢整体。

**追问：群消息的扇出为什么不怕乱序？**

因为**扇出发生在推送阶段，不发生在存储阶段**。一条群消息在 Kafka 里只有一份（key 是群会话），落库一次，seq 分配一次。推给 500 个成员是在 push 服务里做的（难点 6），那里乱序不影响正确性——客户端最终以拉取到的 seq 为准。**这是「存储一次、推送多次」的设计带来的额外好处。**

#### 难点 4 · seq 不重号不漏号：号段分配 🔴

**难在哪**

seq 要满足四个条件，而且四个条件互相拉扯：

| 要求 | 为什么 | 冲突点 |
|---|---|---|
| 唯一 | 不能两条消息同号 | 多实例并发 → 需要协调 |
| 单调递增 | 客户端靠比大小判断新消息 | 本地生成可能倒退 |
| 稠密 | 稀疏就无法用「区间」表达状态（14 篇核心前提） | 号段预分配天然产生空洞 |
| 低延迟 | 发送路径不能等 DB | 每次取号都要 RTT 就慢了 |

「稠密」和「低延迟」是根本冲突：**要快就得预分配，预分配就必然有浪费**。

**方案**

两级号段：Redis 一次给一个实例批 50（单聊）/ 100（群聊），实例在内存里逐个发；Redis 的号段用完时，才去 Mongo `$inc` 申请下一段。

Redis 侧用 **两段式 Lua**，因为 Lua 里不能做 Mongo 调用：

```
第一段（脚本内）：检查 key 是否存在 / 是否被锁
                 ├─ 不存在 → 加锁，返回状态 1（调用方去 Mongo 申请）
                 ├─ 有锁   → 返回状态 2（别人在申请，等）
                 ├─ 段够用 → 直接分配，返回状态 0
                 └─ 段用完 → 加锁，返回状态 3（调用方去 Mongo 申请）
第二段（脚本内）：校验锁值没被别人改过 → 写入新号段 → 解锁
```

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/common/storage/cache/redis/seq_conversation.go:244` `malloc` | 第一段 Lua：状态码 0/1/2/3 |
| `pkg/common/storage/cache/redis/seq_conversation.go:325` `setSeqRetry` | 第二段 Lua：写回新号段 |
| `pkg/common/storage/cache/redis/seq_conversation.go:349` `getMallocSize` | 50 / 100 的取值逻辑 |
| `pkg/common/storage/cache/redis/seq_conversation.go:363` `Malloc` | 对外入口，串起两段 |
| `pkg/common/storage/database/mgo/seq_conversation.go` | Mongo `$inc` 兜底 |

**代价**

1. **空洞**：实例重启、批次没用完、并发竞争失败，都会留下没被使用的号。**这就是为什么「seq 稠密」在 OpenIM 里只是「近似稠密」**，读取侧必须容忍「某个 seq 查不到消息」。
2. **状态机复杂**：四个状态码 + 重试，代码量不小，而且 `setSeqRetry` **没有返回值**（📌 10 次全失败只记日志，调用方以为成功了）。
3. **锁和数据共用同一个 key**：`EXPIRE key lockSecond` 会缩短整个 hash 的寿命，是个隐藏的耦合（📌 详见 12 篇）。

**追问：为什么不直接用 Snowflake？**

Snowflake 生成的是「全局递增」，不是「会话内连续」。客户端要的是「这个会话里我漏了几条」，用 Snowflake 只能比较大小、不能算差值，未读数就没法用减法算（14 篇）。**seq 的本质是「会话内序号」，不是「全局 ID」**——这个区分讲清楚，说明你真理解了这个设计。

#### 难点 5 · 长连接管理：半开连接与状态收敛 🔴

**难在哪**

长连接和 HTTP 请求最大的区别是**它有状态，而且状态会「僵住」**：

- 客户端拔网线、进电梯、手机被系统冻结 → 服务端**收不到任何通知**
- TCP 连接在服务端看起来还「活着」，直到下一次写失败（可能要几分钟）
- 这种连接叫**半开连接**（half-open）

如果有 10 万个这样的僵尸连接，服务端会持续为它们保留内存、往它们身上推送失败的消息、并且**误判用户在线**（导致离线推送不发）。

**方案**

三层：

1. **心跳**：服务端定期 ping，客户端必须回 pong；超时未回就主动关闭。关键是 `pingPeriod < pongWait`，留出约 10% 的抖动余量。
2. **写超时**：每次写设置 deadline，写不出去立刻判定连接死亡，而不是等 TCP 自己超时。
3. **状态收敛**：连接断开后，从连接表删除、从在线 ZSET 删除、通知其他网关节点。三处必须都做，漏一处就出现「在线但收不到」。

**码点**

| 位置 | 作用 |
|---|---|
| `internal/msggateway/ws_server.go:143` | `websocket.Upgrader`，含 `HandshakeTimeout`、`CheckOrigin` |
| `internal/msggateway/client.go` | 读循环 / 写队列，心跳参数（`pingPeriod`、`pongWait`、`writeWait`） |
| `internal/msggateway/user_map.go` | 连接表，按 userID 分片 |
| `internal/msggateway/ws_server.go:171` `Run` | 中心事件循环，串行处理连接的增删 |
| `internal/msggateway/online.go` | 在线状态上报（Redis ZSET） |

**代价**

- **心跳本身消耗资源**：10 万连接 × 每 30 秒一次 ping = 每秒 3000+ 次写。所以心跳间隔不能太短。
- **判定延迟**：最坏情况下，一个已死的连接要等 `pongWait` 才被清理，这段时间内推给它的消息会失败，需要走离线通道兜底。
- **中心事件循环是单点**：所有连接增删都走一个 goroutine，虽然避免了锁，但连接抖动剧烈时（比如服务重启，10 万连接同时重连）这个 goroutine 会成为瓶颈。

**追问：为什么连接表要分片，事件循环却只有一个？**

分工不同：
- **读**（查某个用户的连接）是高频的，每次推送都要查 → 分片 + RWMutex，减少锁竞争
- **写**（增删连接）是低频的，但要求顺序一致（比如「删除旧连接」必须在「插入新连接」之前完成，否则多端互踢会出错）→ 单个 goroutine 串行，天然有序

**「读分片、写串行」是并发设计里非常常用的组合**，值得记住。

#### 难点 6 · 群消息扇出：一条消息打给 500 人 🔴

**难在哪**

一个 500 人群，一条消息要送到 500 个人的连接上。如果同步做，发送方的响应时间就和群规模成正比——500 人的群要 500 次推送，最大的群要几万次。

更麻烦的是**推送是「尽力而为」的**：某个人的连接刚好断了，推送失败，不能因此让整条消息失败。

**方案**

分三段解耦：

```
msgtransfer 落库成功
   └─ 投 toPush topic（一条消息只投一次，key = 群会话）
        └─ push 服务消费
             ├─ 查群成员（走缓存）
             ├─ 分批调网关（每个网关节点一次批量调用）
             └─ 在线推失败的 → 进离线推送
```

关键设计：
1. **一条群消息在 MQ 里只有一份**，不是 500 份。扇出发生在 push 服务内部。
2. **网关提供批量接口** `SuperGroupOnlineBatchPushOneMsg`，一个节点一次调用带一批用户，而不是「一个用户一次 RPC」。
3. **网关内部再用内存队列 + 固定 worker**，把「批量请求」摊平成「单连接写入」。

**码点**

| 位置 | 作用 |
|---|---|
| `internal/push/push_handler.go:221` `Push2Group` | 群推送入口 |
| `internal/push/push_handler.go:286` `groupMessagesHandler` | 分组成员、过滤、调网关 |
| `internal/push/onlinepusher.go:67` `GetConnsAndOnlinePush` | 遍历所有网关节点，`errgroup.SetLimit(maxWorkers)`（`:91`） |
| `internal/msggateway/hub_server.go:157` `SuperGroupOnlineBatchPushOneMsg` | 网关侧批量接口 |
| `internal/msggateway/hub_server.go:81` | `memamq.NewMemoryQueue(512, 1024*16)` = 512 worker + 16384 缓冲 |

**代价**

- **内存队列会满**：16384 的缓冲，突发大群消息时会阻塞 `PushCtx`。这个阻塞是**故意的背压**——不阻塞就会 OOM。代价是 push 服务的消费速度被网关拖慢。
- **推送重复**：批量调用失败会重试，可能重复推送，客户端要按 seq 去重。
- **群成员列表可能过期**：走缓存，刚被踢的人可能还收到一两条推送。这是「实时性 vs 成本」的取舍——要精确就得每次查库，500 人的群每条消息一次查库，扛不住。

**追问：为什么不在发送时就把 500 份消息写进各自的收件箱？**

那是「写扩散」模型（类似早期 Twitter）。优点是读快（每人只读自己的收件箱）；缺点是写放大 500 倍，一个 10 万人的群一条消息要写 10 万次。

OpenIM 选的是「读扩散」：消息只存一份（按会话），读的时候按权限过滤。代价是读取时要判断「这个人能不能看这条消息」（`userMinSeq`/`userMaxSeq` + 群成员校验），但写成本从 O(N) 降到 O(1)。

**这个取舍在面试里非常好用**，因为它对应着经典的「推 vs 拉」问题。能讲清「什么场景该写扩散（朋友圈/Feed）、什么场景该读扩散（IM 群聊）」，是加分项。

#### 难点 7 · 读放大与热 key：三级缓存 🟡

**难在哪**

一条消息要推给 500 人，push 服务要为每个人查一次「他在哪些网关节点上」。500 人 = 500 次查询，如果是 10 万 QPS 的消息量，查询量就是 5000 万/秒。**这不是 QPS 问题，是网络带宽问题**——每次查询哪怕只有 1KB，也是 50GB/s。

同时还有**热 key**：一个明星用户在的群、一个被疯狂转发的人，会让某个 Redis key 的访问集中在单个分片上。

**方案**

三级缓存，每级解决不同的问题：

| 层 | 解决什么 | 延迟量级 |
|---|---|---|
| 本地 LRU（进程内） | 极热数据，避免每次都走网络 | ~100ns |
| Redis | 跨进程共享，容量大 | ~0.3ms |
| MongoDB | 真相 | ~几 ms |

再叠加 **rpccache**：把「一次 RPC 调用」的结果缓存起来，并维护**依赖图**——某个用户的好友列表变了，所有依赖它的缓存项一起失效。

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/localcache/` | 本地 LRU（`lru_lazy.go`、`lru_expiration.go`），分槽减少锁竞争 |
| `pkg/rpccache/common.go` | 缓存封装 + 依赖注册 |
| `pkg/rpccache/friend.go` | 好友关系缓存 + `delLinked` 级联失效 |
| `pkg/common/storage/cache/redis/` | Redis 实现（rockscache 模式：`HASH` + `lockUntil` + `lockOwner`） |
| `pkg/common/redis/`（外部 `redisutil`） | 客户端初始化 |

**代价**

- **一致性变弱**：三级缓存意味着最长可能有「本地缓存 TTL」那么久的脏数据。缓解办法是「失效时广播」——rpccache 的依赖图就是干这个的。
- **可观测性缺失**：📌 `localcache.WithTarget` **全项目零调用**，5 个 rpccache 都用 `EmptyTarget{}`，所以**本地缓存的命中率完全看不到**。这是很实际的问题：你没法判断本地缓存到底有没有起作用。
- **内存**：本地缓存占的是进程内存，多实例部署时每份都存一份，总内存是实例数倍。

**追问：本地缓存和 Redis 不一致怎么办？**

三层策略：
1. **写时失效**：写库成功后删 Redis + 广播让其他实例删本地
2. **短 TTL 兜底**：即使广播丢了，最多脏一个 TTL 周期
3. **关键路径不走本地缓存**：比如权限校验必须读最新，宁可多一次 Redis 查询

**这也解释了为什么 OpenIM 的 `StrongConsistency` 配置默认为 true**（缓存刷新时读请求等待，不返回旧值）——它选择了「宁可慢，不给旧值」。

#### 难点 8 · 写路径削峰：批处理 🔴

**难在哪**

消息发送是**尖峰型**流量：平时 1000 QPS，跨年零点可能 5 万 QPS。如果每条消息都单独写一次 Mongo，尖峰时 Mongo 的写入会成为瓶颈，而且每个连接的网络往返也会把 CPU 吃满。

但批处理有代价：**延迟**。攒批就得等，等就意味着消息晚到。

**方案**

用 batcher 做「双触发」聚合：

```
攒够 500 条  → 立即发车
或 等满 100ms → 强制发车（不管够不够）
```

发车后按会话切片，分给 50 个 worker 并行处理。

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/tools/batcher/batcher.go:34-64` | `WithSize`（500）、`WithBuffer`、`WithWorker`（50）、`WithInterval`（100ms）、`WithSyncWait` |
| `pkg/tools/batcher/batcher.go:152` `scheduler` | 计时器 + 数量双触发 |
| `pkg/tools/batcher/batcher.go:245` `distributeMessage` | 按会话切分 |
| `internal/msgtransfer/online_history_msg_handler.go:18-40` | 常量定义（500 / 100ms / 50） |
| `pkg/common/storage/controller/msg_transfer.go:203` `BatchInsertChat2Cache` | 批量写 Redis |

**代价（三条，都能被追问）**

1. **最坏延迟 = 100ms + 处理时间**。对 IM 来说可接受（人对 200ms 内无感），但对「语音通话信令」这类场景就不行——所以信令走的是另一条路。
2. **单批上限和分桶常量冲突**：`msg_transfer.go:205` 检查 `len > GetSingleGocMsgNum()`（=100）就整批报错，但 batcher 的 `size` 是 500。**热门会话单批超过 100 条时，这一批会全部失败**（📌 参数不一致，是真实缺陷）。
3. **worker 无 `defer recover()`**（`batcher.go:263-278`）：一条畸形消息 panic，整个进程挂掉。

**追问：为什么 interval 是 100ms 而不是 10ms？**

两个考虑：
- 10ms 会让「攒批」几乎失效（大部分时候都攒不够 500 条），退化成「逐条处理 + 10ms 延迟」，白付了延迟
- 100ms 时，高流量下能自然攒够 500 条（按 5000 QPS 算，100ms 有 500 条），低流量下延迟也可接受

**这是「批处理」调参的通用直觉：interval ≈ size / 预期峰值 QPS**。500 / 5000 = 100ms，正好。

#### 难点 9 · 多端同步：怎么知道「我漏了哪些」 🔴

**难在哪**

用户在手机上看了一半，换到电脑上打开，要看到「同一条消息、同样的顺序、同样的已读状态」。这是**状态同步问题**，不是「拉消息」问题。

朴素方案是「客户端每个设备存最后一条消息的 ID，重连时问服务端『这条之后有什么』」。但：
- 客户端可能同时存了几百个会话的状态
- 「之后」在乱序到达时无法定义
- 消息被删了，「最后一条」就不存在了

**方案**

用**每个会话一个整数**（seq）表示「我看到了哪里」。这个整数是服务端分配的，客户端只存不生成。

| 概念 | 含义 | 存储位置 |
|---|---|---|
| 会话 `maxSeq` | 这个会话最新消息的 seq | Redis + Mongo |
| 用户 `max_seq` | 这个用户可见的上界 | 会话表 per-user 行 + seq_user 缓存 |
| 用户 `min_seq` | 这个用户可见的下界 | 同上 |
| 用户 `hasReadSeq` | 已读水位 | seq_user 缓存（Redis） |

同步时：`begin = 本地maxSeq + 1`，`end = min(会话maxSeq, 用户maxSeq)`，按方向拉取，`num` 截断，`isEnd` 判断是否拉完。

**码点**

| 位置 | 作用 |
|---|---|
| `internal/rpc/msg/sync_msg.go:17` `PullMessageBySeqs` | 同步入口，传 `conversation.MaxSeq` 作为上界 |
| `pkg/common/storage/controller/msg.go:370` `GetMsgBySeqsRange` | 四道边界收敛 |
| `pkg/common/storage/controller/msg.go:390-395` | `if userMaxSeq != 0` 的上界收紧 |
| `pkg/common/storage/controller/msg.go:426` `GetMsgBySeqs` | 按指定 seq 列表拉（通知会话走这里） |

**代价**

- **依赖 seq 稠密**：不稠密就会出现「拉到中间卡住」。所以读取侧必须容忍空洞（跳过不存在的 seq）。
- **状态在服务端**：多端一致的前提是所有端都问服务端，客户端不能自己算。这意味着每次冷启动都要一次网络往返（`get_max_seq`）。
- **`hasReadSeq` 只写 Redis**（📌 `readSeqWriteRatio` 声明了但没用）：Redis 过期后回源 Mongo 是旧值，未读数会虚增。

**追问：时间戳为什么不行？**

四个理由（14 篇展开过）：客户端时钟不可信、同一毫秒无法区分先后、时钟可能回拨、时间戳稀疏无法用「区间」表达。**最根本的是第 4 条**：时间戳不能做减法算未读数，seq 可以。

#### 难点 10 · 已读：一个数字不够，一群数字又太贵 🔴

**难在哪**

「已读」在单聊和群聊是两个完全不同的问题：

- 单聊：我读了没有？→ 一个数字（`hasReadSeq`）就够
- 群聊：**谁**读了？→ 500 个人每人一个状态

如果统一用「每人一个布尔标记」，存储是 O(成员数 × 消息数)，一条群消息写 500 次；如果统一用「一个水位」，群聊就没法显示「谁读了」。

**方案**

拆成两个概念，各用各的数据结构：

| | 已读水位 | 已读回执 |
|---|---|---|
| 谁用 | 自己（算未读） | 别人（看「谁读了」） |
| 成本 | O(1) 一个数字 | O(N) 每人一个 |
| 存储 | Redis `seq_user` HASH | Mongo 消息文档里的 `is_read` 数组 |
| 群聊默认 | 有 | **不广播**（只在水位里前进） |

**码点**

| 位置 | 作用 |
|---|---|
| `internal/rpc/msg/as_read.go:92` `MarkMsgsAsRead` | 标记指定消息已读 |
| `internal/rpc/msg/as_read.go:100-116` | 取 `Seqs` 最后一个作为水位，且只允许前进 |
| `internal/rpc/msg/as_read.go:134` `MarkConversationAsRead` | 整个会话标已读 |
| `internal/rpc/msg/as_read.go:150-152` | 补齐区间（📌 无上限，大跨度会构造巨量切片） |
| `pkg/common/storage/database/mgo/msg.go:232` `MarkSingleChatMsgsAsRead` | 单聊才写 `is_read` |

**代价**

- **群聊看不到「谁读了」**：产品上是功能缺失，但技术上是对的——500 人群一条消息广播回执是 N² 成本。
- **水位只能前进**：`MarkMsgsAsRead` 里 `if hasReadSeq > currentHasReadSeq` 才写。这保证了不会因为乱序请求把水位倒退，但也意味着「标记更早的消息已读」不生效（业务上通常不需要）。
- **补齐区间无上限**：`for i := hasReadSeq + 1; i <= req.HasReadSeq; i++` —— 如果客户端传一个巨大的 `HasReadSeq`，会构造一个巨大的切片，**是潜在的 OOM 点**。

**追问：为什么不把已读做成「每条消息一个标记文档」？**

那就是 O(消息数 × 人数) 的存储。500 人群一天 1 万条消息 = 500 万条已读记录。而水位只要 500 个数字。**差了 4 个数量级。**

#### 难点 11 · 在线状态：如何表达「三端在线且 iOS 已过期」 🟡

**难在哪**

「用户在线」不是一个布尔值：

- 一个人可能同时有 iOS、Android、PC 三端在线
- iOS 端可能已经退到后台（还能收推送，但不算「活跃」）
- 服务端进程崩了，在线状态不会自动消失（没有「断开」事件）
- 多个网关节点，每个节点只知道自己的连接

**方案**

用 Redis **ZSET**，`member` = 平台 ID，`score` = **过期时间戳**：

```
ZADD online:{userID} {now+60s} 1        # 平台 1 上线
ZREMRANGEBYSCORE online:{userID} -inf {now}   # 惰性清理过期成员
ZCARD online:{userID}                    # 还有几个端在线
```

关键点有三个：

1. **用 score 而不是 TTL**：TTL 只能对整个 key 生效，没法表达「iOS 过期了但 Android 还在」。
2. **惰性清理**：不靠定时任务删，而是在每次读写这个 key 时顺手清掉过期的（`ZREMRANGEBYSCORE`）。
3. **续期周期 = 租约 / 3**：60 秒租约、20 秒续期，容忍两次续期失败，代价是进程崩溃后最多 60 秒误判在线。

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/common/storage/cache/redis/online.go:30` | `GetOnline`：`ZRangeByScore` 过滤过期 |
| `pkg/common/storage/cache/redis/online.go:66` | `GetAllOnlineUsers`：📌 用 `ZRANGE` 不过滤过期，与上面口径不一致 |
| `internal/msggateway/online.go` | 网关侧上报在线状态 |
| `internal/rpc/user/online.go` | 用户服务侧查询在线状态 |

**代价**

- **崩溃残留**：进程被 kill 时来不及删 key，僵尸成员会留到下次有人写这个 key 才被清掉（📌 `EXPIRE` 每次重置会延长残留时间）。
- **误判窗口**：最坏 60 秒内，一个已经掉线的人仍被判定在线，这期间推给他的消息会失败，需要离线推送兜底。
- **两个函数口径不一致**：`GetOnline` 用 `ZRangeByScore`（过滤过期），`GetAllOnlineUsers` 用 `ZRANGE`（不过期）——**同一份数据，两个函数给出不同答案**。

**追问：为什么不直接用 `SET key 1 EX 60`？**

因为那是「整个用户一个 TTL」。iOS 在线、Android 在线时，key 只有一个 TTL，无法区分哪个端过期了。要做多端就得「每个端一个 key」，那样查一次在线状态要 N 次查询。**ZSET 用一个 key 表达了 N 个独立过期时间**，这是它在这里不可替代的原因。

#### 难点 12 · 缓存一致性：删一个 key 会连带影响谁 🟡

**难在哪**

缓存的最大坑不是「缓存和库不一致」，而是**「缓存之间有依赖」**。

例子：
- `FRIEND_IDS:userA` = A 的好友列表
- `IS_FRIEND:userA-userB` = A 和 B 是不是好友

删掉好友关系时，如果只删了 `FRIEND_IDS:userA`，`IS_FRIEND:userA-userB` 还是 `true`——**用户会看到「已经不是好友但还能发消息」**。

而且缓存项是**动态生成**的：`IS_FRIEND:A-B` 可能在任意时刻被任意请求创建，你不知道有哪些 key 存在。

**方案**

**双向邻接表 + DFS 连通分量**：

1. 每次读到「A 是 B 的好友」时，在内存里记一条边 `A → B`
2. 失效 `FRIEND_IDS:userA` 时，从 A 出发做深度优先遍历，找出所有和 A 连通的缓存项，一起删掉

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/rpccache/common.go` | `GetLink` / `delLinked`，依赖图的维护 |
| `pkg/rpccache/friend.go` | 好友缓存的依赖注册与级联删除 |
| `pkg/rpccache/user.go` | 用户信息缓存 |
| `pkg/rpccache/conversation.go` | 会话缓存 |

**代价**

- **内存**：依赖图本身要占内存，边数随访问过的「好友对」增长。
- **遍历开销**：一个好友很多的人，失效时要遍历一大片。所以 `delLinked` 是 `go` 出去的（`pkg/rpccache/friend.go`）——**注意这个 `go` 不是为了性能，是为了避开「Mutex 不可重入」**：同一分片的锁已经持有，再同步进去会死锁。
- **最终一致**：级联删除是异步的，中间有一小段窗口期能看到不一致。

**追问：为什么不给每个 key 设短 TTL 就完事？**

短 TTL 解决的是「最终会一致」，但不解决「一致之前用户看到错的东西」。好友关系的错乱是**功能性错误**（能发消息给已经删掉的人），不是「数据稍旧」。这类错误必须主动失效，不能靠 TTL。

**判断标准**：数据错了会让用户「做错事」→ 必须主动失效；数据旧了只是「看起来不新」→ TTL 可以接受。

#### 难点 13 · 权限变更的即时生效 🔴

**难在哪**

「把人踢出群」这个操作，要在**多个层面同时生效**：

1. 他不能再拉新消息（拉取时校验）
2. 他不能再发消息（发送时校验）
3. 他的客户端应该收到「你被踢了」的通知
4. 已经推给他但还没处理的消息，不应该再推

如果只做了 1，他还能发消息；只做了 1、2，他的客户端还在显示群；全做了但没做 4，他可能还收到几条。

**方案**

**双层防护：入口校验 + 数据边界**。

| 层面 | 机制 | 码点 |
|---|---|---|
| 发送时 | `verify.go` 六维校验：会话存在、成员身份、群状态、禁言、黑名单、好友关系 | `internal/rpc/msg/verify.go` |
| 拉取时 | `userMaxSeq` 冻结上界、`userMinSeq` 抬高下界 | `controller/msg.go:390-395` |
| 推送时 | 查群成员列表，不在列表里的不推 | `internal/push/push_handler.go:286` |
| 通知 | 系统消息走 `n_` 通知会话 | `pkg/msgprocessor/conversation.go` |

**关键洞察**：`userMaxSeq` 冻结是「数据边界」——即使校验逻辑被绕过（比如某个新接口忘了校验），被踢的人也拉不到新消息，因为他的上界停在那里。**这是「纵深防御」的典型应用：不依赖单一检查点。**

**码点（冻结逻辑）**

| 位置 | 作用 |
|---|---|
| `internal/rpc/group/group.go:1026` `deleteMemberAndSetConversationSeq` | 退群/被踢：`max_seq = 当前群 max` |
| `internal/rpc/group/group.go:1035` `setMemberJoinSeq` | 入群：`max_seq = 0`（解除限制） |
| `internal/push/push_handler.go:402` | push 侧同样逻辑（异步路径） |
| `pkg/common/storage/controller/msg.go:393` | 读取侧 `if userMaxSeq != 0` 才收紧 |

**代价**

- **重复实现**：群服务和 push 服务各有一份冻结逻辑，改了一处忘另一处就会不一致。
- **不精确**：冻结的是「当时的最大 seq」，如果有一条消息正在处理中（已分配 seq 但还没落库），被踢的人可能刚好能看到它。这是「最终一致」的必然代价。
- **入群时写 0 的语义反直觉**：`0` 不是「上界为零」，是「不限制」。⚠️ 面试时如果讲成「设 0 = 看不到历史」，会被懂行的人一眼看穿（我本人就在这里读反过一次，详见 18 篇 1.4 节的修正记录）。

**追问：被踢的人为什么还能看到历史消息？**

因为存储是「按会话存一份」，不是「按人存一份」。他能拉到的范围被 `userMaxSeq` 限制在「被踢那一刻」，之前的历史依然可读。**这是有意的产品设计**（和微信一致：被踢后聊天记录还在本地，重新进群前拉不到新的）。

如果要「彻底不可见」，就得在读取时校验群成员身份，或者把历史消息按人复制一份——前者增加读路径开销，后者是 O(N) 存储。**都不划算，所以选择了「历史保留、新消息切断」。**

#### 难点 14 · 全链路可观测 + 优雅停机 🟡

**难在哪**

微服务下，一个用户操作会经过 API → RPC → MQ → 消费者 → 网关，五跳。出了问题，日志散在五个进程里。**没有统一的追踪 ID，排查等于大海捞针。**

优雅停机是另一面：进程收到 SIGTERM 时，如果立刻退出，正在处理的请求会被中断、Kafka 位点可能没提交、客户端会看到连接被重置。

**方案**

**追踪**：一个 `operationID` 贯穿全链路。
- 同步链路（HTTP → gRPC）通过 `ctx` + metadata 传递
- 异步链路（Kafka）通过**消息体**携带，消费时恢复到 ctx
- 日志库在写日志时自动从 ctx 抽取 6 个字段（operationID、userID、平台等）

**停机**：先停止接收新请求（从服务发现摘除）→ 等在途请求完成（GracefulStop）→ 关连接 → 退出。

**码点**

| 位置 | 作用 |
|---|---|
| `pkg/common/middleware/`（外部 `mcontext`） | operationID 注入与读取 |
| `internal/api/router.go` `ParseOperationID` | HTTP 入口生成/透传 |
| `pkg/common/startrpc/start.go:255` | gRPC `GracefulStop`（📌 与 `cmd/main.go:350` 的 10s 超时冲突） |
| `pkg/common/prommetrics/` | 四类指标：API、RPC、消息、中转 |
| `config/prometheus.yml` + `internal/api/prometheus_discovery.go` | 动态服务发现 |

**代价**

- **超时不匹配**：外层等 10 秒，内层 GracefulStop 等 15 秒 → **内层的优雅等待永远不会完成**，实际是强杀。这是真实的配置缺陷。
- **PID 1 问题**：Docker 里 `ENTRYPOINT sh -c "./mage start && sleep infinity"` → PID 1 是 `sleep`，SIGTERM 打不到 Go 进程，29 个子进程变孤儿。**容器化部署下，优雅停机实际上是失效的。**
- **日志级别反序**：`LevelFatal=0` … `LevelDebugWithSQL=6`，配置里写 `3` 是 Warn 不是 Info。不了解的人会以为「日志丢了」。

**追问：异步链路怎么串？**

把 operationID 放进 Kafka 消息体（不是 header，因为 Kafka 的 header 在跨语言场景下不一定被保留）。消费时读出来，`mcontext.WithOperationID(ctx, id)` 造一个新 ctx。**代价是消息体变大一点点，收益是整条链路可查。**

## 第三部分 · 难点之间不是孤立的

这 14 个难点不是并列关系，它们之间有明确的因果链。**理解这个结构，你讲的时候就不会散。**

```
                    ┌─────────────────────────┐
                    │ 8 写削峰（batcher）      │
                    └───────────┬─────────────┘
                                │ 批处理引入乱序风险
                                ▼
                    ┌─────────────────────────┐
                    │ 3 保序（三层防线）        │
                    └───────────┬─────────────┘
                                │ 保序要求 seq 确定
                                ▼
        ┌───────────────────────────────────────────┐
        │ 4 seq 号段分配                              │
        └───────┬───────────────────────┬───────────┘
                │ 空洞                    │ seq 确定
                ▼                        ▼
    ┌───────────────────┐    ┌─────────────────────────┐
    │ 9 同步（容忍空洞）  │    │ 2 幂等（按 seq 定位）      │
    └───────────┬───────┘    └───────────┬─────────────┘
                │                        │
                │ 同步需要索引             │ 幂等需要位置稳定
                ▼                        ▼
        ┌───────────────────────────────────────────┐
        │ 13 存储模型（100 条一桶 + 位置寻址）         │
        └───────────────────────────────────────────┘
```

另一条链是规模侧的：

```
5 长连接管理 ──→ 6 群扇出 ──→ 7 读放大/热 key ──→ 12 缓存一致性
      │               │
      │               └──→ 11 在线状态（推给谁）
      │
      └──→ 14 可观测性（连接数、推送失败率）
```

**面试时的用法**：不要一个难点一个难点地列，而是**挑一条链讲**。

比如：

> 「这个项目最核心的一条链是『怎么让一条消息又快又对地到对端』。快靠批处理削峰，批处理就会乱序，所以要三层保序；保序的基础是 seq，seq 要快就不能每次查库，所以用号段预分配，号段必然产生空洞，于是读取侧必须容忍空洞；而读的时候为了只取需要的那几条，就有了 100 条一桶的位置寻址。**这几个设计是连着的，任何一个单独拿出来看都不合理。**」

这段话的信息密度，比列 14 个难点高得多。

## 第六部分 · 面试话术（含追问链）

<details>
<summary>🔴 「这个项目你觉得最难的地方是什么？」（推荐答案）</summary>

> 「我会分两层说。
>
> **第一层是消息的正确性**。发送接口只做校验和投递就返回，落库和推送都是异步的——这是为了扛住写放大。但异步就带来三个问题：消息可能丢（位点提交早了）、可能重（位点回退重投）、可能乱序（多段并发）。
>
> 解决方式是一套组合：位点在整批处理完之后才提交，靠『标记最后一条等于标记整批』这个等价关系；落库按 seq 定位，先 update 后 insert，所以重投是幂等的；保序靠三层——Kafka 分区键用会话 ID、batcher 按 key 哈希分片、同 key 成组处理。
>
> **第二层是 seq 的分配**，因为上面所有东西都建立在『seq 唯一且大致连续』上。为了不给发送路径加数据库往返，它用号段预分配：Redis 一次给 50 或 100 个，用完才去 Mongo 取下一段。代价是会产生空洞，所以读取侧必须容忍『某个 seq 查不到消息』。
>
> 我觉得最能体现设计功力的是：**这几个机制是互相咬合的**。批处理带来乱序，所以要保序；保序要求 seq 提前确定，所以要号段；号段产生空洞，所以读取要容错；读取要高效，所以存储用 100 条一桶加位置寻址。单独看任何一个都不合理。」
</details>

<details>
<summary>追问 1：「位点提交早了会丢，那你怎么保证不早？」</summary>

> 「关键是提交的时机必须在『整批 worker 全部完成』之后。代码里是 `WaitGroup.Wait()` 之后才 `Mark` 最后一条、再 `Commit`。这里有个隐含前提：**标记最后一条等价于标记整批**，这要求同步等待——也就是 batcher 的 `syncWait=true`。如果改成异步，标记最后一条时前面的可能还没处理完，这个等价关系就破了。
>
> 不过这块有个真实的缺陷：batcher 的 `Do` 没有返回值，业务失败无法上报，位点照常前进。也就是说**落库失败时这批消息会丢**。要修的话，让 `Do` 返回 error，失败就不 Mark，靠幂等兜住重投。」
</details>

<details>
<summary>追问 2：「seq 为什么不能用数据库自增？」</summary>

> 「能用，但太慢。每条消息一次 `findAndModify` 就是一次跨网络往返，高峰期这条路径会成为瓶颈。更重要的是它没法批量——你没法一次申请 100 个连续 ID。
>
> 号段的本质是『把 100 次往返压成 1 次』。代价是预分配的号可能用不完，产生空洞。而空洞在这个系统里是可接受的，因为读取侧本来就是按 seq 列表查、查不到就跳过。」
</details>

<details>
<summary>追问 3：「如果 Redis 挂了，seq 还能分配吗？」</summary>

> 「分配不出来。`Malloc` 第一步就是走 Redis 的 Lua 脚本，Redis 不可用会直接报错，消息发送链路就断了。这是一个真实的单点——虽然 Redis 可以主从/集群，但它是**强依赖**，不是缓存降级可用的那种。
>
> 相比之下 Mongo 挂了反而好一点：号段还在 Redis 里，能继续分配一段时间（`LAST - CURR` 那么多），只是新号段申请不出来。**所以这里的可用性排序是 Redis > Mongo**，和直觉上『数据库最重要』相反。」
</details>

<details>
<summary>追问 4：「说一个你觉得设计得不好的地方。」</summary>

> 「我挑一个影响比较实际的：**`msg_transfer.go:205` 的批次上限是 100，但 batcher 的批大小是 500**。也就是说热门会话单批超过 100 条时，整批会报 `message count exceeds limit` 直接失败。
>
> 根因是两处用了不同的约束来源：100 来自存储分桶常量 `singleGocMsgNum`（一个文档最多 100 条），500 来自 batcher 的吞吐调参。但这两者本来不该相等——500 条消息完全可以拆进 5 个文档。所以正确做法是『按 docIndex 分组后再检查每组的 100』，而不是拿总数去比 100。
>
> 另一个是 `readSeqWriteRatio` 这个字段声明了但全文没有使用，导致已读水位只写 Redis，Redis 过期后回源 MongoDB 拿到的是旧值，未读数会虚增。这两个都属于『设计了一半』的问题。」
</details>

## 本篇小结：必须记住的 8 句话

| # | 一句话 |
|---|---|
| 1 | 难点 = 两个正确目标冲突，讲难点必须讲**代价** |
| 2 | 「不丢」的难点在**消费侧位点提交时机**，不在发送侧 |
| 3 | 「不重」靠**按 seq 定位 + 先 update 后 insert** 的幂等 |
| 4 | 保序三层，第 1、2 层必须用**同一个 key** |
| 5 | seq 的四个要求里，**稠密**和**低延迟**冲突，号段是妥协产物 |
| 6 | 群消息**存一份、推多次**（读扩散），写扩散的成本是 O(N) |
| 7 | 已读拆两个概念：**水位 O(1) / 回执 O(N)** |
| 8 | `userMaxSeq = 0` 是「不限制」，判断字段语义**看读取侧** |
