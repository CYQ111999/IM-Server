## 一、这套手册怎么用

### 1.1 三阶段目标

| 阶段     | 达成标志                            | 对应 Part         |

### 1.2 单篇的正确读法（四步，别跳）

```
1. 先读「本篇目标」→ 知道要解决什么问题
2. 读正文时，凡遇到 文件:行号，打开源码对照看一眼（30 秒）
3. 合上文章，做「自测题」→ 讲不出来就回去补
4. 找机会做「实验」→ 能动手验证的绝不止于读
```

**关键心态**：不要追求「读完」，要追求「能复述」。一篇 3000 字读完后脑子里只剩 3 句话，那就把 3 句话写下来，比读得快更重要。

## 五、常见误区（先打预防针）

| 误区                 | 事实                                               |
| ------------------ | ------------------------------------------------ |
| 「API 层是业务核心」       | ⚠️ 错。API 层只是 `a2r.Call` 翻译层，业务在 `internal/rpc/*` |
| 「消息发送后就落库了」        | ⚠️ 错。发送只投 Kafka，落库是下游异步                          |
| 「seq 在发消息时生成」      | ⚠️ 错。在 msgtransfer 消费时分配                         |
| 「Redis 是主存储」       | ⚠️ 错。Mongo 是真相，Redis 是缓存 + seq                   |
| 「网关存消息」            | ⚠️ 错。网关无状态，只持有连接                                 |
| 「限流按用户/IP」         | ⚠️ 错。本项目是进程级 BBR 自适应限流                           |
| 「incrversion 是个服务」 | ⚠️ 错。它是泛型算法包，没有 Start、没有 gRPC                    |
| 「有 7 个 server.go」  | ⚠️ 错。只有 `internal/rpc/msg/server.go` 一个          |

> **Part7 的一个更正（重要，务必看）**：`userMaxSeq` 的语义此前的理解是**反的**。
> - 正确语义：`userMaxSeq` 是「可见上界」，但 **`0` 被读取侧特判为「不限制」**（`pkg/common/storage/controller/msg.go:393` `if userMaxSeq != 0`）。
> - 所以「踢人写当前 max」= 冻结上界（历史留着、新消息拉不到）；「入群写 0」= **解除限制（能看到入群前的历史）**，作用是 reset，用于清掉曾被踢残留的冻结值。
> - 此前 18 篇写成「入群设 0 = 看不到历史」，14 篇的面试话术里也写成了「新人 userMinSeq 设成 maxSeq」，**均已修正**。
> - 方法论教训：**判断字段语义看读取点，不看写入点。** 写入点只说明谁在改，读取点才说明值意味着什么。

> **Part5 的一个更正**：之前的笔记写「`internal/msgtransfer/init.go` 的 `for { Subscribe }` 是死代码」是**错的**。`mq.Consumer.Subscribe` 每次只处理一条消息就返回，所以这个循环是「逐条消费」的主循环。真正的 bug 是循环体里出错就 `return`，不重连。已在 23 篇 2.9 节更正。

> **Part6 的三个关键澄清（此前一直是模糊表述）**：
> 1. **「29 个进程」的确切来源**：`start-config.yml` 的 `serviceBinaries` 实例数合计（api 1 + crontask 4 + 8 个 rpc 各 1 + push 8 + msgtransfer 8 = 29）。之前只写「应看到 29 个进程」，没人解释为什么。
> 2. **项目有两套启动入口**：`cmd/main.go`（一体化，12 服务同进程 + inprocess 进程内 RPC）与 `cmd/openim-*/main.go`（拆分，13 个入口经 `pkg/common/cmd` + `startrpc.Start`）。`mage start` 走的是后者。
> 3. **`inprocess` 不是直接函数调用**：`methodRegistry.RegisterService` 仍然走 `codec.Marshal/Unmarshal`，只是省掉网络栈——为的是深拷贝隔离与「一体化/拆分语义一致」。
