# 第一部分 理论：数据怎么在网上走

## 7.1 一切的起点：内存里的结构体，网线上没有

### 7.1.1 一个看似简单的问题

你在 Go 里有一个结构体：

```go
type MsgData struct {
    SendID   string
    RecvID   string
    Content  string
    SendTime int64
}
```

现在你要把它发给 1000 公里外的一台服务器。**网线里只能跑 0 和 1。**

问题来了：**怎么把"一个有字段名的结构体"变成"一串字节"，再在对端变回来？**

这个动作叫**序列化（Serialization）**，反向叫**反序列化（Deserialization）**。

```
内存对象  ──序列化──→  字节流  ──网络──→  字节流  ──反序列化──→  内存对象
{            Encode                        Decode            {
  SendID: "u1"                                                SendID: "u1"
  Content: "hi"                                               Content: "hi"
}                                                             }
```

**关键认知**：字节流里**没有类型信息、没有字段名、没有边界**，这些全靠**双方约定的格式**来还原。所以序列化格式本质上是**一份协议合同**——两边必须完全一致，否则解出来就是垃圾。

### 7.1.2 为什么不能直接 memcpy 内存

新手常有的疑问："结构体在内存里就是连续的字节，直接拷过去不就行了？"

**不行**，三个原因：

**① 内存布局是编译器决定的，不可移植**

```go
type A struct {
    a bool    // 1 字节
    b int64   // 8 字节
}
```

由于**内存对齐（alignment）**，`A` 在 64 位机器上通常占 16 字节（1 字节 bool + 7 字节填充 + 8 字节 int64）。换个编译器/架构，填充可能不同。直接 memcpy 过去，对端按自己的布局解释 → 字段全错位。

**② 指针无意义**

结构体里的指针存的是**本进程的虚拟地址**。传到对端，那个地址在对方进程里指向完全无关的内存。所以序列化必须**把指针指向的内容也带上**（深度序列化）。

**③ 字符串是"指针 + 长度"**

Go 的 string 底层是 `{ptr, len}`，真正的字符数据在别处。直接拷贝结构体只会拷过去一个地址。

📌 **所以序列化不是"拷贝内存"，而是"按约定重新编排数据"**。这个认知很重要——它解释了为什么序列化有性能开销，也解释了为什么不同格式性能差好几倍。

## 7.2 序列化格式的两大阵营：文本 vs 二进制

所有序列化格式，本质上都在回答三个问题：

1. **怎么表示"字段"？**（靠名字？靠编号？靠顺序？）
2. **怎么表示"类型"？**（自带类型信息？还是靠 schema？）
3. **怎么表示"结束"？**（靠长度前缀？靠特殊符号？靠 schema？）

按答案不同，分成两派。

### 7.2.1 文本协议：人能读

**代表**：JSON、XML、YAML、CSV

```json
{"sendID":"user001","recvID":"user002","content":"你好","sendTime":1729500000000}
```

**特点**：

| 维度 | 表现 |
|---|---|
| 可读性 | ✅ 人能直接看懂，抓包就能排查 |
| 体积 | ❌ 大。字段名重复传输，数字也变字符串 |
| 解析速度 | ❌ 慢。要逐字符扫描、处理转义、解析浮点 |
| 类型 | ⚠️ 弱。只有 number/string/bool/null/array/object，int64 会丢精度（JS 的 number 只有 53 位） |
| 跨语言 | ✅ 所有语言都支持 |
| 演进 | ✅ 加字段不影响老客户端（忽略未知字段） |

**为什么 JSON 统治了 Web？** 因为**可调试性**是无价的。一个接口出问题，打开浏览器 F12 就能看到请求响应，不需要任何工具。这个工程价值远超性能损失。

⚠️ **JSON 的一个著名坑**：`int64` 精度丢失。

```js
JSON.parse('{"id": 9007199254740993}')  // → 9007199254740992
```

因为 JS 的 number 是 IEEE 754 双精度，只能精确表示 2^53 以内的整数。IM 里的 msgID、seq 经常是大整数，所以**协议里大整数一律用 string**——这就是为什么很多 API 返回的 ID 是字符串而不是数字。

### 7.2.2 二进制协议：机器高效

**代表**：protobuf、Thrift、MessagePack、FlatBuffers、Avro

```
08 06 75 73 65 72 30 30 31   ← 字段号8 + 长度6 + "user001"
```

**特点**：

| 维度 | 表现 |
|---|---|
| 可读性 | ❌ 二进制，必须用工具解 |
| 体积 | ✅ 小。字段名用数字代替，数字用变长编码 |
| 解析速度 | ✅ 快。按 schema 直接跳读，不需要扫描 |
| 类型 | ✅ 强。int32/int64/bytes/enum 明确 |
| 跨语言 | ✅ 靠 IDL 生成代码 |
| 演进 | ✅ 靠字段号，兼容性好 |

### 7.2.3 怎么选（这是架构决策）

| 场景 | 推荐 | 理由 |
|---|---|---|
| 对外 OpenAPI、第三方接入 | JSON | 谁都能调，文档即示例 |
| 内部服务间高频调用 | protobuf/gRPC | 性能、强类型、自动生成代码 |
| 移动端弱网 | protobuf + 压缩 | 省流量就是省钱 |
| 配置文件 | YAML/JSON | 人工编辑 |
| 日志 | JSON（结构化日志） | 可检索 |

**OpenIM 的选择很有意思**：**两层都用**。

```
外层信封（Req/Resp）：JSON 或 Gob，可选
内层载荷（MsgData）：protobuf，固定
```

**为什么这么设计？** 第二部分 7.12 会详细讲，先记住这个矛盾点：**如果能全用 protobuf，为什么外层还要留一个 JSON 的可能性？**

## 7.3 base64：为什么二进制要"变成文字"

### 7.3.1 问题的产生

假设你已经用 protobuf 把消息序列化成了一串字节：

```
0x0A 0x06 0x75 0x73 0x65 0x72 0x30 0x30 0x31 ...
```

现在你要把它放进一个 **JSON 字符串**里：

```json
{"data": "???"}
```

**问题**：JSON 字符串必须是**合法的 Unicode 文本**。上面那串字节里有 `0x00`、`0xFF` 这类**控制字符和非法 UTF-8 序列**，直接塞进 JSON 会：
- 破坏 JSON 语法（引号、反斜杠可能被误认为语法）；
- 传输过程中被某些中间件按文本处理，字节被改写。

**所以需要一个"把任意字节安全地表示成纯文本"的方法。**

### 7.3.2 base64 是什么

base64 的原理很朴素：**用 64 个可打印字符来表示 6 个 bit**。

```
64 个字符 = A-Z (26) + a-z (26) + 0-9 (10) + '+' + '/'  = 64
6 bit 的取值空间 = 2^6 = 64   ← 正好对应
```

**编码过程**（3 字节 → 4 字符）：

```
原始字节：  01001101 01100001 01101110     (3 字节 = 24 bit)
按 6 bit 切：010011 010110 000101 101110
查表：        T      W      F      u
结果：       "TWFu"
```

**为什么是"膨胀 33%"？**

```
3 字节 → 4 字符 = 24 bit → 32 bit
32 / 24 = 1.333...
```

**每 3 个字节变成 4 个字符，体积增加 1/3**。这是 base64 的固有代价。

### 7.3.3 三种变体（必须分清）

| 变体 | 字符表差异 | 填充 | 用在哪 |
|---|---|---|---|
| **标准 base64** | `+` 和 `/` | `=` 补齐 | 邮件、HTTP Basic Auth |
| **URL-safe base64** | `-` 和 `_` | `=` 补齐 | JWT、URL 参数 |
| **Raw URL-safe base64** | `-` 和 `_` | **无填充** | 严格场景（如本项目 `v` 参数） |

**为什么 URL 里要用 URL-safe 版本？**

因为标准 base64 的 `+` 在 URL 查询串里**会被解码成空格**，`/` 会被当成路径分隔符。你辛苦编码的数据，到了服务端就变了。

**为什么要去掉 `=` 填充？** 因为 `=` 在某些场景（如 JWT、文件名）会造成歧义，而填充长度可以推算出来。

📌 **这就是 06 篇提到 `base64.RawURLEncoding` 的原因**：`v` 参数要放进 URL，必须用无填充的 URL-safe 变体。

### 7.3.4 一个必须纠正的误解

⚠️ **base64 不是加密，也不是压缩。**

- 它是**编码（encoding）**，任何人都能解开；
- 它会让数据**变大** 33%，不是变小。

**看到 base64 就以为是"加密过的"是新手常见错误**。JWT 的 payload 就是 base64，任何人都能读——安全性完全靠签名。

## 7.4 protobuf 深入：为什么它又快又小

protobuf（Protocol Buffers）是 Google 的序列化方案，gRPC 的默认格式。理解它的三个核心机制，就理解了二进制协议的精髓。

### 7.4.1 机制一：用「字段号」代替「字段名」

先写一个 `.proto` 文件（这叫 **IDL，接口定义语言**）：

```protobuf
message MsgData {
  string sendID   = 1;   // ← 1 是字段号
  string recvID   = 2;
  string content  = 3;
  int64  sendTime = 4;
}
```

**对比 JSON**：

```json
{"sendID":"user001","recvID":"user002","content":"你好","sendTime":1729500000000}
     ↑ 12 个字符的字段名                            ↑ 8 个字符
```

```protobuf
字段号1 + 长度6 + "user001"     ≈ 9 字节
字段号2 + 长度6 + "user002"     ≈ 9 字节
字段号3 + 长度6 + "你好"(6字节)  ≈ 9 字节
字段号4 + 数字编码              ≈ 8 字节
```

**字段名完全不传输**——只传字段号。这就是体积优势的主要来源。

**代价**：接收方必须**有同样的 .proto 定义**才能解出字段名。所以 protobuf **不是自描述的**（self-describing），脱离 schema 就是一堆数字。

### 7.4.2 机制二：varint —— 小数字占少字节

固定 4 字节表示 int 很浪费。protobuf 用 **varint（变长整数）**：

```
每个字节用 7 位存数据，最高位（MSB）表示"后面还有没有字节"

数值 1      → 00000001                        （1 字节）
数值 300    → 10101100 00000010               （2 字节）
数值 1729500000000 → 需要 6 字节
```

**规则**：数值越小，占用越少。**这就是为什么字段号 1~15 要用在最频繁的字段上**（它们只需 1 字节编号）。

⚠️ **varint 对负数的坑**：负数用补码表示，会变成"很大"的数（10 字节）。所以 protobuf 对负数用 `sint32/sint64`（zigzag 编码：`-1 → 1`，`1 → 2`）。**用错类型会让体积涨 10 倍**，这是 protobuf 的经典性能陷阱。

### 7.4.3 机制三：TLV 结构——为什么可以跳过不认识的字段

每个字段编码成：

```
[Tag] [Length] [Value]
  ↑      ↑        ↑
字段号+类型  长度   内容（仅变长类型有 Length）
```

**关键能力**：解析器可以**只看 Tag**，如果这个字段号不在我的 schema 里，就根据 Length 直接**跳过 Value**。

**这带来两个极其重要的性质**：

**① 后向兼容（新服务端读旧数据）**
老版本存的数据没有新字段 → 解析时该字段为默认值，不报错。

**② 前向兼容（旧客户端读新数据）**
服务端加了新字段 → 老客户端不认识 → **跳过**，不影响其他字段解析。

**这就是 "向后兼容" 的底层机制**，也是 protobuf 能长期演进的根本原因。JSON 靠"忽略未知 key"也有类似效果，但没有强类型约束。

### 7.4.4 字段号是永久契约（重要纪律）

⚠️ **已经上线的字段号，永远不能改、不能复用。**

```protobuf
message User {
  string name = 1;
  // 后来废弃了 age 字段
  reserved 2;              // ← 必须保留，防止后人复用
  string email = 3;
}
```

**如果复用了字段号 2**：
```
老数据里字段 2 是 int32 age = 25
新代码里字段 2 是 string phone
→ 解析器把 25 当字符串长度 → 崩溃或读出垃圾
```

**这是 protobuf 使用中最严重的错误**，会造成历史数据不可读。所以规范做法是 `reserved`。

## 7.5 Gob：Go 特有的序列化

### 7.5.1 Gob 是什么

`encoding/gob` 是 Go 标准库自带的序列化格式。设计目标：**Go 结构体之间高效传输，无需写 IDL**。

```go
var buf bytes.Buffer
enc := gob.NewEncoder(&buf)
enc.Encode(MsgData{SendID: "u1"})     // 直接用结构体，不需要 .proto

var m MsgData
dec := gob.NewDecoder(&buf)
dec.Decode(&m)
```

### 7.5.2 Gob 的三个特点

| 特点 | 说明 |
|---|---|
| **自描述** | 第一次编码时会带上类型信息（字段名、类型），后续同类型只发值 |
| **Go 专属** | 只有 Go 能解，Java/Python 无法解析 |
| **流式** | Encoder/Decoder 是有状态的，绑定一个 io.Writer/Reader，**连续编码多条** |

**"自描述 + 有状态"是 Gob 能和 protobuf 竞争的原因**：同一个连接上连续发消息，第一条带上类型定义，后面只发值，**平均开销比 protobuf 还低**。

### 7.5.3 为什么 Gob 不能跨语言

因为 Gob 的类型信息是 **Go 的类型系统**（含 struct tag、interface 动态类型），没有跨语言标准。别的语言没有"Go 的 interface 是什么"这个概念。

**所以 Gob 只适合"两端都是 Go"的场景**。

📌 **这解释了 OpenIM 的默认值为什么是 `sdkType=go`**：它的主力客户端是 Go SDK（服务端集成、机器人、压测工具），用 Gob 最省。但这导致**浏览器必须显式声明 `sdkType=js`**，否则就是让 Go 的解码器去解 JSON——必然失败。

### 7.5.4 ⚠️ Gob 的并发陷阱

**Gob 的 Encoder/Decoder 是有状态的，不是线程安全的。**

```go
enc := gob.NewEncoder(w)
go enc.Encode(a)   // ❌ 数据竞争
go enc.Encode(b)   // ❌ 输出会交错，彻底损坏
```

**多 goroutine 同时用同一个 Gob Encoder 编码，会把字节流写乱**。

📌 **这印证了 06 篇 6.13.4 的疑问**：`writeBinaryMsg` 里把 `Encode` 放在锁外，对 Gob 编码器**存在并发隐患**。如果这条连接同时被"响应"和"推送"两个 goroutine 写，就可能损坏。**这是一个真实的潜在 bug**（📌 待验证：需要确认是否有其他同步机制）。

## 7.6 压缩：gzip 是什么，什么时候值得

### 7.6.1 原理（一句话）

gzip = **LZ77（找重复字符串）+ 哈夫曼编码（高频字符用短码）**。

直观理解：文本里"的"、"了"、`"content"` 这类片段重复率高，用"引用前面出现过的位置"代替 → 大幅缩短。

### 7.6.2 什么时候值得压缩

**压缩有固定开销**：
- gzip 头 + 尾 ≈ 18 字节；
- CPU 要扫描全文；
- 小数据压缩后**可能更大**。

**判断标准**：

```
压缩后收益 = 原始大小 × 压缩率 - 18 字节头 - CPU 成本
```

| 数据 | 原始 | 压缩后 | 值得吗 |
|---|---|---|---|
| `"hi"` | 2B | 20B | ❌ 变大了 |
| 1KB 文本 | 1024B | ~500B | ✅ |
| 图片（已压缩） | 200KB | 200KB | ❌ 白费 CPU |
| JSON 日志 | 10KB | ~1.5KB | ✅ 收益巨大 |

**结论**：
- **文本类、结构化数据** → 压缩收益高；
- **已压缩的二进制（图片/视频/zip）** → 不要压，纯浪费。

📌 **这解释了为什么 `compression` 是可选参数、默认关闭**：IM 的大部分消息很小（"在吗"、"好的"），压缩反而亏。只有发长文本、大 JSON 时才值得开。

### 7.6.3 压缩 vs 序列化的顺序

**必须记住这个顺序**：

```
发送：结构体 → 序列化 → 压缩 → 写帧
接收：读帧 → 解压 → 反序列化 → 结构体
```

**为什么不能反过来？** 因为压缩算法处理的是**字节流**，而序列化是把结构体变成字节流。顺序颠倒没有意义（不能压缩结构体）。

⚠️ **这个顺序错了，症状是"解出来是乱码"**——因为对端把你没解压的字节当成了序列化数据。

## 7.7 信封模式（Envelope）：为什么要套两层

### 7.7.1 什么是信封

寄信时，信纸外面要套一个信封，信封上写收件人、寄件人、单号。**信封是给邮政系统看的，信纸是给收件人看的。**

协议设计里同理：

```
┌─────────────────────────────────────┐
│ 信封 Envelope（给传输层/框架看）      │
│  ┌───────────────────────────────┐  │
│  │ 载荷 Payload（给业务代码看）    │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

本项目：

```
Req {
    reqIdentifier  ← 信封：这是什么类型的请求
    token          ← 信封：凭据
    sendID         ← 信封：谁发的
    operationID    ← 信封：追踪 ID
    msgIncr        ← 信封：请求序号
    data           ← 载荷：base64(protobuf MsgData)
}
```

### 7.7.2 为什么要套两层（三个真实理由）

**理由一：统一的"路由"能力**

一条连接上跑着 10 种请求（发消息、拉历史、拉会话、订阅在线状态…）。服务端必须先知道"这是什么请求"，才能决定交给谁处理。

如果只有载荷（纯 protobuf MsgData），服务端拿到字节**根本无法判断类型**——protobuf 不自描述，不同 message 的字节可能长得一样。

**信封的 `reqIdentifier` 就是这个"路由标签"。**

**理由二：统一的"元数据"通道**

token、operationID（链路追踪）、msgIncr（请求配对）这些信息**不属于业务数据**，但每个请求都需要。放进信封，业务载荷就不用重复定义。

**理由三：信封和载荷可以独立演进**

- 信封用 JSON → 加一个字段，老客户端忽略即可；
- 载荷用 protobuf → 加字段靠字段号兼容。

**两者解耦**，各自用最适合的格式。

### 7.7.3 信封模式的代价

**两次序列化 + 一次 base64**：

```
业务对象 --protobuf--> 字节 --base64--> 字符串 --JSON--> 最终字节
```

**性能**：比"纯 protobuf 一条到底"慢，体积也大 33%（base64）。

**为什么还这么做？** 因为**可调试性和通用性**值这个代价。用 JSON 信封，你能直接在浏览器 Network 面板看到 `reqIdentifier: 1003`，一眼知道在发消息；纯二进制协议必须用专用工具解。

📌 **这是典型的"性能让位于可维护性"取舍**。面试时能讲出这个权衡，比背"用了 protobuf 所以快"强得多。

## 7.8 三个 ID 的区别：这是 IM 协议设计的核心

初学者最容易混淆的地方。**ClientMsgID、ServerMsgID、Seq 是三个完全不同的东西**，各有用途，缺一不可。

### 7.8.1 ClientMsgID：客户端生成的"幂等键"

**谁生成**：客户端，在用户点"发送"的瞬间。

**作用**：**去重**。

**为什么需要？**

```
用户点发送 → 客户端发出 → 网络超时 → 客户端不知道成没成功
→ 自动重试 → 服务端收到两条一样的消息 → 用户看到两条"你好"
```

如果有 ClientMsgID：

```
第一条：ClientMsgID = "abc-123" → 服务端存下
重试条：ClientMsgID = "abc-123" → 服务端发现已存在 → 丢弃/返回原结果
```

**这就是"幂等"（Idempotency）**：同一个操作执行多次，效果和执行一次相同。

⚠️ **重试时 ClientMsgID 必须不变**。如果重试时重新生成 ID，幂等就失效了。这是客户端实现的常见 bug。

### 7.8.2 ServerMsgID：服务端生成的"全局唯一标识"

**谁生成**：服务端，收到消息后。

**作用**：**全局唯一引用**。

**为什么 ClientMsgID 不够？**

因为 ClientMsgID 是客户端生成的，**可能冲突**：
- 两个不同的客户端用了相同的 UUID 生成算法（概率极低但存在）；
- 恶意客户端可以故意伪造重复 ID。

服务端需要一个自己完全掌控的、全局唯一的 ID 来标识"这条消息"。本项目的生成方式（`GetMsgID`）：

```
ServerMsgID = md5(时间戳 + 发送者ID + 随机数)
```

**用途**：
- 撤回消息时定位（"撤回 serverMsgID = xxx 这条"）；
- 引用消息时指向（"引用 xxx"）；
- 客户端去重、排序辅助。

### 7.8.3 Seq：会话内自增序号（最重要的一个）

**谁生成**：服务端，**在消息落库阶段**。

**作用**：**排序 + 增量同步**。

**为什么前两个都不行？**

| ID | 能排序吗 | 能判断"漏了哪些"吗 |
|---|---|---|
| ClientMsgID | ❌ 随机的 | ❌ |
| ServerMsgID | ❌ md5 是散列，无序 | ❌ |
| **Seq** | ✅ **单调递增** | ✅ **连续，缺哪个一眼看出** |

**Seq 的关键性质**：
1. **会话内唯一**（不是全局唯一）；
2. **单调递增**；
3. **尽量连续**（Typing 这类不落库的消息不占 seq）。

**它解决了 IM 最核心的问题：断线重连后怎么补齐消息？**

```
客户端本地记录：这个会话我看过的最大 seq = 100
重连后：向服务端请求 seq > 100 的所有消息
服务端：返回 101, 102, ..., 150
```

**这个模型极其简洁**，比"按时间戳范围拉取"可靠得多（时间戳会重复、会乱序、受客户端时钟影响）。

📌 **面试必问**："IM 怎么保证消息不丢不重？" 答案的核心就是 seq 机制。第 11 篇会讲 seq 怎么分配。

### 7.8.4 三者的关系（一张图记住）

```
用户点发送
    ↓
客户端生成 ClientMsgID ← 幂等键（防重复发送）
    ↓
服务端收到，生成 ServerMsgID ← 全局唯一（用于引用/撤回）
    ↓
消息进入 MQ，消费时分配 Seq ← 会话内有序（用于同步）
    ↓
落库、推送
```

| ID | 生成方 | 生成时机 | 唯一性范围 | 核心用途 |
|---|---|---|---|---|
| ClientMsgID | 客户端 | 点发送时 | 客户端保证 | **幂等去重** |
| ServerMsgID | 服务端 | 收到时 | 全局 | **唯一引用** |
| Seq | 服务端 | 落库时 | **会话内** | **排序 + 增量同步** |

⚠️ **一个高频误解**：以为"有 ServerMsgID 就能排序"。**不行**，它是 md5，无序。**只有 seq 能排序**。

## 7.9 指令码与枚举：协议怎么"分流"

### 7.9.1 什么是指令码

一条连接上跑着多种请求。服务端需要一个字段来区分：

```go
switch req.ReqIdentifier {
case 1003:  // 发消息
case 1005:  // 拉消息
case 2005:  // 订阅在线状态
}
```

**这就是指令码（Command / Opcode / ReqIdentifier）**。本质是**协议层的路由键**。

### 7.9.2 分段设计的智慧

本项目的指令码分段：

| 段 | 含义 |
|---|---|
| 1xxx | 客户端 → 服务端（请求） |
| 2xxx | 服务端 → 客户端（推送/通知） |
| 3xxx | 错误 |

**为什么要分段？**

**理由一：一眼看方向**。抓包看到 2001，立刻知道"这是服务端推来的消息"；看到 1003，知道"客户端在发消息"。

**理由二：避免编号冲突**。新增请求就加 1008、1009，新增推送就加 2006，两边不会打架。

**理由三：便于客户端分流**。客户端一个 switch，1xxx 走"等响应"逻辑，2xxx 走"被动接收"逻辑。

📌 这是个**很小的设计，但体现工程素养**。很多项目指令码是乱序的 1、2、3、7、15，后期维护很痛苦。

### 7.9.3 为什么不用字符串做指令码

```go
case "send_msg":     // 字符串
case 1003:           // 数字
```

| | 字符串 | 数字 |
|---|---|---|
| 体积 | 8 字节+ | 1~2 字节（varint） |
| 比较速度 | 逐字符比较 | 整数比较 |
| 拼写错误 | 运行时才发现 | 编译器能查（如果用常量） |
| 可读性 | ✅ 好 | ❌ 需要查表 |

**内部协议用数字，对外 API 用字符串**——这是通用做法。HTTP 路径 `/msg/send_msg` 是人类可读的，底层 WS 指令码 1003 是机器高效的。

## 7.10 协议演进：怎么改协议而不炸掉老客户端

### 7.10.1 三条铁律

**铁律一：只加字段，不改不删**

老客户端不认识新字段 → 忽略；如果改字段含义，老客户端会误解 → 事故。

**铁律二：字段号/字段名永不复用**

（protobuf 的 `reserved`、JSON 的"废弃但不删除"）

**铁律三：默认值要能表达"没有"**

新增字段必须有合理的零值语义，否则老数据解析后行为异常。

### 7.10.2 本项目怎么做的三个例子

**例 1：`v` 参数（新握手方式）**

老方式：10 个 query 参数。
新方式：`v=<base64(json)>`。

**兼容策略**：
```go
if data := query.Get("v"); data != "" {
    return c.parseByJson(data)      // 新的
}
return c.parseByQuery(query, ...)   // 老的
```

**同时支持两种，不破坏老客户端**。这是标准做法。

**例 2：`Options` 的"key 不存在返回 true"**

```go
func (o Options) Is(key string) bool {
    v, ok := o[key]
    if !ok || v {
        return true      // ← key 不存在时当作 true
    }
    return false
}
```

**为什么？** 老客户端根本不传 `options`（或只传部分 key）。如果"不存在 = false"，那么老客户端发的消息会**全部不落库、不推送**——直接瘫痪。

**所以设计成"不存在 = 开"**，新功能默认开启，只有显式传 `false` 才关闭。

⚠️ **代价**：新客户端如果想"默认关闭"某个新开关，必须显式传 `false`，不能靠"不传"。

📌 **这是一个非常典型的"后向兼容压倒优雅"的决策**。第一次读会觉得很反直觉，理解原因后会觉得合理。

**例 3：内容类型用 JSON 字符串而不是结构化**

```go
Content string   // 里面是 JSON：{"content":"你好"}
```

**为什么不用 protobuf 的结构化字段？**

因为消息类型有 11+ 种，每种结构不同（文本有 text，图片有 url/width/height，引用有 quoteMessage）。如果用 `oneof`：

```protobuf
oneof content {
    TextContent text = 10;
    PictureContent picture = 11;
    ...
}
```

**每加一种类型都要改 .proto、重新编译、所有客户端升级 SDK**——太重了。

**用 JSON 字符串**：服务端只当字符串存（**不解析**），加新类型只需客户端约定，**服务端零改动**。

**代价**：
- 服务端无法校验内容合法性（存什么是什么）；
- 无法在服务端做内容搜索（只能正则）；
- 多了 JSON 解析开销（在客户端）。

📌 **这是一个"扩展性 vs 服务端管控力"的取舍**。做 IM 经常会遇到：**消息类型要快速迭代，服务端不想频繁发版** → 把内容当不透明字符串。

## 7.11 理论部分小结

```
数据要在网上跑 → 必须序列化（按约定重新编排，不能 memcpy）
    ↓
文本格式（JSON）：可读、通用、但大且慢；int64 会丢精度
二进制格式（protobuf）：字段号 + varint + TLV，小且快，但需 schema
Go 专用（Gob）：自描述、流式、只有 Go 能解 ← 默认走这个，所以有坑 4
    ↓
二进制要塞进文本字段 → base64（膨胀 33%，URL 里要用 URL-safe 变体）
    ↓
大消息才值得 gzip（小消息压缩反而变大）
    ↓
协议套两层信封：外层管路由/元数据（JSON），内层管业务（protobuf）
    ↓
三个 ID 分工：ClientMsgID 幂等、ServerMsgID 唯一引用、Seq 排序同步
    ↓
协议演进靠"只加不改"+ 字段号不复用 + 默认值语义
```

# 第二部分 源码：OpenIM 的协议实现

## 7.12 协议栈全景：六层，从字节到结构体

```
┌──────────────────────────────────────────────┐
│ ⑥ sdkws.MsgData / GetMaxSeqReq ...           │  protobuf 消息体（业务）
├──────────────────────────────────────────────┤
│ ⑤ data = base64( protobuf )                  │  载荷编码
├──────────────────────────────────────────────┤
│ ④ Req { reqIdentifier, token, sendID, ... }  │  信封（Gob 或 JSON）
├──────────────────────────────────────────────┤
│ ③ gzip（可选）                                │  压缩
├──────────────────────────────────────────────┤
│ ② WebSocket binary 帧（opcode=0x2）           │  传输帧
├──────────────────────────────────────────────┤
│ ① TCP                                        │  字节流
└──────────────────────────────────────────────┘
```

**对照理论 7.7**：④ 是信封，⑤⑥ 是载荷，中间隔了一个 base64。

**发送方向**：⑥ → ⑤ → ④ → ③ → ② → ①
**接收方向**：① → ② → ③ → ④ → ⑤ → ⑥

⚠️ **任何一层顺序错都会失败**，而且错误信息往往指向别的层。这是排查困难的根源。

## 7.13 `Req`：请求信封

```go
// internal/msggateway/message_handler.go:29-36
type Req struct {
    ReqIdentifier int32  `json:"reqIdentifier" validate:"required"`
    Token         string `json:"token"`
    SendID        string `json:"sendID"        validate:"required"`
    OperationID   string `json:"operationID"   validate:"required"`
    MsgIncr       string `json:"msgIncr"       validate:"required"`
    Data          []byte `json:"data"`
}
```

### 逐字段的作用与"为什么需要"

| 字段 | 类型 | 作用 | 对应理论 | 缺了会怎样 |
|---|---|---|---|---|
| `ReqIdentifier` | int32 | **路由键**，决定走哪个分支 | 7.9 | 服务端不知道该怎么处理 |
| `Token` | string | 凭据（冗余，握手时已验） | 7.7 | 无法检测 token 中途过期 |
| `SendID` | string | 声称的发送者 | 7.7 | 无法做防伪造校验 |
| `OperationID` | string | 链路追踪 ID | 7.7 | 日志无法串联一次请求 |
| `MsgIncr` | string | 客户端自增序号，**用于请求-响应配对** | 7.7 | 异步响应无法对应请求 |
| `Data` | `[]byte` | 业务载荷（base64 后的 protobuf） | 7.3 | — |

### 为什么 `MsgIncr` 是必需的（HTTP 不需要）

**HTTP 里不需要"请求序号"**，因为 HTTP/1.1 是"一问一答"：你发一个请求，收到的下一个响应就是它的。

**WebSocket 是全双工多路复用**：

```
客户端 → 请求A(发消息)
客户端 → 请求B(拉历史)
服务端 ← 推送C(别人发来的消息)     ← 插在中间
服务端 ← 响应A
服务端 ← 响应B
```

**响应可能乱序、中间夹着推送**。客户端怎么知道"这个响应是 A 的还是 B 的"？

**靠 `MsgIncr`**：服务端在响应里原样回传，客户端用它匹配。

```go
// Resp 里也有 MsgIncr
type Resp struct {
    ...
    MsgIncr string `json:"msgIncr"`   // 原样回传
}
```

📌 **这是全双工协议必须的设计**。类比：TCP 用序列号保证可靠传输，WS 业务层用 MsgIncr 保证请求响应配对。

### `Data []byte` 与 base64 的隐式转换

```go
Data []byte `json:"data"`
```

**关键点：Go 的 `encoding/json` 对 `[]byte` 自动做 base64 编码。**

```go
type Req struct{ Data []byte }
b, _ := json.Marshal(Req{Data: []byte{0x0A, 0x06}})
// → {"Data":"CgY="}      ← 自动 base64！注意 '=' 填充
```

**为什么用 `[]byte` 而不是 `string` 或 `any`？**

| 类型 | 结果 | 问题 |
|---|---|---|
| `[]byte` | 自动 base64 | ✅ 正确，二进制安全 |
| `string` | 原样输出 | ❌ 二进制会被当 UTF-8，非法序列被替换成 � |
| `any` | 展开成 JSON 对象 | ❌ protobuf 无法对应 JSON 结构，且失去紧凑性 |

**所以 `[]byte` 是唯一正确的选择**，Go 标准库帮你把 base64 这层封装掉了。

⚠️ **但注意**：这是**标准 base64（带 `=`）**，不是 URL-safe。因为它在 JSON body 里，不在 URL 里。**两种 base64 用在不同位置**，别搞混（理论 7.3.3）。

## 7.14 `reqIdentifier` 枚举

```go
// internal/msggateway/constant.go:29-44
const (
    WSGetNewestSeq        = 1001
    WSPullMsgBySeqList    = 1002
    WSSendMsg             = 1003
    WSSendSignalMsg       = 1004
    WSPullMsg             = 1005
    WSGetConvMaxReadSeq   = 1006
    WsPullConvLastMessage = 1007
    WSPushMsg             = 2001
    WSKickOnlineMsg       = 2002
    WsLogoutMsg           = 2003
    WsSetBackgroundStatus = 2004
    WsSubUserOnlineStatus = 2005
    WSDataError           = 3001
)
```

| 值 | 常量 | 方向 | 作用 | 对应业务 |
|---|---|---|---|---|
| 1001 | `WSGetNewestSeq` | C→S | 拉会话最大 seq | 打开 App 时同步 |
| 1002 | `WSPullMsgBySeqList` | C→S | 按 seq 列表批量拉 | 补洞（漏了特定几条） |
| 1003 | `WSSendMsg` | C→S | **发消息** | 核心 |
| 1004 | `WSSendSignalMsg` | C→S | 发信令消息 | 音视频通话信令 |
| 1005 | `WSPullMsg` | C→S | 按 seq 范围拉 | 断线重连补消息 |
| 1006 | `WSGetConvMaxReadSeq` | C→S | 拉会话已读/最大 seq | 红点、已读 |
| 1007 | `WsPullConvLastMessage` | C→S | 拉会话最后一条 | 会话列表预览 |
| **2001** | `WSPushMsg` | **S→C** | **服务端推送消息** | 收消息 |
| 2002 | `WSKickOnlineMsg` | S→C | 踢下线通知 | 多端互踢 |
| 2003 | `WsLogoutMsg` | C→S | 登出 | 主动退出 |
| 2004 | `WsSetBackgroundStatus` | C→S | 设置前后台状态 | 影响推送策略 |
| 2005 | `WsSubUserOnlineStatus` | C→S | 订阅他人在线状态 | "对方正在输入" |
| 3001 | `WSDataError` | S→C | 数据错误 | 兜底 |

### 三个观察

**① 1xxx 是"拉"，2xxx 里只有 2001 是"推"**

注意 1001/1002/1005/1006/1007 全是**同步类请求**（客户端要补齐数据），真正"服务器主动推"的只有 2001。其余 2xxx 是**控制类**（踢人、状态）。

**这说明协议设计是有分类逻辑的**，不是随便编号。

**② 1007 的命名不一致**

其他都是 `WS` 前缀（`WSGetNewestSeq`），只有 1007 是 `Ws`（小写 s）。这是**命名风格的瑕疵**，不影响功能，但说明项目有历史遗留。

📌 读源码时看到这种不一致，**不要以为是你看错了**——真实项目就是这样，规范是逐步收敛的。

**③ 2005 是"订阅"模式，不是"查询"**

`WsSubUserOnlineStatus` 不是"查一次在线状态"，而是"**订阅**，之后状态变化主动通知我"。

这是**观察者模式**在协议层的体现：
```
客户端：我订阅 user002、user003
服务端：（记入 subUserIDs）
        user002 上线 → 主动推 2005 通知
        user003 下线 → 主动推 2005 通知
```

**为什么用订阅而不是轮询？** 因为"正在输入"这种状态变化频繁，轮询会造成大量无效请求（理论 6.2.1 的翻版）。

## 7.15 `Resp`：统一响应信封

```go
// message_handler.go:69-76
type Resp struct {
    ReqIdentifier int32  `json:"reqIdentifier"`
    MsgIncr       string `json:"msgIncr"`
    OperationID   string `json:"operationID"`
    ErrCode       int    `json:"errCode"`
    ErrMsg        string `json:"errMsg"`
    Data          []byte `json:"data"`
}
```

### 与 `Req` 的对称性

| 字段 | Req | Resp | 说明 |
|---|---|---|---|
| `ReqIdentifier` | ✅ | ✅ | 原样回传，客户端知道这是哪个请求的响应 |
| `MsgIncr` | ✅ | ✅ | **原样回传**，用于配对（7.13） |
| `OperationID` | ✅ | ✅ | 原样回传，用于日志串联 |
| `Token` | ✅ | ❌ | 响应不需要带凭据 |
| `SendID` | ✅ | ❌ | 响应不需要 |
| `ErrCode` / `ErrMsg` | ❌ | ✅ | 错误信息 |
| `Data` | ✅ | ✅ | 载荷 |

### 为什么错误不放在 HTTP 状态码里

**因为 WebSocket 没有状态码。** 协议升级后就没有 HTTP 语义了，所有错误必须**放在应用层字段里**。

所以：
```go
ErrCode int    // 0 = 成功，非 0 = 错误码
ErrMsg  string // 人类可读的错误信息
```

**这是 WS 协议设计的基本常识**：一旦升级，HTTP 那套状态码/Header 全部失效，你得自己造一套。

⚠️ **易错**：很多人以为"连接建立成功 = 请求成功"。**错**。连接成功只代表鉴权通过，业务请求可能因为任何原因失败（权限不足、参数错误、对方不存在），全都靠 `ErrCode` 表达。

### `ErrCode` 的取值从哪来

不是随便定义的，来自 `pkg/common/servererrs`：

```go
servererrs.ErrConnOverMaxNumLimit   // 连接数超限
servererrs.ErrTokenNotValid         // token 无效
servererrs.ErrIOSBackgroundPushErr  // iOS 后台推送失败
```

每个错误码有：
- 数字码（客户端判断用）；
- 默认消息（人类可读）；
- 可以 `WrapMsg` 附加细节。

📌 第 08 篇会讲 `errs` 包的错误包装机制。

## 7.16 `MsgData`：业务载荷的核心

`MsgData` **不在本仓库**，它定义在 `github.com/openimsdk/protocol/sdkws`（一个独立的 proto 模块）。所以你在源码里搜不到它的定义，只能看到使用。

### 字段分组

| 分组 | 字段 | 说明 | 对应理论 |
|---|---|---|---|
| **标识** | `ClientMsgID` | 客户端生成，幂等去重键 | 7.8.1 |
| | `ServerMsgID` | 服务端生成，全局唯一 | 7.8.2 |
| | `Seq` | **服务端分配的会话内序号** | 7.8.3 |
| **归属** | `SendID` / `RecvID` / `GroupID` | 发送者/接收者/群 | — |
| | `SessionType` | 1=单聊 2=写群 3=读群 4=通知 | — |
| **内容** | `ContentType` | 内容类型枚举 | 7.17 |
| | `Content` | **JSON 字符串**（不是二进制） | 7.10.2 例 3 |
| **元信息** | `SendTime` | 服务端补的毫秒时间戳 | — |
| | `SenderNickname` / `SenderFaceURL` | 冗余存储 | 见下 |
| | `AtUserIDList` | @ 了谁 | — |
| | `OfflinePushInfo` | 离线推送标题/内容 | — |
| | `Options` | 11 个开关的 map | 7.18 |
| | `Ex` | 业务扩展字段 | — |

### 三个值得深挖的设计

**① `SendTime` 是服务端补的，不是客户端传的**

**为什么？** 因为**客户端时钟不可信**：
- 用户可以手动改系统时间；
- 不同设备时钟有偏差（几秒到几分钟）。

如果按客户端时间排序，会出现"我 10:00 发的消息显示在你 09:58 的消息前面"。

**服务端统一打时间戳**，保证排序基准一致。

⚠️ 但即使这样，**时间戳仍然不能用来排序消息**——同一毫秒可能有多条。**排序只认 seq**（理论 7.8.3）。

**② `SenderNickname` / `SenderFaceURL` 是冗余的**

规范化设计（数据库三大范式）会说"昵称只存用户表，消息表存 userID 就行"。**为什么这里反着做？**

| 理由 | 说明 |
|---|---|
| **性能** | 拉 50 条消息要显示发送者昵称。如果只存 userID，就要么 JOIN，要么再查一次用户服务 → **N+1 查询** |
| **语义** | 要展示"**当时的**昵称"。用户改名后，历史消息应该显示旧昵称还是新昵称？多数产品选择保留历史原貌 |
| **可用性** | 用户服务挂了，历史消息仍然能正常展示 |

📌 **这是"读多写少"场景的经典反规范化（denormalization）**。IM 的消息是"写一次、读无数次"，所以冗余换取读性能是划算的。

⚠️ **产品语义要明确**：本项目选择"历史消息保留发送时的昵称"。这不是 bug，是设计。

**③ `Content` 是 JSON 字符串**

```json
{"content": "{\"content\":\"你好\"}"}
```

外层是 protobuf 的 `content` 字段（string），里面又嵌套了一层 JSON 字符串。

**为什么？（理论 7.10.2 例 3）**

- 11+ 种消息类型，结构完全不同；
- 用 `oneof` 要频繁改 proto、所有客户端升级 SDK；
- 用字符串 → **服务端完全不解析内容**，只当不透明载荷存。

**代价（必须知道）**：
- 服务端无法校验内容合法性（客户端传垃圾也照存）；
- 无法在服务端做内容检索（除非正则）；
- 客户端要双重解析（先解 protobuf，再解 JSON）。

**收益**：新增消息类型**服务端零改动**。

📌 **这是"服务端做薄、客户端做厚"的取舍**。OpenIM 作为通用 IM 基础设施，不可能预知所有业务消息类型，所以这个选择是合理的。

## 7.17 内容类型：11 种消息，服务端只认几个

### 常量在哪

内容类型常量定义在外部模块 `github.com/openimsdk/protocol/constant`，本仓库只引用常量名（如 `constant.Text`、`constant.Picture`）。

**常见类型**（数值以依赖版本为准，本仓库不定义这些数字，所以不在手册里写死数字）：

| 常量名 | 语义 | 服务端是否特殊处理 |
|---|---|---|
| `Text` | 文本 | 否 |
| `Picture` | 图片 | 否（只存 URL） |
| `Voice` | 语音 | 否 |
| `Video` | 视频 | 否 |
| `File` | 文件 | 否 |
| `AtText` | @ 消息 | 解析 `AtUserIDList` |
| `MergeText` | 合并转发 | 否 |
| `Card` | 名片 | 否 |
| `Location` | 位置 | 否 |
| `Custom` | 自定义 | 否 |
| `Revoke` | **撤回** | ✅ 特殊 |
| `Typing` | **正在输入** | ✅ 特殊 |
| `Quote` | 引用 | ✅ 特殊（要处理被引用消息已撤回） |
| `HasReadReceipt` | **已读回执** | ✅ 特殊 |

📌 **注意**：这张表说明一个关键事实——**服务端对大部分消息类型是"透明"的**，只处理 4 类有特殊语义的。这就是"Content 当字符串"的直接后果，也是"通用 IM"的必然设计。

### 服务端真正处理的 4 类

**① Revoke（撤回）**

撤回不是"删掉消息"，而是"发一条撤回通知，并把原消息标记为已撤回"。

为什么要发一条**新消息**？因为：
- 接收方可能已经收到了原消息，你必须通知他"那条撤了"；
- 撤回本身也要占一个 seq（保证各端都能同步到这个事件）。

**② Typing（正在输入）**

**不落库、不占 seq、不推送离线**。只在双方都在线时实时转发。

为什么？因为"正在输入"是**瞬时状态**，1 秒后就过期了。存下来毫无意义，还会污染历史记录。

**③ Quote（引用）**

引用消息里包含被引用消息的 ID 和摘要。但被引用消息**可能已被撤回**——这时要显示"该消息已撤回"，而不是显示原文。

这属于**读时处理**（第 13 篇会讲 `handlerDeleteAndRevoked`）。

**④ HasReadReceipt（已读回执）**

"我读到了 seq=100"。这类消息**不产生未读、不更新会话**，只同步已读位置。

### 自动开关：`encapsulateMsgData`

源码：`internal/rpc/msg/verify.go:134-154`

```go
func (m *MsgServer) encapsulateMsgData(msg *sdkws.MsgData) {
    // 根据 contentType 自动修正 options
    switch msg.ContentType {
    case constant.Revoke:
        msg.Options[...] = false    // 关未读、关离线推送
    case constant.HasReadReceipt:
        msg.Options[...] = false    // 关会话更新、关未读、关推送
    case constant.Typing:
        msg.Options[...] = false    // 关历史、关持久化、关同步、关会话更新、关未读、关推送
    }
    ...
}
```

**为什么要在服务端强制修正，而不是信任客户端传的 options？**

**安全考虑**：如果信任客户端，恶意用户可以发一条 `ContentType=Typing` 但 `IsPersistent=true` 的消息——绕过"不落库"的设计，造成存储污染。

**服务端必须做"语义一致性"校验**：类型和开关必须匹配，不匹配就按类型强制覆盖。

📌 **这是"永远不要相信客户端"的又一例证**（和 06 篇的 `SendID` 校验同源）。

⚠️ **最常见的误解**：以为"所有消息都有 seq"。**Typing 没有**——因为它不落库，不参与 seq 分配。第 11 篇会看到它被分到 `notStorageMsgList`。

## 7.18 `Options`：11 个开关的设计

```go
// pkg/msgprocessor/options.go:10-28
const (
    IsNotNotification          = "isNotNotification"
    IsSendMsg                  = "isSendMsg"
    IsHistory                  = "isHistory"
    IsPersistent               = "isPersistent"
    IsOfflinePush              = "isOfflinePush"
    IsUnreadCount              = "isUnreadCount"
    IsConversationUpdate       = "isConversationUpdate"
    IsSenderSync               = "isSenderSync"
    IsNotPrivate               = "isNotPrivate"
    IsSenderConversationUpdate = "isSenderConversationUpdate"
    IsReactionFromCache        = "isReactionFromCache"
)
```

### 为什么用 map 而不是位图

| 方案 | 体积 | 可读性 | 扩展性 |
|---|---|---|---|
| 位图（bitmap） | 2 字节固定 | ❌ 要查表 | ❌ 加一位要改所有端 |
| **map[string]bool** | 几十字节 | ✅ 键名自解释 | ✅ 加 key 不影响老端 |

**IM 的消息量虽然大，但每条消息几十字节的 options 相比 content 可忽略**。用可读性换这点体积是值的。

📌 **这是"可调试性优先"的又一例**（和用 JSON 信封同源）。

### `Is()` 的反直觉语义

```go
// options.go:109-115
func (o Options) Is(notification string) bool {
    v, ok := o[notification]
    if !ok || v {
        return true          // ⚠️ key 不存在时返回 true
    }
    return false
}
```

**key 不存在 → 返回 true**（理论 7.10.2 例 2）。

**为什么？** 老客户端不传 options，如果"不存在 = false"，那么：
- `IsHistory=false` → 消息不落库 → **聊天记录全丢**；
- `IsSendMsg=false` → 消息不发送 → **功能瘫痪**。

**所以必须"默认开"**。

⚠️ **推论（容易踩）**：新客户端想关闭某个开关，**必须显式传 `false`**。传空 map 等于"全开"，不是"全关"。

**这是个"反直觉但正确"的设计**，读代码时如果不理解，会写出完全错误的行为。

### 默认值

```go
// options.go（NewOptions）
func NewOptions() Options {
    return Options{
        IsSenderSync: true,     // ← 只有这一个默认 true
    }
}
```

**为什么只有 `IsSenderSync` 默认开？**

因为"发送方多端同步"是几乎必然的需求：你在手机上发的消息，PC 上也要看到。其他开关由具体业务逻辑按需设置。

## 7.19 双编码器：Gob vs JSON 的实现

```go
// client.go:88-92
if c.SDKType == GoSDK {
    c.Encoder = NewGobEncoder()
} else {
    c.Encoder = NewJsonEncoder()
}
```

### Gob 实现

```go
// encoder.go:16-38（简化）
type GobEncoder struct {
    enc *gob.Encoder
    dec *gob.Decoder
    buf bytes.Buffer
}

func (e *GobEncoder) Encode(v any) ([]byte, error) {
    e.buf.Reset()
    if err := e.enc.Encode(v); err != nil {
        return nil, err
    }
    return e.buf.Bytes(), nil
}
```

⚠️ **注意 `e.buf` 是共享状态**：这个 Encoder 是**有状态的**，`Encode` 里先 `Reset` 再写。

**如果两个 goroutine 同时调 `Encode`**：
```
goroutine A: buf.Reset()
goroutine B: buf.Reset()        ← A 刚写的内容被清掉
goroutine A: enc.Encode(a)
goroutine B: enc.Encode(b)      ← 两个对象写进同一个 buf
→ 返回的字节是两条消息混在一起
```

**这就是理论 7.5.4 说的并发陷阱**。而 `writeBinaryMsg` 把 `Encode` 放在锁**外**（06 篇 6.13.4），所以：

📌 **真实风险**：如果一条连接同时收到"响应"和"推送"，两个 goroutine 并发 `Encode`，**Gob 编码器可能产出损坏的数据**。

**这是一个值得写进简历的"我发现的问题"**，但要注意措辞——需要先确认是否真的有多 goroutine 并发写同一连接的场景（📌 待验证）。从 `PushMessage` 和 `replyMessage` 都调 `writeBinaryMsg` 来看，**场景是存在的**。

### JSON 实现

```go
// encoder.go:40-60（简化）
type JsonEncoder struct{}

func (e *JsonEncoder) Encode(v any) ([]byte, error) {
    return json.Marshal(v)
}

func (e *JsonEncoder) Decode(data []byte, v any) error {
    return json.Unmarshal(data, v)
}
```

**无状态**，线程安全。这是 JSON 相比 Gob 的一个隐性优势。

### 为什么默认 Gob（复习理论 7.5.3）

| 维度 | Gob | JSON |
|---|---|---|
| 体积 | 小（自描述，后续只发值） | 大（每条都带字段名） |
| 速度 | 快 | 慢 |
| 跨语言 | ❌ | ✅ |
| 线程安全 | ❌（有状态） | ✅ |
| 可调试 | ❌ | ✅ |

**主力客户端是 Go** → 默认 Gob 合理。**但代价是"非 Go 客户端必须显式声明"**，这就是坑 4。

📌 **如果让我改**：我会把默认值改成 `js`（安全优先），让 Go SDK 显式传 `sdkType=go`。这样"忘记传"的后果是"能用但慢一点"，而不是"直接连不上"。**这是"默认值应该选安全的那个"原则**。

## 7.20 压缩的实现

```go

}
```

```go
// client.go:131-137（读方向）

}
```

### 对象池复用

```go
// compressor.go（简化）
var gzipWriterPool = sync.Pool{
    New: func() any {
        return gzip.NewWriter(io.Discard)
    },
}

func CompressWithPool(data []byte) ([]byte, error) {
    w := gzipWriterPool.Get().(*gzip.Writer)
    defer gzipWriterPool.Put(w)
    w.Reset(&buf)          // ← 复用前重置
    w.Write(data)
    w.Close()
    return buf.Bytes(), nil
}
```

**为什么要池化 gzip.Writer？**

`gzip.NewWriter` 内部会分配**约 300KB 的哈希表**（用于 LZ77 匹配）。如果每条消息都新建，GC 会被打爆。

**`sync.Pool` 在这里的收益极大**——这是 Go 高性能服务的标准手法。

⚠️ **注意 `w.Reset(&buf)`**：复用的 Writer 必须重置输出目标，否则会写到上一次的 buffer 里。**忘记 Reset 是对象池最常见的 bug**。

### 压缩的触发条件

```go
// context.go:123-125
if compression := query.Get(Compression); compression == GzipCompressionProtocol {
    c.compression = compression
}
```

**由客户端在握手 URL 里声明**（`compression=gzip`）。

按理论 7.6.2 的分析，这应该是**客户端根据消息大小动态决定**的——小消息压了反而更大。但握手时只能声明"是否支持"，没法按消息动态开关。

📌 **这是一个设计上的粗粒度**：要么全程压，要么全程不压。更好的做法是"超过阈值才压"，但那需要协议里带标志位。

## 7.21 四个坑的完整对照

现在用协议栈（7.12）来解释四个坑，**这是本篇最实用的一张表**：

| # | 现象 | 出错在哪一层 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | `ParseBool "" invalid syntax` | **① 握手层**（还不是 WS） | `isBackground` 空值被送去 ParseBool | URL 显式带 `isBackground=false` |
| 2 | `not support text message type` | **② 帧层** | 读循环只接受 binary（opcode=0x2） | 用 binary 帧发送 |
| 3 | 解码失败 / 字段全空 | **⑤ 载荷层** | `data` 必须是 base64(protobuf)，传了明文 JSON | 用 proto.Marshal + base64 |
| 4 | Gob 解码乱码 | **④ 信封层** | 默认 `sdkType=go` → 走 Gob | URL 带 `sdkType=js` |

**为什么这四个坑难排查？**

因为**错误信息指向的层，往往不是真正出错的层**：
- 坑 3 你以为是"数据格式不对"，实际是"少了一层编码"；
- 坑 4 你以为是"服务端 bug"，实际是自己没声明 SDK 类型。

📌 **排查方法论**：**从外到内逐层验证**。

```
① 握手能成功吗？（curl 看 101）
② 帧类型对吗？（binary）
③ 解压对吗？（如果开了 compression）
④ 信封能解吗？（reqIdentifier 能读出来吗）
⑤ 载荷能解吗？（protobuf 能 Unmarshal 吗）
```

**每一层都有独立的验证方法**，不要跳层猜。

import (
    "encoding/base64"
    "google.golang.org/protobuf/proto"
    "github.com/openimsdk/protocol/sdkws"
    "github.com/openimsdk/protocol/constant"
)

// ① 组装业务载荷
msg := &sdkws.MsgData{
    SendID:      "user001",
    RecvID:      "user002",
    SessionType: constant.SingleChatType,
    ContentType: constant.Text,
    Content:     `{"content":"你好"}`,
    ClientMsgID: "client-xxx",
}

// ② protobuf 序列化
payload, _ := proto.Marshal(msg)

// ③ base64 编码
dataStr := base64.StdEncoding.EncodeToString(payload)

// ④ 组装信封
req := map[string]any{
    "reqIdentifier": 1003,
    "token":         token,
    "sendID":        "user001",
    "operationID":   "op-abc",
    "msgIncr":       "1",
    "data":          dataStr,
}
body, _ := json.Marshal(req)

// ⑤ 写 binary 帧
conn.WriteMessage(websocket.BinaryMessage, body)
```

⚠️ **注意第 ③ 步用的是 `base64.StdEncoding`**（因为 JSON 里的 `[]byte` 用的是标准 base64，不是 URL-safe）。**这里最容易用错变体**。

import base64, json

obj = json.loads(raw)               # 外层信封
print("指令码:", obj["reqIdentifier"], "→", "推送" if obj["reqIdentifier"]==2001 else "响应")

payload = base64.b64decode(obj["data"])
print("protobuf 长度:", len(payload))
print("前 32 字节(hex):", payload[:32].hex())
```

**预期**：能读出 `reqIdentifier: 2001`，`data` 是一段 protobuf 字节。

**这验证了理论 7.7：外层可读、内层不可读。**

# 第五部分 面试话术

## 30 秒版

> "WS 上是**双层编码**：外层是统一信封 `Req/Resp`，负责路由（`reqIdentifier`）、元数据（token、operationID、msgIncr）和错误码；内层是 protobuf 业务载荷，base64 后放进 `data` 字段。
>
> 外层编码器有两套：Go SDK 走 Gob 追求性能和紧凑，其他语言走 JSON 保证通用，用 `sdkType` 参数切换——不传默认是 go，所以非 Go 客户端必须显式声明，否则会 Gob 解码失败。"

## 3 分钟版

> "这个协议设计里有三个我认为很有含金量的点。
>
> **第一是三个 ID 的分工。** ClientMsgID 是客户端生成的幂等键，解决网络超时重试导致的重复消息；ServerMsgID 是服务端生成的全局唯一标识，用于撤回和引用；Seq 是会话内单调递增的序号，负责排序和增量同步。断线重连时客户端只需要上报本地 maxSeq，服务端返回之后的消息——这个模型比按时间戳拉取可靠得多，因为时间戳会重复、会受客户端时钟影响。
>
> **第二是 Content 用 JSON 字符串而不是结构化字段。** 消息类型有十几种，结构完全不同。如果用 protobuf 的 oneof，每加一种类型都要改 proto、重新编译、所有客户端升级 SDK。用字符串的话服务端完全不解析内容，只当不透明载荷存，新增消息类型服务端零改动。代价是服务端无法校验内容合法性、无法做内容检索——这是'服务端做薄'的取舍。
>
> **第三是后向兼容的设计。** options 是个 map，而且 key 不存在时返回 true。因为老客户端不传 options，如果按 false 处理，消息就会不落库、不推送，功能直接瘫痪。所以设计成默认全开，只有显式传 false 才关闭。这个设计很反直觉，但体现了协议演进时'默认值必须选安全的那个'。"

## 追问预判

| 可能被问 | 怎么答 |
|---|---|
| "为什么不全程用 protobuf？" | 外层留 JSON 是为了可调试性——抓包直接能看到 reqIdentifier。全二进制必须用专用工具解。 |
| "base64 不是浪费 33% 带宽吗？" | 是。但外层信封本身很小，载荷才是大头。如果载荷也 base64 就亏了——所以只在 JSON 信封里这样做。 |
| "Gob 有什么问题？" | 只有 Go 能解，而且 Encoder 有状态、非线程安全。项目的 writeBinaryMsg 把 Encode 放在写锁外，多 goroutine 并发写同一连接时可能损坏数据。 |
| "怎么保证消息不重复？" | ClientMsgID 幂等，服务端落库时按它去重。注意重试必须复用同一个 ID。 |
| "消息顺序怎么保证？" | 排序只认 seq。SendTime 只是展示用的，同毫秒多条会乱序。 |
| "怎么加一种新消息类型？" | 客户端约定新的 contentType 和 content 结构，服务端零改动（因为不解析 content）。但如果需要服务端特殊处理（比如撤回），就要改 encapsulateMsgData 和落库逻辑。 |
