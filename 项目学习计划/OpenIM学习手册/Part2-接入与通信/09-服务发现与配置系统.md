# 09 服务发现与配置系统：地址会变，怎么找到它；配置会改，要不要重启

> **本篇定位**：前几篇默认了一件事——"我知道 user 服务在哪"。但实际上**服务的 IP 是会变的**（扩缩容、重启、迁移）。这一篇解决两个问题：
> 1. **服务发现**：调用方怎么动态找到服务实例？
> 2. **配置管理**：25 个配置文件怎么加载、怎么热更新、怎么在多环境下不混乱？
>
> **结构**：
> - **第一部分（9.1–9.7）纯理论**：为什么不能写死地址、三种发现模式、etcd 原理（Raft/KV/watch/lease）、健康检查、配置管理的演进、热更新、12-Factor。
> - **第二部分（9.8–9.15）源码**：22 个子配置、三种发现实现、注册与拿连接、standalone 反射注入。
> - **第三部分**：实验。
>
> **本篇名词**：服务发现（Service Discovery）、注册中心、etcd、Raft、KV、watch、revision、lease（租约）、TTL、心跳续约、健康检查、客户端发现、服务端发现、配置中心、热更新、12-Factor App、viper、struct tag、反射注入、standalone。

# 第一部分 理论：地址为什么会变

## 9.1 一个看似简单的问题：user 服务在哪

### 9.1.1 最朴素的做法：写死在配置里

```yaml
user_rpc: "10.0.0.1:20100"
```

**单机、单实例时完全够用。** 但一旦上生产，三个问题立刻出现：

**问题一：实例会重启，IP 会变**

```
今天：user 服务在 10.0.0.1
明天：容器/VM 重建后变成 10.0.0.7
→ 配置文件里的地址失效 → 全部调用失败
```

**容器环境更严重**：K8s 里 Pod 重建后 IP 一定变。

**问题二：要多实例，一个地址不够**

```
user 服务扩到 3 个实例：10.0.0.1, 10.0.0.2, 10.0.0.3
→ 调用方怎么知道有 3 个？怎么分配流量？
```

**问题三：实例会挂，要能摘除**

```
10.0.0.2 挂了，但配置文件里还有它
→ 1/3 的请求失败
→ 需要有人"把挂掉的实例从列表里去掉"
```

**这三个问题，就是"服务发现"要解决的。**

### 9.1.2 一个类比

**写死地址 = 记住朋友的手机号。**

朋友换号了怎么办？你得手动更新通讯录。有 100 个朋友呢？每次换号都要通知所有人。

**服务发现 = 查通讯录。**

你只知道"我要找张三"，具体号码去通讯录查。张三换号了，通讯录更新，你自动拿到新号。

**注册中心就是这本"通讯录"。**

## 9.2 服务发现的三种模式

### 9.2.1 模式一：静态配置（Static Config）

```
调用方配置：user = [10.0.0.1:20100, 10.0.0.2:20100]
```

**优点**：简单、无额外依赖、无网络开销。
**缺点**：**地址变化要人工改配置、重启服务**。

**适用**：小规模、地址稳定的场景（物理机、固定 IP）。**很多公司的"前三年"都是这么干的**，不必过度设计。

### 9.2.2 模式二：客户端发现（Client-side Discovery）

```
① 服务启动时，向注册中心注册自己：user = 10.0.0.1:20100
② 调用方从注册中心拉取地址列表
③ 调用方自己选一个（负载均衡在客户端做）
④ 注册中心推送变化（或调用方定时拉）
```

**代表**：Eureka + Ribbon、etcd + gRPC、Consul + 客户端 LB。

**优点**：
- 少一跳（不需要经过代理）；
- 客户端可以做智能负载均衡（感知延迟、就近路由）。

**缺点**：
- **每个语言都要实现一套客户端逻辑**（多语言支持成本高）；
- 客户端要维护地址列表和健康状态。

📌 **gRPC 用的是这个模式**（08 篇 8.8 的 Resolver + Balancer）。

### 9.2.3 模式三：服务端发现（Server-side Discovery）

```
① 服务注册到注册中心
② 调用方把请求发给一个"代理/网关"
③ 代理查注册中心，转发到具体实例
```

**代表**：K8s Service（kube-proxy）、Nginx + Consul Template、Istio。

**优点**：
- **客户端无感**（只访问一个固定地址）；
- 多语言零成本。

**缺点**：
- 多一跳（增加延迟）；
- 代理成为关键路径（要高可用）。

### 9.2.4 三种模式对比

| | 静态配置 | 客户端发现 | 服务端发现 |
|---|---|---|---|
| 地址变化 | 手工改+重启 | 自动 | 自动 |
| 多一跳 | 无 | 无 | **有** |
| 多语言成本 | 低 | **高** | 低 |
| 负载均衡 | 自己做 | 客户端做 | 代理做 |
| 典型 | 早期项目 | gRPC、Spring Cloud | K8s、Service Mesh |
| 本项目 | ✅ standalone | ✅ **etcd / k8s 模式** | ❌ |

📌 **本项目支持"客户端发现"（etcd、Kubernetes）和"进程内静态"（standalone）两种**，通过配置切换——这是下一部分要看的。

## 9.3 注册中心：etcd 是什么

### 9.3.1 注册中心要提供什么

一本"通讯录"至少要有四个能力：

| 能力 | 说明 |
|---|---|
| **写入** | 服务启动时登记自己 |
| **读取** | 调用方查列表 |
| **监听** | 列表变了要通知（不然只能轮询） |
| **自动过期** | 服务挂了，条目要自动消失（否则永远留着死地址） |

**第四点最关键**：如果服务是 `kill -9` 挂的，它没机会"主动注销"。**必须有机制让条目自己过期。**

### 9.3.2 etcd 的四个核心概念

etcd 是一个**分布式键值存储**，专为"服务发现/配置共享"设计。

**① KV（键值存储）**

```
/im/user-rpc-service/10.0.0.1:20100  →  {"addr":"10.0.0.1:20100"}
/im/user-rpc-service/10.0.0.2:20100  →  {...}
```

**用"目录 + 前缀"组织**，所以可以"列出某个前缀下的所有 key"——这就是"拉取服务实例列表"。

📌 本项目的 `rootDirectory: im` 就是这个前缀根（`config/discovery.yml`）。

**② Lease（租约）+ TTL（生存时间）**

```
① 服务注册时创建一个 lease，TTL = 5 秒
② 把 key 绑定到这个 lease 上
③ 服务每隔 2 秒"续约"一次（keepalive）
④ 如果服务挂了，不再续约
⑤ 5 秒后 lease 过期 → etcd 自动删除绑定的 key
```

**这就是"自动过期"的实现机制**。不需要服务主动注销，**挂了就自动消失**。

**为什么是"续约"而不是"服务主动发心跳更新 key"？**
- 续约更轻（lease 续期不需要改 key 的值）；
- 语义更清晰（"我还活着" vs "我更新一下数据"）。

**③ Watch（监听）**

```
客户端：watch /im/user-rpc-service/ 前缀
etcd：有变化我推给你（新增/删除/更新）
```

**这是"推送"而不是"轮询"**——服务列表变化时，调用方**立刻**知道，不需要每秒拉一次。

**实现原理**：etcd 维护一个**全局递增的 revision**，客户端 watch 时带上"我看到的 revision"，etcd 把之后的所有事件推给它。**断线重连后能补齐中间的事件**，不丢。

📌 **这个"revision + 事件流"的设计，和 IM 的 seq 机制本质相同**（第 07 篇）——都是"用一个单调递增的数实现增量同步"。**优秀的分布式系统设计是相通的**。

**④ Raft（一致性协议）**

etcd 是**集群**部署的（通常 3 或 5 节点），用 Raft 保证**强一致**：

```
写请求 → Leader 接收 → 同步给 Follower → 多数派确认 → 提交
```

**为什么需要强一致？** 因为服务发现的数据**不能有分歧**：
- 如果节点 A 说 user 在 10.0.0.1，节点 B 说在 10.0.0.2 → 调用方会拿到错误地址。

**代价**：写性能受限于 Raft（一次写要多数派确认）。但服务发现的写频率极低（只在实例变化时写），**完全不是瓶颈**。

⚠️ **为什么不用 Redis 做注册中心？** 可以（很多人这么干），但：
- Redis 主从是**异步复制**，可能丢数据、可能读到旧值；
- Redis 没有原生的 lease + watch 组合（要用 key 过期 + pub/sub 拼）。

**etcd 是为这个场景专门设计的**，所以更合适。**但 Redis 更简单、团队更熟，很多公司还是用 Redis**——这是工程取舍。

## 9.4 健康检查：租约不够，还要探活

### 9.4.1 两种"死"法

| 死法 | 租约能发现吗 |
|---|---|
| 进程崩溃 / 被 kill | ✅ 停止续约 → 过期 |
| **进程活着但卡死**（死锁、GC 停顿、DB 连不上） | ❌ **还在续约，但处理不了请求** |

**第二种更危险**：注册中心认为它健康，流量继续打过去，全部超时。

### 9.4.2 三种探活方式

| 方式 | 原理 | 能发现"卡死"吗 |
|---|---|---|
| **进程级** | 看进程在不在 | ❌ |
| **端口级** | TCP 能不能连上 | ⚠️ 部分（能连上不代表能处理） |
| **业务级** | 调一个健康检查接口，看返回 | ✅ |

**K8s 的三种 probe 正对应这三层**：
- `livenessProbe`：活着吗？不活就重启；
- `readinessProbe`：能接流量吗？不能就从 Service 摘除；
- `startupProbe`：启动完了吗？没完别探活。

📌 **本项目没有内置业务级健康检查接口**（至少 API 层没有 `/health`）。**流量摘除靠 etcd 租约**——这能发现"进程死了"，但发现不了"进程卡死"。**这是一个可以提的改进点**：加一个 `/health` 检查 Mongo/Redis/Kafka 连通性，配合 readiness probe。

⚠️ 但要注意：**健康检查本身也可能拖垮服务**（每个 probe 都查一遍 DB）。所以通常只做"轻量检查"（连接池是否可用），不做"完整业务检查"。

### 9.4.3 优雅下线：一个容易忽略的问题

```
服务要重启
  → 直接 kill
  → 注册中心还没发现（租约没过期）
  → 调用方还在往这个实例打请求
  → 一批请求失败
```

**正确做法**：
```
① 先从注册中心注销（主动删除 key）
② 等待一段时间（让调用方的地址列表更新，通常几秒）
③ 停止接受新请求
④ 处理完存量请求（05 篇讲的 httpServer.Shutdown）
⑤ 退出
```

**这就是"优雅下线"（Graceful Shutdown）**。K8s 里对应 `preStop` hook。

📌 **本项目有没有做？** 从 `api.Start` 看有 `httpServer.Shutdown`（处理存量请求），但**没看到"先从 etcd 注销再等几秒"的逻辑**（📌 待验证）。如果没有，滚动发布时会有少量请求失败——**这是可以提的改进点**。

## 9.5 配置管理：从 `config.yaml` 到配置中心

### 9.5.1 配置的四种形态（演进史）

**阶段一：硬编码常量**

```go
const DBHost = "127.0.0.1"
```

❌ 改一个值要重新编译。

**阶段二：配置文件**

```yaml
mongo:
  address: [localhost:37017]
```

✅ 不用重编译。❌ 改配置要重启，且多环境要维护多份文件。

**阶段三：环境变量 + 配置合并**

```bash
export MONGO_ADDRESS=localhost:37017
```

✅ 适合容器化（12-Factor 推荐）。❌ 变量多了难管理。

**阶段四：配置中心**

```
Nacos / Apollo / etcd / Consul KV
```

✅ 集中管理、按环境隔离、**热更新**、版本回滚、权限控制。❌ 引入新依赖。

**本项目在阶段二和阶段四之间**：**文件为主 + etcd watch 支持热更新**（9.15 讲）。

### 9.5.2 12-Factor App 的配置原则

**第三条：把配置存在环境里（Config in the Environment）**

核心思想：**同一份代码，不同环境用不同配置，不靠改代码区分环境。**

```
❌ if env == "prod" { host = "prod.db" } else { host = "test.db" }
✅ 配置从外部注入，代码不知道自己在哪个环境
```

**为什么？**
- 代码只有一份，构建产物只有一份；
- 环境差异全在配置里，不会"测试环境能跑生产不能跑"；
- 敏感信息（密码）不进代码仓库。

⚠️ **本项目是"配置文件 + 环境变量覆盖"的混合模式**：`config/*.yml` 提供默认值，环境变量可覆盖。

### 9.5.3 配置分文件的三个理由

本项目有 **25 个 .yml**：

```
config/
├── config.yaml            总配置（引用其他文件）
├── discovery.yml          服务发现
├── mongodb.yml            Mongo
├── redis.yml              Redis
├── kafka.yml              Kafka
├── minio.yml              对象存储
├── log.yml                日志
├── openim-api.yml         API 服务
├── openim-msggateway.yml  网关
├── openim-msgtransfer.yml 消息中转
├── openim-push.yml        推送
├── openim-rpc-*.yml       各 RPC 服务
├── prometheus.yml         监控
├── alertmanager.yml       告警
└── ...
```

**为什么不分一个大文件？**

| 理由 | 说明 |
|---|---|
| **服务只需要自己的配置** | msg 服务不需要读 minio 配置 |
| **减少冲突** | 多人改不同文件，不容易 git 冲突 |
| **职责清晰** | 看文件名就知道是什么配置 |
| **可独立挂载** | K8s 里可以只挂载需要的 ConfigMap |

⚠️ **代价**：配置之间的引用关系不直观（`config.yaml` 里要列出所有子文件），漏了某个文件就加载失败。

### 9.5.4 配置加载的三个机制

**① viper：把 yaml 变成 struct**

```go
viper.SetConfigFile("config/openim-api.yml")
viper.ReadInConfig()
viper.Unmarshal(&cfg)      // ← 字段名 → yaml key 的映射
```

**映射靠 `yaml` tag**：

```go
type API struct {
    ListenIP string `yaml:"listenIP"`
    Ports    []int  `yaml:"ports"`
}
```

**注意大小写**：yaml 里是 `listenIP`，Go 字段是 `ListenIP`。**靠 tag 显式映射**，因为 viper 的默认规则（全小写）处理不了驼峰。

**② 环境变量覆盖**

```go
viper.AutomaticEnv()
viper.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))
```

这样 `MONGO_ADDRESS` 能覆盖 `mongo.address`。**容器化部署必备**。

**③ 默认值**

```go
viper.SetDefault("log.level", "info")
```

**优先级**：环境变量 > 配置文件 > 默认值。**这是标准层级**。

### 9.5.5 热更新：改了配置不重启

**问题**：`viper.Unmarshal(&cfg)` 把配置读进了**内存里的 struct**。文件改了，struct 不会自动变。

**要热更新，必须解决两个问题**：

**① 怎么知道文件改了？**
- 轮询文件 mtime；
- 用 fsnotify 监听文件系统事件；
- 从配置中心 watch。

**② 怎么让运行中的代码看到新值？**
这是难点。因为代码里到处是 `cfg.Mongo.Address`（值拷贝），不是指针。

**三种做法**：

| 做法 | 原理 | 问题 |
|---|---|---|
| **重启进程** | 最简单 | 有中断 |
| **原子替换指针** | `atomic.Pointer[Config]` 整体替换 | 需要所有代码用指针访问，且要处理"替换瞬间"的一致性 |
| **只热更新特定字段** | 某些配置单独维护 | 覆盖不全，逻辑复杂 |

⚠️ **本项目支持"监听配置文件变化"（`watchConfigNames` 参数），但具体能热更新到什么程度需要验证**（📌 待验证）。**从架构看，配置以值形式传给各服务，大概率只有部分配置（如日志级别）能真正热生效**。

📌 **这是个诚实的结论**：**"支持 watch" ≠ "所有配置都能热更新"**。很多项目的热更新只对少数字段有效，宣传时容易夸大。

## 9.6 standalone：一个"反微服务"的模式

### 9.6.1 什么是 standalone

**把 12 个服务跑在同一个进程里**，互相调用不走网络，直接调函数（或用进程内"假 RPC"）。

```
生产模式（微服务）：
  api + gateway + 7 个 rpc + transfer + push + cron
  = 12 个进程，通过 gRPC + etcd 通信

standalone 模式：
  1 个进程，12 个服务在里面
```

### 9.6.2 为什么需要它

| 场景 | 为什么 standalone 合适 |
|---|---|
| **本地开发** | 不用起 12 个进程、不用 etcd |
| **演示/Demo** | 一条命令启动全系统 |
| **小规模部署** | 省资源（12 个进程的基线内存可不小） |
| **调试** | 一个断点能跨服务（因为是同一进程） |

📌 **这是很务实的设计**：**微服务架构不该强迫所有人用微服务方式运行**。开发和演示用单体，生产用分布式，**同一份代码**。

### 9.6.3 它是怎么实现的

**核心问题**：代码里写的是 `client.GetUser(ctx, req)`，怎么让它"不走网络"？

**答案：替换服务发现实现。**

```
生产：discovery = etcd 实现 → GetConn 返回真的 gRPC 连接
standalone：discovery = inprocess 实现 → GetConn 返回进程内连接
```

**进程内连接**可能是一个直接调用本地实现的 stub，**序列化都省了**（或者仍序列化以保证行为一致）。

📌 **这叫"依赖注入 + 接口抽象"的胜利**：因为所有代码都依赖 `discovery.Conn` 接口，所以能无缝替换实现。**如果代码里写死了 `etcd.NewClient()`，就做不到。**

### 9.6.4 standalone 带来的配置注入难题

**问题**：12 个服务各有自己的 Config 结构，但 standalone 只有一个 `AllConfig`。**怎么把 AllConfig 拆成 12 份？**

**答案：反射。**

```go
// 伪代码
func inject(target any, all *AllConfig) {
    v := reflect.ValueOf(target).Elem()
    for i := 0; i < v.NumField(); i++ {
        field := v.Field(i)
        // 按字段类型，从 AllConfig 里找同类型的子配置
        if cfg := findSameType(all, field.Type()); cfg != nil {
            field.Set(reflect.ValueOf(cfg))
        }
    }
}
```

**这就是"反射注配置"**（第 04 篇提过，08 篇 8.16.4 也提过）。

**收益**：一份 AllConfig 能注入 12 个服务，不用写 12 个转换函数。

**代价**：
- **没有编译期检查**：字段类型不匹配就静默跳过；
- **难调试**：注入失败不会报错，只会表现为"某个配置是零值"。

📌 **这是本篇第三个"反射带来的隐式约定"**。**项目里反射用得不少，说明它倾向于"用运行时灵活性换代码量"**——这是可以评价的架构倾向。

## 9.7 理论部分小结

```
服务 IP 会变 → 不能写死 → 需要服务发现
    ↓
三种模式：静态配置（简单）/ 客户端发现（gRPC 用）/ 服务端发现（K8s 用）
    ↓
注册中心需要四个能力：写、读、watch、自动过期
    ↓ etcd 用 lease+TTL 实现自动过期，用 revision+watch 实现推送
etcd 用 Raft 保证强一致（服务列表不能有分歧）
    ↓
租约只能发现"进程死了"，发现不了"进程卡死" → 还需要健康检查
    ↓ 以及优雅下线：先注销、等几秒、再停止服务
配置演进：硬编码 → 文件 → 环境变量 → 配置中心
    ↓ 12-Factor：代码只有一份，环境差异全在配置
分文件（25 个 yml）的好处是职责清晰，代价是引用关系不直观
    ↓
viper 靠 yaml tag 把配置映射到 struct；优先级：环境变量 > 文件 > 默认值
热更新难在"怎么让运行中的代码看到新值"，不是"怎么发现文件改了"
    ↓
standalone 用 inprocess 替换 etcd 实现，实现单体运行
    ↓ 靠接口抽象 + 反射注入 Config
```

**第二部分开始，看这套东西在代码里的样子。**

## 9.9 配置加载流程

```
① 读 config/config.yaml（主配置）
   ↓ 里面列出了所有子配置文件
② 依次读每个 .yml，Unmarshal 到对应字段
   ↓
③ 环境变量覆盖（如果有）
   ↓
④ 得到完整的 AllConfig
   ↓
⑤ 分发给各服务：
   - 独立进程模式：每个服务只取自己需要的子配置
   - standalone 模式：反射注入
```

### `config.yaml` 的角色

它本身不是"配置值"，而是**配置清单**：

```yaml
# 大致形态
discovery: config/discovery.yml
mongodb: config/mongodb.yml
redis: config/redis.yml
...
```

**为什么用"清单 + 子文件"而不是一个大文件？**
理由在理论 9.5.3 讲过：职责清晰、减少冲突、可独立挂载。

### 一个容易踩的坑：相对路径

```
如果从 /d/IM-Server 启动，配置路径要写 open-im-server-main/config/
如果从 /d/IM-Server/open-im-server-main 启动，写 config/
```

**配置路径是相对于"工作目录"的，不是相对于二进制文件**。

⚠️ **这就是为什么 `mage start` 必须先 `cd` 到项目根目录**。如果从别处启动，会报"找不到配置文件"。

📌 **更健壮的做法**：用环境变量指定配置目录（`OPENIM_CONFIG_PATH`），或者把配置嵌入二进制（Go 1.16 的 `embed`）。**本项目用的是相对路径 + 约定工作目录**——简单但脆弱。

## 9.10 三种服务发现实现

目录：`pkg/common/discovery/`

```
discovery/
├── discoveryregister.go     ← 统一入口（工厂）
├── direct/                  ← 直连（静态地址）
├── etcd/                    ← etcd 注册中心
├── kubernetes/              ← K8s Service DNS
└── doc.go
```

### 统一入口（工厂模式）

```go
// pkg/common/discovery/discoveryregister.go（简化）
func NewDiscoveryRegister(etcdConfig *config.Etcd, watchNames []string) discovery.SvcDiscoveryRegistry {
    if config.Standalone() {                          // :22-24
        return standalone.GetSvcDiscoveryRegistry()   // 进程内内存 map
    }
    if isKubernetes() {                               // :31-33
        return kdisc.NewDiscoveryRegister(...)         // K8s DNS
    }
    return kdisc.NewDiscoveryRegister(etcdConfig, watchNames)  // etcd
}
```

**三种实现的选择逻辑**：

| 实现 | 触发条件 | 机制 | 适用 |
|---|---|---|---|
| **standalone** | `config.Standalone()` | 进程内内存 map | 本地开发、单体部署 |
| **kubernetes** | 环境变量检测到 K8s | K8s Service DNS | 部署在 K8s |
| **etcd** | 默认 | etcd 注册 + watch | 传统分布式部署 |

📌 **这是"工厂模式 + 接口"的典型用法**：

```
调用方只依赖接口 discovery.SvcDiscoveryRegistry
    ↓
具体用哪个实现，由工厂在启动时决定
    ↓
业务代码完全不知道底层是 etcd 还是内存
```

**收益**：**同一份代码，三种运行形态**（理论 9.6.3）。

### 为什么还有 `direct`（直连）

`direct/` 是"静态地址"模式：配置文件里写死地址，不做任何发现。

**什么时候用？**
- 只有一两个服务、地址固定；
- 调试时想绕过 etcd；
- 在不支持 etcd 的环境跑。

📌 **这说明作者考虑了"降级路径"**：不是所有人都愿意为了跑一个服务而部署 etcd。

### etcd 实现的关键点

虽然代码在外部库 `github.com/openimsdk/tools/discovery/etcd`，但机制可以推知（对应理论 9.3.2）：

```
注册：
  ① 建 lease（TTL 通常 5~10s）
  ② Put(key, value, WithLease(leaseID))
  ③ 起 goroutine 定期 KeepAlive

发现：
  ① Get(prefix, WithPrefix()) 拉全量
  ② Watch(prefix) 监听变化
  ③ 把地址列表喂给 gRPC 的 Resolver
```

⚠️ **一个必须知道的细节**：**注册的 value 里通常存的是"服务地址 + 元数据"**。gRPC 从 Resolver 拿到地址后，才能建 SubConn（08 篇 8.8）。

## 9.11 服务名：`rpcService` 配置

```yaml
# config/discovery.yml
rpcService:
  user: user-rpc-service
  friend: friend-rpc-service
  msg: msg-rpc-service
  push: push-rpc-service
  messageGateway: messagegateway-rpc-service
  group: group-rpc-service
  auth: auth-rpc-service
  conversation: conversation-rpc-service
  third: third-rpc-service
```

**9 个服务名**（7 个 RPC + gateway + push）。

### 为什么服务名要放配置，不写死

**核心原因：环境隔离。**

```
开发环境：user-rpc-service
生产环境：prod-user-rpc-service
```

**如果写死在代码里**，同一个 etcd 集群里测试和生产的服务会**互相发现**——测试流量打到生产，灾难。

⚠️ **所以 etcd 的 `rootDirectory` 也要按环境区分**：

```yaml
rootDirectory: im          # 开发
# rootDirectory: im-prod   # 生产
```

**两个隔离手段**：不同的 rootDirectory（物理隔离）+ 不同的服务名（逻辑隔离）。**双保险**。

📌 **这是"多环境部署"的基本功**。很多事故源于"测试环境误连生产"。

### 服务名的命名风格不一致

注意 `messageGateway` 的**配置 key** 是驼峰，但**服务名**是 `messagegateway-rpc-service`（全小写）。

**为什么？**
- 配置 key 是给人看的，驼峰更好读；
- 服务名会变成 etcd 的 key（`/im/messagegateway-rpc-service/...`），**约定全小写**（和 DNS 风格一致）。

⚠️ **这类"命名转换"很容易出错**。如果代码里某处写成 `messageGateway-rpc-service`，就找不到服务。**统一规范很重要。**

## 9.12 注册与拿连接：两个方向

### 方向一：服务启动时注册（`startrpc` 里）

```go
// pkg/common/startrpc/start.go（简化）
// ① 建 gRPC server（装拦截器）
// ② 监听端口
// ③ 注册到发现中心
err := client.Register(ctx, rpcRegisterName, registerIP, port)
// ④ 调用 rpcFn 完成业务初始化
// ⑤ 阻塞等待退出信号
```

**参数对应**：
- `rpcRegisterName` → `discovery.yml` 里的服务名；
- `registerIP` → 注册到 etcd 的地址（**注意不是 listenIP**）。

### ⚠️ `listenIP` 和 `registerIP` 为什么是两个参数

```
listenIP   = 0.0.0.0      ← 监听所有网卡
registerIP = 10.0.0.1     ← 告诉别人"来这个地址找我"
```

**为什么不能都用 `0.0.0.0`？**

因为 `0.0.0.0` 不是"可连接地址"，它是"监听所有接口"的语义。**调用方拿 `0.0.0.0:20100` 是连不上的。**

**所以必须区分**：
- 监听用 `0.0.0.0`（或具体网卡）；
- 注册用**真实的、其他机器能访问到的 IP**。

📌 **这是容器/多网卡环境最容易踩的坑**：
- 容器里 `0.0.0.0` 监听正常，但如果注册了容器内部 IP（如 `172.17.0.2`），跨主机就不可达；
- 需要注册**宿主机 IP** 或 **Service 地址**。

**本项目把这个做成两个参数，是正确做法**。很多框架只有一个 IP 参数，导致容器化部署必然踩坑。

⚠️ **`registerIP` 怎么来的？** 通常由配置指定或自动探测（取第一个非 loopback 网卡）。**自动探测在多网卡环境下经常选错**（选到 docker0 或虚拟网卡），所以生产环境建议**显式配置**。

### 方向二：调用方拿连接（`rpcli`）

```go
// 各服务的 Start 里
userConn, err := client.GetConn(ctx, cfg.Discovery.RpcService.User)
userClient := rpcli.NewUserClient(userConn)
```

**`GetConn` 做了什么？**

```
① 去发现中心查 "user-rpc-service" 的所有实例
② 建一个 grpc.ClientConn（HTTP/2 连接）
③ 配置 Resolver：后续地址变化时自动更新 SubConn
④ 返回连接
```

**注意第 ③ 步**：连接建立后，**地址列表变化仍然会生效**（Resolver 持续 watch）。所以不需要"重启才能感知扩容"。

📌 **这就是理论 9.2.2 "客户端发现"的实现**：客户端持有地址列表 + 自己负载均衡。

### 连接是复用的还是每次新建

```go
// router.go（API 层）
authConn, err := client.GetConn(ctx, cfg.Discovery.RpcService.Auth)
...
u := NewUserApi(user.NewUserClient(userConn), client, ...)
```

**连接在启动时建一次，之后一直复用。**

**为什么不在每次请求时建？**
- 建连接要 TCP + HTTP/2 握手（几十 ms）；
- gRPC 的 ClientConn 本身就是**并发安全 + 多路复用**的（08 篇 8.4）。

⚠️ **但注意 `GetConn` 可能被调用多次**（每个服务各调一次）。如果内部没有缓存，会建多个 ClientConn。**从 `router.go` 看，是在 router 初始化时集中建的**，所以没问题。

## 9.13 standalone 的反射注入

### 入口

```go
// cmd/main.go:194 附近
// 伪代码
func startAllServices(ctx context.Context, allConfig *config.AllConfig) {
    for _, service := range services {
        // 按类型从 allConfig 里找子配置，注入到 service 的 Config 字段
        injectConfig(service, allConfig)
        // 启动
        go service.Start(...)
    }
}
```

### 注入的核心逻辑

```go
func injectConfig(target any, all *config.AllConfig) {
    v := reflect.ValueOf(target).Elem()
    for i := 0; i < v.NumField(); i++ {
        field := v.Field(i)
        if !field.CanSet() {
            continue
        }
        // 在 AllConfig 里找类型相同的字段
        if cfg := findSameType(all, field.Type()); cfg != nil {
            field.Set(cfg)
        }
    }
}

func findSameType(all *config.AllConfig, t reflect.Type) reflect.Value {
    v := reflect.ValueOf(all).Elem()
    for i := 0; i < v.NumField(); i++ {
        if v.Field(i).Type() == t {
            return v.Field(i)
        }
    }
    return reflect.Value{}
}
```

### 为什么用"类型匹配"而不是"名字匹配"

**因为字段名对不上**：

```go
// 服务的 Config
type Config struct {
    RpcConfig   conf.LocalConfig
    RedisConfig conf.Redis
    MongodbConfig conf.Mongo     // ← 名字叫 MongodbConfig
}

// AllConfig
type AllConfig struct {
    Redis Redis                   // ← 名字叫 Redis
    Mongo Mongo                   // ← 名字叫 Mongo
}
```

**名字完全不同，但类型相同**（都是 `conf.Redis`、`conf.Mongo`）。所以只能按类型匹配。

⚠️ **类型匹配的风险**：
- 如果两个字段类型相同（比如两个 `string`），会匹配到第一个 —— **静默错误**；
- 如果某个配置类型改了（比如 `Mongo` 改了包路径），注入失败但**不报错**。

📌 **这就是理论 9.6.4 说的"没有编译期检查"**。**改进方式**：用接口约束。

```go
type ServiceConfig interface {
    Apply(all *config.AllConfig)
}
```

每个服务的 Config 实现 `Apply`，用**显式赋值**代替反射。**代码多几行，但错误在编译期暴露。**

### standalone 下 `AllConfig` 是唯一的真相源

在 standalone 模式下：
- 只有一份 `AllConfig`；
- 12 个服务共享它（但各取所需）；
- 改一个配置，所有服务都看到。

**这消除了"配置不一致"的风险**——分布式部署时，12 个进程各读各的文件，可能出现"版本不一致"（滚动发布时新旧配置并存）。

📌 **这是 standalone 的一个隐性优势**：**配置天然一致**。

## 9.14 配置热更新

### `watchConfigNames` 参数

```go
// startrpc.Start 的签名
watchConfigNames []string
watchServiceNames []string
```

**两个 watch**：
- `watchConfigNames`：监听**配置文件**变化（如 `mongodb.yml`）；
- `watchServiceNames`：监听**服务实例**变化（如 user 服务扩缩容）。

### 配置变化的处理流程

```
① fsnotify 检测到 mongodb.yml 变了
② 用 Name2Config("mongodb.yml") 找到对应的配置对象
③ 重新读文件 → Unmarshal 到该对象
④ 通知订阅者（如果有回调）
```

**关键问题：第 ③ 步更新的是"AllConfig 里的那个对象"，但各服务持有的是"自己的那份拷贝"。**

**如果服务是值拷贝**：
```go
type Config struct {
    MongodbConfig conf.Mongo    // ← 值，不是指针
}
```
配置更新后，**服务的 `MongodbConfig` 不会变**。

**如果是指针**：
```go
MongodbConfig *conf.Mongo
```
更新能生效（但要处理并发读写）。

📌 **所以"支持 watch" 和 "配置真的生效"是两件事**（理论 9.5.5 的结论）。**具体哪些配置能热生效，必须看代码里是值还是指针**（📌 待验证）。

### 实际能热更新的常见配置

| 配置 | 通常能热更新吗 | 原因 |
|---|---|---|
| 日志级别 | ✅ | 日志库通常支持动态改 |
| 限流阈值 | ✅ | 每次读的时候取 |
| 数据库地址 | ❌ | 连接池已经建好了，改地址要重建 |
| 端口 | ❌ | 已经 Listen 了 |

📌 **这是诚实的技术判断**：**"热更新"这个能力，在实践中往往是"部分热更新"**。声称"支持热更新"却只覆盖 10% 的字段，是常见的过度宣传。

**面试时如果被问**，答："项目支持监听配置文件变化，但实际能生效的范围取决于代码是值传递还是指针传递。像端口、数据库地址这类在启动时固化的配置，改了还是要重启。真正能热更新的通常是日志级别、限流阈值这类每次读取的配置。"

**这个回答比"支持热更新"强得多。**

## 9.15 设计评价

### 做得好的四处

**① 服务发现抽象成接口，三种实现**

同一份代码支持 standalone / etcd / Kubernetes。**这是"可移植性"的典范**。

**② `listenIP` 和 `registerIP` 分开**

避开了容器/多网卡环境最常见的坑。**很多框架只有一���参数，容器化必踩坑。**

**③ standalone 用反射注入，省掉 12 个转换函数**

一份 AllConfig 服务 12 个服务，**代码量大幅减少**。

**④ `rootDirectory` + 服务名双重环境隔离**

避免测试/生产互相发现。

### 有问题的三处

**① `Name2Config` 是 22 个手写 case**

新增子配置必须记得加一行，否则热更新失效。**应该用反射自动建映射**（或者 Map 注册）。

**② 反射注入没有编译期检查**

类型不匹配就静默跳过，表现为"某个配置是零值"。**排查起来极其痛苦**（因为不报错）。

**改进**：用接口 + 显式赋值。

**③ 配置路径依赖工作目录**

从错误的目录启动就找不到配置。**建议支持环境变量指定，或 embed 进二进制**。

📌 **这三条都属于"能跑但不够健壮"**。**真实项目大多如此**——不是设计不出来，而是"当前够用"。

**面试时评价项目，要能说出"哪里可以更好"，而不是"哪里是错的"。** 前者是工程判断，后者容易显得傲慢。

```
/im/user-rpc-service/10.0.0.1:20100
/im/msg-rpc-service/10.0.0.1:20200
...
```

**这直观验证了理论 9.3.2 的 KV + 前缀组织**。

⚠️ 本项目的 etcd 映射到宿主机 12379，容器内是 2379，注意区分。

## 实验 2：观察租约过期

```bash
# ① 停掉某个 RPC 服务
mage stop   # 或在进程列表里 kill 一个

# ② 立刻 watch etcd
etcdctl --endpoints=localhost:2379 watch /im/user-rpc-service/ --prefix

# ③ 观察
# 几秒后出现 DELETE 事件
```

**预期**：服务停掉后，**几秒内**（TTL 时间）key 自动消失。

**这验证了 lease + TTL 的自动过期机制**（理论 9.3.2）。

📌 **关键观察点**：**key 是自动消失的，不是服务主动删的**（因为是 kill 掉的，没机会执行注销逻辑）。

## 实验 3：验证 standalone 不依赖 etcd

```bash
# ① 停掉 etcd
docker stop <etcd容器>

# ② 用 standalone 模式启动
go run ./cmd/main.go -c ./config

# ③ 观察是否正常
curl -X POST http://127.0.0.1:10002/auth/get_admin_token ...
```

**预期**：standalone 模式下**即使 etcd 挂了也能正常工作**（因为用的是进程内发现）。

**这验证了理论 9.6.3：发现实现被替换了。**

## 实验 4：验证 registerIP 的重要性

```bash
# 在容器里启动，看注册到 etcd 的地址是什么
etcdctl --endpoints=localhost:2379 get /im/user-rpc-service/ --prefix
```

**预期**：如果注册的是容器内 IP（172.x），从宿主机就连不上。

**这是容器化部署最常见的坑**，验证一下能加深理解。

# 第五部分 面试话术

## 30 秒版

> "服务发现解决的是'服务 IP 会变'的问题。项目支持三种实现：etcd（生产）、Kubernetes Service DNS、以及 standalone 的进程内内存注册，通过配置切换。
>
> etcd 用 lease + TTL 实现自动过期——服务挂了停止续约，几秒后 key 自动消失，不需要主动注销。用 revision + watch 做推送，断线重连能补齐事件。"

## 3 分钟版

> "这块我认为有三个点值得说。
>
> **第一是发现抽象带来的可移植性。** 所有代码只依赖 `discovery` 接口，具体实现在启动时决定。所以同一份代码可以跑成 12 个进程的微服务，也可以跑成单进程的 standalone 模式。本地开发不用起 etcd，演示一条命令就能启动全系统。这是接口抽象的典型收益。
>
> **第二是 etcd 的 lease 机制。** 服务注册时建一个 TTL 5 秒的租约，定期续约。进程被 kill 后不再续约，5 秒后 key 自动删除——所以不需要"优雅注销"也能自动摘除死实例。但租约只能发现'进程死了'，发现不了'进程卡死但还在续约'，所以严格来说还需要业务级健康检查。项目里没有 /health 接口，这是个可以改进的点。
>
> **第三是 listenIP 和 registerIP 分开。** 监听用 0.0.0.0，注册用真实可达的 IP。因为 0.0.0.0 是'监听所有网卡'的语义，不是一个可连接的地址，调用方拿它连不上。容器和多网卡环境下这个区分是必须的，很多框架只有一个 IP 参数，容器化必踩坑。"

## 追问预判

| 可能被问 | 怎么答 |
|---|---|
| "etcd 挂了怎么办？" | 已建立的连接不受影响（地址已在客户端 Resolver 里），但新实例注册和地址变化感知会失效。生产中 etcd 要 3 节点集群。 |
| "为什么不用 Redis 做注册中心？" | 可以，但 Redis 主从异步复制可能读到旧值，且没有原生 lease+watch 组合。etcd 是为这个场景设计的。 |
| "配置热更新怎么做的？" | 监听配置文件变化，用文件名反查配置对象重新加载。但实际能生效的范围取决于代码是值传递还是指针——端口、数据库地址这类启动时固化的配置改了还是要重启。 |
| "standalone 怎么实现的？" | 替换服务发现实现为进程内内存注册，加上反射把 AllConfig 按类型注入到 12 个服务的 Config 里。 |
| "反射注入有什么问题？" | 没有编译期检查。类型不匹配就静默跳过，表现为某个配置是零值，排查很痛苦。应该用接口 + 显式赋值，把运行时错误变成编译期错误。 |
| "怎么保证测试环境不打到生产？" | 两层隔离：etcd 的 rootDirectory 不同（物理隔离），服务名也不同（逻辑隔离）。 |
