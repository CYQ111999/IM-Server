# 第一部分　理论：本地缓存是「用一致性换延迟」的极致

## 1.1 为什么 Redis 还不够快

22 篇算过：Redis 单机能到 10 万 QPS。这个数字听起来够用了，但 IM 的读放大很严重。

算一笔真实的账。假设 1 万条消息/秒，其中 10% 是群消息，群平均 100 人：

```
消息发送：10000/秒
每条消息的校验：
  · 发送者是否在群（1 次 group_member 查询）
  · 群是否被禁言（1 次 group_info 查询）
  · 发送者是否被禁言（1 次 group_member 查询）
  · 是否是好友（单聊时，1 次 relation 查询）
  · 用户全局免打扰（1 次 user 查询）
→ 平均 3-4 次校验/消息
→ 30000-40000 次缓存查询/秒

消息推送：10000 × 扇出
 · 每条消息要查「接收者的会话设置」
 · 群消息扇出 100 人 → 100 次 conversation 查询
→ 10% 群消息 × 10000 × 100 = 100000 次/秒
```

**合计 15 万+ 次缓存查询/秒**。这个量级：

- Redis 单机能扛（10 万 QPS 是保守估计，实际能到 20 万）
- 但**网络带宽会先炸**：每次查询往返 200 字节，15 万 × 200 = 30MB/秒 = 240Mbps
- 而且**延迟会累积**：每次 0.3ms，一条消息 4 次校验 = 1.2ms，纯网络开销

> 🔴 **这就是本地缓存存在的理由**：把「最热的、几乎不变的数据」放进进程内存。
> - Redis：0.3ms
> - 本地 LRU：**100ns**
>
> **差 3000 倍**。而且不占网络带宽。

## 1.2 LRU：为什么是「哈希表 + 双向链表」

LRU = Least Recently Used（最近最少使用）。淘汰策略是：**优先淘汰最久没被访问的**。

### 为什么需要两个数据结构

单看需求：
1. **O(1) 查找**：给定 key 找到值
2. **O(1) 淘汰**：找到最久没用的那个，删掉
3. **O(1) 更新**：每次访问要把这个 key 移到「最近使用」的位置

| 结构 | 查找 | 按顺序淘汰 | 移到头部 |
|---|---|---|---|
| 数组 | O(n) | O(1) | O(n) |
| 链表 | O(n) | O(1) | O(1)（已知节点） |
| 哈希表 | O(1) | ❌ 无序 | ❌ |
| **哈希表 + 双向链表** | **O(1)** | **O(1)** | **O(1)** |

**组合起来**：
- 哈希表：`key → 链表节点指针`（解决查找）
- 双向链表：节点按「访问时间」排序，头部是最近用的，尾部是最久没用的（解决淘汰）

**为什么是双向链表不是单向？** 因为删除一个节点需要它的前驱。单向链表删除节点要 O(n) 找前驱；双向链表有 `prev` 指针，O(1)。

```
head → [最近用] ⇄ [B] ⇄ [C] ⇄ [最久没用] ← tail

Get(B)：
  哈希表找到 B 节点 → 从原位置摘除（B.prev.next = B.next; B.next.prev = B.prev）
                    → 插到 head 后面
  两步都是 O(1)
```

### OpenIM 用的不是标准 LRU

`pkg/localcache/lru/` 有两个实现：

| 实现 | 淘汰时机 | 过期处理 |
|---|---|---|
| `LazyLRU` | 容量满时 | **惰性**：读取时检查 `expires`，过期就重新 fetch |
| `ExpirationLRU` | 容量满时 + **定时器** | **主动**：`expirable.LRU` 内部有个后台 goroutine 定期清理 |

配置项控制：

```go
// pkg/localcache/option.go:27-29
// expirationEvict 为 true 表示过期定时器到期时主动清理缓存，
// 为 false 表示采用惰性删除。
expirationEvict bool
```

**默认是 `false`（惰性）**，因为：

```
惰性删除：
  · 没有后台 goroutine，零额外开销
  · 但过期的 key 会一直占着内存（直到被访问或被 LRU 淘汰）
  · 内存占用 = 实际写入量（可能远超有效数据量）

主动删除：
  · 后台定时器，定期扫描
  · 内存占用 ≈ 有效数据量
  · 但扫描本身要遍历整个 map（O(n)），数据量大时反而卡
```

> 🔴 **这是一个经典的取舍**：`Redis` 本身也是「惰性 + 定期」的混合策略。纯惰性会内存泄漏，纯定期会 CPU 抖动。**OpenIM 选了纯惰性，靠 LRU 容量上限兜底**——最多 20000 条/槽，不会无限涨。

## 1.3 分片：为什么是 500 个

看默认配置（`option.go:12-13`）：

```go
localSlotNum:  500,      // 500 个槽
localSlotSize: 20000,    // 每槽 20000 条
```

**总容量 = 500 × 20000 = 1000 万条**。这个数字看起来离谱（一个进程缓存 1000 万条用户信息？），实际上**永远不会装满**——因为 TTL 只有 5 分钟。

**分片解决的是锁竞争**。

单槽 LRU 的所有操作要抢同一把锁：

```
5000 QPS 打到一个 LRU 上
→ 每个 Get 都要 Lock/Unlock
→ 锁竞争剧烈，CPU 大量时间在自旋
```

500 个槽之后：

```
5000 QPS / 500 槽 = 每槽 10 QPS
→ 锁竞争降低 500 倍
```

**用哪个槽？哈希取模**：

```go
// pkg/localcache/cache.go:23-27
func LRUStringHash(key string) uint64 {
    h := fnv.New64a()
    h.Write(*(*[]byte)(unsafe.Pointer(&key)))   // ← 零拷贝把 string 转 []byte
    return h.Sum64()
}
```

```go
// pkg/localcache/lru/lru_slot.go:57-59
func (x *slotLRU[K, V]) getIndex(k K) uint64 {
    return x.hash(k) % x.n
}
```

> 🟡 **`*(*[]byte)(unsafe.Pointer(&key))` 是什么？**
>
> 这是把 `string` 的底层结构（`{ptr, len}`）**强转**成 `[]byte` 的底层结构。因为两者内存布局相同（都是 `{数据指针, 长度}`），所以可以零拷贝转换。
>
> **正常写法** `[]byte(key)` 会拷贝一份字符串内容（因为 string 不可变、[]byte 可变，Go 必须拷贝来保证安全）。用 unsafe 跳过这个拷贝。
>
> 这里安全吗？**安全**——因为 `h.Write` 只读不写，不会破坏 string 的不可变性。而且 key 的生命周期覆盖了整个函数调用。
>
> **这是一次极小的优化**（省了一次内存分配），但用 unsafe 有风险。📌 如果面试被问「你用过 unsafe 吗」，这是一个可以讲的例子，但要能说清「为什么在这里是安全的」。

**分片带来的两个问题**：

1. **不能跨片原子操作**：`MGet([k1, k2])` 如果 k1 在槽 3、k2 在槽 7，要分别加锁。`SlotLRU.GetBatch` 就是按槽分组后再分别处理的（`lru_slot.go:21-45`）
2. **删除依赖 key 也分散**：如果 A 依赖 B，它们可能在不同槽，级联删除时要注意锁顺序（下面 1.5 的死锁问题）

## 1.4 两个 TTL：防穿透的细节

22 篇讲过缓存穿透，这里是它在本地缓存层的实现：

```go
// pkg/localcache/option.go:10-21（默认值）
localSuccessTTL: time.Minute,        // 成功 → 1 分钟
localFailedTTL:  time.Second * 5,    // 失败 → 5 秒

// config/local-cache.yml（实际配置）
successExpire: 300    // 成功 → 5 分钟
failedExpire: 5       // 失败 → 5 秒
```

实际生效的是**配置文件的值**（因为 `rpccache` 里显式传了 `WithLocalSuccessTTL(lc.Success())`）。

**为什么失败要缓存？**

如果查一个不存在的用户，每次都 miss、每次都去 RPC 查库、每次都要 10ms——**一个不存在的 ID 就能打爆后端**。

缓存失败 5 秒，等于「5 秒内同样的错误查询只穿透一次」。

**为什么是 5 秒不是 5 分钟？**

因为「不存在」这个结论**可能变化**：用户可能刚被创建。5 秒后重新查，能容忍「新建用户最多 5 秒后才能被查到」。如果设成 5 分钟，用户体验就是「我刚注册，别人 5 分钟加不上我好友」。

> 🔴 **这个「成功长 TTL + 失败短 TTL」的模式，是所有缓存系统的标配**。Redis 层也有一份（`failedExpire: 5`），两层一致。

### 但两个 LRU 实现在这里行为不同

`LazyLRU` 会**缓存错误**（`lru_lazy.go:70-72`）：

```go
v.value, v.err = fetch()
if v.err == nil {
    v.expires = time.Now().Add(x.successTTL).UnixMilli()
} else {
    v.expires = time.Now().Add(x.failedTTL).UnixMilli()   // ← 错误也存 5 秒
}
```

`ExpirationLRU` 会**删掉错误**（`lru_expiration.go:106-111`）：

```go
v.value, v.err = fetch()
if v.err == nil {
    x.target.IncrGetSuccess()
} else {
    x.target.IncrGetFailed()
    x.core.Remove(key)      // ← 错误直接删，不缓存
}
```

**这两个行为不一致**！而且 `ExpirationLRU` 构造函数收了 `failedTTL` 参数，却**从未使用**：

```go
// lru_expiration.go:26-30
type expirationLruItem[V any] struct {
    lock  sync.RWMutex
    err   error
    value V
}   // ← 没有 expires 字段！靠 expirable.LRU 内部的 TTL

// lru_expiration.go:32-38
type ExpirationLRU[K, V any] struct {
    ...
    successTTL time.Duration
    failedTTL  time.Duration      // ← 声明了，零使用
    target     Target
}
```

> ⚠️ **`failedTTL` 是死字段**。`ExpirationLRU` 的失败策略是「删掉」，不是「缓存 5 秒」。所以如果哪天有人把 `expirationEvict` 改成 true，**缓存穿透的保护就失效了**——不存在的 ID 会每次穿透。
>
> 这是一个「两个实现语义不一致」的隐蔽陷阱。默认走 `LazyLRU` 所以没问题，但配置一改就出事。

## 1.5 缓存依赖图：本篇最精彩的部分

### 问题：一个数据由另一个数据推导出来

场景（好友系统，17 篇）：

```
FRIEND_IDS:user1     = ["user2", "user3", ...]         ← 好友列表
IS_FRIEND:user2-user1 = true                            ← user2 是否是 user1 的好友
```

`IS_FRIEND:user2-user1` 的答案**完全由** `FRIEND_IDS:user1` 决定。

现在 user1 删了 user2。会发生什么？

```
① 删掉 FRIEND_IDS:user1       ← 主动失效
② IS_FRIEND:user2-user1 还在！  ← 缓存里还是 true
③ 用户查「user2 是不是好友」→ 读到 true → 错误
```

**这就是「缓存依赖」问题**：失效了 A，但由 A 推导出的 B 没失效。

### 朴素解法：手动删所有相关的

```go
// 删好友时
cache.Del("FRIEND_IDS:user1")
cache.Del("IS_FRIEND:user2-user1")   // ← 得知道有哪些人
cache.Del("IS_FRIEND:user3-user1")
...
```

问题：**你得知道所有依赖它的 key**。好友有 1000 个，就要删 1000 次。而且 `IS_FRIEND` 是**双向**的（`user2-user1` 和 `user1-user2` 都可能有），删漏一个就是脏数据。

### OpenIM 的解法：双向图 + BFS

`pkg/localcache/link/link.go`，109 行，实现了**无向图**：

```go
type Link interface {
    Link(key string, link ...string)    // 建立双向边
    Del(key string) map[string]struct{} // 删除节点，返回所有连通的节点
}
```

**数据结构**：`map[string]map[string]struct{}`，即**邻接表**。

```go
// link.go:20-23
type linkKey struct {
    lock sync.Mutex
    data map[string]map[string]struct{}
}

// link.go:25-36 建立双向边
func (x *linkKey) link(key string, link ...string) {
    x.lock.Lock()
    defer x.lock.Unlock()
    v, ok := x.data[key]
    if !ok {
        v = make(map[string]struct{})
        x.data[key] = v
    }
    for _, k := range link {
        v[k] = struct{}{}
    }
}
```

`Link(key, link...)` 会**双向**建立边（`slot.Link`）：

```go
// link.go:74-87
func (x *slot) Link(key string, link ...string) {
    mk := key
    x.slots[x.index(mk)].link(mk, lks...)     // key → link
    for _, lk := range lks {
        x.slots[x.index(lk)].link(lk, mk)     // link → key（反向）
    }
}
```

**为什么要双向？** 因为 `FRIEND_IDS:user1` 被删时，要知道「哪些 key 依赖我」。如果只存单向（`IS_FRIEND → FRIEND_IDS`），删除时就得遍历所有 key 找「谁的依赖是 FRIEND_IDS」——O(n)。

双向之后，`data["FRIEND_IDS:user1"]` 直接就是所有依赖它的 key 集合。

### BFS 级联删除

```go
// link.go:93-109
func (x *slot) delKey(k string) map[string]struct{} {
    del := make(map[string]struct{})
    stack := []string{k}
    for len(stack) > 0 {
        curr := stack[len(stack)-1]           // 取栈顶（DFS，但用栈做遍历）
        stack = stack[:len(stack)-1]
        if _, ok := del[curr]; ok {
            continue                          // 已访问，跳过（防环）
        }
        del[curr] = struct{}{}
        childKeys := x.slots[x.index(curr)].del(curr)   // 删掉这个节点，拿到邻居
        for ck := range childKeys {
            stack = append(stack, ck)         // 邻居入栈，继续
        }
    }
    return del
}
```

**这段代码做的是「图的连通分量遍历」**：

```
A ←→ B ←→ C
删除 A：
  栈 = [A]
  → 弹 A，标记已访问，删 A 的邻接表，拿到邻居 {B}，B 入栈
  → 栈 = [B]
  → 弹 B，标记，删 B，拿到邻居 {A, C}，A 和 C 入栈
  → 栈 = [A, C]
  → 弹 C，标记，删 C，拿到邻居 {B}，B 入栈
  → 栈 = [A, B]
  → A 已访问跳过；B 已访问跳过
  → 栈空，返回 {A, B, C}
```

**三个关键点**：

1. **`if _, ok := del[curr]; ok { continue }` 防环**。图可能有环（A←→B←→A），不判重会死循环。
2. **边遍历边删**。`x.slots[...].del(curr)` 在遍历过程中就把邻接表删了，所以图会越来越小。
3. **注意这是个 DFS 不是 BFS**（用 `stack` 后进先出）。名字叫 BFS 但实现是 DFS——不过对「求连通分量」来说，DFS 和 BFS 结果一样，无所谓。

> 🔴 **为什么用「栈 + 循环」而不是递归？** 因为递归深度受限于图的大小。如果有一个 10 万节点的依赖链，递归会栈溢出。用显式栈，深度只受内存限制。

### 注册依赖：link 参数

依赖关系是在**读取时**建立的（`cache.go:96-107`）：

```go
func (c *cache[V]) GetLink(ctx context.Context, key string, fetch func(ctx context.Context) (V, error), link ...string) (V, error) {
    if c.local != nil {
        return c.local.Get(key, func() (V, error) {
            if len(link) > 0 && c.link != nil {
                c.link.Link(key, link...)     // ← 回源时建立依赖
            }
            return fetch(ctx)
        })
    }
    ...
}
```

**注意 `link.Link` 是在 `fetch` 之前调用的**。也就是说：**只要发生过一次缓存未命中 + 回源，依赖关系就建立了**。

实际用法（`rpccache/friend.go:57-60`）：

```go
return cache.Unmarshal(f.local.GetLink(ctx,
    cachekey.GetIsFriendKey(possibleFriendUserID, userID),        // ← 缓存的 key
    func(ctx context.Context) ([]byte, error) {
        return cache.Marshal(f.client.FriendClient.IsFriend(ctx, ...))
    },
    cachekey.GetFriendIDsKey(possibleFriendUserID),               // ← 依赖的 key
))
```

**语义**：`IS_FRIEND:x-y` 依赖 `FRIEND_IDS:x`。

**所以当 `FRIEND_IDS:x` 被删除时**：

```
① c.del("FRIEND_IDS:x")
② lks := c.link.Del("FRIEND_IDS:x")     → 拿到 {IS_FRIEND:a-x, IS_FRIEND:b-x, ...}
③ 对每个 lks 里的 key 调 c.local.Del(k)  → 级联删除
```

**这就是「删一个，连带删一片」的实现**。

### 一个防死锁的细节

`onEvict`（LRU 淘汰回调）里有个很讲究的写法（`cache.go:59-67`）：

```go
func (c *cache[V]) onEvict(key string, value V) {
    if c.link != nil {
        // 底层 LRU 仍持锁时不要删除其他 key；
        // 将关联删除延后执行，避免重入同一分片导致死锁。
        if lks := c.link.Del(key); len(lks) > 0 {
            go c.delLinked(key, lks)      // ← 起 goroutine 异步删
        }
    }
}
```

**注释说得很清楚**：「底层 LRU 仍持锁时不要删除其他 key，避免重入同一分片导致死锁。」

想象一下不加 goroutine 的后果：

```
goroutine G1: LRU 槽 3 的 Get 未命中 → 加锁槽 3 → 触发淘汰 → onEvict
            → 删除关联 key（可能在槽 3）→ 再次 Lock 槽 3 → **死锁**
```

Go 的 `sync.Mutex` 不可重入。同一 goroutine 对同一把锁二次 `Lock()` 会永久阻塞。

**修法：起一个新 goroutine 做级联删除**。新 goroutine 是「另一条执行流」，可以安全地等锁。

> 🔴 **这个 `go` 是为了避开「锁不可重入」这个 Go 语言特性**，不是为了性能。很多人在这种地方会下意识地想「异步更快」，但真正的理由是**正确性**。
>
> 代价：级联删除变成**异步**的。如果紧接着读一个依赖 key，可能读到还没被删的旧值。这个窗口是微秒级，IM 能接受。

⚠️ **另一个隐患**：`go c.delLinked(...)` 没有任何生命周期管理。进程退出时这些 goroutine 会被直接杀掉，可能导致链接图处于「删了一半」的状态。不过因为图只在内存里，进程重启就重建了，所以实际影响不大。

## 1.6 单飞（singleflight）：合并并发回源

一个经典问题：

```
1000 个请求同时查 user1
→ 缓存都 miss
→ 1000 个都去 RPC 查
→ RPC 被打爆
```

**解法：单飞**——同一个 key 的并发请求，只放一个去回源，其他等着复用结果。

`LazyLRU.Get` 用了一种巧妙的实现（`lru_lazy.go:44-75`）：

```go
func (x *LazyLRU[K, V]) Get(key K, fetch func() (V, error)) (V, error) {
    x.lock.Lock()
    v, ok := x.core.Get(key)
    if ok {
        x.lock.Unlock()
        v.lock.Lock()                    // ← 锁「这个 item」
        expires, value, err := v.expires, v.value, v.err
        if expires != 0 && expires > time.Now().UnixMilli() {
            v.lock.Unlock()
            return value, err            // 命中，直接返回
        }
        // 过期了：不解锁，继续往下走（去 fetch）
    } else {
        v = &lazyLruItem[V]{}            // 没这个 key：新建一个占位 item
        x.core.Add(key, v)
        v.lock.Lock()                    // 锁这个新 item
        x.lock.Unlock()
    }
    defer v.lock.Unlock()
    if v.expires > time.Now().UnixMilli() {   // ← 双重检查
        return v.value, v.err            // 别人已经 fetch 完了
    }
    v.value, v.err = fetch()             // 只有一个人会走到这里
    ...
}
```

**两级锁的设计**：

```
x.lock     ← 保护整个 LRU 的 map（粗粒度，持有时间极短）
v.lock     ← 保护单个 item（细粒度，持有时间长，包含 fetch）
```

**为什么这么设计？**

如果只用 `x.lock` 保护一切，那 fetch（可能耗时 10ms）期间要一直持有全局锁 → 所有其他 key 的访问都被阻塞。

两级锁之后：**拿到 item 的锁就释放全局锁**，其他人可以继续访问别的 key。

**核心技巧：先 `Add` 一个空 item 再 fetch**。

```go
v = &lazyLruItem[V]{}    // 空 item，expires=0
x.core.Add(key, v)       // 立即放进 map
v.lock.Lock()            // 锁住这个空 item
```

这样**第 2 个并发请求**会 `x.core.Get(key)` 拿到这个空 item，然后尝试 `v.lock.Lock()` —— **阻塞**，直到第一个请求 fetch 完、`Unlock`。

**这就是单飞**：同一个 key 只有第一个请求回源，其他都在 item 的锁上排队。

**双重检查（`:63-65`）**：

```go
if v.expires > time.Now().UnixMilli() {
    return v.value, v.err    // 别人已经填好了
}
```

为什么需要？因为排队期间，第一个请求可能已经 fetch 完成。第二个请求拿到锁后，发现 `expires` 已经被设置，就直接返回，不再 fetch。

> 🔴 **这个模式叫「双重检查锁（Double-Checked Locking）」**，是并发编程的经典模式。第一层检查（无锁，快速路径）→ 加锁 → 第二层检查（防止重复工作）。
>
> **如果没有第二层检查**：1000 个请求排队，第 1 个 fetch 完，剩下的 999 个拿到锁后会**各自再 fetch 一次**（因为它们是排队等到的，不是同时进来的）。单飞就失效了。

⚠️ **一个真实的 bug**：`GetBatch` 里没有单飞保护（`lru_lazy.go:77-138`）。它是「先收集所有 miss 的 key，然后一次 fetch」。如果两个 goroutine 同时 `GetBatch` 同样的 key 集合，会**各自 fetch 一次**。批量场景下这个概率不高（因为批量请求通常是同一个上游发起的），但确实存在重复回源。

## 1.7 跨进程失效：Pub/Sub 广播

本地缓存的根本问题是：**12 个进程各有各的 L1，改了一个，其他 11 个不知道**。

**解法：广播**。

```
节点 A 更新了 user1 的信息
  → 删掉自己的 L1 的 USER_INFO:user1
  → DEL 掉 Redis 的 USER_INFO:user1
  → PUBLISH DELETE_CACHE_USER ["USER_INFO:user1"]
       ↓
  节点 B、C、D... 都订阅了这个 channel
  → 收到消息 → 删掉本地 L1 的 USER_INFO:user1
```

**代码实现**：

发布方（`cache/redis/batch_handler.go:52-79`）：

```go
func (c *BatchDeleterRedis) execDel(ctx context.Context, keys []string) error {
    if len(keys) > 0 {
        // ① 删 Redis（TagAsDeleted，延迟过期）
        err := ProcessKeysBySlot(ctx, c.redisClient, keys, func(ctx context.Context, slot int64, keys []string) error {
            return c.rocksClient.TagAsDeletedBatch2(ctx, keys)
        })
        if err != nil { return err }
        // ② 广播给所有节点
        if len(c.redisPubTopics) > 0 && len(keys) > 0 {
            keysByTopic := localcache.GetPublishKeysByTopic(c.redisPubTopics, keys)
            for topic, keys := range keysByTopic {
                if len(keys) > 0 {
                    data, err := json.Marshal(keys)
                    ...
                    c.redisClient.Publish(ctx, topic, string(data))
                }
            }
        }
    }
    return nil
}
```

订阅方（`rpccache/subscriber.go`）：

```go
func subscriberRedisDeleteCache(ctx context.Context, client redis.UniversalClient, channel string, del func(ctx context.Context, key ...string)) {
    defer func() {
        if r := recover(); r != nil {
            log.ZPanic(ctx, "subscriberRedisDeleteCache Panic", errs.ErrPanic(r))
        }
    }()
    for message := range client.Subscribe(ctx, channel).Channel() {
        var keys []string
        if err := json.Unmarshal([]byte(message.Payload), &keys); err != nil {
            log.ZError(ctx, "subscriberRedisDeleteCache json.Unmarshal error", err)
            continue
        }
        if len(keys) == 0 { continue }
        del(ctx, keys...)
    }
}
```

**注册**（`rpccache/user.go:30-32`）：

```go
if lc.Enable() {
    go subscriberRedisDeleteCache(context.Background(), cli, lc.Topic, x.local.DelLocal)
}
```

**五个 channel，五个业务域**（`config/local-cache.yml`）：

```yaml
auth:         topic: DELETE_CACHE_AUTH
user:         topic: DELETE_CACHE_USER
group:        topic: DELETE_CACHE_GROUP
friend:       topic: DELETE_CACHE_FRIEND
conversation: topic: DELETE_CACHE_CONVERSATION
```

**为什么要分 5 个 channel 而不是 1 个？**

因为**按前缀分流的效率**。一个 channel 里混杂所有 key，订阅方收到后要判断「这个 key 我关心吗」。分 5 个之后，每个订阅者只订阅自己关心的，收到就是自己的。

`GetPublishKeysByTopic` 做的就是这个分流（`localcache/init.go:48-70`）：

```go
func GetPublishKeysByTopic(topics []string, keys []string) map[string][]string {
    keysByTopic := make(map[string][]string)
    for _, topic := range topics {
        keysByTopic[topic] = []string{}
    }
    for _, key := range keys {
        for _, topic := range topics {
            prefixes, ok := subscribe[topic]      // topic → 关心哪些前缀
            if !ok { continue }
            for _, prefix := range prefixes {
                if strings.HasPrefix(key, prefix) {   // ← 精确前缀匹配
                    keysByTopic[topic] = append(keysByTopic[topic], key)
                    break
                }
            }
        }
    }
    return keysByTopic
}
```

**前缀表**（`init.go:18-38`）：

```go
{
    Local: localCache.User,
    Keys:  []string{cachekey.UserInfoKey, cachekey.UserGlobalRecvMsgOptKey},
},
{
    Local: localCache.Group,
    Keys:  []string{cachekey.GroupMemberIDsKey, cachekey.GroupInfoKey, cachekey.GroupMemberInfoKey},
},
{
    Local: localCache.Friend,
    Keys:  []string{cachekey.FriendIDsKey, cachekey.BlackIDsKey},
},
{
    Local: localCache.Conversation,
    Keys:  []string{cachekey.ConversationKey, cachekey.ConversationIDsKey, cachekey.ConversationNotReceiveMessageUserIDsKey},
},
```

> 🔴 **注意这里是「精确前缀列表」，不是「通配符」**。只有列出的前缀对应的 key 才会被广播。
>
> **这意味着：如果一个 key 不在这个列表里，它的失效不会广播到其他节点！** 那些节点会一直用旧值，直到 TTL 到期（5 分钟）。
>
> 比如 `USER_INFO:` 和 `USER_GLOBAL_RECV_MSG_OPT_KEY:` 在列表里，但 `CLIENT_CONFIG:` 不在（虽然它也是用户相关的）。📌 待验证：client_config 的缓存是否真的会不同步。

### Pub/Sub 的三个先天缺陷

**这是一个「能用但不完美」的方案**，必须知道它的局限：

**① 不可靠投递**。Redis Pub/Sub 是「发后即忘」，订阅者不在线（重连中、刚启动）就收不到。

```
t1: 节点 B 重启中
t2: 节点 A 广播删 USER_INFO:user1
t3: 节点 B 启动完成，订阅 channel
→ B 永远不会知道要删这个 key
```

**后果**：B 在 TTL（5 分钟）内读到旧值。

**② 没有 ack**。发布方不知道谁收到了。

**③ 顺序不保证**。多个发布方并发时，消息顺序可能乱。但删除是幂等的（删一次和删两次一样），所以这个不影响。

> 🟡 **改进方向**：用 Redis Stream 替代 Pub/Sub（有消费组、有 ack、可回溯）。但代价是要维护 consumer group 状态，复杂度上升。或者用「版本号」方案——每个 key 带一个版本，读取时对比 Redis 里的全局版本，过期就重读。
>
> OpenIM 选了最简单的 Pub/Sub，因为**5 分钟的 TTL 是兜底**。最坏情况下旧数据只活 5 分钟，IM 能接受。

**分层的意义**：

```

rpccache    = 业务封装（知道缓存什么、依赖什么）
```

`localcache` 是泛型的（`Cache[V any]`），任何类型都能用。`rpccache` 里全部实例化成了 `Cache[[]byte]`——**缓存的是 RPC 响应的 protobuf 字节**。

> 🔴 **这个选择很关键**：缓存的是「RPC 响应」而不是「数据库记录」。为什么？
>
> 因为 L1 的定位是「**挡住 RPC 调用**」，不是「挡数据库」。如果缓存数据库记录，还得自己组装成响应；缓存响应，取出来 `proto.Unmarshal` 就能直接返回。**省掉了「组装」这一层**。
>
> 代价：缓存的是业务快照，如果响应结构变了（比如加了字段），旧缓存反序列化会缺字段。proto 的向后兼容性救了这个（未知字段忽略，缺失字段用零值）。

## 2.2 Cache 接口：只有 5 个方法

```go
// pkg/localcache/cache.go:13-18
type Cache[V any] interface {
    Get(ctx context.Context, key string, fetch func(ctx context.Context) (V, error)) (V, error)
    GetLink(ctx context.Context, key string, fetch func(ctx context.Context) (V, error), link ...string) (V, error)
    Del(ctx context.Context, key ...string)
    DelLocal(ctx context.Context, key ...string)
    Stop()
}
```

**`Get` 和 `GetLink` 的区别**：`Get` 就是 `GetLink` 不带依赖。

```go
// cache.go:92-94
func (c *cache[V]) Get(ctx context.Context, key string, fetch func(ctx context.Context) (V, error)) (V, error) {
    return c.GetLink(ctx, key, fetch)
}
```

**`Del` 和 `DelLocal` 的区别**：

```go
// cache.go:109-118
func (c *cache[V]) Del(ctx context.Context, key ...string) {
    for _, fn := range c.opt.delFn {
        fn(ctx, key...)        // ← 先调注册的删除函数（比如删 Redis + 广播）
    }
    c.del(key...)              // ← 再删本地
}

func (c *cache[V]) DelLocal(ctx context.Context, key ...string) {
    c.del(key...)              // ← 只删本地
}
```

**语义分工**：
- `Del`：**主动失效**（我是数据源，我要通知所有人）→ 删本地 + 调 `delFn`（Redis + 广播）
- `DelLocal`：**被动失效**（别人通知我了）→ 只删本地

**这个区分避免了无限循环**：如果 `DelLocal` 也调 `delFn`，那节点 B 收到广播后调 `DelLocal` → 又广播 → 节点 A 收到 → 又广播 → 死循环。

> 🔴 **这是一个容易踩的坑**：广播型失效系统必须区分「发起方」和「接收方」，否则会递归广播。

## 2.6 依赖关系只有一个地方用

全项目 `GetLink` 只有 **2 处调用**（`rpccache/friend.go:57,83`）：

```go
// 是否好友：IS_FRIEND:x-y 依赖 FRIEND_IDS:x
f.local.GetLink(ctx,
    cachekey.GetIsFriendKey(possibleFriendUserID, userID),
    func(ctx) { return f.client.FriendClient.IsFriend(...) },
    cachekey.GetFriendIDsKey(possibleFriendUserID),      // ← 依赖
)

// 是否拉黑：IS_BLACK:x-y 依赖 BLACK_IDS:y
f.local.GetLink(ctx,
    cachekey.GetIsBlackIDsKey(possibleBlackUserID, userID),
    func(ctx) { return f.client.FriendClient.IsBlack(...) },
    cachekey.GetBlackIDsKey(userID),                     // ← 依赖
)
```

**为什么只有这两个？**

因为这是仅有的「**派生数据**」：

```
IS_FRIEND:x-y      可以被 FRIEND_IDS:x 完全推导出来
IS_BLACK:x-y       可以被 BLACK_IDS:y 完全推导出来
```

其他缓存都没有这种关系：
- `USER_INFO:u` 不依赖任何东西（是源头）
- `GROUP_INFO:g` 不依赖任何东西
- `CONVERSATION:c` 不依赖任何东西（虽然它的 `max_seq` 来自消息，但消息不是缓存）

> 🔴 **所以 link 这套机制只用了两处，但代码写了 109 行 + 一堆测试**。这是一个「**通用机制解决了一个很窄的问题**」的例子。
>
> 值不值得？值得——因为好友关系是**最高频的校验**（每条单聊消息都要查「是不是好友」），而好友列表**经常变**（加好友、删好友、拉黑）。如果每次都靠 TTL 过期（5 分钟），那删了好友之后 5 分钟内还能发消息——这是不可接受的。
>
> **这套机制把「删好友 → 立刻不能发消息」的延迟从 5 分钟降到了微秒级**。

## 2.7 完整的一致性链路

把所有环节串起来，这是「三级缓存怎么保证一致」的完整答案：

```
【写路径】
用户改昵称
  ↓
① 更新 MongoDB（真相）
  ↓
② cache.Del(ctx, "USER_INFO:user1")
   ├─ 调 delFn → BatchDeleterRedis.execDel
   │   ├─ rocksClient.TagAsDeletedBatch2("USER_INFO:user1")   ← Redis 标记失效（TTL 改成 11 秒）
   │   └─ PUBLISH DELETE_CACHE_USER ["USER_INFO:user1"]        ← 广播
   └─ c.del("USER_INFO:user1")                                 ← 删自己的 L1
  ↓
③ 其他 11 个节点的 subscriberRedisDeleteCache 收到消息
   → DelLocal("USER_INFO:user1") → 删各自 L1
  ↓
④ 下次读：L1 miss → L2 miss（已标记失效）→ 回源 Mongo → 逐层回填

【不一致窗口】
写 Mongo（①）→ 广播到达（③）之间，约 1ms
· 这期间其他节点读到旧值
· 如果节点 B 恰好重启错过了广播，靠 TTL 兜底（5 分钟）
```

**这个方案的强度**：**最终一致，窗口 1ms ~ 5 分钟**。

对于 IM 来说够用吗？**够**。因为：
- 消息本身有 seq 保证顺序（13 篇）
- 短暂读到旧的好友状态不会导致数据错误
- 最坏情况是「删了好友之后还能发一条消息」，而这条消息的接收方会正常收（因为消息链路的校验是另一套）

> 🔴 **面试要说清「我们的缓存不是强一致」**。如果吹「强一致」，面试官追问「跨进程的 L1 怎么强一致」就露馅了。正确的说法是：「**写后失效 + TTL 兜底，最终一致，窗口毫秒级；异常情况（广播丢失）最长 5 分钟。**」

## 2.8 三级缓存的性能模型

给一组能直接用的数字：

| 层级 | 介质 | 延迟 | 容量 | 命中率（估） |
|---|---|---|---|---|
| L1 本地 LRU | 进程内存 | **~100ns** | 100 槽 × 2000 条 = 20 万条 | 70-90%（热点数据） |
| L2 Redis | 网络 + 内存 | **~0.3ms** | 按内存，GB 级 | 95%+（L1 未命中的） |
| L3 MongoDB | 磁盘 + 索引 | **~1-10ms** | 无限（可扩） | — |

**平均延迟**（假设 L1 命中 80%，L2 命中 90%）：

```
0.8 × 0.1μs + 0.2 × (0.9 × 300μs + 0.1 × 5000μs)
= 0.08μs + 0.2 × (270μs + 500μs)
= 0.08μs + 154μs
≈ 0.15ms
```

**如果没有 L1，只有 L2 + L3**：

```
0.9 × 300μs + 0.1 × 5000μs = 770μs
```

**差 5 倍**。而如果 L1 命中率能到 95%（热点集中的场景），差距会到 20 倍以上。

> 🔴 **这就是「为什么需要 L1」的量化答案**。不是「感觉更快」，是**平均延迟从 770μs 降到 150μs**。

# 第三部分　实验

### 🧪 实验 24-1：验证本地缓存的存在

本地缓存**不占网络**，所以最容易的验证方式是「看 Redis 的 QPS」。

```bash
# 1. 看 Redis 的命令统计
docker exec -it redis redis-cli -a <密码> INFO commandstats | grep -E "cmdstat_hget|cmdstat_hgetall"

# 2. 连发 100 次同样的请求
for i in $(seq 1 100); do
  curl -s -X POST "http://127.0.0.1:10002/user/get_users_info" \
    -H "Content-Type: application/json" -H "token: <token>" -H "operationID: t$i" \
    -d '{"userIDs":["imAdmin"]}' > /dev/null
done

# 3. 再看命令统计
docker exec -it redis redis-cli -a <密码> INFO commandstats | grep cmdstat_hget
```

**预期**：`calls` 只增加了 **1-2 次**，不是 100 次。因为从第 2 次开始就走 L1 了。

**这是最直观的「本地缓存生效」的证据**。

### 🧪 实验 24-2：验证依赖图级联失效

这个实验能亲眼看到 link 机制。

```bash
# 1. 先查一次「是否好友」，让缓存建立
curl -s -X POST "http://127.0.0.1:10002/friend/is_friend" \
  -H "Content-Type: application/json" -H "token: <tokenA>" -H "operationID: t1" \
  -d '{"userID1":"<userA>","userID2":"<userB>"}'

# 2. 改 userA 的备注（这会触发 FRIEND_INFO 失效，但不会触发 FRIEND_IDS）
curl -s -X POST "http://127.0.0.1:10002/friend/update_friends" ...

# 3. 删好友（这会触发 FRIEND_IDS 失效 → 级联删 IS_FRIEND）
curl -s -X POST "http://127.0.0.1:10002/friend/delete_friend" \
  -H "Content-Type: application/json" -H "token: <tokenA>" -H "operationID: t3" \
  -d '{"ownerUserID":"<userA>","friendUserID":"<userB>"}'

# 4. 立刻查「是否好友」——应该返回 false（不是缓存里的 true）
curl -s -X POST "http://127.0.0.1:10002/friend/is_friend" ...

# 5. 看日志里的广播
docker logs <api-container> 2>&1 | grep -i "delete cache" | tail -5
```

**第 4 步是核心**：如果返回 `false` 且**立即**（不是等 5 分钟），说明级联失效生效了。

📌 **如果拿不到 `false`**，可能是：
- 单进程部署（standalone），广播发给自己但 `DelLocal` 已经被 `Del` 做过了
- 依赖关系还没建立（第一次查 `IS_FRIEND` 时 `FRIEND_IDS` 没被读过）

### 🧪 实验 24-3：看缓存分层带来的延迟差异

```bash
# 冷启动后第一次请求（走 L3 Mongo）
time curl -s -X POST "http://127.0.0.1:10002/user/get_users_info" ... > /dev/null

# 第二次（走 L1）
time curl -s -X POST "http://127.0.0.1:10002/user/get_users_info" ... > /dev/null
```

**注意**：HTTP 的 overhead（TCP、gRPC、序列化）会淹没 L1 vs L2 的差异。所以这个方法**测不出本地缓存的优势**——只能测出「有缓存 vs 没缓存」的差异。

真要测 L1 的收益，得用压测工具（wrk/vegeta）打高并发，看 P99 延迟和 Redis 的 QPS。

# 第五部分　面试话术

**问：你们为什么要做本地缓存？Redis 不够快吗？**

> 「Redis 够快，单机 10 万 QPS。但我们的问题是**读放大**——一条群消息进来要做 3-4 次校验（是否在群、群是否禁言、发送者是否禁言），推送时还要按扇出查每个接收者的会话设置。峰值 15 万次缓存查询/秒，这个量级下瓶颈不是 Redis 的 QPS，而是**网络往返**：每次 0.3ms，一条消息 4 次校验就是 1.2ms 纯网络开销。
> 本地 LRU 是 100ns，比 Redis 快 3000 倍，而且不占带宽。实测平均延迟从 770μs 降到 150μs。」

**追问：本地缓存不怕数据不一致吗？**

> 「怕，所以要有一套失效机制。我们的方案是三层：
> 第一层，写数据时先更 MongoDB，然后 `TagAsDeleted` 标记 Redis 失效——不是 `DEL`，是设置延迟过期，这样后续读请求会走『抢锁回源』而不是『读到旧值』。
> 第二层，同时 `PUBLISH` 到 Redis 的 channel，五个业务域五个 channel，其他节点收到后删自己的本地 L1。
> 第三层，TTL 兜底。本地缓存 5 分钟，Redis 12 小时。
> 所以是最终一致：正常情况窗口 1ms 左右，如果广播丢了（订阅者刚好重启），最长 5 分钟。我们没有做跨进程强一致，因为代价太大而收益很小。」

**追问：能讲讲那个缓存依赖图吗？**

> 「这是我们最精巧的一个设计。
> 问题是这样的：`IS_FRIEND:user2-user1` 这个缓存的值，完全由 `FRIEND_IDS:user1` 决定。删好友时要删 `FRIEND_IDS:user1`，但如果只删这一个，`IS_FRIEND` 还是 true，用户就会看到『不是好友但还能发消息』。
> 朴素解法是删好友时手动把所有相关的 `IS_FRIEND` 都删掉。但好友有 1000 个就得删 1000 次，而且 `IS_FRIEND` 是双向的，容易漏。
> 我们的做法是在**读取时建立依赖**：回源时调 `link.Link(IS_FRIEND_key, FRIEND_IDS_key)`，建一个**双向边**。双向是因为删除时要能反查『谁依赖我』。
> 然后删除时做一次图遍历：删 `FRIEND_IDS:user1`，顺着边找到所有 `IS_FRIEND:*`，一起删。用显式栈而不是递归，防止依赖链太长栈溢出，并且用 visited 集合防环。
> 这样『删好友→立刻不能发消息』的延迟从 TTL 的 5 分钟降到了微秒级。」

**追问：这个实现有什么问题吗？**

> 「有三个。
> 第一，`onEvict` 里级联删除用了 `go` 起新 goroutine。注释说得很清楚，是因为『底层 LRU 仍持锁时删除其他 key 会重入同一分片导致死锁』——Go 的 Mutex 不可重入。所以这个 `go` 是为了正确性不是为了性能。但代价是级联删除变成异步的，有一个微秒级的窗口。
> 第二，`WithTarget` 这个监控接口全项目零调用，所有指标都是 `EmptyTarget` 的空方法。所以**我们看不到本地缓存的命中率**。如果哪天 `slotSize` 配小了导致命中率暴跌，监控发现不了。
> 第三，`WithLocalDisable()` 的实现是错的——名字是禁用本地缓存，实际做的是 `WithLinkSlotNum(0)`，只禁用了依赖图。调用它反而更危险，因为缓存还在但没有级联失效了。目前零调用所以没炸。」
