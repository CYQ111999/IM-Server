# 第一部分　理论：聊天记录为什么长这样

## 1.1 先问一个蠢问题：聊天记录为什么不放 MySQL

你在 bluebell 里写过 `article` 表，一条记录一行，`id` 自增，查列表 `order by create_time desc limit 20`。看起来消息表也能这么干：

```sql
create table message (
  id bigint primary key auto_increment,
  conversation_id varchar(64),
  seq bigint,
  send_id varchar(64),
  content_type int,
  content text,
  send_time bigint,
  ...
);
```

这个设计能跑，但会在三个地方崩掉。

**第一，群聊的写放大。**

单聊一条消息，逻辑上是「一份」：A 发给 B，两个人看到同一份内容。群聊 500 人，一条消息还是「一份」——所有人看到的是同一条。

但如果按「每人一行」建模（很多早期 IM 就是这么做的，为了做「每人独立的删除/已读状态」）：

```
一条群消息 × 500 人 = 500 行
1 万条群消息 = 500 万行
```

这不是理论值。一个有 50 个 500 人群的租户，一天就能产生这个量级。写放大 500 倍，任何单机数据库都扛不住。所以**消息本体必须只存一份**，用户相关的状态（已读、删除）另想办法——这个「另想办法」就是本篇 1.5 节的核心。

**第二，行数没有上限，写入会越来越慢。**

B+ 树索引的写入成本随数据量增长而增长（树变高、页分裂、缓存命中率下降）。消息表是典型的「只追加、按时间递增」的写模式，数据量是无限增长的。MySQL 单表过亿之后，运维成本和查询延迟都会变成工程负担，必须分库分表——而分库分表之后，「按会话查最近 20 条」这个最简单的查询都要处理跨分片聚合。

**第三，消息的 payload 是变长的、多形态的。**

文本消息的 `content` 是 `{"text":"hi"}`；图片消息是 `{"sourcePicture":{"url":...,"width":...}}`；合并转发是一整棵消息树；自定义消息可能是任意的 JSON。放关系表里就是一堆 `text` 字段 + 业务层自己解析，等于放弃了 schema 带来的所有好处，只剩下一堆不适用的约束。

> **一句话结论**：消息是「写多读少、只追加、结构松散、按会话聚合」的数据，它天然不适合强 schema、强事务、单机容量有限的关系库。

**那为什么是 MongoDB？**

三个原因：

1. **文档模型**：一条消息在 BSON 里就是一个嵌套对象，`content` 想怎么嵌就怎么嵌，不需要 schema 迁移。
2. **水平扩展是原生的**：分片键（shard key）一设，MongoDB 自己负责数据分布，不需要业务层写分片路由。
3. **写性能**：WiredTiger 引擎是 B+ 树 + 文档级并发控制，但它的写是「先写 journal 再刷盘」，且支持无索引的集合（消息集合的索引可以做到极少），追加写的吞吐很好。

⚠️ **易错**：不要说「MongoDB 比 MySQL 快」。这是错的。MongoDB 在**特定负载**（无事务、松散结构、追加写、水平扩展）下更合适；在有复杂 join、强事务、多条件组合查询的场景，MySQL 反而更好。面试时说「快」会被追问「为什么快、快多少、什么场景下更慢」，答不上来就是背的。

## 1.2 一条消息一个文档？—— 会死得很惨

选定了 MongoDB，下一个问题是：**文档粒度**。

最直觉的方案是「一条消息一个文档」：

```json
// collection: msg
{ "_id": ObjectId, "conversation_id": "si_A_B", "seq": 10086, "content": {...}, ... }
```

看起来非常干净。问题在于：

**① 文档数量爆炸。** 一条会话 10 万条消息 = 10 万个文档。一个中等规模的 IM 几百万用户，消息文档数直接上十亿。MongoDB 能存，但**索引会大到装不进内存**。

**② 范围查询要扫多个文档。** 「拉 seq 10001~10020 这 20 条」需要 `find({conversation_id, seq: {$gte:10001,$lte:10020}})`，即使有复合索引，也是一次索引扫描 + 20 次文档读取（回表）。看起来不多，但这是**每条消息一次 BSON 解析**。

**③ 每个文档都有固定开销。** BSON 文档有 header、字段名会重复存储（`conversation_id`、`seq`、`send_id` 这些 key 在每个文档里都写一遍）。一条 200 字节的消息，存储开销可能要 300~400 字节。

那反过来，**一条会话一个文档**呢？

```json
{ "conversation_id": "si_A_B", "msgs": [ {seq:1,...}, {seq:2,...}, ..., {seq:1000000,...} ] }
```

更糟：

- **BSON 单文档上限 16MB**。一条消息平均 300 字节，5 万条就爆了。活跃群一天就能超。
- **更新是整文档重写**。WiredTiger 虽然有文档内的原地更新优化，但数组追加导致文档增长时仍要重新分配空间；文档越大，写放大越严重。
- **读一条要拉整个文档**。你只想看 seq 10086，却要把 100 万条消息反序列化。

> 这就是所有时序/日志类存储的共同问题：**粒度太细，索引和元数据开销压垮你；粒度太粗，单条读写的放大倍数压垮你**。

## 1.3 分桶（Bucket Pattern）：100 条一个文档

MongoDB 官方文档里把这个叫 **Bucket Pattern**（分桶模式），时序数据库（InfluxDB、TimescaleDB）里叫 chunk / partition。思路是一样的：

> 把「连续的一段」数据装进同一个容器，容器的编号可以由数据的序号**直接算出来**，不需要查索引。

OpenIM 的选择是 **100 条消息一个文档**：

```
docID = conversationID + ":" + docIndex
docIndex = (seq - 1) / 100
arrayIndex = (seq - 1) % 100
```

具体到 `conversation_id = "si_A_B"`：

| seq 范围 | docID | 数组下标 |
|---|---|---|
| 1 ~ 100 | `si_A_B:0` | 0 ~ 99 |
| 101 ~ 200 | `si_A_B:1` | 0 ~ 99 |
| 10001 ~ 10100 | `si_A_B:100` | 0 ~ 99 |

于是「读 seq 10086」变成：

1. `docIndex = (10086-1)/100 = 100`，`arrayIndex = (10086-1)%100 = 85`
2. 按 `doc_id = "si_A_B:100"` 查一个文档
3. 取 `msgs[85]`

**这是一次主键等值查询 + 一次数组下标访问**，没有范围扫描，没有排序，没有回表。

### 为什么是 100 而不是 1000

这是个纯工程权衡，没有标准答案，但可以算：

| 单文档条数 | 文档大小（按 300B/条估算） | 一个 20 条的分页请求要读几个文档 | 单文档更新成本 |
|---|---|---|---|
| 10 | 3KB | 2~3 | 低 |
| **100** | **30KB** | **1（偶尔 2）** | **中** |
| 1000 | 300KB | 1 | 高（整文档刷盘更贵） |
| 10000 | 3MB | 1 | 很高（接近 16MB 上限） |

100 的妙处在于：**它刚好比一次典型分页的条数（20~50）大，所以绝大多数读取只碰一个文档；同时 30KB 的文档在 WiredTiger 的 page（默认 4KB 压缩块）里还能被高效处理**。

⚠️ **易错**：不要把 100 当成「性能最优解」来背。它是「读放大」和「写放大」的折中点，而且**这个值写死成了常量**（`model/msg.go:11`），改它会导致历史数据全部错位——这点在 13.9 的可改进表里会再提。

### 分桶的代价（必须一起讲）

1. **空洞**：seq 是号段分配的（12 篇），如果某段号只用了 30 个，数组 31~100 就是 `null`。所以数组长度必须一开始就按 100 分配，读出来要能处理 `nil`。
2. **跨文档**：拉 20 条如果正好横跨两个文档，就要读两次。代码里用 `GetDocIDSeqsMap` 先按 docID 分组，就是为了把 N 次读合并成「每个文档一次读」。
3. **不能按内容查**：`msgs` 是数组，想在数组里做复杂条件查询会退化成全文档扫描。所以「搜索消息」在 OpenIM 里是另一套逻辑（`SearchMessage`，走 `$unwind` + 额外索引），不是主链路。
4. **改条数等于改数据格式**：上面说的常量写死问题。

## 1.4 位置寻址 vs 内容索引

这一节要讲清一个容易被忽略的设计哲学差异。

**内容索引**（MySQL / ES 的常规做法）：

```sql
select * from message where conversation_id = ? and seq > ? order by seq limit 20
```

数据库需要：找到索引 → 定位起始位置 → 顺序扫 20 条 → 回表取内容。**你告诉数据库「我要什么」，它自己决定「怎么找」。**

**位置寻址**（OpenIM 的做法）：

```
我要 si_A_B:100 这个文档的 msgs[85]
```

**你直接告诉存储「东西在哪」。**

位置寻址的前提是：**编号必须稠密、连续、由服务端分配**。如果 seq 有大量空洞（比如用时间戳），`(seq-1)/100` 算出来的下标就没有意义，整个模型崩溃。

> 这就是 12 篇要费那么大劲做号段分配器的根本原因——**它不是为了「排序好看」，而是为了「让存储可以用算术定位」**。

在面试里这是个很值钱的因果链：

```
seq 稠密 → 可以用除法算文档下标 → 可以位置寻址 → 不需要范围索引 → 单次等值查询
```

反过来，如果 seq 不稠密，你就必须建 `{conversation_id:1, seq:1}` 复合索引，每次读都是索引扫描。

## 1.5 读时改写：一份数据，N 种视角

现在到了本篇最难的理论点。

同一条群消息，对不同的人有不同的「样子」：

| 视角 | A（发送者） | B（已读的人） | C（删了这条的人） | D（后来被踢出群的人） |
|---|---|---|---|---|
| 内容 | 原文 | 原文 | **看不到** | 原文（但可能超出售权范围） |
| 已读标记 | 无意义 | 已读 | — | — |
| 撤回后 | 撤回提示 | 撤回提示 | — | 撤回提示 |

如果按「写时物化」（write-time materialization）来做，就是每个视角存一份：

```
一条群消息 × 500 人 = 500 份
```

这就是 1.1 节说的写放大 500 倍，直接出局。

所以只能「读时改写」（read-time projection）：

> **存一份「事实」，另存极少量「谁对它做了什么」的标签；读的时候拿「事实 + 标签 + 当前用户」现场算出该用户看到的视图。**

OpenIM 的标签只有三类：

| 标签 | 存储字段 | 语义 | 谁写 |
|---|---|---|---|
| 谁删了 | `del_list: []string` | 这个数组里的 userID 看不到内容 | 用户删除消息时 `$addToSet` |
| 被撤回了 | `revoke: {role,user_id,nickname,time}` | 整条消息变成撤回提示（对所有人） | 撤回时 `$set` |
| 谁读过 | `is_read: bool` | **单聊专用**，标记「对方已读」 | 已读时 `$set`（14 篇细讲） |

读的时候分三步：

```
第一步：拿到原始 msg
第二步：if userID ∈ del_list  → content 清空、status = 已删除
第三步：if revoke != nil      → contentType 改成「撤回通知」、content 换成撤回提示 JSON
```

**这就是「读时改写」的全部内容。**理解它，13 篇后半和 14 篇的已读都能串起来。

### 读时改写的代价

1. **读放大**：每次读都要做判断和可能的 JSON 重写。100 条消息 = 100 次判断，还好；但如果每次都要查库（比如引用消息要查被引用的那条），就贵了——所以代码里用了一个 `cache map[int64][]*MsgInfoModel` 在批内去重（13.6 节）。
2. **逻辑重复**：因为读有两条路径（缓存命中 / 缓存未命中），改写逻辑要在两个地方都做一遍。**这是真实存在的重复代码**，本篇 13.5 节会给对比。
3. **状态无界增长**：`del_list` 只增不减。理论上一个 500 人群，如果所有人都删了同一条消息，就是 500 个字符串塞在一个消息对象里。📌 本项目没有清理机制。

## 1.6 三种「删除」：语义完全不同

IM 里的「删除」至少有三种，混淆了就会写出灾难性的功能：

| 类型 | 触发 | 存储动作 | 影响范围 | 可恢复 |
|---|---|---|---|---|
| **软删除（按人）** | 用户长按「删除」 | `del_list` 加一个 userID | 仅自己 | 理论上可（从数组里移除） |
| **区间清除（按人）** | 「清空聊天记录」 | 抬高该用户的 `userMinSeq` | 仅自己，整个会话 | 否（水位已抬） |
| **物理删除（全局）** | 管理员清理 / 合规要求 | 删整个文档 or 删数组元素 | 所有人 | **否，真删了** |

注意第二种和第一种的本质区别：

- 软删除是**消息级**的，成本 O(1)（一次 `$addToSet`），但状态条目数 = 删除次数。
- 区间清除是**区间级**的，成本 O(1)（写一个水位数字），但**它不删任何消息数据**，只是让这个用户查不到 seq ≤ 水位的消息。

**为什么「清空聊天记录」必须用区间而不是逐条标记？** 一个 10 万条消息的会话，逐条标记要 10 万次写入。用一个水位数字，1 次写入。**这就是「用区间表达批量操作」的威力**——而且这也是 12 篇强调「seq 必须稠密」的第二个理由：**不稠密的序号没法用区间表达**。

## 1.7 缓存：消息该不该缓存、以什么粒度缓存

消息是「最近的最热、越旧越冷」的典型长尾分布，非常适合缓存。但粒度选错会出问题：

| 粒度 | 命中率 | 单次读写大小 | 失效难度 |
|---|---|---|---|
| 按会话 | 高 | 整个会话（不可行，太大） | 简单 |
| **按 seq 单条** | 中（只缓存热门消息） | 小 | **简单：删这一个 key** |
| 按文档（100 条） | 高 | 30KB | 中：一条消息变更要失效整个文档 |

OpenIM 选的是**按 seq 单条**（`GetMsgCacheKey(conversationID, seq)`）。理由：

- 撤回、删除、已读都只影响**单条消息**，按条失效最精确。如果按文档缓存，撤回一条就要删掉 100 条消息的缓存。
- 消息一旦写入就基本不变（不可变数据），缓存穿透的风险低。所以不需要复杂的一致性协议，只需要「变更时删缓存」。

但按条缓存有个后果：**读 20 条要发 20 次 Redis 请求**。所以实现里一定会用 pipeline 或批量接口（`batchGetCache2`）。

另外一个工程细节：缓存层还做了**防击穿**（rockscache，本质是「缓存未命中时加分布式锁，只让一个请求回源」）。这个在 Part5 会细讲，本篇只需要知道它存在。

## 1.8 本篇理论小结

把上面的推理链收成一张图：

```
聊天记录：写多、只追加、结构松散、按会话聚合、无上限增长
   ↓ 所以不用关系库
MongoDB 文档模型
   ↓ 但「一条一文档」索引爆炸、「一会话一文档」超 16MB
分桶：100 条/文档
   ↓ 但桶的定位必须能算出来，不能查索引
seq 必须稠密 → docIndex = (seq-1)/100（位置寻址）
   ↓ 但一条消息有 N 个视角，不能物化 N 份
读时改写：存 1 份 + del_list / revoke / is_read 三个标签
   ↓ 但读很频繁，改写要快
按 seq 单条缓存 + 批量读 + 防击穿
   ↓ 但删除有三种语义
软删除（del_list）/ 区间清除（minSeq 水位）/ 物理删除（管理员）
```

**如果你只能记住一句话**：这套存储模型的所有奇怪之处，都是「为了一次等值查询拿到一串连续消息」这个目标换来的。

## 2.2 位置寻址：四个纯函数

📂 `pkg/common/storage/model/msg.go:94-144`

自己验算一遍（🧪 强烈建议拿纸笔算）：

seq = 100  → docIndex 0,  arrayIndex 99  → "si_A_B:0"   msgs[99]
seq = 101  → docIndex 1,  arrayIndex 0   → "si_A_B:1"   msgs[0]

## 2.3 写入：先 update 后 insert 的幂等状态机

📂 `pkg/common/storage/controller/msg.go:120-220`

这是整个存储层最烧脑的一段。先看它要解决什么问题：

> Kafka 是 at-least-once 的（11 篇）。同一批消息可能被消费两次。所以「写入消息」这个操作**必须幂等**：写两次和写一次结果一样。

OpenIM 的做法不是用唯一索引（消息在数组里，没法建唯一索引），而是：

> **先尝试 update 已存在的位置；如果 update 没匹配到（说明这个位置还是空的），就插入整个新文档；插入时如果撞了 duplicate key，说明别人抢先插了，退回 update 模式。**

伪代码：

```go
tryUpdate := true                      // 当前块是否优先尝试 update
for i := 0; i < len(fields); i++ {
    seq := firstSeq + int64(i)

    if tryUpdate {
        matched := UpdateMsg(docID, index, "msg", field)   // $set msgs.i.msg
        if matched { continue }        // 位置已有数据 → 幂等命中，跳过
    }

    // 位置为空 → 构造新文档，把从 i 开始、属于同一个 docID 的所有消息都塞进去
    doc := MsgDocModel{DocID: ..., Msg: make([]*MsgInfoModel, 100)}
    insert := 0
    for j := i; j < len(fields); j++ {
        if GetDocID(conversationID, firstSeq+j) != doc.DocID { break }
        doc.Msg[GetMsgIndex(firstSeq+j)] = &MsgInfoModel{Msg: fields[j]}
        insert++
    }
    // 补齐 nil 元素（保证数组长度 100，且每个元素的 del_list 是 [] 而不是 null）
    for i, msgInfo := range doc.Msg { if msgInfo == nil { doc.Msg[i] = &MsgInfoModel{} } ... }

    if err := Create(ctx, &doc); err != nil {
        if mongo.IsDuplicateKeyError(err) {
            i--                 // 退回上一个位置
            tryUpdate = true    // 说明有并发的插入者，后续全部改用 update
            continue
        }
        return err
    }
    tryUpdate = false
    i += insert - 1             // 跳过已经插进去的这一段
}
```

🔴 **重点**：`tryUpdate` 这个布尔值的语义是「**乐观假设这个块已经存在**」。第一次是 true，一旦成功插入一个块就变成 false——因为同一批消息后面的块都是新的，没必要再花一次 update 的往返。

🟡 **难点**：为什么插入时要**一次性构造整个文档**（把 i 到该 doc 末尾的所有消息都放进去），而不是一条一条插？

因为 MongoDB 的数组是**位置敏感**的。如果你先插 `msgs[0]`，再想插 `msgs[5]`，MongoDB 无法「跳过中间」——用 `$set msgs.5` 时如果数组长度只有 1，会报错或者创建嵌套结构。**唯一正确的做法是整文档插入，一次把数组填充到位。**

所以代码里那个内层 `for j` 循环，是在**把这一批里属于同一个文档的消息全部收集起来**，然后一次 `Create`。

再看开头那段参数校验（`msg.go:126-143`）：

```go
case updateKeyMsg:
	msg, ok = field.(*model.MsgDataModel)
	if msg != nil && msg.Seq != firstSeq+int64(i) {
		return errs.ErrInternalServer.WrapMsg("seq is invalid")
	}
```

**这一行是号段分配的守卫**：它要求传进来的消息 seq 必须从 `firstSeq` 开始严格连续。如果 12 篇的分配器出了 bug（分配了不连续的号），这里会立刻报错，而不是默默把消息写到错误的位置。

📂 `pkg/common/storage/database/mgo/msg.go:43-73`

```go

	field := fmt.Sprintf("msgs.%d.%s", index, key)      // 例如 "msgs.85.msg"

	update := bson.M{"$set": bson.M{field: value}}

}

// msg.go:59-73  往数组里加元素（去重）

	update := bson.M{"$addToSet": bson.M{field: bson.M{"$each": value}}}
	...
}
```

三个动作覆盖了所有写场景：

| 动作 | 用在 | 关键点 |
|---|---|---|
| `Create` | 新消息写入 | 整文档，数组必须一次填满 |
| `UpdateMsg` + `$set` | 消息本体、撤回 | `res.MatchedCount` 是幂等判据 |
| `PushUnique` + `$addToSet` | `del_list` | **去重**，同一个人删两次不会重复 |

⚠️ **易错**：`$addToSet` 只保证「同一文档内不重复」，不保证并发安全下的**顺序**，但这里不需要顺序。

```

**为什么要写两遍？**

因为读路径有两条：

```
GetMessageBySeqs (controller)
    → msgCache.GetMessageBySeqs
        → [命中] 直接返回缓存里的 MsgInfoModel   ← 没经过 mgo，没做改写！
        → [未命中] FindSeqs → getMsgBySeqIndexIn1Doc（做了改写）

⚠️ **易错**：缓存里存的是**原始数据**（`SetMessageBySeqs` 存的是写入时的 `MsgInfoModel`），不带任何用户视角。所以**每次读都必须重新做改写**，这正是「读时改写」的必然代价。

> 🎯 **这是本篇最值得在面试里讲的一个点**：「缓存层引入之后，读时改写的逻辑必须在缓存之外再做一次，否则缓存命中会漏改写。代价是同一段逻辑有两份实现，改一处漏一处就是 bug。」这句话能同时证明你懂缓存、懂读时改写、还懂代码腐化。

## 2.8 未命中占位：让客户端知道「这里有洞」

```go

	if err := authverify.CheckAdmin(ctx); err != nil { return nil, err }    // 只有管理员
	docs, _ := m.MsgDatabase.GetRandBeforeMsg(ctx, req.Timestamp, int(req.Limit))   // 按时间随机采样
	for i, doc := range docs {
		m.MsgDatabase.DeleteDoc(ctx, doc.DocID)         // 删整个文档（100 条）
		// 从 docID 里解析 conversationID
		index := strings.LastIndex(doc.DocID, ":")
		conversationID := doc.DocID[:index]
		var minSeq int64
		for _, model := range doc.Msg {
			if model.Msg != nil && model.Msg.Seq > minSeq {
				minSeq = model.Msg.Seq        // ⚠️ 变量名叫 minSeq，其实是这个文档里的 maxSeq
			}
		}
		m.MsgDatabase.SetMinSeq(ctx, conversationID, minSeq+1)   // 抬全局水位
	}
	return &msg.DestructMsgsResp{Count: int32(len(docs))}, nil
}
```

这段代码有三个值得注意的地方：

1. **按时间随机采样删除**（`GetRandBeforeMsg`），不是「删最早 N 条」。这是为了分散 IO 压力，避免每次都删同一个会话的同一个文档。
2. **删文档后必须抬 minSeq**，否则用户请求 seq 1~100 会拿到空文档，客户端不知道是"还没加载"还是"已经删了"。
3. ⚠️ **代码里的变量名有误导**：`minSeq` 实际存的是该文档内最大的 seq，最后 `SetMinSeq(minSeq+1)` 才对。这种「变量名与语义相反」的坑，读代码时一定要用数值代入验证。

# 第三部分　实验

## 🧪 实验 1：看一眼真实的文档长什么样

```bash
# 进 mongosh（容器名以 docker ps 为准，端口 37017）
docker exec -it $(docker ps --format '{{.Names}}' | grep mongo) mongosh -u openIM -p <见凭据> --authenticationDatabase admin im_v3

# 找任意一个文档
db.msg.findOne({}, {doc_id:1, "msgs": {$slice: 2}})

# 只 doc_id 分布，确认每个会话每 100 条一个文档
db.msg.aggregate([
  {$group: {_id: {$substrCP: ["$doc_id", 0, {$subtract: [{$strLenCP: "$doc_id"}, {$strLenCP: {$arrayElemAt: [{$split: ["$doc_id", ":"]}, -1]}}]}]}, n: {$sum: 1}}},
  {$limit: 10}
])

# 看 msgs 数组长度是不是 100（含 null）
db.msg.findOne({}, {len: {$size: "$msgs"}})
```

**预期**：`len` 恒为 100（即使会话只有 3 条消息，数组也是 100 个元素，97 个是 `{ del_list: [] }`）。

## 🧪 实验 2：验证「删一条消息」后的存储变化

1. 用两个测试账号发一条消息，记下 seq。
2. 用其中一个账号调用删除接口（`/msg/delete_msgs`，`deleteSyncOpt` 不传或 `isSyncOther=false`）。
3. 再查 Mongo：

```js
db.msg.findOne({"doc_id": "si_<A>_<B>:0"}, {"msgs." + (seq-1) + ".del_list": 1})
// 预期：{ msgs: [ { del_list: [ "<删除者的userID>" ] } ] }
```

4. 再调同一条删除接口一次，再次查询 → `del_list` **长度不变**（验证 `$addToSet` 去重）。

## 🧪 实验 3：验证「清空聊天记录」不删数据

1. 记下清空前 `db.msg.countDocuments({doc_id: /^si_<A>_<B>:/})`。
2. 调 `/msg/clear_conversations_msg`。
3. 再 count 一次 → **数量不变**。
4. 查该用户的 minSeq：

```bash
redis-cli -p 16379 -a <密码> --scan --pattern "*seq*user*min*" | head
# 或直接查 Redis 里该用户的 minSeq key（key 前缀见 cachekey 包）
```

**结论**：清空 = 抬水位，数据一条没删。这也解释了为什么「清空后存储不下降」——**要释放空间必须用管理员的物理删除接口**。

## 🧪 实验 4：观察读时改写

1. 发一条消息，另一个账号撤回它。
2. 用 `pull_msg_by_seqs` 拉这条消息，观察返回的 `contentType` 变成了撤回通知，`content` 是两层 JSON。
3. 直接查 Mongo 看原始数据 → **`msg.content` 还是原文，只有 `revoke` 子文档被写入**。

**这就是「读时改写」最直观的证据：库里的原文没动，是读的时候算出来的。**

## 面试话术（90 秒版）

> 「我们的消息存储用的是 MongoDB 的分桶模型，100 条消息一个文档。为什么不用一条一文档？因为一条会话十万条消息就是十万文档，索引会大到装不进内存，而且范围查询每条都要回表解析 BSON。也不能一会话一文档，BSON 单文档有 16MB 上限，活跃群一天就满了。
>
> 分桶之后，文档定位是纯算术的：`docIndex = (seq-1)/100`，`arrayIndex = (seq-1)%100`，不需要范围索引，一次等值查询加一次 `$arrayElemAt` 就拿到。这也倒逼我们前面必须有一个序号分配器保证 seq 稠密连续。
>
> 一条消息有 N 个用户的视角，但我们只存一份，用三个标签做到：`del_list` 数组存谁删了、`revoke` 子文档存撤回、`is_read` 存单聊已读。读的时候根据当前 userID 现场改写——这叫读时改写。代价是读放大，而且因为加了缓存层，改写逻辑必须在缓存外面再做一遍，否则缓存命中会漏改写，这也是我们代码里确实有两份重复实现的地方。
>
> 删除分三种：按人软删除是 `del_list` 加一个 ID；清空会话是抬高这个用户的 minSeq 水位，一条数据都不删，所以成本是 O(1)；管理员的物理删除才是真删文档，删完还要抬全局 minSeq，否则客户端会拿到空文档不知道是没加载还是已删除。」

## 预判追问

| 追问 | 怎么答 |
|---|---|
| 100 这个数字怎么定的？ | 权衡：要大于典型分页条数（20~50）保证一次命中，又要小于让单文档控制在几十 KB。**并且我强调它是编译期常量、上线后不可改**，这是这个设计的硬伤 |
| 消息要不要做冷热分离？ | 要做。当前实现只有 Redis 24 小时缓存 + Mongo 冷存，没有归档层。生产上会按时间把老文档迁到对象存储/冷库，Redis 只缓存活跃会话 |
| 为什么不用 Cassandra / HBase / TiKV？ | 都能做，本质都是宽表 + 顺序写。选 Mongo 主要是生态和运维成本，另外分桶模型在 Mongo 里实现最自然（原生数组 + 文档级原子更新） |
| Redis 缓存和 Mongo 不一致怎么办？ | 写路径是「先写库再删缓存」，读路径是「缓存未命中回源」，属于 Cache-Aside。因为消息是不可变数据（写入后只会有 revoke/del_list 这种局部变更），不一致窗口很小，且删除是幂等的 |
| 你们怎么保证消息不丢？ | 这里要接 11 篇的答案：批处理完才提交 Kafka 位点 + Mongo 写入幂等（先 update 后 insert）。**但我在代码里发现 batcher 的 `Do` 没有返回值，业务失败无法感知**，这是一个真实的可改进点 |

## 本篇小结

| 你该记住的 | 一句话 |
|---|---|
| 为什么是 Mongo | 写多读少、结构松散、需要水平扩展，不是「因为快」 |
| 为什么分桶 100 | 一条一文档索引爆炸，一会话一文档超 16MB |
| 位置寻址 | `(seq-1)/100` 和 `%100`，一次等值查询拿到连续消息 |
| 读时改写 | 存 1 份 + del_list/revoke/is_read，读时按 userID 现场算 |
| 三种删除 | 软删除（消息级）/ 区间清除（水位）/ 物理删除（真删） |
| 缓存约定 | 按 seq 单条缓存，**写库必删缓存** |
| 最大硬伤 | 100 是编译期常量，上线后不能改 |
