# 第一部分　理论：推送是「无状态服务 + 有状态连接」的缝合处

## 1.1 先分清两个「推送」

中文都叫推送，实际是两条完全不同的链路：

| | 在线推送 | 离线推送 |
|---|---|---|
| 通道 | 你自己的 WebSocket 长连接 | 手机厂商的通道（APNs/FCM/华为/小米…） |
| 谁执行 | 你的网关进程 | 厂商的服务器 |
| 凭据 | 连接句柄（内存里的对象） | 设备 token（注册到厂商） |
| 延迟 | 10~100ms | 100ms~数秒 |
| 可靠性 | 尽力而为（连接可能已半死） | 厂商保证送达（但不保证及时） |
| 成本 | 你自己的机器 | 按条计费 / 有配额 |

**分界线**：**用户有没有一条「活着的、能立刻写数据」的长连接**。

但这条线比想象中模糊，因为「连接活着」有三种含义：

1. TCP 连接存在（内核层面）
2. WebSocket 握手完成、服务端有连接对象
3. **用户真的能被打扰**（App 在前台 / 手机没静音 / 用户没在开会）

第 1、2 条是技术问题，第 3 条是产品问题。**推送系统最容易犯的错，就是用第 2 条代替第 3 条**——PC 客户端挂在后台，连接活得好好的，消息推过去写入成功，于是系统认为"已送达"，不触发离线推送。用户手机上是收不到任何提醒的。

OpenIM 用 `pushTerminal` 这个白名单来解决（见 1.5）。

## 1.2 长连接的路由问题：用户连在哪台机器上

单机时代，这个问题不存在：所有连接都在一个进程的内存 map 里，`map[userID][]*Conn` 一查就有。

多网关节点之后，问题来了：

```
消息 → push 服务 → ？哪个网关节点持有 userID 的连接
```

三种解法：

| 方案 | 做法 | 代价 |
|---|---|---|
| **广播** | 推给所有网关，每个网关查自己的连接表，没有就返回空 | 网关数 × RPC 次数；但实现最简单、无状态 |
| **全局路由表** | Redis 里记 `userID → gatewayAddr` | 表要维护；网关 crash 后残留脏数据；连接迁移要双写 |
| **一致性哈希** | 按 userID 哈希固定到某个网关（客户端连的时候就路由过去） | 需要 LB 配合（如 Envoy ring hash）；扩缩容时连接大量迁移 |

OpenIM 主路径用**广播**（`DefaultAllNode`，`onlinepusher.go:67-120`）：

```go
conns, _ := d.disCov.GetConns(ctx, MessageGateway)      // 拿全部网关地址
for _, conn := range conns {
	wg.Go(func() error {
		reply, _ := msgClient.SuperGroupOnlineBatchPushOneMsg(ctx, input)   // 每个网关都问一遍
		...
	})
}
```

另外还实现了一个 `K8sStaticConsistentHash`（`onlinepusher.go:141-204`），用 `GetUserIdHashGatewayHost` 做哈希路由——但 `NewOnlinePusher` 里并没有用它（`onlinepusher.go:43-56` 三种分支都返回 `DefaultAllNode`）。

📌 **待验证**：`K8sStaticConsistentHash` 是**死代码**（构造了但从未被选用）。这属于瘦身时该清理的项。

**为什么广播能接受？**

因为网关数量是有上限的（一般 3~20 个），而每个网关处理一次"查本地连接表"是 O(1)，没有 IO。相比之下，维护全局路由表的复杂度（一致性、故障恢复、连接迁移）远高于多几次进程内 RPC。

**核心洞察**：**连接表是"有状态"的，所以必须放在网关本地；而网关本地的东西，别人只能靠"问一遍"来获得。** 这就是"广播"在架构上的必然性。

## 1.3 在线状态表：为什么不能用 SET 存一个布尔

最直觉的做法：

```
SET online:{userID} 1 EX 60
```

问题：

**① 只能整 key 过期，不能按端过期。**

一个用户可能同时在线：PC、iOS、Android、Web。iOS 退到后台了但 PC 还活着。如果用 `SET online:user 1`，你无法表达"iOS 离线但 PC 在线"。

**② 无法表达"什么时候过期"。**

用 key TTL 的话，每次心跳都要 `EXPIRE` 续期，而 Redis 的过期删除是**惰性 + 定期采样**的，`GET` 一个刚过期但还没被删的 key 仍会返回旧值（虽然概率低，但对"是否在线"这种判断是致命的）。

**③ 进程崩溃后的残留。**

网关被 `kill -9`，来不及清理任何东西。所有"在线"标记都留在 Redis 里。如果你只靠 TTL（比如 60 秒），那这 60 秒内所有用户都被认为是"在线但推不到"——**消息全部走在线推送失败，而离线推送没触发**。

**OpenIM 的方案：ZSET + score 作为过期时间戳。**

```
key    = online:{userID}
member = platformID        （1=iOS, 2=Android, 3=Windows, 4=OSX, 5=Web ...）
score  = 该平台连接应该过期的时间戳（秒）
```

读的时候：

```go
ZRangeByScore(key, min = now, max = +inf)     // 只取 score >= now 的成员
```

🔴 **重点**：**"过期"是在读的时候用 score 过滤出来的，不依赖 Redis 的 TTL 机制。**

好处：

1. **按平台粒度独立过期**：iOS 的 score 可以是 5 分钟前，PC 的是 30 秒后。
2. **崩溃残留自动失效**：网关挂了不再续期，score 到点后自动"读不到"，不需要任何清理任务。
3. **判断精确**：`ZRangeByScore(now, +inf)` 是**确定性的**，不会出现"key 已过期但读到旧值"的问题。

这个思路在分布式系统里很常见，叫 **lease（租约）**：不删除数据，只让数据"到期自动失效"，避免依赖任何清理动作。

## 1.4 心跳与续期：为什么续期间隔必须是过期时间的 1/3

如果在线状态的租约是 30 分钟（`cachekey.OnlineExpire = time.Hour / 2`），那网关必须**周期性地续期**，否则用户正常在线也会被判定为离线。

续期间隔怎么定？

```
续期间隔 T，租约 L。
如果 T >= L：两次续期之间一定有一段"已过期"的窗口 → 用户被误判离线。
如果 T = L/2：单次续期失败就会在 L/2 后过期 → 容错窗口只有 1 次。
如果 T = L/3：允许连续失败 2 次 → 容错 2 次网络抖动。
```

OpenIM 用的是 `L/3`：

```go
// msggateway/online.go:25
const renewalTime = cachekey.OnlineExpire / 3      // 30min / 3 = 10min
```

⚠️ **但这里有个反直觉的点**：10 分钟才续期一次，意味着**一个网关崩溃后，它的用户最长会有 30 分钟被误判为"在线"**（因为 score 还没到）。

这不是 bug，是**故意的权衡**：

- 租约短（比如 30 秒）→ 心跳频繁 → Redis 写压力大（10 万连接 / 30 秒 = 3333 QPS）
- 租约长（30 分钟）→ Redis 压力小 → 但崩溃后误判窗口长

对于「在线状态判断」这个场景，**误判为在线**的代价是可以接受的：在线推送失败之后，会走离线推送兜底（见 1.5）。而误判为离线代价更大（用户正常在线却收到厂商推送，重复打扰）。

## 1.5 什么算「在线推送成功」

这是本篇最容易做错的设计点。看代码里的判定（`hub_server.go:121-155`）：

```go
for _, client := range clients {                      // 该用户的所有连接（多端）
	userPlatform := &msggateway.SingleMsgToUserPlatform{RecvPlatFormID: int32(client.PlatformID)}

	if client.IsBackground && client.PlatformID == constant.IOSPlatformID {
		// iOS 在后台 → 直接判定为"需要离线推送"
		userPlatform.ResultCode = int64(servererrs.ErrIOSBackgroundPushErr.Code())
		result.Resp = append(result.Resp, userPlatform)
		continue
	}
	if err := client.PushMessage(ctx, msgData); err != nil {
		userPlatform.ResultCode = int64(servererrs.ErrPushMsgErr.Code())
	} else if _, ok := s.pushTerminal[client.PlatformID]; ok {
		result.OnlinePush = true                      // ← 只有白名单平台才算"推送成功"
	}
	result.Resp = append(result.Resp, userPlatform)
}
```

```go
// hub_server.go:83-84
s.pushTerminal[constant.IOSPlatformID] = struct{}{}
s.pushTerminal[constant.AndroidPlatformID] = struct{}{}
```

**两层判定**：

1. **iOS 后台**：即使连接活着、写入成功，也**不算送达**。因为 iOS 后台会冻结进程，长连接收不到数据（或者收到了也不会唤醒 UI）。必须走 APNs。
2. **平台白名单**：只有 iOS/Android 的写入成功才算 `OnlinePush = true`。PC/Web 在线不算——**因为人可能不在电脑前**。

🔴 **重点**：`pushTerminal` 这个名字容易误解，准确语义是「**哪些平台在线时，可以抑制离线推送**」。这个策略本质是产品决策，写在代码里（硬编码）而不是配置里，是它的缺陷。

**iOS 后台判定可信吗？**

`client.IsBackground` 是客户端在 WS 握手时通过 `isBackground` 参数上报的（你在 06 篇踩过的那个坑）。**客户端上报的值永远不可信**（可以伪造、可能滞后）。这是一个**已知的安全/正确性妥协**：恶意客户端可以谎报"我在前台"，从而让服务端抑制离线推送，导致自己收不到通知（只能自损，危害有限）。

## 1.6 群聊扇出：500 人怎么推

一条群消息要送到 500 个人。三种扇出模式：

| 模式 | 写时做什么 | 读时做什么 | 适合 |
|---|---|---|---|
| **写扩散（push）** | 给 500 人各写一份收件箱 | 只读自己的收件箱 | 小群、读多写少 |
| **读扩散（pull）** | 只写 1 份到群 | 每人读时合并所有群的收件箱 | 大群、写多 |
| **推拉结合** | 大群读扩散、小群写扩散 | 按阈值分流 | 大规模 IM（微信/钉钉） |

OpenIM 用的是**纯读扩散 + 在线扇出**：

- **存储**：一条群消息只存 1 份（13 篇）
- **推送**：push 服务拿到群成员列表，**在内存里扇出 500 个推送任务**

这就把"写放大"从存储层转移到了**推送层**，而推送层是可以用并发 + 限流削平的。

代价：离线成员也要逐个判断、逐个走离线推送。所以有 `filterGroupMessageOfflinePush`（`push_handler.go:348-355`）先过滤掉免打扰/拒收的用户。

## 1.7 离线推送的产业链

离线推送不是「你写个 HTTP 请求给手机」那么简单。现实是：

```
你的服务端
   ├─ iOS   → APNs（Apple）                    → 设备
   ├─ Android → FCM（Google，国内不可用）        → 设备
   │           ├─ 华为 HMS
   │           ├─ 小米 MiPush
   │           ├─ OPPO/vivo/荣耀 各自通道
   │           └─ 个推/极光（聚合商，帮你对接所有）
   └─ 每个通道都要：AppID + AppSecret + 设备 token + 证书/密钥
```

三个工程现实：

1. **token 要按「用户 × 平台」存**。同一个用户换手机、重装 App，token 都会变；旧 token 推送会返回 `Unregistered`，必须删除。
2. **token 有时效**。厂商一般给 30~90 天有效期，过期不推。
3. **需要聚合层**。真实项目不会自己对接 6 家厂商，而是接个推/极光，或者像 OpenIM 这样定义 `OfflinePusher` 接口，让使用者自己实现。

本仓库瘦身后只剩 `dummy` 实现（`internal/push/offlinepush/dummy/push.go`）：

```go
func (d *Dummy) Push(ctx context.Context, userIDs []string, title, content string, opts *options.Opts) error {
	if d.v.CompareAndSwap(false, true) {          // 只警告一次，不刷屏
		log.ZWarn(ctx, "dummy push", nil, "ps", "the offline push is not configured. ...")
	}
	return nil
}
```

**这是一个正确的瘦身决策**：保留接口 + 一个空实现，功能链路完整可跑（只是不发通知），需要时实现 `OfflinePusher` 即可。比删掉整个离线推送模块好得多——因为删了之后 `shouldPushOffline` 之后的整条链路都没法讲。

而推送 token 的存储还在（`pkg/common/storage/cache/redis/third.go:37-49`）：

```go
func (c *thirdCache) SetFcmToken(ctx, account string, platformID int, fcmToken string, expireTime int64) error
func (c *thirdCache) GetFcmToken(ctx, account string, platformID int) (string, error)
func (c *thirdCache) DelFcmToken(ctx, account string, platformID int) error
```

⚠️ **命名遗留**：全叫 `FcmToken`，但它存的其实是**任意厂商的 token**（华为、小米、APNs 都往这存）。这是从"只支持 FCM"演进到"多厂商"时没重命名的后果。面试时提到这一点，说明你注意到「命名与语义脱节」这种代码腐化。

## 1.8 时序问题：推送早于落库

这是 IM 里最经典的"幽灵消息"：

```
t0  发送方 → msg RPC → Kafka(toRedis)
t1  msgtransfer 消费 → 分配 seq → 写 Redis → 投 Kafka(toPush)  ← 推送在这条链上
t2  msgtransfer 消费 → 写 Mongo                                  ← 落库在这条链上
```

`toPush` 和 `toMongo` 是**两个独立的 topic**（11 篇），消费进度不同步。所以完全可能出现：

```
t1.5 对端收到推送，显示消息 seq=10088
t1.8 对端下拉/重连，去拉 seq=10088 的详情 → Mongo 里还没有 → 返回"消息已删除"占位
```

**OpenIM 怎么处理？**

代码里只做了**监控**，没有做修复（`push_handler.go:95-101`）：

```go
sec := msgFromMQ.MsgData.SendTime / 1000
nowSec := timeutil.GetCurrentTimestampBySecond()
if nowSec-sec > 10 {                                  // 消息从发出到推送超过 10 秒
	prommetrics.MsgLoneTimePushCounter.Inc()          // 指标：延迟推送计数
	log.ZWarn(ctx, "it's been a while since the message was sent", ...)
}
```

**为什么"超过 10 秒"就告警？** 因为正常情况下 t0→t1 只有几十毫秒。如果超过 10 秒，说明消费堆积了——**这时候 Mongo 落库更可能落后于推送**，幽灵消息的概率大增。所以这个指标本质是「幽灵消息风险指标」。

📌 **待验证/可改进**：真正的修复方案应该是「客户端收到推送后，如果拉不到详情，延迟 500ms 重试一次」。本项目把这件事完全交给客户端。

## 1.9 幂等与去重

推送是 **at-least-once**：

- Kafka 可能重复投递（消费者 rebalance、位点提交失败）
- 在线推送失败后走离线推送，用户可能两路都收到
- 用户在多个设备登录，每个设备都收到

所以客户端**必须去重**，依据是：

| ID | 作用 | 能否作为去重键 |
|---|---|---|
| `clientMsgID` | 客户端生成，同一设备重发时不变 | 可用于"我自己发的消息"去重 |
| `serverMsgID` | 服务端生成，全局唯一 | **推荐作为去重主键** |
| `seq` | 会话内递增 | 只能在同一会话内去重 |

**服务端不做去重**——这是正确的。服务端做去重需要存"已推送过的消息 ID"集合，成本高、TTL 难定。客户端做去重是 O(1) 的（本地已有 seq 集合）。

## 1.10 背压：推送层不能无限积压

推送的负载特征：**突发性极强**。一个 5000 人群里有人 @所有人，瞬间 5000 个推送任务。

如果没有背压，任务全部堆在内存里 → OOM → 进程挂 → 所有连接断 → 更大的雪崩。

OpenIM 在三个地方设了背压：

| 位置 | 机制 | 满了以后 |
|---|---|---|
| push 服务 | Kafka 消费者（`toPush`） | 不消费就不提交位点，消息留在 Kafka |
| 网关入口 | `MemoryQueue(512, 16384)`（512 worker + 16384 缓冲） | `PushCtx` **阻塞**直到有位置或 ctx 超时 |
| 网关内部 | 每连接一个 send channel | 客户端读得慢 → channel 满 → 写超时 → 断开该连接 |

🔴 **重点**：注意 `PushCtx` 是**阻塞**的（`memamq/queue.go:78-90`）：

```go
select {
case mq.taskChan <- task:  return nil
case <-ctx.Done():         return context.Cause(ctx)
}
```

这意味着**网关压力会反向传导到 push 服务**——push 服务调网关的 gRPC 变慢 → `errgroup` 的 goroutine 卡住 → `Push2Group` 变慢 → Kafka 消费变慢 → 消息堆在 Kafka。

**整条链路的最终蓄水池是 Kafka 的磁盘，不是内存。** 这就是 11 篇说的「背压链」的终点。

## 1.11 理论小结

```
推送 = 在线（自有长连接）+ 离线（厂商通道）
  ├─ 路由：广播给所有网关（连接表在网关本地）
  ├─ 在线状态：ZSET，score = 过期时间戳（租约），读时过滤
  ├─ 续期：L/3（容忍 2 次失败，代价是崩溃后 30 分钟误判）
  ├─ 送达判定：iOS 后台不算送达；只有 iOS/Android 在线才算（pushTerminal）
  ├─ 扇出：读扩散存储 + 推送层内存扇出（500 人 500 个任务）
  ├─ 削峰：Kafka + 网关内存队列 + 每连接 send channel，三级背压
  └─ 幂等：服务端不做，客户端按 serverMsgID 去重
```

```go
		fn := func(msg mq.Message) error {
			pushHandler.HandleMs2PsChat(authverify.WithTempAdmin(msg.Context()), msg.Value())
			return nil                          // ⚠️ 永远返回 nil，位点照常前进
		}
		consumerCtx := mcontext.SetOperationID(context.Background(), "push_"+strconv.Itoa(int(rand.Uint32())))
		for {
			if err := pushConsumer.Subscribe(consumerCtx, fn); err != nil {
				log.ZError(consumerCtx, "subscribe err", err)
				return                          // ⚠️ 出错直接退出，不重连
			}
		}
	}()

	// ---- 消费者 2：离线推送 ----
	go func() {
		fn := func(msg mq.Message) error {
			offlineHandler.HandleMsg2OfflinePush(msg.Context(), msg.Value())
			return nil
		}
		...
		for {
			if err := offlinePushConsumer.Subscribe(consumerCtx, fn); err != nil {
				log.ZError(consumerCtx, "subscribe err", err)
				return
			}
		}
	}()
	return nil
}
```

🔴 **重点 1：`WaitCache()`**。

push 服务需要在内存里知道"谁在线"。它靠订阅 Redis 的在线状态广播来维护本地缓存（2.6 节）。如果缓存还没加载完就开始消费消息，会把所有在线用户都判成离线 → **全部走离线推送**。

`WaitCache` 的实现（`rpccache/online.go:301-...`）用 `sync.Cond` 等一个状态机走到 `DoSubscribeOver`：

```go
func (o *defaultOnlineCache) WaitCache() {
	o.Lock.Lock()
	for o.CurrentPhase.Load() < DoSubscribeOver {
		o.Cond.Wait()
	}
}
```

这类「启动时先等缓存就绪」的模式，在推送/网关/消息转发的启动处都该有。**没有它就会出现"启动后前 3 秒的推送全错"这种极难排查的 bug。**

🔴 **重点 2：`WithTempAdmin`**。

```go
pushHandler.HandleMs2PsChat(authverify.WithTempAdmin(msg.Context()), msg.Value())
```

消费者上下文没有用户身份（它不是用户请求发起的），但下游要调 RPC（`CheckAccess` 会校验调用者身份）。所以这里塞一个"临时管理员"身份，让内部调用能通过鉴权。

⚠️ **注意**：`for { Subscribe }` 里 `return` 意味着**订阅出错就永久停止消费，不重连**。这和 11 篇 msgtransfer 里发现的 `for {}` 死代码是同一类问题（那边是 `cancel+return` 让 for 变死代码）。**同一个模块的两个消费者都是这个写法**，说明这是模板代码的复制，不是偶然。

## 2.3 Push2User：在线推完判断是否要离线

📂 `push_handler.go:127-179`

```go
func (c *ConsumerHandler) Push2User(ctx context.Context, userIDs []string, msg *sdkws.MsgData) (err error) {
	// ① webhook（可拦截）
	if err := c.webhookBeforeOnlinePush(ctx, &c.config.WebhooksConfig.BeforeOnlinePush, userIDs, msg); err != nil {
		return err
	}

	// ② 在线推送（真正的推送，含多端）
	wsResults, err := c.GetConnsAndOnlinePush(ctx, msg, userIDs)
	if err != nil { return err }

	// ③ 是否需要离线推送
	if !c.shouldPushOffline(ctx, msg) { return nil }

	for _, v := range wsResults {
		if msg.SendID == v.UserID { continue }        // 发送者不需要离线推送
		if v.OnlinePush { return nil }                // ⚠️ 接收方在线成功 → 直接 return
	}

	needOfflinePushUserID := []string{msg.RecvID}     // ⚠️ 忽略 userIDs，只用 RecvID
	var offlinePushUserID []string
	if err = c.webhookBeforeOfflinePush(ctx, &c.config.WebhooksConfig.BeforeOfflinePush,
		needOfflinePushUserID, msg, &offlinePushUserID); err != nil {
		return err
	}
	if len(offlinePushUserID) > 0 { needOfflinePushUserID = offlinePushUserID }

	err = c.offlinePushMsg(ctx, msg, needOfflinePushUserID)
	if err != nil {
		// ⚠️ 离线推送失败被吞掉，只记日志
		log.ZWarn(ctx, "offlinePushMsg failed", err, "needOfflinePushUserID length", len(needOfflinePushUserID), ...)
		return nil
	}
	return nil
}
```

这段代码有三个真实缺陷（都可写进"可改进"）：

**① `if v.OnlinePush { return nil }` 应该是 `continue`。**

`wsResults` 是**多端**的结果数组（iOS、Android、PC 各一条）。这个循环的本意是"只要有一端在线成功就不离线推送"，但用的是 `return`——一旦某个 v 命中就**直接结束整个函数**，后面即使还有"应该离线推送"的判断也被跳过。

实际上因为"只要有一端成功就不需要离线推送"这个语义本身是对的，`return` 在这里**功能上恰好等价**。但语义上是错的：如果未来要在后面加"发送者其他端同步"之类的逻辑，这个 `return` 会静默跳过。

**② `needOfflinePushUserID` 硬编码 `msg.RecvID`。**

入参 `userIDs` 可能是两个（`RecvID` + `SendID`），但离线推送只取 `RecvID`。这在单聊里是对的（发送者不需要离线推送），但**如果 `SendID == RecvID`（自己发给自己）或者未来单聊支持多接收方，就会出错**。

**③ 离线推送失败被吞。**

`offlinePushMsg` 失败后 `return nil`，只记了个 warn。消息已经落库了（13 篇），用户下次打开 App 能拉到，所以不算"消息丢失"——**但如果用户一直不打开 App，就永远收不到通知**。这就是"通知静默失败"，运维上很难发现（只能靠 `MsgOfflinePushFailedCounter` 指标）。

```go
func (c *ConsumerHandler) groupMessagesHandler(ctx context.Context, groupID string, pushToUserIDs *[]string, msg *sdkws.MsgData) (err error) {

		*pushToUserIDs, err = c.groupLocalCache.GetGroupMemberIDs(ctx, groupID)
		if err != nil { return err }

			var tips sdkws.MemberKickedTips
			unmarshalNotificationElem(msg.Content, &tips)
			kickedUsers := datautil.Slice(tips.KickedUserList, func(e *sdkws.GroupMemberFullInfo) string { return e.UserID })
			c.DeleteMemberAndSetConversationSeq(ctx, groupID, kickedUsers)
			*pushToUserIDs = append(*pushToUserIDs, kickedUsers...)

				defer func(groupID string) {
					if err := c.groupClient.DismissGroup(ctx, groupID, true); err != nil {
						log.ZError(ctx, "DismissGroup Notification clear members", err, ...)
					}
				}(groupID)
			}
		}
	}
	return err
}
```

🔴 **重点**：**为什么"退群/被踢"的用户要追加到推送名单里？**

因为 `GetGroupMemberIDs` 返回的是**当前**成员列表——退群的人已经不在里面了。但这条"你已退出群聊"的通知**必须推给他**，否则他客户端上的群还留着。

**为什么"解散群"要在推送阶段才调 `DismissGroup`？**

时序问题。如果解散群时立刻清空成员，那"群已解散"这条通知就推不出去了（没人收）。所以：

```
1. 发群解散通知（此时成员列表还在）
2. 推送阶段：先算出所有成员 → 推通知 → defer 里再真正 DismissGroup（清空成员）
```

**这是用 `defer` 实现「事后清理」的经典用法**：保证通知先发出去，再销毁数据。

代价：`DismissGroup` 失败只记日志，群成员数据残留。📌 可改进：应该加重试或落补偿任务。

## 2.7 网关侧：批量推送的实现

📂 `internal/msggateway/hub_server.go:157-206`

```go
func (s *Server) SuperGroupOnlineBatchPushOneMsg(ctx context.Context, req *msggateway.OnlineBatchPushOneMsgReq) (*msggateway.OnlineBatchPushOneMsgResp, error) {
	if len(req.PushToUserIDs) == 0 { return &msggateway.OnlineBatchPushOneMsgResp{}, nil }

	ch := make(chan *msggateway.SingleMsgToUserResults, len(req.PushToUserIDs))
	var count atomic.Int64
	count.Add(int64(len(req.PushToUserIDs)))

	for i := range req.PushToUserIDs {
		userID := req.PushToUserIDs[i]
		err := s.queue.PushCtx(ctx, func() {                     // 投内存队列（异步）
			ch <- s.pushToUser(ctx, userID, req.MsgData)
			if count.Add(-1) == 0 { close(ch) }                  // 最后一个人关 channel
		})
		if err != nil {                                          // 队列满/ctx 取消
			if count.Add(-1) == 0 { close(ch) }
			ch <- &msggateway.SingleMsgToUserResults{UserID: userID}   // 补空结果
		}
	}

	resp := &msggateway.OnlineBatchPushOneMsgResp{SinglePushResult: make([]*..., 0, len(req.PushToUserIDs))}
	for {
		select {
		case <-ctx.Done():
			// ctx 超时 → 把还没结果的人都补成"失败"
			userIDSet := datautil.SliceSet(req.PushToUserIDs)
			for _, results := range resp.SinglePushResult { delete(userIDSet, results.UserID) }
			for userID := range userIDSet {
				resp.SinglePushResult = append(resp.SinglePushResult, &...{UserID: userID})
			}
			return resp, nil
		case res, ok := <-ch:
			if !ok { return resp, nil }
			resp.SinglePushResult = append(resp.SinglePushResult, res)
		}
	}
}
```

🟡 **难点**：这段代码是典型的「**N 个任务 + 一个收集 channel + 原子计数关 channel**」模式。四个细节都做对了：

1. **channel 缓冲 = 用户数**，保证 worker 写入不会阻塞（不会出现"worker 卡住等收集者"）。
2. **`count` 初始化为总人数**，每完成一个 `Add(-1)`，减到 0 就 `close(ch)`。用 `atomic.Int64` 而不是 `sync.WaitGroup`，因为需要在**关闭 channel 的同一时刻**判断"是最后一个"。
3. **`ctx.Done()` 分支要补齐结果**：ctx 超时后，已经完成的结果在 `resp` 里，未完成的人要补成空结果，否则上层会以为"这些人推送成功了"（因为 `SliceSub` 找不到他们就当失败——实际上不会误判，但日志会缺人）。
4. **`PushCtx` 失败也要 `count.Add(-1)`**：否则 `count` 永远减不到 0，channel 永远不关闭，整个函数**死锁在 `<-ch`**。这个处理是对的。

⚠️ **`MemoryQueue` 的参数**（`hub_server.go:81`）：

```go
queue: memamq.NewMemoryQueue(512, 1024*16)
// NewMemoryQueue(workerCount int, bufferSize int)
// → 512 个 worker，channel 缓冲 16384 个任务
```

一个网关 10 万在线用户，群发一条消息 → 每个 worker 分到约 200 个用户。512 并发足够。

```go
		changeStatus[i] = make([]UserState, 0, 100)          // 每个请求最多 100 个用户状态
	}

	mergeTicker := time.NewTicker(time.Second)                // 每秒兜底 flush

	// ---- 分片函数：按 userID 的 md5 散列到 concurrent 个分片 ----
	pushUserState := func(us ...UserState) {
		for _, u := range us {
			sum := md5.Sum([]byte(u.UserID))
			i := (binary.BigEndian.Uint64(sum[:]) + rNum) % uint64(concurrent)   // rNum 是进程随机数
			changeStatus[i] = append(changeStatus[i], u)
			status := changeStatus[i]
			if len(status) == cap(status) {                  // 攒够 100 个 → 发一批
				req := &pbuser.SetUserOnlineStatusReq{Status: datautil.Slice(status, local2pb)}
				changeStatus[i] = status[:0]
				select {
				case requestChs[i] <- req:
				default:
					log.ZError(..., "user online processing is too slow", nil)   // 满了就丢
				}
			}
		}
	}

	// ---- 每秒兜底：把没攒满的也发出去 ----
	pushAllUserState := func() { ... }

	// ---- worker：每个分片一个 goroutine，串行处理自己的请求 ----
	for i := 0; i < concurrent; i++ {
		go func(ch <-chan *pbuser.SetUserOnlineStatusReq) {
			for req := range ch { doRequest(req) }
		}(requestChs[i])
	}

	for {
		select {
		case <-mergeTicker.C:
			pushAllUserState()                                    // 每秒兜底
		case now := <-renewalTicker.C:
			deadline := now.Add(-cachekey.OnlineExpire / 3)
			users := ws.clients.GetAllUserStatus(deadline, now)    // 找出快过期的连接
			pushUserState(users...)                               // 批量续期
		case state := <-ws.clients.UserState():
			pushUserState(state)                                  // 连接状态变化（上线/下线）
		}
	}
}
```

🔴 **重点**：这段代码解决了四个问题，每个都值得单独讲：

**① 为什么要分片（concurrent 个 channel）？**

如果只有一个 channel 和一个 worker，所有在线状态更新都串行写 Redis/RPC，吞吐上不去。分片之后 N 个 worker 并行。

**② 为什么按 `md5(userID)` 分片，还加了 `rNum`？**

- 按 userID 哈希 → 同一个用户的更新永远落同一个分片 → **保序**（先上线后下线不会乱）
- 加进程随机数 `rNum` → 避免**多个网关实例**的同一用户落在同一分片（虽然分片是进程内的，加 rNum 主要是打散热点）

**③ 为什么要 `mergeTicker` 每秒兜底？**

因为"攒够 100 个才发"意味着**低频用户永远攒不满**。一个网关如果每分钟只有 5 个连接变化，这些人的状态永远不会被写进 Redis。每秒 flush 一次保证最终一致。

🔴 **这是「批量 + 兜底定时器」的标准模式**，任何做聚合发送的地方都该这么写。

**④ 为什么满了直接丢（`default` 分支）？**

如果队列满（说明下游 Redis/RPC 太慢），继续阻塞会让整个 `ChangeOnlineStatus` 循环卡住 → `UserState()` channel 也不读了 → 连接状态事件堆积 → 更严重的雪崩。

丢掉的后果：某次在线状态更新丢失 → Redis 里的 score 不会续期 → **最多 30 分钟后该用户被误判离线**。

但如果续期也丢了呢？那就真的误判离线了。**这就是为什么租约要 30 分钟**：给了很多次重试机会（每 10 分钟续期一次，可以丢 2 次）。

## 2.10 在线状态的 Redis 实现：租约 + 变更广播

📂 `pkg/common/storage/cache/redis/online.go:37-140`

### 读：按 score 过滤

**没有 TTL 判断，没有清理任务，就是一次 `ZRangeByScore(now, +inf)`。** 过期的成员自动"读不到"。

### 写：Lua 保证原子性 + 只在变化时广播

```go
// online.go:86-140
func (s *userOnline) SetUserOnline(ctx context.Context, userID string, online, offline []int32) error {
	script := `
	local key = KEYS[1]
	local score = ARGV[3]
	local num1 = redis.call("ZCARD", key)
	redis.call("ZREMRANGEBYSCORE", key, "-inf", ARGV[2])       -- ① 清理已过期的
	for i = 5, tonumber(ARGV[4])+4 do
		redis.call("ZREM", key, ARGV[i])                        -- ② 移除下线的平台
	end
	local num2 = redis.call("ZCARD", key)
	for i = 5+tonumber(ARGV[4]), #ARGV do
		redis.call("ZADD", key, score, ARGV[i])                 -- ③ 加入上线的平台（score=到期时间）
	end
	redis.call("EXPIRE", key, ARGV[1])                          -- ④ 整个 key 的兜底过期
	local num3 = redis.call("ZCARD", key)
	local change = (num1 ~= num2) or (num2 ~= num3)             -- ⑤ 成员数变了 → 有变化
	if change then
		local members = redis.call("ZRANGE", key, 0, -1)
		table.insert(members, "1")
		return members
	else
		return {"0"}
	end
	`
	...
	platformIDs, err := s.rdb.Eval(ctx, script, keys, argv).StringSlice()
	if platformIDs[len(platformIDs)-1] != "0" {                 -- ⑥ 有变化才 publish
		platformIDs[len(platformIDs)-1] = userID
		msg := strings.Join(platformIDs, ":")
		s.rdb.Publish(ctx, s.channelName, msg)
	}
	return nil
}
```

🔴 **重点**：这个 Lua 做了五件事，且**全在一个原子操作里**：

1. `ZREMRANGEBYSCORE` 清过期 — 避免 key 无限膨胀（虽然读的时候不看它们，但存储会涨）
2. `ZREM` 移除下线平台
3. `ZADD` 加入上线平台，score = `now + OnlineExpire`
4. `EXPIRE` 给整个 key 兜底过期（**防止 key 永久残留**——如果用户注销/再也不上线，这个 key 没人清）
5. **比较成员数变化，变了才 publish** — 这是性能优化：心跳续期不会改变成员数（`num1 == num2 == num3`），所以**不广播**。只有真正上下线才广播。

⚠️ **但这个 Lua 有两个真实的副作用，值得记下来**：

**① 过期成员只有"被再次写"时才会被清理。**

`ZREMRANGEBYSCORE` 只在 `SetUserOnline` 被调用时执行。如果某个用户从此再也不上线（换手机、卸载、注销），他的 key 里会永久留着那个 score 已过期的成员——**读的时候读不到（`ZRangeByScore(now,+inf)` 会过滤掉），但数据一直在**。

虽然第 ④ 步有 `EXPIRE key expire` 兜底，但 `EXPIRE` 是**每次调用都会重置**的：只要这个 key 上还有任何一次活跃写入，key 就不会过期。所以"僵尸成员"会长期占据内存。对一个几百万用户的系统，这是一种缓慢的内存泄漏。📌 可改进：加定期扫描清理，或对 key 设更短的 TTL。

**② 全量遍历没有做过期过滤。**

对比两个读方法：

```go
// online.go:37-41  单用户：按 score 过滤过期
ZRangeByScore(key, Min: now, Max: +inf)

// online.go:66     全量：ZRANGE 直接取全部成员
strValues, err := s.rdb.ZRange(ctx, key, 0, -1).Result()
```

`GetAllOnlineUsers`（管理端"查看所有在线用户"）用的是 `ZRANGE`，**会把已过期的成员也算成在线**。两个方法对"在线"的判定标准不一致，这是一个真实的口径 bug（影响管理端统计，不影响推送主链路）。

## 面试话术（90 秒版）

> 「推送分两条链路：在线走我们自己的 WebSocket，离线走厂商通道。
>
> 在线的第一个问题是路由：用户连在哪个网关节点上。三种方案——维护全局路由表、一致性哈希、广播。我们选广播，因为连接表必须放在网关本地（有状态），而网关本地的东西别人只能问一遍。网关数一般就几个，多几次进程内 RPC 比维护一张有故障残留的全局表便宜得多。
>
> 第二个问题是怎么判断在线。我们没用 `SET user 1 EX 60`，因为那样只能整 key 过期，没法表达‘iOS 在线但 PC 离线’，而且进程被 kill 后状态要等 TTL 才清。我们用 ZSET，member 是平台 ID，score 是过期时间戳——读的时候 `ZRangeByScore(now, +inf)`，过期的自动读不到。这就是租约模型，不依赖任何清理动作。租约 30 分钟，续期间隔取三分之一，容忍两次失败，代价是网关崩溃后最长 30 分钟误判在线，但误判在线的代价可以接受，因为后面还有离线推送兜底。
>
> 第三个问题是什么算送达。iOS 在后台即使连接活着也不算送达，要交给 APNs。而且只有 iOS/Android 的在线写入成功才会抑制离线推送 —— PC 在线不算，因为人可能不在电脑前。这是我们代码里 `pushTerminal` 白名单干的事。
>
> 群聊是读扩散存储、推送层扇出：一条消息只存一份，push 服务拿群成员列表在内存里扇出，网关侧有一个 512 worker、16384 缓冲的内存队列，队列满了 `PushCtx` 会阻塞，压力反向传导到 Kafka，最终蓄水池是 Kafka 磁盘而不是内存。
>
> 另外推送是 at-least-once，服务端不做去重，客户端按 serverMsgID 去重——‘至少一次 + 幂等’比‘精确一次’简单可靠。」

## 预判追问

| 追问 | 怎么答 |
|---|---|
| 广播给所有网关，网关多了怎么办？ | 网关数超过 20 个就该上一致性哈希或路由表了。我们代码里其实写了 `K8sStaticConsistentHash`，但没接上开关——**这是我读过代码才知道的一个死代码点** |
| 心跳为什么不用 WebSocket 的 ping/pong？ | 用了（06 篇的 pingPeriod/pongWait 保连接活性），但**连接活着 ≠ 在线状态正确**。Redis 里的在线状态是另一套租约，两者目的不同：ping/pong 保连接，租约保状态 |
| 群成员 5000 人，一次 RPC 传 5000 个 userID 会不会太大？ | 会，单个 userID 按 20 字节算就是 100KB。当前实现没分片，这是我列出的可改进项之一 |
| 离线推送 token 失效怎么办？ | 厂商会返回 `Unregistered`，需要删除 token。当前 mock 实现没做，生产实现里必须处理，否则会持续向无效 token 推送浪费配额 |
| 为什么不用 Redis 的 keyspace notification 做过期通知？ | keyspace notification 是**不可靠**的（Redis 重启/主从切换会丢），而且大量过期事件会拖慢 Redis。租约模型在读时判断，没有这个问题 |
| 消息先推送后落库怎么办？ | 会出现"收到推送但拉不到详情"的幽灵消息。我们用 `MsgLoneTimePushCounter` 监控推送延迟超 10 秒的情况作为风险指标，但修复放在客户端（拉不到就延迟重试）。这是我们链路的一个真实短板 |

## 本篇小结

| 你该记住的 | 一句话 |
|---|---|
| 路由 | 连接表在网关本地 → 只能广播问一遍 |
| 在线状态 | ZSET + score=过期时间戳，读时过滤（租约） |
| 续期 | L/3，容忍 2 次失败，代价是崩溃后 30 分钟误判 |
| 送达判定 | iOS 后台不算；只有 iOS/Android 在线才抑制离线推送 |
| 扇出 | 存储读扩散（1 份）+ 推送层内存扇出（N 个任务） |
| 背压 | Kafka → 网关内存队列（阻塞）→ 每连接 channel（断开） |
| 最大硬伤 | 消费者出错不重连 + 群聊离线推送 key 用错，都可能导致堆积或热点 |

## Part3 收尾：把 10-15 串成一条线

```
10 发送链路   客户端 → WS → msg RPC → 校验 → 投 toRedis（key=会话ID）
11 MQ 中转    Kafka 四 topic；batcher 聚合 500 条/100ms；按会话分片保序
12 seq 分配   Redis Lua 号段（单聊 50/群聊 100）+ Mongo $inc 兜底
13 存储模型   100 条/文档；位置寻址 (seq-1)/100；读时改写 del_list/revoke
14 同步已读   水位模型；上界 min(maxSeq,userMaxSeq)；未读 = maxSeq - hasReadSeq
15 推送       ZSET 租约；广播路由；pushTerminal；三级背压
```

**一句话串起来**：
> 消息进来先异步化（11），异步之后必须有服务端序号才能定序（12），有了稠密序号才能用算术定位存储（13），有了序号才能用「比大小」做同步（14），而推送只是把已经落库的消息尽快送到对端屏幕（15）——**推送可以失败，拉取不能错**。
