# 第一部分　理论：同步是分布式系统里最难的那部分

## 1.1 先明确：同步到底在同步什么

一次登录，客户端要拿到：

1. **会话列表**（我跟谁聊过、每个会话最后一条是什么、有多少未读）
2. **每个会话的消息**（从我上次看到的地方往后）
3. **增量变化**（我离线期间，谁加了我好友、我被拉进了哪个群、哪个群解散了）

听起来像三个查询，但真正的难点在于：**客户端本地已有数据**。

服务端不能每次都全量返回（几万条消息，流量和时间都不可接受），必须回答一个更精确的问题：

> **「从你上次的状态，到现在，有哪些变化？」**

这个问题有个学名：**增量同步**（incremental sync）。所有做增量的系统，都要回答三个子问题：

| 子问题 | 答错的后果 |
|---|---|
| 「上次的状态」用什么表示？ | 表示不了 → 只能全量 |
| 两次状态之间怎么算出「变化」？ | 算不准 → 漏消息或重复消息 |
| 客户端的状态丢了（重装/换设备）怎么办？ | 无法恢复 → 功能不可用 |

## 1.2 为什么时间戳不能当"上次的状态"

这是很多人第一反应：客户端记住"我最后一条消息的时间是 10:23:45.123"，下次拉 `send_time > 10:23:45.123`。

四个致命的坑：

1. **客户端时钟不可信**。用户可以改手机时间。
2. **同一毫秒多条消息**。`>` 会漏掉同毫秒的其他消息，`>=` 会重复拉。
3. **服务端时间也不保证单调**。多台机器、NTP 回拨，`send_time` 会出现"后发的消息时间更早"。
4. **不稠密**。时间戳是稀疏的，没法用来做区间运算，也没法算"我漏了几条"。

所以工业界的 IM 都用**服务端分配的逻辑序号**（seq）作为排序和水位的唯一依据。时间只用于展示，不用于同步。

🔴 **这就是 12 篇那个号段分配器存在的第三层意义**：
- 让存储可以算术定位（13 篇）
- 让批量操作可以用区间表达（13 篇的"清空聊天记录"）
- **让同步可以退化成"比大小"**（本篇）

## 1.3 水位（watermark）模型

有了单调递增的 seq，同步就变成一个极其简单的模型：

```
每个会话有两条水位线：

  服务端视角（会话级）
  ├── minSeq：这个会话最早的可见消息（被清空/删除后抬高）
  └── maxSeq：这个会话最新消息的 seq

  用户视角（人 × 会话）
  ├── userMinSeq：这个用户能看到的最早消息（"清空聊天记录"抬的就是它）
  └── userMaxSeq：这个用户能看到的最后消息（被踢出群时冻结在这里）

  这个用户的阅读进度
  └── hasReadSeq：我已经读到哪了（未读数 ≈ maxSeq - hasReadSeq）
```

**客户端只需要记住每个会话的 `hasReadSeq`（也就是它本地已有的最大 seq）**，登录后：

```
for each conversation:
    local_max = 本地最大 seq（0 表示没有）
    pull(conversation, begin = local_max + 1, end = ∞, num = 50)
    直到 isEnd == true
```

**这就是「同步」的全部机制。**没有 diff 算法，没有向量时钟，没有 CRDT——因为 seq 是全序的，水位模型天然正确。

> **水位模型的本质**：用「一个单调递增的整数」代替「一组有向的因果关系」。代价是：你只能表达「我读到哪了」，不能表达「我读过 A 但没读 B」。对聊天场景够用（消息天然是线性的），对协同编辑就不够了（那才需要 CRDT/OT）。

## 1.4 四道边界：为什么"拉取"不像听起来那么简单

上面伪代码里的 `end = ∞` 显然不能真传。真实实现必须处理四个边界：

**① 上界不能是 ∞，必须是 `maxSeq`。**

而且这个 maxSeq 要**取两个值的最小值**：会话的 maxSeq 和用户的 userMaxSeq。被踢出群的人，userMaxSeq 冻结在他被踢的那一刻，防止他继续拉新消息。

**② 下界不能是 1，必须取三个值的最大值：`max(1, 会话minSeq, 用户minSeq)`。**

如果用户清空过聊天记录，`userMinSeq = 5001`，那他请求 seq 1~100 应该返回空，而不是返回历史消息。

**③ 一次不能拉太多，必须 `num` 截断。**

拉 20 万条消息会把服务端和客户端一起打死。所以有 `num` 参数，超出就截断，同时要告诉客户端「还没拉完」（`isEnd = false`）。

**④ 方向有两个。**

- 向上翻历史（看更早的消息）：从 `begin` 往前，`PullOrderDesc`
- 补新消息（重连后）：从本地 max+1 往后，`PullOrderAsc`

方向影响两件事：截断时保留哪一段（最新的一段 or 最早的一段），以及 `isEnd` 怎么判定。

## 1.5 推与拉的分工

一个常见误解：「有了 WebSocket，消息就是推下来的，不需要拉」。

真实系统的分工是：

| 通道 | 职责 | 保证 |
|---|---|---|
| **推（WebSocket）** | 实时性：让你在 100ms 内看到消息 | **尽力而为**，可能丢、可能乱序、可能重复 |
| **拉（HTTP/RPC）** | 正确性：保证你最终看到所有该看到的消息 | **至少一次**，靠 seq 去重后等价于精确一次 |

具体到 OpenIM：

1. 消息发出 → 落库 → 推送 MQ → push 服务 → 网关 → 你的长连接（**推**）
2. 你收到推送，发现 seq 跳了（收到 10088 但本地最大是 10085）→ **主动拉** 10086~10088
3. 你断线重连 → 登录时按每个会话的本地最大 seq **拉**

**推送负责"快"，拉取负责"对"。** 只要拉取是对的，推送丢几条都不影响正确性——这是整个同步设计的底气。

⚠️ **易错**：面试时如果说「我们用 WebSocket 推送所以消息不会丢」，直接判定为没做过 IM。正确的说法是「推送尽力而为，正确性靠 seq 水位 + 拉取补偿」。

## 1.6 「已读」是两个完全不同的东西

这是本篇第二个重点。中文都叫「已读」，但它们是两套机制：

| | 已读水位（read watermark） | 已读回执（read receipt） |
|---|---|---|
| 谁用 | **自己** | **别人** |
| 存什么 | 一个数字 `hasReadSeq` | 一条通知消息 |
| 用途 | 算未读数、决定红点 | 让对方知道"你看了" |
| 粒度 | 会话级（一个数字） | 消息级（哪几条） |
| 成本 | O(1) 写 | O(N) 通知（N = 需要通知的人） |
| 群聊里 | 每人都有一份 | **默认不广播**（见 1.8） |

**为什么必须分开？**

如果只有「已读回执」，你需要给每条消息记录"谁读了"，一条群消息 × 500 人 = 500 条记录，回到 13 篇说的写放大问题。

如果用「已读水位」代替回执，别人只能知道"你读到了 seq N"，无法精确知道"你读了哪几条"——但**对未读数计算来说，这就够了**。

所以 OpenIM 的设计是：

- **水位**：所有人都有，O(1) 存储，用于未读数
- **回执**：单聊发（只有一个人要通知），群聊只发给自己的其他端（不广播）

## 1.7 未读数：`maxSeq - hasReadSeq` 为什么能成立

未读数看起来是个减法：

```go
unreadCount := maxSeq - hasReadSeqs[conversationID]   // conversation.go:167
```

这个减法成立的前提有四个，缺一个就错：

1. **seq 稠密**：1~maxSeq 之间每条 seq 都对应一条"该用户应该看到的消息"，没有大段空洞。否则未读数会虚高（把空洞算成未读）。
2. **只统计别人的消息**：自己发的消息不该算未读。OpenIM 的处理方式是**自己发消息时把自己的 hasReadSeq 推到最新**（`BatchInsertChat2Cache` 里 `userSeqMap[m.SendID] = m.Seq`，见 2.4 节），而不是在减法里排除。
3. **消息必须"算未读"**：不是所有消息都计入。比如撤回通知、已读回执本身、打字状态，这些消息的 `Options` 里 `IsUnreadCount = false`（10 篇讲的 11 个开关之一）。
4. **用户可见范围正确**：`maxSeq` 必须已经和 `userMaxSeq` 取过最小值。否则被踢出群的人，未读数会一直涨。

🔴 **重点**：**未读数不是"数出来的"，是"减出来的"。** 这是个非常反直觉但非常重要的设计——它把"统计 500 条未读消息"从 O(N) 变成 O(1)。

🧪 **反例验证**：如果哪天号段分配器出 bug，分配了 seq 100~199 但只写了 3 条消息（空洞 97 个），未读数会凭空多 97。所以 12 篇说的"空洞不影响未读计算"其实是**有条件成立**的：号段浪费的空洞要远小于总量，且不能出现在用户可见区间内。

## 1.8 群已读回执的成本爆炸

假设 500 人群，每条消息都要广播已读回执：

```
一条消息 × 500 人已读 × 广播给 500 人 = 25 万次推送
```

**这是 N² 的**。所以所有主流 IM 都在这里做取舍：

| 方案 | 成本 | 效果 |
|---|---|---|
| 每条消息记录谁读过 | 写放大 N 倍 | 精确，但不可行 |
| 只记水位（每人的 hasReadSeq） | O(1)/人 | 能算"多少人读到这条"，但需要额外索引 |
| **默认不广播，按需查询** | 0 | 微信式：群聊不显示已读 |
| 单聊发回执 | O(1) | 单聊只有一个人要通知，成本可接受 |

OpenIM 的选择（`as_read.go:174-185`）：

- **单聊**：发回执给对方（`recvID = 对方的 userID`）
- **群聊**：只发给自己（`recvID = 自己`，而且强制用 `SingleChatType` 发）——本质是"同步我自己的多端阅读进度"，**不是群已读回执**

⚠️ **注意那段代码的细节**（`as_read.go:183-184`）：

```go
m.sendMarkAsReadNotification(ctx, req.ConversationID, constant.SingleChatType, req.UserID,
	req.UserID, seqs, hasReadSeq)
```

会话类型被硬编码成了 `SingleChatType`（而不是传 `conversation.ConversationType`）。这不是笔误，是刻意的：**用单聊通知的方式发给"自己"，避免触发群通知的广播逻辑**。这种"用类型参数控制语义"的写法可读性很差，但能看出作者清楚知道自己在绕开什么。

## 1.9 增量同步：会话列表这一类数据怎么同步

消息有 seq 可以做水位，那**会话列表**呢？会话没有天然的单调序号。

常见方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| 全量 | 每次登录返回全部会话 | 会话多（几百个）时流量浪费 |
| 时间戳 | `update_time > last_sync` | 同 1.2，时钟与同毫秒问题 |
| **版本号（version log）** | 每次变更写一条版本日志，客户端记版本号 | 需要额外存储；版本太老要降级全量 |
| hash 比对 | 客户端传本地 ID 列表的 hash，服务端比对 | 只能判断"变没变"，不能判断"变了什么" |

OpenIM **两种都用了**：

1. `GetFullOwnerConversationIDs`（`conversation/sync.go:13-35`）：客户端传 ID 列表 hash，相同就返回 `Equal: true` + 空列表——**省一次全量传输**。
2. `GetIncrementalConversation`（`sync.go:37-63`）：基于版本日志，返回 `Insert / Update / Delete` 三个列表 + `Full` 标记。

版本日志的语义（`incrversion.Option`）：

```go
VersionKey:      req.UserID,              // 版本按用户维度记录
VersionNumber:   req.Version,             // 客户端持有的版本号
Version:         FindConversationUserVersion,        // 查某版本的日志
CacheMaxVersion: FindMaxConversationUserVersionCache, // 查当前最大版本
Resp: func(version, delIDs, insertList, updateList, full) { ... }
```

`full = true` 表示「客户端版本太老，增量日志已经滚掉了，只能全量」。**这是所有基于版本日志/oplog 的同步都必须有的降级路径**——日志不可能永久保留。

📌 **待验证**：版本日志的保留策略（多少条/多少天之后强制 full）在配置里没找到明显项，本仓库不做数据清理，因此实际上不会滚掉，但版本日志表会无限增长。

## 1.10 理论小结

```
同步 = 用单调递增的 seq 表示"上次状态"，用区间拉取求"变化"
  ├─ 上界：min(会话maxSeq, userMaxSeq)
  ├─ 下界：max(1, 会话minSeq, userMinSeq)
  ├─ 截断：num + isEnd
  └─ 方向：Asc 补新 / Desc 翻历史
推送负责快，拉取负责对；拉取至少一次，客户端按 seq 去重
未读数 = maxSeq - hasReadSeq（O(1) 减法，不是 O(N) 统计）
已读水位（自己的，O(1)） ≠ 已读回执（给别人的，O(N)）
群已读默认不广播（N² 成本），单聊才发回执
会话列表用版本日志增量 + hash 快速判断 + full 降级
```

## 2.1 拉取消息的入口

📂 `internal/rpc/msg/sync_msg.go:17-76`

```go
func (m *msgServer) PullMessageBySeqs(ctx context.Context, req *sdkws.PullMessageBySeqsReq) (*sdkws.PullMessageBySeqsResp, error) {
	if err := authverify.CheckAccess(ctx, req.UserID); err != nil { return nil, err }   // 只能拉自己的
	resp := &sdkws.PullMessageBySeqsResp{
		Msgs:             make(map[string]*sdkws.PullMsgs),
		NotificationMsgs: make(map[string]*sdkws.PullMsgs),
	}
	for _, seq := range req.SeqRanges {          // ⚠️ 一次可以拉多个会话，串行处理
		if !msgprocessor.IsNotification(seq.ConversationID) {
			// ---- 普通会话 ----
			conversation, err := m.ConversationLocalCache.GetConversation(ctx, req.UserID, seq.ConversationID)
			if err != nil { continue }           // 会话不存在 → 跳过（注意：不是报错）
			minSeq, maxSeq, msgs, err := m.MsgDatabase.GetMsgBySeqsRange(
				ctx, req.UserID, seq.ConversationID, seq.Begin, seq.End, seq.Num, conversation.MaxSeq)
			if err != nil { continue }
			var isEnd bool
			switch req.Order {
			case sdkws.PullOrder_PullOrderAsc:  isEnd = maxSeq <= seq.End
			case sdkws.PullOrder_PullOrderDesc: isEnd = seq.Begin <= minSeq
			}
			if len(msgs) == 0 { continue }
			resp.Msgs[seq.ConversationID] = &sdkws.PullMsgs{Msgs: msgs, IsEnd: isEnd}
		} else {
			// ---- 通知会话（n_ 前缀）----
			var seqs []int64
			for i := seq.Begin; i <= seq.End; i++ { seqs = append(seqs, i) }
			minSeq, maxSeq, notificationMsgs, err := m.MsgDatabase.GetMsgBySeqs(ctx, req.UserID, seq.ConversationID, seqs)
			...
		}
	}
	return resp, nil
}
```

三个要注意的点：

**① `IsEnd` 的判定逻辑不对称。**

```go
Asc（拉新消息）:  isEnd = maxSeq <= seq.End    // 我要的终点已经超过服务端最大值 → 到底了
Desc（翻历史）:  isEnd = seq.Begin <= minSeq   // 我要的起点已经低于服务端最小值 → 到底了
```

**这两个条件是镜像的**：向上翻的时候看下界，向下补的时候看上界。如果写反，客户端会无限翻页。

**② 通知会话是独立的命名空间。**

`n_` 开头的会话（系统通知，比如"你被拉进群了"）走**另一套 seq 序列**（`n_<userID>`）。它不查会话表（因为通知会话没有 conversation 记录），直接按 seqs 数组取。这就是 10 篇讲的"会话 ID 有三种前缀"在同步层的体现。

**③ 单个会话失败只 `continue`。**

一个会话查不到（比如刚解散），不影响其他会话的拉取。**这是务实的选择**：宁可少返回一个会话，也不让整个请求失败——客户端下次还会再拉。

## 2.2 范围收敛：把请求夹到「我该看到」的区间内

📂 `pkg/common/storage/controller/msg.go:370-424` —— **本篇最核心的函数**

```go
func (db *commonMsgDatabase) GetMsgBySeqsRange(ctx context.Context, userID string, conversationID string,
	begin, end, num, userMaxSeq int64) (int64, int64, []*sdkws.MsgData, error) {

	// 1. 下界：会话级 minSeq 与用户级 minSeq 取大
	userMinSeq, err := db.seqUser.GetUserMinSeq(ctx, conversationID, userID)   // 我清空到哪了
	if err != nil && !errors.Is(err, redis.Nil) { return ... }
	minSeq, err := db.seqConversation.GetMinSeq(ctx, conversationID)           // 会话被删到哪了
	if userMinSeq > minSeq { minSeq = userMinSeq }
	if minSeq > end {
		// 请求的 end 比下界还小 → 这段已经完全不可见
		return 0, 0, nil, nil
	}

	// 2. 上界：会话级 maxSeq 与用户级 maxSeq 取小
	maxSeq, err := db.seqConversation.GetMaxSeq(ctx, conversationID)
	if userMaxSeq != 0 && userMaxSeq < maxSeq { maxSeq = userMaxSeq }

	// 3. 把请求区间夹到 [minSeq, maxSeq]
	if begin < minSeq { begin = minSeq }
	if end > maxSeq { end = maxSeq }
	if end < begin { return 0, 0, nil, errs.ErrArgs.WrapMsg("seq end < begin") }

	// 4. 按 num 截断：超了就只取「最靠近 end 的 num 条」
	var seqs []int64
	if end-begin+1 <= num {
		for i := begin; i <= end; i++ { seqs = append(seqs, i) }
	} else {
		for i := end - num + 1; i <= end; i++ { seqs = append(seqs, i) }
	}
	successMsgs, err := db.GetMessageBySeqs(ctx, conversationID, userID, seqs)
	return minSeq, maxSeq, successMsgs, err
}
```

🔴 **重点**：这段代码就是 1.4 节四道边界的完整实现。逐条对上：

| 理论 | 源码 |
|---|---|
| 上界取最小 | `if userMaxSeq != 0 && userMaxSeq < maxSeq { maxSeq = userMaxSeq }` |
| 下界取最大 | `if userMinSeq > minSeq { minSeq = userMinSeq }` |
| num 截断 | `end-num+1 ~ end`（保留最靠近 end 的一段） |
| 越界直接返回空 | `if minSeq > end { return 0,0,nil,nil }` |

**截断保留哪一段**？保留 `[end-num+1, end]`，也就是**最靠近请求终点的那一段**。为什么？因为拉新消息时 `end` 是"我要到哪"，前面的是过时的；翻历史时同理，`end` 是当前视窗底部。保留靠近 end 的那段符合人的阅读预期。

函数注释里（`msg.go:355-369`）写清了两个用户级水位的业务含义，值得抄下来：

```
"userMaxSeq"：用户在群内可拉取的消息序号上限。未设置（默认 0）时，与会话的 "maxSeq" 相同。
"userMinSeq"：用户在群内拉取消息的起始序号。未设置（默认 0）时，与会话的 "minSeq" 相同。

典型场景：
被踢出群的用户，"userMaxSeq" 可设为其被踢出前的最大序号，限制其只能拉到某个时间点之前的消息。
新入群用户如果不需要历史消息，"userMinSeq" 可设为入群那一刻会话的 "maxSeq"。
```

**同一个机制服务两个完全相反的业务需求**——这是设计得好的地方。面试时可以用它说明「水位不只是个计数器，它是一个可配置的可见性窗口」。

## 2.3 指定序号列表拉取：带着边界判断的版本

📂 `pkg/common/storage/controller/msg.go:465-519`

`GetMessagesBySeqWithBounds` 是给「客户端已经知道具体 seq」的场景用的（比如收到推送发现 seq 跳号，拉 10086~10088）：

```go
for _, seq := range seqs {
	if seq <= 0 { continue }
	if seq >= minSeq && seq <= maxSeq {
		newSeqs = append(newSeqs, seq)          // 可见，正常返回
		continue
	}
	// 请求的序号小于最小序号，且是降序（翻更早）→ 到边界了
	if seq < minSeq && pullOrder == sdkws.PullOrder_PullOrderDesc {
		isEnd = true
		endSeq = minSeq
	}
	// 请求的序号大于最大序号，且是升序（拉更新）→ 到边界了
	if seq > maxSeq && pullOrder == sdkws.PullOrder_PullOrderAsc {
		isEnd = true
		endSeq = maxSeq
	}
}
if len(newSeqs) == 0 { return isEnd, endSeq, nil, nil }
```

它比 `GetMsgBySeqsRange` 多返回一个 `endSeq`——**告诉客户端"真正的边界在哪"，方便客户端修正本地水位**。比如客户端以为有 10100，但服务端只到 10098，`endSeq = 10098`，客户端把本地水位改成 10098，就不会一直重试拉 10099~10100。

## 2.4 写入时就把自己的已读推上去

📂 `pkg/common/storage/controller/msg_transfer.go:203-239`

这是「未读数 = maxSeq - hasReadSeq」能成立的关键细节：

```go
currentMaxSeq, err := db.seqConversation.Malloc(ctx, conversationID, int64(len(msgs)))   // 申请号段
isNew = currentMaxSeq == 0
lastMaxSeq := currentMaxSeq
userSeqMap := make(map[string]int64)
for _, m := range msgs {
	currentMaxSeq++
	m.Seq = currentMaxSeq
	m.SendTime = sendTime
	userSeqMap[m.SendID] = m.Seq      // ← 发送者自己：已读水位 = 自己这条消息的 seq
	seqs = append(seqs, m.Seq)
}
```

调用方（`online_history_msg_handler.go`）随后会：

- 如果 `isNew`（新会话），把 `userSeqMap` 全部写进 `hasReadSeq`——**新会话里，发送者自己发的第一条消息不应该算他未读**
- 否则，也会对发送者 `SetHasReadSeq`

🔴 **重点**：**"自己发的消息不算未读"不是靠减法时排除，而是靠写入时把自己的水位推到最新。** 这个设计让未读数的计算路径完全不需要知道"谁是发送者"，只需要两个数字。

⚠️ **副作用**：如果 A 发消息时手上有一堆未读（500 条没看），发一条消息会把自己的已读水位直接跳到最新——**微信不是这么做的**（发消息不会把未读清零），但这在减法模型下是必然结果。📌 这是一个真实的语义差异，面试时如果能指出它，会显得你思考过模型边界。

## 2.5 会话列表的 maxSeq 从哪来

📂 `internal/rpc/conversation/conversation.go:144-170`

```go
conversations, err := c.conversationDatabase.FindConversations(ctx, req.UserID, conversationIDs)
maxSeqs, err := c.msgClient.GetMaxSeqs(ctx, conversationIDs)          // ← 现查消息服务

	conversation_unreadCount[conversationID] = unreadCount
	unreadTotal += unreadCount

```

🔴 **重点**：**会话表里存的 MaxSeq 不是权威值**。拉列表时实时问消息服务要 `GetMaxSeqs`（最终落到 Redis 的 seq 分配器）。原因：消息落库是异步的（11 篇），会话表如果同步更新会成为写热点，而且多实例并发更新容易互相覆盖。

**代价**：拉一次会话列表要发 4 次 RPC（GetMaxSeqs / GetMsgByConversationIDs / GetHasReadSeqs + 本地的 FindConversations）。这是"读扩散"。优化方向是合并成一个 RPC 或加本地缓存——📌 本项目没做。

**客户端登录后的完整流程**（把本篇串起来）：

```
1. /msg/get_max_seq              → 拿到每个会话服务端最新 seq
2. 对比本地最大 seq：
   ├─ 相等 → 该会话已同步完

4. /msg/get_conversations_has_read_and_max_seq → 校准已读水位
```

⚠️ **易错**：`for range` 里 `append` 到同一个 slice（`sync_msg.go:117-119`）。Go 的 `range` 在循环开始时就把长度定了，所以不会死循环，但**这是很容易被误读成 bug 的写法**。如果后来有人把它改成索引循环 `for i := 0; i < len(ids); i++`，立刻就会无限增长。

## 2.7 已读：四个接口，三种语义

📂 `internal/rpc/msg/as_read.go`

| 接口 | 行 | 语义 | 谁调 |
|---|---|---|---|
| `MarkConversationAsRead` | 134 | 「这个会话我读到 seq N 了」，会补齐区间 | 客户端点进会话 |
| `MarkMsgsAsRead` | 92 | 「这 3 条我读了」，精确列表 | 客户端滚动到某几条 |
| `SetConversationHasReadSeq` | 74 | 「直接设成 N」，不校验区间、不补 Mongo | 管理端/特殊场景 |
| `GetConversationsHasReadAndMaxSeq` | 18 | 批量读水位 + maxSeq | 登录/下拉刷新 |

### MarkConversationAsRead：为什么还要补齐区间

📂 `as_read.go:134-205`

```go
hasReadSeq, _ := m.MsgDatabase.GetHasReadSeq(ctx, req.UserID, req.ConversationID)
var seqs []int64
if conversation.ConversationType == constant.SingleChatType {
	// ① 从上次水位+1 补到本次水位
	for i := hasReadSeq + 1; i <= req.HasReadSeq; i++ { seqs = append(seqs, i) }
	// ② 再并上客户端显式报的 seqs（去重）
	// 避免客户端漏按顺序调用 MarkConversationMessageAsRead
	for _, val := range req.Seqs {
		if !datautil.Contain(val, seqs...) { seqs = append(seqs, val) }
	}
	if len(seqs) > 0 {
		m.MsgDatabase.MarkSingleChatMsgsAsRead(ctx, req.UserID, req.ConversationID, seqs)
	}
	if req.HasReadSeq > hasReadSeq {
		m.MsgDatabase.SetHasReadSeq(ctx, req.UserID, req.ConversationID, req.HasReadSeq)
		hasReadSeq = req.HasReadSeq
	}
	m.sendMarkAsReadNotification(...)
}
```

**为什么补区间？** 因为单聊要在 Mongo 里给每条消息打 `is_read`（13 篇的三个标签之一）。客户端可能只报"我读到 100 了"，但那 100 条里有些没打标记（上次请求失败、客户端崩溃）。**服务端补齐，保证不漏**。

代价很直接：`for i := hasReadSeq+1; i <= req.HasReadSeq; i++`——如果 `hasReadSeq=0` 而 `req.HasReadSeq=100000`，会构造一个 10 万元的切片，然后对 1000 个文档做 BulkWrite。📌 **这是可被滥用的性能点**（见 2.12）。

### 单聊写 Mongo，群聊不写

📂 `pkg/common/storage/database/mgo/msg.go:232-260`

```go
func (m *MsgMgo) MarkSingleChatMsgsAsRead(ctx context.Context, userID string, docID string, indexes []int64) error {
	var updates []mongo.WriteModel
	for _, index := range indexes {
		filter := bson.M{
			"doc_id": docID,
			fmt.Sprintf("msgs.%d.msg.send_id", index): bson.M{"$ne": userID},   // ← 不标记自己发的
		}
		update := bson.M{"$set": bson.M{fmt.Sprintf("msgs.%d.is_read", index): true}}
		updates = append(updates, mongo.NewUpdateManyModel().SetFilter(filter).SetUpdate(update))
	}
	_, err := m.coll.BulkWrite(ctx, updates)      // 一次 BulkWrite 批量提交
	return err
}
```

三个细节：

1. **`send_id != userID` 的过滤条件**：不把自己的消息标记成已读——因为"已读"在单聊里的语义是"**对方**读了"。
2. **`BulkWrite`**：一批 seq 一次往返，而不是 N 次 update。
3. **函数名带 `SingleChat`**：这个限制是刻意的。

**群聊为什么不写？**

群聊 500 人，每人读一次要给 100 条消息各写一次 `is_read`——而且是 500 份"谁读了"的信息，一个 `bool` 根本存不下。所以群聊只更新水位（`as_read.go:176-182`），**不落库任何消息级已读状态**。

这就是 1.8 节的代码证据：**群已读回执在存储层就是被放弃的**。

## 2.8 已读水位的存储：Redis 为主，Mongo 为备

📂 `pkg/common/storage/cache/redis/seq_user.go`

```go
// seq_user.go:15-21
func NewSeqUserCacheRedis(rdb redis.UniversalClient, mgo database.SeqUser) cache.SeqUser {
	return &seqUserCacheRedis{
		mgo:               mgo,
		readSeqWriteRatio: 100,           // ← 声明了，但全文没有任何地方使用（见 2.12）
		expireTime:        time.Hour * 24 * 7,
		readExpireTime:    time.Hour * 24 * 30,
		rocks:             newRocksCacheClient(rdb),
	}
}

// seq_user.go:74-88  写已读水位
func (s *seqUserCacheRedis) SetUserReadSeq(ctx context.Context, conversationID string, userID string, seq int64) error {
	if s.rocks.GetRedis() == nil {
		return s.SetUserReadSeqToDB(ctx, conversationID, userID, seq)   // 无 Redis 环境 → 直接落库
	}
	dbSeq, err := s.GetUserReadSeq(ctx, conversationID, userID)         // 先读
	if err != nil { return err }
	if dbSeq < seq {                                                   // 只允许前进
		s.rocks.GetClient().RawSet(ctx, s.getSeqUserReadSeqKey(...), strconv.Itoa(int(seq)), s.readExpireTime)
	}
	return nil
}
```

**设计意图很清楚**：已读水位是高频写（每读一条消息就可能更新一次），但**丢失代价不大**（最多未读数偏多）。所以：

- 写：只写 Redis（30 天过期）
- 读：先 Redis，未命中回源 Mongo
- **Mongo 只在某些时机被写**（`SetUserReadSeqToDB` 的调用方）

⚠️ **但这里有个真问题**：`readSeqWriteRatio: 100` 这个字段**在整个仓库里没有任何地方使用**（`grep readSeqWriteRatio` 只有定义和赋值两处）。从命名推断，原设计是"每 100 次写才落一次库"（典型的 write-behind 批量落库），**但这个机制没实现**。

后果：如果 Redis 里的 key 过期（30 天没操作该会话）或 Redis 数据丢失，`GetUserReadSeq` 会回源 Mongo 拿到一个**很久以前的值**，导致未读数突然变大（用户看到几百条"新"消息）。

📌 这不是"确定会发生的线上故障"，而是一个**设计意图未落地的证据**。面试里讲它，比讲十个架构图都有说服力。

## 2.9 增量同步：版本日志

📂 `internal/rpc/conversation/sync.go:13-63`

```go
// ① hash 快速判断"有没有变"
func (c *conversationServer) GetFullOwnerConversationIDs(...) {
	vl, _ := c.conversationDatabase.FindMaxConversationUserVersionCache(ctx, req.UserID)
	conversationIDs, _ := c.conversationDatabase.GetConversationIDs(ctx, req.UserID)
	idHash := hashutil.IdHash(conversationIDs)
	if req.IdHash == idHash {
		conversationIDs = nil                 // hash 相同 → 一个都不返回
	}
	return &...{Version: uint64(vl.Version), VersionID: vl.ID.Hex(),
	            Equal: req.IdHash == idHash, ConversationIDs: conversationIDs}
}

// ② 版本号增量
func (c *conversationServer) GetIncrementalConversation(ctx context.Context, req *...) {
	opt := incrversion.Option[*conversation.Conversation, ...]{
		VersionKey:      req.UserID,                    // 版本按用户维度
		VersionID:       req.VersionID,
		VersionNumber:   req.Version,
		Version:         c.conversationDatabase.FindConversationUserVersion,
		CacheMaxVersion: c.conversationDatabase.FindMaxConversationUserVersionCache,
		Find:            func(...) { return c.getConversations(...) },
		Resp: func(version *model.VersionLog, delIDs []string, insertList, updateList []*conversation.Conversation, full bool) *... {
			return &...{VersionID: version.ID.Hex(), Version: uint64(version.Version),
			            Full: full, Delete: delIDs, Insert: insertList, Update: updateList}
		},
	}
	return opt.Build()
}
```

🔴 **重点**：`incrversion` 是**泛型算法包**，不是服务（08 篇纠正过的错误假设）。四个调用点：

| 调用点 | 同步什么 |
|---|---|
| `conversation/sync.go:41` | 会话 |
| `relation/sync.go:71` | 好友 |
| `group/sync.go:83` | 群成员 |
| `group/sync.go:150` | 我加入的群 |

**它的算法**（简化）：

```
if 客户端版本 == 当前最大版本 → 返回空（没有变化）
if 客户端版本 太老（日志被清理） → full = true，返回全量
否则 → 查版本日志，聚合出 Delete / Insert / Update 三个列表
```

**`Design` 评价**：把「增量同步」抽象成一个泛型 Option，四个业务域复用同一套逻辑，这是本仓库里设计得最漂亮的部分之一。而且注意它的 `Resp` 回调是**泛型输出**，调用方自己决定怎么组装返回体——比硬编码返回结构灵活。

| 9 | `msg.go:545-547` | `GetMaxSeqs` 直接透传 redis 层，没有本地缓存 | 每个用户的会话列表都打一次 Redis | 加 short-TTL 本地缓存 |
| 10 | `as_read.go:82-84` | `SetConversationHasReadSeq` 只校验 `<= maxSeq`，不校验下界 | 可以回退已读水位（传入更小的值） | 加 `>= 当前值` 校验（除非明确需要回退） |

# 第三部分　实验

## 🧪 实验 1：观察 isEnd 的两个方向

```bash
# 拿到 token 后，先用 get_max_seq 看某会话的 maxSeq = N
curl -s -X POST "http://127.0.0.1:10002/msg/get_max_seq" \
  -H "Content-Type: application/json" -H "token: $TOKEN" -H "operationID: t1" \
  -d '{"userID":"<uid>"}'

# 升序拉到超出范围，观察 isEnd
curl -s -X POST "http://127.0.0.1:10002/msg/pull_msg_by_seqs" \
  -H "Content-Type: application/json" -H "token: $TOKEN" -H "operationID: t1" \
  -d '{"userID":"<uid>","order":0,
       "seqRanges":[{"conversationID":"si_A_B","begin":1,"end":999999,"num":20}]}'
```

**预期**：返回 20 条（最靠近 end 的那段），`isEnd = true`（因为 `maxSeq <= end`）。

再试降序（`order:1`）+ `begin=1` → `isEnd = true`（因为 `begin <= minSeq`）。

## 🧪 实验 2：验证「清空后拉不到旧消息」

1. 记下某会话 maxSeq。
2. 调 `/msg/clear_conversations_msg`。
3. 用 `begin=1, end=maxSeq` 拉 → 返回空或只返回占位消息。
4. 查 Redis 里该 user 的 minSeq，确认等于 `maxSeq + 1`。

## 🧪 实验 3：验证单聊 is_read 落库

1. A 发 3 条消息给 B。
2. B 调 `/msg/mark_conversation_as_read`，`hasReadSeq = 最大 seq`。
3. 查 Mongo：

```js
db.msg.findOne({"doc_id":"si_A_B:0"}, {"msgs.is_read":1, "msgs.msg.send_id":1})
// 预期：A 发的消息 is_read=true；如果 B 也发过消息，B 发的那些 is_read=false
```

4. 换成**群会话**重复 → 群里所有消息的 `is_read` **不会变**（群聊不落库）。

## 🧪 实验 4：验证未读数是减法

1. A 给 B 发 5 条消息（不读）。
2. B 调 `/conversation/get_conversations` → 该会话 `unreadCount = 5`。
3. B 读 2 条（`mark_msgs_as_read`，seqs = 前 2 条）→ `unreadCount = 3`。
4. B 自己发 1 条消息 → `unreadCount = 0`（**验证 2.4 节的副作用**：发消息会把自己的水位推到最新）。

**第 4 步是本篇最值得亲手做一次的实验**——它会让你真正理解「减法模型」的边界。

## 面试话术（90 秒版）

> 「消息同步我用的是序号水位模型，不是时间戳。每个会话有一个服务端分配的稠密 seq，客户端只需要记住本地最大 seq。登录时先调 get_max_seq 拿到服务端最新，然后对落后的会话按 begin=本地+1、end=服务端maxSeq 拉取，用 num 截断、isEnd 判断是否拉完。
>
> 关键在于拉取时要做范围收敛：上界取 min(会话maxSeq, userMaxSeq)，下界取 max(1, 会话minSeq, userMinSeq)。这两个用户级水位分别解决两个相反方向的问题——退群/被踢时把 maxSeq 写成当时的群 max，上界被冻结，历史还在但拉不到新消息；重新入群时把它写回 0，`if userMaxSeq != 0` 不成立，上界不再收紧，等于恢复全部可见。注意 0 的语义是「没有限制」而不是「上界为零」，这一点必须看读取侧才能确认。
>
> 未读数是个 O(1) 的减法：maxSeq - hasReadSeq，不是统计出来的。成立的前提是 seq 稠密、只有别人的消息计入、非计数类消息的 Options 里关掉 IsUnreadCount，以及 maxSeq 已经和 userMaxSeq 取过最小值。
>
> 已读要区分两个概念：已读水位是给自己用的，一个数字，O(1)；已读回执是给别人看的，O(N)。所以单聊才发回执，群聊默认不广播——500 人群一条消息广播回执就是 N² 的成本。群聊只更新水位，不往 Mongo 写 is_read，因为一个 bool 表达不了‘500 人里谁读了’。
>
> 会话列表这类没有单调序号的数据用版本日志增量同步，客户端版本太老就降级全量，另外还有一个 ID 列表 hash 比对，hash 相同直接返回空，省一次全量传输。」

## 预判追问

| 追问 | 怎么答 |
|---|---|
| 客户端状态丢了怎么办？ | 本地最大 seq = 0，等价于全量拉。会话列表用 `GetFullOwnerConversationIDs` 拿全量 ID，再逐个会话拉最近 N 条 + 用户上滑时往回翻 |
| 推送和拉取会不会重复？ | 会，而且设计上就允许重复。客户端按 serverMsgID/clientMsgID 去重，服务端不做 exactly-once。**「至少一次 + 幂等去重」比「精确一次」简单且可靠** |
| 拉取时消息还在 Kafka 里没落库怎么办？ | 会出现「seq 存在但消息查不到」的洞。当前实现返回占位消息（`Status=已删除`），客户端会显示一条"消息已删除"。更好的做法是短暂重试或延迟返回——**这是本项目的一个真实短板** |
| 为什么不用 etcd/Kafka 那种 consumer offset 存同步进度？ | 服务端也可以存，但存客户端更自然：换设备时用户希望重新同步，而不是继承另一台设备的进度 |
| 群聊想做已读回执怎么办？ | 需要单独的"已读人数"存储：要么按消息维度存一个位图（500 人 = 63 字节），要么按水位存"多少人读到 seq N"（需要有序集合 + 范围计数）。前者精确但写放大，后者便宜但只能算"读到这条的人数" |

## 本篇小结

| 你该记住的 | 一句话 |
|---|---|
| 同步的本质 | 用「一个整数」表示上次状态，用区间拉取求变化 |
| 四道边界 | 上界取小、下界取大、num 截断、方向决定 isEnd |
| 用户级水位 | userMaxSeq 是上界（踢群写当前 max 冻结，入群写 0 解除），userMinSeq 是下界（清除/焚毁抬高） |
| 推拉分工 | 推负责快，拉负责对；至少一次 + 客户端幂等 |
| 未读数 | `maxSeq - hasReadSeq` 的减法，四个前提缺一不可 |
| 两个已读 | 水位（自己，O(1)）≠ 回执（别人，O(N)）；群聊不广播 |
| 最大硬伤 | 已读水位只写 Redis，`readSeqWriteRatio` 的批量落库没实现 |
