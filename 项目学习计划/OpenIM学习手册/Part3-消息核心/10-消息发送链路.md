# 第一部分 理论：发一条消息，究竟难在哪

## 10.1 先破除一个错觉：发消息不是「一次 HTTP 请求」

如果你只做过 bluebell 那种 Web 项目，你对「提交数据」的直觉大概是这样的：

```
前端 POST /post/create  →  后端 INSERT INTO post  →  返回 {"id": 123}
```

一次请求，一次写库，返回主键。干净利落。

IM 的发消息**看起来**也是这样：

```
客户端发消息  →  服务端  →  返回「发送成功」
```

但如果服务端真的这么干，它会立刻在三个地方崩掉。我们逐个看。

### 10.1.1 崩溃点一：一个群 500 人，写一次要写 500 份吗

假设一个 500 人微信群，你发一句「收到」。

如果按「每个接收者一条记录」的朴素设计，这条消息要写 500 条记录。一个 10 万人的大群，一条消息写 10 万条。热门群里一分钟几百条消息，写放大就是几千万行。

**这不是优化问题，是设计错误。** 消息本身只有一份，它属于「这个会话」，不属于「每个用户」。

> 正确的心智模型：**消息归属于会话（Conversation），不归属于用户**。用户与消息的关系是「可见性」关系，用序号范围来表达，而不是一人一份拷贝。这个思想在第 13 篇（消息存储模型）会展开成一整套 Mongo 文档设计。

### 10.1.2 崩溃点二：发送接口被 10 万 QPS 打进来

即时通讯的流量特征和电商完全不同：**没有明显的波峰波谷，但突发性极强**。跨年零点、明星塌房、红包雨，一秒内的消息量可以是平峰的几十倍。

如果发送接口同步做这些事：

```
校验权限（查群成员，一次 RPC）
  → 分配序号（写 Mongo）
  → 写 Redis
  → 写 Mongo
  → 查在线状态（查 Redis）
  → gRPC 推给网关
  → 推给每个在线用户
```

一次发送要串行做 6 件跨网络的事。每件 1ms 就是 6ms，峰值 QPS 一上来，Mongo 先顶不住，然后 goroutine 堆积，内存爆，整个服务雪崩。

**关键洞察**：这 6 件事里，只有第一件（校验权限）是「必须立刻知道结果」的。剩下 5 件，用户并不关心它是 1 毫秒后完成还是 100 毫秒后完成——用户只关心「消息别丢」。

所以架构上做了切割：**发送接口只做「校验 + 收下 + 排队」，剩下的交给后台流水线**。这就是第 03 篇讲的「发送 ≠ 落库 ≠ 推送」在本篇的具体落地。

### 10.1.3 崩溃点三：网络断了，客户端不知道到底发成功没有

客户端发出消息后，可能遇到这些情况：

| 情况 | 客户端看到什么 | 真实情况 |
|---|---|---|
| 服务端处理成功，响应正常返回 | 成功 | 成功 |
| 服务端处理成功，响应在回程丢了 | **超时** | **其实已成功** |
| 服务端没收到，请求在路上丢了 | 超时 | 失败 |
| 服务端处理到一半进程崩了 | 超时 | 不确定 |

对客户端来说，中间两种「超时」长得一模一样。它能做的只有一件事：**重试**。

而重试会带来一个新问题：如果第一次其实成功了，重试就会产生**两条一样的消息**。

解决这个问题的通用手段叫**幂等**（Idempotent）：同一个操作执行一次和执行多次，结果相同。IM 里实现幂等的抓手，就是本篇要讲的三个 ID。

## 10.2 三个 ID：ClientMsgID、ServerMsgID、Seq

这是整个消息系统里最容易被面试官追问、也最容易答混的一组概念。先用一句话区分：

| ID | 谁生成 | 什么时候生成 | 作用 |
|---|---|---|---|
| **ClientMsgID** | 客户端 | 用户按下发送键的瞬间 | 客户端侧的**幂等键**，用于去重、把「发送中」的气泡和「已送达」的响应配对 |
| **ServerMsgID** | 服务端 | 服务端收到消息时 | 服务端的**全局唯一标识**，用于日志追踪、撤回、引用、定位单条消息 |
| **Seq** | 服务端 | **落库前**（本篇的主角之一，详见第 12 篇） | 会话内的**单调递增序号**，用于排序、同步、已读、断线补偿 |

### 10.2.1 为什么客户端 ID 和服务器 ID 都要有

你可能会问：一个 ID 不够吗？

**不够，因为它们的生命周期和归属方不同。**

ClientMsgID 是客户端在**离线状态**下也能生成的——用户在地铁里没信号，消息先存本地，ID 已经生成了。这个 ID 必须由客户端负责唯一（通常用 UUID 或「设备ID+本地自增」）。

ServerMsgID 是服务端生成的，客户端在发送前根本不可能知道。它的价值在于**服务端视角的唯一性**：一条消息可能被多个客户端重复发送（重试），但服务端只认第一次，最终只产生一个 ServerMsgID。

两者合起来，才能回答两个不同的问题：

- 「这条消息是不是我刚才发的那条？」→ 比对 ClientMsgID
- 「服务端认为这是哪条消息？」→ 用 ServerMsgID

### 10.2.2 Seq 为什么不能由客户端生成

这是面试高频题。想清楚三点就够了：

1. **客户端不可信**。改个客户端就能伪造 seq，插到别人消息中间。
2. **客户端之间没有共享状态**。两个人同时发消息，谁先谁后，客户端无法协商。
3. **多端登录**。同一个账号在手机和电脑上同时发消息，两个设备各自生成的 seq 必然冲突。

所以 seq 必须由**服务端在单一位置集中分配**。OpenIM 把这个位置放在了消息中转服务（msgtransfer）里，而不是发送接口里——这一点非常关键，第 12 篇会用整篇讲为什么。

### 10.2.3 一个容易被忽略的事实：发送成功的响应里没有 seq

回忆一下你在客户端开发时的经验：调用发送消息接口，返回的字段是 `serverMsgID`、`clientMsgID`、`sendTime`。

**没有 seq。**

这不是遗漏，是必然结果。因为在 OpenIM 的架构里，发送接口返回时，消息才刚被扔进 Kafka，还没被消费，seq 根本还没分配出来。

那客户端怎么知道自己的消息排在第几位？

答案是：**客户端不关心 seq，它靠「推送」拿到。** 消息落库并分配 seq 后，会走推送通道（`toPush` topic）回到发送者自己的其他端，也回到接收方。客户端收到推送时，消息里就带着 seq 了。

> 这个设计带来一个副作用，也是真实存在的体验问题：发送者刚发完消息，自己的气泡是「本地插入」的，还没 seq；等推送回来才「对齐」到服务端的序号。所以你在弱网下偶尔会看到消息「跳一下」。这是最终一致性的代价，第 15 篇会讲怎么缓解。

## 10.3 会话（Conversation）：IM 里最重要的领域概念

### 10.3.1 会话是什么

**会话 = 一组参与者之间的一条持续对话线。**

它不是一个抽象概念，它有实实在在的 ID、有属性、有生命周期。你可以把它理解成一个「聊天窗口」在服务端的投影：

- 你和小明聊天 → 一个单聊会话
- 你在「技术交流群」里发言 → 一个群聊会话
- 系统给你发的「你已被移出群聊」→ 一个通知会话

**为什么要有会话这个概念？** 因为几乎所有 IM 操作都需要一个「范围」：

| 操作 | 范围是什么 |
|---|---|
| 消息排序 | 会话内有序 |
| 未读数 | 会话维度统计 |
| 已读回执 | 会话内「我已读到第几条」 |
| 消息同步 | 按会话拉取 |
| 置顶/免打扰 | 会话级设置 |
| 清空聊天记录 | 清空某会话 |

没有会话，这些操作就没有边界。

### 10.3.2 会话 ID 是怎么拼出来的

单聊有个经典难题：A 给 B 发消息，和 B 给 A 发消息，必须是**同一个会话**。

如果直接拼 `A_B` 和 `B_A`，就会变成两个会话，聊天记录裂成两半。

解决办法很朴素：**排序后拼接**。取两个 userID，字典序排序，再连起来。这样 A→B 和 B→A 都能算出同一个字符串。

OpenIM 在此基础上加了**类型前缀**，让会话 ID 自带类型信息：

| 会话类型 | 前缀 | 例子 |
|---|---|---|
| 单聊 | `si_` | `si_userA_userB` |
| 群聊 | `sg_` | `sg_groupID` |
| 通知 | `n_` | `n_userA_userB` |

前缀的价值在于：拿到一个 conversationID，不查库就能知道它是什么类型（判断前缀即可），从而走不同的处理分支。这是一个很实用的工程技巧——**把类型信息编码进 ID**。

> 注意一个容易踩的坑：MQ 的分区键（key）和会话 ID **不是同一个东西**。单聊的 MQ key 是 `userA_userB`（排序拼接，**不带 `si_` 前缀**），群聊的 MQ key 就是 `groupID`。这个差异在第二部分 10.15 节会具体指出，读代码时非常容易看漏。

## 10.4 发送的「契约」：ACK、超时、重试、幂等

### 10.4.1 什么是 ACK

ACK 就是「确认收到」。它是可靠传输的基石。

在 IM 里其实有**两层 ACK**，很多人只想到第一层：

| 层级 | 谁发给谁 | 含义 |
|---|---|---|
| **第一层** | 服务端 → 发送者 | 「你的消息我收下了」（本篇讲的就是这个） |
| **第二层** | 接收方 → 服务端 → 发送者 | 「我已经收到了你那条消息」（已读回执，第 14 篇讲） |

第一层 ACK 的关键在于：它保证的是「**我已经负责了**」，而不是「**已经处理完了**」。

这是一个非常重要的语义差别。用快递类比：

- 你把包裹交给快递员，快递员给你一张单子 → 这是第一层 ACK（责任转移）
- 收件人签收 → 这是第二层 ACK（送达完成）

本篇讲的 `SendMsg` 返回，就是「快递员收件」。包裹还没到收件人手里，甚至还没上飞机。

### 10.4.2 至少一次（at-least-once）与幂等

分布式系统里有三种投递语义：

| 语义 | 含义 | 实现难度 | 典型场景 |
|---|---|---|---|
| **至多一次** at-most-once | 可能丢，不重复 | 简单 | 日志采集、埋点 |
| **至少一次** at-least-once | 不丢，可能重复 | 中等 | **IM、支付通知** |
| **恰好一次** exactly-once | 不丢不重 | 很难 | 金融账务（通常靠幂等模拟） |

IM 选择的是「至少一次」，因为**丢消息比重复消息严重得多**。重复消息用户体验上顶多看到两条一样的，丢消息则可能导致业务事故。

而「至少一次」必然带来重复，所以**下游每一个环节都必须能处理重复**：

| 环节 | 防重复手段 |
|---|---|
| 客户端重试 | ClientMsgID（客户端自己配对，不重复插入气泡） |
| 服务端接收 | ServerMsgID（服务端为每次接收生成，但内容相同的重试要靠业务去重） |
| Redis 写入 | 以 seq 为 hash field，重复写覆盖同一格（天然幂等） |
| Mongo 写入 | 先 update 命中则跳过，未命中才 insert；insert 撞主键转 update（第 13 篇） |
| 推送 | 客户端按 seq 去重 |

**记住一句话：整条链路没有一个环节假设「消息只会来一次」。**

### 10.4.3 超时怎么定

发送接口的超时设置是个权衡：

- 太短（比如 100ms）→ 正常请求也被判超时，客户端疯狂重试，放大流量
- 太长（比如 30s）→ 用户盯着转圈，体验差；故障时连接被长时间占用

OpenIM 的 `SendMsg` 路径上有几个必须串行完成的动作：一次权限校验（可能查本地缓存，miss 时走 gRPC 到 group/user 服务）、一次 Kafka 投递。正常情况都在毫秒级。所以客户端 SDK 一般给 3–10 秒。

## 10.5 为什么发送时要校验：六个维度

用户点了发送，服务端凭什么相信他有权发这条消息？

答案是：**什么都不信，逐项校验**。这是 IM 与普通业务系统最大的安全差异之一——普通系统校验「你有没有登录」，IM 还要校验「你能不能给这个人发」「你在这个群里是什么身份」。

### 10.5.1 身份维度：你真的是你吗

最外层，HTTP/WS 层已经验过 token（第 05、06 篇）。但这只证明「这个连接是 userA 的」。

还要防一手：**请求体里声明的 SendID 必须是当前登录用户**。否则 userA 可以构造一个 `SendID=userB` 的请求，冒充别人发消息。

这个检查在 RPC 层做，叫 `CheckAccess`——因为 API 层可以绕过（比如服务间调用），RPC 层才是最后一道门。

### 10.5.2 关系维度：陌生人能给你发消息吗

单聊场景，要判断：

- **是否被拉黑**：B 把 A 拉黑了，A 就不能发
- **是否好友**：这一条是**可配置**的。很多产品允许「陌生人可发一条」，有些则要求必须是好友

注意这里有个易错点：好友校验是**开关**，不是硬编码。因为不同产品的策略不同。

### 10.5.3 群维度：你在群里吗，你被禁言了吗

群聊的校验明显更长，因为它有更多状态：

1. 群是否存在、是否已解散（解散了还能不能发？只有「群已解散」这条通知能发）
2. 是不是超级群（超级群成员太多，跳过成员校验——这是一个性能取舍）
3. 发送者是不是管理员（管理员豁免大部分限制）
4. 发送者是不是群成员（不在群里不能发）
5. 是否被单独禁言（`MuteEndTime` 未到）
6. 群是否全员禁言（此时只有群主和管理员能发）

**注意这里的顺序**：从「最便宜、最能提前短路」的检查开始，贵的检查放后面。查群信息比查成员列表便宜，所以群状态检查在最前。

### 10.5.4 内容维度：通知类消息豁免

系统通知（`ContentType` 落在 `[NotificationBegin, NotificationEnd]` 区间内）不受上面这些限制。否则「你已被移出群」这条通知都发不出去——因为发送者（系统）不在群里。

这是一个很典型的**元规则**：**规则的执行者本身常常需要豁免规则。**

### 10.5.5 接收者维度：对方愿不愿意收

这一层最容易被忽略，但它和「发送者能不能发」是两件事：

| 接收偏好 | 行为 |
|---|---|
| 接收消息 | 正常 |
| 不接收消息 | **消息直接丢弃**（连发都不发） |
| 接收但不提醒 | 消息照发，但不做离线推送 |

而且这个偏好有**两级**：用户级全局设置 + 单个会话级设置。会话级优先于全局级。

### 10.5.6 为什么这些校验必须在「发送时」做

有人可能会想：能不能异步校验？反正消息已经进队列了。

**不能。** 因为校验失败必须是**同步返回错误**给用户的。用户点了发送，你告诉他「成功了」，结果三秒后消息被悄悄丢弃——这是灾难性体验。

所以校验是唯一一个「必须留在同步路径上」的步骤。这是第 10.1.2 节那个切割的边界所在：**校验同步，其余异步**。

## 10.6 消息开关（Options）：用一个 map 控制十一种行为

### 10.6.1 问题：一条消息的行为维度太多

一条消息发出去之后，服务端要对它做很多决策：

- 要不要存历史记录？（打字状态不用存）
- 要不要计入未读数？（已读回执不计）
- 要不要做离线推送？（静音消息不推）
- 要不要更新会话列表的「最后一条消息」？
- 要不要同步给发送者自己的其他端？
- 这条消息是「通知」还是「普通消息」？

这些决策**不是按消息类型硬编码的**，因为同一种消息类型在不同场景下需求不同。比如「@所有人」的通知，既要有历史记录，又不要计入未读。

### 10.6.2 解法：把决策提取成一组布尔开关

OpenIM 的做法是：给每条消息挂一个 `map[string]bool`，key 是开关名，value 是开关状态。

好处是：

- **可扩展**：加一个新行为，只加一个 key，不用改函数签名
- **可覆盖**：默认值在构造时设定，具体场景在发送前覆盖
- **可透传**：这个 map 会一路带到存储层、推送层，各层自己读自己关心的开关

坏处也很明显：

- **没有编译期检查**：key 写错一个字母，编译通过，运行时静默走默认值
- **默认值语义反直觉**：这个 map 有一个特殊约定——**key 不存在时视为 true**。也就是说「没设置」等于「开启」。这个设计非常容易让新人写出 bug，第 10.14 节会详细分析。

### 10.6.3 开关名清单

从源码中能读到 11 个开关，按用途归类如下：

| 类别 | 开关 | 含义 |
|---|---|---|
| **分类** | `IsNotNotification` | 这是普通消息还是通知 |
| | `IsSendMsg` | 是否需要克隆出一条「给用户看」的消息 |
| **存储** | `IsHistory` | 是否存历史（进 Mongo） |
| | `IsPersistent` | 是否持久化 |
| **通知** | `IsOfflinePush` | 是否离线推送 |
| | `IsUnreadCount` | 是否计入未读 |
| **同步** | `IsSenderSync` | 是否同步给发送者其他端 |
| **会话** | `IsConversationUpdate` | 是否更新会话「最后一条」 |
| | `IsSenderConversationUpdate` | 是否更新发送者自己的会话 |
| **其它** | `IsNotPrivate` | 是否非私密（用于读扩散判断） |
| | `IsReactionFromCache` | 表情回复是否从缓存取 |

## 10.7 为什么发送接口不落库

这是本篇最核心的架构结论，值得单独一节。

### 10.7.1 一条消息在 OpenIM 里经过的站点

```
发送接口（rpc/msg SendMsg）
   ↓ 只做：校验 + 补字段 + 投 MQ
Kafka: toRedis
   ↓ msgtransfer 消费、聚合、分配 seq、写 Redis
   ├→ Kafka: toMongo   → 落 Mongo（真正的持久化）
   └→ Kafka: toPush    → 推送（在线/离线）
```

发送接口返回成功时，消息躺在 Kafka 里。**Kafka 是它的第一个「安全位置」。**

### 10.7.2 这样做安全吗

会有人担心：Kafka 里的消息会不会丢？

Kafka 的可靠性来自两点：

1. **副本**：每个 partition 有多个副本，leader 挂了 follower 顶上
2. **持久化**：消息落盘（不是纯内存）

所以「进了 Kafka」在工程上已经可以算「不会丢」了（前提是生产端配置了合适的 acks，OpenIM 用的是同步发送 + 等待确认）。

### 10.7.3 代价是什么

三个代价，必须清楚：

**代价一：最终一致性。** 发送成功 ≠ 可查询。如果客户端发完消息立刻调「拉取历史消息」，可能拉不到——因为消息可能还没落 Mongo。这就是为什么客户端必须用「本地插入 + 推送对齐」的策略，而不能依赖「发完立刻查」。

**代价二：发送者看不到 seq。** 10.2.3 节讲过。

**代价三：发送成功率与落库成功率解耦。** 如果 Kafka 投递成功但后续落库一直失败，用户会看到「发送成功」，但消息实际丢了。所以监控上必须分开看两个指标：`SingleChatMsgProcessSuccessCounter`（发送接口侧）和 `MsgInsertMongoSuccessCounter`（落库侧）。**这两个指标的差值就是「黑洞消息」的数量**——一个非常值得关注的线上指标。

### 10.7.4 为什么不能「同步写 Redis 就够了」

有人会想：那至少把消息同步写进 Redis 吧，Redis 那么快。

问题是：**Redis 不是可靠存储**。它可能因为内存策略淘汰 key，也可能因为主从切换丢最后一段数据。用 Redis 当消息的真源，等于把可靠性交给一个不保证持久化的组件。

OpenIM 的做法是：**Redis 用于「可重建的加速层」，Mongo 才是真相**。所以 Redis 写失败不影响消息继续落库（第 11 篇会看到代码里对这个错误的特殊处理：只忽略 `redis.Nil`，其它错误记日志但不阻断后续流程）。

## 10.8 Webhook：把业务钩子外置

### 10.8.1 什么是 Webhook

Webhook 直译「网络钩子」，本质是**反向回调**：系统在关键节点主动向你配置的 URL 发一个 HTTP 请求，你可以：

- 只观察（记录审计日志）
- 修改数据（在发送前改写消息内容）
- 拒绝操作（返回错误，中断流程）

用类比说：普通接口是「你打电话问我」，Webhook 是「我到点了给你打个电话通知你」。

### 10.8.2 为什么 IM 需要 Webhook

因为 IM 是**基础能力**，业务方有无数定制需求：

- 敏感词过滤（发送前把消息内容过一遍）
- 消息审计（谁在什么时候给谁发了什么）
- 积分/风控（发消息扣积分，异常频率拦截）
- 特殊消息改写（把某个 emoji 替换成内部表情 ID）

如果这些都做进 IM 核心，代码会烂掉。所以设计成**外置钩子**：核心只负责在正确的位置调用你。

### 10.8.3 OpenIM 的钩子位置

从源码能看到至少这些时机：

| 钩子 | 时机 | 能否修改数据 |
|---|---|---|
| `BeforeSendSingleMsg` | 单聊发送前 | 能（校验/拒绝） |
| `BeforeSendGroupMsg` | 群聊发送前 | 能 |
| `BeforeMsgModify` | 消息落 MQ 前 | **能改消息体** |
| `AfterSendSingleMsg` | 单聊发送后（异步） | 不能 |
| `AfterSendGroupMsg` | 群聊发送后（异步） | 不能 |
| `AfterMsgSaveDB` | 落库后 | 不能 |
| `BeforeOnlinePush` | 在线推送前 | 能改推送目标 |
| `BeforeOfflinePush` | 离线推送前 | 能改推送目标 |

这里有个设计上很讲究的细节：**`BeforeMsgModify` 可以把原始消息存一份副本（before），发送完成后对比，如果 webhook 改了内容，就把修改后的消息放在响应的 `Modify` 字段里返回给客户端。**

为什么？因为客户端已经把「原文」插进本地数据库了。如果服务端改成了敏感词替换版，客户端要能拿到新版本去覆盖本地那条，否则用户 A 看到自己发的原文，用户 B 看到的是替换版，两边不一致。

这个机制叫**发送后回写修正**，是很典型的「先乐观展示、后纠偏」模式。

## 10.10 SendMsg：只有 16 行的入口

```go
// internal/rpc/msg/send.go:23-39
func (m *msgServer) SendMsg(ctx context.Context, req *pbmsg.SendMsgReq) (*pbmsg.SendMsgResp, error) {
	if req.MsgData == nil {
		return nil, errs.ErrArgs.WrapMsg("msgData is nil")
	}
	if err := authverify.CheckAccess(ctx, req.MsgData.SendID); err != nil {
		return nil, err
	}
	before := new(*sdkws.MsgData)
	resp, err := m.sendMsg(ctx, req, before)
	if err != nil {
		return nil, err
	}
	if *before != nil && proto.Equal(*before, req.MsgData) == false {
		resp.Modify = req.MsgData
	}
	return resp, nil
}
```

这 16 行里有三件事值得停下来看。

### 10.10.1 `CheckAccess` 是最后一道门

`authverify.CheckAccess(ctx, req.MsgData.SendID)` 做的事是：从 gRPC context 的 metadata 里取出「当前调用者是谁」，和 `req.MsgData.SendID` 比对。

**为什么 API 层验过 token 了，这里还要再验一次？**

因为 RPC 层不只被 API 调用。它还被：
- 其他 RPC 服务调用（内部服务间互调）
- 消息中转服务调用（系统自己给自己发通知）
- 管理后台调用
- 直连（如果端口暴露了）

API 层的 token 校验只保护 HTTP 入口。**RPC 层必须自己再守一次**，这是纵深防御（Defense in Depth）。

而且这里有个很关键的设计：**授权在 RPC 层，认证在 API 层**。第 05 篇讲过这个分工。

### 10.10.2 `before` 是个 `**sdkws.MsgData`

这个双指针看起来很奇怪，它的用途是**让下游函数可以选择性地「录像」**。

调用方传一个「空的指针的地址」进来。下游如果想知道「webhook 有没有改消息」，就在调用 webhook **之前**把自己收到的消息存进这个指针：

```go
*before = proto.Clone(req.MsgData)   // 概念示意
```

调用返回后，把 `*before`（原始快照）和 `req.MsgData`（可能被改过的当前值）做 `proto.Equal` 比较。不相等就说明被改了，把新值塞进 `resp.Modify`。

**为什么要用双指针而不是返回值？**

因为 `sendMsg` 已经有 3 个返回场景（单聊/群聊/通知），如果再加一个「原始消息」返回值，三个分支都要多返回一个值，而其中有些分支根本不会修改消息（比如通知分支压根没调 webhook）。用指针做「出参」，让**需要它的分支才写**，代码更省事。

这是一个典型的 Go 风格取舍：牺牲一点可读性，换调用点的简洁。

### 10.10.3 没有 `defer recover`

注意 `SendMsg` 没有 `defer func(){ recover() }()`。这依赖 gRPC 拦截器链里的 `PanicCapture`（第 08 篇讲过 `startrpc.Start` 注册的 5 个内置拦截器）。

**这意味着：如果直接调用 `SendMsg`（不走 gRPC），panic 会直接冒上去。** 这是个隐含约定，写单测时要小心。

## 10.11 分流：三种会话类型

```go
// internal/rpc/msg/send.go:41-53
func (m *msgServer) sendMsg(ctx context.Context, req *pbmsg.SendMsgReq, before **sdkws.MsgData) (*pbmsg.SendMsgResp, error) {
	m.encapsulateMsgData(req.MsgData)
	switch req.MsgData.SessionType {
	case constant.SingleChatType:
		return m.sendMsgSingleChat(ctx, req, before)
	case constant.NotificationChatType:
		return m.sendMsgNotification(ctx, req, before)
	case constant.ReadGroupChatType:
		return m.sendMsgGroupChat(ctx, req, before)
	default:
		return nil, errs.ErrArgs.WrapMsg("unknown sessionType")
	}
}
```

### 10.11.1 为什么先 `encapsulateMsgData` 再分流

因为「补 ServerMsgID 和 SendTime」对所有类型都一样，属于**公共前置动作**。放在 switch 前面，避免三个分支各写一遍。

这是一个非常常见的重构手法：**把分支里的重复前置逻辑提到分支前**。

### 10.11.2 三种类型的处理差异

| 类型 | 是否校验 | 接收偏好 | webhook | 特殊逻辑 |
|---|---|---|---|---|
| 单聊 `SingleChatType` | ✅ `messageVerification` | ✅ 会丢弃 | Before/After 单聊钩子 | 无 |
| 群聊 `ReadGroupChatType` | ✅ `messageVerification` | ❌ | Before/After 群聊钩子 | `@` 处理 |
| 通知 `NotificationChatType` | ❌ 完全不校验 | ❌ | ❌ | 无 |

**通知类型为什么完全不校验？**

看代码：

```go
// internal/rpc/msg/send.go:147-157
func (m *msgServer) sendMsgNotification(ctx context.Context, req *pbmsg.SendMsgReq, before **sdkws.MsgData) (resp *pbmsg.SendMsgResp, err error) {
	if err := m.MsgDatabase.MsgToMQ(ctx, conversationutil.GenConversationUniqueKeyForSingle(req.MsgData.SendID, req.MsgData.RecvID), req.MsgData); err != nil {
		return nil, err
	}
	resp = &pbmsg.SendMsgResp{
		ServerMsgID: req.MsgData.ServerMsgID,
		ClientMsgID: req.MsgData.ClientMsgID,
		SendTime:    req.MsgData.SendTime,
	}
	return resp, nil
}
```

整个函数只做了一件事：投 MQ。没有校验，没有 webhook，没有接收偏好。

**原因**：通知是服务端自己产生的（「你已被踢出群」「你的好友申请通过了」），不来自用户输入。**服务端自己发的东西不需要防自己。** 唯一的防线是 `SendMsg` 顶部的 `CheckAccess`——但即使是这个，系统内部调用时也会带上是管理员/系统账号的身份。

> 这是一个很值得在面试里提的设计判断：**校验的成本要按「输入的信任等级」分配，不是所有路径都要全套校验。**

### 10.12.1 ServerMsgID 怎么生成

```go
// internal/rpc/msg/verify.go:157-160
func GetMsgID(sendID string) string {
	t := timeutil.GetCurrentTimeFormatted()
	return encrypt.Md5(t + "-" + sendID + "-" + strconv.Itoa(rand.Int()))
}
```

`MD5(时间字符串 + "-" + sendID + "-" + 随机数)`。

**这个实现有两个值得注意的点：**

1. **故意不要求绝对唯一**。MD5 有碰撞概率，但输入含随机数，实际碰撞率可以忽略。用 MD5 而不是 UUID，是因为 MD5 是 32 位十六进制字符串，比 UUID 短，索引更省空间。
2. **`rand.Int()` 用的是全局 math/rand**。如果没有 seed（Go 1.20+ 自动 seed），在极端并发下可能撞。更严谨的做法是用 `crypto/rand` 或 snowflake。这是一个可以指出的改进点。

### 10.12.2 SendTime 的 `if == 0` 判断

为什么要判断？因为**发送时间允许客户端指定**。

有些场景需要补发历史消息（比如从别的系统迁移过来），客户端会带一个历史时间戳。此时服务端不应该覆盖它。

但注意：`BatchInsertChat2Cache` 里**强制覆盖了 SendTime**（第 12 篇会讲），所以这个「允许客户端指定」的意图在落库时会被抹平。这是一个实际存在的语义冲突：

- 发送接口：允许客户端指定 SendTime
- 中转落库：强制所有同批消息用同一个 SendTime

结果就是「客户端指定的时间会被丢弃」。你可以自己去验证这一点（第三部分实验 3）。

### 10.12.3 按内容类型改写开关

这是全篇最实用的一个知识点。看四组：

**第一组：普通消息类型（Text/Picture/Voice/...）**

`case` 分支是**空的**——什么都不做。因为默认开关在 `NewOptions` 里已经设好了，普通消息不需要特殊处理。

**第二组：撤回消息（`Revoke`）**

```go
datautil.SetSwitchFromOptions(msg.Options, constant.IsUnreadCount, false)
datautil.SetSwitchFromOptions(msg.Options, constant.IsOfflinePush, false)
```

撤回消息：
- **不计未读**：你撤回一条消息，对方不应该多一个未读红点
- **不离线推送**：半夜撤回一条消息把对方手机震醒，是产品事故

**第三组：已读回执（`HasReadReceipt`）**

```go
datautil.SetSwitchFromOptions(msg.Options, constant.IsConversationUpdate, false)
datautil.SetSwitchFromOptions(msg.Options, constant.IsSenderConversationUpdate, false)
datautil.SetSwitchFromOptions(msg.Options, constant.IsUnreadCount, false)
datautil.SetSwitchFromOptions(msg.Options, constant.IsOfflinePush, false)
```

已读回执要关掉**四个**开关。最关键的是前两个：**不能让「已读回执」变成会话列表里的「最后一条消息」**。否则你打开一个聊天窗口，会话列表里那一行会变成「对方已读」，而不是最后一条实际聊天内容。

这就是 IM 里「不可见消息」的概念：它要传输、要处理，但**不能污染用户的可见状态**。

**第四组：正在输入（`Typing`）**

关掉 **七个** 开关：

```go
IsHistory           // 不存历史（打字状态存了没意义）
IsPersistent        // 不持久化
IsSenderSync        // 不同步给发送者自己其他端（我在手机打字，电脑不用显示）
IsConversationUpdate
IsSenderConversationUpdate
IsUnreadCount
IsOfflinePush
```

打字状态是**瞬时状态**，不是消息。它只需要「从 A 的客户端传到 B 的客户端」，传完就没了。所以它把「所有需要留下痕迹」的开关全关掉，只保留「推送」这一条路。

> 这四个分组体现了同一个设计原则：**一条消息的「生命周期长度」不同，需要的开关组合就不同。**
> - 普通消息：全生命周期（存、推、计未读、进会话）
> - 撤回：短生命周期但可见（推、更新会话，不计未读）
> - 已读回执：静默传递（推，不更新会话）
> - 打字：纯瞬时（只推）

```go
memberIDs, err := m.GroupLocalCache.GetGroupMemberIDMap(ctx, data.MsgData.GroupID)
if _, ok := memberIDs[data.MsgData.SendID]; !ok {
	return servererrs.ErrNotInGroupYet.Wrap()
}

// verify.go:106-112  闸门 6：取成员详情
groupMemberInfo, err := m.GroupLocalCache.GetGroupMember(ctx, ...)

// verify.go:113-114  闸门 7：群主豁免
if groupMemberInfo.RoleLevel == constant.GroupOwner {
	return nil
}

// verify.go:116-122  闸门 8：禁言检查
if groupMemberInfo.MuteEndTime >= time.Now().UnixMilli() {
	return servererrs.ErrMutedInGroup.Wrap()
}
if groupInfo.Status == constant.GroupStatusMuted && groupMemberInfo.RoleLevel != constant.GroupAdmin {
	return servererrs.ErrMutedGroup.Wrap()
}
```

几个非常值得记住的细节：

**细节 1：超级群为什么直接放行？**

超级群（SuperGroup）动辄上万人。如果每条消息都去校验「发送者是不是成员」，就是每发一条消息查一次上万人的成员列表——即使有本地缓存，首屏加载也是灾难。

这是**功能为性能让步**的显式取舍。安全上的补丁是：超级群的加群方式通常更严格（需要审批），所以「成员身份」的假设在入口处已经保证了。

**细节 2：解散的群为什么还要允许发「群已解散」通知？**

因为解散这个动作本身需要发一条通知告诉所有成员。如果解散后群里什么都不能发，这条通知就发不出去。所以做了一个精确的例外。

**精确的例外**比「放宽整体规则」好得多——这是设计上的克制。

**细节 3：禁言有两条独立的规则**

| 规则 | 来源 | 谁能豁免 |
|---|---|---|
| 单人禁言 | `groupMemberInfo.MuteEndTime` | 群主 |
| 全员禁言 | `groupInfo.Status == GroupStatusMuted` | 群主、管理员 |

注意全员禁言那条判断：`RoleLevel != constant.GroupAdmin`。也就是说：
- 群主 → 上面已经 `return nil` 了
- 管理员 → 全员禁言时**可以发**
- 普通成员 → 被拦

这是符合产品直觉的（管理员要能发公告）。

### 10.13.3 一个隐藏的调用开销

`GetGroupInfo`、`GetGroupMemberIDMap`、`GetGroupMember` 三次调用，看起来是三次远程查询。实际上它们是**本地缓存**（`rpccache.GroupLocalCache`），只有 miss 时才走 gRPC。

但 `GetGroupMemberIDMap` 在万人群里，即使是缓存也是一次返回上万个 ID 的 map——内存拷贝代价不小。

**这解释了一个现象**：为什么群聊的发送接口 P99 延迟通常明显高于单聊。你如果压测过就会发现这个差异（第三部分实验 4 会验证）。

## 10.14 Options 的实现：一个反直觉的默认值约定

```go
// pkg/msgprocessor/options.go:109-115
func (o Options) Is(notification string) bool {
	v, ok := o[notification]
	if !ok || v {
		return true
	}
	return false
}
```

**这三行的语义是：key 不存在时，返回 true。**

这不是笔误。它意味着：

- `IsHistory()` 在 key 缺失时返回 **true**（会存历史）
- `IsOfflinePush()` 在 key 缺失时返回 **true**（会离线推送）
- `IsUnreadCount()` 在 key 缺失时返回 **true**（会计未读）

把两个因素放一起看才明白它的意图：

```go
// pkg/msgprocessor/options.go:10-28
func NewOptions(opts ...OptionsOpt) Options {
	options := make(map[string]bool, 11)
	options[constant.IsNotNotification] = false
	options[constant.IsSendMsg] = false
	options[constant.IsHistory] = false
	options[constant.IsPersistent] = false
	options[constant.IsOfflinePush] = false
	options[constant.IsUnreadCount] = false
	options[constant.IsConversationUpdate] = false
	options[constant.IsSenderSync] = true
	options[constant.IsNotPrivate] = false
	options[constant.IsSenderConversationUpdate] = false
	options[constant.IsReactionFromCache] = false
	...
}
```

**`NewOptions` 显式把所有 key 都写成 false（除了 `IsSenderSync`），而 `Is()` 在 key 缺失时返回 true。**

这两个看似矛盾的设计合起来的效果是：

- 用 `NewOptions()` 构造的 map，所有开关都是 **false**
- 如果消息来自客户端（客户端可能根本没传 options），map 是空的 → 所有开关都是 **true**

**也就是说：客户端不传 options 时，服务端走「全部开启」的保守策略；内部构造的 options 走「全部关闭」的显式策略。**

这个设计的好坏可以争论，但它确实达成了「安全默认」：如果某个客户端老版本不传开关，服务端会老老实实存历史、推离线、计未读——不会因为字段缺失而丢功能。

### 10.14.1 一个确实存在的 bug

```go
// pkg/msgprocessor/options.go:30-34
func NewMsgOptions() Options {
	options := make(map[string]bool, 11)
	options[constant.IsOfflinePush] = false
	return make(map[string]bool)
}
```

**前两行构造的 map 被丢弃了，`return` 又新建了一个空 map。**

后果：

1. 第 32 行的赋值完全无效（`ineffectual assignment`，`go vet`/`golangci-lint` 应该能报出来）
2. 返回的空 map 会在 `Is()` 里被解读为「全部开启」

这个函数被 `categorizeMessageLists` 用来克隆通知消息的 options：

```go
// internal/msgtransfer/online_history_msg_handler.go:206-212
if v.message.Options != nil {
	msg.Options = msgprocessor.NewMsgOptions()
}
msg.Options = msgprocessor.WithOptions(msg.Options,
	msgprocessor.WithOfflinePush(options.IsOfflinePush()),
	msgprocessor.WithUnreadCount(options.IsUnreadCount()),
)
```

好在后面立刻用 `WithOptions` 显式设置了两个开关。所以**实际行为影响很小**——只有 `IsHistory`、`IsPersistent` 这些没被显式设置的开关会落到「true」。

但这是一个非常适合在面试里说的点：**「我在阅读时发现一个赋值即丢弃的实现，虽然当前因后续覆盖而未产生致命影响，但它暴露了 options 这套设计缺少编译期约束的问题。」**

## 10.15 MsgToMQ：整个发送链路的终点

```go
// pkg/common/storage/controller/msg.go:112-118
func (db *commonMsgDatabase) MsgToMQ(ctx context.Context, key string, msg2mq *sdkws.MsgData) error {
	data, err := proto.Marshal(msg2mq)
	if err != nil {
		return err
	}
	return db.producer.SendMessage(ctx, key, data)
}
```

就三行：protobuf 序列化 → 发送。但有两个细节极其重要。

### 10.15.1 key 是什么

看调用点：

```go
// 群聊 internal/rpc/msg/send.go:67
err = m.MsgDatabase.MsgToMQ(ctx,
	conversationutil.GenConversationUniqueKeyForGroup(req.MsgData.GroupID),
	req.MsgData)

// 单聊 internal/rpc/msg/send.go:178
if err := m.MsgDatabase.MsgToMQ(ctx,
	conversationutil.GenConversationUniqueKeyForSingle(req.MsgData.SendID, req.MsgData.RecvID),
	req.MsgData); err != nil {
```

再看这两个函数：

```go
// pkg/util/conversationutil/conversationutil.go:14-16
func GenConversationUniqueKeyForGroup(groupID string) string {
	return groupID
}

// pkg/util/conversationutil/conversationutil.go:30-34
func GenConversationUniqueKeyForSingle(sendID, recvID string) string {
	l := []string{sendID, recvID}
	sort.Strings(l)
	return strings.Join(l, "_")
}
```

**关键点：单聊的 MQ key 是 `userA_userB`，没有 `si_` 前缀；而 conversationID 是 `si_userA_userB`。**

这不是同一个东西。对比一下：

| 函数 | 输入 | 输出 |
|---|---|---|
| `GenConversationIDForSingle("A","B")` | A, B | `si_A_B` |
| `GenConversationUniqueKeyForSingle("A","B")` | A, B | `A_B` |
| `GenConversationUniqueKeyForGroup("G")` | G | `G` |

**为什么要区分？**

- `conversationID` 用于存储层（会话表、消息文档 ID 前缀），需要带类型前缀以便区分
- `UniqueKey` 用于 MQ 分区，只需要「同一会话得到同一个值」，越简单越好

但这就带来一个隐患：**MQ 层不区分单聊和群聊**。如果一个群 ID 恰好是 `A_B` 这种格式（先不管现实约束），它就会和单聊的 key 撞上，被分到同一个 partition、同一个批处理分片。

实际风险很低（群 ID 是系统生成的随机串），但这是一个**命名空间没隔离**的设计瑕疵。可以把 MQ key 也加上前缀来彻底解决。

### 10.15.2 为什么 key 这么关键

因为下游的批处理框架用它做**分片**：

```go
// internal/msgtransfer/online_history_msg_handler.go:95-98
b.Sharding = func(key string) int {
	hashCode := stringutil.GetHashCode(key)
	return int(hashCode) % och.redisMessageBatches.Worker()
}
```

同一个 key（同一会话）永远落到同一个 worker（只要 Worker 数量不变）。

**这是「同会话有序」的第一块基石**，第 11 篇会完整展开。

而 Kafka 侧的分区也依赖 key：生产端按 key 哈希选 partition，同一个 key 进同一个 partition，也就保证了消费顺序。

**所以 key 的选择同时影响两件事：Kafka 分区保序 + 内存批处理分片保序。这两层都必须保序，缺一不可。**

## 10.16 @所有人：为什么必须异步

```go
// internal/rpc/msg/send.go:71-73
if req.MsgData.ContentType == constant.AtText {
	go m.setConversationAtInfo(ctx, req.MsgData)
}
```

注意这个 `go`。

### 10.16.1 setConversationAtInfo 做了什么

看 `send.go:85-145`，逻辑分两条：

**情况 A：@所有人**

```go
tagAll := datautil.Contain(constant.AtAllString, msg.AtUserIDList...)
if tagAll {
	memberUserIDList = datautil.DeleteElems(memberUserIDList, msg.SendID)  // 排除自己
	atUserID = datautil.Single([]string{constant.AtAllString}, msg.AtUserIDList)

	if len(atUserID) == 0 {  // 只 @所有人
		conversation.GroupAtType = &wrapperspb.Int32Value{Value: constant.AtAll}
	} else {  // @所有人 + 具体某人
		conversation.GroupAtType = &wrapperspb.Int32Value{Value: constant.AtAllAtMe}
		... SetConversations(atUserID, conversation)  // 先给被点名的人设 AtAllAtMe
		memberUserIDList = datautil.Single(atUserID, memberUserIDList)
	}
	conversation.GroupAtType = &wrapperspb.Int32Value{Value: constant.AtAll}
	SetConversations(memberUserIDList, conversation)  // 剩下的设 AtAll
}
```

注意这里的**两阶段写入**：

1. 先给「被点名的少数人」设 `AtAllAtMe`（既 @我 又 @所有人）
2. 再从剩余名单里剔除这些人，给剩下的设 `AtAll`

为什么要分开？因为 `UpdateMany` 是覆盖式的：如果用同一个 `GroupAtType` 写给所有人，那被点名的人就只剩 `AtAll`，丢掉「@我」这个更强的提示。

**这是一个很细的细节，也是面试可以炫的点：批量更新时，不同分组要写不同的值，就必须分组多次写，不能一次覆盖。**

**情况 B：只 @具体的人**

```go
// send.go:137-144
atUserID = datautil.SliceIntersectFuncs(msg.AtUserIDList, memberUserIDList, ...)
conversation.GroupAtType = &wrapperspb.Int32Value{Value: constant.AtMe}
SetConversations(atUserID, conversation)
```

用**交集**：只有当被 @ 的人确实在群里，才给他设置标记。

这是防御性设计——客户端可能 @ 一个已经退群的人。

### 10.16.2 为什么必须 `go`

`SetConversations` 是**对每个被 @ 的用户**做一次会话更新。@所有人 = 给全群每个成员更新会话。

一个 1000 人群，这就是 1000 次会话写入。如果同步做，发送接口要等 1000 次写完才返回，用户看到的就是「转圈 2 秒」。

所以必须异步。而且代码里做了两层保护：

```go
// send.go:89-93
defer func() {
	if r := recover(); r != nil {
		log.ZPanic(nctx, "setConversationAtInfo Panic", errs.ErrPanic(r))
	}
}()
```

`go` 出去的函数**必须自己 recover**，否则 panic 会直接导致整个进程崩溃（goroutine 里的 panic 不会被外层 recover 捕获）。这是 Go 并发的铁律。

还有一个很巧妙的细节：

```go
// send.go:95
ctx := mcontext.NewCtx("@@@" + mcontext.GetOperationID(nctx))
```

给异步任务造了一个新 context，但**把原始 operationID 拼上 `@@@` 前缀**保留下来。

为什么？因为原始 ctx 在函数返回后可能被取消（gRPC ctx 是请求级的）。但链路追踪又需要把异步任务和原请求关联起来。所以造一个新 ctx（不受取消影响），同时把 operationID 带着。

**`@@@` 是人为加的标记**，方便在日志里 grep 出「这是异步 @ 处理产生的日志，不属于原请求的同步链路」。

> 这个小技巧很值得学：**异步任务留痕的正确做法是「新 ctx + 继承追踪 ID + 加标记」，而不是直接把原 ctx 传进去（会随请求取消而失效），也不是完全丢掉（会丢失可观测性）。**

### 10.17.1 SendSimpleMsg

**它比 `SendMsg` 多做了两件事：补发送者头像和昵称。**

这是给**服务端内部调用**用的便捷接口。普通客户端发消息时，头像是客户端传的（或者客户端不传，服务端从缓存补）。而这个接口专门服务「服务端自己也想发一条长得像用户发的消息」的场景——比如从业务系统导入一条历史消息。

### 10.17.2 客户端到底怎么发消息

这里必须澄清一个高频误区：

**普通客户端不能走 HTTP 的 `/msg/send_msg`。** 那个接口要求管理员身份。

普通用户发消息的唯一路径是 **WebSocket**：

```
WS 连接 → Req{reqIdentifier: SendMsg, token, data: base64(pb MsgData)}
  → msggateway 解码
  → gRPC 调用 rpc/msg.SendMsg
```

这个设计的原因：HTTP 是无状态的，每次发消息都要重新建连、重新验 token；而 IM 用户是长连接在线的，走已建立的 WS 连接可以省掉整个 HTTP 握手和鉴权开销。

第 06、07 篇讲过这条链路的细节。这里只需要记住：**WS 是唯一入口，`/msg/send_msg` 是管理端接口。**

## 10.18 设计评价：这套设计的得与失

### 10.18.1 做得好的地方

| 设计 | 好处 |
|---|---|
| 校验同步、其余异步 | 用户感知的延迟只取决于校验 + 一次 MQ 投递 |
| Options 开关集中管理 | 行为可组合，新消息类型不用改核心逻辑 |
| Webhook 外置 | 业务定制不污染核心 |
| `before` 快照机制 | Webhook 改消息后能回写纠偏客户端 |
| 通知类消息豁免校验 | 避免「规则执行者被规则挡住」 |
| 异步任务保留 operationID | 可观测性不打折 |

### 10.18.2 可以改进的地方

| 问题 | 位置 | 影响 | 建议 |
|---|---|---|---|
| `NewMsgOptions` 赋值即丢弃 | `options.go:30-34` | 返回的 map 缺默认值 | 改成 `return options` |
| Options 无编译期检查 | 全篇 | key 拼错静默失效 | 用带类型的常量 struct 或 `iota` 位图 |
| `GetMsgID` 用 math/rand | `verify.go:159` | 极端并发下有碰撞风险 | 换 snowflake 或用 crypto/rand |
| MQ key 与 conversationID 命名空间不隔离 | `conversationutil.go` | 理论上可能撞 key | MQ key 也加类型前缀 |
| webhook 在核心校验之前 | `verify.go:50` | 被拉黑的用户仍会触发外部 HTTP 调用 | 把 webhook 放到黑名单检查之后 |
| `SendTime` 语义前后不一致 | `verify.go:131` vs `msg_transfer.go:212` | 客户端指定的时间被落库时覆盖 | 明确文档化或统一行为 |

### 10.18.3 一个必须理解的取舍：为什么不做同步落库

新手常问：「为什么不干脆同步写 Mongo，保证强一致？」

算一笔账：一条群消息要写 Mongo 一次（不是 500 次，因为消息归属于会话），单次写入假设 2ms。QPS 10 万时，Mongo 需要 20 万 IOPS 的写入能力——这已经超出单机 Mongo 的舒适区，必须分片。

而异步化之后，Mongo 的写入是**批量**的：一批最多 100 条（一个文档），一次写入覆盖 100 条消息。写入次数直接降到 1/100。

**这就是批处理的价值：它把「N 次网络往返」变成「N/100 次」。** 这是第 11、12 篇的核心主题。

# 第三部分 实验：亲手验证本篇的结论

> 前提：中间件已起（`docker compose up -d`），服务已构建并启动（`mage build && mage start`）。

## 实验 1：验证「发送成功但立即可查不到」（最终一致性窗口）

**目的**：亲眼看到发送返回成功时，消息还没落库。

**步骤**：

1. 用管理端接口发一条消息（`/msg/send_msg`，需要 admin token）：

```bash
ADMIN_TOKEN=$(curl -s -X POST "http://127.0.0.1:10002/auth/get_admin_token" \
  -H "Content-Type: application/json" -H "operationID: exp1" \
  -d '{"secret":"<见凭据文件>","userID":"imAdmin"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)

curl -s -X POST "http://127.0.0.1:10002/msg/send_msg" \
  -H "Content-Type: application/json" \
  -H "token: $ADMIN_TOKEN" \
  -H "operationID: exp1" \
  -d '{
    "sendID":"imAdmin",
    "recvID":"<某个已注册用户>",
    "sessionType":1,
    "contentType":101,
    "content":{"content":"实验1-验证异步落库"}
  }'
```

2. 立刻（不要等）查 Mongo：

```bash
docker exec -i <mongo容器名> mongosh --quiet -u <用户> -p <密码> --authenticationDatabase admin im_v3 \
  --eval 'db.msg.find().sort({_id:-1}).limit(1)'
```

**预期现象**：发送接口返回 `errCode: 0`，但 Mongo 查询可能还是上一次的结果（延迟通常在几十到几百毫秒）。

**如果查不到，再等 1 秒重查**——会出现。这就证明了「发送成功 ≠ 已落库」。

> 容器名可以用 `docker ps --format '{{.Names}}' | grep mongo` 查。

## 实验 2：验证 Seq 是服务端分配的

**目的**：证明同一个会话的消息，seq 严格递增且连续。

**步骤**：连续发 3 条消息，然后查 Mongo：

```bash
docker exec -i <mongo容器名> mongosh --quiet ... im_v3 \
  --eval 'db.msg.find().sort({_id:-1}).limit(1).forEach(d => {
    d.msgs.filter(m => m.msg).slice(-5).forEach(m => print(m.msg.seq, m.msg.content))
  })'
```

**预期现象**：三条件消息的 seq 是连续的三个数字（比如 47、48、49）。

**进阶验证**：并发发 10 条（用 `xargs -P 10`），你会发现 seq 依然连续无空洞——但顺序可能和你发送的顺序不完全一致。**这正是「会话内有序」的真正含义：有序指的是 seq 单调递增，不是指「你按发送顺序拿到的」。**

## 实验 3：验证 SendTime 会被覆盖

**目的**：验证 10.12.2 节说的「客户端指定的 SendTime 在落库时被抹平」。

**步骤**：发一条消息，故意带一个很早的 `sendTime`：

```bash
curl -s -X POST "http://127.0.0.1:10002/msg/send_msg" ... \
  -d '{"sendID":"imAdmin","recvID":"xxx","sessionType":1,"contentType":101,
       "content":{"content":"实验3-指定旧时间"},"sendTime":1600000000000}'
```

然后查响应和 Mongo 里的 `send_time`。

**预期现象**：

- 响应里的 `sendTime` 可能是你传的旧值（或服务端补的值，取决于是否走 `if msg.SendTime == 0` 分支）
- Mongo 里的 `send_time` 是**当前时间**（被 `BatchInsertChat2Cache` 覆盖了）

这个「不一致」就是本篇 10.12.2 节指出的语义冲突。

## 实验 4：验证群聊比单聊慢

**目的**：验证 10.13.3 节说的「群校验开销更大」。

**步骤**：各压 100 次，比 P99。

```bash
# 单聊
for i in $(seq 100); do
  curl -s -o /dev/null -w "%{time_total}\n" -X POST "http://127.0.0.1:10002/msg/send_msg" \
    -H "Content-Type: application/json" -H "token: $ADMIN_TOKEN" -H "operationID: perf-s-$i" \
    -d '{"sendID":"imAdmin","recvID":"userA","sessionType":1,"contentType":101,"content":{"content":"s"}}'
done | sort -n | tail -5

# 群聊（换成 sessionType:3 + groupID）
```

**预期现象**：群聊的尾部延迟明显更高。差距取决于群成员数量和缓存命中率。

> 注意：这测的是管理端 HTTP 接口，多了 HTTP 开销，但相对差异仍然成立。要更准确应该压 WS。

## 实验 5：验证 Options 的「缺省即开启」

**目的**：验证 `Is()` 在 key 缺失时返回 true。

**步骤**：发一条**不带 options** 的消息，然后看 Mongo 里存了什么。

```bash
curl -s -X POST ... -d '{"sendID":"imAdmin","recvID":"userA","sessionType":1,
  "contentType":101,"content":{"content":"实验5-无options"}}'
```

**预期现象**：消息正常存进了 Mongo（`IsHistory` 缺省为 true）。如果 `Is()` 的默认是 false，这条消息就会被当「不存历史」而丢掉。

**这个实验的意义**：让你亲身体会「默认值设计」对系统行为的决定性影响。

# 面试话术

## 30 秒版本（被问「你们消息发送怎么做的」）

> 发送链路是这么切的：WS 网关收到消息后 gRPC 调到 msg 服务，msg 服务只做三件事——身份校验、业务校验（黑名单、群成员、禁言）、补 ServerMsgID 和时间戳，然后把 protobuf 扔进 Kafka 的 toRedis topic 就返回成功。
>
> 落库和推送都不在同步路径上。消息由 msgtransfer 消费后分配会话内 seq、写 Redis、再分发到 toMongo 和 toPush。所以发送成功只代表「服务端接管了」，不代表「已可查询」——这是有意的最终一致性设计，换来的是发送接口的延迟只跟一次 MQ 投递相关。

## 3 分钟版本（被追问细节时补充）

在 30 秒版本基础上，按这个顺序展开：

1. **三个 ID 的分工**：ClientMsgID 是客户端的幂等键，ServerMsgID 是服务端唯一标识，Seq 是会话内序号、落库时才分配。发送响应里没有 seq，因为那时候还没分配。
2. **校验的六个维度**：身份（CheckAccess 挡冒充）、关系（黑名单/好友开关）、群（存在性/成员/禁言/全员禁言）、内容（通知类豁免）、接收偏好（对方不接收就直接丢）、以及可选的 webhook 外置钩子。
3. **Options 开关**：11 个布尔开关控制一条消息的生命周期。不同内容类型关掉不同的开关——撤回不计未读不推送，已读回执不更新会话，打字状态只推不存。
4. **一个具体的设计细节**（挑一个讲，显示你真读过代码）：
   - @所有人要分组两次写会话表，否则被点名的人会丢掉 `AtAllAtMe` 标记；
   - 或者：异步处理必须新建 ctx 并保留 operationID 加 `@@@` 前缀，否则原 ctx 取消后追踪断裂。
5. **主动说出改进点**：Options 用 map[string]bool 缺少编译期约束，我读代码时就发现 `NewMsgOptions` 有个赋值即丢弃的实现。

## 预判追问与答法

**Q：发送成功但用户查不到消息，这不是 bug 吗？**
A：是有意的。可靠性的边界划在「消息进了 Kafka」——Kafka 有副本和持久化，所以不会丢。而「可查询」需要等落库，这是异步的。客户端的产品设计必须配合这个模型：本地先插入气泡，收到推送后按 seq 对齐。如果强求「发完立刻可查」，就得同步写 Mongo，写入放大 100 倍，峰值扛不住。

**Q：如果 Kafka 投递成功但落库一直失败怎么办？**
A：这是个真实的可靠性缺口，用户会看到「发送成功」但消息实际丢了。工程上要靠两个手段：一是监控两个指标的差值（发送成功数 vs 落库成功数），差值持续不为零就告警；二是消费端不能吞错提交位点——OpenIM 的做法是批处理完成后才 `Mark + Commit`，失败就不提交，Kafka 会重投。重投带来的重复由 Mongo 的幂等写入吸收。

**Q：为什么要区分 notification 类型？**
A：两类需求不同。普通消息要排序、要未读、要推送；通知是系统事件（加群、踢人、撤回提示），它也要显示在会话里，但语义上是「事件」不是「聊天」。OpenIM 的 `NotificationChatType` 走的是 `n_` 前缀的独立会话，且完全跳过业务校验——因为发送方是系统自己，不来自用户输入。

**Q：一条消息在系统里最多可能重复几次？**
A：理论上不设上限（at-least-once + 无限重试）。所以设计上每个环节都要能吸收重复：客户端按 ClientMsgID 去重、Redis 按 seq 做 hash field 天然覆盖、Mongo 先 update 后 insert。没有一个环节假设「只来一次」。
