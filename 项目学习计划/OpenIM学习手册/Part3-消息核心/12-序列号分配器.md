# 12 序列号分配器：一个「自增」为什么要写三百行

> **本篇定位**：seq（序列号）看起来是最简单的东西——不就是自增 1 吗？但在分布式 IM 里，它是**全系统最关键、最容易出错、也最能体现工程功力**的一块。读完你应该能解释：
> - 为什么不能用时间戳排序
> - 为什么不能每条消息都去数据库自增
> - 「号段预分配」是怎么把数据库压力降两个数量级的
> - 为什么号段会制造「空洞」，空洞又该怎么补
> - Redis 的两个 Lua 脚本和「锁状态码」到底在防什么
>
> **阅读方式**：第一部分（12.1–12.9）纯理论；第二部分（12.10–12.17）源码；第三部分实验。
>

# 第一部分 理论：分布式自增为什么这么难

## 12.1 先想清楚：seq 到底用来干什么

很多人以为 seq 只是「给消息编个号，好看」。不是的。seq 承担了**四个功能**，每一个都不可替代。

### 12.1.1 功能一：排序（但为什么不用时间戳）

直觉上，消息都有 `sendTime`，按时间排序不就行了？

**不行。** 原因有三个，一个比一个致命。

**原因一：客户端时间不可信。**

用户的手机时间可能是错的——有人手动改过，有人时区不对，有人系统时钟漂移。如果两条消息靠客户端时间排序，你可能会看到「今天下午的消息」排在「昨天上午的消息」前面。

**原因二：同一个毫秒内无法区分先后。**

A 和 B 在同一毫秒各发一条消息（在热门群里，同一毫秒几十条消息太常见了）。时间戳相同，谁在前？无法判断。而 seq 是整数，绝不相同。

**原因三：时间戳无法表达「连续」。**

这是最本质的差异。时间戳是**稀疏**的（两条消息可能差 3 秒，也可能差 1 毫秒），而 seq 是**稠密**的（1, 2, 3, 4...）。

「稠密」这个性质带来一个巨大的好处：**你可以用「范围」来表达「我有哪些消息」。**

```
「我有 seq 1 到 100 的消息」         ← 一次表达，O(1)
「我有 100 条消息，时间从 T1 到 T2」  ← 无法确定中间有没有缺
```

有了这个性质，客户端同步模型就变成了极其简单的「比大小」：

```
本地记住 maxSeq = 100
重连时说：给我 seq > 100 的消息
服务端：SELECT WHERE seq > 100
```

**这一条链路的简洁性，全部来自「seq 稠密且单调」这个性质。**

### 12.1.2 功能二：同步（断线补偿）

用户在地铁里断网 5 分钟，重连后要拉这 5 分钟的消息。

如果没有 seq，怎么拉？按时间？时间不可靠。按「最后一条消息 ID」？那需要服务端支持「从这个 ID 之后拉」，本质上还是需要一个可比较的序号。

### 12.1.3 功能三：已读回执

「我已读到第 15 条」。用 seq 表达就是 `hasReadSeq = 15`，一个整数。

如果用消息 ID 表达，你得存一个列表——「我读过 msgID_1, msgID_2, ..., msgID_15」。消息一多，这个列表就爆炸了。

**这就是「用序号把集合压缩成一个数字」的威力。**

### 12.1.4 功能四：未读数

未读数 = `maxSeq - hasReadSeq`。

两个整数相减，O(1)。没有 seq 的话，未读数得靠「统计有多少条消息我没读」——一次 count 查询，随着消息量增长越来越慢。

> **这四个功能合起来说明一件事：seq 不是「排序用的编号」，它是「会话状态的坐标系」。** 有了它，所有跟「进度」有关的状态（读到哪、看到哪、删到哪）都能用一个整数表示。

## 12.2 三种常见的「自增」方案

### 12.2.1 方案一：数据库自增 ID

最朴素：

```sql
-- MySQL
INSERT INTO msg (...) VALUES (...);  -- id 自动 +1
```

或者 Mongo 的 `findOneAndUpdate({$inc: {seq: 1}})`。

**优点**：绝对单调、绝对连续、绝对不会重复（数据库保证）。

**缺点**：**每条消息一次数据库往返。**

算笔账：一个热门群，每秒 100 条消息。100 次数据库更新/秒，每次都要行锁（或文档锁）+ 写日志 + 等副本确认。

单看 100 QPS 不算高。但 OpenIM 要支撑的是**所有会话的总和**——1 万个活跃会话，每个每秒 10 条，就是 10 万 QPS 的自增请求。

而且这里有个隐藏问题：**同一个会话的自增是串行的**（因为要保证单调），所以同一个热门会话的并发写入会被数据库的行锁串行化。这是**热点行**问题，比总量更致命。

### 12.2.2 方案二：Snowflake（雪花算法）

Twitter 的经典方案：`时间戳(41位) + 机器ID(10位) + 序列号(12位)`。

**优点**：本地生成，无网络开销，性能极高（单机每秒几百万）。

**缺点**：**不连续**。

看它的结构就知道：时间戳在高位，序列号在低位。同一毫秒内连续，但**跨毫秒时会跳一大段**（因为低位归零，高位进位）。

比如：

```
...000 1111 1111 1111   (毫秒 T 的最后一条)
...001 0000 0000 0000   (毫秒 T+1 的第一条)
```

中间跳了 4096 个数字。

**这对 IM 是致命的**：seq 不连续，就没法用「范围」表达「我有哪些消息」，也没法用 `maxSeq - hasReadSeq` 算未读（会算出一个巨大的数）。

所以 Snowflake 适合做**消息 ID**（唯一即可，不需要连续），**不适合做 seq**。

> 这个对比很值得记住：**「唯一」和「连续」是两个不同的需求，需要不同的方案。** 很多人把 Snowflake 当万能 ID 生成器，用在需要连续序号的地方就出问题。

### 12.2.3 方案三：号段预分配（Segment）

这是 OpenIM 用的方案，也是美团 Leaf、滴滴 TinyID 等主流方案的核心思想。

**核心思路：一次向数据库申请一段（比如 50 个），在内存/Redis 里慢慢发。**

```
向 DB 申请：给我 50 个 → DB 返回 100（意思是：100~149 这段归你了）
本地发放：  100, 101, 102, ..., 149
发完了再申请下一段：150
```

**收益**：数据库写入次数从「每条消息一次」降到「每 50 条一次」——**降 50 倍**。群聊按 100 算，降 100 倍。

**代价**：**号段会浪费。**

如果进程在发到 120 的时候崩了，那么 121~149 这 29 个号就永久不会被使用。这就是 **「seq 空洞」**。

### 12.2.4 三种方案对比

| 维度 | DB 自增 | Snowflake | 号段 |
|---|---|---|---|
| 连续性 | ✅ 绝对连续 | ❌ 跳变 | ⚠️ 段内连续，段间可能有洞 |
| 性能 | 差（每条约一次 DB） | 极高（本地） | 高（每 N 条一次 DB） |
| 热点行问题 | ❌ 严重 | ✅ 无 | ✅ 大幅缓解 |
| 实现复杂度 | 低 | 中 | **高**（要处理锁、过期、空洞） |
| 依赖 | DB | 时钟 + 机器 ID | DB + 缓存 |

**OpenIM 选号段的理由**：IM 需要连续（排除 Snowflake），又扛不住每条一次 DB（排除 DB 自增），所以只能选号段，并**接受空洞的存在**。

## 12.3 空洞：号段模式的固有代价

### 12.3.1 空洞是怎么产生的

四个来源：

| 来源 | 例子 | 浪费量 |
|---|---|---|
| **进程崩溃** | 申请了 50 个，发了 20 个就崩了 | 剩 30 个 |
| **Redis key 过期** | 冷会话的号段在 Redis 里过期了 | 整段 |
| **分配成功但写失败** | Malloc 成功，但 `SetMessageBySeqs` 失败 | 这一段 |
| **多实例竞争失败** | 拿到了号段但被别的实例抢占（见 12.5） | 视实现 |

### 12.3.2 空洞为什么不能让客户端看到

假设客户端本地有 seq 到 100，服务端返回了 101、102、105（中间缺 103、104）。

客户端的同步逻辑通常是：

```go
for seq := localMax + 1; seq <= serverMax; seq++ {
    // 拉 seq 的消息
}
```

如果它期待「每个 seq 都有消息」，遇到 103、104 缺失就会：

- 一直重试拉 103（死循环）
- 或者认为同步未完成，卡住

**所以空洞必须被「填掉」或者「明示」。**

### 12.3.3 两种填洞策略

**策略 A：占位消息（墓碑）**

给空洞的 seq 生成一条「空消息」，客户端收到后跳过。OpenIM 在 model 层预留了这个能力：

```go
// pkg/common/storage/model/msg.go:133-140
func (*MsgDocModel) GenExceptionMessageBySeqs(seqs []int64) (exceptionMsg []*sdkws.MsgData) {
	for _, v := range seqs {
		msgModel := new(sdkws.MsgData)
		msgModel.Seq = v
		exceptionMsg = append(exceptionMsg, msgModel)
	}
	return exceptionMsg
}
```

注意：**这个方法在当前项目里没有任何调用方**（只有定义处）。也就是说，占位机制**设计了但没接上**。这是一个真实的、可以指出的实现缺失。

**策略 B：在响应里带「缺失的 seq 列表」**

服务端拉消息时，返回实际有的消息 + 一个「缺哪些 seq」的列表。客户端据此跳过。

OpenIM 用的是**更简单的策略 C**：

**策略 C：按「实际拉到的消息」推进，不假设连续**

看同步接口的核心逻辑（`internal/rpc/msg/sync_msg.go:31-45`）：

```go
minSeq, maxSeq, msgs, err := m.MsgDatabase.GetMsgBySeqsRange(ctx, req.UserID, seq.ConversationID, ...)
...
isEnd = seq.Begin <= minSeq
```

它拿的是「实际的消息列表」和 `minSeq/maxSeq`，客户端按**实际收到的消息**更新本地状态，而不是按序号逐个拉。

这样即使中间有洞，客户端也不会卡住——它只是「没收到那几个 seq 的消息」，下次同步时从「已收到的最大 seq + 1」开始。

**这个设计的代价**：如果空洞之后又来了新消息，那么空洞会被永久跳过（客户端不会回头找）。对 IM 来说这是可接受的——**那几个 seq 本来就没有消息**。

> 这是一个很务实的取舍：**与其花大力气填洞，不如让客户端不依赖「绝对连续」这个假设。**
>
> 但代价是：如果客户端逻辑写得不严谨（比如假设连续），就会出问题。所以这是一个「服务端简化，把复杂度推给客户端」的选择。

### 12.3.4 空洞有多大

算一下：单聊每段预分配 50，群聊 100。

假设一天有 1000 次进程重启（非常保守），每次浪费半段（25/50），一天浪费 2.5 万~5 万个 seq。

对比一天的消息量（假设 1 亿条），浪费率 0.03%。**完全可以接受。**

这就是号段方案可行的核心原因：**浪费的是「号段」，不是「消息」；而号段的空间几乎是无限的（int64）。**

## 12.4 分布式锁：为什么这里必须加锁

### 12.4.1 问题：两个实例同时发现「号段用完了」

```
实例 A：读 CURR=100, LAST=149 → 149 不够了，要去 DB 申请
实例 B：读 CURR=100, LAST=149 → 149 不够了，要去 DB 申请
```

如果两个都去申请，会拿到 `[150,199]` 和 `[200,249]` 两段。然后两个都往 Redis 里写自己的那段——**后写的覆盖先写的**。

结果：A 以为自己的号段是 150-199，实际 Redis 里是 200-249。A 发出去的 seq 是 150、151...（自己内存里的），B 也从 200 开始发。

**两条消息流交叉，seq 乱序。**

所以必须保证：**同一时刻，只有一个实例在为这个会话申请新号段。**

### 12.4.2 三种加锁方式

| 方式 | 原理 | 问题 |
|---|---|---|
| **悲观锁**（Redis SETNX + 过期） | 先抢锁，抢到才干活 | 锁超时后可能被别的实例抢；锁续期复杂 |
| **乐观锁**（CAS） | 读版本号，写时校验版本号有没有变 | 冲突时要重试，高竞争下大量失败 |
| **Lua 原子脚本** | 把「读+判断+写」打包成一个原子操作 | Lua 里不能做网络 IO（不能查 DB） |

**OpenIM 的解法很巧妙：用 Lua 做「判定 + 加锁」，把「去 DB 申请」留在 Lua 外面。**

为什么不能全放进 Lua？因为 Redis 的 Lua 脚本里**不能发起外部网络请求**（Lua 只能操作 Redis 自己的数据）。所以「向 Mongo 申请号段」这一步必须在脚本外面做。

于是流程变成：

```
Lua 脚本 ①：检查状态
  - key 不存在 → 加锁，返回「你需要去 DB 申请」（状态 1）
  - 已有锁（别人在申请）→ 返回「等着」（状态 2）
  - 有可用号段 → 直接分配，返回 seq（状态 0）
  - 号段不够了 → 加锁，返回「你需要去 DB 申请」（状态 3）

（如果在状态 1 / 3）→ 应用层去 Mongo 申请号段

Lua 脚本 ②：把新号段写回 Redis 并释放锁
  - 锁还是我的 → 写入新号段，删锁，返回成功
  - 锁已经不是我的（超时被抢）→ 不写，返回失败
```

**这个「两段式」设计是整个 seq 模块最精彩的地方。** 它把「不可能放进一个原子操作的事情」拆成两次原子操作，中间用一个「锁」串起来。

### 12.4.3 锁的三种状态与它们的意义

看代码注释（`seq_conversation.go:213-215`）：

```
// 0：成功
// 1：成功，锁已过期且未被其他实例抢占
// 2：已被锁定，但不是自己加的锁
```

这三个状态对应三种情况：

| 状态 | 含义 | 后果 |
|---|---|---|
| 0 | 锁是我的，顺利写入 | 完美 |
| 1 | 我的锁过期了，但没人抢——我仍然写入了 | 有风险但可接受 |
| 2 | 锁被别人抢了 | **必须放弃写入** |

**状态 2 是最关键的。** 它防止的是：实例 A 的锁过期了（因为 A 去 DB 申请花的时间太长），实例 B 抢到了锁并申请了新号段。然后 A 也回来写——如果 A 也写，就会覆盖 B 的。

所以脚本里必须有这句：

```lua
if redis.call("HGET", key, "LOCK") ~= lockValue then
    return 2
end
```

**比较锁的值（一个随机数），而不是「有没有锁」。** 这是分布式锁的经典陷阱——「检查锁是否存在」是不够的，必须是「检查锁是不是我的」。

> 这里可以联系第 08 篇讲的 gRPC 拦截器、第 06 篇讲的多端互踢——**分布式锁的核心不是「加锁」，是「安全地释放锁」。**

### 12.4.4 锁超时：多长合适

锁的超时时间配置在 `Redis.lockTime`。

太短：DB 申请还没回来锁就过期了，别的实例抢锁，产生并发申请。
太长：某个实例崩了之后，锁要等很久才释放（期间该会话完全无法发消息）。

这是一个**「故障恢复速度 vs 并发安全」的权衡**。OpenIM 用 `s.lockTime` 配置，默认值在 `config/redis.yml`。

**还有一个隐患**：`setSeqRetry` 只重试 10 次，每次间隔 250ms（`wait` 函数），总共 2.5 秒。如果锁持有者超过 2.5 秒没释放，写入就彻底失败了（只记日志）。

```go
// seq_conversation.go:325-347
func (s *seqConversationCacheRedis) setSeqRetry(...) {
	for i := 0; i < 10; i++ {
		state, err := s.setSeq(ctx, key, owner, currSeq, lastSeq, mill)
		...
	}
	log.ZError(ctx, "set seq cache retrying still failed", ...)
}
```

**注意这个函数没有返回值。** 重试失败只是记日志，调用方（`mallocTime`）不知道，仍然返回已经分配给自己的 seq。

后果：**Redis 里的号段没更新，但应用已经用了这段号。** 其他实例下次申请时会从旧位置开始，导致**重复分配**（两个不同的消息拿到相同的 seq）。

这是一个真实的正确性风险。虽然概率低（需要锁竞争超 2.5 秒），但后果严重（seq 重复 → 客户端去重、消息丢失）。

## 12.5 过期与冷会话

### 12.5.1 为什么 Redis 里的号段要设过期时间

因为会话可能很多，但**活跃的很少**。

一个运营 3 年的 IM 系统，可能有 100 万个会话。如果每个会话的 seq 缓存都常驻 Redis，内存会很可观（每个 hash 大概几百字节，100 万个就是几百 MB）。

所以设一个过期时间（`dataTime`），比如 5 分钟。**5 分钟内没有新消息的会话，缓存被清掉。**

代价是什么？

**号段作废。** 假设会话 A 缓存在 Redis 里是 `CURR=120, LAST=149`，过期了。下次来消息时要重新从 Mongo 申请——Mongo 那边 `max_seq` 已经是 150 了（因为上一次申请时 `$inc` 到了 150），所以新号段从 150 开始。

121~149 这 29 个号**被跳过**。

**这就是「冷会话」产生空洞的主要来源。** 而且它比进程崩溃更常见——只要有会话「聊一阵停一阵」，每次停超过过期时间就会浪费一段。

### 12.5.2 一个反直觉的推论

**seq 空洞的数量与会话的「活跃模式」强相关，而不是与消息量相关。**

一个「每天聊一次」的会话，每次都会浪费一段（因为两次之间缓存早过期了）。

这意味着：**seq 的实际值可能远大于消息总数。**

比如一个会话聊了 1000 条消息，但断断续续聊了一年，seq 可能已经到 5000 了。

**这不是 bug，是被接受的设计。** 因为：
- int64 的空间是 9.2 × 10^18，浪费几十倍完全无所谓
- 客户端从不假设「maxSeq == 消息总数」
- 未读数用 `maxSeq - hasReadSeq` 计算，空洞不影响这个差值的正确性（因为两端都是 maxSeq 坐标系）

> 这个认知很重要：**seq 的绝对值没有业务含义，只有相对顺序有含义。**

## 12.6 单聊 50 / 群聊 100 是怎么定的

```go
// pkg/common/storage/cache/redis/seq_conversation.go:349-361
func (s *seqConversationCacheRedis) getMallocSize(conversationID string, size int64) int64 {
	if size == 0 {
		return 0
	}
	var basicSize int64
	if msgprocessor.IsGroupConversationID(conversationID) {
		basicSize = 100
	} else {
		basicSize = 50
	}
	basicSize += size
	return basicSize
}
```

注意这个函数是**「预分配量 = 基础量 + 本次需要量」**，不是「固定 50/100」。

举例：
- 单聊要分配 3 个 seq → 预分配 `50 + 3 = 53`
- 群聊要分配 3 个 seq → 预分配 `100 + 3 = 103`

**为什么要加 `size`？** 因为如果本次请求就要 120 个（大批量补发历史消息），基础量 50 不够用，必须至少给 120。所以是 `max(基础量, size) + 一点余量`——这里写成 `基础量 + size` 更保守（一定够）。

**为什么群聊的预分配量更大？**

因为群聊的消息密度更高（一个群几十上百人在聊），号段消耗更快，频繁申请的成本更高。

这是一个**按负载特征调参**的例子：不是拍脑袋，而是根据「该类型会话的平均消息速率」决定预取量。

> 注意这里 `IsGroupConversationID` 判断的是**前缀 `sg_`**（`pkg/util/conversationutil/conversationutil.go:19-21`），也就是靠 conversationID 的格式来区分类型。**这是「把类型编码进 ID」这个设计带来的便利**（第 10 篇讲过）。

## 12.7 Mongo 兜底：原子分配的最后一层

```go
// pkg/common/storage/database/mgo/seq_conversation.go:51-69
func (s *seqConversationMongo) Malloc(ctx context.Context, conversationID string, size int64) (int64, error) {
	if size < 0 {
		return 0, errors.New("size must be greater than 0")
	}
	if size == 0 {
		return s.GetMaxSeq(ctx, conversationID)
	}
	filter := map[string]any{"conversation_id": conversationID}
	update := map[string]any{
		"$inc":         map[string]any{"max_seq": size},
		"$setOnInsert": map[string]any{"min_seq": int64(0)},
	}
	opt := options.FindOneAndUpdate().SetUpsert(true).SetReturnDocument(options.After).SetProjection(map[string]any{"_id": 0, "max_seq": 1})
	lastSeq, err := mongoutil.FindOneAndUpdate[int64](ctx, s.coll, filter, update, opt)
	if err != nil {
		return 0, err
	}
	return lastSeq - size, nil
}
```

### 12.7.1 这 18 行里的三个关键设计

**设计 1：`$inc` 是原子操作**

MongoDB 的 `$inc` 在**单个文档**上是原子的。这意味着即使 100 个实例同时对同一个 conversation 执行 `$inc`，每个都会拿到不同的结果，绝不会有两个拿到同一个值。

**这是整个 seq 系统正确性的最终保证。** Redis 层可能有锁竞争、可能过期、可能重试失败，但只要走到 Mongo，`$inc` 就保证了不重复。

**设计 2：`FindOneAndUpdate` + `SetReturnDocument(After)`**

先加再读，返回**加完之后**的值。然后 `lastSeq - size` 反推出「这一段从哪开始」。

```
初始 max_seq = 100
$inc 50 → max_seq 变成 150，返回 150
150 - 50 = 100  → 这段是 [100, 149]（或者按代码语义是 100 起，150 是下一个）
```

注意这里有个**语义细节**：返回 `lastSeq - size`，而 Redis 里 `setSeq` 的 `currSeq` 参数是 `seq + size`。看 `mallocTime` 的调用：

```go
// seq_conversation.go:382-388
seq, err := s.mgo.Malloc(ctx, conversationID, mallocSize)
s.setSeqRetry(ctx, key, states[1], seq+size, seq+mallocSize, states[2])
return seq, 0, nil
```

所以：Mongo 返回的 `seq` 是这一段可用的**起点**，`seq+size` 是「本批已用掉的部分」，`seq+mallocSize` 是「这段的上界」。

**这就是「段内游标」的设计**：CURR 指向「下一个可分配的」，LAST 指向「本段上界」。

**设计 3：`SetUpsert(true)` + `$setOnInsert`**

第一次为某个会话分配时，文档不存在，`upsert` 会创建它。`$setOnInsert` 保证只在「插入时」设置 `min_seq=0`，如果文档已存在就不动它（否则会把 `min_seq` 重置，导致消息被误判为「已清理」）。

**这是一个很容易踩的坑**：如果用 `$set` 而不是 `$setOnInsert`，每次分配都会重置 min_seq。

### 12.7.2 索引

```go
// seq_conversation.go:14-25
func NewSeqConversationMongo(db *mongo.Database) (database.SeqConversation, error) {
	coll := db.Collection(database.SeqConversationName)
	_, err := coll.Indexes().CreateOne(context.Background(), mongo.IndexModel{
		Keys: bson.D{{Key: "conversation_id", Value: 1}},
	})
	...
}
```

`conversation_id` 上建了**普通索引**（不是唯一索引）。

**这有一个隐患**：`upsert` 依赖 filter 命中。如果并发 upsert 同一个不存在的 conversation_id，Mongo 可能插入两条文档（因为不是唯一索引，不会冲突报错）。

结果：两个文档，`$inc` 分别作用在不同文档上 → **seq 重复**。

正确做法是 `Unique: true` 建唯一索引。加上唯一索引后，并发 upsert 会有一个失败（duplicate key），重试即可。

> **这是一个真实的正确性缺陷，值得在面试里说**：seq 的最终保证依赖 Mongo 的原子性，但唯一索引的缺失让「首次创建」这个窗口存在竞态。虽然窗口极小（只在会话的第一条消息时），但严格来说不完美。
>
> 你可以在 Mongo 里验证这一点：`db.seq_conversation.getIndexes()` 看是否有 unique。

## 12.8 冷启动与「isNewConversation」

```go
// controller/msg_transfer.go:219
isNew = currentMaxSeq == 0
```

`Malloc` 返回 0 意味着「这个会话之前没有消息」。这个信息被用来做两件事：

1. 创建会话记录（第 11 篇 11.14.4 节）
2. **可能还有其他依赖**

但这里有个**语义陷阱**：

`Malloc` 返回 0 有两种情况：
- 会话真的是新的（从没发过消息）
- 会话存在，但 `max_seq` 恰好是 0（理论上不会有消息，所以等价）

更微妙的是：`isNew` 只在**第一次 Malloc** 时为 true。如果同一次请求里因为某种原因 Malloc 了两次（不会发生，但逻辑上），第二次就不是 new 了。

**这个设计依赖「Malloc 返回 0 等价于新会话」这个不变式。** 只要 `max_seq` 从 0 开始且只增不减，这个不变式就成立。

## 12.9 一个容易被忽略的问题：谁保证「同一批消息的 seq 连续」

`BatchInsertChat2Cache` 分配的是「一段」seq，然后把这段按顺序分配给批内消息：

```go
// controller/msg_transfer.go:221-229
userSeqMap := make(map[string]int64)
seqs := make([]int64, 0, lenList)
for _, m := range msgs {
	currentMaxSeq++
	m.Seq = currentMaxSeq
	m.SendTime = sendTime
	userSeqMap[m.SendID] = m.Seq
	seqs = append(seqs, m.Seq)
}
```

**关键：`msgs` 这个切片的顺序，决定了 seq 的顺序。**

那 `msgs` 的顺序从哪来？从 `storageMessageList` 来，而它来自 `storageList`，来自 `categorizeMessageLists` 的遍历顺序，最终来自 `parseConsumerMessages` 遍历 `consumerMessages` 的顺序。

`consumerMessages` 是 `batcher` 按 key 分组后 append 进去的，保持了**到达顺序**。

**所以：seq 的顺序 = Kafka 消息的到达顺序 = 生产顺序（因为同 key 同分区，分区内有序）。**

这条链就是第 11 篇讲的「保序三层」的最终落点：**三层保序，最终体现为「seq 分配顺序正确」。**

如果任何一层破了，seq 就会乱——虽然还是连续的，但「先发的消息拿到更大的 seq」。

**这解释了一个现象**：为什么「保序」在 IM 里这么难做好——它不是某个函数写对就行，而是整条链路每一层都得配合。

## 12.10 分层结构

```
调用方（msgtransfer）
   ↓
controller.MsgTransferDatabase.BatchInsertChat2Cache   ← 业务语义层
   ↓ 调 Malloc
cache.SeqConversationCache（接口）                      ← 抽象层
   ↓
redis.seqConversationCacheRedis                        ← 缓存实现（热路径）
   ↓ 号段不够时兜底
database.SeqConversation（接口）
   ↓
mgo.seqConversationMongo                               ← 持久化层（冷路径）
```

**为什么要有这么多层？**

| 层 | 职责 |
|---|---|
| controller | 业务语义：把「分配 seq」和「发消息」组合起来 |
| cache 接口 | 让上层不依赖 Redis（还能换别实现） |
| redis 实现 | 热路径：号段 + 锁 + Lua |
| database 接口 | 让 redis 实现不依赖 Mongo |
| mgo 实现 | 冷路径：原子 `$inc` |

注意一个细节：**Redis 实现依赖了 Mongo 实现**（`seqConversationCacheRedis` 有一个 `mgo database.SeqConversation` 字段）。所以这个名字叫 "cache" 的组件，实际上是「带持久化兜底的号段分配器」。

**这是一个命名上的误导**：叫 `SeqConversationCache` 会让人以为它只是缓存，可以随时清空。实际上它承担了**正确的号段分配**这个核心职责。

> 更好的命名可能是 `SeqAllocator`。这是一个可以在 code review 里提的意见。

## 12.11 Lua 脚本一：malloc（判定 + 加锁 + 分配）

```go
// pkg/common/storage/cache/redis/seq_conversation.go:244-312
func (s *seqConversationCacheRedis) malloc(ctx context.Context, key string, size int64) ([]int64, error) {
	// 0：成功
	// 1：需要获取并加锁
	// 2：已被锁定
	// 3：已超过最大值且处于加锁状态
	script := `
local key = KEYS[1]
local size = tonumber(ARGV[1])
local lockSecond = ARGV[2]
local dataSecond = ARGV[3]
local mallocTime = ARGV[4]
local result = {}

-- ① key 不存在：加锁，让调用方去 DB 申请
if redis.call("EXISTS", key) == 0 then
	local lockValue = math.random(0, 999999999)
	redis.call("HSET", key, "LOCK", lockValue)
	redis.call("EXPIRE", key, lockSecond)
	table.insert(result, 1)
	table.insert(result, lockValue)
	table.insert(result, mallocTime)
	return result
end

-- ② 已有锁：别人正在申请，等着
if redis.call("HEXISTS", key, "LOCK") == 1 then
	table.insert(result, 2)
	return result
end

local curr_seq = tonumber(redis.call("HGET", key, "CURR"))
local last_seq = tonumber(redis.call("HGET", key, "LAST"))

-- ③ size == 0：只读，返回当前状态
if size == 0 then
	redis.call("EXPIRE", key, dataSecond)
	table.insert(result, 0)
	table.insert(result, curr_seq)
	table.insert(result, last_seq)
	local setTime = redis.call("HGET", key, "TIME")
	if setTime then
		table.insert(result, setTime)
	else
		table.insert(result, 0)
	end
	return result
end

-- ④ 号段够用：直接分配
local max_seq = curr_seq + size
if max_seq > last_seq then
	-- 号段不够：加锁 + 把 CURR 推到 LAST，返回状态 3
	local lockValue = math.random(0, 999999999)
	redis.call("HSET", key, "LOCK", lockValue)
	redis.call("HSET", key, "CURR", last_seq)
	redis.call("HSET", key, "TIME", mallocTime)
	redis.call("EXPIRE", key, lockSecond)
	table.insert(result, 3)
	table.insert(result, curr_seq)
	table.insert(result, last_seq)
	table.insert(result, lockValue)
	table.insert(result, mallocTime)
	return result
end

-- ⑤ 正常分配
redis.call("HSET", key, "CURR", max_seq)
redis.call("HSET", key, "TIME", ARGV[4])
redis.call("EXPIRE", key, dataSecond)
table.insert(result, 0)
table.insert(result, curr_seq)
table.insert(result, last_seq)
table.insert(result, mallocTime)
return result
`
	result, err := s.rcClient.GetRedis().Eval(ctx, script, []string{key}, size, int64(s.lockTime/time.Second), int64(s.dataTime/time.Second), time.Now().UnixMilli()).Int64Slice()
	...
}
```

### 12.11.1 为什么必须用 Lua

Redis 单条命令是原子的，但「读 CURR → 比较 → 写 CURR」是三条命令。如果不用 Lua：

```
实例A：HGET CURR → 100
实例B：HGET CURR → 100
实例A：HSET CURR 105
实例B：HSET CURR 105    ← 两个都拿到 100，都写了 105 → 重复分配
```

用 `EVAL` 执行 Lua，整个脚本在 Redis 里**串行执行**（Redis 是单线程模型），中间不会插入其他命令。

**这就是「Redis 单线程」这个「缺点」变成优点的场景**：它天然提供了脚本级的原子性。

> 补充一句：Redis 6.0 之后有 IO 多线程，但**命令执行仍然是单线程**，所以 Lua 的原子性不受影响。

### 12.11.2 逐段拆解

**段 ①：key 不存在**

```lua
local lockValue = math.random(0, 999999999)
redis.call("HSET", key, "LOCK", lockValue)
redis.call("EXPIRE", key, lockSecond)
```

生成一个随机锁值，写入 `LOCK` 字段，设**锁的过期时间**（不是数据的过期时间）。

然后返回 `[1, lockValue, mallocTime]`，告诉应用层：「你去 DB 申请吧，锁我给你加好了，凭证是这个随机数。」

**为什么锁值用随机数而不是实例 ID？**

因为实例 ID 可能重复（比如容器重启后 IP 复用、或者配置错误）。随机数碰撞概率极低。

更严谨的做法是用 `UUID` 或者 `实例ID + 时间戳 + 随机数`。9 位随机数（10^9）在实例数不多的情况下够用。

**注意段 ① 里 `EXPIRE key lockSecond` 设的是整个 key 的过期时间**，不是单独字段。所以如果锁超时时间 < 数据过期时间，key 会提前消失——下一次请求又走段 ①（key 不存在）。这个行为是「自洽」的，但会浪费号段。

**段 ②：已有锁**

```lua
if redis.call("HEXISTS", key, "LOCK") == 1 then
	table.insert(result, 2)
	return result
end
```

**注意：这里没有检查「锁是不是我的」。** 为什么不检查？

因为这一步对应的是「分配请求」而不是「写入请求」。如果锁存在，就一定是**别的实例**在申请（自己的锁在申请完成后会被 `setSeq` 删掉）。所以直接返回「等着」。

**段 ③：size == 0（只读）**

```lua
if size == 0 then
	redis.call("EXPIRE", key, dataSecond)
	...
	return result
end
```

`size == 0` 表示「我不分配，只想知道当前 seq 多少」。这个用途是 `GetMaxSeq` 之类的查询。

**注意这里 `EXPIRE key dataSecond` 会续期**——一次读操作也会延长缓存寿命。这是一个有意的设计（读说明会话是活跃的），但会让「只读不写」的会话长期占用内存。

**段 ④：号段不够**

```lua
local max_seq = curr_seq + size
if max_seq > last_seq then
	local lockValue = math.random(0, 999999999)
	redis.call("HSET", key, "LOCK", lockValue)
	redis.call("HSET", key, "CURR", last_seq)   -- ← 关键
	...
	table.insert(result, 3)
	table.insert(result, curr_seq)
	table.insert(result, last_seq)
	...
```

**这里有个很关键的细节：`HSET key CURR last_seq`——把游标推到段末尾。**

为什么？因为这一段的「剩余部分」要被放弃了。如果不推，下次申请时会从 `curr_seq` 开始，而 `curr_seq` 已经在段内——但 DB 那边已经 `$inc` 到了 `last_seq`，两边不一致。

等等，仔细想一下：如果 `max_seq = curr_seq + size > last_seq`，说明**这段剩余的号不够本次请求**。此时有两种处理：

**处理 A（OpenIM 的做法）**：放弃剩余号，把 CURR 推到 LAST，去 DB 申请新段。
**处理 B**：先用掉剩余的，不够的部分去申请新段。

OpenIM 选了 A。代价是**浪费 `last_seq - curr_seq` 个号**（可能多达几十个）。

**但为什么这样做更简单？** 因为如果选 B，一次请求会跨越两段，返回的 seq 就不连续了（剩余部分 + 新段开头）。而 `BatchInsertChat2Cache` 假设「分配到的是一段连续的 seq」（它用 `currentMaxSeq++` 逐个填充）。

**这是一个「为了实现简单，接受号段浪费」的取舍。** 非常合理——因为 seq 空间不值钱，代码复杂度才值钱。

**段 ⑤：正常分配**

```lua
redis.call("HSET", key, "CURR", max_seq)
redis.call("HSET", key, "TIME", ARGV[4])
redis.call("EXPIRE", key, dataSecond)   -- ← 续期数据过期时间
```

把 CURR 推进 `size` 个，续期，返回 `[0, curr_seq, last_seq, mallocTime]`。

返回的是 `curr_seq`（**分配前的值**），调用方从这个值开始用。

### 12.11.3 返回值格式不统一

注意四种状态的返回长度不同：

| 状态 | 返回 |
|---|---|
| 0 | `[0, curr_seq, last_seq, mallocTime]`（4 个） |
| 1 | `[1, lockValue, mallocTime]`（3 个） |
| 2 | `[2]`（1 个） |
| 3 | `[3, curr_seq, last_seq, lockValue, mallocTime]`（5 个） |

**这是一个容易出 bug 的地方**——调用方必须按状态取不同下标。看 `mallocTime` 的处理：

```go
switch states[0] {
case 0:
	return states[1], states[3], nil        // seq, time
case 1:
	...
	s.setSeqRetry(ctx, key, states[1], seq+size, seq+mallocSize, states[2])  // lockValue=states[1], mill=states[2]
	return seq, 0, nil
case 2:
	...
case 3:
	currSeq := states[1]
	lastSeq := states[2]
	mill := states[4]                        // ← 注意是 4，不是 3
	...
	s.setSeqRetry(ctx, key, states[3], ...)  // lockValue=states[3]
}
```

**状态 3 里 `states[3]` 是 lockValue、`states[4]` 是 mill**，而状态 1 里 `states[1]` 是 lockValue、`states[2]` 是 mill。

**下标不同，极易写错。** 如果这里写错一个，锁值传错，`setSeq` 就会一直返回状态 2（锁不是我的），号段永远写不回去。

> 这是「Lua 返回数组」这种弱类型接口的典型风险。更好的做法是返回 JSON（`cjson.encode`），或者统一返回固定长度 + 用 0 占位。

## 12.12 Lua 脚本二：setSeq（写回 + 释放锁）

```go
// seq_conversation.go:209-241
func (s *seqConversationCacheRedis) setSeq(ctx context.Context, key string, owner int64, currSeq int64, lastSeq int64, mill int64) (int64, error) {
	if lastSeq < currSeq {
		return 0, errs.New("lastSeq must be greater than currSeq")
	}
	// 0：成功
	// 1：成功，锁已过期且未被其他实例抢占
	// 2：已被锁定，但不是自己加的锁
	script := `
local key = KEYS[1]
local lockValue = ARGV[1]
local dataSecond = ARGV[2]
local curr_seq = tonumber(ARGV[3])
local last_seq = tonumber(ARGV[4])
local mallocTime = ARGV[5]

-- ① key 消失了（过期）
if redis.call("EXISTS", key) == 0 then
	redis.call("HSET", key, "CURR", curr_seq, "LAST", last_seq, "TIME", mallocTime)
	redis.call("EXPIRE", key, dataSecond)
	return 1
end

-- ② 锁不是我的：放弃
if redis.call("HGET", key, "LOCK") ~= lockValue then
	return 2
end

-- ③ 正常：写回 + 删锁
redis.call("HDEL", key, "LOCK")
redis.call("HSET", key, "CURR", curr_seq, "LAST", last_seq, "TIME", mallocTime)
redis.call("EXPIRE", key, dataSecond)
return 0
`
	result, err := s.rcClient.GetRedis().Eval(ctx, script, []string{key}, owner, int64(s.dataTime/time.Second), currSeq, lastSeq, mill).Int64()
	...
}
```

### 12.12.1 段 ① 的微妙之处

如果 key 在「申请号段」期间过期了（因为锁的 TTL 比数据 TTL 短，或者 Redis 内存压力淘汰了），那么 `EXISTS == 0`。

此时**直接写入新号段**，返回状态 1。

**但这安全吗？** 如果 key 消失了，说明没有其他实例在操作它（否则 key 会被重建）。所以写入是安全的。

**除非**：另一个实例在 key 消失的瞬间也走了段 ①，也加了锁、也去 DB 申请了。这种情况下两个实例会各写一次，后写的覆盖先写的。

**这是一个极小的竞态窗口**，OpenIM 选择接受（返回状态 1 时只打 Warn 日志）。

### 12.12.2 段 ② 是整个锁机制的核心

```lua
if redis.call("HGET", key, "LOCK") ~= lockValue then
	return 2
end
```

**这一行防止的是「过期锁的持有者回来乱写」。**

场景重现：

```
t=0   实例A 抢锁（lockValue=111），lockSecond=3s
t=0   实例A 去 Mongo 申请号段（慢，花了 5 秒）
t=3   锁过期，key 里的 LOCK 字段被 Redis 删了（其实 EXPIRE 是整个 key，所以 key 也没了）
      —— 或者如果只删字段，LOCK 消失
t=4   实例B 抢锁成功（lockValue=222），去 Mongo 申请，写回新段
t=5   实例A 回来，调 setSeq(lockValue=111)
      → HGET LOCK = 222 ≠ 111 → 返回 2，放弃写入
```

**如果没有这一行**，实例 A 会用自己的（过期的）号段覆盖实例 B 的，导致 seq 回退 + 重复分配。

> **分布式锁的三个必需条件**：
> 1. 加锁要原子（Lua 里 HSET + EXPIRE）
> 2. 要有超时（防死锁）
> 3. **释放时要校验持有者**（防误删）
>
> 第 3 点是最容易被漏掉的。很多「手写分布式锁」的代码只做了前两点。

### 12.12.3 一个实现隐患：`EXPIRE` 作用在整个 key 上

注意锁和数据存在**同一个 hash** 里：

```
key = malloc_seq:si_A_B
  CURR = 120
  LAST = 149
  TIME = 1729500000000
  LOCK = 837261945     ← 临时字段
```

用 `EXPIRE key N` 会同时影响锁和数据。

**问题**：段 ① 里 `EXPIRE key lockSecond`（3 秒），而数据需要 `dataSecond`（比如 5 分钟）。如果一次申请花了 3 秒以上，整个 key（含数据）就没了——**已有的号段也丢了**。

**这是「锁和数据共用一个 key」的固有缺陷。** 正确做法是用两个 key：`seq:conv` 和 `lock:seq:conv`。

> 这是一个可以在面试里提的设计瑕疵：**锁的生命周期应该短，数据的生命周期应该长，放在同一个 key 里必然冲突。**

## 12.13 mallocTime：状态机

```go
// seq_conversation.go:368-418
func (s *seqConversationCacheRedis) mallocTime(ctx context.Context, conversationID string, size int64) (int64, int64, error) {
	if size < 0 {
		return 0, 0, errs.New("size must be greater than 0")
	}
	key := s.getSeqMallocKey(conversationID)
	for i := 0; i < 10; i++ {
		states, err := s.malloc(ctx, key, size)
		if err != nil {
			return 0, 0, err
		}
		switch states[0] {
		case 0: // success
			return states[1], states[3], nil
		case 1: // 未找到（key 不存在，已加锁）
			mallocSize := s.getMallocSize(conversationID, size)
			seq, err := s.mgo.Malloc(ctx, conversationID, mallocSize)
			if err != nil {
				return 0, 0, err
			}
			s.setSeqRetry(ctx, key, states[1], seq+size, seq+mallocSize, states[2])
			return seq, 0, nil
		case 2: // locked
			if err := s.wait(ctx); err != nil {
				return 0, 0, err
			}
			continue
		case 3: // 超过缓存最大值
			currSeq := states[1]
			lastSeq := states[2]
			mill := states[4]
			mallocSize := s.getMallocSize(conversationID, size)
			seq, err := s.mgo.Malloc(ctx, conversationID, mallocSize)
			if err != nil {
				return 0, 0, err
			}
			if lastSeq == seq {
				s.setSeqRetry(ctx, key, states[3], currSeq+size, seq+mallocSize, mill)
				return currSeq, states[4], nil
			} else {
				log.ZWarn(ctx, "malloc seq not equal cache last seq", nil, ...)
				s.setSeqRetry(ctx, key, states[3], seq+size, seq+mallocSize, mill)
				return seq, mill, nil
			}
		default:
			return 0, 0, errs.New(fmt.Sprintf("unknown state: %d", states[0]))
		}
	}
	return 0, 0, errs.New("malloc seq waiting for lock timeout", "conversationID", conversationID, "size", size)
}
```

### 12.13.1 状态 1：会话第一次出现

```
Lua 返回 [1, lockValue, mallTime]  → 说明 key 不存在，锁已加好
  ↓
mgo.Malloc(mallocSize)  → 从 DB 申请一段
  ↓
setSeqRetry(lockValue, seq+size, seq+mallocSize, mallTime)
  → 把「本批已用到的位置」和「段上界」写回 Redis
  ↓
返回 seq（本批的起点）
```

注意写回的是 `seq + size`（不是 `seq`）——因为**本批的 `size` 个号已经被这次请求用掉了**，Redis 里的游标要指向「下一个可用」。

这是一个容易搞错的点：**返回给调用方的是 `seq`（起点），写回 Redis 的是 `seq + size`（下一个）。**

### 12.13.2 状态 2：等锁

```go
if err := s.wait(ctx); err != nil {
	return 0, 0, err
}
continue
```

`wait` 就是睡 250ms：

```go
// seq_conversation.go:314-323
func (s *seqConversationCacheRedis) wait(ctx context.Context) error {
	timer := time.NewTimer(time.Second / 4)
	defer timer.Stop()
	select {
	case <-timer.C:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

**为什么是 250ms？** 因为没有更好的办法——它是「让出锁给别的实例完成申请」的经验值。太短会空转，太长会拖慢。

**最多等 10 次 = 2.5 秒**，超时返回错误。

**这个设计有性能问题**：如果同一个会话在 2.5 秒内有大量并发分配请求，会有很多 goroutine 在 `wait` 里睡。虽然睡了不占 CPU，但**占 goroutine 和 ctx**。

更好的做法是：用 Redis 的 `BLPOP` 等待通知，或者用「其他实例已经申请好了就直接读新值」的乐观策略。

### 12.13.3 状态 3 里的 `lastSeq == seq` 判断

这是全篇最精妙的一段：

```go
if lastSeq == seq {
	// 缓存里的 LAST 和 DB 返回的起点一致 → 说明没人抢过，可以直接用
	s.setSeqRetry(ctx, key, states[3], currSeq+size, seq+mallocSize, mill)
	return currSeq, states[4], nil
} else {
	// 不一致 → 说明有别的实例已经申请过了，缓存过期了
	log.ZWarn(ctx, "malloc seq not equal cache last seq", nil, ...)
	s.setSeqRetry(ctx, key, states[3], seq+size, seq+mallocSize, mill)
	return seq, mill, nil
}
```

**情况 A（`lastSeq == seq`）：缓存没被抢**

```
Redis: CURR=100, LAST=149      ← 缓存里认为段上界是 149
本次要用 5 个：100+5=105 < 149？不是，假设用了 48 个后 CURR=148
148 + 5 = 153 > 149  → 状态 3
Mongo.Malloc  → 返回 149（因为 max_seq 从 150 起）→ seq=149？ 
```

等等，让我重新算。Mongo 的 `max_seq` 在上一段申请时被 `$inc` 到了 150（表示 150 是下一个可用）。所以 `Malloc(100)` 会把 `max_seq` 从 150 增到 250，返回 `250-100=150`。

所以 `seq = 150`，而 `lastSeq = 149`。**不相等！**

那什么时候相等？

`lastSeq == seq` 意味着：**缓存里的 LAST 恰好等于 DB 这次返回的起点**。

这说明 DB 的 `max_seq` 从来没变过（还是 150），也就是说**没有其他实例申请过**。而 `lastSeq = 149`，`seq = 150`——差 1。

Hmm，那应该是 `lastSeq + 1 == seq`？

除非……看 `setSeq` 写回的 `lastSeq` 是 `seq + mallocSize`。

让我重新推一遍完整流程：

**第一次（会话新建）**：
```
Mongo: max_seq = 0
mallocTime 状态 1 → mgo.Malloc(mallocSize=53) → max_seq 变 53，返回 0
setSeqRetry(lockValue, currSeq=0+3=3, lastSeq=0+53=53)
Redis: CURR=3, LAST=53
返回 seq=0
```
所以本批用 0,1,2（size=3），下一个可用是 3。段上界 53（即 0~52 可用，53 是下一个段的起点）。

**第二次（CURR=3，要 5 个）**：
```
3 + 5 = 8 < 53 → 状态 0，直接分配
返回 3，Redis: CURR=8
```

**用到 CURR=52 时，要 5 个**：
```
52 + 5 = 57 > 53 → 状态 3
CURR 被推到 53
mgo.Malloc(100+5=105) → max_seq 从 53 增到 158，返回 53
seq = 53
lastSeq（缓存里的）= 53
```
**相等！** 因为 `seq = max_seq_old = 53`，而缓存的 `LAST = 53`（上次写回的 `0 + 53`）。

所以 `lastSeq == seq` 表示：**DB 的 max_seq 还是我上次申请后留下的值**，说明中间没有其他实例动过。

**这验证了「上次写回的 lastSeq == DB 的当前 max_seq」这个不变式。**

情况 A 的处理：`return currSeq, states[4], nil`——**返回 `currSeq`（52），而不是 `seq`（53）**！

为什么？因为 `currSeq=52` 是「缓存里认为的下一个可用」，而 `seq=53` 是「DB 说从这里开始」。

**这两个不一样！** 52 是缓存里的游标（意味着 52 还没被用），53 是 DB 的下一个。

等等，这里可能有问题：如果 `currSeq=52` 表示「52 可用」，那么返回 52 作为起点，用掉 52，下一个是 53。合理。

而 `setSeqRetry(currSeq+size = 52+5 = 57, seq+mallocSize = 53+105 = 158)`。

**于是 Redis 里 CURR=57，LAST=158。但 DB 里 max_seq=158。**

等等，57 是「52+5」，说明这次用了 52,53,54,55,56。但 53,54... 属于新申请的段吗？新段是 [53, 157]（因为 max_seq 从 53 增到 158）。

所以用了 52（旧段最后一个）+ 53,54,55,56（新段前四个）。**跨段了！**

而 `BatchInsertChat2Cache` 假设 seq 连续：`currentMaxSeq++` 逐个填。52,53,54,55,56 确实连续。所以没问题。

**好，这个逻辑是对的。** 情况 A 是「跨段但连续」的场景。

**情况 B（`lastSeq != seq`）：缓存过期/被抢**

这表示 DB 的 max_seq 已经比缓存里的 LAST 更大了（有别的实例申请过）。

此时**必须用 `seq`（DB 返回的起点）**，因为缓存里的 `currSeq` 可能已经被别人用掉了。

```go
s.setSeqRetry(ctx, key, states[3], seq+size, seq+mallocSize, mill)
return seq, mill, nil
```

**这是「以 DB 为准」的原则**——缓存不可信时，相信持久层。

> 这段代码体现了分布式系统的一个核心原则：**当缓存与持久层冲突时，持久层赢。** 缓存只是加速，不是权威。

## 12.14 BatchInsertChat2Cache：seq 落地的最后一步

```go
// pkg/common/storage/controller/msg_transfer.go:203-239
func (db *msgTransferDatabase) BatchInsertChat2Cache(ctx context.Context, conversationID string, msgs []*sdkws.MsgData) (seq int64, isNew bool, userHasReadMap map[string]int64, err error) {
	lenList := len(msgs)
	if int64(lenList) > db.msgTable.GetSingleGocMsgNum() {
		return 0, false, nil, errs.New("message count exceeds limit", "limit", db.msgTable.GetSingleGocMsgNum()).Wrap()
	}
	if lenList < 1 {
		return 0, false, nil, errs.New("no messages to insert", "minCount", 1).Wrap()
	}
	// 强制同一批次消息的发送时间一致
	sendTime := time.Now().UnixMilli()
	// 从序号分配器申请一段连续序号
	currentMaxSeq, err := db.seqConversation.Malloc(ctx, conversationID, int64(len(msgs)))
	if err != nil {
		log.ZError(ctx, "storage.seq.Malloc", err)
		return 0, false, nil, err
	}
	isNew = currentMaxSeq == 0
	lastMaxSeq := currentMaxSeq
	userSeqMap := make(map[string]int64)
	seqs := make([]int64, 0, lenList)
	for _, m := range msgs {
		currentMaxSeq++
		m.Seq = currentMaxSeq
		m.SendTime = sendTime
		userSeqMap[m.SendID] = m.Seq
		seqs = append(seqs, m.Seq)
	}
	msgToDB := func(msg *sdkws.MsgData) *model.MsgInfoModel {
		return &model.MsgInfoModel{Msg: convert.MsgPb2DB(msg)}
	}
	if err := db.msgCache.SetMessageBySeqs(ctx, conversationID, datautil.Slice(msgs, msgToDB)); err != nil {
		return 0, false, nil, err
	}
	return lastMaxSeq, isNew, userSeqMap, nil
}
```

### 12.14.1 三条边界检查

```go
if int64(lenList) > db.msgTable.GetSingleGocMsgNum() {   // 100
	return 0, false, nil, errs.New("message count exceeds limit", ...)
}
if lenList < 1 {
	return 0, false, nil, errs.New("no messages to insert", ...)
}
```

**为什么一批不能超过 100 条？**

因为 Mongo 的消息文档模型是**一个文档存 100 条消息**（第 13 篇详讲）。如果一批超过 100 条，就会跨文档，而 `BatchInsertBlock` 的逻辑是按文档分块写的——超过 100 条其实也能处理（它会循环切块），但这里直接拒绝了。

**这是一个「防御性限制」**：批处理框架的 size 是 500，理论上一个批次可能攒到 500 条同一会话的消息。此时 `BatchInsertChat2Cache` 会直接报错。

**这是一个真实的 bug 风险**：如果一个热门群在 100ms 内涌入 500 条消息（大群完全可能），这个批次会**整个失败**，消息全丢。

`batcher` 的 `size = 500` 和 `GetSingleGocMsgNum() = 100` 之间存在**参数不一致**。

> **这是一个非常有价值的发现**，值得在面试里说：**批处理的批次大小（500）大于单文档容量（100），热门会话可能触发「message count exceeds limit」直接丢整批。** 合理的修法是在 `do()` 里按 100 切分 storageMessageList，分批调用。
>
> 你可以在实验里验证：往同一个群快速发 200 条消息，看日志里有没有这个错误。

### 12.14.2 `sendTime` 强制统一

```go
sendTime := time.Now().UnixMilli()
for _, m := range msgs {
	m.Seq = currentMaxSeq
	m.SendTime = sendTime
}
```

**整批消息用同一个 `sendTime`。**

为什么要覆盖客户端传的时间？三个可能的原因：

1. **批内排序**：如果同一批消息的 sendTime 不同，客户端按时间排序会和 seq 顺序冲突。统一时间后，排序只能靠 seq，反而一致。
2. **防止客户端伪造时间**：恶意客户端可以传未来时间让消息「置顶」。
3. **简化对齐**：同批消息在 UI 上应该看起来是「同时到的」。

**但这和 `encapsulateMsgData` 里的 `if msg.SendTime == 0` 语义冲突**（第 10 篇 10.12.2）。发送接口允许客户端指定，落库时无条件覆盖。**这是一个真实的语义矛盾。**

### 12.14.3 `userSeqMap` 的作用

```go
userSeqMap[m.SendID] = m.Seq
```

记录「每个发送者在本批中的最大 seq」。

这个 map 被用来：
1. 写 Redis（`SetHasReadSeqs`）—— 发送者自动标记为「已读到自己的最新消息」
2. 异步写 DB（第 11 篇 11.14.3）

**为什么是「最大 seq」而不是「所有 seq」？** 因为已读 seq 只需记最大值（单调）。

**注意一个 bug 风险**：`userSeqMap[m.SendID] = m.Seq` 是**覆盖式赋值**。如果同一批里有两个不同的发送者 A 和 B，map 里会有两项。但如果 A 发了 5 条，只有最后一条的 seq 被记录——这是正确的（最大值）。

但如果**遍历顺序不是按 seq 递增**呢？那 `userSeqMap` 存的就不是最大值了。

而 `msgs` 的顺序是确定的（按到达顺序），seq 也是按这个顺序递增分配的，所以最后一次赋值一定是最大值。**依赖了这个隐含的顺序关系**。

更严谨的写法应该是 `if m.Seq > userSeqMap[m.SendID] { ... }`。

### 12.14.4 `SetMessageBySeqs` 的幂等性

```go
db.msgCache.SetMessageBySeqs(ctx, conversationID, ...)
```

Redis 侧的实现（`pkg/common/storage/cache/redis/msg.go`）是把每条消息以 seq 为 field 写进一个 hash。

**重复执行会覆盖同一个 field**，所以幂等。

**但注意：seq 是这次新分配的**。如果同一批消息被消费两次，第二次会拿到**新的 seq**，写到**新的 field**——于是 Redis 里有两份内容相同、seq 不同的消息。

**这就是第 11 篇 11.8 节说的「seq 分配不幂等」的具体表现。**

## 12.15 全局视角：一次 Malloc 的完整决策树

把上面所有内容串起来：

```
BatchInsertChat2Cache 调 Malloc(convID, n)
  │
  ├─ 第 1 次尝试 malloc Lua
  │    ├─ key 不存在 → [1] 加锁 → 去 Mongo 申请 → setSeq 写回 → 返回 seq
  │    ├─ 有锁      → [2] 睡 250ms → 重试（最多 10 次）
  │    ├─ 号段够    → [0] 直接返回 → 完成
  │    └─ 号段不够  → [3] 加锁 → 去 Mongo 申请
  │                       ├─ lastSeq == seq → 用缓存游标，跨段连续
  │                       └─ lastSeq != seq → 用 DB 起点，以 DB 为准
  └─ 重试 10 次仍失败 → 返回 error → 本批消息处理失败
```

**六个分支、两种数据源、一个锁、两个 Lua 脚本。** 这就是「一个自增」背后的全部复杂度。

## 12.16 设计评价

### 12.16.1 做得好的地方

| 设计 | 价值 |
|---|---|
| 号段预分配（50/100） | DB 压力降 1~2 个数量级 |
| Lua 原子脚本 | 读-判-写一体，无竞态 |
| 锁值随机数 + 校验 | 防「过期锁持有者乱写」 |
| 状态码分级（0/1/2/3） | 调用方能区分「该重试」还是「该等」 |
| 缓存与 DB 冲突时以 DB 为准 | 保证不重复分配 |
| `$inc` + `FindOneAndUpdate` | 最终原子性保证 |
| `SetMinSeq/GetMinSeq` 独立 | 支持「清理历史消息」后调整下界 |

### 12.16.2 可以改进的地方

| 问题 | 位置 | 影响 | 建议 |
|---|---|---|---|
| `conversation_id` 无唯一索引 | `mgo/seq_conversation.go:16-20` | 并发首次 upsert 可能插两条文档 → seq 重复 | 加 `Unique: true` |
| 锁与数据共用同一个 key | `redis/seq_conversation.go:259` | 锁的 `EXPIRE` 会缩短数据寿命 | 拆成两个 key |
| `setSeqRetry` 无返回值 | `:325-347` | 写回失败时调用方不知道，可能重复分配 | 返回 error |
| 状态 3 的 `CURR` 被推到 `LAST` | `:288` | 剩余号段全浪费 | 先用剩余再申请（但会跨段不连续） |
| 锁值只有 9 位随机数 | `:257` | 碰撞概率虽低但非零 | 用 UUID 或 实例ID+时间戳 |
| `wait` 固定 250ms | `:315` | 不区分场景，可能空转或过慢 | 指数退避 + 抖动 |
| 状态 1 的 `EXISTS==0` 分支直接写 | `:223-227` | 极小概率与另一实例的申请冲突 | 重新走 malloc 脚本 |
| `getMallocSize` 的 `basicSize + size` | `:359` | 大批量时预分配过多 | 可用 `max(basicSize, size) * 1.2` |
| 批次大小 500 > 单文档 100 | `msg_transfer.go:205` | 热门会话可能整批失败 | 在 `do()` 里切分 |

### 12.16.3 一个必须理解的核心思想

**seq 分配器的本质是「把随机并发的分配请求，串行化成一条单调递增的序列」。**

分布式系统里做串行化的三种手段，这里全用上了：

| 手段 | 用在哪 | 保证范围 |
|---|---|---|
| Kafka 分区 | 同会话消息串行进消费者 | 宏观顺序 |
| 内存分片 | 同会话消息串行进 worker | 批内顺序 |
| Redis Lua + 锁 | 同会话的号段分配串行 | 分配原子性 |
| Mongo `$inc` | 跨实例的最终原子性 | 不重复 |

**四层串行化，每一层解决上一层的漏洞。** 这就是「一个自增」要写三百行的原因。

2. 发 3 条消息到该会话
3. 再 `HGETALL`

**预期**：CURR 从 105 变成 108，LAST 不变。这就是「号段内消耗」。

4. 一直发到 CURR 接近 LAST，再发一条，观察 LAST 跳变（新号段）。

## 实验 2：验证号段浪费（冷会话空洞）

**目的**：验证「缓存过期导致 seq 跳变」。

**步骤**：
1. 给某会话发 1 条消息，记下它的 seq（假设 100）
2. 记下 Redis 里的 `CURR/LAST`（假设 CURR=101, LAST=153）
3. 手动删掉这个 key：`DEL <key>`
4. 再发 1 条消息
5. 查 Mongo 里这条新消息的 seq

**预期现象**：新消息的 seq **不是 101**，而是 **153**（因为 `max_seq` 在 Mongo 里已经是 153 了）。

**这直接证明了「101~152 这 52 个 seq 被永久浪费」。**

## 实验 3：验证空洞不影响客户端同步

**目的**：确认空洞存在时客户端也能正常拉消息。

**步骤**：
1. 按实验 2 制造一个 52 的跳变
2. 用 `PullMessageBySeqs` 拉 `[100, 200]` 范围

```bash
curl -s -X POST "http://127.0.0.1:10002/msg/pull_msg_by_seqs" \
  -H "Content-Type: application/json" -H "token: $ADMIN_TOKEN" -H "operationID: hole" \
  -d '{"userID":"userA","seqs":[{"conversationID":"si_imAdmin_userA","begin":100,"end":200,"num":100}]}'
```

**预期现象**：返回的消息里，seq 是 100 和 153（中间没有 101~152）。响应里的 `maxSeq` 是 153。

**结论**：客户端拿到的是「实际存在的消息」，而不是「每个 seq 都有」。这就是 12.3.3 节说的策略 C。

## 实验 4：压测 seq 分配的唯一性

**目的**：验证高并发下 seq 不重复。

**方法**：并发往同一个会话发 200 条消息。

```bash
seq 1 200 | xargs -P 50 -I{} curl -s -o /dev/null -X POST "http://127.0.0.1:10002/msg/send_msg" \
  -H "Content-Type: application/json" -H "token: $ADMIN_TOKEN" -H "operationID: seqtest-{}" \
  -d '{"sendID":"imAdmin","recvID":"userA","sessionType":1,"contentType":101,"content":{"content":"seqtest-{}"}}'

sleep 3
```

然后统计 Mongo 里该会话的 seq：

```bash
docker exec -i <mongo> mongosh --quiet ... im_v3 --eval '
var seqs = [];
db.msg.find().forEach(function(d) {
  d.msgs.forEach(function(m) { if (m.msg && m.msg.content && m.msg.content.indexOf("seqtest") >= 0) seqs.push(m.msg.seq); });
});
seqs.sort(function(a,b){return a-b});
print("count:", seqs.length);
print("unique:", new Set(seqs).size);
print("first:", seqs[0], "last:", seqs[seqs.length-1]);
'
```

**预期现象**：`count == unique == 200`。

**如果 unique < count**：说明 seq 重复了，可能是并发 upsert 竞态（12.7.2 节）。这种情况在全新会话上更容易复现。

## 实验 5：查看 seq_conversation 的索引与文档

```bash
docker exec -i <mongo> mongosh --quiet ... im_v3 --eval '
print("=== 索引 ===");
db.seq_conversation.getIndexes().forEach(i => printjson(i));
print("=== 文档样例 ===");
db.seq_conversation.find().limit(3).forEach(d => printjson(d));
print("=== 重复检查 ===");
db.seq_conversation.aggregate([
  {$group: {_id: "$conversation_id", n: {$sum: 1}}},

```

**预期现象**：
- 索引只有 `_id` 和 `conversation_id`，**没有 unique: true**
- 文档形如 `{conversation_id: "si_A_B", min_seq: 0, max_seq: 153}`
- 重复检查应该为空（如果出现过并发首次写入，这里会有数据）

**这个实验能验证 12.7.2 节指出的隐患。**

## 实验 6：验证锁竞争

**目的**：观察状态 2（等锁）。

**方法**：
1. 手动在 Redis 里给某个会话加锁，模拟「别的实例正在申请」：

```redis
HSET MALLOC_SEQ:si_imAdmin_userA LOCK 123456789
EXPIRE MALLOC_SEQ:si_imAdmin_userA 10
```

2. 发一条消息

**预期现象**：
- 发送接口仍然返回成功（因为它只投 Kafka）
- msgtransfer 日志里出现 `storage.seq.Malloc` 错误，或者「malloc seq waiting for lock timeout」
- 消息**没有分配 seq**（在这 10 秒内）

3. 清除锁后，Kafka 重投（如果位点没提交），消息正常处理。

**这个实验能直观看到「锁竞争导致消息延迟处理」。**

# 面试话术

## 30 秒版本

> 消息的 seq 是服务端在 msgtransfer 落库前分配的，用「号段预分配」：单聊一次向 Mongo 申请 50 个、群聊 100 个，缓存在 Redis 的 hash 里（CURR 游标 + LAST 上界），批内消息用 CURR++ 逐个填充。
>
> 并发控制靠 Lua 脚本 + 锁：脚本判断「key 不存在 / 有锁 / 号段够 / 号段不够」四种状态，号段不够时加锁、去 Mongo 用 `$inc` 原子申请、再用第二个 Lua 脚本校验锁值写回。锁值用随机数，释放时校验持有者，防止过期锁持有者覆盖别人的号段。

## 3 分钟版本

在 30 秒基础上展开：

1. **为什么必须服务端分配**：客户端时间不可信、多端并发无法协商、可伪造。而且 seq 必须是**稠密连续**的——因为要用「范围」表达「我有哪些消息」，用 `maxSeq - hasReadSeq` 算未读。
2. **为什么不用 Snowflake**：雪花 ID 跨毫秒会跳变几千个数字，不连续，没法用范围表达。
3. **为什么不用 DB 每条自增**：热门会话是热点行，同一会话的分配必须串行，会成为瓶颈。号段把这降到 1/50 或 1/100。
4. **代价是空洞**：进程崩溃、缓存过期、跨段申请失败都会浪费号段。一个「每天聊一次」的会话每次都要浪费一段，所以 seq 的实际值可能远大于消息总数。这在 int64 空间里完全可接受。
5. **并发控制的关键设计**（挑最精妙的一点讲）：
   - Redis Lua 里不能做网络 IO，所以「去 Mongo 申请」必须留在脚本外，于是拆成「脚本一加锁 → 外部申请 → 脚本二校验锁值写回」两段式；
   - 或者：状态 3 里通过 `lastSeq == seq` 判断「缓存是否被别的实例抢先过」，不相等就以 DB 为准，体现「缓存与持久层冲突时持久层赢」。
6. **主动指出缺陷**：
   - `conversation_id` 没建唯一索引，并发首次 upsert 可能插两条文档导致 seq 重复；
   - 锁和数据共用一个 key，锁的 `EXPIRE` 会缩短数据寿命；
   - `setSeqRetry` 无返回值，写回失败调用方不知情，可能重复分配。

## 预判追问与答法

**Q：为什么单聊 50、群聊 100？**
A：预取量应该和「该类型会话的消息速率」匹配。群聊消息密度更高，号段消耗更快，预取少了会频繁申请。但也不能太大——预取越多，崩溃/过期时浪费越多。这两个数字是经验值，实际应该按线上的「每段存活时长」指标调：如果发现一个号段平均 2 分钟就用完，说明偏小；如果经常用不到 20% 就过期，说明偏大。

**Q：如果两个实例同时发现号段用完，怎么办？**
A：Lua 脚本里 `HEXISTS LOCK` 会拦住第二个。第一个加锁成功后去 Mongo 申请，第二个返回状态 2 然后睡 250ms 重试。最多重试 10 次（2.5 秒），超时返回错误。这个错误会导致本批消息处理失败，Kafka 位点不前进（理论上），下次重投再试。

**Q：锁过期了怎么办？**
A：两个 Lua 脚本都处理了。malloc 脚本在 key 存在但没锁时，直接把 CURR 推到 LAST 并重新加锁；setSeq 脚本会校验 `HGET LOCK == lockValue`，如果不等于（说明锁过期后被别人抢了）就返回 2 放弃写入。**关键是「校验持有者」而不是「检查是否存在」**——这是手写分布式锁最容易漏的一步。

**Q：怎么保证不重复分配？**
A：最终保证在 Mongo 的 `$inc`——单文档上的 `$inc` 是原子的，100 个实例并发也不会拿到同一个值。Redis 层只是加速，即使 Redis 整个挂了，Mongo 依然能正确分配（只是慢）。

不过我要补充一个缺陷：`seq_conversation` 集合的 `conversation_id` 没建唯一索引，所以「会话第一次分配」这个窗口里，并发 upsert 可能插入两条文档，`$inc` 分别作用在不同文档上，就会重复。窗口极小但确实存在。

**Q：seq 空洞会不会导致消息丢失？**
A：不会。空洞只意味着「那些 seq 没有对应消息」，客户端拉消息时拿到的是实际存在的消息列表，按「已收到的最大 seq + 1」推进。代价是：如果客户端逻辑假设「seq 连续」，就会卡住或死循环。所以这是一个「服务端简化，把契约推给客户端」的设计。

项目里其实预留了填洞能力（`GenExceptionMessageBySeqs` 生成占位消息），但**这个方法没有任何调用方**——设计了没接上。

**Q：为什么要 `sendTime` 强制统一？**
A：为了让批内消息的排序只能靠 seq，避免「时间排序」和「seq 排序」冲突。同批消息在 UI 上也应该看起来是同时到的。副作用是客户端指定的时间会被丢弃，这跟发送接口里「允许客户端指定 sendTime」的语义是矛盾的——这是一个真实的语义不一致，我读代码时发现的。
