# 第一部分 理论：消息队列到底在解决什么问题

## 11.1 先问一个笨问题：为什么不能直接调下一个函数

如果不用消息队列，发送接口完全可以这样写：

```go
func SendMsg(...) {
    // 1. 校验
    // 2. 分配 seq
    // 3. 写 Redis
    // 4. 写 Mongo
    // 5. 查在线用户
    // 6. 推送给每个在线用户
    return 成功
}
```

一个函数从头做到尾，逻辑清晰，调试方便。为什么要拆成「投队列 + 另一个服务消费」？

因为这里有三个无法回避的物理事实。

### 11.1.1 事实一：这些步骤的「时间尺度」差了几个数量级

| 步骤 | 典型耗时 | 波动性 |
|---|---|---|
| 参数校验 | 微秒级 | 极小 |
| 查本地缓存 | 微秒级 | 小 |
| 查 Redis | 0.1–1 ms | 中 |
| 写 Mongo | 1–10 ms | **大**（磁盘、索引、副本同步） |
| gRPC 推给网关 | 0.5–5 ms | **大**（网络、网关负载） |

如果你把「微秒级的校验」和「十毫秒级的 Mongo 写」串在一个请求里，那么**整个接口的延迟由最慢的那一环决定**，而且它的抖动会直接传导给用户。

更糟的是：Mongo 一抖（比如做了个索引重建），所有发送请求全部卡住，goroutine 堆积，内存涨，最后整个服务挂掉。**这叫「级联故障」，是微服务里最经典的死法。**

消息队列在这里起的作用叫**「隔离故障域」**：Mongo 慢了，队列积压，但发送接口不受影响。

### 11.1.2 事实二：有些步骤可以「攒着一起做」

写 Mongo 这件事有个特点：**写 1 条和写 100 条，成本差不多。**

因为一次写入的开销主要在「建立上下文、加锁、写磁盘、等副本确认」，而不是「数据量本身」。

所以如果攒 100 条一起写，单位成本能降到 1/100。

但问题来了：**你怎么知道接下来会来 100 条？**

答案是：**等一等就知道了。** 这就是批处理（batching）的核心——用几十毫秒的延迟，换几十倍的吞吐。

消息队列天然支持这件事：消费端可以从队列里一次拉一批（Kafka 的 `Fetch` 就是批量拉取），也可以在自己的内存里再攒一层。

### 11.1.3 事实三：有些步骤必须「能被重放」

假设第 6 步（推送）失败了。如果没有队列，你只能：

- 让整个请求失败，让客户端重试 → 于是第 2–5 步白做了，还要处理重复
- 或者吞掉错误，用户永远收不到推送

两种都糟。

有了队列，推送就是一个**独立的消费阶段**。它失败了，队列里的消息还在（位点没提交），可以重投、可以重试、可以补偿。**这就是「可重放性」的价值。**

### 11.1.4 一句话总结

消息队列在 IM 里的三个作用，按重要性排序：

1. **削峰填谷**：把突发的写入压力摊平到一段时间内处理
2. **故障隔离**：下游任何环节变慢/挂掉，都不影响上游
3. **可重放**：失败的处理可以重试，不必让用户重发

顺带还有第四个作用，在这个项目里特别重要：**它是「顺序」和「批处理」这两个需求的物理载体。**

## 11.2 消息队列的基本模型：五个名词

不用背，理解它们之间的关系即可。

```
生产者 Producer ──→ ┌─────────────────────────┐
                    │  Broker（消息服务器）      │
                    │   Topic A                │
                    │    ├ Partition 0  [0,1,2,3...]  ← 只能追加
                    │    ├ Partition 1  [0,1,2,3...]  │
                    │    └ Partition 2  [0,1,2,3...]  │
                    └─────────────────────────┘
                                  │
                    消费者组 Consumer Group
                      ├ Consumer 1  ← 领走 Partition 0
                      ├ Consumer 2  ← 领走 Partition 1
                      └ Consumer 3  ← 领走 Partition 2
```

### 11.2.1 Topic（主题）

**Topic 是消息的分类目录。** 你可以理解成一个「频道」或者「信箱」。

发消息时必须指定 topic，消费时也必须订阅 topic。不同 topic 的消息互不干扰。

OpenIM 用了四个 topic：

| Topic | 谁生产 | 谁消费 | 干什么 |
|---|---|---|---|
| `toRedis` | msg 服务 | msgtransfer | 分配 seq、写 Redis 缓存、建会话 |
| `toMongo` | msgtransfer | msgtransfer（另一个消费者） | 真正持久化到 Mongo |
| `toPush` | msgtransfer | push 服务 | 在线推送 + 离线推送决策 |
| `toOfflinePush` | push 服务 | push 服务（另一个消费者） | 走厂商通道做离线推送 |

**这四个 topic 串成了一条流水线**：消息依次经过，每经过一站就完成一部分工作。这是本篇最重要的结构认识。

### 11.2.2 Partition（分区）

**Topic 可以分成多个 Partition，每个 Partition 是一个独立的、只能追加的日志。**

为什么要分区？两个原因：

1. **并行度**：一个 partition 只能被一个消费者消费（在同一消费组内），所以 3 个 partition 最多 3 个消费者并行。要更高的吞吐就加 partition。
2. **顺序性**：**Kafka 只保证「单个 partition 内」的消息有序**，跨 partition 不保证。

第 2 点极其关键。它直接推导出后面所有的设计：

> 如果我要保证「同一个会话的消息按发送顺序被处理」，我就必须让同一个会话的消息进同一个 partition。
> 怎么做到？**用会话 ID 做分区键（key）**，Kafka 会对 key 做哈希，同 key 必然同 partition。

这就是第 10 篇讲「MsgToMQ 的 key 为什么是会话维度」的真正原因。

### 11.2.3 Offset（位点）

**Offset 是消息在 partition 里的位置编号**，从 0 开始单调递增，像数组下标。

消费者记录「我处理到哪了」，这个记录就叫**位点（offset）**。下次重启从这个位置继续。

### 11.2.4 Consumer Group（消费组）

**消费组是一组协同工作的消费者，共同消费一个 topic。**

关键规则：

- 同一个消费组内，**一个 partition 只会被一个消费者处理**（不会重复消费）
- 不同消费组之间**互不影响**，各自维护自己的位点（可以重复消费）

这解释了 OpenIM 的消费组配置：

```yaml
toRedisGroupID: redis
toMongoGroupID: mongo
toPushGroupID: push
toOfflinePushGroupID: offlinePush
```

每个 topic 一个独立消费组。这样当你扩容 push 服务到 3 个实例时，它们属于同一个组 `push`，Kafka 会自动把 `toPush` 的分区分配给三个实例，不会重复推送。

### 11.2.5 位点提交：at-least-once 的实现机制

消费者的处理流程是：

```
1. 拉取一批消息（offset 100-199）
2. 处理它们
3. 提交位点（告诉 Kafka：我处理到 199 了）
```

如果第 3 步在崩溃前没执行，那么重启后会从 100 重新拉——**消息被重复处理**。

如果先提交再处理，崩了就会丢消息。

所以默认策略是「先处理后提交」，得到 **at-least-once**（至少一次）。这也解释了第 10 篇说的「每个环节都要能吸收重复」。

> **OpenIM 的做法更严格一点**：它把「提交位点」这一步**手动化**了。批处理全部完成后，才调用 `Mark() + Commit()`。这样如果批处理中途失败，位点不前进，整批会重投。（源码位置：`online_history_msg_handler.go:105-108`，本篇 11.16 节详解）

## 11.3 Kafka 的几个反直觉特性

这几个点是面试常问、也最容易理解错的。

### 11.3.1 消费者是「拉」还是「推」

**Kafka 消费者是主动拉（pull）的**，broker 不会主动推。

为什么？因为 broker 不知道消费者的处理能力。如果是推，消费者处理慢的时候会被压垮。拉模式让消费者自己控制节奏：处理得慢就少拉点。

> 注意区分：前面讲 IM 消息「服务器推给客户端」是推模式；这里 Kafka 的「broker 给消费者」是拉模式。**两个层面的推/拉是不同的事，不要混。**

### 11.3.2 一条消息被消费后会被删除吗

**不会立即删除。** Kafka 的保留策略是按**时间**（默认 7 天）或**大小**，不是按消费状态。

这带来两个后果：

1. **可以重置位点重放历史消息**（运维利器，但也危险）
2. **磁盘会持续增长**，需要配保留策略

### 11.3.3 增加消费者一定能提升吞吐吗

**不一定。** 上限是 partition 数量。

如果你有 3 个 partition，起了 5 个消费者，那么**有 2 个会闲着**（分不到 partition）。

所以扩容前必须先扩 partition。而 partition 数量**只能增不能减**（Kafka 的限制），且增加 partition 会**破坏 key 到 partition 的映射**——原来同一个会话在 partition 1，扩完可能跑到 partition 3。这是一个真实的运维陷阱：

> 扩容 partition 后，短时间内的消息可能乱序（旧消息在旧 partition，新消息在新 partition，两个 partition 并行消费）。

### 11.3.4 消费组再平衡（Rebalance）

当消费者加入或离开（扩容、缩容、崩溃、网络抖动），消费组会重新分配 partition。这个过程叫 **Rebalance**。

Rebalance 期间**整个消费组会暂停消费**（Stop-The-World）。如果频繁 Rebalance，消费会反复卡顿。

常见触发原因：
- 消费者心跳超时（处理一批消息太久，没来得及发心跳）
- `max.poll.interval.ms` 超时（两次拉取间隔太长）

**这解释了一个设计约束**：单批消息的处理时间不能太长。OpenIM 的批处理是 500 条 / 100ms 间隔，正常情况下处理很快；但如果下游 Mongo 卡了 30 秒，就可能触发 Rebalance。这是一个需要监控的边界。

## 11.4 三种队列引擎：为什么要可替换

OpenIM 的 `mqbuild` 支持三种引擎：

| 引擎 | 适用场景 | 特点 |
|---|---|---|
| **Kafka** | 生产环境 | 高吞吐、持久化、多副本，但运维重 |
| **Redis Stream** | 中小规模 / 已有 Redis | 轻量，但持久性和吞吐弱于 Kafka |
| **内存（simmq）** | 单机开发 / 演示 | 零依赖，进程重启消息全丢 |

为什么要有三种？

因为**部署形态差异巨大**：

- 大厂生产：Kafka 集群现成，用 Kafka
- 中小项目：不想多维护一套 Kafka，Redis 反正有，用 Stream
- 本地开发：只想跑通功能，不想起 Kafka，用内存

配置在 `config/share.yml`：

```yaml
queue: kafka
```

改一个字符串就能切换引擎。这背后是**面向接口编程**的威力——上层代码只依赖 `mq.Producer` / `mq.Consumer` 接口，不关心底层是谁。

> 这是「依赖倒置原则」的教科书级应用：高层模块（msgtransfer）不依赖低层模块（Kafka），两者都依赖抽象（mq 接口）。切换 Kafka → Redis Stream 不需要改一行业务代码。

## 11.5 批处理（Batching）：用延迟换吞吐

### 11.5.1 一个生活类比

想象你是一个快递员，要送 100 个包裹到同一栋楼。

- **方式 A（逐条）**：每拿一个包裹就跑一趟。100 趟。
- **方式 B（批量）**：先把 100 个包裹装车，跑一趟。

显然 B 高效。但 B 有个代价：**你得等包裹攒够才发车**。

如果包裹来得很慢（一分钟一个），等攒够 100 个要 100 分钟，那用户会骂人。

所以真实的策略是：**「攒够 100 个就走，或者等 50 毫秒还没攒够也走」**。

这就是批处理的**双触发条件**：

```
min(数量达到阈值, 等待时间达到阈值) → 立即处理
```

### 11.5.2 OpenIM 的批处理参数

```go
// internal/msgtransfer/online_history_msg_handler.go:32-39
const (
	size              = 500                     // 攒够 500 条就处理
	mainDataBuffer    = 500                     // 主输入 channel 缓冲 500
	subChanBuffer     = 50                      // 每个 worker 的输入缓冲 50
	worker            = 50                      // 50 个处理协程
	interval          = 100 * time.Millisecond  // 或者每 100ms 强制处理
	hasReadChanBuffer = 1000                    // 已读 seq 异步通道缓冲
)
```

画成图：

```
Kafka ──→ [data chan 容量500] ──→ scheduler（唯一）
                                     │ 攒到 500 条 或 100ms 到点
                                     ↓
                              按 key 分组 + 哈希分片
                                     │
              ┌──────────┬───────────┼───────────┬──────────┐
              ↓          ↓           ↓           ↓          ↓
          worker0    worker1     worker2  ...  worker49   （各带容量50的 channel）
              ↓          ↓           ↓           ↓          ↓
         处理会话A   处理会话B    处理会话C    ...      处理会话X
```

### 11.5.3 500 条 / 100ms 这两个数怎么来的

这是典型的**经验值 + 压测调优**，没有理论最优解。但可以推导出约束：

**为什么 size 不能太大？**

- 一批太大会导致单批处理时间长 → 可能触发 Kafka Rebalance
- 失败时重投的代价大（500 条全重来）
- 内存占用

**为什么 interval 不能太大？**

- 消息稀疏时（比如凌晨），等 1 秒才处理一批，用户会感到明显延迟
- 100ms 基本是人感觉不到的上限

**为什么 worker 是 50？**

- 每个 worker 处理一个「分片」的会话，是 CPU + IO 混合型任务
- 50 在 4–8 核机器上能跑满 IO 等待，又不至于过度切换

> 面试时被问「这个参数怎么定」，正确答法是：**说清约束条件，然后说明要靠压测找拐点**。不要说「拍脑袋定的」，也不要说「这是最优值」。

### 11.5.4 批处理的三个隐藏代价

| 代价 | 说明 |
|---|---|
| **延迟增加** | 最坏情况多等一个 interval（100ms） |
| **失败放大** | 一批里只要有一条处理失败，整批可能都要重来（取决于错误处理策略） |
| **内存占用** | 攒着的消息都在内存里，size × 单条大小 × 并发批次数 |

## 11.6 分片（Sharding）：保序的真正机制

### 11.6.1 问题：50 个 worker 并行，怎么保证同会话不乱序

假设会话 A 的消息 M1、M2、M3 被同一个批次收进来了。如果三个 worker 同时处理，M2 可能先于 M1 写完——seq 就乱了。

解决办法：**同一个会话的消息，永远交给同一个 worker。**

实现：

```go
// internal/msgtransfer/online_history_msg_handler.go:95-98
b.Sharding = func(key string) int {
	hashCode := stringutil.GetHashCode(key)
	return int(hashCode) % och.redisMessageBatches.Worker()
}
```

三步：
1. 对 key（会话唯一键）做哈希，得到一个整数
2. 对 worker 数量取模，得到 `[0, worker-1]` 之间的一个下标
3. 这个 key 的所有消息都投给这个 worker 的 channel

因为哈希函数是确定的（同一个 key 永远得到同一个值），取模也是确定的，所以**同一个 key 永远落同一个 worker**。

### 11.6.2 这里有个前提：worker 数量必须固定

如果 worker 数从 50 变成 51，`hash % 50` 和 `hash % 51` 的结果不同，同一个会话就会跑到别的 worker 去。

**这就是「一致性哈希」要解决的问题**：让节点增减时，只有少量 key 需要重新映射。

OpenIM 这里没做一致性哈希，因为 worker 数量是**进程内固定的常量**，不会动态变。所以简单取模就够了。

但如果要做「动态调整 worker 数量」或「多实例共享分片」，就必须上一致性哈希（或者像 Redis Cluster 那样的固定槽位方案）。

> 这是一个可以主动指出的设计局限：**取模分片在「分片数固定」时是正确且高效的，一旦分片数可变就会失效。**

### 11.6.3 保序的三层防线

到这里可以给出完整答案了。OpenIM 保证「同会话有序」靠三层：

| 层级 | 机制 | 保证什么 |
|---|---|---|
| **Kafka 分区** | 用会话 key 做分区键 | 同会话进同一 partition，消费顺序 = 生产顺序 |
| **内存分片** | hash(key) % worker | 同会话进同一 worker，批内不会并发处理 |
| **批量写入** | 一个 key 的消息作为一个 `Msg` 投给 worker | 一次 `Do` 调用内顺序处理 |

三层缺一不可：

- 少了第 1 层：不同实例消费到同一会话的不同消息，并发乱序
- 少了第 2 层：同一批次内 50 个 worker 并发处理同一会话
- 少了第 3 层：即使同一 worker，如果一条一条异步处理也没用

**这就是「有序」在分布式系统里的真实代价：它不是一个开关，是一整条链路上每一层都得配合。**

## 11.7 背压（Backpressure）：慢下来的时候会发生什么

### 11.7.1 什么是背压

**背压 = 下游处理不过来时，压力反向传导给上游，让上游慢下来。**

这是分布式系统的安全阀。没有背压的系统，遇到突发流量只有一种结局：内存爆掉，进程被 OOM Killer 干掉。

### 11.7.2 OpenIM 的背压链

看这条链路：

```
Kafka 消费回调 HandlerRedisMessage
  → b.Put(data)                  // 写 data chan（容量 500）
    → 满了就阻塞
      → 回调阻塞
        → Kafka 客户端不再拉新消息
          → broker 侧堆积（消息留在磁盘上，不占内存）
```

这是一条**优雅的背压链**：压力最终落到了 Kafka 的磁盘上，而不是内存里。

```go
// pkg/tools/batcher/batcher.go:138-150
func (b *Batcher[T]) Put(ctx context.Context, data *T) error {
	if data == nil {
		return errs.New("data can not be nil").Wrap()
	}
	select {
	case <-b.globalCtx.Done():
		return errs.New("data channel is closed").Wrap()
	case <-ctx.Done():
		return ctx.Err()
	case b.data <- data:
		return nil
	}
}
```

注意这里用了 `select` 三路：

1. 全局 ctx 取消（服务要关了）→ 返回错误
2. 本条消息的 ctx 取消（超时）→ 返回 `ctx.Err()`
3. 写入成功

**第 2 路很关键**：如果 data chan 满了，`Put` 会一直阻塞，但一旦消息的 ctx 超时，它就会放弃写入并返回错误。这避免了「无限等一个永远不来的空位」。

不过要注意一个副作用：`HandlerRedisMessage` 里对 `Put` 的错误**只记日志，仍然返回 nil**：

```go
// online_history_msg_handler.go:385-391
func (och *OnlineHistoryRedisConsumerHandler) HandlerRedisMessage(msg mq.Message) error {
	err := och.redisMessageBatches.Put(msg.Context(), &ConsumerMessage{...})
	if err != nil {
		log.ZWarn(msg.Context(), "put msg to  error", err, "key", msg.Key(), "value", msg.Value())
	}
	return nil
}
```

返回 nil 意味着 Kafka 认为这条消息处理成功，位点会前进。**如果 `Put` 因为缓冲满超时而失败，这条消息就丢了。**

这是一个真实的可靠性短板。更严格的写法应该是返回 error，让 Kafka 不提交位点（下次重投）。

> **面试可以讲这个点**：这是一个「日志告警型」的错误处理——出了问题只记日志不阻断，牺牲可靠性换简单。如果要做严，应该返回错误让消费失败重试，或者加一个本地落盘缓冲。

### 11.7.3 另一种背压：worker channel 的缓冲

```go
subChanBuffer = 50
```

每个 worker 的输入 channel 缓冲 50 个 `Msg`。如果 worker 处理慢，这个 channel 会满，`distributeMessage` 里的 `b.chArrays[channelID] <- ...` 会阻塞。

而 `distributeMessage` 是在 **scheduler goroutine** 里同步执行的，所以：

```
某个 worker 慢 → 它的 channel 满 → scheduler 阻塞 → data chan 不再被消费 → 满 → Put 阻塞
```

**背压完美地传导到了最上游。** 这是设计得比较好的地方。

副作用是：**一个慢的分片会拖慢整个 scheduler**。如果某个会话特别热（比如一个百万人大群），处理它的 worker 会成为瓶颈，整个流水线的吞吐都被它拉下来。

这是「按 key 分片」的固有缺点：**热点 key 无法拆分**。解决思路是「热点会话单独隔离处理」，但那就破坏了同会话有序的保证，需要更复杂的设计。

## 11.8 幂等：重复消费时怎么不出错

at-least-once 意味着每条消息都可能被处理多次。每个写入点都必须幂等。

看 OpenIM 在 msgtransfer 这一站的三个写入点：

| 写入点 | 幂等机制 |
|---|---|
| **Redis 消息缓存** | 以 seq 为 hash field，同一个 seq 重复写就是覆盖 |
| **Redis seq 分配** | 见第 12 篇（Lua 脚本 + 锁） |
| **Mongo 落库** | 先 update 命中则跳过，未命中才 insert；insert 撞 `_id` 唯一索引则转 update |
| **会话更新** | `SetConversations` 是覆盖式写，重复执行结果相同 |

**注意一个反直觉的点：seq 的重复分配是不幂等的。**

如果同一批消息被消费两次，会分配两段不同的 seq：

```
第一次：M1→seq 101, M2→seq 102
第二次：M1→seq 103, M2→seq 104
```

结果是 Mongo 里可能同时存在 seq 101 和 103 两条内容相同（ClientMsgID 相同）的消息。

**这是 OpenIM 的一个真实弱点。** 它靠的是：
1. Kafka 位点提交相对及时（批处理完就提交），重复窗口小
2. 客户端拉消息时按 ClientMsgID 去重

但从服务端视角，**没有做到严格幂等**。要做严格幂等，需要在 Redis 里维护「ClientMsgID → seq」的映射，分配前先查。这是一个可以指出的改进方向。

## 11.9 消费者为什么不会「抢同一条消息」

最后一个理论点，容易混淆。

| 场景 | 会不会重复消费同一条 |
|---|---|
| 同一消费组内多个消费者 | ❌ 不会，partition 被独占分配 |
| 不同消费组消费同一 topic | ✅ 会，各自独立位点 |
| 消费者崩溃重启（未提交位点） | ✅ 会，从上次提交位置重来 |
| 同一消费者内多线程 | ❌ 不会（Kafka 客户端保证分区内单线程） |

所以「重复」只会来自「位点回退」和「生产端重复投递」，不会来自「多个消费者抢活」。

## 11.11 msgtransfer：一个进程，两条消费流水线

### 11.11.1 初始化顺序

**最关键的结构认识：msgtransfer 同时是 `toMongo` 的生产者和消费者。**

```
msgtransfer ──生产──→ toMongo ──消费──→ msgtransfer（另一个 handler）
```

为什么要绕一圈，而不是「分配完 seq 直接写 Mongo」？

三个理由：

1. **解耦写入节奏**：分配 seq 是内存+Redis 操作（快），写 Mongo 是磁盘操作（慢）。中间隔一层，分配 seq 就不会被 Mongo 拖慢。
2. **可观测**：`toMongo` 的积压量直接反映「落库跟不上」的程度，是一个天然的监控指标。
3. **可重放**：落库失败可以重投，而不需要重新分配 seq（seq 一旦分配就不能变，否则会话序号出现空洞或重复）。

第 3 点是本质原因：**seq 分配和落库必须在不同的、可以独立重试的阶段。**

### 11.11.2 两条消费循环

```go
// internal/msgtransfer/init.go:113-149
func (m *MsgTransfer) Start(ctx context.Context) error {
	var cancel context.CancelCauseFunc
	m.ctx, cancel = context.WithCancelCause(ctx)

	// 循环 1：消费 toRedis
	go func() {
		for {
			if err := m.historyConsumer.Subscribe(m.ctx, m.historyHandler.HandlerRedisMessage); err != nil {
				cancel(fmt.Errorf("history consumer %w", err))
				return
			}
		}
	}()

	// 循环 2：消费 toMongo
	go func() {
		fn := func(msg mq.Message) error {
			m.historyMongoHandler.HandleChatWs2Mongo(msg)
			return nil
		}
		for {
			if err := m.historyMongoConsumer.Subscribe(m.ctx, fn); err != nil {
				cancel(fmt.Errorf("history mongo consumer %w", err))
				return
			}
		}
	}()

	// 循环 3：已读 seq 异步落库
	go m.historyHandler.HandleUserHasReadSeqMessages(m.ctx)

	err := m.historyHandler.redisMessageBatches.Start()
	...
}
```

几个必须注意的细节：

**细节 1：`Subscribe` 外面包了一层 `for {}`**

为什么？因为 `Subscribe` 是阻塞的，正常情况下只有 ctx 取消才返回。但如果它因为**网络抖动、broker 重启**而返回错误，这层 `for` 会让它自动重连。

**但这里有个 bug 风险**：看代码，`Subscribe` 返回 err 时执行的是 `cancel(...)` 然后 `return`——**它并没有重连，而是直接退出了！**

```go
if err := m.historyConsumer.Subscribe(m.ctx, m.historyHandler.HandlerRedisMessage); err != nil {
	cancel(fmt.Errorf("history consumer %w", err))
	log.ZError(m.ctx, "historyConsumer err", err)
	return   // ← 直接 return，for 循环白写了
}
```

所以这个 `for {}` 实际上是**死代码**（只可能执行一次）。正确写法应该是 `log + continue`（带退避），或者把 `cancel` 放在重试多次之后。

> **这是一个非常好的面试素材**：能指出「这里有个 for 循环但实际不会循环」说明你不是在背架构图，而是真的一行行读过代码。

**细节 2：`historyMongoHandler.HandleChatWs2Mongo(msg)` 的返回值被吞掉**

```go
fn := func(msg mq.Message) error {
	m.historyMongoHandler.HandleChatWs2Mongo(msg)
	return nil   // ← 永远返回 nil
}
```

`HandleChatWs2Mongo` 没有返回值（`online_msg_to_mongo_handler.go:28`），它内部自己处理错误：成功就 `val.Mark()`，失败只记日志。

**所以落库失败时，位点还是会被提交**——除非 Kafka 客户端有别的机制。这意味着**落库失败的消息会丢**。

回忆第 10 篇 10.18.2 节列的「黑洞消息」风险，这里就是它的具体实现位置。

> 这也解释了为什么 `HandleChatWs2Mongo` 要放在「我要做的内部改进」清单里：**把落库结果返回给调用方，让失败的消息不提交位点**。这是一个改动小、收益明确的改进点（第 00 篇总纲里提到的「一处内部改进」）。

**细节 3：`cancel` 用的是 `context.WithCancelCause`**

普通的 `context.WithCancel` 只能取消，不能带原因。`WithCancelCause` 可以传一个 error，最后用 `context.Cause(m.ctx)` 取出来。

好处是：进程退出时能告诉上层「我是因为哪个消费者的什么错误退出的」，而不是笼统的 `context canceled`。

## 11.12 batcher：50 行核心代码撑起整个吞吐

这是全篇最值得精读的一段。文件只有 285 行，但设计密度很高。

### 11.12.1 三层结构

```
Put() ──→ data chan ──→ scheduler goroutine ──→ chArrays[0..49] ──→ 50 个 run() goroutine
         （容量500）      （唯一，攒批+分片）      （每个容量50）        （调 Do 处理）
```

### 11.12.2 scheduler：攒批逻辑

```go
// pkg/tools/batcher/batcher.go:152-210
func (b *Batcher[T]) scheduler() {
	ticker := time.NewTicker(b.config.interval)
	externallyClosed := false
	defer func() {
		ticker.Stop()
		for _, ch := range b.chArrays {
			close(ch)
		}
		if !externallyClosed {
			close(b.data)
		}
		b.wait.Done()
	}()

	vals := make(map[string][]*T)
	count := 0
	var lastAny *T

	for {
		select {
		case data, ok := <-b.data:
			if !ok {
				externallyClosed = true
				return
			}
			if data == nil {
				if count > 0 {
					b.distributeMessage(vals, count, lastAny)
				}
				return
			}

			key := b.Key(data)
			vals[key] = append(vals[key], data)
			lastAny = data

			count++
			if count >= b.config.size {
				b.distributeMessage(vals, count, lastAny)
				vals = make(map[string][]*T)
				count = 0
			}

		case <-ticker.C:
			if count > 0 {
				b.distributeMessage(vals, count, lastAny)
				vals = make(map[string][]*T)
				count = 0
			}
		}
	}
}
```

**逐行要点：**

**要点 1：`vals` 是 `map[key][]*T`，天然按会话分组**

这是「分组」的实现方式：收到消息就按 key 塞进 map 的对应 slice。攒批结束时，每个 key 已经是一个有序的数组。

**为什么用 map 而不是先攒一个大 slice 再分组？**

因为用 map 是 O(1) 插入，分组在攒的过程中就完成了。如果先攒 slice 再分组，要额外遍历一遍。而且 `vals[key] = append(...)` 保证了**同 key 的消息保持到达顺序**（append 到尾部）。

**要点 2：`ticker` 是「兜底触发」**

如果消息稀疏，`count` 永远到不了 500，就靠 100ms 的 ticker 强制刷出去。

**这是一个经典的双触发设计**，与 11.5.1 节讲的快递员策略完全对应。

**要点 3：`data == nil` 是关闭信号**

`Close()` 里发一个 `nil`，scheduler 收到后把剩余的刷出去再退出。注意这里是**先 flush 再 return**，不能丢数据。

**要点 4：`externallyClosed` 这个变量**

这是个 bug 修复的痕迹（注释里提了 issue #3653）。原因是：如果外部已经 `close(b.data)`，那么 defer 里再 `close(b.data)` 会 panic（`close of closed channel`）。

**这是一个很好的 Go 并发知识点**：channel 的所有权必须明确。谁创建谁关闭（或者谁发送谁关闭），否则就会出现重复关闭。

**要点 5：`lastAny` 不是 `lastMessage`**

注意传给 `distributeMessage` 的是**整批最后一条**（`lastAny`），不是某个 key 的最后一条。这个参数用于 `OnComplete` 里的 `Mark + Commit`——标记「这批消息已经处理到哪」。（见 11.16 节）

### 11.12.3 distributeMessage：分片 + 同步等待

```go
// pkg/tools/batcher/batcher.go:245-261
func (b *Batcher[T]) distributeMessage(messages map[string][]*T, totalCount int, lastMessage *T) {
	triggerID := idutil.OperationIDGenerator()
	b.HookFunc(triggerID, messages, totalCount, lastMessage)
	for key, data := range messages {
		if b.config.syncWait {
			b.counter.Add(1)
		}
		channelID := b.Sharding(key)
		b.chArrays[channelID] <- &Msg[T]{key: key, triggerID: triggerID, val: data}
	}
	if b.config.syncWait {
		b.counter.Wait()
	}
	if b.OnComplete != nil {
		b.OnComplete(lastMessage, totalCount)
	}
}
```

**这是全篇最关键的五段代码之一。逐点分析：**

**要点 1：`triggerID` 是给整批消息用的追踪 ID**

```go
triggerID := idutil.OperationIDGenerator()
```

注意它是**整批**共用一个。这个名字起得很准确：**trigger（触发）**，表示「这一批是由同一次触发产生的」。

为什么要这个？因为一条消息从发送到落库，跨越了多个异步阶段，原始的 operationID 已经断了。用 triggerID 可以把「同一批进来的消息」关联起来，方便排查「这一批为什么都失败了」。

**要点 2：`b.counter.Add(1)` / `Wait()` 是同步等待**

`syncWait = true`（构造时设置了 `WithSyncWait(true)`，见 `online_history_msg_handler.go:92`）意味着：**scheduler 会阻塞等所有 worker 处理完这一批，才继续下一批。**

这带来两个重要后果：

| 后果 | 影响 |
|---|---|
| ✅ 位点提交顺序正确 | 只有全部处理完才 `OnComplete` → `Commit`，不会出现「提交了但没处理完」 |
| ❌ 吞吐受限 | 下一批必须等上一批全做完，scheduler 无法流水线化 |

**为什么选择「受限但正确」？**

因为位点提交的正确性优先于吞吐。如果异步不等待，可能出现「第 1 批还没处理完，第 2 批已经处理完并提交了位点」——一旦此时进程崩溃，第 1 批就永久丢了。

> 这是一个非常经典的分布式权衡：**「异步 + 位点」必须搭配「同步等待」，否则位点会撒谎。**

**要点 3：`b.chArrays[channelID] <- ...` 可能阻塞**

如果目标 worker 慢，它的 channel 满了，这行会阻塞，整个 scheduler 停下。这就是 11.7.3 节说的「一个慢分片拖慢全局」。

**要点 4：`HookFunc` 是空实现（默认）**

```go
// pkg/tools/batcher/batcher.go:86-88
func emptyOnComplete[T any](*T, int) {}

```

留着这个钩子是给业务加观测用的（比如统计每批大小）。当前项目没用，属于「预留扩展点」。

### 11.12.4 run：每个 worker 的处理循环

```go
// pkg/tools/batcher/batcher.go:263-278
func (b *Batcher[T]) run(channelID int, ch <-chan *Msg[T]) {
	defer b.wait.Done()
	ctx := authverify.WithTempAdmin(context.Background())
	for {
		select {
		case messages, ok := <-ch:
			if !ok {
				return
			}
			b.Do(ctx, channelID, messages)
			if b.config.syncWait {
				b.counter.Done()
			}
		}
	}
}
```

**要点 1：`authverify.WithTempAdmin(context.Background())`**

**这一行非常重要，是本篇最容易被忽略的细节。**

worker 用的 ctx 是 `context.Background()`（全新的，不带任何调用者身份），但包了一层 `WithTempAdmin`——把它标记成**临时管理员**。

为什么要这样？

因为下游处理时会调用其他 RPC 服务（比如 `GetGroupMemberUserIDs`、`CreateGroupChatConversations`），而这些 RPC 的入口有 `CheckAccess` 校验（第 10 篇讲的）。worker 是一个「系统后台任务」，它没有真实用户身份，如果不标记成管理员，就会被权限校验挡住。

**这是「系统内部调用如何绕过用户级鉴权」的标准解法：显式声明自己是特权身份，而不是关掉校验。**

对比一下错误做法：如果把 `CheckAccess` 改成「查不到用户身份就放行」，那就等于开了后门。而 `WithTempAdmin` 是显式的、可审计的（日志里能看到是谁在调用）。

**要点 2：`Do` 是同步调用**

```go
b.Do(ctx, channelID, messages)
```

`Do` 返回后才 `counter.Done()`。所以 `Wait()` 真的能等到所有处理完成。

**要点 3：`defer b.wait.Done()` 但**没有** `recover`**

如果 `Do` 里 panic，这个 goroutine 会崩，`counter.Done()` 不会执行，`counter.Wait()` 永远卡住 → **整个批处理死锁**。

而 goroutine 里的 panic 会导致**整个进程崩溃**（Go 的默认行为）。

好在 `Do` 的实现（`online_history_msg_handler.go:112`）里没有 recover，所以 panic 直接崩进程。**这在某种程度上是「好事」**：崩了能重启，死锁就只能人工介入。

但从健壮性角度，更稳妥的做法是在 `run` 里加 recover 并保证 `counter.Done()`（用 defer）。

> **这是一个值得指出的可靠性缺口**：批处理框架的 worker 没有 panic 保护，任何一条畸形消息导致的 panic 都会让整个服务崩。生产环境应该加 `defer recover()`。

## 11.13 Do：一批消息的八步处理

```go
// internal/msgtransfer/online_history_msg_handler.go:112-128
func (och *OnlineHistoryRedisConsumerHandler) do(ctx context.Context, channelID int, val *batcher.Msg[ConsumerMessage]) {
	ctx = mcontext.WithTriggerIDContext(ctx, val.TriggerID())
	ctxMessages := och.parseConsumerMessages(ctx, val.Val())
	ctx = withAggregationCtx(ctx, ctxMessages)
	log.ZInfo(ctx, "msg arrived channel", "channel id", channelID, "msgList length", len(ctxMessages), "key", val.Key())
	och.doSetReadSeq(ctx, ctxMessages)

	storageMsgList, notStorageMsgList, storageNotificationList, notStorageNotificationList :=
		och.categorizeMessageLists(ctxMessages)

	conversationIDMsg := msgprocessor.GetChatConversationIDByMsg(ctxMessages[0].message)
	conversationIDNotification := msgprocessor.GetNotificationConversationIDByMsg(ctxMessages[0].message)
	och.handleMsg(ctx, val.Key(), conversationIDMsg, storageMsgList, notStorageMsgList)
	och.handleNotification(ctx, val.Key(), conversationIDNotification, storageNotificationList, notStorageNotificationList)
}
```

拆成八步：

| 步 | 动作 | 作用 |
|---|---|---|
| 1 | `WithTriggerIDContext` | 给 ctx 挂上批次追踪 ID |
| 2 | `parseConsumerMessages` | protobuf 反序列化，坏消息跳过 |
| 3 | `withAggregationCtx` | 把这一批所有原始 operationID 拼起来 |
| 4 | `doSetReadSeq` | 把已读回执类消息的 seq 直接写 DB |
| 5 | `categorizeMessageLists` | 四分类 |
| 6 | 算两个 conversationID | 普通消息会话 vs 通知会话 |
| 7 | `handleMsg` | 处理普通消息 |
| 8 | `handleNotification` | 处理通知消息 |

### 11.13.1 第 2 步：坏消息为什么只是「跳过」

```go
// online_history_msg_handler.go:178-194
func (och *OnlineHistoryRedisConsumerHandler) parseConsumerMessages(ctx context.Context, consumerMessages []*ConsumerMessage) []*ContextMsg {
	var ctxMessages []*ContextMsg
	for i := 0; i < len(consumerMessages); i++ {
		ctxMsg := &ContextMsg{}
		msgFromMQ := &sdkws.MsgData{}
		err := proto.Unmarshal(consumerMessages[i].Value, msgFromMQ)
		if err != nil {
			log.ZWarn(ctx, "msg_transfer Unmarshal msg err", err, string(consumerMessages[i].Value))
			continue   // ← 跳过
		}
		...
	}
}
```

反序列化失败的消息**记日志后跳过**，不阻断整批。

这是**「毒丸消息」（poison message）**的处理：如果一条消息永远无法解析，让它阻断整个队列会导致永久停滞。所以必须跳过。

代价是：**这条消息彻底丢了**。更严谨的做法是投到一个「死信队列」（DLQ）里，供后续人工分析。

> `string(consumerMessages[i].Value)` 把原始字节打成字符串——这个日志很有用，但要注意消息里可能有敏感内容，生产环境要谨慎。

### 11.13.2 第 3 步：withAggregationCtx 的巧思

```go
// online_history_msg_handler.go:371-383
func withAggregationCtx(ctx context.Context, values []*ContextMsg) context.Context {
	var allMessageOperationID string
	for i, v := range values {
		if opid := mcontext.GetOperationID(v.ctx); opid != "" {
			if i == 0 {
				allMessageOperationID += opid
			} else {
				allMessageOperationID += "$" + opid
			}
		}
	}
	return mcontext.SetOperationID(ctx, allMessageOperationID)
}
```

把这一批里**每条消息**的原始 operationID 用 `$` 拼成一个大字符串（例如 `abc123$def456$ghi789`），设为新的 operationID。

**为什么这么做？**

因为追踪系统通常只支持「一个 ID 查一条链路」。而这里 500 条消息被合并成一次处理，如果只保留第一条的 ID，另外 499 条就查不到落库日志了。

拼接之后，**任何一条原始消息的 operationID 都能通过「包含匹配」搜到这一批的日志**。

代价是：operationID 变得很长（500 条 × 32 字符 ≈ 16KB）。这会出现在每条日志里，日志体积显著增大。

**这是一个「可观测性 vs 存储成本」的权衡**，而且选择了偏向前者。生产环境如果日志量很大，可能需要改成「只记第一条 + 记录一个批次 ID」。

### 11.13.3 第 4 步：doSetReadSeq 为什么单独处理

```go
// online_history_msg_handler.go:130-176
func (och *OnlineHistoryRedisConsumerHandler) doSetReadSeq(ctx context.Context, msgs []*ContextMsg) {
	conversationUserSeq := make(map[string]map[string]int64)
	for _, msg := range msgs {
		if msg.message.ContentType != constant.HasReadReceipt {
			continue
		}
		var elem sdkws.NotificationElem
		json.Unmarshal(msg.message.Content, &elem)
		var tips sdkws.MarkAsReadTips
		json.Unmarshal([]byte(elem.Detail), &tips)
		if len(tips.ConversationID) == 0 || tips.HasReadSeq < 0 {
			continue
		}
		// 从 tips.Seqs 中计算最大 seq
		for _, seq := range tips.Seqs {
			if tips.HasReadSeq < seq {
				tips.HasReadSeq = seq
			}
		}
		// 只保留最大值
		if conversationUserSeq[tips.ConversationID][tips.MarkAsReadUserID] < tips.HasReadSeq {
			conversationUserSeq[tips.ConversationID][tips.MarkAsReadUserID] = tips.HasReadSeq
		}
	}
	for convID, userSeqMap := range conversationUserSeq {
		och.msgTransferDatabase.SetHasReadSeqToDB(ctx, convID, userSeqMap)
	}
}
```

**要点 1：只处理 `HasReadReceipt` 类型**

已读回执是「通知类消息」，它本身不需要存历史，但它携带的「已读 seq」需要**落库**。所以单独提前处理，不进入后面的正常消息流程。

**要点 2：取最大值而不是逐个写**

如果一批里有同一用户的三条已读回执（读了 10、读了 12、读了 15），只需要写 `15`——因为已读 seq 是单调的，写最大值覆盖即可。

这是一个**「合并写」优化**，把 N 次 DB 写降到 1 次。IM 里这种「单调递增取最大」的模式非常常见（未读数、已读 seq、maxSeq 都是）。

**要点 3：两次 JSON 反序列化**

```go
json.Unmarshal(msg.message.Content, &elem)      // 第一层：NotificationElem
json.Unmarshal([]byte(elem.Detail), &tips)      // 第二层：MarkAsReadTips
```

消息内容是一个 JSON，里面有个 `detail` 字段又是**序列化后的 JSON 字符串**。这是「双层 JSON」结构。

为什么要这样？因为 `NotificationElem` 是个通用信封（所有通知共用一个结构），`Detail` 存具体的业务数据（不同通知类型结构不同）。

**代价是解析成本翻倍**，而且 `elem.Detail` 是 string 不是 object，前端也要解两次。这是协议设计上的一个妥协——用「字符串套字符串」换「信封结构统一」。

### 11.13.4 第 5 步：四分类的意义

```go
// online_history_msg_handler.go:197-238
func (och *OnlineHistoryRedisConsumerHandler) categorizeMessageLists(totalMsgs []*ContextMsg) (storageMsgList,
	notStorageMsgList, storageNotificationList, notStorageNotificationList []*ContextMsg) {
	for _, v := range totalMsgs {
		options := msgprocessor.Options(v.message.Options)
		if !options.IsNotNotification() {
			// 是通知
			if options.IsSendMsg() {
				// 从通知消息中克隆一条用于存储的消息
				msg := proto.Clone(v.message).(*sdkws.MsgData)
				if v.message.Options != nil {
					msg.Options = msgprocessor.NewMsgOptions()
				}
				msg.Options = msgprocessor.WithOptions(msg.Options,
					msgprocessor.WithOfflinePush(options.IsOfflinePush()),
					msgprocessor.WithUnreadCount(options.IsUnreadCount()),
				)
				v.message.Options = msgprocessor.WithOptions(
					v.message.Options,
					msgprocessor.WithOfflinePush(false),
					msgprocessor.WithUnreadCount(false),
				)
				ctxMsg := &ContextMsg{message: msg, ctx: v.ctx}
				storageMsgList = append(storageMsgList, ctxMsg)
			}
			if options.IsHistory() {
				storageNotificationList = append(storageNotificationList, v)
			} else {
				notStorageNotificationList = append(notStorageNotificationList, v)
			}
		} else {
			if options.IsHistory() {
				storageMsgList = append(storageMsgList, v)
			} else {
				notStorageMsgList = append(notStorageMsgList, v)
			}
		}
	}
	return
}
```

**这段代码的核心是「克隆 + 双份不同配置」，非常精妙，值得慢慢拆。**

先看判定树：

```
IsNotNotification() == false（是通知）
├── IsSendMsg() == true
│     → 克隆一份进 storageMsgList（要存储的「消息版本」）
│     → 原消息按 IsHistory() 进 storageNotificationList 或 notStorageNotificationList
└── IsSendMsg() == false
      → 原消息按 IsHistory() 进 storageNotificationList 或 notStorageNotificationList

IsNotNotification() == true（是普通消息）
├── IsHistory() → storageMsgList
└── !IsHistory() → notStorageMsgList
```

**为什么要「克隆一条」？**

想象一个场景：你被拉进一个群，系统发了一条通知「A 邀请你加入了群聊」。

这条通知有两个身份：
1. **它是通知**：要显示在会话里（存进通知会话）
2. **它也是消息**：某些产品需要它出现在聊天记录里（存进普通会话）

而两个身份需要的开关不同：
- 通知版本：不推送、不计未读（`WithOfflinePush(false)` / `WithUnreadCount(false)`）
- 消息版本：**保留**原来的推送和未读设置（`WithOfflinePush(options.IsOfflinePush())`）

所以：**克隆一份，两个版本各改各的开关，互不干扰。**

再仔细看这段：

```go
msg.Options = msgprocessor.NewMsgOptions()          // 新版本用空 map
msg.Options = msgprocessor.WithOptions(msg.Options,
	msgprocessor.WithOfflinePush(options.IsOfflinePush()),
	msgprocessor.WithUnreadCount(options.IsUnreadCount()))   // 只继承这两个

v.message.Options = msgprocessor.WithOptions(v.message.Options,
	msgprocessor.WithOfflinePush(false),
	msgprocessor.WithUnreadCount(false))            // 原版本关掉这两个
```

**注意这里改了 `v.message`（原消息）的 Options！** 而 `v.message` 还会被后续的 `toPushTopic` 使用（`handleNotification` 里 `och.toPushTopic(ctx, key, conversationID, storageList)` 传的是原始的 `v`）。

所以效果是：
- 通知版本推送出去时：不推离线、不计未读
- 消息版本存库时：保留原始的推送/未读设置（虽然存库时这两个开关意义不大）

**这个修改是「就地篡改」的，有副作用风险。** 如果后续有代码依赖原始的 Options，就会读到改过的值。更安全的写法是克隆两份，都不动原对象。

> 这是一个可以指出的**「克隆不彻底」问题**：只克隆了要给存储的那份，另一份直接改了原对象。在多处引用同一对象的场景下，这种写法容易埋雷。

### 11.13.5 为什么区分「消息会话」和「通知会话」

```go
conversationIDMsg := msgprocessor.GetChatConversationIDByMsg(ctxMessages[0].message)
conversationIDNotification := msgprocessor.GetNotificationConversationIDByMsg(ctxMessages[0].message)
```

同一个会话，有两个 ID：

| 变量 | 格式 | 用途 |
|---|---|---|
| `conversationIDMsg` | `si_A_B` / `sg_G` | 存聊天消息 |
| `conversationIDNotification` | `n_A_B` / `n_G` | 存通知消息 |

**为什么要分成两个会话？**

因为通知的**可见性规则不同**：

- 通知不计未读（你不想因为「A 加入了群聊」多一个红点）
- 通知不影响会话列表的「最后一条消息」（否则会话列表会全是「xx 加入了群聊」）
- 通知可以独立清理

但这些通知又要**显示在聊天窗口里**（你希望看到「A 加入了群聊」夹在消息中间）。

所以设计成：**存储上分开（两个会话 ID），展示上合并（客户端按时间穿插）。**

这是一个很巧妙的设计：**用存储的分离来换取规则的独立，用客户端的合并来保证体验的连贯。**

注意 `GetChatConversationIDByMsg(ctxMessages[0].message)` 用的是**第一条消息**来算会话 ID。这是安全的，因为同一个 key（同一会话）的消息，算出来的会话 ID 必然相同。

但如果一批里混了单聊和群聊呢？**不可能**，因为 key 不同会被分到不同的 `Msg` 里。

## 11.14 handleMsg：真正的核心流程

```go
// online_history_msg_handler.go:240-315
func (och *OnlineHistoryRedisConsumerHandler) handleMsg(ctx context.Context, key, conversationID string, storageList, notStorageList []*ContextMsg) {
	for _, storageMsg := range storageList {
		log.ZDebug(ctx, "handle storage msg", "msg", storageMsg.message.String())
	}

	// ① 先推「不存储」的消息（比如打字状态、已读回执）
	och.toPushTopic(ctx, key, conversationID, notStorageList)

	// ② 准备存储列表
	var storageMessageList []*sdkws.MsgData
	for _, msg := range storageList {
		storageMessageList = append(storageMessageList, msg.message)
	}

	if len(storageMessageList) > 0 {
		msg := storageMessageList[0]
		// ③ 分配 seq + 写 Redis
		lastSeq, isNewConversation, userSeqMap, err := och.msgTransferDatabase.BatchInsertChat2Cache(ctx, conversationID, storageMessageList)
		if err != nil && !errors.Is(errs.Unwrap(err), redis.Nil) {
			log.ZWarn(ctx, "batch data insert to redis err", err, "storageMsgList", storageMessageList)
			return   // ← 注意这个 return
		}

		// ④ 把「发送者已读到自己的最新消息」写进 Redis
		err = och.msgTransferDatabase.SetHasReadSeqs(ctx, conversationID, userSeqMap)
		if err != nil {
			prommetrics.SeqSetFailedCounter.Inc()
		}

		// ⑤ 异步落 DB（通过 channel 交给专门的 goroutine）
		och.conversationUserHasReadChan <- &userHasReadSeq{
			conversationID: conversationID,
			userHasReadMap: userSeqMap,
		}

		// ⑥ 新会话要创建会话记录
		if isNewConversation {
			switch msg.SessionType {
			case constant.ReadGroupChatType:
				userIDs, err := och.groupClient.GetGroupMemberUserIDs(ctx, msg.GroupID)
				och.conversationClient.CreateGroupChatConversations(ctx, msg.GroupID, userIDs)
			case constant.SingleChatType, constant.NotificationChatType:
				req := &pbconv.CreateSingleChatConversationsReq{...}
				och.conversationClient.CreateSingleChatConversations(ctx, req)
			}
		}

		// ⑦ 投 toMongo
		err = och.msgTransferDatabase.MsgToMongoMQ(ctx, key, conversationID, storageMessageList, lastSeq)

		// ⑧ 投 toPush（存储版本）
		och.toPushTopic(ctx, key, conversationID, storageList)
	}
}
```

### 11.14.1 步骤 ① 的位置很讲究：先推「不存储」的

`notStorageList` 里是什么？打字状态、已读回执、撤回提示这类**不需要存历史**的消息。

**为什么先推它们？**

因为它们**不需要等 seq**。普通消息必须等 `BatchInsertChat2Cache` 分配完 seq 才能推（推送的包里要带 seq，客户端用来排序）。而打字状态没有 seq，可以立刻推。

提前推 = 用户更快看到「对方正在输入」。

**这是一个「快路径/慢路径分离」的优化**：不依赖 seq 的消息走快路，依赖 seq 的走慢路。

### 11.14.2 步骤 ③ 的错误处理：只忽略 `redis.Nil`

```go
if err != nil && !errors.Is(errs.Unwrap(err), redis.Nil) {
	log.ZWarn(ctx, "batch data insert to redis err", err, "storageMsgList", storageMessageList)
	return
}
```

**这里的关键判断：如果错误是 `redis.Nil`，不返回，继续往下走。**

`redis.Nil` 在 go-redis 里表示「key 不存在」，通常出现在某些 GET 操作上。在写入路径上出现，意味着某个前置读取出问题了。

**为什么忽略它？**

因为后面还要写 Mongo——**Redis 只是缓存，写失败不该阻断持久化**。如果 Redis 挂了，消息至少能落 Mongo，客户端重连后按 seq 从 Mongo 拉。

但注意：**如果 Redis 写失败，seq 也已经分配了**（`BatchInsertChat2Cache` 里先 Malloc 再 SetMessageBySeqs）。所以这条消息在 Redis 里没有，但 Mongo 里有——是一个「缓存缺失但数据完整」的状态，可以接受。

而如果错误不是 `redis.Nil`（比如连接失败），直接 `return`，**后面的 toMongo 也不执行，消息丢了**。

> 这又是一个可靠性缺口：Redis 短暂不可用会导致消息没能落 Mongo。更好的做法是「Redis 失败也继续投 toMongo」，因为 Mongo 才是真相。
>
> 这可以和第 10 篇说的「黑洞消息」一起作为「改进清单」的两项。

### 11.14.3 步骤 ⑤ 为什么用 channel 而不是直接写

```go
och.conversationUserHasReadChan <- &userHasReadSeq{...}

// 另一个 goroutine 消费
func (och *OnlineHistoryRedisConsumerHandler) HandleUserHasReadSeqMessages(ctx context.Context) {
	defer func() {
		if r := recover(); r != nil {
			log.ZPanic(ctx, "HandleUserHasReadSeqMessages Panic", errs.ErrPanic(r))
		}
	}()
	defer och.wg.Done()
	for msg := range och.conversationUserHasReadChan {
		if err := och.msgTransferDatabase.SetHasReadSeqToDB(ctx, msg.conversationID, msg.userHasReadMap); err != nil {
			log.ZWarn(ctx, "set read seq to db error", err, ...)
		}
	}
}
```

**注意步骤 ④ 和步骤 ⑤ 做的是几乎一样的事：**

| 步骤 | 方法 | 目标 |
|---|---|---|
| ④ | `SetHasReadSeqs` | Redis |
| ⑤ | `SetHasReadSeqToDB`（经 channel） | Mongo |

所以设计意图是：**Redis 同步写（快、重要，用于未读数计算），Mongo 异步写（慢、可容忍延迟，用于持久化）。**

为什么 Mongo 要异步？因为「发送者已读到自己发的最新消息」这件事**不影响消息本身的可靠性**，晚几百毫秒落库完全没关系。

而 channel 缓冲是 1000（`hasReadChanBuffer`），能吸收突发。如果满了，`<-` 会阻塞 `handleMsg`——**又一层背压**。

**这里还有个细节：`HandleUserHasReadSeqMessages` 在 `Start` 里用 `go` 起，但 `Close()` 时会 `close(chan)` + `wg.Wait()`。** 保证了优雅退出时把缓冲里的都写完。

### 11.14.4 步骤 ⑥ 的 `isNewConversation` 是怎么来的

```go
// controller/msg_transfer.go:219
isNew = currentMaxSeq == 0
```

`BatchInsertChat2Cache` 返回的 `currentMaxSeq` 是**分配前的最大 seq**。如果是 0，说明这个会话从来没有消息——这是一个全新的会话。

**为什么需要创建会话记录？**

因为会话列表（`/conversation/get_all`）查的是 conversation 表。如果只写消息不建会话，用户就看不到这个聊天窗口。

单聊和群聊的创建方式不同：

```go
// 单聊：只创建一条记录，但内部会给双方都建（CreateSingleChatConversations 的语义）
req := &pbconv.CreateSingleChatConversationsReq{RecvID:..., SendID:..., ConversationID:..., ConversationType:...}

// 群聊：先拉全部群成员，再批量创建
userIDs, err := och.groupClient.GetGroupMemberUserIDs(ctx, msg.GroupID)
och.conversationClient.CreateGroupChatConversations(ctx, msg.GroupID, userIDs)
```

群聊这里有个**性能隐患**：一个万人群的第一条消息，要拉一万个成员 ID 然后创建一万条会话记录。这是同步在执行（虽然在 worker 里，不阻塞其他会话）。

**这就是「冷启动成本」**：一个从没聊过的大群，第一条消息特别慢。

OpenIM 的取舍是：`if isNewConversation` 才做，所以只有第一次有代价。后续消息都是直接 `SetConversations` 更新。

### 11.14.5 步骤 ⑦ 和 ⑧ 的顺序

```go
err = och.msgTransferDatabase.MsgToMongoMQ(ctx, key, conversationID, storageMessageList, lastSeq)  // 先落库
och.toPushTopic(ctx, key, conversationID, storageList)                                              // 后推送
```

**先投 Mongo，后投 Push。**

为什么是这个顺序？

因为**推送包里要带 seq**，而 seq 已经有了（步骤 ③ 分配的）。所以两者其实互不依赖。

顺序的意义在于**故障时的行为**：

- 如果 toMongo 投递失败，仍然会推送 → 用户看到了消息，但数据库里没有 → 重连后消息消失（"幽灵消息"）
- 如果顺序反过来，推送成功后落库失败，结果一样

所以这个顺序**并不能避免幽灵消息**。真正的保障是：Mongo 投递失败会记 `ZError`（便于告警），而推送是无条件执行的。

更严谨的做法是：**落库成功后再推送**。但那会让推送延迟增加一个 Mongo 写入的时间，违背了「先让用户看到」的体验优先原则。

**这是一个明确的「体验优先于强一致」的取舍。**

## 11.15 toPushTopic：逐条投递的细节

```go
// online_history_msg_handler.go:362-369
func (och *OnlineHistoryRedisConsumerHandler) toPushTopic(ctx context.Context, key, conversationID string, msgs []*ContextMsg) {
	for _, v := range msgs {
		log.ZDebug(ctx, "push msg to topic", "msg", v.message.String())
		if err := och.msgTransferDatabase.MsgToPushMQ(v.ctx, key, conversationID, v.message); err != nil {
			log.ZError(ctx, "msg to push topic error", err, "msg", v.message.String())
		}
	}
}
```

**注意这里是「逐条」而不是「批量」。**

对比 `MsgToMongoMQ`：

```go
// controller/msg_transfer.go:273-285
func (db *msgTransferDatabase) MsgToMongoMQ(ctx context.Context, key, conversationID string, messages []*sdkws.MsgData, lastSeq int64) error {
	if len(messages) > 0 {
		data, err := proto.Marshal(&pbmsg.MsgDataToMongoByMQ{LastSeq: lastSeq, ConversationID: conversationID, MsgData: messages})
		...
		db.producerToMongo.SendMessage(ctx, key, data)
	}
}
```

Mongo 是**一个包带整批消息**，Push 是**一条一个包**。

**为什么不同？**

| 维度 | toMongo | toPush |
|---|---|---|
| 消费者 | msgtransfer 自己 | push 服务 |
| 处理方式 | 批量写一个 Mongo 文档 | 每条独立处理（推送目标不同） |
| 批量的收益 | 大（一次写入覆盖 100 条） | 小（每条消息的接收者不同） |
| 失败影响 | 整批失败要重来 | 单条失败不影响其他 |

推送的本质是「一条消息 → 找出它的接收者 → 推给每个人」。不同消息的接收者完全不同（不同群、不同单聊），**批量没有共享收益**。

而且如果批量推送失败，整批都要重试。逐条推的话，失败只影响一条。

**这是一个很重要的架构判断：批量的前提是「操作可以合并」。** 写同一个文档可以合并，推不同会话的消息不能合并。

还有一个细节：**`v.ctx` 而不是外面的 `ctx`**。

```go
och.msgTransferDatabase.MsgToPushMQ(v.ctx, key, conversationID, v.message)
```

`v.ctx` 是**每条消息自己的 ctx**（在 `parseConsumerMessages` 里从 `consumerMessages[i].Ctx` 取的）。而 `do` 里的 `ctx` 是批处理创建的新 ctx。

用每条消息的 ctx，意味着：**如果某条消息的原始 ctx 已经超时/取消，这条消息的推送会被跳过。** 这是一个「新鲜度」保护——太老的消息不必再推了。

（Kafka 的 `msg.Context()` 返回的 ctx 生命周期由消息本身决定，具体实现要看 `tools/mq` 包。这点标 📌 待验证。）

## 11.16 Mark 与 Commit：位点何时前进

```go
// internal/msgtransfer/online_history_msg_handler.go:105-108
och.redisMessageBatches.OnComplete = func(lastMessage *ConsumerMessage, totalCount int) {
	lastMessage.Raw.Mark()
	lastMessage.Raw.Commit()
}
```

只有两行，但这是**整个可靠性保证的锚点**。

### 11.16.1 Mark 和 Commit 的区别

| 方法 | 含义 |
|---|---|
| `Mark()` | 标记这条消息「已处理」（本地状态，不发给 broker） |
| `Commit()` | 提交位点（告诉 Kafka：我处理到这儿了） |

分两步的原因：Kafka 的自动提交是**周期性的**（比如每 5 秒一次），而 `Mark` 是立刻标记，`Commit` 才是真正推进位点。

### 11.16.2 为什么用 `lastMessage`

因为批处理是「攒了一批」，这一批的位点应该提交到最后一条。**不能提交中间某条**，否则中间之后的会重投。

而 `lastMessage` 正是 `scheduler` 里跟踪的 `lastAny`（该批最后收到的那条）。

### 11.16.3 这个方法在哪被调用

在 `distributeMessage` 的**最后**：

```go
if b.config.syncWait {
	b.counter.Wait()      // 等所有 worker 处理完
}
if b.OnComplete != nil {
	b.OnComplete(lastMessage, totalCount)   // 然后才 Mark+Commit
}
```

**顺序是：全部处理完 → 才提交位点。**

这就是 at-least-once 的实现：**宁可重复，不可遗漏。**

### 11.16.4 但 `do` 里有多个 `return`

回到 11.14.2 节的错误处理：

```go
if err != nil && !errors.Is(errs.Unwrap(err), redis.Nil) {
	log.ZWarn(ctx, "batch data insert to redis err", err, "storageMsgList", storageMessageList)
	return    // ← 提前返回
}
```

这里提前 return 只是退出 `handleMsg`，**`do` 会继续执行 `handleNotification`，然后返回，`counter.Done()` 仍然会被执行，位点仍然前进。**

**所以「Redis 写失败导致 return」并不会导致消息重投——它会被当作「处理成功」提交掉。**

这是一个重要的认知：**`return` ≠ 失败重试。** 在批处理框架里，只有 panic 或者「不调 Done」才能阻止位点前进。

要真正实现「失败重试」，`Do` 必须返回 error，并且 `distributeMessage` 根据 error 决定是否调 `OnComplete`。当前框架没有这个能力。

> **这是本篇最重要的源码结论，也是最适合在面试里说的**：
> 「这个批处理框架的失败语义是缺失的——`Do` 没有返回值，任何业务失败都只能记日志，位点照样前进。要做严格的至少一次，必须让 `Do` 返回 error 并在 `OnComplete` 前判断。我把它列为本项目的改进点之一。」

## 11.17 设计评价

### 11.17.1 做得好的地方

| 设计 | 价值 |
|---|---|
| MQ 抽象层（3 种引擎可切换） | 同一套代码适应从本地开发到生产集群 |
| 逻辑 topic → 真实 topic 映射 | 多环境隔离，代码不感知 |
| 双触发批处理（500 条 / 100ms） | 兼顾吞吐与延迟 |
| 按 key 哈希分片 | 同会话严格保序 |
| `syncWait` + `OnComplete` | 位点不会「撒谎」 |
| 背压链完整（channel 阻塞 → 停止拉取） | 内存不会被打爆 |
| `WithTempAdmin` 标记系统身份 | 特权调用显式化、可审计 |
| 快慢路径分离（先推无 seq 消息） | 打字状态延迟更低 |

### 11.17.2 可以改进的地方

| 问题 | 位置 | 影响 | 建议 |
|---|---|---|---|
| `Subscribe` 外的 `for {}` 是死代码 | `init.go:117-125` | 消费异常直接退出，无重连 | 改为 `continue` + 指数退避 |
| `HandleChatWs2Mongo` 吞掉错误 | `init.go:128-131` | 落库失败仍提交位点，消息丢 | 改为返回 error |
| `Do` 无返回值，失败无法重试 | `batcher.go:272` | 业务失败被当作成功 | 让 `Do` 返回 error |
| worker 无 panic 保护 | `batcher.go:263-278` | 一条畸形消息崩整个进程 | `defer recover()` + 保证 `Done` |
| `Put` 失败只记日志仍返回 nil | `online_history_msg_handler.go:385-391` | 缓冲满时消息丢 | 返回 error |
| Redis 写失败直接 return，不落 Mongo | `online_history_msg_handler.go:254-257` | 缓存故障导致消息丢失 | Redis 失败也继续投 toMongo |
| 就地篡改 `v.message.Options` | `online_history_msg_handler.go:213-217` | 副作用可能影响后续使用 | 克隆两份都不动原对象 |
| 取模分片不支持动态扩缩容 | `online_history_msg_handler.go:95-98` | worker 数变化会乱序 | 上一致性哈希 |
| seq 分配不幂等 | `msg_transfer.go:214` | 重复消费产生重复 seq | 维护 ClientMsgID→seq 映射 |
| operationID 拼接过长 | `online_history_msg_handler.go:371-383` | 日志体积膨胀 | 改为批次 ID + 首条 ID |

**这 10 条里有 6 条是「可靠性缺口」**，都值得在面试里主动说。能指出这些问题，比背架构图有说服力得多。

### 11.17.3 一个必须理解的整体图景

最后用一张表把四个 topic 的职责钉死：

| Topic | 归属阶段 | 输入 | 输出 | 失败后果 |
|---|---|---|---|---|
| `toRedis` | 中转 | `MsgData`（pb） | 分配 seq、写 Redis、建会话、投 toMongo/toPush | 消息丢失（发送端已返回成功） |
| `toMongo` | 落库 | `MsgDataToMongoByMQ`（含 lastSeq） | Mongo 文档 | 消息在 Redis 有、Mongo 无 → 重启后消失 |
| `toPush` | 推送 | `PushMsgDataToMQ`（含 conversationID） | 在线推送 / 触发离线推送 | 用户收不到推送，重连后可拉到 |
| `toOfflinePush` | 离线 | 用户 ID 列表 + 消息 | 厂商通道推送 | 手机不弹通知，App 内仍可见 |

**这四个阶段的重要性是递减的**：

- `toRedis` 失败 = 消息彻底丢失（最严重）
- `toMongo` 失败 = 消息短暂可见后消失（严重）
- `toPush` 失败 = 实时性受损（可接受）
- `toOfflinePush` 失败 = 通知缺失（最轻）

**所以监控的优先级应该和这个顺序一致。** 这是从架构推导运维策略的方法。

## 实验 1：看四个 topic 真实存在

```bash
docker ps --format '{{.Names}}' | grep kafka
# 假设容器名 kafka

docker exec -it <kafka容器> kafka-topics.sh --bootstrap-server localhost:9092 --list
```

**预期现象**：能看到 `toRedis`、`toMongo`、`toPush`、`toOfflinePush` 四个（具体名字取决于 `config/kafka.yml`）。

**再查分区数**：

```bash
docker exec -it <kafka容器> kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic toRedis
```

**预期现象**：能看到 PartitionCount 和每个 partition 的 leader/replicas。单机部署通常只有 1 个 partition——**这意味着这个环境里的「分区保序」其实是靠「只有一个分区」天然实现的**，多分区下的行为需要集群才能验证。

## 实验 2：观察消费组位点

```bash
docker exec -it <kafka容器> kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group redis
```

**预期现象**：

```
GROUP  TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
redis  toRedis  0          1234            1234            0
```

`LAG` 是**积压量** = 生产位置 - 消费位置。这是最重要的监控指标：

- LAG 持续为 0：处理能力足够
- LAG 持续增长：消费跟不上，要么加实例要么查下游

**动手做**：发 100 条消息，立刻再执行一次，你能看到 LAG 短暂跳一下然后归零。

## 实验 3：验证批处理真的在攒批

**目的**：确认「100ms 或 500 条」的双触发。

**方法**：快速发 200 条消息，然后看 msgtransfer 的日志（`_output/logs/msgtransfer.log`），搜索 `msg arrived channel`，看每次的 `msgList length`。

**预期现象**：

- 如果发得很快：能看到 length 接近 200 的大批次
- 如果一条一条慢慢发（间隔 > 100ms）：每条都是一个独立批次，length=1

**这直接验证了 ticker 兜底的存在。**

## 实验 4：验证同会话保序

**目的**：同一会话大量消息，seq 必须连续。

```bash
# 并发发 50 条到同一个会话
seq 1 50 | xargs -P 20 -I{} curl -s -o /dev/null -X POST "http://127.0.0.1:10002/msg/send_msg" \
  -H "Content-Type: application/json" -H "token: $ADMIN_TOKEN" -H "operationID: order-{}" \
  -d '{"sendID":"imAdmin","recvID":"userA","sessionType":1,"contentType":101,"content":{"content":"order-{}"}}'
```

然后查 Mongo 里该会话的 seq 序列，检查是否连续：

```bash
docker exec -i <mongo> mongosh --quiet ... im_v3 --eval '
db.msg.find({"doc_id": /si_/}).forEach(d => {
  d.msgs.filter(m=>m.msg).forEach(m => print(m.msg.seq))
})' | sort -n | awk 'NR>1 && $1!=prev+1 {print "GAP after", prev, "next", $1} {prev=$1} END {print "total", NR}'
```

**预期现象**：没有 GAP 输出，total = 50（或更多，如果之前有消息）。

**如果出现 GAP**：说明 seq 分配有空洞。正常情况下不应该有——因为 `Malloc` 是原子的。**空洞只可能来自「分配了但没写成功」**（见第 12 篇）。

## 实验 5：模拟 Redis 不可用，看消息是否丢

**这是一个破坏性实验，做完记得恢复。**

```bash
docker stop <redis容器>
# 发一条消息，观察返回
# 然后恢复
docker start <redis容器>
```

**预期现象**：

- 发送接口**仍然返回成功**（因为发送只写 Kafka，不碰 Redis）
- msgtransfer 日志里出现 `batch data insert to redis err`
- 消息**没有落进 Mongo**（因为 11.14.2 节的 `return`）

**这个实验能直观验证本篇指出的可靠性缺口。** 想更严谨的话，可以在恢复 Redis 后查 Mongo 确认消息确实丢了。

## 实验 6：切换 MQ 引擎

**目的**：验证 MQ 抽象层真的可替换。

改 `config/share.yml`：

```yaml
queue: redis
```

然后 `mage stop && mage start`，观察服务能否正常收发消息。

**预期现象**：功能正常，但 Kafka 的 `toRedis` 等 topic 不再被使用，改走 Redis Stream（key 前缀 `mq:`）。

**注意**：切换引擎后消费组位点的语义会变（Redis Stream 用消费者组 + 消息 ID），但上层代码零改动——这就是抽象层的价值。

# 面试话术

## 30 秒版本

> 消息从 msg 服务投进 Kafka 的 `toRedis` topic，msgtransfer 消费后做三件事：分配会话内 seq 并写 Redis、投 `toMongo` 落库、投 `toPush` 推送。
>
> 消费端用了批处理框架：攒够 500 条或等满 100ms 就处理一批，按会话 key 哈希分片到 50 个 worker，保证同会话的消息永远由同一个 worker 顺序处理。一批全部处理完才提交 Kafka 位点，所以是 at-least-once。

## 3 分钟版本

在 30 秒基础上按这个顺序展开：

1. **为什么要 MQ**：削峰、故障隔离、可重放。关键是把「十毫秒级的 Mongo 写」从同步路径上摘掉，避免 Mongo 抖动直接传导成发送接口超时。
2. **四个 topic 是一条流水线**：toRedis（分配 seq）→ toMongo（落库）+ toPush（推送）→ toOfflinePush（厂商通道）。四个阶段的重要性递减，监控优先级也应该递减。
3. **保序的三层防线**：Kafka 用会话 key 做分区键 → 内存 hash(key)%worker 分片 → 一批同 key 消息作为一个单位投给 worker。三层缺一不可。
4. **批处理的双触发**：500 条 或 100ms，前者保吞吐，后者保低峰期延迟。
5. **背压链**：worker 慢 → 分片 channel 满 → scheduler 阻塞 → data chan 满 → Kafka 停止拉取 → 压力落到 broker 磁盘而不是内存。
6. **主动说出缺陷**（最能体现你真读过代码）：
   - `Do` 没有返回值，业务失败只能记日志，位点照样前进 → 失败语义缺失
   - `HandleChatWs2Mongo` 吞错误，落库失败也提交位点
   - `Subscribe` 外的 `for {}` 是死代码，消费异常直接退出不重连
   - Redis 写失败直接 return，跳过了 toMongo 投递

## 预判追问与答法

**Q：Kafka 的 partition 数量怎么定？**
A：上限由消费并行度决定——一个 partition 只能被一个消费者消费，所以要 ≥ 期望的消费者数。但也不能太多，因为 partition 增加会破坏 key→partition 的映射，导致短时间乱序；同时 partition 数影响 broker 的文件句柄和选举开销。经验值是「峰值吞吐 / 单分区吞吐」再留一倍余量，且尽量在业务上线前定好，避免中途扩。

**Q：Rebalance 会带来什么问题？**
A：Rebalance 期间整个消费组暂停消费（Stop-The-World）。如果频繁触发，消费会反复卡顿、LAG 飙升。常见触发原因是消费者处理太慢导致心跳超时或 `max.poll.interval.ms` 超时。所以批处理参数不能定得太大，单批处理时间要远小于 `max.poll.interval.ms`。

**Q：批处理会不会导致消息延迟？**
A：会，最坏多等一个 interval（100ms）。这是有意用延迟换吞吐。但即使不批处理，网络往返和 Redis/Mongo 的单次开销也不小，实际端到端延迟差异远小于 100ms——因为批处理同时把 N 次写操作合并成了一次。

**Q：为什么不用 RabbitMQ？**
A：这个项目对「顺序」和「吞吐」的要求更高，Kafka 的分区保序 + 高吞吐更合适。RabbitMQ 的强项是复杂路由和低延迟（毫秒级），但单队列吞吐和堆积能力不如 Kafka。而且 Kafka 支持位点重置重放，运维上更灵活。另外项目做了 MQ 抽象层，理论上也能接 RabbitMQ。

**Q：at-least-once 意味着重复，重复消息怎么处理？**
A：每个写入点都要幂等。Redis 消息缓存以 seq 为 hash field，重复写就是覆盖；Mongo 用「先 update 命中则跳过，未命中才 insert，insert 撞唯一索引转 update」；客户端按 ClientMsgID 去重。但我要诚实说一点：**seq 分配本身不幂等**——重复消费会分配新的 seq，产生内容重复但 seq 不同的两条消息。这是这个项目的一个弱点。

**Q：如果 Kafka 挂了怎么办？**
A：发送接口会立刻失败（`SendMessage` 返回错误），用户看到发送失败可以重试——这比「假装成功然后丢消息」好。但如果是消费端挂了而生产端正常，消息会在 Kafka 里堆积，恢复后继续消费，不会丢。所以关键是要监控 LAG。
